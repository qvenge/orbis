# Шаблон промпта оркестратора исполнения плана

Как пользоваться: заполнить `{{плейсхолдеры}}`, готовый экземпляр положить в леджер среза
(`.superpowers/sdd/<дата>-<срез>/orchestrator-prompt.md`) и отдать агенту-оркестратору.
Шаблон под срез не редактировать — улучшения ехать сюда отдельным docs-коммитом, чтобы
следующий срез их унаследовал. Промпт не повторяет план: порядок задач, ограничения,
модели сабагентов и протокол мержа живут в плане, здесь — только оркестровка. Правка 27.09.2026:
гейт и финальное ревью — Opus 5.5 (Fable 5.1 — второй линзой), мерж в main — один раз готовым срезом
вместе с владельцем, прод — только с владельцем (было: гейт fable и ff-мерж после каждой задачи).

---

```
Исполни план {{название среза}} в {{абсолютный путь к репозиторию}}.

ИСТОЧНИК ИСТИНЫ
{{путь к плану}} (main {{хеш}} или новее).
Прочитай целиком до первого действия. Порядок задач, параллельность, глобальные
ограничения, состав брифов, модели сабагентов и протокол коммита/мержа — В ПЛАНЕ;
исполняй как написано, не переопределяй. Метод — superpowers:subagent-driven-development
(назван в шапке плана). Спеку и ревью не редактируй.

Начни с Задачи {{номер первой задачи}}. {{«Сейчас, ответов владельца не жди» | условие старта}}.

ПОЛИТИКА ОТКЛОНЕНИЙ
- Факты плана опровергаемы. Опровержение пробоем: точечно поправь план (docs-коммит,
  причина в сообщении), рулинг — в facts.md леджера, продолжай.
- {{Вопросы владельцу В-…}} исполняй по умолчаниям плана. Ответ владельца «не по
  умолчанию» в ходе работы — точечная правка плана ДО старта задетой задачи.
- Решай сам и записывай рулинг. Стоп и вопрос владельцу только если: блокер противоречит
  решению спеки или рулингу её ревью; опровергнут факт, на котором стоят две и более
  задач; требуется прод-операция вне чек-листа деплой-задачи плана.

РЕВЬЮ-ПАКЕТ (перед каждым гейтом; ревьюеру — push только пакет, pull всё остальное)
Собери {{путь к леджеру}}/review-pack-task-N.md:
(1) git diff --stat <sha-до-задачи>..HEAD и путь к task-N.diff
    (git diff -U15; при диффе >2000 строк — -U8);
(2) текст задачи N из плана + её строки маппинга приёмки и инвариантов;
(3) 5–15 релевантных фактов из facts.md / recon-* (отбираешь ты, по области задачи);
(4) хвост bun run test со счётчиками и кодом возврата (ревьюер полный сьют не гоняет,
    точечные прогоны — можно).
Ревьюеру передавай ТОЛЬКО пакет и строку «источники для пробоя: <пути к спеке, плану,
конспектам>». В промпте ревьюера обязательно:
- «дифф — карта, не доказательство: каждое сомнение пробивай чтением файлов в worktree»;
- «перечисли, что ДОЛЖНО было измениться при этом брифе, но в диффе НЕ изменилось:
  вызыватели, пересборщики, тесты, документы» (главные дефекты прошлых ревью лежали
  вне диффа);
- «вердикт — APPROVE либо находки Critical/Important/Minor, каждая файл:строка +
  сценарий провала; без пересказа диффа».
Ре-ревью после фиксов — тот же ревьюер, возобновлённый (нового не заводи): тот же пакет +
дельта-дифф фикса + список находок с пометками «что сделано».

ГЕЙТЫ И УЧЁТ
- Сабагенты — не ниже Opus 5 (model: opus); sonnet и haiku — никогда; ID модели сверяй по
  ответу сабагента и пиши в progress.md.
- Задача закрыта = зелёные bun run test / lint / typecheck + гейт-ревью Opus 5.5 (model: opus;
  соответствие брифу И качество кода; вторая линза Fable 5.1, model: fable, — по плану или
  по твоему усмотрению) + коммит в ветке среза + пуш ветки ради CI и зелёный CI.
  Critical/Important из ревью — фикс до закрытия задачи, не «потом». В main после задачи
  НЕ мержим: мерж — один раз, готовым срезом, в прод-задаче вместе с владельцем.
- После каждой задачи — запись в progress.md: хеш коммита, счётчики сьютов, рулинги,
  и УЧЁТ РЕВЬЮ: размер пакета (строк диффа / байт), расход ревью-агента (токены из
  результата диспатча), находки по севиритям и их исход (подтверждена-исправлена /
  отклонена пробоем). После Задачи {{номер контрольной задачи}} сведи промежуточный
  итог: находки стабильны, расход упал? — если нет, скажи об этом владельцу, не молчи.
- Между задачами держи свой контекст пустым от чужой работы: всё тяжёлое — сабагентам,
  себе — вердикты и рулинги.

ЖЁСТКАЯ ОСТАНОВКА перед прод-задачей плана: мерж в main, пересев, деплой, перевод данных и
живая приёмка — только отдельным словом владельца и вместе с ним. Пуш main — только по его
команде.

ГОТОВО (до прод-задачи) = Задачи {{диапазон}} закрыты в ветке, приёмка {{диапазон приёмки}}
пройдена, финальное ревью ветки — Opus 5.5 APPROVE (Fable 5.1 — второй линзой), фикс-волна
закрыта, progress.md — итоговая запись (включая сводку учёта ревью по всем задачам) и доклад
владельцу. Прод-задача — отдельным словом.
```
