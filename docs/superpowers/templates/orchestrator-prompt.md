# Шаблон промпта оркестратора исполнения плана

Как пользоваться: заполнить `{{плейсхолдеры}}`, готовый экземпляр положить в леджер среза
(`.superpowers/sdd/<дата>-<срез>/orchestrator-prompt.md`) и отдать агенту-оркестратору.
Шаблон под срез не редактировать — улучшения ехать сюда отдельным docs-коммитом, чтобы
следующий срез их унаследовал. Промпт не повторяет план: порядок задач, ограничения,
модели сабагентов и протокол коммита живут в плане, здесь — только оркестровка. Правка 27.09.2026:
гейт и финальное ревью — Opus 5.5 (Fable 5.1 — второй линзой), мерж в main — один раз готовым срезом
вместе с владельцем, прод — только с владельцем (было: гейт fable и ff-мерж после каждой задачи).
Вторая правка 27.09.2026 (по промпту среза 1б): остановка перед финальным ревью, лог решений
`rulings.md`, адресная вторая линза Fable, судьба мелких находок, бриф имплементеру, экономия без
потери качества, передача каждые N задач, особые условия остановки плана, main пушится только
готовым срезом, автодеплой Render не выключается.

---

```
Исполни план {{название среза}} в {{абсолютный путь к репозиторию}}.

ИСТОЧНИК ИСТИНЫ
{{путь к плану}} (main {{хеш}} или новее).
Прочитай целиком до первого действия. Порядок задач, параллельность, глобальные
ограничения, состав брифов, модели сабагентов и протокол коммита — В ПЛАНЕ;
исполняй как написано, не переопределяй. Метод — superpowers:subagent-driven-development
(назван в шапке плана). Спеку, её ревью и выполненные спеки прежних срезов не редактируй.
Леджер ($L) — {{путь к леджеру}}: факты и рулинги плана, разведка, отчёты ревью плана.

Начни с Задачи {{номер первой задачи}}. {{«Сейчас, ответов владельца не жди» | условие старта}}.

ЭТАПЫ И ОСТАНОВКИ (перед каждым тяжёлым этапом — отдельное слово владельца)
- Задачи {{первая}}–{{последняя до финального ревью}} — подряд, без пауз между задачами.
- Перед финальным ревью ветки (Задача {{номер}}) — остановка: короткий доклад и вопрос
  владельцу «начинать финальное ревью?». Финальное ревью — его словом.
- После финального ревью — ЖЁСТКАЯ ОСТАНОВКА перед прод-задачей (ниже).

ПОЛИТИКА ОТКЛОНЕНИЙ
- Факты плана опровергаемы. Опровержение пробоем: точечно поправь план (docs-коммит в
  ветке, причина в сообщении), запись — в rulings.md, продолжай. Факты плана и леджера
  без сомнения не переразведывай.
- {{Вопросы владельцу В-…}} исполняй по умолчаниям плана. Ответ владельца «не по
  умолчанию» в ходе работы — точечная правка плана ДО старта задетой задачи.
- Спорное решай сам, не останавливаясь, и пиши в лог решений. Стоп и вопрос владельцу
  только если: блокер противоречит спеке или решению владельца; опровергнут факт, на
  котором стоят две и более задач; требуется прод-операция вне прод-задачи плана{{; особые
  условия остановки плана — например «нужна миграция БД»}}.

ЛОГ РЕШЕНИЙ — $L/rulings.md, строка на решение:
`R-N | дата время | задача | вопрос | решение | почему (факт, адрес) | цена, если неверно | обратимо?`
Туда же — опровергнутые факты плана и точечные правки плана. Из него собирается итоговый доклад.

КТО ЧТО ДЕЛАЕТ
- Сабагенты — только самый последний Opus (сейчас Opus 5.5, model: opus); ID модели сверяй по
  ответу сабагента и пиши в progress.md — ниже последнего Opus результат не принимается;
  sonnet и haiku — никогда. Fable 5.1 (model: fable) — только вторая линза ревью.
- Имплементер — один в дереве. Бриф = текст задачи из плана + 5–15 фактов леджера,
  которые отобрал ты; «прочитай всё» не поручай.
- Гейт задачи — Opus 5.5: соответствие брифу И качество кода.
- Вторая линза Fable 5.1 — параллельно с гейтом, адресно: задачи {{список задач, где нужен
  иной взгляд}} и финальное ревью. Её фокус — сквозные оси, цельность замысла, расхождения
  со спекой и решениями владельца; кодовые мелочи — дело гейта.
- Ре-ревью после фиксов — тот же ревьюер, возобновлённый (нового не заводи).
- Ты сам: собираешь пакеты, проверяешь каждую находку пробоем по коду, правишь текст (план,
  докблоки, документы), ведёшь учёт. Новый код пишут агенты.

РЕВЬЮ-ПАКЕТ (перед каждым гейтом; ревьюеру — push только пакет, pull всё остальное)
Собери $L/review-pack-task-N.md:
(1) git diff --stat <sha-до-задачи>..HEAD и путь к task-N.diff
    (git diff -U15; при диффе >2000 строк — -U8);
(2) текст задачи N из плана + её строки маппинга приёмки и инвариантов;
(3) 5–15 релевантных фактов из леджера (отбираешь ты, по области задачи);
(4) хвост bun run test со счётчиками и кодом возврата (ревьюер полный сьют не гоняет,
    точечные прогоны — можно).
Ревьюеру передавай ТОЛЬКО пакет и строку «источники для пробоя: <пути к спеке, плану,
конспектам>». В промпте ревьюера обязательно:
- «дифф — карта, не доказательство: каждое сомнение пробивай чтением файлов в worktree»;
- «перечисли, что ДОЛЖНО было измениться при этом брифе, но в диффе НЕ изменилось:
  вызыватели, пересборщики, тесты, документы» (главные дефекты прошлых ревью лежали
  вне диффа);
- «вердикт — APPROVE либо находки Critical/Important/Minor, каждая файл:строка +
  сценарий провала; без пересказа диффа».
Ре-ревью получает тот же пакет + дельта-дифф фикса + список находок с пометками «что сделано».

ЗАКРЫТИЕ ЗАДАЧИ
Задача закрыта = зелёные bun run test / lint / typecheck и сторожа задачи + гейт APPROVE
(и Fable, где назначена) + коммит в ветке среза + пуш ветки ради CI и зелёный CI.
Critical/Important — фикс до закрытия задачи, не «потом». Minor: дёшево — в тот же фикс;
иначе — строка `minor (deferred)` в progress.md с адресом. Ложную находку отклони пробоем и
запиши.

MAIN И ДЕПЛОЙ
- В main до прод-задачи ничего не мержим и не пушим: main пушится один раз — готовым срезом,
  в прод-задаче, вместе с владельцем. Пуш ветки среза ради CI — можно всегда.
- Автодеплой Render НЕ выключать: порядок «данные до кода» держит прод-задача (пересев →
  пуш в main → автодеплой выкатывает сам). Ручной деплой из main на время среза запрещён.

ТОКЕНЫ — экономь, качество не трогай
- Своё окно держи пустым от чужой работы: дифы, логи и файлы читают агенты; тебе — вердикты,
  числа, рулинги. Вывод прогонов — в файл.
- Параллельно — только гейт и Fable одной задачи; агентов, читающих одни и те же файлы,
  одновременно не запускай.
- НЕ экономь на: гейте каждой задачи, мутационных проверках, полном прогоне перед закрытием,
  фиксе Important.

УЧЁТ
- После каждой задачи — запись в progress.md: хеш коммита, счётчики сьютов, ID моделей
  сабагентов, номера решений из rulings.md и УЧЁТ РЕВЬЮ: размер пакета (строк диффа / байт),
  расход ревью-агентов (токены из результата диспатча), находки по севиритям и их исход
  (подтверждена-исправлена / отклонена пробоем).
- Каждые {{N, обычно 5}} задач и перед каждой остановкой — $L/handoff-exec-<N>.md: HEAD, что
  закрыто, открытые хвосты, что дальше — чтобы другая сессия продолжила без пересказа.
- После Задачи {{номер контрольной задачи}} сведи промежуточный итог: находки стабильны,
  расход упал? — если нет, скажи об этом владельцу, не молчи.

ЖЁСТКАЯ ОСТАНОВКА перед прод-задачей плана: пересев, пуш main, деплой, перевод данных и
живая приёмка — только отдельным словом владельца и вместе с ним.

ГОТОВО (до прод-задачи) = Задачи {{диапазон}} закрыты в ветке, приёмка {{диапазон приёмки}}
пройдена, финальное ревью ветки — Opus 5.5 APPROVE (Fable 5.1 — второй линзой), фикс-волна
закрыта, progress.md (включая сводку учёта ревью по всем задачам) и rulings.md сведены.
Доклад владельцу простыми словами: что сделано; все решения с ценой (из rulings.md); вопросы
владельцу; счёт ревью и расход. Прод-задача — отдельным словом.
```
