## Что это

No-code платформа «база → таблицы → типизированные поля → записи». Запись принадлежит одной таблице, схема — у таблицы. Поверх:

- **Виды над таблицей:** grid, kanban, calendar, gallery, timeline / gantt, form, list. Вид хранит фильтр, сортировку, группировку, видимость полей.
- **Interfaces:** страницы из элементов (списки, графики, формы, кнопки), привязанных к данным; права на интерфейс; порталы для внешних людей.
- **Automations:** триггер (запись создана / изменена / попала под условие, форма отправлена, расписание, вебхук) → действия (правка записи, письмо, Slack, скрипт, AI-шаг).
- **AI:** AI-поля (сгенерировать, классифицировать, резюмировать по полям записи), Cobuilder и Omni — сборка базы и интерфейса из описания словами, разговор с данными. Платится кредитами.
- **Расширения:** extensions, scripting на JS, marketplace, шаблоны баз.
- **Связность наружу:** sync между базами и с внешними системами, REST API, webhooks.
- **Аудитория и деньги:** команды и бизнес-процессы; цена за место плюс AI-кредиты; бесплатный план ограничен числом записей на базу.

## Для чего команды его используют

Там, где таблица в Excel / Google Sheets переросла себя: данным нужны связи, несколько представлений, формы и автоматизации, а программистов под это не дают. Типичные сценарии:

| Сценарий | Что внутри |
|---|---|
| Контент и маркетинг | редакционный календарь, кампании, согласования, библиотека ассетов с вложениями; одна таблица — календарём редактору, канбаном дизайнеру, списком руководителю |
| Продукт | роадмап, запросы фич, баги, репозиторий исследований, чек-листы запусков; часто прослойка между Jira и стейкхолдерами |
| Проекты и программы | задачи, сроки, timeline / gantt, загрузка людей, портфель проектов |
| Лёгкий CRM | лиды, сделки по стадиям, контакты — до перехода на HubSpot / Salesforce |
| Операции | инвентарь, поставщики, заказы, закупки, мероприятия |
| Найм и HR | воронка кандидатов от формы до оффера, онбординг, справочник сотрудников |
| Приём заявок | форма создаёт запись, автоматизация назначает исполнителя и пишет в Slack |
| Каталоги и базы знаний | товары, конкуренты, медиатека, оборудование |
| Порталы и дашборды | экран под роль: заказчику — его заявка, руководителю — сводка |

Почему именно он: закрывает пустоту между таблицей и настоящим приложением — отдел строит себе инструмент сам за день. Где его не используют: тяжёлые транзакционные системы, бухгалтерия, аналитические хранилища, личные заметки; лимиты записей и цена за место отсекают большие объёмы и большие команды.

## Что общего с Orbis по докам

| Общее | Airtable | Orbis |
|---|---|---|
| Данные первичны, экраны — линзы | таблица переживает любой вид | «данные существуют до приложений»; выключил приложение — записи читаемы |
| Типизированный словарь | поля с типами, linked record, lookup, rollup | реестр свойств с закрытым словарём kind, `ref`, `deref` глубины 1, вычисляемые величины ведомостей |
| Формулы | formula field | язык E — тотальные выражения без циклов и IO |
| Экраны из деклараций | Interfaces: элементы над данными | страницы из блоков; блок = подписка + форма показа, данных не содержит; рендер детерминированный |
| Автоматизации | триггер по условию + действия | правила каталога с `when` на E, действия-рецепты, рутины |
| AI собирает приложение по просьбе | Cobuilder / Omni | агент собирает страницу один раз, результат — артефакт; AI платно у обоих |
| Расширения и рынок | extensions, scripting, шаблоны | приложения из семи элементов, ярус 2 в песочнице, эталон при копировании |
| Внешний API | REST, webhooks | MCP с грантами |

Ориентир: по модели данных Orbis ближе к Tana, по страницам — к Notion, а с Airtable сходится в слое приложений и автоматизаций.

## Чем отличаются

| Ось | Airtable | Orbis по доке |
|---|---|---|
| Единица данных | запись в одной таблице | запись без типа, аспекты складываются, свойства независимы от аспектов |
| Одна вещь в нескольких ролях | две записи и связь | одна запись с task + financial + schedule |
| Связь экрана с данными | вид растёт из таблицы | блок подписан на контракт («когда», «движение денег») |
| Связи | linked record, смысл — в названии поля | роли рёбер с ограничениями как данные |
| Границы данных | база — силос, между базами sync-копии | один граф на владельца (после D44 — на граф) |
| Ввод | сетка, формы, импорт, API | fast-path без LLM, чат, quick-add, CSV; режим не выбирают |
| Текст | long text как поле | тело записи — документ; страница — запись, её схема — её тело |
| Запросы | фильтры вида, formula, `filterByFormula` | один канон Q-AST на списки, блоки, цели, тулы AI |
| AI | функция: поле, Omni, шаг автоматизации | участник графа: журнал с атрибуцией, Undo, уровень по риску, классификатор делегирования, рутины, внешние агенты |
| Обратимость | история ревизий, снапшоты; автоматизации не откатываются | каждое действие в журнале с обратной операцией |
| Кто пользуется | команда с ролями | один владелец и его агенты (ступени 2–3 — D44) |
| Деньги | место + AI-кредиты | захват бесплатно, понимание и AI платно (D36) |
| Выход на рынок | один горизонтальный продукт | констелляция вертикальных приложений |
| Схема | данные, привязанные к базе | реестры с дельтами, выключаемые модули, `proposed`, садовник |

## Сильные и слабые стороны

**Где Airtable сильнее:** зрелость, экосистема, интеграции и sync, корпоративная безопасность; совместная работа с правами до поля и порталами; сетка как универсальный интерфейс с массовыми правками; шире типы полей (вложения, кнопка, пользователь, штрихкод, рейтинг); AI-сборка приложений уже у пользователей.

**Где Orbis сильнее (по доке):** аспекты вместо таблиц и жест «навесь аспект»; контракты и подписки — новый домен строками реестров; ввод без формы с извлечением структуры; AI как правая рука под наблюдаемостью, откатом и замками; прозрачность и обратимость в ядре; данные принадлежат владельцу, экспорт всегда, П0 даёт заменить встроенное приложение; один граф на всю жизнь и кросс-доменные вопросы.

**Слабости Orbis, которых у Airtable нет:** продукт в большой части — описание; порог понятийной модели выше таблицы и поля; нет коллаборации, офлайна, вложений, внешних синков кроме CSV; экономика AI не измерена; производительность на объёмах не доказана.

## Что мешает использовать Orbis под командные сценарии (кроме общего доступа)

Первый ответ называл шесть препятствий; в ходе разговора три из них были **уточнены или сняты** — ниже итоговая редакция.

| Препятствие | Итоговая оценка |
|---|---|
| Нет файлов (вложений нет в закрытом словаре §А2-2) | **снято как концептуальное:** вложения планируются (рулинг Р-Г-5, 19.09). Остаётся кандидатом на решение |
| Массовая табличная работа | **не ограничение ядра, а не спроектированная поверхность.** В ядре есть пакетное исполнение, создание тулом, импорт с провенансом (`entity_origins`), типизированный реестр (сопоставление колонок выводится само), правило «пачка — одна строка журнала и один откат». Нет: общего импорта файла в аспект, таблицы-блока с правкой в ячейках и по колонке, вставки из таблицы. Правило «одно намерение — одна запись» относится к пути модели, не к импорту; кап на сто — ручка политики пачек агента |
| Объёмы | **не доказаны, не запрещены.** Раскладка: `props jsonb`; фильтры по диапазону и сортировки по сумме и дате хотят btree-индекс на свойство; реестр уже знает, по чему фильтруют, и умеет `storage: core` — индексы из реестра и типизированные проекции горячих свойств были бы продолжением, не перепроектированием. **Поправка, найденная позже:** по D43 (`01-architecture` §4.10, «честная оговорка про GIN») под ролью приложения планировщик **не выбирает ни один GIN на `entities`** из-за security qual RLS и non-leakproof операторов — 44 мс против 0,5 мс на 50 000 строк; фраза первого ответа «GIN хорош для равенства» для прода неверна. Подписки компилируются в SQL из нескольких ведомостей (проба P2: наивный план взрывается на скромных данных) — перф-гейт обязан оставаться. Агенту над большим графом нужен поиск по смыслу (эмбеддинги — Future). Планка невысока: сам Airtable ограничивает базу десятками–сотнями тысяч записей |
| Внешние эффекты только через AI | **интеграции планируются (Р-Г-5), но внутри сидит решение:** действия собираются из графовых тулов без IO (§Б6-3), E без IO, входящих вебхуков нет. Детерминированный внешний шаг (вебхук, письмо, Slack) требует нового вида шага с паттерном «намерение до внешнего эффекта» (разбор T3 Code, И2) и замком «внешнее» — иначе «интеграция» значит «рутина с моделью за деньги» |
| Формулы не колонки | держится: вычисляемые величины живут в ведомостях подписок и каталоге правил (рост по правилу «форма дважды»); вычисляемое свойство по произвольной формуле в каталоге v1 одно — `nearest_ancestor` |
| Бизнес-модель смотрит в другую сторону | держится частично: D36 — вертикальные приложения для жизни; рулингом Р-Г-1 (19.09) добавлен параллельный B2B-канал на том же ядре |

Вынесенное за скобки «общий доступ, роли» оказалось не недостающей функцией, а осью дизайна («граф принадлежит человеку, а не организации») — из этого выросло D44.

## Где Orbis подошёл бы лучше Airtable

- **Одна вещь в нескольких ролях:** запуск или мероприятие — одна запись с задачей, временем и деньгами, а не три таблицы со связями.
- **Разнородное на одном экране:** календарь по контракту «когда» показывает интервью, дедлайны и платежи вместе.
- **Знание вперемешку со структурой:** репозиторий исследований, разбор конкурентов, заметки по клиентам — тело-документ, живые запросы, обратные ссылки, извлечение свойств.
- **Бизнес одного человека:** клиенты, счета, задачи, календарь и личные финансы в одном графе; вопрос «могу ли взять проект по деньгам и времени».
- **Работа, которую делают агенты:** контент-конвейер, мониторинг метрик, недельные обзоры, код через Claude Code — AI как участник с журналом, откатом и уровнями.
- **Трекер, который меняет форму:** хобби → подработка → бизнес через «навесь аспект», без перестройки таблиц.

## Где Orbis не подходит совсем

- операции с объёмами и вложениями: инвентарь, каталоги, закупки, обработка заказов;
- конвейеры заявок от посторонних: форма на сайте, маршрутизация, SLA, уведомления исполнителям, портал заказчику;
- медиатеки и подбор персонала (ядро сценария — вложения и переписка с внешними людьми);
- команды, которым AI запрещён или не нужен: без AI Orbis — медленный Airtable без сетки;
- ~~данные, которые должны пережить владельца~~ — **снимается направлением D44:** граф компании передаётся сменой держателей гранта владельца (ступени 2–3 ещё не построены).

## Что не берём

Таблицу как единицу данных; базы-силосы с sync-копиями; цену за место; Interfaces как непрозрачную конфигурацию (у нас тело страницы — текст, версионируемый и диффуемый); AI как поле без журнала и отката.

## Что из разбора выросло

Вопрос владельца 19.09 «а что если Orbis — каркас, на котором собирается хоть личный ассистент, хоть корпоративная среда типа Airtable» → рулинги Р-Г-1 (продаётся готовый продукт, который агент пересобирает под покупателя; B2C и B2B на одном ядре) и Р-Г-2 («работа рядом с жизнью») → вопрос о принципале → D44 «граф как единица владения». Весь ход и реестры двух ревью — в спеке `specs/2026-09-19-graph-ownership-unit-design.md`.

## Опровергаемые утверждения этого разбора

Сторона Airtable не снималась с первоисточников. До решений, опирающихся на этот текст, перепроверить:

1. возможности Omni и Cobuilder на сегодня (что именно собирается из описания: база, интерфейс, автоматизации);
2. утверждение «вид и элемент интерфейса растут из одной таблицы» — не появились ли элементы с несколькими источниками;
3. лимиты записей на базу по планам и цену места;
4. «автоматизации не откатываются» и состав истории ревизий;
5. наличие у Airtable собственных агентов с идентичностью, журналом и политикой подтверждений — если появились, строка «AI — функция» устарела;
6. состав типов полей и порталы для внешних пользователей.

Сторона Orbis: числа и адреса — на дату разговора; раскладка хранения и владения изменилась срезом «Г» (колонка `graph_id`, RLS через членство) — утверждения о RLS читать с поправкой на D44.
