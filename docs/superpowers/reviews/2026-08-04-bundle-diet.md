## Работа 1 (первая, самая дешёвая): `supabase-js` → `auth-js`

**Что не так.** `apps/web/src/auth/supabase.ts:1` импортирует `createClient` из
`@supabase/supabase-js`, который тянет в бандл `postgrest-js`, `realtime-js` (+ `phoenix`,
websocket-клиент), `storage-js` и `functions-js`. Web не вызывает из них **ничего**: все данные
идут через tRPC. Сплошной поиск по `apps/web/src` даёт ровно четыре обращения к клиенту, все
к `.auth`:

- `auth/supabase.ts:30` — `supabase.auth.getSession()`
- `auth/supabase.ts:33` — `supabase.auth.onAuthStateChange(...)`
- `auth/LoginScreen.tsx:20` — `supabase.auth.signInWithPassword({ email, password })`
- `auth/AuthProvider.tsx:34` — `supabase.auth.signOut()`

**Что сделать.** Заменить на `@supabase/auth-js` (тот же auth-клиент отдельным пакетом; уже лежит
в `node_modules` транзитивно). Правка — один файл `apps/web/src/auth/supabase.ts`, публичный
интерфейс модуля (`supabase`, `useSession`, `SessionState`) сохраняется, остальные три файла
не трогаются.

**Ожидаемая экономия:** большая часть из 51.6 кБ, ориентировочно **30–40 кБ gzip** — больше,
чем весь markdown-стек. Точная цифра снимается замером до/после.

**Риски и на что смотреть.**
- `persistSession` / `autoRefreshToken` обязаны продолжать работать: сессия переживает F5,
  токен обновляется сам. Проверять живым смоуком, а не только сьютом.
- Локальный Supabase подписывает JWT **ES256** — сервер проверяет подпись по JWKS
  (`SUPABASE_URL`), и это не должно измениться.
- В тестах web supabase мокается — проверить, что мок не завязан на форму пакета.
- Приёмка: вход, выход, перезагрузка страницы с живой сессией, протухший токен.

### Итог: исполнено 2026-08-08 (ветка `backlog-cards-auth-diet`, `dc342a9`..`0e6514d`)

Обе сборки сняты на одной машине и одном vite: «до» — чистый `main@2067e64` во временном
worktree, «после» — HEAD ветки. Оба чанка сжаты **одним и тем же** `gzip -c`, тем самым,
что в рецепте ниже.

| | сырых | gzip -6 (`gzip -c`) | gzip -9 |
|---|---|---|---|
| до (`supabase-js`, `main@2067e64`) | 1 024 018 Б | 293 311 Б | 292 591 Б |
| после (`auth-js`) | 913 840 Б | **263 024 Б** | 262 379 Б |
| выигрыш | −110 178 Б (−110.2 кБ) | **−30 287 Б (−30.3 кБ)** | −30 212 Б (−30.2 кБ) |

PWA-precache: 1031 KiB → **928.92 KiB**, те же 8 записей. Чанк по-прежнему один.

**Вышло меньше ожидания.** Здесь обещалось «30–40 кБ»; разведка перед работой уточнила
ожидание до «около 31 кБ» (Р10 спеки `2026-08-08-empty-cards-and-auth-diet-design.md:220-226`:
песочный замер esbuild дал ≈31,5 кБ). Настоящая экономия — **30.3 кБ**: ниже уточнённого
ожидания и ровно на нижней границе исходного диапазона. Причина была названа заранее и
подтвердилась: у `auth-js` нет ни `exports`, ни `sideEffects: false`, а `module` указывает
на неминифицированный вывод `tsc` — rollup вытряхивает его хуже, чем esbuild в песочнице.

Ждать все 51.6 кБ из таблицы выше было нельзя изначально: `auth-js` — часть того же
поддерева `supabase-js`, и он в бандле остаётся. Ушло postgrest/realtime/storage/functions
плюс `phoenix`.

**Цифру из вывода сборки в этот ряд подставлять нельзя.** Vite печатает рядом с чанком свой
`gzip:` — он систематически примерно на 1.2% БОЛЬШЕ настоящего: на одном и том же файле
266.20 кБ против 263 024 Б у `gzip -c` (проверено и `zlib.gzipSync` — 263 972 Б, тоже не
совпадает с vite). Историческая база ниже снята рецептом этого документа, то есть настоящим
`gzip`; смешение линеек сдвинуло бы ряд на ~3 кБ.

**Две поправки к прогнозу выше — из исполнения, а не из рассуждения:**

- **«Правка — один файл» неверно.** `@supabase/supabase-js` объявлен в `apps/web/package.json`,
  а `auth-js` лежал в `node_modules` только транзитивно. Импортировать его, не объявив, —
  phantom dependency: правка обязана нести `package.json` + `bun.lock` одним коммитом
  (Dockerfile и CI ставят `--frozen-lockfile`).
- **«Публичный интерфейс модуля сохраняется» неверно.** `AuthClient` — это сам auth-объект,
  а не контейнер с полем `.auth`, поэтому экспорт `supabase` стал `auth`, и три потребителя
  (`LoginScreen.tsx`, `AuthProvider.tsx`, мок в `AuthProvider.test.tsx`) правились.

Главная ловушка, которой в прогнозе не было вовсе: три вещи, которые supabase-js выводил из
`VITE_SUPABASE_URL` сам (`url`, `storageKey`, `headers`), у голого `auth-js` необязательны и
забытая уходит в **молчаливый** дефолт — ни ошибки типов, ни ошибки рантайма. Цена забытого
`storageKey` — тихий разлогин всех живых сессий в проде (воспроизведён пробоем на живом
стенде). Формулы вынесены в `apps/web/src/auth/config.ts` и пиннятся двумя тестами:
`config.test.ts` (сами формулы) и `supabase.test.ts` (их применение в построенном клиенте).

## Работа 2 (вторая): ленивая загрузка редко нужных экранов

В `apps/web/src` сегодня **ноль** `React.lazy`, `Suspense` и динамических `import()`
(проверено grep'ом при разведке фазы D), а сборщик уже предупреждает про чанк больше 500 кБ.

Кандидаты — то, что открывается по явному действию и не нужно на первом экране:

- **query-builder** (`features/query-builder/*` — форма, `FieldRows`, `model`): открывается
  кнопкой «настроить» на виджете, лежит в бандле всегда;
- **CSV-импорт** (`features/import/*`): открывается из чата, разовый сценарий;
- вкладка **Budget** целиком — самый крупный кандидат, но и самый спорный (её открывают часто).

**Осторожно:** это первое разбиение в проекте, то есть архитектурное решение, а не микроправка.
Оно меняет поведение PWA (несколько файлов в precache вместо одного) и требует продумать
состояние загрузки, чтобы экран не мигал.

### Итог: исполнено 2026-08-10 (ветка `backlog-lazy-split`, `1a3ff84`..`8eba7e1`)

Обе сборки сняты на одной машине и одном vite 8.1.3, обе сжаты тем же `gzip -c` из рецепта
ниже. «До» — `144e6f0` (последний коммит ветки до первого разреза; бандл там побайтово равен
`main@1a3ff84`) во временном worktree; «после» — HEAD ветки. Числа `gzip:` из вывода vite не
использованы нигде.

**Что сделано.** Шесть точек монтирования в `app/router.tsx` переведены на `React.lazy`:
четыре экрана Budget (`BudgetScreen`, `CategoryScreen`, `RolloverScreen`, `TransactionsScreen`),
`ImportFlow` и `entity-detail/DetailScreen`. Плюс инфраструктура, без которой разбиение —
регресс, а не диета: `ScreenFallback` (шапка + скелетон вместо мигания), `ChunkErrorBoundary`
(до этой ветки границ ошибок в приложении не было **вовсе** — любая ошибка рендера уносила
React-корень в белый экран), `chunk-reload.ts` (один автоперезаход на сессию вкладки по
`vite:preloadError`) и честный **404** на промах `/assets/*` в `apps/server/src/app.ts` —
раньше туда уходил `index.html` с кодом 200 и `text/html`.

**Начальная загрузка** = входной чанк + всё, что он тянет **статически** (в `index.html` это
`<script type="module">` + `<link rel="modulepreload">`). Сравнивать по одному входному чанку
нельзя — именно на этом обжигается любая оценка разбиения.

| | входной чанк | статически из него | **начальная загрузка** | ленивых чанков |
|---|---:|---:|---:|---:|
| до (`144e6f0`) | 263 909 Б | — | **263 909 Б** | 0 |
| после (`8eba7e1`) | 157 672 Б | `Input-*.js` 56 799 Б | **214 471 Б** | 9 (62 759 Б) |
| выигрыш | | | **−49 438 Б (−18.73%)** | |

В сыром виде: 916 574 Б → 736 899 Б (−179 675 Б, −19.60%). Ленивые чанки: `DetailScreen`
29 645, `dist` (внутренности radix) 7 164, `ImportFlow` 7 707, `BudgetScreen` 5 796,
`NativeRow` 3 356, `TransactionsScreen` 3 069, `CategoryScreen` 2 851, `RolloverScreen` 2 682,
`txQuery` 489. Входной чанк тянет статически **ровно один** файл — разрез границу не размыл.

Совокупно для пользователя, обошедшего все экраны: 214 471 + 62 759 = 277 230 Б против
263 909 — **+13 321 Б (+5.05%)**. Это цена границ разреза, и она честная: 49.4 кБ ушли с
первого кадра, 13.3 кБ добавились тем, кто откроет вообще всё.

**Чего НЕ вышло — по пунктам, потому что каждый обещал больше, чем дал.**

- **Раздел «Работа 2» назвал трёх кандидатов, и втроём они дают 12 887 Б (−4.88%)** — вчетверо
  меньше, чем дала одна Работа 1. Три четверти итога (36 551 Б) принёс **`entity-detail`,
  которого в списке не было вовсе**. Работа вышла в плюс не потому, что разбор был прав, а
  потому, что разведка переопределила постановку.
- **Причина недобора у названных кандидатов — общий чанк.** rolldown выносит из ленивых
  экранов всё, что у них общее с остальным приложением, и **входной чанк импортирует этот
  общий чанк статически**, да ещё и с `modulepreload`. Прототип на живой сборке дал
  **13.2 кБ** там, где подмена модулей в песочнице обещала 24. У нас общим оказался
  `Input-*.js` — 56 799 Б gzip, которые с первого кадра не уходят никуда.
- **Двое из трёх кандидатов не уносят с собой ни одного вендорного байта.** У query-builder и
  CSV-импорта вендорные чанки после выноса байт-в-байт те же; у Budget уезжает 556 Б иконок.
  Единственное вендорное поддерево, которое действительно уехало, — внутренности radix
  (7 164 Б), и уехали они не потому, что `DetailScreen` их единственный потребитель (их шесть),
  а потому, что он был последним **статическим**.
- **«Вкладку Budget целиком» — нельзя.** `useBudget` дёргают `TabBar` и `SidebarNav` на каждом
  рендере, `EnvelopeCard` — карточка чата; эти два модуля держатся из main при любом разрезе.
  Ленивы четыре экрана, а не фича.
- **Для установленного PWA это не экономия трафика.** `globPatterns` кладёт в предкеш все
  чанки: было **8 записей (931.84 KiB)**, стало **18 записей (938.41 KiB)**. Пользователь с
  живым service worker качает столько же — экономится парсинг и исполнение первого кадра, не
  байты по сети. Решение оставить предкеш полным принято сознательно (**D33**, Р6 спеки):
  урезать его — значит урезать офлайн.
- **CSS не режется** — Tailwind v4 отдаёт один глобальный лист: 7 549 → 7 562 Б, и вся
  разница — классы двух новых компонентов.
- **Предупреждение сборщика про >500 кБ осталось**: входной чанк 537.09 кБ сырых против
  916.57 до работы. Порог не перейдён.

Разбор того, что осознанно не чинилось (в т.ч. снятая фоновая догрузка чанков и её преемник),
— `docs/superpowers/reviews/2026-08-10-lazy-split-backlog.md`. Архитектурное решение — **D33**
в `docs/prd/04-decision-log.md`.

## Чего делать НЕ надо (решено при разборе)

- **Свой мини-рендерер markdown** вместо `react-markdown`. Сэкономит ~40 кБ, но вместе с ними
  уедет `rehype-sanitize`, а тело сущности и ответы модели могут нести что угодно — вплоть
  до текста из импортированной банковской выписки. Менять проверенную санитизацию на свою ради
  40 кБ — плохой размен. (Отдельно: `hast-util-sanitize` сравнивает протокол регистрозависимо —
  известный минор бэклога фазы C; это долг, а не повод переписывать рендерер.)
- **Ленивая загрузка markdown.** Он нужен и в ленте чата, и в body сущности, то есть почти
  на каждом экране; ленивость даст мерцание при первой отрисовке, а сэкономит только на экране
  логина.

## Рецепт замера (чтобы не выяснять заново)

Разбивка получается временным патчем `apps/web/vite.config.ts` — добавить в `defineConfig`
перед ключом `server`:

```ts
build: {
  rollupOptions: {
    output: {
      manualChunks(id) {
        if (!id.includes('node_modules')) return;
        if (/react-markdown|remark|rehype|micromark|mdast|hast|unified|unist|vfile|property-information|space-separated|comma-separated|character-entities|decode-named|bail|trough|is-plain-obj|zwitch|longest-streak|ccount|markdown-table|escape-string-regexp|devlop|estree|html-url-attributes|trim-lines|parse-entities/.test(id)) return 'x-markdown';
        if (/radix-ui|@radix-ui|aria-hidden|react-remove-scroll|use-sidecar|get-nonce|floating-ui|tabbable/.test(id)) return 'x-radix';
        if (/@tanstack/.test(id)) return 'x-tanstack';
        if (/@trpc|superjson|copy-anything|is-what/.test(id)) return 'x-trpc';
        if (/@supabase/.test(id)) return 'x-supabase';
        if (/lucide-react/.test(id)) return 'x-lucide';
        if (/zustand|use-sync-external/.test(id)) return 'x-zustand';
        if (/[\\/]node_modules[\\/](react|react-dom|scheduler)[\\/]/.test(id)) return 'x-react';
        return 'x-vendor-rest';
      },
    },
  },
},
```

Затем:

```bash
VITE_SUPABASE_URL=http://127.0.0.1:54321 VITE_SUPABASE_ANON_KEY=x bun run --filter @orbis/web build
for f in apps/web/dist/assets/*.js; do printf "%-34s %7s\n" "$(basename $f)" "$(gzip -c $f | wc -c)"; done | sort -k2 -nr
```

**Патч обязательно откатить** (`git checkout apps/web/vite.config.ts`) и пересобрать штатный
бандл — иначе на стенд уедет сборка с чужой разбивкой.

Историческая база для сравнения: **237.9 кБ** (до фазы C) → **287.2 кБ** (markdown, фаза C) →
**292.1 кБ** (query-builder, фаза D) → **293.3 кБ** (`main@2067e64`, роадмап закрыт) →
**263.0 кБ** (auth-js, 2026-08-08) → **263.9 кБ** (`main@1a3ff84`, три работы бэклога —
исходная база работы 2) → **214.5 кБ** (ленивые экраны, 2026-08-10).

Весь ряд — настоящий `gzip -c` (уровень 6), как в команде выше. Число из строки отчёта vite
(`gzip: …`) в этот ряд не годится: оно примерно на 1.2% больше, см. итог работы 1.

**С 2026-08-10 ряд меряет не «чанк», а начальную загрузку** — сумму входного чанка и всего,
что он тянет статически. До разбиения это было одно и то же число (чанк был один), после —
уже нет, и сравнивать соседние точки ряда можно только так. Команда для этой суммы:

```bash
grep -o '<\(script\|link\)[^>]*>' apps/web/dist/index.html   # чей вес считать: module + modulepreload
for f in apps/web/dist/assets/*; do printf "%-40s %8s %8s\n" "$(basename $f)" "$(wc -c < $f)" "$(gzip -c $f | wc -c)"; done | sort -k3 -nr
```
