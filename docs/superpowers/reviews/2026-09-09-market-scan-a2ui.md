## Что это

**A2UI** — открытый протокол (Apache 2.0), начатый Google в декабре 2025 и переехавший в
отдельную организацию `a2ui-project`; вклад CopilotKit; 16,3k★, ~1170 коммитов, статус в
README — «early stage public preview». Тезис из анонса: «We needed a way to transmit UI that is
**safe like data, but expressive like code**». Агент присылает не HTML и не код, а **декларацию
из компонентов заранее одобренного каталога**; клиент рисует их своими нативными компонентами
в своей дизайн-системе. «Agents can only use pre-approved components from your catalog — no UI
injection attacks».

**Устройство (v1.0, RC).** Единица — *surface* с `surfaceId`, `catalogId` и *data model*
(JSON). Сообщения агент → клиент: `createSurface` (можно сразу с компонентами и данными),
`updateComponents` (плоский список компонентов, дерево — ссылками по `id`, корень — `root`),
`updateDataModel` (адрес — JSON Pointer, upsert, `null` удаляет), `deleteSurface`,
`callRendererFunction`. Клиент → агент: `action` (имя + контекст, в контекст подставляются
привязки к данным), `callAgentFunction`, ответы функций, `error`. Структура и данные разведены
намеренно: свойства компонентов — либо литерал, либо `{path}`, либо вызов функции каталога;
списки — шаблон над путём с относительной областью видимости. Поля ввода привязаны двусторонне
к локальной модели данных, агент получает состояние **только по действию** (кнопка), при
`sendDataModel: true` — целиком. У компонентов есть `checks` (правила валидации функциями
каталога; пока не выполнены — интерактивные элементы выключены), `accessibility`
(label/description/live/hidden) и ограничения композиции `allowedParents`/`allowedChildren`.
Функции каталога помечены `allowedCallers: rendererOnly | agentOnly | rendererOrAgent`, и
рендерер эту границу проверяет на рантайме. Базовый каталог — 18 компонентов (Text с
Markdown, Image, Icon, Video, AudioPlayer, Row, Column, List, Card, Tabs, Divider, Modal,
Button, CheckBox, TextField, DateTimeInput, ChoicePicker, Slider) и 15 функций (валидаторы,
форматирование, логика, `openUrl`). Прогрессивный рендер: рисовать можно, как только пришёл
`root`. Транспорт любой с гарантией порядка и границ сообщений: AG-UI, A2A, MCP, SSE,
WebSocket, REST.

**Как это делает агент.** История версий — сама по себе урок. v0.8 строилась на строгом
structured output; v0.9 (июль 2026) сменила философию на «**prompt-first**»: схема каталога и
примеры кладутся в системный промпт, модель генерирует свободно, валидатор ловит ошибки, агент
сам исправляет до отправки клиенту. Причина смены — по CopilotKit/InfoQ — модели «ломались на
сложных вложенных структурах в масштабе». Агентный SDK — **только Python** (`a2ui-agent-sdk`,
`A2uiSchemaManager.generate_system_prompt(...)` собирает роль + правила + схему + few-shot);
TypeScript-SDK для агентной стороны нет, а официальный гайд по агенту без A2A заканчивается
строкой `TODO: Continue this guide…`.

**Рендереры.** Поддерживаемые: React, Lit (эталон), Angular, Flutter GenUI — все «Stable» для
v0.8 и v0.9.1, v1.0 у всех четырёх «Planned». `@a2ui/react` 0.11.0 опубликован 2026-09-01,
релизы ежемесячные; peer `react ^19.2.7`; тянет `@a2ui/web_core`, `zod ^3.25`, `markdown-it`;
1,04 МБ unpacked. Кастомные компоненты — Zod-схема + `createComponentImplementation()`, стили —
CSS-переменные `--a2ui-*`. Экосистема: `@a2ui-sdk/react` (Radix + Tailwind, сообщество),
**Vercel json-render** (тот же паттерн «Zod-каталог → JSON от модели → рендер», 36 компонентов
shadcn, интеграция с AI SDK; сами Vercel описывают разницу как «инструмент, связанный с
приложением» против «протокола между агентами»), рендереры под Compose, React Native, Lynx.

**Позиционирование** (таблица с a2ui.org, дословно по строкам): A2UI — «Declarative component
blueprints», рендер нативными компонентами, «Host app controls: inherits design system»,
«Designed for streaming output»; MCP Apps — «Pre-built HTML via `ui://` URIs», «Sandboxed
iframe», «Isolated: remote server controls appearance», генерация моделью — ❌; AG-UI — труба,
не формат («use AG-UI as the pipe, A2UI as the content»). Совет самих авторов: «choose MCP Apps
when the server should own the full UI experience; choose A2UI when you want dynamic,
cross-platform UI that fits naturally into your app». Связка с MCP описана в блоге Google
«A2UI + MCP Apps»: тул-результат с MIME `application/a2ui+json` внутри MCP-ресурса со схемой
`a2ui://`; хост, который это умеет, рисует нативно, а iframe остаётся «for highly tailored,
complex experiences».

## Где мы сейчас (факты Orbis, к которым это примеряется)

1. **Карточки чата — закрытый союз из 11 `kind`** (`apps/server/src/tools/registry.ts:220–347`;
   зеркало на web — `apps/web/src/features/chat/cards/types.ts`, дублирование **намеренное**:
   «типы намеренно не общие»). Производит их **диспатч тулов**, а не модель
   (`apps/server/src/ai/send-message.ts`, `collect`); лежат в `chat_messages.metadata.cards`;
   рендер — `switch` в `renderCards.tsx`, неизвестный `kind` → `null`, и абзац текста остаётся
   единственным носителем смысла. То есть у нас уже «каталог-allowlist», но выбирает из него не
   модель, а сервер по факту действия.
2. **Модель отвечает текстом + вызовами тулов**, структурного UI-вывода нет; стриминг ответа —
   в Future Directions (00-product §10), не реализован. Главное преимущество A2UI —
   прогрессивный рендер потока — нам пока не к чему приложить.
3. **Форма из декларации у нас уже есть**: форма query-блока строит контролы по типу свойства
   из реестра («переименование подписи меняет форму без единой правки кода», 02-core-os §3.4),
   карточки аспектов — «поля по схеме, inline-правка»; валидация значений — `value-schema.ts` /
   `property-type.ts` в `packages/shared/src/registry`; `view_config.keyFields` аспекта задаёт
   строки карточки записи.
4. **Часть Б (идёт сейчас, срез Б-1):** подписка поверхности = `surface` + `definition`
   (01-architecture §4.16), «поверхность узнаёт о новом домене декларацией, а не своим экраном»
   (§11.4); модули выключаемы (задача 17 — `MODULE_DISABLED`). Шов D35 «одна декларация — все
   поверхности» и требование карты работ: «вид из декларации должен рождаться приличным».
5. **§10 продукта** держит пункт «**iframe-изоляция сторонних views**», рядом — Hub Launcher,
   marketplace community-аспектов, Platform Bridge и нативная оболочка; D36 — констелляция
   приложений над одним графом.
6. **Бюджет промпта** — «самое тревожное место, и оно НЕ решено» (проба P1, п. 6): промпт уложен
   в 8 КБ ценой сворачивания реестра; «одна декларация — все поверхности» не означает «весь
   реестр в каждом промпте».
7. `orbis_ask` (D42 ОЧ.5) — вопрос рутины владельцу с `options` до четырёх **строк**;
   `routineOnly`. Флаги направления у тулов уже есть: `agentOnly`, `routineOnly`
   (01-architecture §9.2).
8. Рулинг 23.08: пользователей нет, единственный MCP-клиент — локальный Claude Code.

## Использовать напрямую? Три точки входа и вердикты

**А. Чат: модель сама собирает UI по A2UI вместо фиксированных карточек — нет.**
Наши карточки — не «что модель хочет показать», а «что система сделала или о чём спрашивает»:
они несут `pendingId`/`runId`/`undoActionId`, читают судьбу с сервера (`routine.proposal`,
`routine.runUnits`), а лента обязана читаться без сети из текста. Отдать компоновку модели
значит: (а) промпт + схема каталога + примеры в каждом запросе — ровно то, что проба P1 велела
не делать; (б) петля «сгенерировал → провалидировал → исправил» на каждый ответ — платные
токены на нашем «AI только платно»; (в) недетерминированный вид одного и того же подтверждения —
плашка подтверждения обязана быть верным отображением payload'а, а не сочинением модели;
(г) агентная сторона A2UI на TypeScript — «напиши сам», официальный гайд оборван на `TODO`.
Смена v0.8 → v0.9 у самих авторов подтверждает наш D29 (`strict:false`): строгая схема сложного
вложенного JSON от модели не держится. Прогрессивный рендер, ради которого A2UI и придуман,
без стриминга (§10) нам нечем использовать.

**Б. MCP-сервер отдаёт карточки как `application/a2ui+json` — шов, не работа.**
Технически дёшево: второй сериализатор над тем же союзом из 11 `kind` рядом с текстом.
Но хост должен уметь это рисовать, а какие умеют — не перечислено; у хостов Anthropic стандарт
сегодня — MCP Apps (`ui://`, iframe). Единственный наш MCP-клиент — локальный Claude Code
(рулинг 23.08). Делать — когда появится реальный хост, а не протокол.

**В. Сторонние views констелляции — кандидат на формат, не на рантайм.**
Это единственное место, где A2UI бьёт точно в нашу развилку. §10 держит ответ «iframe-изоляция
сторонних views»; вся идея A2UI — альтернатива этому ответу: сторонний модуль присылает не код,
а декларацию из **нашего** каталога, вид наследует **нашу** дизайн-систему, песочница не нужна,
и та же декларация рисуется на web и в нативной оболочке / мобильной поверхности V3 — то, чего
iframe не даст. Это буквально вторая половина формулы «новый домен = записи в реестрах +
подписки поверхностей» и шов «одна декларация — все поверхности». Но брать стоит **формат**
(каталог как JSON-схема с инструкциями, плоский список компонентов со ссылками, привязка к
данным JSON Pointer'ом, `checks`, ограничения композиции, атрибуты доступности), а не
**протокол сообщений** (жизненный цикл surface, стриминг, функции в обе стороны) — у декларации
в реестре нет ни потока, ни собеседника. И не сейчас: marketplace и сторонние модули дальше
Б-1, а рендереры A2UI сами ещё не догнали v1.0 — формат имеет смысл фиксировать, когда
стабилизируется он и появится первый сторонний модуль.

**Итого напрямую — нет.** Зависимость `@a2ui/react` не берём: 1 МБ на дисциплине «−18,7 % к
бандлу», второй Markdown-движок (`markdown-it`) рядом с `react-markdown` и Tiptap, стили через
свои CSS-переменные мимо Tailwind-токенов, спека, ломавшаяся 0.8 → 0.9 и меняющаяся снова в 1.0.

## Что перенимаем

| № | Идея | Что именно | Куда (решение владельца) |
|---|---|---|---|
| 1 | **Native-first вместо iframe для сторонних views** | заменить в §10 ответ «iframe-изоляция сторонних views» на «декларация из каталога хоста — по умолчанию; iframe — только хвост „highly tailored“» (разрез самих авторов A2UI + MCP Apps). Довод, которого у нас не было: одна декларация рисуется и на web, и в нативной оболочке / мобильной поверхности | 00-product §10; D36 — шов «сторонний модуль = реестры + подписки + декларации видов» |
| 2 | **Вопрос рутины как форма по реестру** | `orbis_ask` сегодня даёт до четырёх строк-кнопок; A2UI показывает следующий шаг: поля вопроса типизированы (у нас — типами свойств реестра → те же контролы, что в форме query-блока), значения живут локально, рутина получает **модель данных по действию**, а не текст; `checks` из `value-schema` до нажатия. Ответ на «какая дата? какая сумма?» перестаёт быть строкой, которую следующему прогону надо парсить | D42 ОЧ.5, `QuestionCardData`, `askJsonSchema`; после Б-1 |
| 3 | **Правила формы декларации вида** | когда придёт время формата «вид из декларации» (карта работ: «должен рождаться приличным»), взять готовые: плоский список + `root` (прогрессивный рендер), `allowedParents`/`allowedChildren` (валидация композиции, коды `UNALLOWED_*`), `accessibility` как поле декларации, а не забота рендерера; разделение структуры и данных с адресацией JSON Pointer'ом — чтобы обновление данных не перерисовывало структуру | спека формата видов (не заведена); шов D35 |
| 4 | **Шов MCP: `application/a2ui+json`** | записать как шов, а не задачу: сериализатор союза карточек в A2UI-surface, включаемый по capability хоста; триггер — появление хоста, который это рендерит | 01-architecture §9.3 (MCP — тонкий адаптер), «Швы под будущее» |

## Совпадения (подтверждают выбор, брать нечего)

- **Каталог как allowlist, модель не рисует, а выбирает** — у нас то же, и строже: выбирает
  даже не модель, а сервер по факту действия.
- **`allowedCallers: rendererOnly | agentOnly | rendererOrAgent`** — наши `agentOnly` /
  `routineOnly` у тулов, та же мысль «направление вызова — часть декларации».
- **Состояние UI уходит агенту только по действию, а не по каждому вводу** — наш Ш1: правка
  предложения становится новым предложением с детерминированным id только по нажатию.
- **v0.8 → v0.9 «prompt-first»** — тот же урок, что D29 и проба P1: строгие схемы сложного
  JSON от модели не масштабируются; лечится валидацией и подмножеством каталога в промпте.
- **Судьба единицы читается с сервера, а не из карточки** (`ProposalCard`, `DeferredActionCard`)
  — то же разделение «структура в сообщении, данные живые», что `updateDataModel` в A2UI.

## Что не берём

- Протокол сообщений A2UI в чате (surface lifecycle, стриминг, функции в обе стороны) — см. А.
- `@a2ui/react` и `@a2ui/web_core` как зависимость — см. «Итого».
- Python-SDK агентной стороны — сервер на TypeScript; переписывать `A2uiSchemaManager` ради
  чата, которому это не нужно, незачем.
- Vercel json-render — тот же паттерн ближе к нашему стеку (Zod, shadcn, AI SDK), но это
  «модель собирает UI» для чата — тот же вердикт А.
