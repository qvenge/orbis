## 1. Корень серии пустых карточек: инструкция велит модели то, чего грамматика не умеет

Самый ценный пункт списка. Работа этой ветки убрала **симптом** (голая рамка стала строкой
«Ничего не найдено»), причина осталась на месте.

**Что происходит.** Инструкция аспекта `orbis/financial` прямо велит модели резолвить
категорию по синонимам через запрос:

> `category_ref` — uuid категории-сущности: **резолви по aliases категорий через
> `entity_query`** — `packages/shared/src/aspect-registry.ts:48`

Грамматика запросов по `aliases` искать **не умеет**:

- `search=` — это FTS ровно по `title` + `body`, конфигурация `simple`
  (`apps/server/src/query/compile.ts:218-221`);
- фильтрация по массивам внутри аспектов объявлена неопределённой прямым комментарием
  каталога: «object/array (recurrence, **aliases**, byweekday): фильтрация по ним грамматикой
  не определена» (`packages/shared/src/query/catalog.ts:87`).

А синонимы у сидированных категорий живут **только** в `aliases`: в `SeedCategory` нет
никакого второго поля под них (`apps/server/src/seed/categories.ts:8-14`), и у всех 12
категорий заполнен ровно он — `['транспорт', 'transport', 'такси', 'метро']` у «Транспорт»
(`:32`), `['еда', 'food', 'продукты', ...]` у «Еда» (`:24`).

Отсюда `search=такси` по категории «Транспорт» даёт ноль **гарантированно**, а не случайно.
Модель, честно выполняя инструкцию, ловит нули и пробует ещё раз — это и есть наблюдавшаяся
в смоуке серия пустых карточек.

**Инструкция доезжает до модели дважды**, так что «незаметной» она не бывает:

- описанием attach-тула — `description: row.aiInstructions || row.description || ''`
  (`apps/server/src/tools/registry.ts:428-432`);
- блоком «Инструкции активных аспектов» системного контекста
  (`apps/server/src/llm/context.ts:259-264`).

**Два варианта починки, между ними нужен выбор владельца:**

1. **Текст инструкции** — велеть модели тянуть все категории одним
   `aspect=orbis/category, limit=50` и выбирать глазами. Дёшево, но лечит следствие: любой
   будущий автор аспекта прочтёт грамматику как умеющую алиасы.
2. **Настоящий резолв по алиасам в грамматике.** Дороже, но общий код уже написан и
   проверен: `packages/shared/src/fast-path/index.ts:78-79` матчит слово по
   `c.aliases.map(a => a.toLowerCase())`, и этим кодом уже пользуются оба берега — web
   (`apps/web/src/features/chat/useFastPath.ts`) и серверный импорт выписки
   (`apps/server/src/import/review.ts`, «тот же словарь, что у fast-path»).

**Почему не в эту ветку** (Р6): правка меняет **поведение агента**, а не вёрстку; инструкции
живут в таблице `aspect_definitions`, то есть **требуют пересева реестра на проде**;
проверяется всё это только живым прогоном модели. Смешивать с косметикой карточки и
миграцией auth — плохой размен по риску.

## 2. `count` карточки занижен при упоре в лимит — и после задачи 1 это стало видно

**Что происходит.** У `entity_query` число карточки — это длина уже усечённой SQL-выдачи:
`count: entities.length` берётся из строк, которые вернул запрос
(`apps/server/src/tools/dispatch.ts:344-353`, присваивание на `:350`), а сам запрос всегда
несёт `LIMIT`: `ast.limit`, а без него — дефолтный cap `DEFAULT_LIMIT = 500`
(`apps/server/src/query/compile.ts:55-56` и `:62-69`, строка `LIMIT` — `:68`). Полного числа
совпадений сервер по этому пути не считает вовсе.

**Почему пункт открыт именно сейчас.** До задачи 1 поле `count` не читалось в `apps/web`
нигде — число существовало и не показывалось. Теперь оно на экране подписью «Совпадений: N»
(`apps/web/src/features/chat/cards/QueryResultCard.tsx:45-47`), то есть на 500+ строках стало
**видимым враньём**: пользователь читает «Совпадений: 500» там, где их 900.

Свойство предсуществующее — задача 1 его не создала, а обнажила; менять поведение сервера
в косметической ветке было бы подменой работы.

**Ингредиент починки уже лежит рядом**: `compileCount` — тот же `WHERE`, но `count(*)` без
`limit`/`sortBy`/cap (`apps/server/src/query/compile.ts:71-74`); ровно так же устроен агрегат
`compileSum` (`:87-91`), у которого поэтому `count` честный. Цена — второй SQL-запрос на
каждый `entity_query`; альтернатива — не показывать число при `count === limit` или
подписывать его «500+».

## 3. N+1 у длинной карточки: строка списка = отдельный `entity.get`

Каждая строка карточки резолвит заголовок своим запросом:
`const q = trpc.entity.get.useQuery({ id })` в `apps/web/src/lib/entity-ref/EntityRef.tsx:11`
(дальше `:12-19` — skeleton и фолбэк на укороченный id). Карточка на N результатов стоит
**N запросов**; React Query их кэширует и дедупит, но не батчит.

**У целей цена умножается.** Прогресс цели считается обходом графа, а не читается из поля:
замерено счётчиком запросов драйвера и запиннено тестом
(`apps/server/src/goals/progress.test.ts:569-572`) — обычная сущность **6** запросов, цель
**10**. То есть карточка, перечисляющая N целей, стоит N×10 вместо N×6. Это записанная цена
решения **D23** (`docs/superpowers/reviews/2026-08-05-slice3e-backlog.md:293-304`), и оговорка
финального ревью фазы E называет карточку `query_result` в чате прямо: чтения по одному через
`entity.get` четыре лишних запроса на цель платят уже сегодня.

Блокером не сочли: путь N+1 предсуществующий, выборка ограничена лимитом. Снимается либо
батч-ручкой резолва заголовков, либо кэшем `current_value`
(`packages/shared/src/schemas/aspects.ts:144` — поле объявлено и пустует).

## 4. Нет серверного теста на форму карточки при нулевой выдаче

Единственный серверный тест, где `entity_query` возвращает пусто, —
`apps/server/src/tools/dispatch.test.ts:435-440` («entity_query: RLS — чужие сущности не
видны»). Он проверяет `expect(r.result).toHaveLength(0)` и **на `r.card` не смотрит вообще**.
Соседний тест непустой выдачи форму карточки как раз пиннит целиком (`:427-432`), так что
пробел именно в нулевой ветке.

При этом на выпуске карточки при нуле молча держатся два теста агент-петли — они зелены
**именно потому**, что сервер её выпускает:

- `apps/server/src/ai/send-message.test.ts:251-285` — свежий пользователь, пустой граф, ждёт
  ровно `cards === ['query_result','entity_card']` (утверждение на `:276-279`);
- `:293-317` — десять `entity_query` подряд, ждёт ровно `MAX_AGENT_STEPS - 1` карточек
  (утверждение на `:313`).

То есть контракт «при нуле карточка всё равно выпускается» сегодня охраняется побочно, через
счёт карточек в чужих тестах. Стоит закрепить явным тестом формы: `count === 0`,
`entityIds === []`, `kind === 'query_result'`. Это дёшево и делает пункт 2 спеки Р1
(«серверная правка ломает два живых теста») проверяемым фактом, а не рассуждением.

## 5. `supabase.test.ts` завязан на ОТСУТСТВИЕ `VITE_SUPABASE_*` в окружении

Пункт добавлен после задач 2–3; в исходном списке разведки его не было.

`apps/web/src/auth/supabase.test.ts` сравнивает поля построенного клиента с **литералами**,
которые верны только пока переменные окружения не заданы и работают фолбэки модуля
(`'http://localhost:54321'` и `'anon'` — `apps/web/src/auth/supabase.ts:5-6`). Допущение записано
в шапке теста честно (`supabase.test.ts:16-17`), но ничем не защищено: `apps/web/.env`
загружается vite и в vitest тоже (общий конфиг `apps/web/vite.config.ts`, ключ `test` в том же
`defineConfig`), а `.env` в `.gitignore` — то есть заводится локально, невидимо для ревью.

**Проверено пробоем, а не предположено.** Создал `apps/web/.env` с прод-подобными значениями
и прогнал два auth-файла:

```
printf 'VITE_SUPABASE_URL=https://ceovqtdibalxnqkgedrl.supabase.co\nVITE_SUPABASE_ANON_KEY=devkey\n' > apps/web/.env
bun run --filter @orbis/web test -- supabase.test.ts config.test.ts

 FAIL  src/auth/supabase.test.ts > url — адрес проекта, а не молчаливый дефолт localhost:9999
 AssertionError: expected 'https://ceovqtdibalxnqkgedrl.supabase…' to be 'http://localhost:54321/auth/v1'
 FAIL  src/auth/supabase.test.ts > заголовки несут apikey и Authorization
 AssertionError: expected 'devkey' to be 'anon'
 Test Files  1 failed | 1 passed (2)
      Tests  3 failed | 5 passed (8)
```

Падают **три теста из четырёх** (`storageKey`, `url`, `headers`); четвёртый — про
`flowType`/`persistSession` — от окружения не зависит и остаётся зелёным. `config.test.ts`
не затронут вовсе: он чистый, окружение не читает. Файл `.env` после пробоя удалён.

Сообщение при этом ничем не выдаёт причину: разработчик видит, что клиент построен на
прод-URL, и не понимает, чего от него хочет тест — до `.env` надо додуматься самому.

**Кандидат на правку:** сравнивать поле построенного клиента с ожиданием, **вычисленным по
той же формуле** от того же `import.meta.env` (`storageKeyFor(url)`, `authUrl(url)`), а не с
литералом. Мутационную силу теста это сохраняет — снос строки `storageKey: storageKeyFor(url)`
из `supabase.ts` по-прежнему роняет тест, потому что клиент уйдёт в дефолт
`'supabase.auth.token'`, а ожидание останется вычисленным. Литеральные значения при этом
никуда не деваются: их пиннит `config.test.ts` (прод-реф, `localhost:54321`, `127.0.0.1`,
хвостовой слэш), где вычислять ожидание из той же формулы как раз нельзя — там формула и есть
предмет проверки.

Оговорка, чтобы правку не сделали слепо: у `headers.apikey` формулы нет, ожидание там —
сам `import.meta.env.VITE_SUPABASE_ANON_KEY` с тем же фолбэком `'anon'`, и это уже не «пин
формулы», а тавтология. Третий тест честнее переписать на утверждение «`apikey` присутствует
и равен `Authorization` без префикса `Bearer `» — оно ловит ту же мутацию (снос `apikey`
из `headers`) и от окружения не зависит.

## Живой смоук (локальный стенд, прод-сборка) — пройден 2026-08-08

Стенд: сервер из `apps/server` на `PORT=3000` (порт выбран не случайно — локальный Supabase
разрешает redirect только на `http://127.0.0.1:3000`, `supabase/config.toml:159,163`, иначе
magic link уводит в никуда), Supabase `http://127.0.0.1:54321`, провайдер модели — OpenAI
(ключ в `apps/server/.env` есть; запись прошлого захода «ключа LLM на локальном стенде нет»
устарела). Старый бандл собран из чистого `main@2067e64` во временном worktree —
`index-D3TM1D9b.js`, новый — `index-COai79sS.js`.

| Сценарий | Итог |
|---|---|
| Пустой поиск от настоящей модели | Модель сделала **два** безрезультатных `entity_query` подряд — в ленте две карточки со строкой «Ничего не найдено» вместо двух голых рамок |
| Непустой поиск | «Совпадений: 1» + строка результата |
| **Переживание живой сессии: старый бандл → новый** | Вход magic link'ом на `index-D3TM1D9b.js` (клиент `supabase-js`) записал ключ `sb-127-auth-token`; после подмены бандла на `index-COai79sS.js` (голый `auth-js`) сессия **прочитана из того же ключа**, пользователь остался внутри. Главный риск работы закрыт живьём |
| Перезагрузка с живой сессией | Сессия жива |
| Вход magic link на НОВОМ клиенте | Сессия принята, hash разобран и очищен (`detectSessionInUrl` работает) |
| Выход | Кнопки выхода в интерфейсе нет вовсе — единственный путь по коду — 401 → `emitUnauthorized` → `signOut` (`AuthProvider.tsx:33-35`). Воспроизведён порчей токенов: экран логина, ключ из `localStorage` удалён |
| Две вкладки | Выход в одной разлогинил вторую — BroadcastChannel по `storageKey` работает |

**Ловушка, стоившая времени:** снятого service worker'а недостаточно. Приложение
регистрирует его заново при первой же загрузке, поэтому после подмены `dist` страница
подняла СТАРЫЙ бандл из кеша и «проверка» показала бы не то. Снимать SW нужно **повторно,
после подмены**, и заходить с cache-bust параметром.

### Единственный непройденный пункт приёмки

**Вход по паролю формой** (`signInWithPassword`, `LoginScreen.tsx:20`) живьём не проверен:
ввод паролей в поля мне запрещён правилами, даже для тестового пользователя на localhost.
Косвенное покрытие: (а) эндпоинт `token?grant_type=password` принят с **теми самыми**
заголовками, что шлёт новый клиент (`apikey` + `Authorization: Bearer <anon>`) — HTTP 200 и
сессия; (б) url/headers/storageKey нового клиента уже проверены сквозняком через magic link,
это тот же клиент и тот же транспорт; (в) сама форма и вызов покрыты сьютом на моке.
Владельцу: одна проверка формой на стенде закрывает этот хвост за минуту.
