## Короткий ответ

1. **Архитектура Linear как она есть — не подходит, и это не вкусовое.** Её сердце — самописный sync engine: четвёртый по счёту движок их CTO, полгода работы до первого экрана продукта, два-три человека на поддержку, годы переделок под масштаб. Решение D1 (02.07.2026) запрещает ровно это: «при возврате к офлайну — готовый движок, не самописный протокол репликации (обе прошлые итерации сошлись: самописная синхронизация — худший вариант)». Сам Tuomas Artman в 2023-м сказал, что сегодня, вероятно, начал бы с готового решения.
2. **Идеи Linear подходят почти целиком**, и бо́льшую часть ощущения скорости можно получить **без движка**. Сегодня Orbis медленный не потому, что у него нет sync engine, а потому, что каждый экран каждый раз идёт в сеть: кеш живёт только в памяти, оптимистичны 3 мутации из 46, канала «сервер → клиент» нет вовсе, любая мутация перезапрашивает всё смонтированное.
3. **Локальная копия графа (настоящая модель Linear) — жизнеспособна позже на готовых кубиках**: TanStack DB на клиенте + ElectricSQL только на чтение. Эта пара — единственная из разобранных, которая сохраняет инвариант «все записи — через executor». Персональный граф мал, поэтому целиком помещается на клиенте — масштабных болей Linear у нас не будет. Главная цена — не транспорт, а **запросы**: чтобы читать из памяти, Q-AST должен исполняться на клиенте, а второй бэкенд query-движка D1 вырезал как дорогой.
4. **Частичный офлайн в духе Linear** («страховка, а не режим»): чтение последнего увиденного + очередь правок с досылкой. Первая половина — побочный эффект ступени 1, вторая — ступень 3.

## Что делает Linear быстрым — по слоям

Коды источников — в разделе «Источники».

**1. Источник истины — сервер, но UI в сеть не ходит.** Главная база — Postgres [DS26]; в клиентской базе нет неподтверждённых изменений [RE]. При первом входе клиент скачивает воркспейс в IndexedDB (отдельная база на пару «пользователь × воркспейс», по таблице на модель + `_meta` с `lastSyncId` + `_transaction` с неотправленным), строит граф объектов в памяти и рендерит; затем подключается к синхронизации и докачивает пропущенное [PM21; RE]. **UI читает синхронно из памяти** — пул `modelLookup` (id → объект); все поля — наблюдаемые значения MobX, компонент в `observer` перерисовывается при любом изменении, своём или пришедшем по сети [DT ~49:00]. Асинхронно подгружается только ленивое.

**2. Модель на клиенте.** Декораторы `@ClientModel`, `@Property`, `@Reference` (пара `assigneeId` + вычисляемый `assignee`), `@OneToMany` → `LazyReferenceCollection`; ~80 моделей в `ModelRegistry` [RE]. У каждой модели — стратегия загрузки: `instant` (при старте), `lazy` (целиком по требованию), `partial` (частями, например содержимое документов), `explicitlyRequested` (история документа) [RE]. Хеш схемы → версия IndexedDB → миграция; до мая 2021 любая смена схемы стирала всё и запускала полный bootstrap, потом — только изменённые модели [PM21]. Сервер может заставить все клиенты сбросить кеш, подняв «версию базы» [INC26]. Клиентские модели пишутся **вручную** параллельно серверным [DT ~43–45:00].

**3. Bootstrap.** Три вида: полный, частичный (по группе синхронизации), локальный (IndexedDB + докачка дельт) [RE]. Полный отдаётся потоком из кеша в Mongo (Bigtable оказался в 3–4 раза медленнее) [DT ~46–48:00]; распакованный — до ~100 МБ [DT ~46:00]. Сразу грузится немногое (воркспейс, команды, люди, метки), задачи и вложения — лениво; с 2023 централизованный загрузчик собирает запросы со всего UI, убирает дубли и шлёт одной пачкой [DT ~30–33:00].

**4. Путь записи.** Присваивание `issue.title = …` сразу меняет модель в памяти; `save()` рождает транзакцию; транзакции копятся в очереди (и в IndexedDB), уходят пачкой **через обычный GraphQL API, а не через сокет — чтобы не писать бизнес-логику дважды** [DT ~37–39:00]. Ответ несёт `lastSyncId`; транзакция считается завершённой, когда в потоке пришла дельта с этим номером [RE]. При отказе — откат и тост с текстом серверной ошибки [DT ~50:00]. Undo/redo — тоже транзакции [RE]. Плашка «Syncing» появляется, только если клиент офлайн или применение идёт дольше 4 с [HN26]. Неудобная правда: после перезапуска транзакции проигрываются повторно и **не идемпотентны** [RE].

**5. Путь синхронизации.** WebSocket после bootstrap; монотонный `syncId` задаёт полный порядок; дельта-пакет — список действий (вставка / правка / архивация / удаление / смена групп) с полным снимком строки; рассылается всем клиентам, включая автора, вместе с побочными эффектами (история, активность) [RE; INC24]. **Права — группы синхронизации** (пользователь, команды, роли): серверные резолверы добавляют фильтр к каждому запросу [RE; INC26]. Дельты порождает логика приложения: прямая правка БД мимо неё дельт не даёт — клиенты и кеш продолжали показывать удалённое, кеш бэкенда жил ~24 ч [INC24]. На 18.08.2026: крупнейшие воркспейсы — около миллиона действий в сутки, всего больше 20 ТБ; чтение дельт перенесли в turbopuffer, авторитетный журнал остался в Postgres [DS26].

**6. Конфликты.** Last-writer-wins по полю, в порядке применения на сервере; CRDT для полей нет [DT ~25:00]. Документация Linear прямо предупреждает: время правки не проверяется, офлайн-правки могут затереть чужие [DOC]. Для текста описаний до конца 2023-го было сохранение по потере фокуса с перезаписью чужого; с 06.12.2023 — совместное редактирование (Yjs + ProseMirror) [DT ~22–26:00; CL23-12].

**7. Офлайн.** «Offline mode is designed as a failsafe and not a full-fledged feature» [DOC]. Полный офлайн никогда не был целью; сценарий — самолёт: читать, создавать, комментировать; опасные операции (создать команду) код может офлайн отклонить [DT ~10–11:00, ~50:00]. Ошибку «не стартует офлайн» чинили ещё в апреле 2024 [CL24-04].

**8. Скорость помимо синхронизации.** Перерисовка по отдельным свойствам (MobX); command menu — самая первая задача продукта (LIN-1), «скорость, клавиатура, реальное время» [LF ~18:00]; виртуализированные меню [PM21]; styled-components заменены на StyleX [SX26]. Поиск был клиентским, с 10.04.2025 — серверный гибридный [CL25-04]. Десктоп — Electron-обёртка того же веба [CL19].

## Цена и мнение авторов

- Четвёртый sync engine Tuomas Artman (CouchDB-прототип, отвергнутый Firebase…) [DT ~20–23:00]; около полугода на sync-стек и command menu **до продукта** [LF ~21:50]; движок с 2019 пишет в основном он сам [LF ~3:16]; в 07.2023 всю инфраструктуру вместе с sync держали три человека [DT ~7:30]; по его же словам, реверс-инжиниринг описывает движок лучше их внутренней документации [HN25].
- 2023: «сегодня, вероятно, начал бы с готового, но ожидаю, что упрусь и уйду на своё»; ни одно готовое решение Linear бы не подошло из-за специфичных оптимизаций старта [DT ~23:50–25:00].
- 2024: local-first годится для ограниченных данных, которые человек просматривает, а не для огромных массивов [LF ~51:16, ~59:40].
- Официальных связей Linear с Zero / Replicache / Electric нет. Aaron Boodman (Rocicorp) позиционирует Zero как «упрощение для приложений вроде Linear и Notion» и намеренно не делает в нём офлайн-запись [HN26].

## Слабые места Linear

- **Сам Linear, 2021:** то, что делает его быстрым, замедляет на росте — записи в IndexedDB медленные, весь набор в памяти — узкое место, клиенты часто уходили в полный bootstrap [PM21].
- **Тихая потеря данных:** LWW без интерфейса конфликтов, офлайн-правки затирают чужие [DOC]; на HN — «UI показал, а на сервер ушло только утром» [HN26].
- **Права на клиенте — новая поверхность утечки.** 24.03.2026 оптимизация с ошибкой затенения переменной отключила фильтр групп: за час ≈7 000 полных bootstrap положили данные приватных команд в локальные базы; лечили принудительной перезагрузкой клиентов и разлогином мобильных [INC26].
- **Обход движка = рассинхрон:** прямые правки БД не дают дельт, многослойные кеши скрывали удаление [INC24].
- **Ресурсы:** ~21 МБ JS, жалобы на CPU и память, медленную первую загрузку [PD26; HN26].

## Где Orbis сейчас

**Замер 27.09.2026** (с машины владельца, 6 проб `curl` к `https://orbis-64q4.onrender.com/health`): TCP-соединение 112–132 мс — это и есть один сетевой круг до сервера; запрос целиком с новым соединением 360–540 мс. Трафик идёт через край Cloudflare в Париже (`cf-ray …-CDG`) к Render во Франкфурте; Render ↔ Supabase (eu-central-1) — 3,9–4,2 мс (`01-phase0-findings.md:79`), то есть «сервер далеко от базы» — не наша проблема. Сжатие (br) делает Cloudflare. **Любое действие, которое ждёт сервер, стоит минимум ~120 мс сети плюс работа сервера** — это нижняя граница, и её не убрать ничем, кроме «не ходить в сеть».

**Что видно по коду** (разведка по `main`, ссылки выборочно перепроверены):

| # | Узкое место | Где |
|---|---|---|
| 1 | Кеш только в памяти, `gcTime` по умолчанию 5 мин, смонтирован всегда один экран: вернулся через 5 минут — скелетон и полная загрузка; после перезапуска PWA всё снова из сети. PRD так и пишет: кеш «не переживает вкладку» | `trpc.ts:16-21`, `01-architecture.md:784` |
| 2 | Канала «сервер → клиент» нет (ни WebSocket, ни SSE, ни Realtime), `refetchOnWindowFocus: false`. **Правку агента через MCP открытый экран не увидит никогда** — только после перемонтирования, своей мутации или перезагрузки. Это бьёт прямо во второй якорный сценарий «человек + агенты» | `trpc.ts:18` |
| 3 | Оптимистичны 3 мутации из ~46 (правка записи, пузырь чата, fast-path); остальные блокируют кнопку до ответа. PRD требует «мутации клиента — оптимистичные» | `useEntityDetail.ts:250-276`; `01-architecture.md:1320` |
| 4 | Одна широкая инвалидация на всё: любая мутация, включая автосохранение тела раз в 2 с, перезапрашивает все `entity.get` (с body, bodyDoc, backlinks, thread), пины сайдбара и блоки | `invalidate.ts:55-69`, `useBodySave.ts:44-50` |
| 5 | Последовательные цепочки: чат — `ensureThread`, потом `listMessages`; карточка — чанк → `entity.get` → вторая волна (`entity.blocks` + повторный реестр); prefetch нет нигде | `useChatThread.ts`, `03-pending.md:131` |
| 6 | Цена процедуры на сервере: каждая — транзакция (BEGIN, `set_config`, `SET LOCAL ROLE`, запросы, COMMIT, ≥5 обращений по ~4 мс), а пул — 3 соединения; экран записи — 5–8 процедур, они встают в очередь | `with-identity.ts:47-65`, `client.ts:13` |
| 7 | Тяжёлые списки: каждая строка несёт полное body; «показать ещё» перезапрашивает весь список | `wire.ts:22-39`, `useEntities.ts:5-18` |
| 8 | Render free: засыпание и холодный старт ~минута, держится внешним пингом раз в 10 мин | `render.yaml:10`, `keep-warm.yml` |

**Оценка, не замер:** открыть карточку записи на тёплом соединении — две волны запросов по ~150–250 мс, то есть ~0,4–0,5 с до полного экрана; у Linear — ноль сети. Замеров со стороны пользователя (навигация, INP, LCP) в Orbis нет вообще — это первое, что стоит завести.

**Побочная находка (корректность, не скорость):** гейт тела сравнивает `expectedUpdatedAt` с `updated_at` **всей строки** (`executor.ts:2163-2176`). Значит, любая правка агента в свойствах записи ломает сохранение тела у человека («Изменено в другом месте»), хотя текст никто не трогал. С агентами, работающими параллельно, это будет всплывать постоянно.

## Идеи

**И1. Чтение из памяти, а не из сети.**
Прецедент: UI Linear читает синхронно из пула объектов; сеть — только для ленивых данных [RE; DT ~49:00].
Почему нам: персональный граф мал — у Linear боли начинаются с миллиона действий в сутки на воркспейс, у владельца их сотни. Весь граф помещается на клиенте, навигация перестаёт стоить ~120 мс+ за круг.
Цена: клиентский слой коллекций; **главное — запросы**: блоки страниц и списки задаются Q-AST, который исполняется только на сервере (`compile-ast.ts`). Либо переводить Q-AST в живые запросы на клиенте (второй бэкенд движка + сьют эквивалентности — ровно то, что D1 вырезал), либо гибрид: простые списки и карточки — из памяти, сложные запросы — сервером.
Адрес-кандидат: ступень 2; ревизия D1 (`04-decision-log.md`).

**И2. Сервер сам сообщает об изменениях.**
Прецедент: WebSocket + дельты с монотонным `syncId`, рассылка всем, включая автора [RE; INC24].
Почему нам: без этого второй якорный сценарий слеп — владелец не видит, как агент работает, пока не перезагрузит экран.
Цена: ступень 1 — лёгкий SSE-сигнал «в графе изменились id …» от executor после коммита (журнал действий уже есть — это готовый курсор) → точечная инвалидация; ступень 2 — логическая репликация готового движка. Урок INC24: всё, что идёт мимо executor (ops-скрипты, пересев, миграции), сигнала не даст — нужен общий «сброс по версии». Инвариант «один путь мутаций» делает сигнал из executor надёжнее, чем был у Linear.
Адрес-кандидат: `01-architecture` §5.1; ступень 1.

**И3. Подтверждать запись по номеру из потока, а не по ответу.**
Прецедент: транзакция Linear завершена, когда пришла дельта с её `lastSyncId` [DT ~39:00; RE]; у Electric + TanStack DB то же через txid из `pg_current_xact_id()`.
Почему нам: убирает мигание «оптимистичное → старое из refetch → новое» и гонку «ответ пришёл, а список ещё старый».
Цена: executor возвращает txid.
Адрес-кандидат: ступень 2.

**И4. Всё частое — оптимистично; ошибка — тост с серверным текстом; «синхронизация» видна только после 4 с.**
Прецедент: [RE; DT ~50:00; HN26].
Почему нам: 3 из ~46 мутаций сегодня — главный разрыв с ощущением Linear, и он дешёвый.
Специфика Orbis: executor может не применить правку, а превратить её в **предложение** (политика подтверждений) — оптимистика должна уметь уступить серверному состоянию, а не показать ошибку.
Адрес-кандидат: ступень 1.

**И5. Стратегии загрузки: сразу / лениво / частями.**
Прецедент: `loadStrategy` у каждой модели; задачи и вложения убраны из стартовой загрузки в 2023 [RE; DT].
Почему нам: строка любого списка сейчас везёт полное body (`wire.ts:22-39`).
Адрес-кандидат: ступень 1 (списки без body); ступень 2 (тела — `partial`).

**И6. Постоянная локальная база + версия схемы как ключ сброса.**
Прецедент: IndexedDB, хеш схемы → миграция, серверная «версия базы» сбрасывает все клиенты [RE; INC26].
Почему нам: мгновенный холодный старт с последними известными данными. Шов у нас уже есть — `registry_version` и `MIN_COMPATIBLE_CLIENT_VERSION` (ответ 412).
Цена: на ступени 1 — `persistQueryClient` в IndexedDB с ключом сброса по версии приложения и реестра; чистка при выходе; финансы и заметки оказываются на устройстве (IndexedDB не шифруется).
Адрес-кандидат: `01-architecture` §5.1 (строка «кеш не переживает вкладку», `:784`).

**И7. Офлайн — страховка, а не режим.**
Прецедент: дословная позиция Linear [DOC].
Почему нам: подтверждает философию D2. Естественный следующий шаг — буфер не только для create, а для всех простых правок (статус, свойство, связь), с идемпотентностью по ключу. LWW Linear с тихой потерей для тел **не берём**: у нас есть optimistic-check и локальные черновики тела.
Адрес-кандидат: D2; ступень 3.

**И8. Один загрузчик на весь UI: пачка без дублей.**
Прецедент: [DT ~33:00].
У нас уже частично есть (блоки пачкой до 30, `httpBatchLink`) — подтверждение, а не новая идея.

## Предлагаемая лестница (каждая ступень измерима и может оказаться последней)

**Ступень 0 — замерить.** Метрики со стороны пользователя: время навигации до готового экрана, INP, холодный старт PWA, с отправкой на сервер. Бюджет-цель, например «повторный переход < 100 мс, действие отражается < 50 мс». Без этого любая ступень — вера. Размер: часы.

**Ступень 1 — «ощущение Linear без движка»** (малый срез, D1 не трогает):
- (а) постоянный кеш запросов в IndexedDB + `gcTime` в часах + показ из кеша с фоновым обновлением → мгновенный старт и **чтение недавно открытого без сети**;
- (б) SSE-сигнал изменений из executor → точечная инвалидация, правки агентов видны живьём, широкая `invalidateGraph` уходит;
- (в) оптимистика для частых мутаций (статус, создание, связь, свойство);
- (г) prefetch по наведению и выбору с клавиатуры; убрать последовательные цепочки;
- (д) списки без body;
- (е) гейт тела — по версии тела, а не строки (побочная находка выше);
- по желанию: платный инстанс Render без засыпания.

**Ступень 2 — локальный граф** (отдельный срез, ревизия D1): TanStack DB-коллекции сущностей и связей текущего графа. Сначала — поверх существующего tRPC (без инфраструктуры), затем замена источника на Electric (только чтение, фильтр по графу в прокси). Записи остаются tRPC → executor, подтверждение по txid. Открытый вопрос ступени — Q-AST на клиенте или гибрид (И1).

**Ступень 3 — частичный офлайн на запись**: outbox `offline-transactions` поверх ступени 2, идемпотентность executor по ключу (D2 её уже требует для create), LWW по полям для простых правок, тело — черновик + optimistic-check.

**Транспорт (по вопросу владельца «а WebSockets и GraphQL нам нужны будут?», 27.09):** ни на одной ступени не нужны.
GraphQL у Linear — единый API для своего клиента и публичного доступа, чтобы не писать бизнес-логику дважды [DT ~37–39:00];
у нас эту роль уже несут tRPC (свой клиент) и реестр тулов → MCP (агенты), GraphQL стал бы третьим контрактом к тому же
executor. Канал «сервер → клиент» нужен в одну сторону — это SSE: tRPC v11 (у нас `^11.18`) умеет подписки поверх SSE
(`httpSubscriptionLink`), браузер сам переподключается и передаёт `Last-Event-ID` — готовый курсор по журналу executor;
нужен пинг раз в ~30 с против закрытия тихого соединения прокси. Electric на ступени 2 тоже ходит по HTTP — long-polling
(`live=true`) или SSE (`live_sse=true`), WebSocket не использует (electric.ax/docs/api/http, 27.09). WebSocket понадобится
только для двустороннего потока с малой задержкой — совместного редактирования текста (Yjs) и «присутствия» (00-product §10,
Future), и то отдельным сервисом для редактора, а не заменой транспорта.

**Yjs и совместное редактирование (по вопросу владельца «стоит ли заложить уже сейчас», 28.09):** рекомендация — не
сейчас; **владелец согласился 28.09** («ок, согласен»). Текст в CRDT — отдельный слой со своим каналом (у Linear Yjs появился в 2023, через четыре года после движка), лестница
1–3 его не касается; при добавлении позже переписываются хранение тела, хук сохранения и сервис WebSocket, редактор и схема
документа остаются (y-prosemirror представляет любой документ ProseMirror). Главная цена «сейчас» — не транспорт, а
конфликт с обещанием «любое действие агента атрибутировано и обратимо»: журнал, Undo и предложения Ш1 построены на «версия
N → N+1», в CRDT их пришлось бы перепроектировать. Однажды это уже спроектировали (леджер v3, BODY-03…11) и сняли решением
D3. Заготовки, которые стоит сделать: версия текста отдельно от версии записи (ступень 1, (е)); обязательные устойчивые id
блоков (UniqueID уже в редакторе) — на них возможно промежуточное слияние по блокам; производные представления тела
(markdown, ссылки) — только сервером из документа; все записи тела — через executor. Триггеры возврата: графы компаний и
общие заметки (D44, ступень 2), частые конфликты текста после ступени 3, агенты, правящие длинный документ одновременно с
человеком.

**Когда строить (по вопросу владельца 28.09, рекомендация, не решение):**
- **Сейчас — ничего тяжёлого.** Срез 1б стоит на жёсткой остановке перед продом; ступень 1 трогает тот же клиентский слой
  данных (QueryClient, инвалидация, холодный старт — задача 3 плана 1б), параллельная ветка дала бы конфликты и замер
  движущейся цели.
- **Решено владельцем 28–29.09: ступень 0+1 — после 1в, до среза «Бюджет», текста записи и среза 2 страниц** (порядок: 1в → 0+1 → «Бюджет» → текст записи → срез 2; спека `specs/2026-09-29-speed-stages-0-1-design.md`). Ранее: **ступень 0+1 — после 1в** (спека 1в написана, планировщик запускается; рекомендация координатора была «до 1в» — довод ниже умеренный). Исходная рекомендация: **сразу после прода 1б, до 1в и до работы над логикой агентов.** 1в и агентная работа тогда строятся на
  новом слое (точечная инвалидация, сигнал изменений, постоянный кеш), а не переделываются под него; канал «сервер →
  клиент» — прямой вклад в сценарий «человек + агенты». Первой задачей — замер (база после 1б), в тот же срез — версия
  текста отдельно от версии записи. Честная оговорка: переделка 1в под ступень 1 была бы небольшой (инвалидация
  централизована в `invalidateGraph` и пачке блоков), так что довод «до 1в» умеренный; сильный довод — агентный фокус
  и начало ежедневного пользования владельцем.
- **Ступень 2 — не по календарю, а по четырём условиям:** (1) ступень 1 измерена и оставшаяся боль — именно сетевые
  чтения; (2) модель данных устоялась (остаток реформы свойств, 1в) — каждая миграция таблиц = полная перекачка на всех
  устройствах; (3) персистентность TanStack DB + возобновление Electric стабилизированы (RFC TanStack/db#1659 закрыт,
  лучше 1.0) и наш тест «закрыть на N дней → открыть» зелёный; (4) решены Q-AST на клиенте или гибрид, ревизия D1 и
  инфраструктура (платный Render с диском, прямое подключение к Supabase).
- **Ступень 3 — по реальной нужде в офлайне**, после ступени 2. **Yjs — по триггерам выше.**

## Слабые места этой рекомендации

- **Ступень 1 показывает устаревшее.** Повестка «со вчера» на секунду — это ложь, если не видна свежесть. Нужен признак «обновляется»; для денег — особенно.
- **Персистенция кеша затронет чат.** Владелец раньше отказался хранить историю чата в браузере (правило «только в памяти»). По умолчанию чат из постоянного кеша исключать — нужно подтверждение владельца.
- **SSE на телефоне:** PWA в фоне рвёт соединение; при возврате нужна перепроверка по видимости страницы (сейчас `refetchOnWindowFocus: false` выключен сознательно — придётся заменить на курсор «что изменилось с …»).
- **Сигнал из executor — это кусочек самописного протокола.** Честная граница: он только говорит «перечитай вот это», не реплицирует данные; ошибка в нём даёт устаревший экран, но не рассинхрон базы. Если его начнёт тянуть в «докачку данных», это знак, что пора на ступень 2, а не дописывать протокол.
- **Ступень 2 опирается на бету** (TanStack DB 0.x, персистентность — alpha) и добавляет инфраструктуру (репликационный слот, диск, вероятно Supabase Pro) — ежемесячные деньги и новая точка отказа.
- **Права во втором месте** (прокси Electric) — ровно класс ошибки INC26.
- **Докатывание после перезапуска — самое молодое место стека** (дополнено 28.09 по вопросу владельца «как докатываются изменения после старта устройства спустя время»). Механизм: клиент хранит закладку потока (`handle` + `offset`), при старте показывает копию с диска и просит у Electric всё после закладки; Electric всё это время читал WAL и копил журнал формы вашего графа; при негодной закладке — `409 must-refetch` и полная перекачка формы (причины: смена схемы таблицы — то есть наши миграции, смена определения формы, вытеснение по `ELECTRIC_MAX_SHAPES`, потеря слота репликации или диска Electric; electric.ax/docs/api/http, electric-sql.com/docs/guides/troubleshooting). Риск: связка «персистентность TanStack DB + возобновление Electric» в 2026 ломалась именно здесь — RFC TanStack/db#1659 (открыт 08.07.2026, на 28.09 открыт): коллекция навсегда пустеет, когда закладка ушла дальше данных (#1589), гонки гидрации, потеря офлайн-мутаций при перезапуске без durable outbox, конфликты вкладок; часть закрыта PR #1846, #1853, #1910 и др. Для ступени 2 это гейт: свой тест «закрыть на N дней → открыть» и «две вкладки» до того, как на это опираться. Строки и закладка должны писаться на диск атомарно.
- **Скорость Linear — не только sync:** клавиатура, command menu, перерисовка по свойствам. Движок без этого даст быстрый, но не «линеаровский» продукт.

## Что сознательно не берём

- **Самописный sync engine** (D1; цена у Linear — выше).
- **LWW с тихой потерей для тел записей** — у нас optimistic-check и черновики; Linear для текста сам ушёл на Yjs.
- **Клиентскую схему вручную параллельно серверной** — у нас реестр единый источник; если понадобится клиентская модель — генерировать из реестра.
- **Zero сейчас** — второй язык запросов, двойные мутаторы, нет фильтра по JSON и офлайн-записи. Пересмотреть, если появится фильтр по JSON и выбор упадёт на «переписать чтение целиком».
- **PowerSync** — конфигурация, вырезанная D1; CRUD-очередь вместо намерений executor. Запасной вариант, только если офлайн-запись станет обязательной.
- Replicache, LiveStore, Triplit, InstantDB, Jazz, Convex — не синхронизируют нашу схему или заменяют бэкенд.
