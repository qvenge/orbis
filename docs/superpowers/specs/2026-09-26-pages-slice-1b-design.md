## 0. Цель, принципы, критерии успеха

### 0.1 Цель

Срез 1 концепции разрезан на 1а «Страница и шаблон» (в проде) и 1б; 1б разрезан по слоям (Р-2): **1б «Оболочка и приложения»**
— эта спека; **1в «Бюджет и Повестка из блоков»** — следующая.

1б делает **место** данными: приложение — запись, которая описывает место (домашняя, разделы, форма навигации, состав); функции
приходят **расширениями**, которые включаются и выключаются целиком; адрес несёт приложение явно; присутствие хоста — «назад»,
домой, меню, поиск, чат, новая запись — рисует хост одинаково для всех приложений; навигация больше никогда не стоит внизу экрана.

### 0.2 Принципы среза (решения владельца, действуют на всю спеку)

1. **Временная особая возможность — только с адресом снятия** (Р-2). Реестр — §15.
2. **Система сама не пишет ни в граф, ни в журнал** (Р-24). Любое изменение данных — действие владельца или агента под его
   правилами; обновления поставки приходят только предложениями; разовые переводы данных — в прод-процедуре с явным словом
   владельца. **Уточнение (Р-28, п. 4):** следствия правил самого владельца — материализация заведённого им повтора, проводка
   плановых платежей по сроку — это действие по его правилу, как у рутины, а не «система сама». Проверка «нет тихих записей»
   (С1б-5) касается онбординга и входа, не чтения данных.
3. **Один термин на понятие.** Словарь — §1.

### 0.3 Срез удался, когда

1. На телефоне (PWA) внизу экрана нет навигации: разделы приложения — наверху; внизу справа — кнопки хоста «поиск, чат, новая
   запись»; «назад» ведёт по стопке раздела, как в нативном приложении.
2. Владелец собирает своё приложение из своих страниц; запись, открытая в нём, — в рамке его приложения; та же запись из чата —
   по правилу открытия (§5).
3. Выключение расширения (например, «Цели») гасит его целиком — агент его не видит, карточка становится плашкой, данные читаемы и
   не правятся — и включение возвращает всё. «Финансы» выключены до 1в тем же механизмом.
4. Шаблон хоста, оболочка хоста и «Домой» — записи владельца: он правит их сам, агент — по его просьбе; «вернуть как было»
   возвращает эталон; релиз ничего не меняет без согласия владельца.
5. Поиск по записям, страницам и приложениям — одним нажатием с любого экрана (и ⌘K на десктопе).

## 1. Словарь 1б

Прочие термины — словарь концепции §1 (запись, аспект, страница, тело, блок, контейнер, вкладки, примитив, компонент, карточка
аспекта, шаблон, параметр, рамка, шапка, адрес, история, действие, рутина). Правки концепции — §17.

| Термин | Значение | Что с ним |
|---|---|---|
| **Расширение** | единица функций **без своего места**: манифест, словарь, действия, свои карточки аспектов, страницы, рутины, инструкции агенту; включается и выключается целиком | новое (заменяет «модуль» и «приложение как семь элементов») |
| **Приложение** | **место**: оболочка + состав (ссылки на расширения) + свои страницы и шаблоны. Приносит поставка (маркетплейс — позже) или собирает владелец. Хост — приложение не из маркетплейса | переопределено |
| **Оболочка** | запись-приложение, описание места: имя, иконка, домашняя, навигация, форма навигации, состав, «Открывать вместо», «Выключено» | переопределено: «экран записи» из неё ушёл (§5) |
| **Раздел** | пункт навигации приложения: ссылка на запись; у раздела своя стопка экранов (§7.3) | новое, **вместо «размещения»** |
| **Навигация** | упорядоченный список разделов в оболочке; показывается сверху (на десктопе — сайдбаром), **никогда внизу** | уточнено: хранится у приложения, не у страницы |
| **Форма навигации** | как показаны разделы: «список из заголовка», «домашняя как центр» (1б); «выдвижной список», «вкладки сверху» (позже) | новое, по образцу «формы показа» блока |
| **Присутствие хоста** | доверенное хоста поверх любого содержимого: вверху «‹ ⌂ ⋯»; внизу справа — кнопки хоста; на десктопе — рейка; доверенные плашки | расширено (было: «назад», «⋯», плашки) |
| **Кнопки хоста** | группа [🔍 поиск \| 💬 чат \| ＋ новая запись] внизу справа на всех экранах | новое |
| **Тулбар** | группа плавающих кнопок действий приложения или шаблона внизу слева | слово §11 концепции; место решено, сам тулбар — срез 2 |
| **Эталон** | версия страницы, шаблона или оболочки, которую приносит поставка; запись поставки хранит его ключ, отпечаток (хеш канонической печати) и текст | уточнено |
| **Запись поставки** | запись владельца, которую поставка создаёт при заведении графа (или приносит предложением позже): шаблон хоста, оболочка хоста, «Домой», «Записи», шесть списков; несёт служебный аспект «поставка» с эталоном; дальше — данные владельца | новое (вместо «копии при первой правке» ревизии 1, Р-28 п. 2) |
| **Дом** | приложение, в рамке которого открывается страница; свойство страницы; пусто — хост | уточнено: явное свойство |

**Уходят:** «размещение» (→ раздел); «модуль» (→ расширение; остаются имя колонки БД и операции журнала `module_set`, §8.2);
«view»/«Views» в интерфейсе; «сущность» в подписях интерфейса (→ запись); «смарт-лист» (с 1а → страница / блок данных);
«Закрепить» (→ «Добавить в навигацию», §9.3).

**Слово «панель»** — не термин; его можно использовать по необходимости и осмысленно (Р-25). В спеке для конкретных вещей —
«тулбар», «боковой чат», «выдвижной список». FAB не вводится: плавающие кнопки хоста — «кнопки хоста».

«Язык» ниже — пояснение, не термин: контракты, роли связей, глаголы контракта, общие для расширений (§3.2).

## 3. Картина: хост, язык, расширения, приложения

### 3.1 Ядро (хост)

Граф, агент, доверенный интерфейс, примитивы, рантайм рамки. **Словарь ядра — только понятия, на которых стоят механизмы ядра**
(Р-4, Р-8): заметка, задача, расписание, исполнитель и прогон, рутина, память, страница, приложение, поставка (служебный, §9.1);
**стандартные свойства**
«сумма», «валюта», «направление», «дата» (исключение Р-7, §8.1). Проверка «ядро или расширение»: ядро — если без понятия не
работает механизм хоста; расширение — если кусок самодостаточен и его выключение не вредит остальному.

### 3.2 Язык между расширениями

**Контракт — отдельная единица и не выключается ни вместе с каким расширением** (Р-5, Р-6). Дублирование закрывают три механизма:
аспекты разных расширений реализуют один контракт; две вещи одной записи — два аспекта на ней; одинаковая величина — одно свойство
(поиск по каталогу до создания, `property_merge`, садовник). Чужой аспект или свойство расширение напрямую не использует — только
через контракт; исключение — стандартные свойства ядра. Тем же правилам следуют **роли связей** и **глаголы контракта** (срез 2)
(Р-7).

**В 1б исполняется:** контракты «движение денег» и «конверт», роли «тикет», «привязка конверта», «родитель категории» и
стандартные свойства «сумма», «валюта», «направление», «дата» перестают принадлежать расширениям (`module: null`). Публикация
контрактов и всё, что к ней относится, — маркетплейс (§16).

## 4. Где что лежит

### 4.1 Расширение — декларация в коде поставки

Манифест расширения (тип «манифест расширения», сменяет `ModuleManifest`):

- id, имя, иконка, описание;
- тулы и фрагменты промпта — как у сегодняшнего `MODULE_MANIFESTS`;
- **свои карточки аспектов** с **рангом** (порядок в `{{cards: own}}`, §8.5): финансовая — в манифесте Финансов, карточка цели — в
  манифесте Целей; свои карточки ядра (исполнитель, рутина, прогон) — у хоста;
- **«читает» контракты** — объявление (проверка — с первым расширением не из поставки, §15); **«реализует»** выводится из
  привязок `implements` аспектов расширения и не дублируется.

Строки словаря расширения размечены колонкой `module` и в манифесте не дублируются. **Карточки — компоненты web**, поэтому в web
есть **реестр карточек расширений** — единственное место («корень сборки»), которому разрешено импортировать каталоги расширений
(С1б-10). Состояние «включено / выключено» — маска графа (`user_settings.disabled_modules`). **Таблицы расширений в базе нет** —
до первого расширения не из поставки (§15). Манифест **приложения** в 1б — сама запись-приложение (имя, иконка, состав);
разрешения приложения — маркетплейс. Собственный словарь владельца принадлежит графу, не расширению.

### 4.2 Приложение — запись с аспектом «приложение»

Новый аспект ядра **«приложение»**. Имя — заголовок записи, иконка — эмодзи записи. Свойства (ключи — план; типы — существующие,
нового kind не нужно):

| Свойство | Тип | Смысл |
|---|---|---|
| «Домашняя» | `ref` (одна запись) | что открывает ⌂ приложения |
| «Навигация» | `ref` списком; порядок — порядок значения | разделы (§6.2); **только ссылки на записи** — «Записи» теперь страница (§3.5) |
| «Форма навигации» | `select` | «список из заголовка» (по умолчанию), «домашняя как центр» |
| «Состав» | `select` списком (id расширений поставки) | **объявление**: какие расширения приложение предлагает включать и выключать вместе с собой (§8.6); маску само не меняет |
| «Открывать вместо» | `ref` списком (приложения) | запомненный выбор места для спора (§5.3); подпись отличается от «Главнее, чем» шаблона 1а |
| «Выключено» | `boolean` | выключенное приложение (§8.6); ставит только действие владельца |

Хост выключить нельзя; запись шаблона хоста опознаётся не свойством оболочки, а ключом эталона (§9.2). Модель аспект «приложение»
до среза 2 **не навешивает сама** (`AUTHORING_DEFERRED_ASPECTS`, §15), но **правит записи-приложения по просьбе** обычным
`entity_update` (записи поставки — тоже записи, §9.1). Правила каталога — план (например, «Открывать вместо» — без себя; «Дом» не указывает на
оболочку хоста; уникальность живой записи поставки — `unique_among` на аспекте «поставка», §9.1). **«Выключено» пишет только
действие владельца «Выключить приложение»** (свойство защищено от записи агентом, как свойства эталона; механизм — план; уточнение
по ре-ревью, Н-8).

### 4.3 Дом страницы

У страницы свойство **«Дом»** — `ref` на запись-приложение; пусто — хост. Шаблон **принадлежит своему дому** — отсюда правило
открытия (§5).

- **Хост — это пустой «Дом»**: «Дом» никогда не указывает на запись-оболочку хоста (правило каталога); все правила ниже для A =
  хост ничего не пишут — страница остаётся с пустым «Домом» (уточнение по ре-ревью, Н-1).
- **Бездомная** — страница с пустым «Дом», которая **не стоит ни в одной навигации и не служит домашней ни одному приложению**
  (включая оболочку хоста). «Домой», «Записи» и пять списков навигации хоста — не бездомные; поставленные в чужое приложение, они
  становятся там ярлыками «↗». «Жизнь» в навигации хоста не стоит — она бездомная, пока её не поставят.
- **Первое место задаёт дом**: бездомная страница, поставленная домашней или разделом приложения A (A ≠ хост), получает «Дом» = A.
  Исполняет **сервер** одной пачкой с одним Undo для любого актора (владелец в интерфейсе, агент по просьбе).
- **Шаблон** получает дом: «Сделать шаблоном для…», вызванное в рамке приложения A (A ≠ хост), ставит «Дом» = A (если пуст); поле
  «Дом» — в карточке аспекта «страница» (общий контрол).
- «Новое приложение» с выбранной домашней — одна пачка: создать запись-приложение и поставить домашней «Дом» (§9.5).

### 4.4 Навигация хранится у приложения

Отступление от концепции §5.4, принятое владельцем (Р-13): у связи нет свойств и порядка; порядок разделов — забота приложения;
дом — явное свойство. Агент меняет навигацию обычной правкой записи-приложения. «Где размещена эта страница» — обратные ссылки
(ссылочное свойство зеркалится в связи). **Архивный раздел** (как и архивная «Домашняя» или приложение в «Открывать вместо»):
показывается плашкой; при следующей записи навигации клиент вычищает архивные id (как РП-21 1а), чтобы проверка ссылок не отвергла
правку; тег `needs-review` на записи-приложении из-за архивации её раздела **не ставится** (плашка — достаточный сигнал; механизм —
план).

### 4.5 Почему страница, шаблон и приложение — записи

Правило (Р-13): **запись** — вещь, которую владелец или агент создаёт, правит, обсуждает и связывает; **схема** (реестр) — то, по
чему читаются записи; **служебная таблица** — неизменное или секретное. Запись даёт журнал и Undo, версии тела, тред, обратные
ссылки, поиск, экспорт, синхронизацию, Ш1; один язык агента; одни правила; запросы; один API клиентов; данные владельца. Цена —
служебные записи смешиваются с данными (фильтр в Записях, §9.6), структуру можно сломать (гарантии §6.6), целостность держат
правила. Расширение — не запись: это правила игры и словарь, ближе к схеме.

## 5. Правило открытия записи

### 5.1 Шаблоны принадлежат приложениям (Р-12)

Внутри приложения запись показывается его шаблонами — дизайн внутри приложения согласован. **Карточку аспекта приносит
расширение, шаблон — приложение.** Шаблоны владельца из 1а (дом пуст) принадлежат хосту и работают, когда ни одно приложение не
подходит.

### 5.2 Алгоритм

Адрес = приложение A + запись R. Одна **чистая функция** в `@orbis/shared` — продолжение `chooseTemplate` 1а.

0. A выключено или в архиве → **хост** + плашка «[A] выключено — [включить]»; для зарезервированного ключа `budget` — плашка
   «придёт со следующим срезом». Дальше — как A = хост.
1. R несёт аспект «страница» → **своё тело** в рамке дома страницы (дом выключен — хост + плашка).
2. Кандидаты — шаблоны A (у хоста — шаблоны владельца с пустым домом; шаблон хоста — запасной, не кандидат). Внутри A — правило 1а:
   подходящие (набор ⊆ аспекты R), больший набор, ничья — выбор для спора, иначе детерминированно + плашка; сломанный — следующий +
   плашка.
3. В A подходящего нет, A — не хост → **шаблон хоста в рамке A** + неблокирующая плашка «В „A“ нет вида для таких записей — открыть
   в [X]» (X — приложения из п. 4).
4. A — хост (чат, поиск, Записи, ссылка из хоста) → **P = включённые, неархивные приложения с подходящим шаблоном** (только
   приложения, Р-28 п. 1):
   - P пусто → хост: шаблон владельца в хосте по п. 2, иначе шаблон хоста;
   - одно → **сразу туда**, без вопроса; «‹» возвращает;
   - два и больше → запомненный выбор («Открывать вместо»); нет — вопрос «Где открывать такие записи?» с галочкой «запомнить»
     (по умолчанию включена).
5. Не отрисовался даже шаблон хоста → базовый вид записи (гарантия 1а).

### 5.3 Память выбора места

- Запоминается выбор **для набора мест**, а не для записи и не «последний выбор»: «записи, которым подходят и Проекты, и Мой дом,
  открывать в Моём доме». Хранится свойством «Открывать вместо» у приложения-победителя — зеркально «Главнее, чем» шаблона 1а:
  одна пачка, один Undo; из «Открывать вместо» проигравших победитель вычищается; противоречие (A вместо B и B вместо A) —
  несделанный выбор; архивные и выключенные приложения из списка вычищаются.
- Новый участник спора → вопрос снова; смена — пункт «⋯» «Сменить, где открывать такие записи».
- Хост в споре мест не участвует (Р-28 п. 1), поэтому хранить выбор «в пользу хоста» не нужно.

### 5.4 Меню «⋯» записи

К пунктам 1а («Открыть через шаблон хоста», «Открыть через „X“», «Настроить шаблон „X“», …) добавляются «Открыть в
[приложение]» (разово, для каждого приложения из P) и «Сменить, где открывать такие записи» (при споре мест). Меню одно — §6.4.

### 5.5 Что перерешено

Концепция §6.3 «одна и та же задача… выглядит одинаково» → **содержимое из графа одинаково везде, раскладка принадлежит
приложению** (гарантия дописывания карточек держит, что ни один аспект не пропадает). Концепция §5.5 — элемент «экран записи»
уходит из оболочки. §17.

## 6. Рамка и навигация

### 6.1 Модель «Orbis как ОС телефона» (Р-14)

Оболочка у каждого приложения своя; **форму навигации приложение выбирает само** из закрытого набора форм хоста; присутствие хоста
рисует хост одинаково для всех. Приложение не может спрятать или перекрыть присутствие хоста — иначе оно могло бы «запереть»
пользователя.

**Правило зон** (Р-14, Р-17): **сверху — куда идти** (присутствие хоста «‹ ⌂ ⋯», навигация приложения); **снизу — частые дела
хоста и действия приложения** (кнопки хоста справа; тулбар приложения слева — срез 2). Нижней навигации нет ни в одной форме: низ
отдан действиям, а у нижних вкладок не больше пяти мест («Ещё» владелец отверг). Отвергнут и вариант «вкладки на разделах, тулбар
на экранах содержимого»: одно место означало бы то «перейти», то «сделать», и правило зависело бы от маршрута.

### 6.2 Телефон

1. **Вверху — присутствие хоста**: слева «‹», если есть куда вернуться; справа «⌂ ⋯». От шапки не зависит.
2. **Навигация приложения — вверху**, в форме оболочки. В 1б две формы:
   - **«список из заголовка»** (по умолчанию): заголовок шапки «иконка · раздел ▾» раскрывает сверху лист разделов; у раздела видно,
     где вы остановились («Категории · Еда», §7.3);
   - **«домашняя как центр»**: постоянной навигации нет, разделы — плитки (ссылки) на домашней странице приложения.

   «Выдвижной список» и «вкладки сверху» — по мере нужды (§15). Все формы оставляют место присутствия хоста свободным.
3. **Переключатель приложений** — блок «Приложения» (новый примитив хоста; имя в грамматике — план) на странице «Домой»; ставится на
   любую страницу. Запасной путь — пункт «Все приложения» в хостовом разделе «⋯».
4. **Внизу справа — кнопки хоста [🔍 | 💬 | ＋]** на всех экранах. Прочий низ в 1б пуст (Р-14); тулбар приложений — срез 2.
   Сегодняшний нижний ряд вкладок (`TabBar`) уходит. Содержимому — отступ снизу под кнопки.
5. **Стиль**: кнопки хоста — тёмные сплошные, как присутствие хоста; кнопки приложения (тулбар, срез 2) — светлые, с подписями.
   **Это доверие**: приложение не может нарисовать кнопку в стиле хоста и подделать «спросить агента»; тулбар — примитив хоста со
   стилем хоста (Р-15).

### 6.3 Десктоп (Р-16, «совмещение»)

- **Слева — тёмная рейка хоста «куда»**: ⌂, иконки приложений (переключатель в одно нажатие), внизу настройки.
- Дальше — **сайдбар с навигацией** текущего приложения (любая форма на десктопе — сайдбар) и шапка содержимого с «‹ ⋯».
- **Внизу справа — те же кнопки хоста**. 💬 открывает и закрывает **боковой чат** справа: данные видны, кнопки хоста на месте,
  активное 💬 подсвечено. **⌘K / Ctrl+K** — поиск.
- Цена: две реализации рамки — один набор элементов хоста держат тесты (С1б-7).

### 6.4 Кнопки хоста и меню «⋯»

- **🔍 Поиск** (Р-17) — глобальный поиск хоста (сегодня в интерфейсе его нет). Ищет записи (заголовок и текст — фильтр канона
  `search`), страницы и приложения; результаты по группам; страницы и приложения, скрытые из Записей (§9.6), в поиске видны.
  Телефон — строка ввода внизу над клавиатурой, результаты выше; десктоп — окно вверху по центру, там же переход к странице или
  приложению по имени. Найденное открывается по правилу открытия (§5). Разбор адреса `/search?q=…` потребует принимать строку
  запроса (сегодня путь с query разбирается в `null`).
- **💬 Чат** — общий чат хоста; в поле ввода уже стоит ссылка на текущую запись или страницу (её можно убрать) — агент видит
  контекст обычной ссылкой. Тред записи остаётся блоком `{{thread}}` шаблона. Телефон — экран хоста, десктоп — боковой чат.
- **＋ Новая запись** — рисует хост; **тип новой записи объявляет место** (срез 2); в 1б плюс везде открывает сегодняшний быстрый
  ввод, на записи — с её контекстом (семантика варианта контекста — план).
- **Меню «⋯» одно** на экране, с двумя разделами: «этот экран» (пункты записи или страницы) и «хост» («Все приложения»,
  «Приложения и расширения», «Настройки»). Отдельной иконки настроек в шапке больше нет.

### 6.5 Оболочка хоста (запись поставки)

- **Домашняя** — страница поставки «Домой»: блок «Приложения» и то, что владелец на неё поставит.
- **Навигация** — «Записи» и пять страниц из сегодняшних закреплённых (§9.4): «Daily Planning», «Upcoming», «All Tasks», «Год»,
  «Рутины». Чата в навигации нет (он в кнопках хоста), Повестки — нет (выключена до 1в).
- **Форма навигации** — «список из заголовка».

### 6.6 Гарантии рамки

- Присутствие хоста и кнопки хоста рисуются всегда, на любой странице и при любой форме навигации.
- Запись-оболочка хоста испорчена или в архиве → рамка хоста рисуется по эталону; «Домой» в архиве → ⌂ хоста показывает плашку
  «Домашняя в архиве — [восстановить]».
- Раздел, ссылающийся на архивную запись, — плашка, не пустота (§4.4).

## 7. Адреса и история

### 7.1 Адрес

Адрес = **приложение + запись** (+ параметры — позже, место оставлено). Страница — тоже запись. У встроенных экранов хоста (чат,
поиск, настройки) — адреса «хост + экран». Состояние экрана — вкладка шаблона, разовое «открыть через X», прокрутка — в истории,
не в адресе; «поделиться» даёт адрес без состояния.

| Что | Ссылка |
|---|---|
| домашняя хоста | `/` |
| запись в хосте | `/r/<id записи>` |
| экраны хоста | `/chat`, `/search?q=…`, `/settings` |
| домашняя приложения | `/a/<приложение>` |
| запись в приложении | `/a/<приложение>/r/<id записи>` |

Имя приложения в ссылке: у приложений поставки — ключ эталона (`/a/budget` одинаков в любом графе; в 1б зарезервирован, §3.4), у
своих — id записи-приложения. Короткие имена своих приложений — позже (уникальность выразима правилом `unique_among`, если имя
обязательно или лежит на своём аспекте-области; отложено по YAGNI). **Старые ссылки переводятся**: `/entity/…` → запись в хосте (дальше правило открытия); `/thread/<id треда>` → запись этого треда в
хосте (поиск записи по треду; тред без записи — глобальный — `/chat`); `/browser` → страница
«Записи»; `/budget…` → плашка «Бюджет придёт со следующим срезом»; `/agenda` → плашка «Повестка придёт со следующим срезом»;
`/chat` — экран хоста.

### 7.2 Какое приложение в адресе при переходе

- **Страница** открывается в рамке своего дома, откуда бы ни пришла ссылка; в навигации чужого приложения она — ярлык «↗ Дом». Смена
  дома меняет ссылку; старая продолжает работать.
- **Запись** (не страница): ссылка внутри страниц приложения несёт это приложение; из чата, поиска и хоста — правило открытия
  (§5.2, п. 4).
- Разбор и сборка адреса — чистые функции `@orbis/shared` (адрес — идентификатор места ядра: нативный клиент понимает те же ссылки);
  «в какой рамке и каким шаблоном» — функция §5.2.

### 7.3 История: одна модель, два поведения, стопки разделов (Р-19, Р-21)

**Модель** одна: **приложение → разделы → у каждого раздела своя стопка экранов**, плюс общий **журнал переходов между
приложениями**. Приложение помнит активный раздел.

- Переход внутри раздела кладётся в его стопку — в том числе ссылка на запись, «принадлежащую» другому разделу.
- Повторное нажатие на текущий раздел / иконку текущего приложения → корень раздела / домашняя приложения.
- У формы «домашняя как центр» разделов нет — одна стопка.
- **Экраны хоста, вызванные кнопками хоста** (чат на телефоне, поиск, быстрый ввод, настройки), ложатся **поверх текущего раздела**
  (в его стопку) с адресом «хост + экран»; «‹» возвращает в раздел. Переход по ссылке из чата или поиска открывает запись по правилу
  открытия; его **источник** — раздел, из которого вызван экран хоста.
- **Боковой чат на десктопе** и окно поиска ⌘K — не элементы истории; ссылка из них открывает запись в основной области по правилу
  открытия, источник — текущий раздел основной области.
- Переживает перезапуск: активный раздел и последнее место каждого раздела; глубина стопки — нет.

**Поведение** — по способу запуска (`display-mode: standalone`, метка WebView — план):

| | Как приложение (PWA, WebView, установленное на десктопе) | Как сайт (вкладка браузера) |
|---|---|---|
| «‹» и системный «назад» | по стопке текущего раздела; на её дне после перехода по ссылке — возврат в источник | «назад» браузера по порядку |
| переключение приложения / раздела | восстанавливает его стопку | открывает его последнее место |
| история браузера | одна запись; системный «назад» перехватывается и работает как «‹» | каждый переход — честная запись; «назад» браузера не подменяем |

Поведение — **чистая функция «модель + действие → модель»** с тестами на обе стороны; в экранах нет «если PWA». На дне стопки
корневого приложения системный «назад» на Android закрывает Orbis. Стрелку «назад» окна установленного на десктопе приложения —
проверить живьём. Сохранение навигации — **новая версия ключа**, старое `orbis:nav:v1` (без версии и переноса) не переносится.

### 7.4 Ссылки внутри записей (Р-20)

В данных — **ссылки на записи по id** (чип `[[entity:…]]`, ссылочные свойства, связи), **не адреса**. Адрес вычисляется при
нажатии. Приложение и страница — записи: ссылка на запись-приложение открывает приложение, на страницу — её в доме. **Вставленный
в тело адрес Orbis редактор превращает в ссылку на запись.** «Скопировать ссылку» даёт полный адрес. Подсказка «открывать в таком
приложении» у ссылки — не 1б.

Слоты, привязанные у Финансов к их собственным свойствам (обязательная «категория» — `orbis/finance_category`, а также `planned`, `recurring`, `counterparty`, `bank_txn_id`; у «конверта» — всё, кроме валюты), остаются за Финансами и при выключении у финансовой реализации только читаются; сам контракт жив |
| модуль `goals` | расширение Цели |
| модуль `ade` | расширения Проекты (проект, стадия, родительский и корневой проект) и Разработка (репозиторий) |
| контракты «движение денег», «конверт»; роли «тикет», «привязка конверта», «родитель категории» | язык: `module: null` |

Цена переноса в ядро: правило сида действий требует пространства имён модуля — правило допускает пространство ядра, ключ
`planner/postpone_overdue` и имя тула `action_planner_postpone_overdue` меняются (эталоны тулов и действий пересдаются);
поверхность `planner/agenda` — в пространство ядра (голова `core` в регэкспе поверхностей уже есть). Пользователей нет,
единственный MCP-клиент локальный.

### 8.2 Слово «модуль» и модельно видимое

- В типах и именах кода «модуль» → «расширение». **Остаются** с пометкой в описании: колонка `module` в шести таблицах реестров
  (переименование — миграция ради слова) и операция журнала `module_set` (её хранят записи журнала и обратные операции). Прочие имена
  (провод `disabledModules`, ручка `setModuleEnabled`, код отказа `MODULE_DISABLED`) — план, с явным списком исключений сторожа
  (С1б-10).
- `moduleOfTool` возвращает только значения словаря — новое id расширения без записи в словарь дало бы «неизвестный тул» вместо
  `MODULE_DISABLED`: словарь расширений — единственный источник.
- **Обязательная работа с промптом** (ревью, Opus I-6): «агент не видит выключенное расширение» требует
  - **v8** промпта чата: рукописный блок «Цели и горизонты» (`v7.ts`) **делится** — строки о целях уходят во фрагмент манифеста
    Целей, строки о горизонтах планирования по страницам хоста (Daily Planning, Upcoming, «Год», «Жизнь») остаются в v8 (уточнение
    по ре-ревью, Н-7); слова «smart lists» заменяются; «модуль» в тексте → «расширение»;
  - **routine-v4**: `routine-v3` называет финансовые свойства и категорию — во фрагмент Финансов;
  - **описания core-тулов** (слой 5), называющие id Финансов (`entity_query`, `entity_create`, `entity_update`, `user_query`,
    `property_catalog`), — нейтральными примерами; «модуль» в описаниях `property_catalog`, `run_action`, `rule_set` → «расширение»;
  - пересдача эталона тулов и перезамер `prompt-size`.

  Граница проверки С1б-4 — три канала (чат, рутина, MCP) и слой 5.

### 8.3 Что значит «расширение выключено» (Р-23, Р-28)

| Что | При выключенном расширении |
|---|---|
| агент | не видит: тулов, фрагментов промпта, строк индекса аспектов нет; **его свойств нет и в `property_catalog`** |
| новые записи и аспекты | создать нельзя, включая сев (§8.6 — порядок онбординга); **материализация повторов для записей с его аспектами останавливается**: шаблоны отсеиваются до исполнения (без отказов в журнал сервера); при включении ленивая материализация догоняет пропущенное **в пределах ретро-пола правила материализации (92 дня)** |
| действия, движки, рутины | не работают: `run_action`, «план → факт» (обход маски ручкой `budget.confirmPurchase` — закрыть), проводка плановых (`budget.postDue`), импорт; **рутины**, все разрешённые тулы которых принадлежат выключенному расширению, планировщик **пропускает** (без записи в граф) |
| правила его аспектов | **продолжают работать** на правке существующих записей — целостность данных (Р-23 перерешил в этой части Р-7); отказ называет расширение («правило Финансов: …») |
| свойства расширения (`module` = это расширение; стандартные свойства ядра — сумма, валюта, направление, дата — правятся как обычно) | **только чтение на сервере для всех акторов** — владельца в интерфейсе, агента, MCP (Р-28 п. 3); исключения — механизмы правил, догонки материализации и Undo; **снять аспект выключенного расширения нельзя**. Перерешает §Б8-3 спеки реформы («скрытое ≠ удалённое: правка разрешена») и рулинг Ф-34 — эррата ревизией владельца (§17) |
| существующие записи | видны везде (поиск, Записи, запросы); правка их прочих полей разрешена |
| его карточка на записи | поля только чтение + плашка «[Расширение] выключено — [включить]» |
| его блоки на страницах | плашка «выключено — [включить]», никогда пустота |
| его страницы | в 1б у расширений страниц нет; в 1в — гаснут с расширением (плашка на месте раздела) |
| язык (контракты, роли, стандартные свойства) | работает: правила памяти с областью «движение денег» живут |

### 8.5 Шаблон хоста не называет расширений (Р-23)

Пять строк `{{card: …}}` вкладки «Запись» шаблона хоста заменяются одной — **`{{cards: own}}`**: карточки всех аспектов записи, у
которых есть своя карточка (ядра и расширений по манифестам), не размещённые шаблоном явно, **в порядке рангов своих карточек**
(§4.1); ранги поставки воспроизводят порядок 1а — цель, исполнитель, рутина, прогон, финансы; карточка исполнителя ранжируется
своим рангом, а не аспектом, по которому показывается. `{{cards}}` («остальные») их не повторяет. Вид экрана записи совпадает со
снимком 1а (С1б-9). Новая форма грамматики меняет эталонный текст шаблона хоста и требует ревизии спеки 1а §8.1 до задачи плана с
шаблоном (пин `host-template.test.ts`, §14).

### 8.6 Управление, онбординг, выкатка

- В настройках вкладка «Views» становится **«Приложения и расширения»**: список, переключатели, что каждое приносит; раздел
  «Обновления» (§9.1); «Новое приложение» (§9.5).
- **Выключить приложение** — действие владельца: диалог показывает, что изменится — место и расширения его «Состава», которых нет в
  «Составе» других включённых приложений (Р-9, отмечены по умолчанию, владелец может снять галочки); одна пачка, один Undo: свойство
  «Выключено» + `module_set` отмеченных расширений. **Правка «Состава» маску не меняет** — включать и выключать расширения может
  только владелец (`module_set` — только `actorKind: owner`), агент не включит Финансы правкой записи.
- Удаление (архив) приложения спрашивает, выключить ли осиротевшие расширения (расширения поставки не удаляются, только
  выключаются).
- **Выключаются все расширения** (П0). Журнал и Undo — `module_set`.
- **Онбординг нового графа** — один раз, при заведении графа (действие владельца): сев мира (12 категорий Финансов, шесть списков
  страницами) → записи поставки (§9.1) → маска с выключенными Финансами. **Сев — до маски**: иначе пачка сева с категориями получит
  отказ выключенного расширения.
- **Признак «граф заведён» — наличие записи поставки «оболочка хоста»**, в том числе архивной (Р-29, ответ владельца на Н-3):
  физически её удалить в продукте нельзя, только заархивировать. Вход, на котором её нет, заводит граф (сев мира и записей
  поставки); вход, на котором она есть, не пишет ничего. **После прод-операции `reset-world`** (она сносит весь мир, но сохраняет
  строку настроек) оболочки хоста нет — ближайший вход заводит граф заново; строка настроек маркером больше не служит. Один путь для
  нового графа и после пересева, миграции не нужно; `reset-world` — инструмент до начала настоящего пользования.
- **На каждом входе онбординг ничего не пишет.** Снимаются поимённо все досевы безусловного пути (сегодня `OnboardingGate` зовёт сид
  на каждом старте): дописывание `orbis-budget` в `installedViews`; повторный сев недостающего мира; `backfillHorizons`,
  `backfillRoutinesList` (строки мимо исполнителя); `backfillRoutinesListBody` (прямой UPDATE тела «Рутин» мимо журнала и версий);
  оба `pinIfAbsent`; досев рутины «Перенос остатков»; досев садовника словаря (`seedGardener`, уточнение по ре-ревью, Н-4). Новая запись поставки в существующем графе приходит только предложением
  (§9.1) или прод-процедурой с словом владельца.
- `installedViews` и `pinnedEntities` перестают использоваться (колонки удаляются позже).
- Бейдж Повестки уходит из оболочки (сегодня её хук смонтирован в оболочке и шлёт запрос на любом экране).
- Код экранов Бюджета и Повестки остаётся в репозитории, недоступен из интерфейса; удаляется в 1в (§15).

## 9. Записи поставки, навигация, закреплённые

### 9.1 Записи поставки и обновления (Р-24, Р-28 п. 2)

**Всё, что приносит поставка хоста, — записи владельца** с эталоном, созданные при заведении графа: шаблон хоста (§9.2),
оболочка хоста (§6.5), «Домой», «Записи» (§3.5), шесть списков (§9.4). Агент их правит по просьбе владельца (они записи), у всех
есть id, обратные ссылки работают. *Перерешает Р-24 п. 1 ревизии 1 («пока не правили — копии нет, место меняется с продуктом»):
неправленые записи поставки тоже обновляются только предложениями.*

1. **Эталон** лежит на **своём служебном аспекте ядра «поставка»** (уточнение по ре-ревью, Н-2): ключ эталона (**фильтруемое
   свойство** `text`/`select`, обязательное на этом аспекте — по нему ищутся записи поставки и собирается «Обновления»), отпечаток и
   текст эталона (форма — план). Уникальность живой записи на ключ держит правило `unique_among` **с областью-аспектом «поставка»**:
   `unique_among` считает «нет значения» частью комбинации и не имеет условия `when`, поэтому правило на аспекте «страница» или
   «приложение» объявило бы дублями любые две записи владельца без ключа. Аспект «поставка» модель не навешивает
   (`AUTHORING_DEFERRED_ASPECTS`); его свойства пишет **только механизм поставки** (сев при заведении графа, «принять обновление», «вернуть как было») — агент
   ключ не подделает. Правлена ли запись — каноническая печать ≠ канонической печати эталона. У записи-приложения «текст» —
   каноническая печать её свойств.
2. **Релизы записи поставки не трогают никогда.** Новый эталон → предложение: плашка на записи и список «Обновления» в «Приложения и
   расширения»: **[сравнить] [принять — прежняя версия сохранится] [оставить своё]**; для записей, которые владелец не правил, —
   кнопка **«принять все»** (всё равно явное действие). Отказ запоминается до следующего эталона. Сравнение в 1б — **двустороннее**
   (дифф Ш1), трёхстороннее слияние — позже.
3. **Новая запись поставки** в существующем графе (в будущем релизе) — тоже предложение: «В поставке появилось: … — [добавить]».
4. **«Вернуть как было»** в «⋯» — действие владельца: содержимое записи заменяется текущим эталоном (прежнее — в версиях тела, у
   записи-приложения — в журнале для Undo); для оболочки хоста диалог сначала показывает, какие разделы, добавленные владельцем,
   исчезнут.
5. Признак в «⋯»: «как в поставке» / «изменено вами».

### 9.2 Шаблон хоста

- Запись поставки: страница с ключом эталона шаблона хоста. **Род тела — «шаблон»** определяется ключом эталона (иначе её `{{body}}`
  на странице считался бы ошибкой места 1а); из кандидатов выбора (`templatesFromRows`) она исключена — это запасной шаблон (§5.2).
- «⋯ → Настроить шаблон хоста» — редактор настройки 1а с баннером «Вы правите шаблон хоста — изменится вид всех записей, для которых
  нет своего шаблона».
- Гарантии: запись сломана или в архиве → эталон из кода → базовый вид записи.

### 9.3 Навигация вместо закреплённых

- **Закреплённые становятся навигацией оболочки хоста**; `pinnedEntities` уходит.
- **«Добавить в навигацию»** (один глагол вместо «Закрепить» и «Добавить в приложение») в «⋯» записи: выбор приложения (по
  умолчанию — текущее) или «Новое приложение…»; **без дублей**; рядом «Убрать из навигации».
- **«⋯ → Настроить навигацию»** — редактор записи-приложения: порядок перетаскиванием, добавить (поиском), убрать, домашняя, форма
  навигации, имя, иконка. Новый контрол — «упорядоченный список ссылок».
- **Бейдж раздела** — число из первого блока данных страницы раздела; все бейджи навигации — **одной пачкой** `entity.blocks`
  (снимается второй путь данных 1а: `entity.get` на каждый пин плюс `entity.count`).
- В списке разделов видно, где вы остановились (§7.3).
- `entity.updateBatch` учится создавать запись (`entity_create` в пачке): «Новое приложение…», «Добавить в навигацию → Новое
  приложение…» — одна пачка, один Undo.

### 9.4 Смарт-листы становятся страницами

Шесть записей с тегом `smart-list` (Daily Planning, Upcoming, All Tasks, Год, Жизнь, Рутины) — записи поставки: аспект «страница»,
эталон, дом — хост; тег уходит (его никто не читает). Пять из них — разделы навигации хоста, как сегодня в закреплённых. Мёртвый
вариант контекста быстрого ввода `smart-list` уходит. Слова «smart lists» в промпте — v8 (§8.2).

### 9.5 Своё приложение

«Приложения и расширения → Новое приложение» или «⋯ → Добавить в навигацию → Новое приложение…»: одна пачка — создать
запись-приложение без эталона (домашняя — выбранная страница, навигация пуста или с этой страницей, форма — «список из заголовка»)
и поставить странице «Дом», если она бездомная (§4.3). «Состав» — по выбору владельца (§8.6).

### 9.6 Страницы и приложения в Записях

В общем списке блока `{{records}}` страницы и приложения по умолчанию не показываются; переключатель «показать страницы и
приложения». Поиск показывает их отдельными группами (§6.4).

## 11. Натяжения и честные цены

- **В 1б нет ни одного нашего включённого приложения**: модель приложения проверяется на хосте, выключении Финансов и Целей и на
  приложении владельца из его страниц.
- **Одна запись выглядит по-разному в разных приложениях** — цена Р-12; содержимое одинаково, раскладка — приложения.
- **Шаблоны владельца в хосте уступают приложениям**: из чата запись, для которой подходит шаблон приложения, откроется там, а не
  шаблоном в хосте (Р-28 п. 1); разово — «⋯ → Открыть через …».
- **Каждый релиз с новым эталоном даёт предложение**, даже для неправленых записей поставки (Р-28 п. 2); смягчает «принять все».
- **Правила выключенного расширения продолжают отказывать** на правке — спасает только понятный текст отказа.
- **При выключенных Финансах повторяющиеся задачи с финансовым аспектом** не материализуются и пропадают со страниц хоста (Daily
  Planning, Upcoming) до включения; догонка — в пределах 92 дней.
- **Две реализации рамки и два поведения истории** — два набора тестов; поведение держит одна чистая функция.
- **Навигация сверху дальше от пальца** — цена правила зон.

## 12. Хранение, миграции, выкатка данных

- **Миграций по дизайну нет.** Аспект «приложение», его свойства, «Дом», свойства эталона — строки сида реестра (нового kind не
  нужно: `ref`, `ref` списком, `select`, `boolean`, `text`); маска — существующая колонка. План, нашедший необходимость миграции,
  **останавливается и докладывает**; следующий номер — `0023`.
- **Скрытые цены, известные сейчас** (ревью): пины числа аспектов и свойств, карты аспект → модуль (`builtin.test.ts`,
  `modules.test.ts`, ≈57 строк серверных тестов с литералами модулей); эталоны тулов и действий; сторож `check-lazy-chunks`
  (сверяет ленивые экраны роутера и общий чанк из `features/budget` — упадёт, когда экраны Бюджета уйдут из роутера); счёт примет
  маркеров в `grammar-copies.test.ts` (новые `{{cards: own}}`, «Приложения», `{{records}}`); пин `host-template.test.ts` против §8.1
  спеки 1а; `ScreenHeader` — 16 вызовов в 14 файлах; литералы вкладок — 9 прод-файлов web и 127 вхождений в тестах; сужение
  `pageBlock` — после переписи v3 в проде; **вес `{{records}}`**: сегодня экран Browser грузится в первом кадре, а блок на странице
  рисуется в ленивом чанке экрана записи под сторожем веса 1а (≈27,5 из ≈34,9 кБ) — блоку нужна своя точка лени (уточнение по
  ре-ревью, Н-9).
- **Порядок выкатки — как у 1а**: жёсткая остановка перед продом, прод-процедура только вместе с владельцем, **пересев реестра до
  кода**, автодеплой — по ранбуку.
- **Разовый перевод данных** в прод-процедуре с слова владельца: записи поставки — шаблон хоста, «Домой», «Записи», оболочка хоста
  с навигацией «Записи» + пять закреплённых в их порядке (дубли убраны; если закреплённые совпадают с эталоном — запись «как в
  поставке», иначе — «изменено вами»); шесть смарт-листов → страницы с эталоном, тег снят; Финансы → выключены в маске; прочие
  записи не трогаются. Подпись перевода в журнале — план вместе с владельцем.
- **Нет тихих записей** после выкатки (С1б-5).

## Приложение Б. Версии единиц — черновик, который только открывает обсуждение

**Не решение** (Р-10). Записано, чтобы не потерять ход мысли; вернуться при маркетплейсе.

- В одном графе стоит **одна версия расширения**: словарь задаёт смысл данных, данные одни.
- Ссылки на единицы — **линия и минимум** («Питание 1.x, не ниже 1.2»); точная версия — у «замка», у эталона записи поставки, в
  журнале.
- Совместимые правки: контракт — новый необязательный слот, новое значение набора, новый глагол (две линии сосуществуют); роль —
  подпись, описание; расширение — новые свойства, необязательные свойства аспекта, действия, страницы, компоненты (двух линий в графе
  нет); приложение — оболочка, страницы, новое расширение в составе.
- Обновления: совместимое обновление правил игры — само; записи поставки — только предложениями; новая линия расширения — согласие и
  **переезд данных** через конвейер действий; «требует хост не ниже X».
- До маркетплейса — только эталон записи поставки с отпечатком (1б, §9.1); остальное — к маркетплейсу; дисциплина переездов — со
  слова владельца «начинаю пользоваться».
