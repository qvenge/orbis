# Тип свойства `ref` — решения до спеки

> **Статус после обсуждения 23.08 (вечер):** выбран путь С — «свойство — факт, роль — интерпретация»
> (`2026-08-23-properties-model-notes.md`). Решения ниже остаются в силе с поправками:
> Р1 — тип живёт в определении **свойства**, а не в схеме аспекта; JSON Schema роли — производная для тулов,
> `x-orbis-type` в ней — копия. Р3/Р15-scope — без изменений. Р6 — пикер по типу, проекция по label (key
> упразднён). Р11 — перевод встроенных идёт через реестр свойств с id вида `orbis/category_ref`; требование
> «схема совпадает по canonicalJson» снимается — миграции данных нет (пользователей нет, база пересевается).
> В1 (квалифицированные имена) — решается квалификацией по **label роли**, см. Р13 новой заметки.

**Статус:** зафиксированные решения обсуждения 2026-08-22/23. Это не спека, а её будущий
раздел: полноценная спека «Кастомные свойства и аспекты» пишется позже и заберёт отсюда
решения Р1–Р11 как есть, если к тому моменту их не опровергнет проба. Открытые вопросы
В1–В4 — её входные данные.

## 1. Зачем

Сегодняшний механизм аспектов негибок в трёх местах, и все три сходятся на ссылках:

- **Ссылка реализована один раз и руками.** Единственное ссылочное поле с собственным
  контролом — `orbis/financial.category_ref`: пикер категорий привязан к паре «имя аспекта +
  имя поля» (`apps/web/src/features/entity-detail/AspectCards.tsx`, константы
  `FINANCIAL`/`CATEGORY_REF`). Тот же `category_ref` у `orbis/budget` пикера не получает и
  показывает голый uuid.
- **Ссылка не проверяется.** На записи `category_ref` исполнитель не проверяет ни
  существование цели, ни что это категория: схема реестра видит только
  `{type: string, format: uuid}` (`packages/shared/src/schemas/aspects.ts:69,91`). Единственное
  ссылочное поле с инвариантом — `grant_id` (`apps/server/src/executor/invariants.ts:279-323`),
  и это ссылка не на сущность, а в `agent_grants`.
- **Ссылка односторонняя.** В `relations` поле-ссылка не попадает; «кто ссылается на
  категорию» достаётся ручным SQL по jsonb (`apps/server/src/import/review.ts:491-506`).

JSON Schema проверяет форму значения, а не смысл: «строка-uuid» подходит под id любой
сущности. Смысл «ссылка на сущность с аспектом X» сегодня живёт в имени поля и в трёх
местах кода, которые это имя знают.

Калька с Notion («relation → одна база») отклонена: в Orbis баз нет, множество сущностей
описывается запросом §6.1, и цель ссылки должна говорить на этом языке.

## 3. Решения

**Р1. Тип свойства — размеченное объединение, JSON Schema — производная.** Определение
свойства: `{ name, label, type: { kind, …конфиг }, required?, ai_hint? }`. Колонка
`aspect_definitions.schema` генерируется компилятором из списка свойств и остаётся
контрактом для ajv, каталога query, `attach_*`, drift-проверки и экспорта — ни один из них
не меняется. Смысл уезжает в схему ключом `x-orbis-type` (копия `type` свойства),
зарегистрированным в ajv как keyword без валидации (`ajv.addKeyword`), чтобы `strict: true`
его не отверг.

**Р2. `ref.target` — запрос §6.1, а не id аспекта.** Форма:
`{ kind: 'ref', target?: string | string[], cardinality?: 'one' | 'many' }`.
Отсутствие `target` — любая сущность владельца. Список — OR запросов (грамматика
запрещает `aspect=a|b`, и список целей дешевле правки языка). `aspect=orbis/category` —
просто самый частый случай; равно выразимы цели по тегу, по полю
(`aspect=orbis/category, spend_class=discretionary`), по родителю (`children_of=<id>`),
по двум аспектам сразу.

**Р3. Цель — статическое подмножество грамматики.** В `target` запрещены относительные
date-токены (`today`, `overdue`, `next_7d`, `after_7d`), `search=`, `this`, `sortBy`,
`limit`, `display`, `title`, `archived`. Иначе валидность ссылки зависела бы от даты или
контекста. Реестр отвергает нестатическую цель при сохранении свойства; парсер получает флаг
режима «цель» и отказывает с позицией, как при прочих ошибках §6.4.

**Р4. Проверка ссылки — седьмой потребитель query-движка (§6.3).** «Валидна ли ссылка» =
«попадает ли сущность `id` в множество `target`»: компиляция цели + `AND id = $1` под RLS
актора. Одним махом: существование, принадлежность владельцу, соответствие множеству.
Покрывается теми же golden-тестами §6.2. Для `cardinality: 'many'` — одна проверка на весь
массив (`id = ANY($1)` и сравнение числа найденных).

**Р5. Проверяется установка значения, а не каждая запись сущности.** Цель без узла
`archived` компилируется с `NOT archived` (факт выше), поэтому архивирование категории
делает ссылку на неё «не в множестве». Если бы проверка шла при каждой записи транзакции,
архивирование категории заморозило бы все её транзакции (fail-closed). Поэтому
исполнитель проверяет ссылку, только когда её значение появляется или меняется;
неизменённое значение при правке заголовка/тегов не перепроверяется. Политика «что делать
со ссылками при архивации цели» — В3.

**Р6. Пикер и контрол — по типу, тем же запросом.** UI выбирает контрол по
`x-orbis-type.kind`, не по имени поля; для `ref` — пикер сущностей, варианты которого
загружаются запросом `target` (для списка целей — объединение). `CategoryField` становится
частным случаем и уходит. `orbis/budget.category_ref` получает пикер автоматически.

**Р7. `cardinality: 'many'` — ограниченный массив id.** Правило 1 §10: массив внутри аспекта
допустим только ограниченный. Кап обязателен в конфиге типа (`max`), дефолт назначает спека.
Фильтр в query — containment по массиву, как у `orbis/category.aliases`
(`catalog.ts`, тип `array`).

**Р8. Зеркалирование в `relations` — решение, а не побочный эффект.** Исполнитель при
установке/смене/снятии значения `ref` пишет/удаляет строку `relations` с
`relation_type = 'ref'` и меткой свойства в `meta` (`{ aspect, property }`). Цель: один граф
для backlinks и обхода — «кто ссылается на X» перестаёт зависеть от того, поле это или
связь. Истина — поле в аспекте; строка `relations` — производная и пересоздаётся при
расхождении (правило 3 §10). Форма метки и индекс под обратный обход — В2.

**Р9. Очередь 2 — вычисляемые свойства на стороне цели, форма совместима.**
`{ kind: 'backref', via: '<aspect>.<property>' }` (список ссылающихся),
`{ kind: 'rollup', via, aggregate, property }` (агрегат по ним),
`{ kind: 'lookup', via: '<property>', property }` (поле цели на источнике). Все три —
производные из `relations` и графа, кэш, не истина (правило 3 §10); прецедент —
`orbis/goal.progress_source`. В первую версию не входят; Р2–Р8 их не исключают.

**Р10. Ссылки не на сущности — отдельные `kind`.** `grant_id` → `{ kind: 'grant' }`
(проверка — существующий инвариант), будущий участник (видение, В7) →
`{ kind: 'participant' }`. Универсален способ описать ссылку **на сущность**, а не один тип
для всего. Служебные uuid-поля `orbis/agent-run` (`action_id`, `pending_id`, `edited_from`)
— не `ref`: они указывают на действия и отложенные решения, а не на сущности графа;
перепроверить при переводе встроенных аспектов на словарь (Р11).

**Р11. Встроенные аспекты переводятся на тот же словарь.** `BUILTIN_ASPECT_META` + zod-схемы
`schemas/aspects.ts` переписываются списками свойств; JSON Schema для `orbis/*` и `user/*`
генерирует один компилятор. Переводимые поля: `category_ref` (financial, budget) →
`target: 'aspect=orbis/category'`; `routine_id` (agent-run) → `'aspect=orbis/routine'`;
`project_id` (routine) → `'aspect=orbis/project'`; `grant_id` ×2 → `kind: 'grant'`.
Сгенерированная схема обязана совпасть с нынешней байт-в-байт по `canonicalJson`, кроме
добавленного `x-orbis-type`, — иначе drift-проверка и пересев реестра на проде превращаются
в миграцию данных. Это приёмочная проверка задачи перевода.

**Р12. Цель как сохранённый список — расширение, не дефолт.** `target` может в будущем
указывать на smart list (сущность с сохранённым запросом): множество правится в одном месте.
Цена — та же, что у удаления варианта `select`: сужение делает часть ссылок невалидными;
политика — прогон §3.10 с тегом `needs-review`. В первой версии — только строка/список
строк.

## 4. Открытые вопросы (входные данные спеки)

- **В1. Квалифицированные имена в query** (`orbis/budget.category_ref=X`). Нужны независимо
  от `ref`: любой кастомный аспект с полем `status`/`date` ломает голые имена в существующих
  запросах (фильтр Browser шлёт голое `status=`, `apps/web/src/features/browser/query.ts:15`).
  Решение по грамматике — в спеке свойств; `ref` на него опирается для одноимённых полей.
- **В2. Метка свойства в `relations`.** `meta: { aspect, property }` без миграции — или
  колонка `property` с индексом `(target_id, relation_type, property)` под `backref`.
  Решать по замеру: обратный обход по jsonb под RLS GIN не берёт (D41, известный долг).
- **В3. Политика при архивации/удалении цели.** Варианты: запретить архивацию, пока есть
  ссылки; обнулить ссылки; оставить и пометить источники `needs-review`. Удаление цели —
  `ON DELETE CASCADE` на `relations` уже снимает зеркало, поле остаётся висячим.
  Предпочтение на сегодня — третий вариант (ничего не теряется, видно в Browser), но это
  решение спеки.
- **В4. Что значит «свойство целиком».** Развилка «3-лайт / 3-полный» (значение в аспекте vs
  одно значение на сущности), «+ свойство» на встроенном аспекте через аспект-спутник,
  словарь типов и контролы, чек-лист §12.10/§12.8 — всё это обсуждается отдельно; `ref`
  спроектирован так, чтобы работать в обоих вариантах.

## 5. Что не входит

Спека свойств целиком, CRUD реестра, конструктор аспектов, формы по схеме, квалифицированные
имена — отдельные решения. Здесь зафиксирован только тип `ref` и его место в будущем
словаре.
