## Что установила разведка

Два факта ревизии 1 опровергнуты ревью (помечены ниже); остальные подтверждены пробоем.

**Тело в предложении показывается хуже всех остальных полей.** `updateRows` гоняет тело через
тот же цикл, что заголовок, метки и эмодзи (`lifecycle.ts:1434`, словарь `CORE_FIELD_LABELS`
на `lifecycle.ts:914`): строка «„План дня“: тело» и `after` — **весь новый markdown целиком**.
`before` не приезжает вовсе, и docblock честно объясняет почему: у полей вне аспектов
предусловий нет, «что было — покажет сама запись» (`lifecycle.ts:1403-1405`). Владелец утром
получает не «что изменится», а «вот новый текст, сличай сам».

**Поля аспектов, наоборот, показываются правильно.** «Было» берётся из СНЯТОГО предусловия,
а не из графа сейчас (`lifecycle.ts:1398-1402`) — именно с ним предложение сверится на
«Принять». Это решение V1.7, и оно остаётся: дифф тела встраивается рядом, а не вместо.

**Канонизация тела — одна на всех и живёт в `shared`.** `canonicalizeBody`
(`packages/shared/src/doc/convert.ts:391`) возвращает `{doc, body}`; executor гоняет через неё
каждое тело, пришедшее **строкой** (`executor.ts:795-815`, «ОДИН путь канонизации на всех»).
Значит дифф для показа можно считать той же функцией, и показанное совпадёт с применённым не
по совпадению, а по построению. TipTap 3.30 есть и в `shared`, и в `web`; дифф-библиотеки нет
ни одной.

**Тело в тул-контракте — строка, но exec-путь принимает и документ** *(факт ревизии 1
«bodyDoc существует только на UI-пути» опровергнут ревью)*. `entityUpdateUiInput` — UI-форма
(`contracts/tools.ts:68-70`), но `entityUpdateExecInput` — схема, которой executor разбирает
операции батча, то есть payload pending, — тоже принимает `bodyDoc`
(`contracts/tools.ts:137-138`). Executor пишет по нему веткой редактора со страховкой
`bodyPairFromDoc`/`projectionKeepsEverything` (`executor.ts:1340-1399`,
`convert.ts:446-502`); известные потери сериализации перечислены в докблоке
(`convert.ts:492-496`) и приняты именно потому, что правдой остаётся документ. Предложение
рутины приходит markdown'ом без блочных `id` (`UniqueID` — расширение редактора,
`entity-editor/extensions.ts`, `strip-ids.ts`).

**Предложение хранится неизменяемым payload'ом pending.** `runPropose` собирает операции,
снимает предусловия по прочитанной строке (`propose.ts:550-582`) и кладёт их в pending с
`tool: 'batch_execute'`, `input: {batch_id: pendingId, operations}` (`propose.ts:245-262`).
Читает их обратно `storedProposal` из `chat_messages.metadata` — **пробой по `run_id` с
`LIMIT 1` без порядка** (`lifecycle.ts:1286-1289`): корректно ровно потому, что V1 держит
«одно предложение на прогон». Applied-путь — `approvePending` → батч executor'а
(`lifecycle.ts:1079-1090`). Гашение (`closeOpenOfRun`) бьёт по `run.proposal.pending_id`,
а не пробой по `run_id` (`lifecycle.ts:278-282`).

**На чём держится сегодняшняя идемпотентность решения.** Id предложения детерминирован
(`dedupeKey = 'proposal:' + runId` → `pendingMessageId`, `propose.ts:181-182`), approve
ключует батч тем же id (`batchId: pendingId`, `pending.ts:367-371`) — отсюда replay при
двойном нажатии. Сериализация approve/reject — advisory-замок по pendingId **первым
statement'ом** транзакции (`acquirePendingLock`, `pending.ts:287-296`). Причину отказа
`rejectedReason` читает enum'ом из трёх значений и **незнакомую строку откатывает к
`'owner'`** (`pending.ts:243`, `:276`). `decideProposal` адресуется только `runId`
(`routers/routine.ts:202`). Пометки судьбы (`settleProposal`, `closeOpenOfRun`) пересобирают
объект `proposal` **явным списком полей** (`lifecycle.ts:1184-1189`, `:309-314`).

**Одна сущность — одна правка тела в предложении** (`propose.ts:435-444`): вторая правка того
же тела отвергается как коллизия. Потолок предложения — 50 операций
(`routines/constants.ts:15`). У `entity_create` предусловий нет (`propose.ts:200-205`).

**`proposal` в аспекте прогона — `.strict()`**: `pending_id`, `status`, `decided_at?`,
`mismatches?` (`schemas/aspects.ts:234-249`). Новое поле требует правки схемы и **пересева
реестра на проде до деплоя** (валидация — ajv по `aspect_definitions.schema`,
`aspects-validate.ts`); добавление optional-поля существующие прогоны не ломает, бэкфилл не
нужен — подтверждено ревью и ответом независимо.

**Правка значений полей в UI уже существует, но уже, чем казалось** —
`entity-detail/AspectCards.tsx`: сырая форма по фактическим полям (Р-9 V1), однако
**нескалярные значения — только чтение** (`AspectCards.tsx:45-57`, `:143`), а тип
восстанавливается по исходному значению (`coerce`, `:31-35`) — число с опечаткой даёт `NaN`.

**«Сервер уже умеет отвечать, есть ли у записи открытое предложение»** *(факт ревизии 1
опровергнут ревью)*. `openProposal` — булево «у **рутины** есть открытое предложение» в
`routine.overview` (`routers/routine.ts:261`). Вопрос «у **записи** есть открытое
предложение» сервер не отвечает ничем — нужен новый запрос (Ш1.3).

# Решения

## РЕШЕНИЕ Ш1.1. Дифф тела — блочный, с внутриблочным сравнением; строится только для живого предложения

Сравниваются два канона: текущее тело записи и предложенный markdown, оба через
`canonicalizeBody`. Единица — блок документа (абзац, пункт списка, заголовок, строка таблицы).
Сопоставление — по нормализованному тексту блока, **не по `id`**: у предложенного markdown их
нет, и притворяться, что есть, значит сопоставлять по позиции и объявлять перестановку полной
заменой.

Изменённые блоки дополнительно сравниваются **внутри — по словам**. Без этого перенос
«10:00 → 14:00» рисуется как удаление абзаца и добавление другого, и владелец утром опять
сличает два текста глазами — то есть работа не сделана.

Выход — последовательность `{ kind: 'same' | 'added' | 'removed' | 'changed', before?, after?,
parts? }`, где `parts` заполнены только у `changed`.

**Дифф считается только при `status === 'pending'`** (ревизия 2, С1 ревью). Для решённого
предложения дифф против текущего тела бессмыслен: после `approved` он весь `same`, после
отказа и чужих правок — шум. Решённая карточка показывает статус, объяснение и ссылку на
аудит; дифф из журнала (`prior.body` action'а) — шов, не этот срез. Заодно это естественный
потолок нагрузки: открытых предложений у рутины не больше одного (V1.8).

**Если тело записи менялось после составления, дифф не строится** (ревизия 2, С1 ревью).
У тела нет снятого предусловия — только `expectedUpdatedAt` (`propose.ts:581`), поэтому
«было» диффа — граф сейчас. Разошёлся `updated_at` записи с `expectedUpdatedAt` операции —
вместо диффа пометка «тело изменилось после составления»: дифф против нового тела нарисовал
бы согласие там, где «Принять» ответит отказом, — ровно то, от чего V1.7 защищает поля.

## РЕШЕНИЕ Ш1.2. Дифф для показа считает сервер; в режиме правки клиент пересчитывает

`routine.proposal` дополняется диффом на тех строках, где правится тело. Карточка и слой
рисуют готовое.

Не клиент — по двум причинам, и первая тяжелее второй: в карточке треда **текущего тела нет
вовсе** (карточка знает только `runId`), а сервер его и так читает, чтобы снять предусловия.
Вторая — карточка и экран записи обязаны показывать одно и то же, а две точки вызова общей
функции расходятся ровно тогда, когда одну поправят.

**В режиме правки дифф пересчитывает клиент** (ревизия 2, С9 ревью): на экране записи текущее
тело есть — довод про карточку к слою не относится, — а гонять каждое нажатие клавиши на
сервер нельзя. Функция диффа поэтому живёт в `shared` и вызывается с обеих сторон (открытый
вопрос 1).

Инвариант «показано = применится» расщеплён ревизией 2 (см. Инварианты, п. 1): для
неправленого пути он проверяется тестом на сервере — применить предложение и сверить канон
применённого тела с `after`-стороной диффа; для правленого он становится гарантией
bodyDoc-пути (Ш1.11).

## РЕШЕНИЕ Ш1.3. Карточка — сводка, экран записи — подробность; предложений у записи может быть несколько

**Карточка предложения** (тред рутины и экран прогона) остаётся точкой встречи: объяснение
прозой, перечень затронутых записей, число правок в каждой, свёрнутый дифф тела и кнопки.
Полный дифф в ленте треда не разворачивается — предложение из пяти записей превратило бы ленту
в простыню.

**Карточка получает свой `pendingId` и сверяет его с живым** (ревизия 2, С3 ревью). Сегодня
`ProposalCard` знает только `runId` (`renderCards.tsx:107`, `cards/types.ts`), а Ш1 вводит
второе предложение на прогон: без сверки карточки исходного и правленого рисовались бы
одинаково. Совпал с `view.pendingId` — живое с кнопками; не совпал — «заменено правкой
владельца», без кнопок, со ссылкой на живое.

**Экран записи** получает слой предложения: плашка сверху («Предложение рутины „Утро“ — 3
правки»), тело диффом, правки полей строками под ним, те же кнопки. Слой — не вкладка:
вкладка спрятала бы предложение от того, кто открыл запись обычным путём, а именно так
владелец в неё и заходит.

**Запрос «открытые предложения по записи» — новый** (ревизия 2: факт «сервер уже умеет»
опровергнут — `openProposal` отвечает по рутине, не по записи). Форма — containment-проба
`{pending: {input: {operations: [{input: {id}}]}}}` (GIN `jsonb_path_ops` её берёт) с отсевом
по статусу прогона (`proposal.status === 'pending'`, прогон не в архиве). Ответ —
**список**: две рутины могут трогать одну запись, и слой показывает все открытые предложения,
решение по каждому — своё. Выбирать одно нельзя: это скрыло бы второе.

## РЕШЕНИЕ Ш1.4. Правится тело и значения полей; неизменен набор ключей «операция + аспект + поле»

Владелец правит:
- **тело** — редактором в слое предложения; правка начинается с ПРЕДЛОЖЕННОГО текста, а не с
  текущего (иначе «поправить предложение» превращается в «написать заново»). Редактор слоя
  монтируется **без** `useBodySave` и без черновиков (ревизия 2, С8 ревью): автосохранение
  писало бы предложенный текст в саму запись с первого штриха и бампало `updated_at` —
  предложение само делало бы себя `stale`. Клиент не шлёт правку тела, если документ не
  отличается от предложенного (сравнение по смыслу со снятием блочных id, `strip-ids.ts`) —
  открытие редактора без правки не порождает нового предложения;
- **значения полей** — прямо в строке правки, формой из `AspectCards` (та же сырая форма, что
  на записи: enum текстом — принято Р-9). Нескалярные значения не правятся — как и на записи
  (см. «Известные границы»).

Чего сделать нельзя — сформулировано ревизией 2 жёстче, чем «набор операций неизменен»
(Б3 ревью): **неизменен набор ключей `(index, aspect?, field)`; тело правится только в
операции, где `body` был**. Причина та же, что у запрета новых операций, и она техническая:
предусловие снимается по каждому полю патча (`propose.ts:555-567`), CAS тела — только при
`body` (`:581`); правка, добавившая полю новый ключ, была бы записью **без предусловия** —
то есть тем самым «прочитать граф на минуту позже и молча расширить окно», только полем, а не
операцией. Сервер проверяет равенство множества ключей до создания нового предложения.
Добавить или убрать операцию нельзя по той же причине; убрать правку — отклонить предложение
целиком; тронуть что-то ещё — обычное действие после принятия.

Названная мелочь: правка «вернуть значение как было» операцию не удаляет (набор неизменен) —
применится запись прежнего значения, и в журнале появится действие без фактического
изменения. Не дефект, но владелец увидит эту строку в ленте.

## РЕШЕНИЕ Ш1.5. Принятие с правками — одно действие владельца и лестница транзакций

Владелец правит и жмёт «Принять» — второго шага «сохранить правку» нет.

Формулировка ревизии 1 «в одной транзакции» была ложью о коде и снята ревью (Б1): `execute`
открывает собственный `withIdentity`-tx и вложения не допускает (`pending.ts:354`),
`rejectPending` — свой (`pending.ts:440`). Вместо неё — лестница, у которой каждый шов назван.

**Вход.** `routine.decideProposal` принимает `pendingId` — тот, что владелец видел на
карточке, — и необязательный `edits`:
`{ body: [{ index, bodyDoc }], fields: [{ index, aspect?, field, value }] }` — адресация по
номеру операции и полю, то есть ровно по тем строкам, которые владелец видел. Тело едет
**документом**, не markdown'ом (Ш1.11). Расхождение `pendingId` с живым
`proposal.pending_id` прогона → `already`: «принимаю то, что вижу» — обязательство сервера,
а не интерфейса (Б2 ревью: с двумя предложениями на прогон адресация одним `runId` молча
сливала бы две сессии правки — индексы легли бы на чужой payload с той же раскладкой).

**Id нового предложения детерминирован содержимым правки**:
`pendingMessageId(owner, 'edit:' + <исходный pendingId> + ':' + hash(edits))`. Не просто
`'edit:' + исходный` — тогда две **разные** правки схлопнулись бы в один PK, и вторая вкладка
применила бы чужую правку с ответом «applied» (`appendMessageIdempotent` возвращает исходную
запись). Одинаковая правка — честный replay, разная — разные id. `hash` считается по
канонической сериализации `edits` (стабильный порядок ключей, каноническая JSON-форма
документа) — правило сериализации фиксирует планирование (открытый вопрос 3).

**Лестница** (P1 — исходное предложение, P2 — правленое):

1. **Один tx**: advisory-замок P1 **до первого чтения состояния этого pendingId** и не
   отпускается до конца tx (контракт `acquirePendingLock`; формулировка исправлена по факту
   реализации — «первым statement'ом» было неверно: первыми идут два statement'а
   `withIdentity`, задающие личность для RLS, замок третий) →
   перечитка: P1 не `pending` → `already` с его статусом → `rejectPending(P1, 'edited')`
   **и** `createPending(P2)` тем же tx. Metadata P2 несёт ссылку `edited_from: P1` (Ш1.8,
   п. 2) — она же обратный индекс правила возобновления. Требуется tx-вариант
   `rejectPending` (сегодня он открывает свой tx) — правка контракта `policy/pending.ts`,
   отдельная задача планирования. Атомарность шага закрывает разом: сироту P2 (проигрыш
   гонки за P1 откатывает и его рождение), потерю правок при сбое (обе записи либо легли,
   либо нет) и гонку двух правок (проигравший конкурент видит `alreadyRejected` и второго
   P2 не заводит).
2. Перевод `proposal.pending_id` прогона на P2 плюс `edited_from` — CAS на весь объект
   `proposal`, как в `settleProposal`.
3. `approvePending(P2)` — полный конвейер, ревалидация, `batchId = P2`.
4. `settleProposal` по исходу (`approved` | `stale` с расхождениями).

**Причина отказа `'edited'`** — новая, со своим текстом ленты («Предложение заменено правкой
владельца»). Enum `rejectReason` (`pending.ts:243`), `REJECT_CONTENT` и
`STATUS_BY_REJECT_REASON` (`'edited'` → статус `superseded` на прогоне) расширяются **тем же
релизом**, что первый писатель причины: fallback чтения откатывает незнакомую строку к
`'owner'` (`pending.ts:276`), и без синхронного расширения правка владельца читалась бы
историей как «владелец отклонил».

**Правило возобновления** (крэш-окно между шагами; ревизия 2 по реплике ревьюера).
`decideProposal` по предложению, отклонённому причиной `'edited'`, не отвечает голым отказом:
сервер находит дитя по ссылке `edited_from`, **доводит шаг 2** (самолечение указателя), и
дальше — по совпадению: hash правки сходится с id дитяти → идемпотентно довести шаги 3–4
(двойной тап проходит лестницу целиком и получает replay); не сходится или правки нет →
ответ «заменено правкой владельца, живое предложение — вот» (расширение
`DecideProposalResult`, форма за планированием) — клиент перечитывает и показывает P2.
Дальнейшая правка P2 — обычная правка: лестница рекурсивна, живое предложение всегда одно.

**Исходы сбоя по швам, названные ценой:** крэш после шага 1 — лечится первым же запросом
(правило возобновления); структурная VALIDATION на шаге 3 (владелец ввёл значение сырой
формой) — P2 живо и правимо, владелец правит и жмёт ещё раз — та же цена контракта §7.10,
что в V1 («ошибка возможна после Принять»); `stale` на шаге 3 — P2 гаснет `stale` с разбором
расхождений, как сегодня.

**`storedProposal` переводится на адресацию по `pending_id`** (Б4 ревью — лучшая находка:
проба по `run_id` с `LIMIT 1` при двух предложениях на прогон отдаёт произвольное, и view
показал бы операции P1 под id P2). Проба — `{pending: {id}}`, как у `findPendingMessage`.

Если `edits` пуст и `pendingId` совпал с живым — путь ровно сегодняшний: ни P2, ни лишнего
объекта в истории.

## РЕШЕНИЕ Ш1.6. Предусловия не переснимаются никогда

Ни при правке текста, ни при правке значения. Предусловие описывает **граф на момент
составления**, правка меняет **намерение владельца** — это разные вещи, и смешивать их значит
подменять наблюдение желанием.

Следствие, которое надо принять сознательно: если граф за это время разошёлся, правленое
предложение получит тот же `stale`, что получило бы неправленое, — владелец потеряет
потраченное на правку время (см. «Известные границы»).

Граница следствия — уже, чем звучала в ревизии 1 (С7 ревью): `stale` гарантирован **полям с
предусловиями** и **телу** (CAS `expectedUpdatedAt`, снятый при составлении,
`propose.ts:581`, — сохраняется как есть). `title`, `tags`, `emoji`, `archived`, `meta` не
защищены ни предусловием, ни CAS — правленые или нет, они затирают чужую правку молча. Это
граница V1, не новая дыра Ш1; вписана в «Известные границы».

## РЕШЕНИЕ Ш1.7. Применение остаётся работой прогона

Действия применённого предложения пишутся с источником `routine` и `run_id` прогона — так же,
как у неправленого (V1, расщепление атрибуции Р-7).

Соблазн записать правленое применение как `ui` есть, и он ошибочен: откат прогона инвертирует
**только** действия источника `routine` (V1, финальное ревью; `rollback.ts:154`), и правленое
предложение выпало бы из отката — то есть «отменить прогон» перестало бы отменять его главный
результат.

Факт правки фиксируется не источником, а пометкой на предложении (Ш1.8). Нести ли
`edited_from` ещё и в самом action журнала — вопрос владельцу (В-1 ниже); рекомендация
контроллера и ревью совпала: нести — журнал отвечает на «кто это написал», и «рутина» без
оговорки неполон; цена — поле в `pendingRecord` и провод через `execute` тем же приёмом, что
`actor_grant_id`/`run_id` (`pending.ts:361-366`).

## РЕШЕНИЕ Ш1.8. Происхождение правленого предложения записывается в двух местах

1. **В аспекте прогона** — `proposal.edited_from: uuid` (id исходного pending). Объект
   `.strict()` (`schemas/aspects.ts:234-249`), поэтому изменение схемы обязывает к **пересеву
   реестра на проде до деплоя**; optional-поле существующих прогонов не ломает, бэкфилл не
   нужен (подтверждено ревью и ответом). Поле обязаны протаскивать **оба** места, которые
   пересобирают объект `proposal` явным списком полей: `settleProposal`
   (`lifecycle.ts:1184-1189`) и `closeOpenOfRun` (`:309-314`) — иначе первый же патч статуса
   молча оторвёт цепочку (С5 ревью).
2. **В карточке нового pending** — ссылка `edited_from` на исходную карточку, чтобы лента
   треда читалась как «рутина предложила → владелец поправил и принял», а не как два
   независимых события. Эта же ссылка — обратный индекс правила возобновления Ш1.5.

Это же и есть данные, на которых будет учиться классификатор V2: пара «предложено А — принято
А′». Никакого обучения сейчас не строится — сохраняется только связь; следующему прогону в
историю едет одно поле «принято с правками» (из `edited_from`) — это контекст, не обучение.

## РЕШЕНИЕ Ш1.9. Правка добавляет ровно одну гонку — и вот чем она закрыта

Формулировка ревизии 1 «гонок правка не добавляет» опровергнута ревью (Б2): правка меняет ключ
идемпотентности. Новая гонка одна — **два решения с правками по одному предложению** (две
вкладки, двойной тап), — и закрыта она тремя механизмами Ш1.5 вместе:

- **адресация по `pendingId`**: решение по не тому предложению, что живо, → `already`;
- **атомарный шаг 1**: гонку за P1 выигрывает ровно один — проигравший видит
  `alreadyRejected('edited')` и второго P2 не заводит; молча не проигрывает никто — ответ
  называет живое предложение;
- **детерминированный id по содержимому правки**: двойной тап той же правки — полный replay
  лестницы, не второе применение; другая правка — другой id, и её судит правило
  возобновления.

Прежние две проверки на «Принять» остаются как были: статус ещё `pending` и предусловия
сходятся; правка меняет только `after`-значения, которые ни с чем не сверяются. Три исхода
не меняются по форме: `applied`, `stale` со списком расхождений, `already` с текущим
статусом. Гашение новым прогоном (V1.8) во время правки: `supersedeOpen` бьёт в P1 по
`run.proposal.pending_id` (`lifecycle.ts:278-282`) — кто первым взял замок P1, тот и решил;
проигравшая правка получает `already`, и владелец видит, чей это был ход.

## РЕШЕНИЕ Ш1.10. Потолок диффа — по числу блоков; спаривание изменённых блоков задано явно

Квадратично сравнение **по числу блоков**, и потолок ревизии 1 мерил не то (С6 ревью: 64 КБ
чеклиста — это тысячи блоков и десятки миллионов ячеек на каждый показ). Ревизия 2:

- сопоставление блоков — Myers `O(ND)`, не наивный LCS;
- потолок — **число блоков** тела (не байты); сверх потолка строка показывается прежней
  формой («тело» + предложенный текст) с пометкой «слишком большое тело — дифф не построен»;
- внутриблочное сравнение — только для **спаренных** блоков и с потолком длины блока;
- правило спаривания `removed`/`added` в `changed` задаётся явно: позиция внутри замены плюс
  порог похожести — без него приёмка 4 неопределена на реальном плане дня, где один пункт
  изменён, а соседний вставлен.

Дифф считается только для живого предложения (Ш1.1) — открытых не больше одного на рутину
(V1.8), фоновой нагрузки потолок не создаёт. Конкретные числа (потолок блоков, порог
похожести) — планированию, замерить на реальных телах.

## РЕШЕНИЕ Ш1.11. Правка тела едет документом, не markdown'ом

`edits.body` несёт `bodyDoc`; при сборке P2 операция меняет форму `body` → `bodyDoc`
(XOR-схема `entityUpdateExecInput` это допускает; `expectedUpdatedAt` сохраняется как есть —
Ш1.6).

Причина — Б5 ревью, и она тяжелее, чем кажется. В форме ревизии 1 (`markdown`) правленый
документ шёл `serialize` → `canonicalizeBody` → в БД ложилась `parse(serialize(D))` —
проекция проекции. Известные потери сериализации (`convert.ts:492-496`: блок кода становится
абзацем, подпись ссылки обрезается) для редактора приняты потому, что правдой остаётся
`body_doc`; в markdown-пути правдой становилась бы ровно потерянная сторона, и страховка
`bodyPairFromDoc`/`projectionKeepsEverything` (`convert.ts:446-502`) не работала бы вовсе.
Инвариант «показано = применится» для правленого тела был бы не строгим, а ложным.

С `bodyDoc` он становится гарантией редактора: в БД ложится показанный документ, тем же
путём и с той же страховкой, что обычное сохранение тела.

## Инварианты, которые проверяются, а не подразумеваются

1. **Показанное применяется** — в двух половинах (ревизия 2): **(а)** неправленое: канон
   применённого тела равен `after`-стороне серверного диффа (тест на сервере);
   **(б)** правленое: в БД ложится документ, который показывал редактор (гарантия
   bodyDoc-пути, Ш1.11).
2. **Правка не трогает предусловия и не расширяет их множество.** Набор `precondition` в
   новом payload'е побайтно равен исходному, **и** множество ключей
   `(index, aspect?, field)` затронутых полей равно исходному (Б3: равенства предусловий
   мало — новый ключ был бы записью без предусловия при неизменных предусловиях).
3. **Число операций сохраняется.** `operations.length` нового pending равен исходному.
4. **Правленое откатывается.** Откат прогона инвертирует применённое правленое предложение так
   же полно, как неправленое.
5. **Двойное нажатие безопасно.** Та же правка — тот же id — replay, не второе применение;
   без правок — сегодняшний replay по `batchId`.
6. **Исходное предложение мертво.** После правки его статус — `superseded` (причина
   `'edited'`), кнопок под ним нет; `decideProposal` по нему отвечает не голым отказом, а
   указанием на живое (правило возобновления Ш1.5).
7. **Прогон указывает ровно на одно живое предложение.** Прочие читаются только по явному
   id (`storedProposal` — по `pending_id`, не пробой по `run_id`); цепочка предыдущих — по
   `edited_from`, и её протаскивают оба писателя объекта `proposal` (Ш1.8).
8. **Владелец различает своё и рутинное.** Карточка принятого правленого предложения говорит,
   что оно правлено, и ведёт к исходному; карточки исходного и правленого различимы
   (`pendingId` на карточке, Ш1.3).
9. **Правка не расширяет права.** `edits` меняет значения в уже разрешённом наборе ключей;
   проверки `orbis_propose` по объекту (рутины, назначения, прогоны) остаются на применении.

## Известные границы

- **Правки владельца теряются при `stale` — но не бесследно.** Применять нечего, предложение
  мертво; правленый payload остаётся в карточке P2 в треде, перенести его в запись владелец
  должен сам. Живое лечение — не копить правку, а править и принимать сразу. Кнопка
  «применить как свою правку» (источник `ui`, свежий снимок) — вопрос владельцу В-2: она
  вводит путь применения мимо прогона.
- **Строки `entity_create` не правятся.** У создания нет предусловий (`propose.ts:200-205`),
  а правка заголовка новой задачи — это правка записи, которой ещё нет. В ревизии 1
  подразумевалось, теперь названо.
- **Нескалярные значения полей не правятся** — как и на самой записи (`AspectCards`: теги,
  `recurrence`, `aliases` — только чтение). Число с опечаткой в сырой форме даёт `NaN` →
  VALIDATION после «Принять» — исход после кнопки, принятая цена контракта §7.10.
- **Поля вне аспектов не защищены от чужой правки.** `title`/`tags`/`emoji`/`archived`/`meta`
  не имеют ни предусловия, ни CAS — затирают чужое молча, правленые и неправленые одинаково.
  Граница V1, Ш1 её не расширяет и не чинит.
- **Дифф не понимает перестановку блоков.** Перенос абзаца выше показывается как удаление и
  добавление. Лечится только сопоставлением по содержимому с порогом похожести — отложено до
  первой жалобы на живом использовании.
- **Правка полей — сырой формой** (Р-9 V1): enum вводится текстом, дата — строкой. Наследуется
  вместе с `AspectCards`; отдельной работой не становится.
- **Внутриблочный дифф — по словам, не по символам.** Для русского текста этого достаточно; для
  правки внутри слова покажет слово целиком.
- **Слой предложения — только на записи, которую предложение трогает.** Создание сущности
  (`entity_create`) показывать негде: записи ещё нет. Такие операции остаются строками в
  карточке.

## Что НЕ входит

- Выборочное принятие отдельных строк или операций (владелец выбрал полное принятие).
- Добавление операций в предложение (Ш1.4).
- Обучение классификатора на парах «предложено — принято» — это V2; здесь только связь и одно
  поле контекста в истории прогонов.
- Уведомление о готовом предложении — это V3; deep-link в слой
  (`orbis://entity/<id>?proposal=<runId>`) фиксируется сейчас как шов: уведомление обязано
  вести в конкретное предложение, не в приложение вообще.
- Дифф для решённых предложений из журнала (`prior.body` action'а) — шов (Ш1.1).
- Дифф для тикетных прогонов ADE: предложений там нет, там чекпойнты.
- Правка предложений, пришедших не от рутины (подтверждения чата) — у них другой смысл:
  за ними стоит разговор, который только что был.
- Кнопка «применить как свою правку» после `stale` — вопрос В-2, по умолчанию не входит.
- Сравнение закреплённых версий тела между собой (С11) — соседняя механика, отдельная работа.

## Приёмка

1. Рутина предложила правку тела «Плана дня» — карточка показывает свёрнутый дифф, а не
   полный текст.
2. Тап по записи в карточке открывает запись со слоем предложения: тело диффом, поля строками.
3. Открытие той же записи обычным путём показывает плашку «есть предложение».
4. Изменённый блок показывает внутреннее различие: «10:00» зачёркнуто, «14:00» добавлено.
5. Правка текста в слое и «Принять» — в записи ровно тот документ, что показывал редактор
   (проверяется чтением записи, включая блок кода и ссылку с подписью — потери сериализации
   Ш1.11).
6. Правка значения поля (время задачи) и «Принять» — применяется правленое значение.
7. Принятие без правок работает ровно как до этой работы; нового pending не появляется.
8. Открытие слоя, правка в редакторе и уход без «Принять» — запись не изменилась,
   `updated_at` не сдвинулся, нового предложения не появилось.
9. После принятия с правками исходное предложение в треде — «заменено правкой владельца», без
   кнопок, со ссылкой на живое; новое — «принято».
10. «Отменить последнее» после принятия правленого предложения возвращает граф в исходное
    состояние.
11. Откат прогона после принятия правленого предложения инвертирует применённое.
12. Граф разошёлся между составлением и принятием → «устарело» со списком расхождений,
    независимо от того, правил ли владелец; тело записи менялось → в слое вместо диффа
    пометка «тело изменилось после составления».
13. Новый прогон погасил предложение, пока владелец правил → «решено без тебя», правки не
    применяются.
14. Двойное нажатие «Принять» с правками — одно применение (replay той же лестницы).
15. Две вкладки с разными правками одного предложения: применяется одна, вторая получает
    «заменено правкой владельца» с указанием живого — молча не проигрывает никто.
16. Тело больше потолка блоков → прежняя форма показа с пометкой, кнопки работают.
17. Предложение из нескольких записей: карточка перечисляет все, слой открывается для каждой.
18. Две рутины с открытыми предложениями по одной записи: слой показывает оба, решение по
    каждому — своё.

## Вопросы владельцу

- **В-1. Нести ли `edited_from` в самом action журнала §7.8.** Технически применение обязано
  остаться `routine` (Ш1.7). Вопрос — достаточно ли пометки на предложении, или запись
  журнала должна сама говорить «правлено владельцем». Рекомендация (контроллёр и ревью
  сошлись): нести — журнал отвечает на «кто это написал»; цена — поле в `pendingRecord` и
  провод через `execute`, как у `actor_grant_id`.
- **В-2. Кнопка «применить как свою правку» после `stale`.** Правки сохранены в payload'е P2;
  кнопка применяла бы их источником `ui` со свежим снимком — путь применения **мимо**
  прогона, его надо принимать осознанно, а не как удобство. По умолчанию — не входит.

   `convert.ts` или отдельный пакет. Разведке проверить, не тянет ли `shared` лишнего в
   бандл web (там уже TipTap, но дифф — новый код на обеих сторонах; в режиме правки его
   зовёт клиент — Ш1.2).
2. **Tx-вариант `rejectPending`** — шаг 1 лестницы Ш1.5 требует гашения P1 и создания P2 в
   одном tx; сегодня `rejectPending` открывает свой. Правка контракта `policy/pending.ts` —
   отдельная задача, не деталь реализации.
3. **Каноническая сериализация `hash(edits)`** — стабильный порядок ключей и каноническая
   JSON-форма `bodyDoc`; без неё детерминизм id вырождается молча, а с ним — replay двойного
   тапа и различение «свой ретрай / чужая правка».
4. **Форма ответа «заменено правкой»** — расширение `DecideProposalResult` (правило
   возобновления Ш1.5 отвечает указанием на живое предложение); согласовать с клиентом
   карточки.
5. **Слой предложения и вкладки detail-экрана** — вкладки управляются из `DetailScreen` (один
   источник правды, `1d51c46`). Проверить, как плашка уживается с вкладкой «Версии» и не
   ломает ли ленивую загрузку экрана; редактор слоя — без `useBodySave` (Ш1.4), проверить,
   что монтирование второго редактора на экране не дерётся с первым за черновики и фокус.
6. **Числа Ш1.10** — потолок блоков и порог похожести спаривания взяты дизайном без замера.
   Померить на реальных телах и подвинуть.

Снятые вопросы ревизии 1: адресация `edits` (решена — `pendingId` + `index`, `storedProposal`
переводится на `pending_id`); пересев реестра (подтверждён — optional-поле, без бэкфилла,
пересев до деплоя).

## Прецеденты с рынка (ревалидация 2026-08-20)

Добавлено по `reviews/2026-08-20-market-rescan-validation.md` (части I.4, III.2) — три факта,
усиливающие принятую конструкцию, и два правила к реализации:

1. **Nimbalyst решил нашу развилку противоположно — и заплатил.** У них предложение **и есть
   тело** («AI edits are written to disk immediately»), неизменяемым хранится снимок «до»
   (pre-edit tag), «ручная правка + сохранение» гасит предложение. Цена подтверждена их багом
   **NIM-402**: «Accept-All re-applies a per-group-rejected change» — при базе «диск — источник
   истины» пересчёт baseline теряет акт отклонения. Их довод (чужого исполнителя нельзя
   заставить ходить через свой тул — ловим постфактум watcher'ом) к нам не применим: наш
   исполнитель ходит через `mcp__orbis__*` по построению. Конструкция «новое pending с
   неизменяемым payload» — теперь аргумент с прецедентом, а не вкусовщина.
2. **Правило baseline** (Nimbalyst, тест «Baseline Tracking»): «subsequent AI edits should use
   accepted state as baseline, not original» — следующая правка агента сравнивается с
   **принятым** состоянием, не с исходным. Проверить, что наш конвейер (предусловия снимаются
   при формировании нового предложения) даёт это свойство по построению.
3. **Атрибуция в контракте показа**: `DiffState` Nimbalyst наружу несёт `sessionId`; наш
   аналог — `run_id` в карточке предложения, держать его в контракте показа, не только в
   журнале.
4. **Tana — независимая сходимость**: внешние MCP-клиенты «create proposals attached to a
   session, and you review, edit, or discard them, **just like changes from Tana's built-in
   AI**». Два следствия: единый контур приёмки для внутреннего и внешнего AI — проверить, что
   внешний MCP-клиент физически не может писать мимо приёмки; «предложения привязаны к сессии»
   — их группировка пачки в один принимаемый объект совпадает с нашим батчем предложения.
5. **Preflight пакета** (oh-my-pi): «multi-section patches are preflighted up front so a
   partial batch never lands» — все операции проверяются до записи; полу-применённое
   состояние, которое Undo не разберёт, недопустимо. Для лестницы Ш1.5 это требование к
   каждому шагу, где батч трогает больше одной записи.
