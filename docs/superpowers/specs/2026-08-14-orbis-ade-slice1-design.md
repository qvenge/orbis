## Что установила разведка

**Спека уже разделена надвое, и разделение никто не проверяет.** В коде стоит **2215 ссылок
на §-разделы PRD в 264 файлах** — связь код↔документ существует и поддерживается вручную.
`packages/shared/src/contracts/budget.ts` — уже контракт, отдельный от `docs/prd/03-budget.md`,
и его jsdoc ссылается на разделы PRD. Расхождение видно невооружённым глазом: PRD §2.4 говорит
«`daily_pace` отрицателен» при перерасходе, контракт на строке 16 — «`dailyPace = null` при
`remaining < 0`». Один из двух документов врёт сегодня, и ничто этого не ловит.

**Модель сущностей уже рассчитана на проекты.** §2.2 перечисляет «Проекты» прямо в колонке
сущностей, а историю чатов и provenance импорта — в колонке отдельных таблиц. §4.2 задаёт
семантику `parent` дословно как «проект → задача». `orbis/task` (§3.2) несёт шесть статусов
`inbox | planned | in_progress | waiting | done | cancelled`, приоритет, срок, `completed_at`,
`effort_min` и `waiting_for` — «кого/чего ждём».

**Скоупы прав заложены, но не реализованы.** `agent_grants.scope` (§4.14) — `text NOT NULL
default 'full'` с комментарием «задел под скоупы; значение пока одно». Таблица, экран
«Настройки → Агенты» и немедленный отзыв по одному доступу уже работают.

**`entity_origins` под аудит агента не приспособлена.** Она про импорт: уникальность
`(owner_id, namespace, external_id)`, undo импорта физически удаляет строки.

**Редактор строится параллельно и садится первым.** Реализация идёт в `notion-editor`
(worktree `.claude/worktrees/notion-editor`): на 2026-08-14 там 8 коммитов — миграция `0007`
(`body_doc` + trigram-индекс), бэкфилл, пакет `packages/shared/src/doc/`; план v2 редактора
(`85c70ab`) заменил «байт-в-байт» **канонизацией** — `body` в БД всегда `serialize(parse(md))`,
байт-в-байт остаётся только для сидов. На `main` этого ещё нет (последняя миграция — `0006`).
**Решение владельца 2026-08-14: срез 1 стартует после посадки редактора в `main`** — экраны
строятся сразу на трёх табах Р9 «Сущность · Детали · Тред», миграции среза нумеруются после
редакторских, а обещания о восстановлении тел даются в терминах канона, не байтов (С11). Р5 и
Р13 редактора резервируют блочный агентский контракт `body_replace_block` / `body_insert_after`
/ `body_delete_block` и фиксируют, что сегодняшний `entity_update{body}` — строковый,
переписывает тело целиком, и при этом парсинг выдаёт блокам новые id.

**ФАКТ СПАЙКА. Круг «спека → работа → отчёт» замыкается сегодня.** `@agentclientprotocol/claude-agent-acp`
0.66.0 прогнал задачу без единого ключа в окружении, списавшись из подписки — в потоке пришло
`_claude/rateLimit: {rateLimitType: "five_hour", overageStatus: "rejected", isUsingOverage:
false}`. Агент получил спеку требования через MCP-инструмент, выполнил, **сам проверил
приёмочный критерий** и отчитался обратно. 35 секунд, три запроса разрешения.

**ФАКТ СПАЙКА. Транспорт MCP `type: "acp"` молча игнорируется.** Протокол объявляет транспорт,
где MCP-сервер предоставляет сам клиент по ACP-каналу; `claude-agent-acp` принимает параметр
**без ошибки**, но инструменты не появляются, а `codex-acp` честно объявляет `"acp": false`.
Рабочие сегодня — `stdio` и `http`.

**ФАКТ СПАЙКА. Адаптеры process-local.** Документация Codex App Server прямо предупреждает, что
это не HTTP API для веб-приложений. Orbis с Render не может рулить агентом напрямую.

**Облачный режим не даёт интерактивных ворот.** Рутины Claude Code выполняются автономно: ни
выбора режима прав, ни запросов подтверждения во время прогона. Коннекторы берутся из аккаунта
claude.ai (локальные `claude mcp add` туда не попадают), их трафик идёт через серверы Anthropic
мимо сетевого allowlist. `POST /v1/claude_code/routines/{trig_…}/fire` создаёт новую сессию,
**ключа идемпотентности нет** — ретрай вебхука создаёт вторую сессию.

# Рамка программы

## РАМКА Р1. Источник истины разделён по природе содержимого

Требование «код не может отклоняться от спеки» держится на одном механизме: дельта спеки и
дельта кода приезжают **одним неделимым изменением**, и проверка не пускает половину. Такая
единица есть только в git — коммит и пул-реквест. Если спека лежит в базе, код мержится в одном
месте, а спека меняется в другом, и «неделимо» вырождается в «мы постараемся».

Поэтому:

| Содержимое | Где живёт | Почему |
|---|---|---|
| Контракты, инварианты, приёмочные критерии | git, рядом с кодом | только там общая с кодом единица изменения |
| Экономика, маркетинг, стратегия, план | Orbis | гейт их не проверит, git ничего не даёт |
| Продуктовое описание | Orbis | меняется по своим причинам, не по правкам кода |
| Архитектура, карта модулей, граф зависимостей | **выводится из кода** | рукописная карта устаревает за месяц |
| Задачи, исполнители, прогоны, статусы, обсуждение | Orbis | этого в git нет и быть не должно |

Из интерфейса разделение не видно: открыл проект — видишь всё. Часть страниц правится в Orbis,
часть помечена «отражение репозитория, правка через PR». Orbis **предлагает** дельту спеки
через PR и не пишет в git в обход.

**Судьба действующего PRD-корпуса** (решение владельца 2026-08-14, полный объём важнее скорости).
Корпус не переносится разовым актом — он трансформируется по правилам, и правила — часть рамки:

1. **§-адрес стабилен, пока на него ссылается код.** ~2474 ссылки в 270 файлах — актив, который
   нельзя рвать: раздел не удаляется и не переезжает, пока grep по его адресу не пуст. Со среза 2
   это держит механизм, а не дисциплина: линт битых §-ссылок в CI, со среза 3 — дрейф-гейт.
2. **Перенос факта неделим**: текст в новый дом + шапка «superseded → адрес» в старом +
   обновление всех ссылок — одним изменением. Прецедент механизма — D10.
3. **Контрактная часть (01, 02, 03) никуда не «переезжает»** — в срезе 2 она разбирается на
   EARS-критерии у модулей; производный реестр даёт новую адресацию (REQ-id), и код постепенно
   переводится с § на REQ-id. Файл раздела живёт, пока жив последний §-референс на него.
4. **Журнал решений (04) остаётся в git навсегда**: решения обосновывают код и адресуются его
   историей.
5. **Продуктовая часть (00: vision, боли, метрики, роадмап, стратегия)** — единственная, что
   переезжает в Orbis содержимым; в git остаётся файл-указатель со статусом superseded. Новые
   живые продуктовые документы заводятся сразу в Orbis, не в `docs/`.

## РАМКА Р2. Гейт строится на двух уровнях из трёх

Уровень 1 — **якорь и AST-хеш**: кусок спеки привязан к символу кода, хешируется нормализованное
AST. Переформатирование дрейфом не считается, изменение сигнатуры — считается.

Уровень 3 — **приёмочные критерии как тесты**: связь двусторонняя, критерий без теста — дыра,
тест без критерия — незаказанная работа. Единственный уровень, проверяющий поведение.

Уровень 2 — **граф намерения против графа улик** (объявленные зависимости против реальных
импортов) — **отложен**. На монорепо из трёх пакетов он даёт меньше, чем стоит своего
статического анализатора; правила направления зависимостей уже описаны в
`docs/implementation/00-architecture.md` и позже проверяются малой кровью.

## РАМКА Р3. Критерии в EARS живут у кода; реестр требований — производный

Критерий записывается как `КОГДА <условие> СИСТЕМА ДОЛЖНА <поведение>` и лежит там, где его
можно проверить: есть модуль-владелец — в его контракте рядом с кодом; требование сквозное —
отдельным файлом спеки, тоже в git, с якорями к нескольким символам.

**Реестр требований никто не пишет руками.** Его собирает CLI из всех критериев, откуда бы они
ни были, и Orbis потребляет именно этот индекс — как `drift.lock` и как граф улик: выводимое, а
не поддерживаемое.

Рукописный реестр как первоисточник отклонён: он не может нести AST-якорь, когда требование
размазано по пяти модулям, и становится третьим слоем синхронизации — той самой «тройкой
контрактов, притворяющихся одним», за которую критикуют SDD.

## РАМКА Р4. Порядок срезов

1. **Круг** — сущность проекта, тикеты, тред, агент заводит и двигает сущности, отчитывается,
   человек видит и решает. ← **специфицируется здесь**
2. **Спека и критерии** — модель контрактов, EARS-критерии, производный реестр требований.
3. **Дрейф-гейт в CI** — якоря, хеши, связь критериев с тестами.
4. **Актуальность остального** — выведение архитектурных документов из кода, правка документов
   агентом. Зависит от блочных инструментов редактора.
5. **Облачный режим** — рутины, работа при выключенном ноутбуке.

Круг и гейт **независимы** технически: гейт — CLI и lock-файл внутри репозитория, Orbis ему не
нужен; кругу не нужен гейт. Порядок определён ценностью, а не зависимостями. Круг первым, потому
что он форма всего остального, и на нём выяснится, чего спека реально требует; строить проверку
для документов, которых ещё нет, — то самое ригидное планирование наперёд.

# Решения среза 1

## РЕШЕНИЕ С1. Тикет без требования

Тикет говорит «сделать X» и однажды закрывается навсегда. Требование говорит «система обещает
X» — оно не закрывается никогда, у него состояние покрытия, и нарушить его можно через год
чужой правкой. Слить их в одну сущность значит потерять обещание в момент закрытия тикета — тот
самый механизм устаревания, от которого уходим.

В срезе 1 заводится **только тикет**. Требование появляется в срезе 2 вместе со спекой и
критериями; связь «тикет породил требования» — существующие `relations`.

Вариант «одна сущность, аспекты копятся» отклонён: одна фича порождает несколько требований —
«экраны грузятся по требованию» и «при сбое загрузки чанка показывается ретрай» суть разные
обещания, в одну сущность они не помещаются.

## РЕШЕНИЕ С2. Раннера нет: агент приходит сам

В облачном режиме Orbis физически не может толкать команды в идущую сессию — `fire` создаёт
сессию и отпускает. Значит агент **сам приходит** за работой. Тот же способ работает локально,
и круг получается один на оба режима, а не два разных.

Локальный раннер — процесс на машине, WS-канал, полный поток `session/update` и интерактивные
ворота — **не входит**. Инфраструктуры срез 1 требует ноль: MCP-сервер с OAuth в проде и
проверен живьём.

**Цена названа прямо:** отчёт агента — это то, что агент сам о себе говорит. Соврать, умолчать
или ошибиться в самооценке он может, и защиты от этого в срезе 1 нет. Частично лечится срезом 3:
тогда «готово» без зелёного CI не пройдёт.

## РЕШЕНИЕ С3. Процесс — прозой, чекпойнт — существующим статусом

Процесс работы описывается **прозой в `body` проекта**: стадии, где останавливаться, чего
спрашивать. Агент читает его при захвате тикета.

Чекпойнт не требует новой схемы: агент ставит тикет в `waiting`, кладёт вопрос в `waiting_for`
и **останавливается**. Человек отвечает — работа продолжается следующим прогоном.

Аспект-схема процесса со стадиями и флагами подтверждения отклонена на этом этапе: формы
реальных процессов пока не наблюдались, и схема угадывалась бы. Проза правится как текст.

## РЕШЕНИЕ С4. Четыре аспекта, ноль новых таблиц сущностей

**`orbis/project`** — маркер затеи с жизненным циклом; в аспекте — только то, что нужно машине,
всё остальное про проект — в `body`. Кодовой специфики в нём **нет** — она вынесена в отдельный
аспект **`orbis/repo`** (адрес репозитория, ветка по умолчанию) на той же сущности. Решение
владельца 2026-08-17: круг «тикет → прогон → чекпойнт» — общий механизм делегирования сферы,
код-проекты — лишь первая сфера, и кодовое не должно врастать в общее понятие проекта.

**`orbis/task`** — **без изменений**. Шесть статусов покрывают «бэклог / в работе / выполнен»
целиком.

**`orbis/assignment`** — отдельный аспект на той же сущности тикета: кто исполнитель (человек
или агент), какой именно, и **признак `may_close`** — разрешено ли исполнителю самому переводить
тикет в `done`. Признак булев, по умолчанию **выключен**; иных уровней автономии в срезе 1 нет.
Исполнитель-агент задаётся **ссылкой на `agent_grants.id`** — только так `orbis_my_queue` и
`orbis_claim_task` однозначно сопоставляют предъявленный грант с назначением (несколько сессий
на одном гранте — норма: это один исполнитель); исполнитель-человек — отдельной формой поля,
без ссылки.
Отдельным аспектом, а не полем в `orbis/task`, потому что `orbis/task` живёт в личной ОС, где
про исполнителей-агентов знать незачем.

**`orbis/agent-run`** — прогон агента, дочерняя тикету сущность.

Связи целиком на существующих типах: проект →`parent`→ тикет →`parent`→ прогон, между тикетами
`blocks` с готовой проверкой ацикличности.

Пересев реестра аспектов на проде обязателен, как было с `orbis/goal`.

## РЕШЕНИЕ С5. Прогон — сущность, а не запись в треде

Прогонов на тикет бывает несколько: первый упал, второй доделал, и это надо различать. По ним
нужны запросы — «что упало за неделю», «сколько стоил тикет». И это тот самый журнал с
исполнителями, который просил владелец, — в виде данных, а не переписки.

Прогон несёт: начало, исполнителя, исход, ссылку на сессию (в облачном режиме туда ляжет
`claude_code_session_url`), расход и **упорядоченный журнал шагов**. Каждый шаг: короткая
сводка «что тронул» для ленты, флаг «тронул внешнее» — создал ветку, изменил файлы — и
**ссылка на `action_id` журнала действий §7.8**: мутации глаголов идут через executor и уже
журналируются с актором и inverse, «чем было, чем стало» второй раз не хранится. Журнал
действий живёт 90 дней (RET-02) — прогон переживает его как долгоживущая сводка; откат прогона
(С12) возможен, пока живы его inverse-записи, и это принимается: откатывать прогоны старше
квартала опаснее, чем не откатывать.

Прогоны **прячутся из основных выдач** Browser и поиска по прецеденту D20 (recurring-шаблоны):
каждый `orbis_run_step` поднимал бы прогон в топ листинга «свежего». Их дом — экран тикета и
запросы по аспекту.

## РЕШЕНИЕ С6. Оборванный прогон: статус по признаку эффекта

Статус отвечает на «что делать дальше», а не «что было»: что было, живёт в прогонах и не
теряется ни при каком статусе.

- **шагов с эффектом нет** → `planned`, безопасно перезапустить;
- **эффект был** → `waiting`, а в `waiting_for` — «прогон оборван, состояние работы неизвестно:
  ветка такая-то, последний шаг такой-то». Человек смотрит на остатки и решает.

Возврат **брошенного** прогона в `planned` запрещён: он стирает факт, что работа велась, и
следующий агент натыкается на чужую недоделанную ветку. Ответ на чекпойнт (С3, С10) ведёт в
`planned` штатно, и это не противоречие: тот прогон завершился сам и оставил сводку, а
`orbis_claim_task` отдаёт историю прогонов — `planned` значит не «начать с чистого листа», а
«готов к следующему прогону; контекст — в истории».

Два вида `waiting` различаются без нового статуса: последний прогон завершился штатно — это
вопрос с чекпойнта; брошен — это разбор. Новый статус в `orbis/task` не заводится: аспект общий
с личной ОС.

Отметка живости идёт вместе с записью шага, отдельного heartbeat нет. Порог щедрый — агент
думает над одним вызовом минутами. Подметание — при чтении очереди **и при открытии экранов
проекта и тикета**: инвариант «тикет не висит `in_progress` навсегда» не должен зависеть от
того, что какой-то агент однажды позовёт `orbis_my_queue`. Подобранный прогон закрывается
**терминально**: поздние `orbis_run_step` / `orbis_finish` от него получают отказ со ссылкой
на разбор; `orbis_finish` по тикету не в `in_progress` — тоже отказ.

## РЕШЕНИЕ С7. Правила живут в узких глагольных инструментах; скоуп `worker`

Правило нельзя охранять инструментом, который умеет всё: получив сырой `entity_update`,
исполнитель поставит `done` в обход — не со зла, а потому что короче. Значит правила живут
внутри инструментов, а сырые мутации сущностей исполнителю закрыты скоупом.

Первое настоящее значение `agent_grants.scope` — `worker`. Таблица, экран и отзыв готовы.

Это не педантизм: в облачном режиме рутина получает **все** инструменты коннектора без единого
подтверждения (и по умолчанию — все коннекторы аккаунта), и скоуп на стороне Orbis остаётся
единственной защитой записи.

**Глаголы — операции executor'а, не обход.** Каждый глагол проходит тот же семистадийный
конвейер §9.2: журнал §7.8 с актором-агентом и inverse, Undo, карточки — как у любого
потребителя; «один путь мутаций» (§9.1) не двоится. Захват — CAS-расширение стадий 4–5:
«тикет всё ещё назначен этому гранту и не `in_progress`» проверяется и применяется одной
транзакцией. В таблице §7.10 все глаголы классифицируются **`execute`**, с инвариантом:
глагол исполнителя никогда не возвращает `pending` — фоновому прогону некому подтверждать.

**Семь глаголов исполнителя:**

| Инструмент | Делает |
|---|---|
| `orbis_my_queue` | что мне назначено; по дороге подметает зависшие прогоны |
| `orbis_claim_task` | **атомарный** захват: тикет в `in_progress`, прогон создан; возвращает задание, `body` проекта с процессом и историю прошлых прогонов одним ответом |
| `orbis_run_step` | зафиксировать шаг, включая флаг «тронул внешнее» |
| `orbis_checkpoint` | встать в `waiting` с вопросом и остановиться |
| `orbis_finish` | «готово, проверь» |
| `thread_post` | существующий инструмент, допущенный в скоуп: предложения и заметки в треды проекта и назначенных тикетов (С9) |
| чтение | существующими инструментами, целиком; риск полного чтения личного графа фоновым исполнителем **принят владельцем явно** (2026-08-14, «Известные границы») |

Атомарность захвата закрывает и отсутствие ключа идемпотентности у `fire`: ретрай вебхука
создаст вторую сессию, но не вторую работу.

## РЕШЕНИЕ С8. Агент не закрывает тикет

`orbis_finish` переводит тикет в `waiting`, а в `waiting_for` кладёт сводку исполнителя — что
сделано и что проверить. **Не** в `done`. Если в `orbis/assignment` признак `may_close` включён
— в `done`.

Это первое **скоуп-правило** среза 1 — и оно не одиноко: классификатор §7.10 уже сегодня жёстко
гейтит незнакомые тулы, архивацию по инициативе агента и большие батчи. Остальные чекпойнты
держатся на промпте и могут быть проскочены; этот не проскочится, потому что инструмент откажет.

## РЕШЕНИЕ С9. Агент не правит документы проекта

Исполнитель пишет только в своё: тикеты, статусы, прогоны.

Основания, и все три временные: он работает в фоне, возможно параллельно с человеком в том же
документе, а `entity_update{body}` переписывает тело **целиком** — это 409 по
`expectedUpdatedAt` и перевыдача id всем блокам (Р5 редактора). Откатывать нечем: закреплённые
версии появляются здесь, но привычка их ставить — нет. Блочных инструментов ещё не существует.

**Запрет снимается по условию, а не по дате:** есть `body_replace_block` /
`body_insert_after` / `body_delete_block`. Это срез 4.

Уже в срезе 1 агент **предлагает** — глаголом `thread_post` из скоупа (С7): заметив, что раздел
устарел, пишет в тред проекта «предлагаю такой текст». Применяет человек, на переднем плане.
Симметрично тому, как Orbis предлагает дельту спеки через PR (Р1).

Ограничение касается **исполнителя**. Чат Orbis, действующий от имени владельца на переднем
плане, правит что угодно, как и сегодня.

## РЕШЕНИЕ С10. Экран — три таба; чекпойнт живёт на «Сущности»

Строится на трёх табах редактора (Р9): по решению владельца (2026-08-14) срез стартует после
посадки редактора, ждать нечего не приходится. Чекпойнт-блок — отдельный компонент, не
привязанный к устройству экрана.

**Проект.** «Сущность» — документ: проза плюс живые `{{query:…}}`-блоки «в работе», «ждут меня»,
«бэклог», «последние прогоны»; при создании засевается заготовкой. «Детали» — карточка
`orbis/project`, тикеты подзадачами, связанное. «Тред» — разговор.

**Тикет.** «Сущность» — задание, и сюда же **вопрос чекпойнта с кнопкой «Ответить и вернуть в
работу»**: по прецеденту Р9, оставившей полосу прогресса цели на первом табе, — тикет в
`waiting` открывают ради ответа. «Детали» — карточки `orbis/task` и `orbis/assignment`,
прогоны, блокировки.

Кнопка, а не просто сообщение в треде: иначе неясно, был ли комментарий ответом на чекпойнт.
Пишет ответ и переводит статус одним действием, без полусостояний.

**Прогон.** Лента шагов, исход, расход, ссылка на сессию.

**Внимание.** «Ждут меня» — запрос по `status = waiting` среди тикетов проектов; закреплённая
сущность в сайдбаре и бейдж на вкладке, оба механизма готовы.

Канбан с перетаскиванием отклонён: компонента в Orbis нет, стоит недели, даёт удобство, а не
возможность. Секции списками по статусу теми же query-блоками.

## РЕШЕНИЕ С11. Закреплённые версии вместо сплошной истории

Версию создаёт **человек по решению**, с подписью. Сплошная автоматическая история не строится
**и не откладывается — она отпадает**.

Обоснование: сохранение в редакторе идёт по паузе в наборе (Р10 редактора), поэтому
автоматическая история дала бы версию на каждую паузу — свалку, требующую политики схлопывания,
которую пришлось бы угадывать. Именованные версии убирают эту задачу целиком.

Дыра закрывается правилом: **агент обязан закрепить версию перед первой правкой документа в
прогоне** (актуально со среза 4). Тогда журнал шагов даёт откат действий, а закреплённая версия
— состояние, к которому откатывать. Осмысленные автоматические точки — события домена: перед
правкой агентом, при закрытии тикета, при релизе; не таймер.

**Версия — у одной сущности.** «Версия проекта» позже собирается как именованный набор ссылок
на версии сущностей; переделывать при этом нечего.

**Хранение — отдельная таблица `entity_versions`**, по §2.2 в одном ряду с историей чатов и
provenance импорта. Сущностями версии не делаются: они не единицы графа, на них не ссылаются
связями, и по снимку на сущность засорили бы браузер.

**Снимок и откат — только тело** (решение владельца 2026-08-14): `body_doc`, до его появления —
`body`. Аспекты в снимок **не входят**: у тикета аспекты — состояние процесса (`status`,
`waiting_for`, назначение), и их откат вернул бы статусы мимо правил С6–С8. Связи не входят по
той же причине: они про положение в графе, а не про содержание, и откат связей задел бы соседние
сущности. Откат пишет восстановленное тело **через executor тем же конвейером и конвертером, что
обычная запись** (после посадки редактора `body` в БД — всегда канон): содержание возвращается
канонично эквивалентным, не «побайтно».

`entity_origins` не переиспользуется и не трогается: она про импорт, undo физически удаляет
строки.

## РЕШЕНИЕ С12. Откат прогона касается только Orbis

Кнопка на экране прогона: обратное применение **inverse-записей журнала §7.8** по шагам прогона,
в обратном порядке, существующей механикой Undo (`executor/undo.ts`) — с проверкой, что
затронутые сущности с тех пор не менялись; менялись — показываем конфликт, а не затираем молча.
Новый механизм отката не строится; предел глубины — retention журнала (RET-02, 90 дней), см. С5.

Ветку и коммиты агента откат **не трогает** — там git, и откат там делается git'ом. Смешение
двух механизмов дало бы «отменил в Orbis, а код остался», что хуже, чем не откатывать вовсе. На
экране прогона написано прямо: что откачено в Orbis и что осталось в репозитории.

## Инварианты, которые проверяются, а не подразумеваются

1. **Захват атомарен.** Два одновременных `orbis_claim_task` на один тикет: ровно один получает
   работу, второй — отказ. Тестом на гонку, не на глаз.
2. **Скоуп `worker` не может тронуть чужое.** Попытка выставить `done` или записать `body`
   отклоняется на сервере, а не промптом.
3. **Каждый глагол проходит executor и попадает в журнал §7.8** с актором-агентом и inverse;
   «отмени последнее» работает и для действий исполнителя, как требует §6.2 продукта.
4. **Ни один глагол исполнителя не возвращает `pending`** — классификация §7.10 закреплена
   тестом.
5. **Брошенный прогон с эффектом никогда не даёт `planned`**, а сам прогон терминален: поздние
   шаги от него отклоняются.
6. **Прогон без шагов дольше порога помечается брошенным** — при чтении очереди и при открытии
   экранов, — и тикет не остаётся в `in_progress` навсегда.
7. **Откат прогона не затирает чужие изменения** — при расхождении показывает конфликт.
8. **Откат к версии восстанавливает тело канонично эквивалентным** — и только тело: аспекты и
   связи не трогаются.
9. **RLS новых таблиц запинена поимённо**, как заведено для новых таблиц.

## Известные границы

- **Запуск исполнителя в срезе 1 — ручной.** «Агент приходит сам» означает: когда владелец сам
  запустил Claude Code — и перезапустил после ответа на чекпойнт. Из интерфейса запуск
  невозможен до среза 5. Официально опёртый мост до тех пор — `claude setup-token` +
  `claude -p` по расписанию на машине владельца.
- **Чтение worker-скоупа не ограничено**: фоновый исполнитель может читать весь личный граф
  (финансы, память, заметки), а канал наружу у него есть всегда — сеть локально, в облаке
  трафик коннекторов идёт мимо сетевого allowlist. Риск принят владельцем явно 2026-08-14;
  пересмотр обязателен при выходе за пределы «владелец — единственный пользователь».
- Отчёт агента непроверяем (С2). Снимается срезом 3.
- Интерактивных ворот нет ни локально, ни в облаке; чекпойнты держатся на промпте, кроме
  запрета закрывать тикет (С8).
- Параллельные агенты не изолированы: два тикета, трогающих одни файлы, подерутся за дерево.
  Назначать по одному тикету за раз; изоляция по worktree приходит с раннером — **правовой
  статус которого под подпиской не разрешён**: февральское (2026) ограничение Anthropic на
  подписочный OAuth в стороннем ПО не отозвано, июньская «пауза» касается биллинговой схемы.
  Рамка считает раннер риском, а не данностью; официально опёртые пути — `claude -p` под
  собственной подпиской и облачные рутины.
- Если владелец сам испортит документ и не закрепил версию — вернуть нечем, кроме undo в
  редакторе. Не дыра этой работы: так в Orbis сегодня.
- `fire` без ключа идемпотентности создаёт лишние сессии (подтверждено документацией дословно);
  лишней работы не создаёт (С7), но лишние сессии тратят лимит. Полезная нагрузка `fire`
  приходит рутине **как недоверенные данные** — сохранённый промпт рутины обязан явно на неё
  сослаться, иначе текст инертен (важно для среза 5).

## Швы под будущее: заделы срезов 2–4

Добавлено 2026-08-14 по разбору свежих соседей (Xirp от Spotify, oh-my-pi, Prime Agent).
В срезе 1 не строится ничего — фиксируются требования к будущим механизмам, дешёвые сейчас
и дорогие потом:

1. **Блочные правки — с контент-хешем-guard'ом (срез 4).** Контракт
   `body_replace_block(id, md, content_hash)`: правка применяется, только если хеш содержимого
   блока совпадает; разошёлся — отказ **до** порчи, конфликт на уровне блока вместо 409 всего
   тела. Прецедент — hashline-правки oh-my-pi (якорь по контент-хешу, отказ до порчи файла,
   −61% выходных токенов). Это то же семейство механизмов, что AST-якоря Р2: один словарь
   «якорь разошёлся → отказ» на редактор и на дрейф-гейт.
2. **Якорный патч-формат (срезы 2–3).** Для `drift.lock` и агентских правок спеки — компактная
   якорная форма по образцу omp: `@@ anchor:"sha256-…" @@` плюс правка; якорь — нормализованный
   контент/AST-хеш. Семантика Р2 не меняется — фиксируется форма записи.
3. **Предложения агента — evidence-backed (срез 4, уточнение С9).** Предложение правки
   документа в тред обязано ссылаться на прогон-триггер («после прогона X выяснилось Y») —
   прогоны уже сущности, ссылка бесплатна. Прецедент — `/refine` Prime Agent: каждое улучшение
   записывает триггер и исход. Его же Factorio-кейс (цикл самоулучшения, найдя эксплойт, начал
   строить навыки читерства) — довод, почему применяет человек: самомодификация без человека в
   петле оптимизирует не то.

Добавлено 2026-08-16 по разбору Code Wiki (Google) — их продакшен реализует ровно тезис Р1
«архитектура выводится из кода»:

4. **Перегенерация производных доков — по событию домена, не по таймеру (срез 4).**
   Производные архитектурные документы перестраиваются на мерж в `main` (шаг CI) — тот же
   принцип, что у автоматических точек версий в С11. Прецедент — Code Wiki: пересканирование
   на каждый коммит; документация перегенерируется, а не правится.
5. **Производные доки — слой контекста тредов проекта (срез 4).** Чат проекта отвечает из
   выведенной вики, а не из сырого кода — шестой кандидат в пятислойную модель контекста
   (PRD §7.1). Прецедент — Gemini-чат Code Wiki, заземлённый в вики репозитория.
6. **Каждое утверждение производного дока — ссылкой в код (срез 4).** Требование к генератору:
   объяснение ведёт в строку/символ; якоря Р2 и REQ-id реестра дают это бесплатно. Прецедент —
   гиперссылки Code Wiki из объяснения в исходник.

- Облачные рутины и работа при выключенном ноутбуке — срез 5.

- Версионирование набором сущностей (С11).

## Приёмка

1. Создан проект — видна заготовка с живыми блоками.
2. В треде проекта «сделай A, B, C» — три тикета в `inbox`, дочерние проекту.
3. Назначение агенту — `orbis/assignment` заполнен.
4. Claude Code с коннектором Orbis: `orbis_my_queue` вернул три тикета.
5. `orbis_claim_task` — тикет в `in_progress`, прогон создан; тот же вызов от второго агента
   отклонён.
6. Шаги агента видны лентой на экране прогона.
7. Чекпойнт — тикет в `waiting`, вопрос виден, тикет в «ждут меня», бейдж на вкладке.
8. Ответ кнопкой — `planned`; следующий прогон видит ответ и историю прошлых прогонов.
9. `orbis_finish` — тикет в `waiting` «готово, проверь», **не** в `done`.
10. Попытка агента выставить `done` в обход — отклонена скоупом.
11. Прогон убит на середине: без шагов с эффектом тикет в `planned`, с эффектом — в `waiting`
    с описанием остатков.
12. Закреплена версия, документ изменён, выполнен откат — содержание вернулось канонично
    эквивалентным; статусы и связи не тронуты.
13. Откат прогона — статусы вернулись; на экране написано, что осталось в репозитории.
14. Шаги прогона видны и в журнале действий с актором-агентом; «отмени последнее» из чата
    отменяет действие исполнителя.
15. PRD приведён к факту тем же изменением: §2.2 (таблица версий), §3 (три аспекта), §4.14
    (семантика `scope`), §7.10 (классификация глаголов), §9.3 и 02-core-os §5.9 (worker больше
    не закрывает тикет сам).

## Уточнения по факту реализации (2026-08-18)

Срез реализован и слит (`main`, 18 задач, решение журнала — **D37**). Решения С1–С12 выше
**не переписываются**: они остались верны, и читать их надо как есть. Ниже — построчный список
того, где факт **уточнил** или **сузил** сказанное, каждый пункт с причиной. Всё, чего в списке
нет, реализовано как записано.

### Инварианты

- **Инвариант 3 сужен: «шесть глаголов-мутаций графа» вместо «каждый глагол».** Через executor
  и журнал §7.8 идут пять глаголов исполнителя и `entity_update`-операции ответа на чекпойнт;
  `thread_post` идёт **мимо** executor'а. Причина не в удобстве: сообщение в тред и есть
  артефакт, `chat_messages` append-only (PRD §4.6), `inverse` у поста не бывает — писать его в
  журнал значило бы заводить запись, которую Undo не может отменить. Ровно так же ведёт себя
  обычное сообщение владельца. Пометка автора у поста агента остаётся (`author_kind`), и в
  треде видно, что заметку оставил не человек.
- **Инвариант 5 уточнён: терминальность двойная.** Предпроверка по прочитанному состоянию плюс
  CAS-предусловие `outcome` под замком. При **заданном ключе идемпотентности** предпроверка
  намеренно **не отказывает** — вызов идёт в executor, потому что повтор того же вызова обязан
  вернуть свой сохранённый ответ, а replay проверяется раньше предусловий. Отказали бы раньше —
  повтор `checkpoint`/`finish` навсегда получал бы `CONFLICT` вместо собственного результата, и
  агент считал бы работу несделанной.
- **Инвариант 7 уточнён: окно конфликтов — от ПЕРВОГО живого действия прогона.** См. С12 ниже.

### С4 — реестр аспектов

- `name` записей реестра — английские (`Project`, `Repo`, `Assignment`, `Agent run`), по общей
  конвенции реестра; русские подписи полей живут в `field-labels.ts` клиента.
- `repo.url` — строка **без проверки формата**: SSH-адреса `git@host:owner/repo.git` не являются
  URI, и валидация «как URL» отклоняла бы самый частый способ подключения.
- **Иконка `orbis/assignment` — 🎯, та же, что у `orbis/goal`.** Столкновение известно и
  оставлено решением владельца: смена иконки тривиальна, но требует пересева реестра на проде.
- `grant_id` есть в двух аспектах (`orbis/assignment`, `orbis/agent-run`) — запрос `grant_id=…`
  без `aspect=` даёт явную ошибку неоднозначности, а не молча выбирает один из двух.
- Служебный `orbis/agent-run` **не получает `attach_*`-тула**; реестр целиком — 27 тулов
  (11 core, 5 глаголов, 11 attach), публичных в MCP — 25.

### С5 — служебные сущности

- **Механизм — неявное исключение в компиляторе запроса** (`NOT (aspects ?| …)`): построчный
  фильтр, GIN отрицание не покрывает. «Названным» служебный аспект считается, если запрос
  указал `aspect=<служебный>` **или** хотя бы одно поле фильтра разрешается в служебный аспект
  (`outcome=running` без `aspect=` выдачу не обнуляет). `sortBy` по такому полю названием **не
  считается** — сортировка не отбирает.
- Границы механизма: подсказки @-упоминаний в редакторе идут сырым `LIKE` мимо компилятора, и
  прогоны там видны (упоминание прогона в тексте законно); агрегаты (`count`/`sum`/`latest`) по
  полю служебного аспекта **без фильтра по нему** дают молчаливый ноль — не сценарий среза.
- Переключатель «показать служебные» (02-core-os §3.9) означает выдачу **одних** служебных
  (`aspect=orbis/agent-run`): формы «все и служебные заодно» грамматика не даёт.

### С6 — подметание

- **Порог — 30 минут** (закрывает открытый вопрос 2 ниже).
- `orbis_my_queue` подметает **все** брошенные прогоны владельца, а не только прогоны
  вызывающего гранта: записи идут с `actor_grant_id` вызывающего и `run_id` подмётанного
  прогона, но с `source: 'system'` — «отмени последнее» их пропускает, а точечный откат по
  `run_id` — нет. С экранов проекта и тикета то же делает `agentRun.sweep`.
- Архивные прогоны не подметаются: архив — это «убрано с глаз», а не «сделай».

### С7 — глаголы, скоуп, грант

- **Гейт скоупа fail-closed по факту:** условие — `scope !== 'full'`, а не `=== 'worker'`.
  Колонка текстовая, и незнакомое значение обязано сужать доступ, а не открывать полный.
  Порядок гейтов диспатча: `internalOnly` → скоуп → `agentOnly` (глагол без гранта →
  `VALIDATION`) → классификатор §7.10. Скоуп стоит **до** классификатора: тот по актору
  сознательно не ветвится.
- `thread_post` для `worker` разрешён в треды назначенных тикетов и **любого прямого родителя**
  по связи `parent` — не только проекта: «проект» в С7 назван по типичному случаю, а проверка
  смотрит на связь. Чужая и несуществующая сущность дают `FORBIDDEN_LEVEL`, а не `NOT_FOUND`:
  исполнителю не с чего узнавать, что за пределами его назначений вообще что-то есть.
- **Каждый вызов глагола с ключом идемпотентности идёт batch-путём executor'а** — action
  `type: 'batch'`, и в ленте чата он выглядит карточкой «batch: операций — N» с маркером
  актора-агента, не обогащённой сущностью. Названо в «Известных границах» ниже.
- **CAS-предусловие `precondition: [{aspect, field, in}]` — только exec-схема** executor'а;
  тул-контракт, MCP и tRPC его не видят. Отказ — `CONFLICT` с
  `details {reason: 'precondition_failed', precondition: <первый провалившийся>, actual}`;
  отсутствующее поле — всегда конфликт.
- **Захват** — batch из трёх операций: `entity_update` тикета с тремя предусловиями,
  `entity_create` прогона, `relation_create` (`parent`: тикет → прогон). Повтор с тем же `id`
  отдаёт **тот же** `run_id` и `replayed: true`; тот же `id` для другого тикета или от другого
  гранта — `CONFLICT` (replay-guard): иначе исполнитель получил бы чужой прогон.
- **Шаги** — CAS по `step_count` с ретраем ×3; потолок `steps` — 500, 501-й шаг отклоняется
  `VALIDATION`.
- **Живой грант в назначении проверяется на `entity_update` только когда патч трогает
  `orbis/assignment`.** Проверять на каждой правке нельзя: отзыв гранта иначе замораживал бы
  тикет целиком, вплоть до переименования, — а отзыв закрывает доступ агенту, не сущность.
  При `entity_create` и `attach_*` проверка идёт всегда при наличии аспекта.
- Все глаголы — уровень `execute`, никогда `pending`; закреплено на трёх уровнях
  (классификатор, диспатч, провод ответа). Реестр тулов чата `agentOnly` не видит вовсе, а
  подтверждение отложенного действия скоуп не ревалидирует — `worker` до `pending` не доходит.
- Выдача области: радио на экране согласия («Полный доступ» / «Только исполнитель (worker)»),
  `issue-pat … --scope worker` (fail-closed на незнакомом значении, код возврата 2),
  `scopes_supported: ['full','worker']` в метаданных, область в ответе `/oauth/token` на обоих
  путях, бейдж в «Настройки → Агенты». Параметр `scope` из запроса клиента **игнорируется**.

### С8 — итог и закрытие тикета

- `orbis_finish` без `may_close` → тикет в `waiting`, а в `waiting_for` ложится **сам отчёт**;
  с `may_close` → `done` и `waiting_for: null`, причём право сверяется ещё раз под замком
  (`precondition: may_close in [true]`): владелец мог снять его между чтением и записью.
- Уход из `waiting` всегда снимает `waiting_for` — конвенция среза, одинаковая у итога, ответа
  на чекпойнт, подметания и чекбокса задачи.

### С10 — экраны и засев

- **Заготовка тела проекта — 4 query-блока, не 5** (проза процесса + «в работе», «ждут меня»,
  «бэклог», «последние прогоны»), и шаблон **каноничен**: executor кладёт в тело результат
  канонизации, любое расхождение сдвигало бы заготовку на первом же сохранении.
- «Тело во входе есть» = непустой после `trim` `body` **либо любой** `bodyDoc`. Пустая или
  пробельная строка телом не считается (иначе `body: ""` от модели отдавал бы пустой проект
  вместо заготовки); пустой документ из редактора считается всегда — это осознанное «я стёр
  всё». Inverse засеявшего `attach` восстанавливает пустое тело.
- Блок «Последние прогоны» работает через денормализованный `project_id` на прогоне: `this`
  грамматики достаёт детей, а прогон — внук проекта.
- Раскладка по вкладкам: чекпойнт-блок и лента прогона — на «Сущности»; назначение, прогоны и
  версии — на «Деталях». Вкладки управляются из `DetailScreen` (один источник правды), версии
  грузятся только на **открытых** «Деталях», и вкладка не сбрасывается при переходе между
  записями. Подметание — один раз на монтирование экрана тикета или проекта (гвард против
  двойного монтирования в StrictMode).
- `AssignmentCard`: перевод «агент → человек» шлёт `grant_id: null`; `expectedUpdatedAt` для
  аспектных правок сервер игнорирует, поэтому 409 на этой карточке недостижим.

### С11 — версии тела

- Миграции — `0010` (сгенерированная, таблица и индекс) и `0011` (рукописная: RLS, политика
  `owner_owns_row_and_entity`, гранты); прежняя `0010_drop_body_before_doc` переехала в `0012`.
  RLS — `WITH CHECK` шире `USING` (прецедент `0002`), pgTAP-группа на месте.
- Операции `entity_version_pin` / `entity_version_delete` — **внутренние**, в `CORE_TOOLS` не
  входят и модели не видны; наружу это tRPC владельца (`version.pin/list/restore`).
  Восстановление — тот же `entity_update` (документом, если версия схемы совпадает с текущей,
  иначе строкой). Undo закрепления — физическое удаление строки; у `entity_version_delete`
  inverse пустой.
- Web: закрепление — пункт меню «Закрепить версию» (пункт «Закрепить» рядом — это pinned в
  сайдбаре, §3.2 02-core-os); конфликт восстановления (409) показывается инлайн в карточке
  версий, а не тостом.

### С12 — откат прогона

- «Действие прогона» = `run_id === runId` **и** `source !== 'ui'`. Ответ владельца на чекпойнт
  тоже несёт `run_id` (он про этот прогон и стоит рядом с вопросом на экране), но идёт с
  `source: 'ui'` — это его решение, а не работа исполнителя, и откат его не снимает.
  Обслуживание круга (`source: 'system'`, подметание) откатывается вместе с прогоном намеренно.
- **Окно поиска конфликтов — от ПЕРВОГО живого действия прогона**, а не от последнего, и
  сравнение идёт составным курсором `(created_at, id)`. Причина: прогон длится часами, правка
  владельца лежит **между** действиями, а inverse `entity_update` возвращает аспект-ключ
  целиком — окно «после последнего действия» такую правку просто не видит, и откат `claim`
  стёр бы её вместе со статусом.
- **Гранулярность конфликта — сущность:** любая правка тикета владельцем во время прогона
  блокирует откат. Уже отменённые чужие действия конфликтом не считаются — их эффекта в графе
  больше нет.
- Серия отмен идёт в обратном порядке и **не атомарна**: `undoAction` открывает собственную
  транзакцию, склеить их нечем. TOCTOU между предпроверкой и серией — свойство дизайна, а не
  недосмотр; отказ на середине возвращает `partial` со списком уже отменённого и адресом
  отказа. Текст `note` — постоянный («откачено в Orbis, ветку откатывайте git'ом»), а не
  собранный по факту: граница — свойство механизма, а не этого прогона.
- Undo шага владельцем из чата («отмени последнее») работает; audit-запись несёт
  `actor_kind: 'agent'`, `actor_grant_id` и `run_id`.

### Открытые вопросы — закрыты

- **Вопрос 2 «порог брошенного прогона» — 30 минут** (`RUN_STALE_AFTER_MS`). Щедрость
  намеренна: между шагами агент гоняет тесты, думает и читает. Цена ошибки несимметрична —
  ложное срабатывание уводит тикет в `waiting` и стоит внимания человека, пропуск стоит только
  ожидания. Тесты инжектируют собственный порог и часы.

### Швы — что отложено

- **Журнал наблюдений (В6 рамки видения, D35) — отложен.** В срезе он не строится; шов
  оставлен веткой чтения в диспатче тулов, где уже есть грант вызывающего. Решение
  зафиксировано в D37.
- **Retention журнала (RET-02) не реализован**, поэтому предела глубины отката сегодня нет —
  ограничение из С5 («откатывать прогоны старше квартала опаснее») пока не наступает
  механически.

### Известные границы — дополнения

- **Полный грант и чат технически могут создать или править прогон вручную** —
  `entity_create`/`entity_update`/`batch_execute` аспект `orbis/agent-run` принимают, а
  `attach_*`-тула у него нет. Удерживает только `ai_instructions` аспекта, то есть промпт, а не
  механизм. Скоуп `worker` такого пути не имеет вовсе — ему сырые мутации закрыты.
- **Вызовы глаголов выглядят в ленте чата батчами.** Карточка «batch: операций — N» сущностью
  не обогащается, и по ней не видно, какой именно глагол сработал; маркер актора-агента есть.
  Разбор — на экране прогона, где лента шагов читается по-человечески.
