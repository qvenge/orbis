## §1. Зачем

Два факта кода, установленные разведкой:

1. **`orbis_checkpoint` не блокирует прогон — он его закрывает.** Вопрос — терминальный исход: `outcome:'checkpoint'`, `finished_at`, цикл модели выходит (`agent-loop/verbs.ts:886-901`, `runner.ts:378-385`). Ответ владельца читает *следующий* прогон через историю. Один вопрос стоит прогону всей оставшейся работы.
2. **Откладывать действия рутине запрещено инвариантом 5** (V1.10): `source==='routine' && level!=='execute'` → `FORBIDDEN_LEVEL` «в фоне небезопасное отклоняется, а не откладывается» (`tools/dispatch.ts:752-758`). Рутина физически не может ни спросить «между делом», ни отложить архивацию на решение владельца — только отказаться или остановиться.

Следствие для North Star (§4 миссии): «брать больше» упирается в то, что каждый вопрос обрывает работу, а каждое небезопасное действие — тупик. Cloudflare OS называет ровно этот антипаттерн причиной, по которой пользователи включают auto-approve — «which is, obviously, unsafe». Срез даёт противоположное: прогон доделывает всё, что может, вопросы и небезопасное копятся **пачкой решений**, владелец разбирает её когда удобно — поштучно или разом — и одним нажатием продолжает работу рутины.

## §2. Словарь

- **Единица решения** — pending в треде рутины, один из двух видов:
  - **вопрос** (`kind:'question'`) — текст ≤4000 + опциональные варианты ответа (≤4); payload-операций нет; на него *отвечают*;
  - **отложенное действие** (`kind:'action'`) — payload = вызов тула (как у сегодняшнего чатового pending); его *принимают или отклоняют*.
- **Пачка решений** — все открытые единицы прогона (продуктово: и рутины — открытые единицы всех её прогонов).
- **`undecided`** — скалярный флажок на аспекте прогона: «у прогона есть нерешённые единицы».

## §3. Решения

### ОЧ.1. Скоуп: вопросы + действия, без симуляции результата *(выбор владельца)*

Оси: (А) нетерминальные вопросы, (Б) отложенные действия. Ось (В) — симуляция результата отложенного действия (полная Cloudflare-модель) — **не берётся**: честная симуляция невозможна (`updatedAt` не подделать — `monotonicUpdatedAt` `executor.ts:941-943`, правка body требует настоящего штампа `:1207-1218`; серверные достройки — бюджет-хук A4 `:445-447`, засев тела С10, канонизация `:1419-1428` — невидимы вызывающему; dry-run пути в executor нет, `preview` исполняет). Модель получает честное `{status:'pending_confirmation', pendingId}` — эта ветка `toolResultPayload` уже существует и помечена «для рутины недостижима» (`runner.ts:434-440`). Симуляция — шов (§10).

### ОЧ.2. Носитель — существующий pending; второго механизма отложенного не заводим

`policy/pending.ts` даёт боем проверенное: immutable payload в `chat_messages.metadata.pending` (схема без `.strict()` — поля добавляются без миграции, проверено на `run_id`/`actor_grant_id`), невидимость для журнала §7.8 до применения, двухуровневую идемпотентность одним ключом (`pendingMessageId` + `batchId = pendingId` + `batchAuditMessageId`), сериализацию approve/reject advisory-lock'ом, append-only судьбу, атрибуцию сквозь одобрение. Прямое указание кода: «второй механизм „отложенной правки" пришлось бы отдельно учить откату, ревалидации и сериализации — то есть повторить pending хуже» (`routines/propose.ts:6-9`).

Расширение записи: `kind: 'question' | 'action'`; **отсутствие поля = `'action'`** — все существующие pending читаются без изменений. Для вопроса — поля `question`, `options?`; payload-полей (`tool`, `input`) у вопроса нет.

### ОЧ.3. Гранулярность приёмки: поштучно; зависимое — в один pending *(выбор владельца)*

Единица приёмки = один pending; внутри — атомарно (один batch executor'а, одна транзакция, один action §7.8, общий откат). Пачка = несколько **независимых** единиц: решаются порознь или кнопкой «Принять все»; отклонение одной не трогает другие. Зависимые операции обязаны лежать в одном pending — **зависимостей между pending'ами нет по построению**, а не разруливаются постфактум (урок NIM-402 из разбора рынка: частичное принятие с пересчётом базы воскрешает отклонённое). Сегодняшние confirm-действия рутины одиночны (архивация — `confirmation.ts:54-64`), поэтому автоотложка диспатчем кладёт в pending ровно один вызов; групповой глагол — шов (§10).

«Всё или ничего» V1.7 не отменяется — он сужается до своей естественной области: **внутри единицы**. На пачку он не распространяется.

### ОЧ.4. Отложка — на диспатче; инвариант 5 переформулируется

В `runMutation` (`dispatch.ts:747-758`) гейт рутины меняется по уровню классификатора §7.10:

| Уровень | Сегодня | Становится |
|---|---|---|
| `execute` | исполнить | исполнить (без изменений) |
| `explicit-confirmation` | `FORBIDDEN_LEVEL` | **`createPending(kind:'action')` в тред рутины + ответ модели `pending_confirmation`** |
| `preview` | `FORBIDDEN_LEVEL` (недостижим: batch рутине закрыт) | недостижим, без изменений |
| `forbidden` | `FORBIDDEN_LEVEL` | `FORBIDDEN_LEVEL` (запрещённое не откладывается никогда) |

Классификатор не меняется вовсе — он по-прежнему не смотрит на `source` (`confirmation.ts:4-6`); меняется только реакция диспатча на уровень для `source:'routine'`. Запреты по объекту (`FORBIDDEN_ASPECTS`) действуют до постановки — отказ получает агент, не владелец на кнопке (принцип `propose.ts:19-22`).

**Инвариант 5, новая формулировка:** «В фоне небезопасное **откладывается с продолжением работы** (pending-единица в треде рутины), запрещённое — отклоняется». Исходное обоснование («pending повис бы вопросом без контекста» — `dispatch.ts:747-751`) снято по существу: контекст пачке даёт отчёт завершившегося прогона рядом с карточками.

### ОЧ.5. `orbis_ask` — нетерминальный вопрос; терминальный `orbis_checkpoint` остаётся

Новый тул `orbis_ask`: `{run_id, question ≤4000, options?: string[] ≤4}` → pending `kind:'question'`, модели возвращается `{pending_id}`. Отдельного ключа идемпотентности во входе нет — он выводится из содержимого (ОЧ.9). Рутина получает **оба** инструмента: `orbis_ask` («спрошу и продолжу») и терминальный `orbis_checkpoint` («без ответа дальше бессмысленно» — поведение не меняется: исход `checkpoint`, блок вопроса, `answered`). Выбор делает модель; различие объясняет новый промпт **`routine-v2.ts` + фикстура** (правка промпта = новый файл, правило `routine-v1.ts:2-4`); описание тулов в реестре правится соответственно (`registry.ts:667-678`).

`orbis_ask` — обычный нетерминальный тул: не входит в `TERMINAL_TOOLS` (`runner.ts:51`), результат кладётся в разговор, вызов считается шагом (`runner.ts:400-413`).

### ОЧ.6. `undecided` — скаляр на аспекте прогона; исходы не меняются

`RUN_OUTCOMES` не расширяется. Отложивший прогон завершается обычным `finished` (или `checkpoint`, если позвал терминальный — тогда у прогона и терминальный вопрос, и пачка; блоки UI независимы). Close-патч прогона дополнительно пишет `undecided: true`, если открытые единицы есть (раннер ведёт их список за прогон). Массив деталей на аспекте не заводится — массив объектов нефильтруем (D31); детали живут в треде, числа для UI считает сервер GIN-пробой (как сегодняшний `waiting`-бейдж).

Пишущие `undecided`: close-патч — бухгалтерия `source:'system'` (как usage, Р-7); снятие — серверные процедуры решений (`source:'ui'`, решение владельца), под advisory-lock по `runId`, когда открытых единиц у прогона не осталось. Инвариант 6 («модель не трогает `orbis/agent-run`», `executor/invariants.ts:403-419`) не нарушается. Цена: одно новое поле в `.strict()`-аспекте прогона → одноразовый пересев реестра на проде до деплоя.

### ОЧ.7. Ответы доезжают через тред; продолжение — кнопкой «Продолжить сейчас» *(выбор владельца)*

Ответ на вопрос и решения по действиям — append-only сообщения в треде рутины. Следующий прогон читает их **без новой механики**: снимок треда уже входит в подготовку прогона (`runner.ts:191-235`); `routineHistory` дополняется сводкой «спрашивал N, отвечено M» вместо сегодняшней пары скаляров (`context.ts:129-131`).

Продолжение работы: кнопка **«Продолжить сейчас»** на пачке = существующий `runNow` (`routers/routine.ts`). Плановый прогон по расписанию — второй, гарантированный путь чтения ответов. Автозапуск по каждому ответу отклонён (дебаунс-механика планировщика, прогоны без явного запроса владельца); ждать только расписания — отклонено (теряется пол-ценности отложенности).

### ОЧ.8. Гашение: V1.8 распространяется на пачку

Новый прогон рутины — плановый или «Продолжить сейчас» — **гасит все нерешённые единицы прошлых прогонов**: действия → `rejectPending` (`superseded`/`stale`), вопросы → append-сообщение гашения (`stale`). `closeOpenOfRun` (`lifecycle.ts:262-353`) обобщается с «один вопрос + одно предложение» до списка; порядок сохраняется — «сначала судьба pending, потом патч прогона» (`lifecycle.ts:252-254`), чужая причина не перезаписывается (`:290-296`). Откат прогона гасит так же (уже вызывает `closeOpenOfRun`, `rollback.ts:418-428`).

Гашение также **снимает `undecided`** с прогонов, чьи единицы погасило (той же бухгалтерией `source:'system'`, что и остальной патч гашения): погашенная пачка не должна оставлять прогон в «Ждут ответа».

Следствие, которое владелец знает: ответил на часть и нажал «Продолжить» — остальное погашено; актуальное прогон переспросит/переотложит заново по свежему состоянию графа. «Не копить четыре плана к пятнице» работает и здесь. Таймаута у единиц нет — гашение следующим прогоном остаётся единственным сроком жизни (как у всего открытого).

### ОЧ.9. Идемпотентность всех рёбер

- Постановка действия: дедуп-ключ `defer:{runId}:{hash(tool + канонический input)}` → `pendingMessageId` — ретрай моделью того же вызова в том же прогоне возвращает тот же `pendingId`, второй карточки нет.
- Постановка вопроса: `ask:{runId}:{hash(question + options)}`.
- «Принять» — существующий replay (`batchId = pendingId`); «Отклонить» — повтор возвращает исходную причину (`pending.ts:436-438`).
- **Ответ на вопрос — replay, не CONFLICT**: append-сообщение с детерминированным PK (`answerMessageId(owner, pendingId)` по образцу `rejectMessageId`); повторный ответ возвращает исходный. Отличие от терминального чекпойнта (второй ответ — CONFLICT, `lifecycle.ts:805-810`) сознательное: у пачки двойные клики — норма.

### ОЧ.10. Потолок шагов рутинного раннера — своя константа

Вопросы и отложки тратят шаги, а `MAX_AGENT_STEPS = 8` общий с чатом (`packages/shared/src/constants.ts:9`). Вводится `ROUTINE_MAX_STEPS = 12` (в `routines/constants.ts`, используется только рутинным раннером; чат не меняется). Дедлайн `RUN_DEADLINE_MS = 10 мин` не меняется — прогон не ждёт ответов, он работает и завершается. `steps: max(500)` в аспекте — запас не трогаем.

### ОЧ.11. «Принять все» — последовательно, не атомарно между единицами

N последовательных `approvePending` (каждый — атомарный batch под своим advisory-lock). Между единицами атомарности нет и она не обещается — как у отката прогона: «обещание уровня UX, а не инвариант БД» (`rollback.ts:17-22`). Итог — сводка по каждой единице: `applied / stale (mismatches) / rejected / already`. Одна протухшая не блокирует остальные (этим пачка и отличается от предложения V1.7). Идемпотентно по построению — повтор кнопки = N replay'ев.

### ОЧ.12. Контракт един; гейт доступа — временный, с условием снятия *(выбор владельца)*

В схеме `orbis_ask`, записи pending и флажке `undecided` нет ничего рутинного (есть `run_id` и тред — у тикетного прогона они тоже есть). Гейт «только внутренний раннер» — одна проверка в диспатче, помеченная временной. Причины гейта: (1) Orbis контролирует петлю только внутреннего раннера — внешний агент может задать вопросы и умереть, оставив тикет `in_progress` без сигнала владельцу; (2) «Продолжить сейчас» для внешнего не работает — Orbis не умеет его запускать (шов «запуск исполнителя», ADE-срез 1 п.7 / срез 5); (3) боль сейчас у рутины — у внешнего пути есть рабочая модель (тикет `waiting`). **Условие снятия**: появление запуска исполнителя; тогда открытие = снять гейт + научить закрытие внешнего прогона выставлять `undecided` на тикетном пути (§10).

## §4. Модель данных

**Запись pending** (расширение, без миграции — схема `pendingRecord` без `.strict()`, `pending.ts:63-90`):

```
pending: {
  id, created_at, actor_kind, source,        // существующие
  run_id, routine_id?, actor_grant_id?,      // существующие optional
  kind?: 'question' | 'action',              // отсутствует = 'action' (обратная совместимость)
  // kind:'action' — как сегодня:
  tool?, input?,
  // kind:'question':
  question?, options?: string[],
}
```

**Судьбы.** Действие: `pending → approved | rejected(owner|superseded|stale|…) ` — существующие. Вопрос: `open → answered | stale`; оба перехода — append-only сообщениями с детерминированными PK: ответ — `answerMessageId(owner, pendingId)`, metadata `{type:'question_answered', answer, option?}`; гашение — по образцу reject-сообщения, `{type:'question_stale'}`. Pending-сообщение никогда не правится.

**Аспект прогона**: новое поле `undecided?: true` (скаляр; отсутствие = решать нечего). Существующие `checkpoint`/`reply` (терминальный путь) не меняются.

**Открытые единицы прогона** ищутся GIN-пробой `metadata @> {"pending":{"run_id": …}}` минус решённые (по PK ответов/отказов/audit) — тот же приём, что у `runActions` (`rollback.ts:200-205`).

## §5. Поток прогона

1. Модель зовёт тул. Нетерминальный мутирующий вызов идёт в `runMutation`; по уровню — исполнение или отложка (ОЧ.4). `orbis_ask` — создание вопроса. Оба возвращают модели честный результат (`pending_confirmation` / `{pending_id}`), результат кладётся в разговор, вызов = шаг.
2. `createPending` для отложки/вопроса — в собственной транзакции (как чатовый путь); карточка (`args.card`) — своего вида (§7).
3. Прогон завершается как обычно: `settle`/терминальный глагол. Close-патч — с `undecided:true`, если раннер ставил единицы и они не решены (список ведётся в памяти прогона; финальная сверка — GIN-пробой).
4. **Сбой-лестница** (урок Б1 Ш1 — перечислить, что остаётся на каждом шве):
   - pending создан, крэш до ответа модели → прогон закроет подметание (`failed`), единицы живы, гасятся следующим прогоном (V1.8). Рабочее состояние.
   - крэш между терминальным глаголом и close-патчем `undecided` → смарт-лист пачку не видит, бейдж рутины (по треду) видит; расхождение живёт до следующего прогона. Признанная цена.
   - «Принять» исполнилось, снятие `undecided` упало → флажок пересчитается при следующем решении или погаснет гашением. Признанная цена.

## §6. Решения владельца

Все процедуры адресуются **`pendingId`** (уроки Б2/Б4 ревью Ш1 — с рождения, не патчем):

- `decideDeferred(pendingId, 'approve'|'reject')` → существующие `approvePending`/`rejectPending`; исходы `applied | stale(mismatches) | rejected | already` — значения, не исключения (форма `lifecycle.ts:900-904`).
- `answerQuestion(pendingId, answer | option)` → advisory-lock(pendingId) → append-ответ → под lock(runId) пересчёт открытых → снятие `undecided`, если пусто.
- `decideAll(runId)` («Принять все») → список открытых `kind:'action'` прогона → последовательные approve → сводка (ОЧ.11). Вопросы кнопка не трогает — на них отвечают.
- «Продолжить сейчас» → существующий `runNow` (скрыта при паузе рутины).

Атрибуция: применённое действие — `source:'routine'` + `run_id` (протаскивается `pending.ts:361-369`) → журнал, Undo, откат прогона работают без доработок; ответы и решения владельца — `source:'ui'` → откатом прогона не трогаются (`rollback.ts:96-100`).

## §7. UI

- **Карточка вопроса**: текст; варианты-кнопки (если есть) + поле свободного ответа; после ответа — показан ответ, спокойное состояние; погашенный — «снят следующим прогоном».
- **Карточка отложенного действия**: строки «что изменится» в форме карточки предложения («было» из снятого предусловия, «станет» из payload; `CORE_FIELD_LABELS` без «было» — как у предложения); «Принять / Отклонить»; протухшая — `mismatchNotes`.
- Решённые карточки не исчезают (append-only), но сворачиваются в строку-итог — правило «прячем всё, кроме требующего ответа».
- **Экран прогона** (`RunFeed`): блок «Пачка решений» — единицы прогона со статусами, сверху «Принять все» и «Продолжить сейчас». Существующий блок терминального вопроса (`RoutineQuestionBlock`) — без изменений.
- **Бейдж** обзора рутин учитывает пачки (сервер, GIN-проба — рядом с сегодняшним `waiting`, `routers/routine.ts:260`). **Смарт-лист «Ждут ответа»** — два query-блока: `outcome=checkpoint` + `undecided=true` (`seed/smart-lists.ts:82` + пересев).

## §8. Согласование с Ш1

Ш1 (ревизия 2 не начата) и этот срез стоят на одном носителе и не противоречат друг другу; общие точки, обязательные к соблюдению здесь:

1. Предусловия снимаются при постановке и не переснимаются (Ш1.6) — окно ожидания пачки длиннее, `stale` на approve честен.
2. Правка отложенного действия до принятия — механика Ш1 (`новое pending + edited_from + reason 'edited'`) переносится без изменения этого среза; здесь правки нет (§10).
3. Применение сохраняет `source:'routine'` + `run_id` (Ш1.7).
4. Адресация решений — по `pendingId` (Б2); чтение payload — по `pending.id`, не по вторичному ключу (Б4).
5. Инвариант Ш1-ревизии «на прогоне живо не больше одного предложения» относится к предложениям (`orbis_propose`); единиц пачки на прогоне много — это разные вещи, `storedProposal`-путь единицы не используют.

## §9. Инварианты среза

1. В фоне небезопасное **откладывается с продолжением работы**; запрещённое (`forbidden`) — отклоняется и не откладывается никогда.
2. Единица приёмки атомарна (один pending = один batch executor'а: одна tx, один action, общий откат). Пачка между единицами не атомарна и не претендует.
3. Зависимые операции — только внутри одной единицы; зависимостей между единицами нет по построению.
4. Предусловия единицы снимаются при постановке и не переснимаются.
5. Применённая единица — `source:'routine'` + `run_id`; решение/ответ владельца — `source:'ui'`.
6. Живой прогон никогда не `undecided`; флажок ставится только close-патчем (`system`) и снимается либо процедурами решений (`ui`), либо гашением (`system`). Модель `orbis/agent-run` не трогает (инвариант 6 V1 живёт).
7. Постановка, решение, ответ и гашение идемпотентны; повтор — replay, не дубль и не CONFLICT.
8. Судьбы единиц — только append-only сообщениями; pending-запись не правится.

## §10. Швы (не входит, с условием снятия)

1. **`ask`/`undecided` для внешнего исполнителя** — при появлении запуска исполнителя (ADE-срез 1 «Швы» п.7 / срез 5): снять гейт диспатча + научить закрытие внешнего прогона (включая sweep) выставлять `undecided` и сигнал на тикете.
2. **Симуляция результата** — по спросу живых сценариев; форма: то же `pending_confirmation` + виртуальное состояние (прототип — `BatchState`, `executor.ts:148-169`); для `entity_create` клиентский UUID уже даёт «известный заранее id» бесплатно (`tools.ts:11`).
3. **Правка единицы до принятия** — из Ш1 ревизии 2, без изменения этого среза.
4. **Групповая отложка** (несколько операций одной единицей по воле агента) — нетерминальный глагол по форме `orbis_propose`, когда появятся внешние/составные действия.
5. **Решение-сущность графа** (адресат, роль — decision gate как у Orca) — вместе с участником-сущностью (В7).
6. **Уведомления о пачке** — V3 «увидел — ответил»; до них пачка видна при заходе (известная граница видения).

## §11. Что не входит (без шва)

- Изменения тикетного/MCP-пути и терминального `orbis_checkpoint` — ни поведения, ни контракта.
- Изменения классификатора §7.10 (таблица уровней не меняется).
- Таймауты/сроки жизни единиц (гашение V1.8 — единственный срок).
- batch-undo UI («Отменить» на карточке пачки действий) — отдельный долг П2, не смешивается.
- `orbis_propose` и режим propose рутины — не меняются.

## §12. Сценарии приёмки

1. Прогон задал 2 вопроса `orbis_ask`, продолжил, завершился `finished`; на прогоне `undecided`; в треде 2 карточки вопроса.
2. Архивация из act-прогона → отложена карточкой; модель получила `pending_confirmation` и доработала остальное; в журнале §7.8 отложка следа не оставила.
3. «Принять» действия → применено `source:'routine'`+`run_id`; один action в журнале; откат прогона откатывает и его.
4. «Отклонить» → append-отказ; повторное отклонение возвращает исходную причину.
5. Ответ на вопрос → append-ответ; повторный ответ — replay исходного, не CONFLICT.
6. «Принять все» при одной протухшей → сводка: N applied, 1 stale с полным списком расхождений; остальные применены.
7. «Продолжить сейчас» → `runNow`; новый прогон видит ответы в снимке треда; нерешённые единицы погашены (`stale`/`superseded`).
8. Плановый прогон гасит нерешённое так же (V1.8).
9. Терминальный `orbis_checkpoint` рутины работает как в V1: исход `checkpoint`, блок вопроса, `answered`; пачка и терминальный вопрос сосуществуют на одном прогоне.
10. Двойной клик «Принять» → replay, одна запись в журнале.
11. Смарт-лист «Ждут ответа» показывает и `checkpoint`-прогоны, и `undecided`-пачки; после решения всех единиц прогон из списка уходит.
12. Запрещённое (`forbidden`, `FORBIDDEN_ASPECTS`) → отказ агенту, карточки нет.
13. Крэш прогона после создания единиц → sweep закрыл `failed`; карточки живы; следующий прогон погасил.
14. Грант/MCP: `orbis_ask` недоступен (отказ реестра/диспатча); `orbis_checkpoint` тикетного пути не изменился.
15. Ретрай моделью того же отложенного вызова в том же прогоне → тот же `pendingId`, вторая карточка не появилась.
