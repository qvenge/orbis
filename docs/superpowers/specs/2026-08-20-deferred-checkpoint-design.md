## §1. Зачем

Два факта кода, установленные разведкой и подтверждённые ревью:

1. **`orbis_checkpoint` не блокирует прогон — он его закрывает.** Вопрос — терминальный исход: `outcome:'checkpoint'`, `finished_at`, цикл модели выходит (`agent-loop/verbs.ts:884-909`, `runner.ts:378-385`). Ответ владельца читает *следующий* прогон через историю. Один вопрос стоит прогону всей оставшейся работы.
2. **Откладывать действия рутине запрещено инвариантом 5** (V1.10): `source==='routine' && level!=='execute'` → `FORBIDDEN_LEVEL` «в фоне небезопасное отклоняется, а не откладывается» (`tools/dispatch.ts:752-758`).

Следствие для North Star (§4 миссии): «брать больше» упирается в то, что каждый вопрос обрывает работу, а каждое небезопасное действие — тупик. Cloudflare OS называет этот антипаттерн причиной, по которой пользователи включают auto-approve — «which is, obviously, unsafe». Срез даёт противоположное: прогон доделывает всё, что может, вопросы и небезопасное копятся **пачкой решений**, владелец разбирает её когда удобно — поштучно или разом — и одним нажатием продолжает работу рутины.

## §2. Словарь

- **Единица решения** — pending в треде рутины с **обязательным** полем `kind`:
  - **вопрос** (`kind:'question'`) — текст ≤4000 + опциональные варианты ответа (≤4); payload-операций нет; на него *отвечают*;
  - **отложенное действие** (`kind:'action'`) — payload = вызов тула + **предусловия, снятые при постановке** (ОЧ.13); его *принимают или отклоняют*.
- **Пачка решений** — все открытые единицы прогона (продуктово: и рутины — открытые единицы всех её прогонов).
- **`undecided`** — скалярный флажок на аспекте прогона: «у прогона есть нерешённые единицы». Все писатели — `source:'system'` (ОЧ.6).

## §3. Решения

### ОЧ.1. Скоуп: вопросы + действия, без симуляции результата *(выбор владельца)*

Оси: (А) нетерминальные вопросы, (Б) отложенные действия. Ось (В) — симуляция результата — **не берётся**: честная симуляция невозможна (`monotonicUpdatedAt` `executor.ts:941-943`; правка body требует настоящего штампа `:1205-1220`; серверные достройки — бюджет-хук, засев тела, канонизация `:1419-1428` — невидимы вызывающему; dry-run пути нет, `preview` исполняет). Модель получает честное `{status:'pending_confirmation', pendingId}` — ветка `toolResultPayload` уже существует (`runner.ts:433-440`). Симуляция — шов (§10).

### ОЧ.2. Носитель — существующий pending; второго механизма отложенного не заводим

`policy/pending.ts` даёт боем проверенное: immutable payload в `chat_messages.metadata.pending` (схема без `.strict()` — поля добавляются без миграции), невидимость для журнала §7.8 до применения, двухуровневую идемпотентность одним ключом (`pendingMessageId` + `batchId = pendingId` + `batchAuditMessageId`), сериализацию advisory-lock'ом, append-only судьбу, атрибуцию сквозь одобрение. «Второй механизм „отложенной правки" пришлось бы отдельно учить откату, ревалидации и сериализации — то есть повторить pending хуже» (`routines/propose.ts:6-9`).

Расширение записи: `kind`, для вопроса — `question`, `options?`; для действия — снятые предусловия (ОЧ.13). **У единиц `kind` обязателен и явен** (Б5); правило «отсутствие `kind` = действие» действует только при одиночном чтении по id — для обратной совместимости чатовых pending и предложений. Схема ослабляет `tool`/`input` до условно-обязательных (обязательны при `kind:'action'` и при отсутствии `kind`); `approvePending`/`rejectPending` отказывают на `kind:'question'` структурной ошибкой, процедура ответа — на `kind:'action'`; чатовые `ai.approve`/`ai.reject` получают тот же гейт (С7 ревью).

### ОЧ.3. Гранулярность приёмки: поштучно; зависимое — в один pending *(выбор владельца)*

Единица приёмки = один pending; внутри — атомарно (один batch executor'а, одна транзакция, один action §7.8, общий откат). Пачка = несколько **независимых** единиц: решаются порознь или кнопкой «Принять все»; отклонение одной не трогает другие. Зависимые операции обязаны лежать в одном pending — **зависимостей между pending'ами нет по построению** (урок NIM-402). Сегодняшние confirm-действия рутины одиночны, автоотложка кладёт один вызов; групповой глагол — шов (§10). «Всё или ничего» V1.7 сужается до своей естественной области — внутри единицы.

### ОЧ.4. Отложка — на диспатче; объектный пре-чек; инвариант 5 переформулируется

В `runMutation` гейт рутины меняется по уровню классификатора §7.10 **после нового объектного пре-чека**:

| Условие | Сегодня | Становится |
|---|---|---|
| цель в `ROUTINE_UNTOUCHABLE_OBJECTS` ∪ `orbis/assignment`, `grantsAutonomy`, или правка инструкции act-рутины | `FORBIDDEN_LEVEL` (частично — лишь на executor'е) | **`FORBIDDEN_LEVEL` агенту на диспатче, отложки нет** |
| `execute` | исполнить | исполнить (без изменений) |
| `explicit-confirmation` (прочее) | `FORBIDDEN_LEVEL` | **снять предусловия (ОЧ.13) → `createPending(kind:'action')` → ответ модели `pending_confirmation`** |
| `preview` | недостижим (batch рутине закрыт) | недостижим, без изменений |
| `forbidden` | `FORBIDDEN_LEVEL` | `FORBIDDEN_LEVEL` |

Пре-чек по объекту (Б2 ревью) — чтение целей из БД в диспатче до постановки (прецедент — `actRoutineInstructionTargets`, `dispatch.ts:742-745`): карточка, которую executor гарантированно убьёт на «Принять» (`invariants.ts:364-425`), не должна родиться — «отказ на approve пришёл бы владельцу, который ни в чём не виноват» (`propose.ts:19-22`). Отдельно и важнее: **выдача автономии и правка инструкций рутин из фона не откладываются** — карточка «снять замок V1.10» в пачке под «Принять все» недопустима (умолчание §14.В1). Классификатор §7.10 не меняется.

**Инвариант 5, новая формулировка:** «В фоне небезопасное **откладывается с продолжением работы** (pending-единица в треде рутины); запрещённое — по уровню или по объекту — отклоняется и не откладывается». Исходное обоснование («pending повис бы вопросом без контекста») снято: контекст пачке даёт отчёт завершившегося прогона рядом с карточками.

### ОЧ.5. `orbis_ask` — нетерминальный вопрос в `ROUTINE_BASE_TOOLS`; терминальный `orbis_checkpoint` остаётся

Новый тул `orbis_ask`: `{run_id, question ≤4000, options?: string[] ≤4}` → pending `kind:'question'`, модели возвращается `{pending_id}`. Ключа идемпотентности во входе нет — выводится из содержимого (ОЧ.9).

`orbis_ask` входит в **`ROUTINE_BASE_TOOLS`** (`registry.ts:73`) — доступен рутине в обоих режимах, симметрично чекпойнту: довод «отнять вопрос у режима `propose` значило бы оставить рутину без выхода» (`registry.ts:67-70`) распространяется на нетерминальный вопрос (Б6 ревью). **Инвариант 4 V1 переформулируется**: «режим `propose`: любая мутация, кроме `orbis_propose` и глаголов базы рутины (`orbis_checkpoint`, `orbis_ask`), отклоняется на сервере». Гранту/MCP `orbis_ask` закрыт (ОЧ.12).

Терминальный `orbis_checkpoint` («без ответа дальше бессмысленно») не меняется: исход `checkpoint`, блок вопроса, `answered`. Выбор делает модель; различие объясняет новый промпт **`routine-v2.ts` + фикстура**; описания обоих тулов в реестре правятся (сегодняшний текст чекпойнта писан под грантовый путь, `registry.ts:667-678`).

`orbis_ask` — обычный нетерминальный тул: не в `TERMINAL_TOOLS`, результат кладётся в разговор, вызов пишется шагом.

### ОЧ.6. `undecided` — скаляр на аспекте прогона; все писатели — `source:'system'`

`RUN_OUTCOMES` не расширяется. Отложивший прогон завершается обычным `finished` (или `checkpoint` — тогда у прогона и терминальный вопрос, и пачка). Close-патч пишет `undecided: true`, если открытые единицы есть. Массив деталей на аспекте не заводится (D31); детали — в треде.

**Все три писателя флажка — `source:'system'` (+`run_id`)**: постановка (close-патч), снятие (процедуры решений — после решающего действия, бухгалтерским патчем), гашение (Б7 ревью — рулинг V1 о пометках судьбы, спека V1:636: иначе «отмени последнее» после «Принять» снимает флажок, а не действие; `undo.ts:74` пропускает только `system`). Решение владельца атрибутировано там, где оно есть: ответ — `ui`-сообщением, применение — `routine` через approve. Инвариант 6 V1 не нарушается. Цена: одно поле в `.strict()`-аспекте → одноразовый пересев реестра.

### ОЧ.7. Ответы доезжают новым слоем истории прогонов; продолжение — кнопкой «Продолжить сейчас» *(выбор владельца; механизм — ревизия 2 по Б1)*

Контекст рутинного прогона ленту треда **не читает** — «ВМЕСТО ЛЕНТЫ ТРЕДА — ИСТОРИЯ ПРОГОНОВ» (`routines/context.ts:9-11`); утверждение ревизии 1 «снимок треда уже входит в подготовку» было ложным. Доставка — **расширение `RoutineHistoryItem`**: к каждому прогону хвоста истории — список его единиц `{вопрос → ответ | судьба}` и `{действие → принято/отклонено/снято}`, собранный GIN-пробой `{pending:{run_id, kind}}` + PK судеб; строка истории на каждую решённую единицу («спрашивал: … — ответ: …»; «откладывал: … — принято»). Потолки: текст единицы ≤ `HISTORY_TEXT_CAP` (500), единиц — не больше капа ОЧ.10; переполнение — усечение с «и ещё N». Хвост истории — прежние 7 прогонов.

Продолжение работы: кнопка **«Продолжить сейчас»** на пачке = существующий `runNow`. Плановый прогон — второй, гарантированный путь чтения. Автозапуск по каждому ответу отклонён (дебаунс-механика, прогоны без явного запроса); ждать только расписания — отклонено (теряется пол-ценности).

### ОЧ.8. Гашение: V1.8 распространяется на пачку; судьба вопроса — единственна

Новый прогон — плановый или «Продолжить сейчас» — **гасит все нерешённые единицы прошлых прогонов**: действия → `rejectPending` со **своими текстами** для единиц (не «Предложение…» — С6 ревью), вопросы → append-сообщение гашения со своим текстом. `closeOpenOfRun` обобщается с «один вопрос ИЛИ одно предложение» до списка; порядок «сначала судьба pending, потом патч прогона» и уважение чужой причины сохраняются (`lifecycle.ts:252-257`, `:289-296`). Откат прогона гасит так же. Гашение снимает `undecided` с прогонов, чьи единицы погасило (`source:'system'`).

**Правило единственности судьбы вопроса** (Б4 ревью): ответ и гашение — оба под `lock(pendingId)`; под замком перечитываются оба PK; **первая записанная судьба финальна**. Ответ на погашенный → структурный `{status:'stale'}` без записи (карточка показывает «снят следующим прогоном» — умолчание §14.В2); гашение отвеченного → пропуск: ответ важнее гашения — то же правило, что у терминального пути (`lifecycle.ts:331-334`). `undecided` считает решёнными обе судьбы.

Следствие, которое владелец знает: ответил на часть и нажал «Продолжить» — остальное погашено; актуальное прогон переспросит/переотложит заново по свежему состоянию. Особый случай: «Продолжить сейчас» при неотвеченном **терминальном** чекпойнте того же прогона гасит и его (V1.8) — кнопка предупреждает об этом явно (умолчание §14.В3). Таймаута у единиц нет.

### ОЧ.9. Идемпотентность всех рёбер

- Постановка действия: дедуп-ключ `defer:{runId}:{hash(tool + canonical(input))}`; вопроса — `ask:{runId}:{hash(question + options)}`. **`canonical` — общая утилита канонической сериализации** (рекурсивная сортировка ключей + `JSON.stringify`), фиксируется этим срезом и закрывает открытый вопрос 3 Ш1 rev 2 (С4 ревью) — правило одно на оба среза.
- «Принять» — существующий replay (`batchId = pendingId`); «Отклонить» — повтор возвращает исходную причину.
- **Ответ на вопрос — replay, не CONFLICT**: append-сообщение с PK `answerMessageId(owner, pendingId)`. Процедура сравнивает содержимое: тот же ответ → replay; **другой** ответ → `{status:'already', answer}` с показом применившегося (С5 ревью — молчаливое схлопывание разных ответов запрещено).

### ОЧ.10. Потолки: свой лимит шагов и кап единиц на прогон

- `ROUTINE_MAX_STEPS = 12` (только рутинный раннер; чат не меняется). Единица потолка — **вызов провайдера**, не вызов тула: несколько tool_use одним ответом модели — один шаг (С9 ревью); дедлайн 10 мин не меняется — прогон не ждёт, он работает и завершается.
- **Кап единиц на прогон — 10** (умолчание §14.В4): превышение — структурный отказ `orbis_ask`/отложки («пачка полна — заверши прогон»); модель корректируется. Ограничивает карточки в треде и пачке реально (шаги этого не делают — С3 ревью); созвучен доводу потолка предложения («список, который не помещается на экран, — требование довериться», `routines/constants.ts:6-8`).

### ОЧ.11. «Принять все» — последовательно, не атомарно между единицами

N последовательных `approvePending` (каждый — атомарный batch под своим advisory-lock). Между единицами атомарности нет и она не обещается — как у отката прогона («обещание уровня UX», `rollback.ts:17-22`). Итог — сводка по каждой: `applied / stale (mismatches) / rejected / already`. Одна протухшая не блокирует остальные. Повтор кнопки = N replay'ев. Кнопка трогает только `kind:'action'` — вопросы не «принимаются».

### ОЧ.12. Контракт един; гейт доступа — временный, с условием снятия *(выбор владельца)*

В схеме `orbis_ask`, записи pending и флажке `undecided` нет ничего рутинного. Гейт «только внутренний раннер» — существующий механизм `routineOnly`/`routineGate` (прецедент `orbis_propose`, `registry.ts:613`). Причины: (1) Orbis контролирует петлю только внутреннего раннера — внешний агент может задать вопросы и умереть, оставив тикет без сигнала; (2) «Продолжить сейчас» для внешнего не работает — Orbis не умеет его запускать (шов «запуск исполнителя»); (3) боль сейчас у рутины. **Условие снятия**: появление запуска исполнителя (§10.1).

### ОЧ.13. Предусловия единицы снимаются диспатчем при постановке *(ревизия 2 по Б3)*

Дисп-путь `createPending` сегодня сохраняет payload как есть — без предусловий отложенная архивация «не протухнет никогда», карточке неоткуда взять «было», `stale` недостижим (Б3 ревью). При постановке единицы-действия диспатч читает цель и снимает предусловия **по образцу `buildUpdate`** (`propose.ts:545-591`): по каждому затрагиваемому полю `in:[текущее]`/`absent:true`; для тела — `expectedUpdatedAt`; для архивации — `archived absent/false` + снимок заголовка для карточки. Проверка — как у предложения: полным конвейером на approve, с полным списком расхождений (`executor.ts:852-895`). Инвариант «предусловия снимаются один раз и не переснимаются» (Ш1.6) получает носителя.

## §4. Модель данных

**Запись pending** (расширение, без миграции):

```
pending: {
  id, created_at, actor_kind, source,          // существующие
  run_id, routine_id?, actor_grant_id?,        // существующие optional
  kind?: 'question' | 'action',                // у ЕДИНИЦ — обязателен и явен (Б5);
                                               // отсутствие = 'action' только при чтении по id
  // kind:'action':
  tool?, input?,                               // input несёт снятые предусловия (ОЧ.13)
  // kind:'question':
  question?, options?: string[],
}
```

**Судьбы.** Действие: `pending → approved | rejected(owner|superseded|stale|…)` — существующие, **со своими текстами для единиц** (С6). Вопрос: `open → answered | stale`; переходы — append-only сообщениями с детерминированными PK: ответ — `answerMessageId(owner, pendingId)`, `{type:'question_answered', answer, option?}`; гашение — `{type:'question_stale'}` со своим текстом. Pending-запись не правится. Единственность судьбы — ОЧ.8.

**Аспект прогона**: `undecided?: true` (скаляр). `checkpoint`/`reply` терминального пути не меняются.

**Пробы единиц** — всегда `{pending:{run_id, kind:…}}` (Б5): сверка `undecided`, `decideAll`, гашение, история, экран прогона. Предложение (`orbis_propose`, без `kind`) под эти пробы **не попадает**; `storedProposal` переводится на `{pending:{id}}` — общая работа со Ш1 rev 2 (§8).

## §5. Поток прогона

1. Модель зовёт тул. Мутация → `runMutation`: объектный пре-чек → классификация → исполнение или отложка (ОЧ.4, ОЧ.13). `orbis_ask` — создание вопроса. Оба возвращают модели честный результат, результат в разговор, вызов пишется шагом.
2. `createPending` — в собственной транзакции; карточка своего вида; кап ОЧ.10 проверяется до записи.
3. Прогон завершается как обычно; close-патч — с `undecided:true`, если открытые единицы есть (список ведётся в памяти; финальная сверка — проба по `run_id, kind`).
4. **Подметание** рутинного прогона дополняется той же пробой и флажком в собственный CAS-патч (С1 ревью) — смерть процесса не теряет `undecided` («рестарт и сон — основной вид сбоя», V1.12).
5. **Сбой-лестница**:
   - pending создан, крэш до ответа модели → sweep закроет `failed` **с флажком** (п.4), единицы живы, гасятся следующим прогоном.
   - «Принять» исполнилось, снятие `undecided` упало → пересчёт при следующем решении или гашении. Признанная цена.
   - решение единицы мимо `decideDeferred` (чатовые `ai.approve`/`ai.reject` — с гейтом `kind`, С7) пересчёт флажка не делает → чинится лениво там же. Признанная цена.
   - пауза рутины: ответы принимаются, читать некому до снятия паузы — плашка на пачке (§7); подсветка паузы ответом — вне среза (С2).

## §6. Решения владельца

Все процедуры адресуются **`pendingId`**:

- `decideDeferred(pendingId, 'approve'|'reject')` → существующие `approvePending`/`rejectPending`; отказ на `kind:'question'` структурной ошибкой; исходы `applied | stale(mismatches) | rejected | already` — значения.
- `answerQuestion(pendingId, answer | option)` → `lock(pendingId)` → перечитка обеих судеб (ОЧ.8) → append-ответ (или `already`/`stale` — ОЧ.9) → бухгалтерский патч `undecided` (`system`), когда открытых не осталось.
- `decideAll(runId)` («Принять все») → открытые `{run_id, kind:'action'}` → последовательные approve → сводка (ОЧ.11).
- «Продолжить сейчас» → существующий `runNow` (скрыта при паузе; предупреждение при живом терминальном вопросе — ОЧ.8).

Атрибуция: применённое действие — `source:'routine'` + `run_id` → журнал, Undo, откат прогона работают без доработок; ответы — `ui`-сообщения; патчи флажка — `system` (ОЧ.6).

## §7. UI

- **Карточка вопроса**: текст; варианты-кнопки + поле свободного ответа; после ответа — показан ответ; погашенный — «снят следующим прогоном», ответа не принимает.
- **Карточка отложенного действия**: строки «было (из снятого предусловия ОЧ.13) → станет»; «Принять / Отклонить»; протухшая — `mismatchNotes`.
- Решённые карточки сворачиваются в строку-итог («прячем всё, кроме требующего ответа»).
- **Экран прогона**: блок «Пачка решений» — единицы со статусами, «Принять все», «Продолжить сейчас» (с предупреждением при неотвеченном терминальном вопросе); плашка «рутина на паузе — ответы прочитает после возобновления» при паузе. Блок терминального вопроса — без изменений.
- **Бейдж** «ждут» — **аспектным фильтром по прогонам** (`undecided=true` в `runsOfParent`), как сегодняшний `waiting` — без GIN-проб треда (С8); точное число единиц — только на экране прогона (одна проба). **Смарт-лист «Ждут ответа»** — два query-блока: `outcome=checkpoint` + `undecided=true` (+ пересев).

## §8. Согласование с Ш1 (ревизия 2, `ea58692`, D41)

1. Предусловия снимаются при постановке и не переснимаются (Ш1.6) — теперь с носителем и у диспатч-пути (ОЧ.13).
2. Правка единицы до принятия — механика Ш1 (`новое pending + edited_from + reason 'edited'`) переносится без изменения этого среза (§10.3).
3. Применение сохраняет `source:'routine'` + `run_id` (Ш1.7).
4. Адресация решений — по `pendingId` (Б2 Ш1); чтение payload — по `pending.id` (Б4 Ш1).
5. **Общие работы, «делается один раз, кто первым дойдёт»**: tx-вариант `rejectPending` (лестница Ш1.5 и гашение списка здесь); **перевод `storedProposal` на `{pending:{id}}`** — обязательное предусловие обоих срезов (Б5 этого ревью = Б4 того); **утилита канонической сериализации** (ОЧ.9 = открытый вопрос 3 Ш1).

## §9. Инварианты среза

1. В фоне небезопасное **откладывается с продолжением работы**; запрещённое — **по уровню или по объекту** (`ROUTINE_UNTOUCHABLE_OBJECTS` ∪ `orbis/assignment`, `grantsAutonomy`, инструкция act-рутины) — отклоняется и не откладывается никогда.
2. Единица приёмки атомарна (один pending = один batch executor'а). Пачка между единицами не атомарна и не претендует.
3. Зависимые операции — только внутри одной единицы; зависимостей между единицами нет по построению.
4. Предусловия единицы снимаются при постановке (диспатчем — ОЧ.13, глаголами — как сегодня) и не переснимаются.
5. Применённая единица — `source:'routine'` + `run_id`; ответ владельца — `ui`; патчи `undecided` — только `system`.
6. Живой прогон никогда не `undecided`; флажок пишут close-патч, sweep и процедуры решений/гашения — все `source:'system'`. Модель `orbis/agent-run` не трогает (инвариант 6 V1 живёт).
7. Постановка, решение, ответ и гашение идемпотентны; повтор — replay; **другой** ответ — `already` с показом применившегося.
8. Судьбы единиц — только append-only сообщениями; судьба единственна: первая записанная финальна, ответ важнее гашения; pending-запись не правится.
9. Единиц на прогон — не больше капа (ОЧ.10); превышение — структурный отказ агенту, не молчаливое усечение.

## §10. Швы (не входит, с условием снятия)

1. **`ask`/`undecided` для внешнего исполнителя** — при появлении запуска исполнителя: снять гейт + научить закрытие внешнего прогона (включая sweep) выставлять `undecided` и сигнал на тикете.
2. **Симуляция результата** — по спросу живых сценариев; форма: `pending_confirmation` + виртуальное состояние (прототип `BatchState`); клиентский UUID даёт «известный заранее id» для `entity_create` бесплатно.
3. **Правка единицы до принятия** — из Ш1 (`edited_from`, `'edited'`), без изменения этого среза.
4. **Групповая отложка** — нетерминальный глагол по форме `orbis_propose`, когда появятся внешние/составные действия.
5. **Решение-сущность графа** (адресат, роль) — вместе с участником-сущностью (В7).
6. **Уведомления о пачке** — V3; до них пачка видна при заходе.
7. **Подсветка паузы ответом** (С2) — вместе с пересмотром пауз.

## §11. Что не входит (без шва)

- Изменения тикетного/MCP-пути и терминального `orbis_checkpoint` — ни поведения, ни контракта.
- Изменения классификатора §7.10 (таблица уровней не меняется; меняется реакция диспатча).
- Таймауты единиц (гашение V1.8 — единственный срок).
- batch-undo UI — отдельный долг П2.
- `orbis_propose` — не меняется (режим `propose` меняется ровно на доступность глаголов базы — ОЧ.5).

## §12. Сценарии приёмки

1. Прогон задал 2 вопроса `orbis_ask` (в т.ч. в режиме `propose`), продолжил, завершился `finished`; `undecided`; 2 карточки.
2. Архивация из act-прогона → отложена карточкой **с «было» из снятого предусловия**; модель получила `pending_confirmation` и доработала; в журнале §7.8 отложка следа не оставила.
3. «Принять» → применено `source:'routine'`+`run_id`; один action; откат прогона откатывает и его.
4. «Отклонить» → append-отказ **с текстом единицы, не предложения**; повтор возвращает исходную причину.
5. Ответ на вопрос → append-ответ; повторный тот же — replay; **другой** — `already` с показом применившегося.
6. «Принять все» при одной протухшей → сводка: N applied, 1 stale с расхождениями; вопросы не тронуты.
7. «Продолжить сейчас» → `runNow`; новый прогон видит ответы **в истории прогонов** (строки единиц); нерешённое погашено.
8. Плановый прогон гасит так же; гашение сняло `undecided`.
9. Терминальный `orbis_checkpoint` работает как в V1; пачка и терминальный вопрос сосуществуют; «Продолжить сейчас» при неотвеченном терминальном вопросе предупреждает и гасит его.
10. Двойной клик «Принять» → replay, одна запись в журнале.
11. Смарт-лист видит `checkpoint`-прогоны и `undecided`-пачки; propose-прогон с ждущим предложением в `undecided` **не попадает** (проба по `kind`).
12. Запрещённое по уровню И по объекту (архивация рутины, `grantsAutonomy`, инструкция act-рутины) → отказ агенту на диспатче, карточки нет.
13. Крэш прогона после создания единиц → sweep закрыл `failed` **с `undecided`**; карточки живы; следующий прогон погасил.
14. Грант/MCP: `orbis_ask` недоступен; тикетный чекпойнт не изменился.
15. Ретрай моделью того же вызова (в т.ч. с переставленными ключами JSON — каноникализация) → тот же `pendingId`, второй карточки нет.
16. 11-я единица прогона → структурный отказ «пачка полна»; прогон завершается штатно.
17. Гонка «ответ vs гашение» → первая судьба финальна; ответ на погашенный → `stale` без записи; гашение отвеченного → пропуск.
18. «Отмени последнее» после «Принять» единицы → отменяется **применённое действие**, не патч флажка (все патчи флажка — `system`).
19. `decideAll` не трогает предложение propose-прогона (проба по `kind`); `decideProposal` работает как прежде.
