# Свойства и роли — решения до спеки (путь С)

**Статус:** зафиксированные решения обсуждения 2026-08-23 (вторая половина дня). Не спека: полноценная
спека «Свойства и роли» пишется отдельно и забирает отсюда решения Р1–Р20, если их не опровергнет проба.
Предшественник — `2026-08-23-property-ref-type-notes.md` (тип `ref`); что в нём изменилось — в его шапке.
Вопросы владельцу — §5; мои сомнения, ещё не ставшие вопросами, — §6.

## 1. Рулинги владельца, на которых стоит документ

- **Пользователей нет.** Продукт задеплоен, но в фазе активной разработки; всё в базе можно сносить и
  переписывать. Владелец явно скажет, когда начнёт пользоваться сам. До этого — никаких compat-слоёв
  ради прод-данных, никакого «двойного чтения».
- **Единственный MCP-клиент** — локальный Claude Code на машине владельца.
- **Цена работ — не ограничение.** «Если надо переделать ядро — переделаем, чтобы сделать правильно и
  хорошо». Критерий — North Star (05-mission §4) и анти-цели (§5).
- Валидатор — «сделать правильно»; разрастание словаря — проблема реальная, меры смягчения
  проектировать (§3, Р17).

## 2. Почему путь С, а не 3-лайт

3-лайт (определение общее, значение в аспекте) с дополнениями «зеркало» и «личный аспект свойств»
признан **компенсацией** аспект-центричного хранилища: зеркало — денормализация с инвариантом
согласованности, `user/fields` — «аспект, который ничего не значит». Путь А дрейфует в С по
накоплению, но в худшей форме. Аргументы за С, проверенные North Star: структура приходит после данных
(§3.9/§3.10 PRD уже признают это — в С это операция реестра, не миграция); общий словарь фактов для
констелляции приложений (D36); «не ещё один трекер» (факт пишется без выбора типа); «не чёрный ящик»
(у факта один адрес → диффы, undo, атрибуция читаются). Прецеденты семантики: Tana (supertags + глобальные
поля, одно значение на узел), Anytype (types + relations), Obsidian (свойства типизированы глобально).

## 3. Решения

**Р1. Модель.** Свойство — факт; роль — интерпретация. Сущность = core + body + `props` + `roles`.
Слоя `meta` нет (Р14). Роль — то, что сегодня называется аспектом (термин — В1).

**Р2. Реестр свойств.** Поля: `id`, `key`, `label`, `description`, `type`, `status` (`active` |
`proposed` | `deprecated`), `scope?` (Р15), `merged_into?` (Р10). Четыре имени у свойства — четыре разные
судьбы (решение В4, 23.08 вечер): **id** — тождество, не меняется никогда; **key** — машинная ручка,
меняется редко и без следа в данных; **label** — подпись per-locale, меняется свободно; **description** —
смысл per-locale, меняется свободно. Первый вариант заметки отказывался от key ради «без алиасов»; с
хранением запросов как AST по id (Р12) алиасы не нужны ни одному хранимому артефакту, и key возвращён.

**Р3. Id и key.** **Id:** встроенные — фиксированные читаемые строки `orbis/task_status`, `orbis/amount`,
`orbis/category_ref` (наш контракт с собой, как имена таблиц); пользовательские и из приложений — uuid.
Id не выходит за пределы хранилища, SQL и кода; на экране — баг. **Key:** ASCII-слаг в namespace автора
(`orbis/task_status`, `user/effort`, `health-app/weight`), один на все локали, уникален среди видимого
пользователю набора (`orbis/*` + свои + подключённые приложения) — проверяется при создании и
переименовании. Key видят машины и продвинутый текстовый режим: имена параметров `attach_*`, текст
запросов от LLM и кода, MCP, golden-тесты, канонический экспорт. У встроенных key изначально равен id;
расходятся только при переименовании key. Переименование key — видимое изменение машинного контракта
(модель в диалоге получит «неизвестное поле» и перечитает каталог; внешний агент с key в промпте
сломается — и это правильно); **алиасов key нет.** Слаг при создании пользовательского свойства: AI
предлагает английский (`user/effort`), без AI — транслитерация; коллизия → суффикс; ставки низкие,
потому что key изменяем. Варианты `select` — та же пара: `key` варианта (`done`, стабильный ASCII, хранится
в данных как сегодня) + label per-locale; переименование варианта — смена label, не key.

**Р4. Label и description.** Оба — **per-locale** (В4): встроенные и из приложений — `{ru, en, …}`,
пользовательские — одна запись на языке автора; fallback — локаль пользователя → `en` → любая.
Label — подпись, свободно меняется, **уникален внутри роли** (обязательно:
иначе два параметра «статус» в одном туле) и желательно глобально у пользователя — конструктор
подсказывает: «„статус“ уже есть у задачи — то же свойство или другое?». Description —
**обязательное** поле: для AI это единственный носитель смысла (уходит в `description` параметра
JSON Schema тулов и в каталог `entity_query`), для человека — разводка одинаковых label и понимание
чужих свойств, для садовника словаря — основание «это одно и то же?». Встроенные и из приложений — без
description не принимаются; пользовательские — AI предлагает черновик из контекста создания.

**Р5. Роль.** `id`, `label`, `description`, набор ссылок на свойства с `required`, `ai_instructions`,
`tag_mappings`, служебность, view-подсказки. **У свойства один тип и одни ограничения; роль может
добавить только обязательность** (и, возможно, значение по умолчанию — спека). Другие ограничения
(усилие 1–5 vs 1–10) — другое свойство: значения не взаимозаменяемы. Роль ссылается на свойства,
**не владеет ими**: namespace свойства — автор (`orbis/`, `user/`, `<app>/`), никогда не роль.

**Р6. Хранение.** `entities.props jsonb` — `{ "<prop-id>": value }`, одно значение на свойство на
сущность; `entities.roles` — массив id ролей. GIN по обоим. `ref` хранит uuid сущности, как сегодня;
`cardinality: many` — ограниченный массив (правило 1 §10). Два стиля id в одной карте — намеренно (Р3).

**Р7. Валидация.** Композиционная, над результатом слияния всей сущности, как сегодня
(`mergeAspects → validate → commit`): каждое свойство — по своему типу (ajv по сгенерированной
схеме свойства), каждая роль — обязательные присутствуют, неизвестных свойств нет. Атомарность —
на уровне операции: `attach_<роль>` принимается целиком или отвергается. JSON Schema на роль
по-прежнему генерируется — для тулов. Доменные инварианты (`grant_id` ⇔ `executor=agent`,
`status ↔ completed_at`, условный `occurred_on`) переводятся с тестами-близнецами; golden-корпус
«сущность → вердикт» на старом и новом валидаторе до замены.

**Р8. Тулы LLM и MCP.** `attach_<роль>` остаются (генерируются из набора роли), `entity_query`
принимает текст грамматики и исполняет на лету — этот путь не меняется. Имена параметров тулов —
**key** (Р3); `description` параметра — label + description в локали пользователя + варианты. Кириллица в
именах параметров не возникает (снято С1).

**Р9. Снятие роли не уничтожает факты.** Свойства, которые больше не требует ни одна роль, остаются
свободными (видны в «Свойствах», доступны query). Удаление факта — отдельное явное действие, обратимое.

**Р10. Операции реестра.** Три: **сослаться** (добавить существующее свойство в роль — данных не
трогает); **переименовать label/description** (бесплатно); **слить** (`merged_into` на поглощённом,
резолвер следует в один шаг; ключи в `props` переписываются исполнителем в транзакции с журналом и
undo; конфликт значений на одной сущности — в пачку решений D42). Слияние — **единственная операция
реестра, трогающая данные**. Операции «переименовать id/key» больше не существует.

**Р11. Именование встроенных при переводе.** Id называет смысл, не владельца: `orbis/amount`,
`orbis/currency`, `orbis/category_ref` (financial+budget → одно свойство); `orbis/task_status`,
`orbis/project_stage`, `orbis/routine_stage` (разные enum — разные факты); `orbis/due_date` ≠
`orbis/start_at` (срок ≠ начало). Служебные uuid агент-прогона (`action_id`, `pending_id`,
`edited_from`) — не `ref`. `grant_id` → `kind: 'grant'`. Полная таблица по 13 аспектам — задача спеки.
Варианты `select` — key варианта + label per-locale (Р3).

**Р12. Сохранённые запросы — ссылки, не имена.** Каноническая форма сохранённого запроса —
разобранный AST с id свойств/ролей/сущностей; текст грамматики — поверхность ввода и показа. Узел
query-блока хранит `text` + `ast` (ast пуст, если текст не разбирается или не резолвится — блок
показывает текст с ошибкой, как сегодня). `progress_source` — так же. Резолв label → id на границе
сохранения; исполнение компилирует id → `props->>'<id>'`. Парсер принимает key (`orbis/task_status=done`) и label (`статус=сделано`, резолв по локали, квалификация
аспектом при неоднозначности); сериализатор печатает **key для машин и label для человека** — два рендера
одного AST. **Алиасов имён нет** — они были заплаткой на хранение имён в тексте.
`query_refs[]` на сущности (как `body_refs`) — индекс «где используется». Экспорт: markdown-проекция
с актуальными label + снимок реестра (id ↔ label ↔ description); импорт резолвит по снимку.
Прецедент внутри Orbis: сущности в body адресуются `[[entity:uuid]]`/`{{embed:uuid}}`, не заголовком.
Поднятие `DOC_SCHEMA_VERSION` согласовать со спекой трансклюзии (В4).

**Р13. Грамматика.** Сам язык не меняется по сути, меняется роль: из формата хранения — в синтаксис
ввода/вывода. Правки: label в позиции поля с кавычками (`"дата оплаты">2026-08-01`); квалификация
аспектом для неоднозначных label (форма в спеке); key всегда однозначен; `aspect=` принимает key аспекта
(`orbis/task`, как сегодня) и label. Статическое подмножество для
`ref.target`/`scope` — по заметке о `ref`.

**Р14. `meta` удаляется.** Факт: сегодня `meta` — write-only (пишет AI через тулы без схемы, не
читает ни web, ни сервер; §3.10 не реализован) — дефект по анти-цели 3. В С свойство существует
независимо от роли, поэтому AI пишет извлечённый факт **свободным свойством** (`orbis/amount` на
записи без роли); §3.9 становится свойством модели, §3.10 — «навесь роль, обязательные уже стоят».
Новый факт без подходящего свойства: AI заводит свойство в статусе `proposed` (label, черновик
description, тип по значению) — видно сразу, подтверждение через пачку D42 / садовника, **кап** на
неподтверждённые; либо факт остаётся текстом в body (правило для промпта: свойство — то, по чему
захотят фильтровать или считать). Запрет application state в `props` сохраняется. **`tags`
остаются** как единственный слой без схемы; `relations.meta` — другое, не трогается. Уходят:
колонка, `meta` в тулах/wire, абзацы в промптах v1–v4 и routine-промптах, GIN по meta.

**Р15. Scope свойства — статический запрос** (из обсуждения «личного аспекта свойств», остаётся в
С): свойство со `scope` (`aspect=…`, `tags=…`, `children_of=<id>`) — «колонка»: показывается пустым на
каждой подходящей сущности, столбец в списках; без scope — «по требованию». Тот же механизм, что
`ref.target`. Нужен фильтр присутствия поля в грамматике (`has=…`) — спека.

**Р16. Тип `ref`** — по заметке `2026-08-23-property-ref-type-notes.md` с поправками из её шапки
(тип живёт в определении свойства, `x-orbis-type` в схеме роли — производная; проверка через
query-движок; зеркало в `relations` — решение).

**Р17. Садоводство словаря — постоянная функция продукта**, не одноразовая работа. Меры:
namespace = автор; общие понятия (`orbis/amount`, `orbis/date`, `orbis/weight`) заводятся в
`orbis/` заранее, чтобы приложения ссылались, а не дублировали; операция «слить» (Р10); AI-садовник —
рутина, которая замечает похожие свойства и приносит предложение в пачку D42, не молча; отчёт о
сиротах (свойство без роли и без значений) и о `proposed` старше N дней; подсказка похожих при
создании (Р4). Это обратная сторона «одного графа» (05-mission §2) — проектируется с первой версии.

**Р18. Продукт: человек не набирает запросы.** Базовый путь — речь/чат (AI формулирует) и форма
(конструктор уже правит AST — `QueryBuilderForm.tsx:4-5`). Текстовая грамматика — контракт для машин
(LLM, MCP, код, golden-тесты) и опциональный режим для продвинутых; переход форма ↔ текст становится
двусторонним (оба правят один AST). В форме — «опиши словами» → AI предлагает AST. Человек видит
label и description, не id и не key; отсюда Р4 про уникальность label.

**Р19. Локализация.** Label/description per-locale (В4, рынок глобальный, D36); key и id от локали не
зависят; хранение по id делает смену языка бесплатной. Переопределение пользователем label/description
встроенного свойства — запись в его локали поверх системной (тип, key, обязательность — нет).

**Р20. Что переписывается.** `entities.aspects` → `props` + `roles` (механическая развёртка
`aspects->'A'->>'f'` → `props->>'<id>'` в 77 SQL-местах / 15 файлах сервера, 36 местах web; общие
свойства — выбор значения); `aspect_definitions` → реестр свойств + реестр ролей; валидатор; схемы
тулов; wire-проекция; `field-labels.ts` и `BUILTIN_ASPECT_META` → реестр; `DOC_SCHEMA_VERSION`;
PRD 01 §2.1/§3/§4/§6/§7.6/§9.2/§10/§12 и 02-core-os §3.4–§3.5; промпты; ~88 тестовых файлов.
Миграции данных нет — база пересевается (§1).

## 4. Что НЕ решено и уходит в спеку

Политика `proposed`-свойств (кап, кто и когда подтверждает, судьба неподтверждённых); форма
квалификации в грамматике и правила кавычек; `has=` (присутствие поля); значение по умолчанию на
уровне роли; порядок полей в роли и в «Свойствах»; индекс под `backref` (В2 заметки о `ref`);
политика при архивации цели `ref` (В3 там же); `backref/rollup/lookup` (очередь 2); «повышение»
набора свободных свойств в роль; таблица перевода 13 встроенных аспектов; view с проекцией label для
отладки; экспорт со снимком реестра.

## 5. Вопросы владельцу

- **В1. Термин.** «Аспект» — слово во всём PRD, коде, UI и промптах. В модели С это «роль»
  (интерпретация фактов). Оставляем «аспект» как имя роли (меньше правок, но слово означает уже
  другое) или переименовываем — «роль» в модели и, например, «тип записи» для пользователя?
  **Решено владельцем 23.08: оставляем «аспект».** Слово «роль» в этом документе читать как «аспект»;
  в спеке — только «аспект».
- **В2. Теги.** Оставить `tags` как есть — единственный слой без схемы (моя рекомендация), или свести
  к встроенному multi-select свойству `orbis/tags` (одна механика, но теги теряют «бесплатность»)?
  **Решено владельцем 23.08: теги остаются как есть; вернуться позже.**
- **В3. Порядок работ.** Реформа свойств трогает `DOC_SCHEMA_VERSION` и `{{…}}`-семью узлов —
  то же, что спека трансклюзии (ревизия 2, ждёт ваших ответов). Что первым: свойства, трансклюзия,
  или одна спека документа для обоих?
  **Решено владельцем 23.08: свойства первыми, трансклюзия потом.** Связь слабее, чем казалось:
  без пользователей двойное поднятие `DOC_SCHEMA_VERSION` ничего не стоит; трансклюзия ляжет на новую
  модель сущности.
- **В4. Язык встроенных label по умолчанию.** Русский сейчас, локализация по Р19 — сразу в первой
  версии (label per-locale в реестре) или позже (одна строка, перевод потом)?
  **Решено владельцем 23.08: per-locale сразу; key возвращён четвёртым полем как изменяемый слаг**
  (врущий слаг сбивает AI, а менять key дешевле, чем id) — см. Р2/Р3. Снимает С1–С3.

## 6. Мои сомнения (не стали вопросами, но названы)

- **С1–С3 — сняты решением В4** (key как имя параметра; key варианта + label per-locale;
  переопределение label — запись в локали пользователя). Оставлены в истории git.
- **С4. `proposed`-свойства от AI** — самый рискованный по разрастанию словаря элемент; кап и
  садовник обязаны войти в первую версию, иначе Р14 лучше ограничить «только существующими
  свойствами + текст в body».

## 7. Редактирование встроенных аспектов и свойств — ЧЕРНОВИК (23.08, вечер)

Владелец: «дать пользователю максимально гибко настраивать систему под себя и не навязывать своё
видение — только предложить, с возможностью менять/удалять/добавлять». Принято как направление с
оговоркой анти-цели 5: гибкость — возможность, не обязанность; умолчания работают сами, настройка —
словами через AI, конструктор не обязателен. «Не навязывать» = «всё объяснимо и всё заменяемо».

**Факт.** Сегодня встроенные неизменяемы: схемы в коде, реестр — копия, drift-проверка. За частью
словаря стоит код: только на варианты `done/cancelled/expense/income` — 30 мест сервера и 22 файла
сервера+web (чекбокс, Agenda, `excludeBlocked` в `compile.ts:254`, `status ↔ completed_at`, бюджетная
математика, биндинг к конверту, быстрый ввод, импорт, промпты).

**Два сорта встроенного.** Словарь *с контрактом* (`task_status` и его варианты, `due_date`, `start_at`,
`amount`, `direction`, `category_ref`, `currency`, `occurred_on`, `limit`/период, `spend_class`,
`progress_source`) и *просто словарь* (`location`, `timezone`, `effort_min`, `waiting_for`, `unit`…).
Служебные аспекты исполнителя (`agent-run`, `assignment`, `routine`) — механика, настраиваются только
label/description.

**Решения (черновые).**
- **Ч1. Модули.** Встроенные аспекты приходят модулями (Финансы: financial/budget/category; Планировщик:
  task/schedule; Цели: goal; ADE: project/repo/assignment/agent-run/routine; Память: memory — состав в
  спеке). «Удалить встроенный аспект» = выключить модуль: аспекты, экраны, тулы и промпт-фрагменты
  модуля уходят вместе. Рамка совпадает с констелляцией D36 — принято владельцем 23.08.
- **Ч2. Дельты, не правка.** Системное определение неизменяемо и версионировано (из кода); пользовательские
  изменения — дельты в отдельной таблице: label/description/иконка/порядок/скрытие, добавленные к
  встроенному аспекту свойства (жест «+ свойство к задаче» — без аспекта-спутника), добавленные варианты
  enum, ослабленная обязательность там, где код это терпит (явный список). Эффективное определение =
  система ⊕ дельта. Обновление системы при живой дельте — трёхстороннее слияние с отчётом о конфликтах
  (наш новый вариант `review` vs пользовательский `в ревью` → предложение слить), не тихий выбор.
  Типы и key встроенных дельта не меняет (приложения D36 на них стоят).
- **Ч3. Честные зависимости вместо запретов.** У свойства с контрактом — список «кто на нём стоит»
  («статус использует Agenda, чекбокс, блокировки, быстрый ввод»); UI показывает это и предлагает
  доступное: скрыть, добавить вариант, форкнуть. Удаление встроенного свойства = скрыть/deprecate, данные
  остаются; смена типа = форк (своё свойство), никогда in-place.
- **Ч4. Контракты.** Модули зависят не от id свойств, а от **контрактов** (семантических интерфейсов):
  `когда` (момент/дата), `завершаемость` (статус + карта вариантов → сделано/отменено/активно),
  `движение денег` (сумма, направление, категория, дата, валюта, план/факт), `конверт` (лимит, период),
  `прогресс`, `категоризуемость` — список уточняет разведка. Встроенные аспекты — реализации по
  умолчанию; пользовательский аспект может реализовать контракт и попасть в Agenda/бюджет без правок
  кода; добавленный вариант enum пользователь сам относит к значению контракта. Перевод модулей на
  контракты — одновременно с переводом SQL на `props` (одна работа, не две).
  **Контракты — в этой же спеке** (решение владельца 23.08).
- **Ч5. Промпты — из эффективного реестра** (система ⊕ дельта + контракты), рукописные перечни полей
  (v4: «сумма живёт в orbis/financial (amount, direction…)») уходят. D35 «одна декларация — все
  поверхности».
- **Ч6. Операции над словарём — через исполнителя**, с журналом и undo, как правки сущностей.

- **Ч7. Три слоя и двусторонние контракты (24.08–25.08, принято владельцем).** Ответ на вопрос «что можно
  не зашивать в код вообще».

  **Слои.** A — данные (правятся через исполнителя: журнал, дифф Ш1, undo; авторы — модули сидом,
  пользователь, AI): весь словарь и дельты; контракты (слоты + классы значений + именованные наборы
  классов, напр. `closed = [done, cancelled]`); привязки аспектов (`implements`: `bind` слот→свойство +
  `value_map` вариант→класс); роли связей с generic-ограничениями (`target_max_incoming`, `acyclic`,
  контракты концов, `created_by`); правила из каталога ~10 шаблонов (`requires_when`, `forbidden_when`,
  `on_enter_class`, `default`, `unique_among`, `mirror_relation`); декларативные агрегаты поверх
  query-AST (spent, effective_limit, правило валюты — одной строкой вместо 13 копий) и декларации
  материализации повторов (формула id, наследуемые свойства, горизонт); паттерны fast-path; схемы и
  описания тулов, промпт-фрагменты (кроме политики-прозы), сиды; **подписки** (см. ниже). B — ядро,
  код навсегда: интерпретаторы (движок шаблонов правил, вычислитель выражений, компилятор
  запросов/агрегатов, резолвер контрактов, генератор тулов/промпта, рендер-атомы), машинерия
  (хранение, конкурентность, журнал/undo, RLS, транспорт, исполнитель), bootstrap-онтология.
  C — именованный остаток: доменный код модулей, не легший в шаблоны v1 (rollover, дедуп по сходству,
  эскалация…), каждый пункт с записью «почему в коде»; метрика сжатия — 568 мест инвентаря.
  **Дисциплина против inner-platform:** шаблон попадает в каталог только при ≥2 повторах формы;
  выражения — тотальные (без циклов/IO, с бюджетом); каждая декларация — через исполнителя.
  Sandbox-плагины (код как данные) — НЕ идут; негорячий остаток логики — внутреннему исполнителю
  (садовник, эвристики) вместо плагинов. Обоснование North Star: автор деклараций — в основном AI;
  декларацию, в отличие от кода, можно провалидировать, показать диффом, принять пачкой, откатить.

  **Хранение.** Образец один, проверенный на `aspect_definitions`: определение из кода → сид →
  таблица → drift-проверка → RLS «встроенные + свои» → кеш процесса с инвалидацией. Три новые
  таблицы: `property_definitions`, `contract_definitions`, `relation_role_definitions` (роль ребра —
  на самом ребре, `relations.meta.role` или колонка — по замеру). Привязки и правила — НЕ таблицы:
  jsonb-поля в строке владельца (правило не существует без владельца и умирает с ним; отдельная
  таблица дала бы сирот; извне ссылаются только на контракты и роли — им и таблицы). Колонка
  `aggregations` (§4.3 PRD) — зарезервированный клапан, используется по назначению. Модуль — манифест
  в коде (словарь + процедурный остаток + поверхности), включённость — `user_settings`
  (расширение `installedViews`); таблицы модулей нет.

  **Права (v1, если не сказано иное).** Принцип: создавать можно то, у чего есть generic-потребитель;
  править чужое нельзя там, где на определение опирается код модуля. Свойства/аспекты: смотреть,
  создавать — да; встроенные — дельтой (label/description/скрыть/добавить свойства и варианты; тип и
  key — нет). Привязки: создавать свои — да (главный жест: свой аспект реализует встроенный контракт);
  у встроенных аспектов — только дополнять (map добавленных вариантов). Контракты: встроенный —
  **API модуля**, неизменяем (кроме label/description в локали); свои — позже, вместе с
  view-декларациями (раньше это запись без потребителя). Правила: свои из каталога на своих
  свойствах/аспектах — да; правила модулей — смотреть (честные зависимости Ч3), не править;
  «пользователь запер сам себя правилом» лечится честной ошибкой с именем правила и кнопкой
  «отключить», не запретом. Роли связей: `subitem` — всем; свои роли — v1.5 (архитектурно то же,
  вопрос объёма); `created_by: system` рука не создаёт. Обычный путь всего этого — сказать AI
  словами; конструкторы — продвинутый слой (анти-цель 5).

  **Двусторонние контракты: подписки.** У контракта две стороны, и обе — данные: привязка
  (реализация) и **подписка** (потребление). Функция = движок (код: раскладка, сетка, слияние,
  производительность) + подписка (данные: что показывать и когда прятать):
  `{view: agenda, sources: [{show: {contract: when, window: today..+7d}}, {section: overdue,
  hide_when: {contract: completable, class_set: closed}}]}`. Стороны не знают друг о друге — обе
  ссылаются на стабильные id контракта; тренировка попадает в Agenda, потому что обе стороны
  сослались на «когда». В v1 подписками становятся: **Agenda** (три захардкоженных запроса → сид
  Планировщика), **строки списков** (таблица M14 «контракт → элемент», включая порядок совмещения —
  сегодня он различается между NativeRow и EntityRow), **`excludeBlocked`** («блокер снят, когда
  класс ∈ closed»). Обязательное правило: подписки ссылаются на **именованные наборы классов**
  контракта, не перечисляют классы (иначе семь мест `!done&!cancelled` станут семью разъехавшимися
  подписками); явный перечень — осознанное отклонение, видимое в диффе. Следствия: «Agenda гейта не
  имеет намеренно» снимается — движок без подписок честно пуст, выключение модуля уносит его
  подписку; модуль/AI/пользователь добавляют источник в чужой экран подпиской, не трогая движок.
  Свои подписки: v1 — правкой через AI; полный конструктор view — отдельный срез к «карте работ».

- **Ч8. Подписки по всему продукту (25.08, распоряжение владельца: «Agenda была примером — то же для
  остальных частей, Budget в первую очередь»).** Каждая поверхность раскладывается на движок (код) /
  подписку (данные) / именованный остаток C. Подписка ссылается только на контракты и именованные
  наборы — никогда на аспекты и сырые значения.

  **Budget (полный разбор).** Движок: экраны Overview/конверт/категория, прогресс-бары, навигация
  периодов, механизмы биндинга/rollover/план→факт. Подписка (сид модуля Финансы): источник
  `movement = {contract: money-movement, counted_set: facts}` (facts = planned=false ∧
  occurred_on<=$today ∧ не шаблон); конверт `{contract: envelope, binding_role: envelope-binding,
  selector: {match: [finance_category, currency, period], tie_break: [shorter_period, later_start,
  min_id]}}`; агрегаты-декларации поверх query-AST (клапан §4.3): `spent = sum(amount) over movement
  bound via envelope-binding`, `effective_limit = limit + carryover`, `remaining`, `unbudgeted`,
  `daily_pace`; `currency_rule: owner_default_if_absent` (одна строка вместо 13 копий Z2-П3); фазы
  upcoming/active/closed; `alerts.warn_at = 0.85`; дерево категорий `{role: category-parent, rollup:
  same_currency_only}`; rollover `{source: exact_calendar_month, carry: remaining}`. Настраивается
  потребительски: порог тревоги, состав counted_set (вторая линия планов), правило валюты, политика
  rollover; производительски — автоматично (свой аспект с привязкой к money-movement попадает в spent
  без правки Budget). Остаток C: decimal-арифметика (реализация типа), advisory-lock уникальности
  (конкурентность), поток план→факт (политика подтверждений), дедуп-эвристика. Выгода формы: три
  чтения `planned` и 13 копий правила валюты (Z2) невоспроизводимы — набор и правило определены один
  раз, агрегаты ссылаются.

  **Остальные поверхности** (движок / подписка / C): Browser-списки — список и чипы / строка =
  таблица M14 + какие чипы-фильтры (сегодня зашиты status/priority → «фильтры по контрактам») / —;
  Detail — карточка / элементы шапки по контрактам (чекбокс, полоса прогресса) и порядок секций / —;
  чат-карточки — рендер / keyFields → ключевые слоты контрактов / —; fast-path — парсер / паттерны
  M13 и приоритет memory-rules над aliases / сам разбор; импорт CSV — конвейер и ревью / маппинг
  колонок → слоты money-movement, параметры дедупа (±1 день, порог сходства), порядок резолва
  категории / эвристика сходства; Цели — вычислитель / `progress_source` — УЖЕ подписка (образец) / —;
  очередь исполнителя — глаголы и CAS / декларация claimable (роль ticket, класс active,
  executor=agent) — данные с `created_by: system`, пользователь не правит / механика прогонов;
  эскалация/подтверждения — классификатор / позже контракт «чувствительность» / текущая эвристика
  (Z2: переписывается при переходе на props); контекст LLM — сборка слоёв / подписка «память»
  (cap 50, приоритеты), контракты в описании якоря / политика-проза.

  **Хранение подписок:** одна таблица `subscription_definitions` (`surface`, `owner_id` NULL = сид
  модуля, definition jsonb) — тот же цикл сид → drift → дельта пользователя → кеш. Не в
  `user_settings`: подписка — декларация с диффом и undo, не флажок.

- **Ч9. Связи: транзитивный обход и вычисляемое «в каком проекте» (25.08, принято владельцем по
  сценарию «проект → подпроект → задача → подзадача»).** Кодовая база в проблему уже упиралась:
  `orbis/routine.project_id` — ручная денормализация с комментарием «`this` грамматики не достаёт
  внуков» (`aspects.ts:262`). Решения: (1) в грамматику/AST входят `descendants_of=` / `ancestors_of=`
  с уточнением `via=<роль>` — рекурсивный CTE по индексу `(source_id, role)`, кап глубины (~32);
  предикаты `has_children` / `has_relation` — отрицание через булево дерево В12 («терминальная
  задача» = `!has_children via=subitem`); результат — обычные сущности: сортировка/лимит/smart list
  работают как везде. (2) Новый шаблон каталога правил `nearest_ancestor`: вычисляемое свойство по
  графу (истина — рёбра, свойство — кэш по правилу 3 §10, пересчёт затронутого поддерева при правке
  рёбер); заводятся ОБА свойства — `orbis/parent_project` (ближайший проект) и `orbis/root_project`
  (корневой), на общей доске по умолчанию корневое; свойство — обычное: группировка колонками,
  фильтр, индекс, живой заголовок (ref). Ручная денормализация `routine.project_id` заменяется этим
  правилом. Граница С5 пересмотрена: транзитивный обход одной роли — В v1; произвольные графовые
  обходы (пути, смешанные роли, поиск циклов из запроса) — по-прежнему нет.

- **Ч10. Связи: закрывающий пакет (25.08, принят владельцем).** С1 — колонка `relation_type`
  УДАЛЯЕТСЯ: роль — единственная истина ребра (следствие В4б: роль обязательна и несёт базу;
  «все иерархические» компилятор разворачивает из кеша реестра в `role IN (…)`; удаление бесплатно
  по В9). С3 — определение роли несёт именование сторон (`source: «конверт», target: «транзакция»`,
  per-locale) — UI backlinks/карты подписывает направление из реестра (приложение М2/Ч3/D35).
  С4 — типизированных свойств на рёбрах НЕТ (ноль найденных кейсов — ноль механизма, дисциплина Ч7);
  `relations.meta` остаётся системной (зеркало `ref`, undo — В2) и пользователю не открывается.
  С2 — флаг `symmetric` у роли: **named-future**, описывается в спеке, реализуется при втором кейсе
  (сегодня единственный — `mention`, и backlinks уже смотрят в обе стороны). С6 — перед спекой
  свойств выполняется сверка модели ролей со спекой «Карта работ» (черновик 22.08) — процессный шаг
  из порядка В3.

**Ограничения, названные вслух.** Служебные аспекты не настраиваются; дельта не меняет тип/key
встроенного; ослабление обязательности — по месту, с null-толерантностью кода; смена типа — только
форк; контракты — новый слой, требующий переписать чтение модулей; скрытое ≠ удалённое (код и старые
запросы скрытое видят); перекроенный до неузнаваемости аспект модель понимает ровно настолько, насколько
хороши description и контракт.

оценкой заменимости жёсткой связи универсальным настраиваемым механизмом — отдельный файл в
`docs/superpowers/reviews/`.
