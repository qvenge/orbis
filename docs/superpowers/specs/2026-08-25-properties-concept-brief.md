## §1. Зачем: мотивация в три шага

**Шаг 1 — исходная боль.** Механизм аспектов негибок: 13 встроенных аспектов зашиты в код, пользователь не может ни завести своё свойство, ни изменить встроенное, ни добавить вариант статуса. Владелец хочет «максимально гибко настраивать систему под себя и не навязывать своё видение — только предложить, с возможностью менять/удалять/добавлять».

**Шаг 2 — почему это вопрос ядра, а не UI.** Разведка (568 мест в пяти зонах кода) показала: жёсткость сидит не в отсутствии экранов настройки, а в модели данных. Значение существует только внутри аспекта (`aspects['orbis/task'].status`) — у факта нет собственного тождества; смысл («это задача», «это завершено», «это ребро — привязка к конверту») вычисляется кодом из формы данных, а не записан в данных; функции (Agenda, Budget, чекбокс) привязаны к конкретным id аспектов и значениям enum, поэтому пользовательский аспект мёртв для всех функций.

**Шаг 3 — критерий North Star.** «Помогает ли это Orbis брать на себя больше — так, чтобы человек мог спокойно это отдать?» (05-mission §4). Главный автор настроек — не человек, а AI («правая рука»): структура приходит ПОСЛЕ данных (ретро-миграция §3.10 уже признаёт это), AI постоянно предлагает новые типы, свойства, правила. Декларацию — в отличие от кода — можно провалидировать, показать диффом, принять пачкой, откатить undo. Поэтому цель реформы: **перевести из кода в данные всё, что отвечает на вопросы «что существует, что это значит и что должно выполняться», оставив кодом только «чем это исполняется»**. Каждая ступень декларативности расширяет зону безопасной автономии AI.

Рулинги, задающие рамку: пользователей и прод-данных нет (базу можно пересевать; обратная совместимость бесплатна); цена работ не ограничение («надо переделать ядро — переделаем»); гибкость — возможность, не обязанность (анти-цель 5: умолчания работают сами, настройка — словами через AI).

## §2. Сдвиг модели: свойство — факт, аспект — интерпретация («путь С»)

Было: сущность = карта «аспект → объект полей»; JSON Schema аспекта — истина; поле не существует вне аспекта. Станет:

```
сущность = core (title, body, tags) + props {property-id → значение} + aspects [id]
```

- **Свойство** — самостоятельный факт с тождеством: реестр `id` (неизменяем; встроенные — читаемые строки `orbis/task_status`, пользовательские — uuid) + `key` (ASCII-слаг, изменяем без следа в данных) + `label`/`description` (per-locale, свободно) + `type` (закрытый словарь kind'ов). Одно свойство — одно значение на сущности. Суффикс `_ref` упразднён (тип `ref` сам говорит).
- **Аспект** — интерпретация: «что эта сущность есть» — набор ссылок на свойства с обязательностью + ai_instructions + tag_mappings. JSON Schema — генерируемая производная (для валидатора и тулов LLM). Слово «аспект» сохранено (рулинг В1).
- **`meta` удаляется**: извлечённый AI факт — свободное свойство (существующее или `proposed` с капом), а не write-only мешок.
- **Сохранённые запросы — AST по ссылкам (id), текст грамматики — проекция** (парсер принимает key и label, сериализатор печатает key машинам / label людям). Фильтр канонически — булево дерево and/or/not (текст — плоский сахар). Прецедент внутри системы: сущности в body уже адресуются `[[entity:uuid]]`, не заголовком.
- Прецеденты рынка, подтверждающие семантику: Tana (supertags + глобальные поля, одно значение на узел), Anytype, Obsidian; Notion как контрпример (свойство заперто в базе — у Orbis баз нет, сущность мультиаспектна).

## §3. Понятия поверх сдвига

| Понятие | Отвечает на вопрос | Где живёт |
|---|---|---|
| Свойство | «что это за значение?» | таблица `property_definitions` |
| Аспект | «что эта сущность есть?» | `aspect_definitions` (состав меняется); пользовательские дельты поверх встроенных |
| Контракт | «что код умеет с этим делать?» — слоты + классы значений + именованные наборы (`closed = [done, cancelled]`) | таблица `contract_definitions`; встроенный контракт = API модуля, неизменяем |
| Привязка | «чем аспект реализует контракт?» — `bind` (слот→свойство) + `value_map` (вариант→класс) | jsonb-поле `implements` в аспекте; главный пользовательский жест |
| Роль связи | «что значит это ребро?» — с generic-ограничениями (`target_max_incoming`, `acyclic`, контракты концов, `created_by`, именование сторон) | таблица `relation_role_definitions`; на ребре — колонка `role`; `relation_type` УДАЛЯЕТСЯ (роль — единственная истина) |
| Правило | «что должно выполняться?» — каталог ~10 шаблонов (`requires_when`, `on_enter_class`, `default`, `unique_among`, `nearest_ancestor`, агрегаты, материализация…) | jsonb-поля в строке владельца (свойства/аспекта/роли) — НЕ таблица (правило умирает с владельцем) |
| Подписка | «что эта поверхность показывает/считает?» — consumer-сторона контракта | таблица `subscription_definitions`; Budget/Agenda/строки/excludeBlocked — сиды модулей |
| Модуль | «что включено у пользователя?» — словарь + код-остаток + поверхности, вкл/выкл целиком | манифест в коде + `user_settings` |

Ключевая симметрия: у сущности «форма» (props) и «смысл» (аспекты); у ребра «форма» (source/target) и «смысл» (роль); у контракта две стороны — привязка (реализация) и подписка (потребление), обе — данные, друг о друге не знают, ссылаются на стабильную середину.

## §4. Принципы (по ним проверять каждое решение)

1. **Одна истина, остальное — проекции.** Значение — по id; схема, wire, текст запроса, промпт, подписи — генерируются. Переименование ничего не переписывает в данных; слияние — единственная операция реестра, трогающая данные.
2. **Три слоя**: A — данные (правятся через исполнителя: журнал, дифф, undo); B — ядро-интерпретаторы и машинерия (код навсегда); C — именованный остаток кода с записью «почему» (метрика сжатия — 568 мест инвентаря). Sandbox-плагинов нет; негорячий остаток — внутреннему исполнителю (AI-рутины).
3. **Дисциплина против inner-platform**: шаблон/kind попадает в каталог при ≥2 повторах формы; выражения тотальные; ноль кейсов — ноль механизма.
4. **Модули не знают друг о друге**: общее для двоих — контракт ядра; присутствие на чужой поверхности — только подпиской; механизма «модуль требует модуль» нет.
5. **Не навязывать = всё объяснимо и всё заменяемо**: у ограничений — честные зависимости («статус использует Agenda, чекбокс…») вместо серых кнопок; удаление встроенного = скрытие/выключение модуля; смена типа = форк.
6. **Fail-closed и наблюдаемость**: невалидное — незаписываемо (а не «записано и молча мёртво»); каждое изменение реестра — действие исполнителя.
7. **Словарь требует садовника**: разрастание свойств — постоянная функция (namespace'ы, слияние, AI-предложения, отчёт о сиротах) — обратная сторона «одного графа».

## §6. Задание проверяющему: что искать

Ищи **дыры, противоречия и нестыковки** — не пересматривая принятые решения (Р/Ч/В — норматив; находка «решение Х плохое» допустима только как доказанное противоречие другому решению или принципу §4). Классы, по которым пройтись:

1. **Внутренние противоречия**: Р↔Ч↔В-решения, принятые в разные дни, могут конфликтовать (ранние Р писались до Ч7–Ч10; шапки-поправки могли покрыть не всё). Пример класса: квалификация «аспект.поле» из ранних решений против namespaced key из В11.
2. **Неразобранные взаимодействия механизмов**: дельты × локали × подписки; `proposed`-свойства × генерация тулов; слияние свойств × AST сохранённых запросов × undo; выключение модуля × его роли на существующих рёбрах × его контракты в `value_map` пользовательских аспектов; дельта пользователя × обновление системного определения (трёхстороннее слияние) × drift-проверка.
3. **Недоопределённости, где спека упрётся**: у каждого понятия §3 проверь «кто создаёт / кто правит / кто удаляет / что происходит с данными и ссылками при удалении»; жизненный цикл `proposed`; судьба привязок при deprecated-свойстве; порядок children в иерархии (рёбра не упорядочены — а карта работ и подзадачи ждут порядка?); конкурентность правок реестра (LWW? CAS?).
4. **Производительность и конкурентность деклараций**: агрегаты-декларации Budget на каждом чтении Overview; пересчёт `nearest_ancestor` при перевешивании большого поддерева; кеш эффективного реестра и его инвалидация при дельтах; RLS на новых таблицах.
5. **Безопасность и полномочия**: может ли act-рутина (автономный AI) править реестр — и что её ограничивает; `created_by: system` — где проверяется; подписка как вектор «тихо перенастроить, что видит владелец» (анти-цель 3).
6. **AI-поверхность**: генерация промпта из реестра при сотнях пользовательских свойств (бюджет токенов); `attach_*` для аспекта с привязками — как модель узнаёт классы контрактов; `entity_query` с AST — как модель строит булево дерево.
7. **Согласованность с PRD**: какие параграфы 00–03 становятся ложью и не названы в Р20; инварианты §13 PRD 01 — что с ними.
8. **Пропущенное**: чего в документах НЕТ вовсе, а спека без этого не пишется (мой известный список: экран/UX реестра для человека; ошибки валидации привязок; версия/миграция самих деклараций подписок; экспорт при per-locale). Найди своё.

Формат находок: таблица «№ | документ:место | класс (противоречие / взаимодействие / недоопределённость / производительность / безопасность / PRD / пропуск) | суть | предложение», отсортированная по важности; отдельно — вердикт «готовы ли заметки быть входом спеки и что обязательно закрыть до неё».
