## 1. Словарь

| Термин | Значение |
|---|---|
| **Ядро** | слои 1–3 и 7: граф, словарь, действия с конвейером, журналом и Undo, агент, доступ и разрешения; открыто клиентам одним API |
| **Клиент** | программа, показывающая ядро пользователю; два вида — декларативный и нативный |
| **Декларативный клиент** | слои 4–6: блоки, страницы, шаблоны, оболочки, рамка, песочница компонентов; в нём и живёт механизм страниц |

| **Запись** | узел графа |
| **Аспект** | интерпретация записи («это задача»); у аспекта есть **карточка аспекта**; шаблоны сами объявляют, для каких аспектов подходят (§5.3) |

| **Расширение** | единица функций **без своего места**: манифест, словарь, действия, свои карточки аспектов, страницы, рутины, инструкции агенту; включается и выключается целиком (§3.3) |
| **Приложение** | **место**: оболочка + состав (ссылки на расширения) + свои страницы и шаблоны; приносит поставка или собирает владелец (§3.3) |

| **Страница** | запись с аспектом «страница»; открывается своим телом |
| **Тело** | документ записи: дерево узлов из текста и блоков |
| **Блок** | узел тела: подписка + форма показа + настройки; данных не содержит |
| **Контейнер** | блок, содержащий блоки: колонки, вкладки |
| **Вкладки** | контейнер в теле; переключают содержимое внутри одной открытой страницы |
| **Примитив** | блок из стандартной библиотеки хоста |
| **Компонент** | блок, который приносит расширение: ярус 1 — композиция примитивов декларацией; ярус 2 — код в песочнице |
| **Карточка аспекта** | блок, показывающий данные аспекта на записи: по умолчанию собран из реестра, расширение-хозяин аспекта может принести свою |
| **Шаблон** | страница с параметром `this` (запись), объявляющая набор аспектов, для которых подходит; принадлежит приложению — своему дому |
| **Параметр** | ручка страницы, меняющая показ, но не граф; типизирован (первый тип — «период»); текущее значение — состояние экрана в истории |
| **Оболочка** | запись-приложение, описание места: имя, иконка, домашняя, навигация, форма навигации, состав |
| **Раздел** | пункт навигации приложения: ссылка на запись; у раздела своя стопка экранов |
| **Навигация** | упорядоченный список разделов в оболочке; сверху, на десктопе — сайдбаром; **никогда не внизу экрана** |
| **Форма навигации** | как показаны разделы: «список из заголовка», «домашняя как центр»; другие формы — по нужде; выбирает приложение из закрытого набора хоста |
| **Рамка** | то, что хост рисует вокруг содержимого: присутствие хоста, шапка (необязательна), навигация |
| **Шапка** | необязательный элемент рамки с именем экрана |
| **Присутствие хоста** | доверенное хоста поверх любого содержимого: вверху «‹ ⌂ ⋯», внизу справа — кнопки хоста, на десктопе — рейка; доверенные плашки |
| **Кнопки хоста** | группа [поиск \| чат \| новая запись] внизу справа на всех экранах |
| **Тулбар** | группа плавающих кнопок действий приложения внизу слева (место решено, сам тулбар — отложен, §11) |
| **Дом** | приложение, в рамке которого открывается страница; свойство страницы; пусто — хост |
| **Адрес** | приложение + запись (+ параметры — позже); страница — тоже запись |
| **История** | одна модель: приложение → разделы → у раздела своя стопка экранов; два поведения — «как приложение» и «как сайт» (§6.5) |
| **Эталон** | версия записи поставки (страницы, шаблона, оболочки), которую приносит поставка: ключ, отпечаток, текст |
| **Запись поставки** | запись владельца, которую поставка создаёт при заведении графа; несёт эталон; обновления приходят предложениями (§5.5) |
| **Действие** | именованный рецепт из реестра; конвейер мутаций, подтверждение по риску, журнал, Undo |
| **Рутина** | действие агента во времени |
| **Адрес слота** | обращение в запросе к слоту контракта: значения свойств, которые к нему привязали аспекты записи (§3.5) |
| **Значение контракта** | то, что контракт объявил своим значением из своих слотов; даёт адрес «контракт целиком» — у «когда» это даты записи (§3.5) |
| **Токен даты** | относительный день или период в запросе («сегодня», «7 дней», «этот месяц»); абсолютных дат на страницах нет |
| **Группировка** | показ строк блока данных группами по ключу; первый ключ — день |

Понятия, которых в концепции **нет**: view, модуль, FAB, уровень, пространство, режим, секция, главный аспект, размещение
(→ раздел). «Панель» — не термин: слово можно использовать по необходимости и осмысленно.

## 2. Суть в пяти фразах

1. **Модель работает в момент авторства, рендер детерминированный.** Агент собирает страницу один раз по просьбе; результат хранится версионируемым артефактом (не кэшем); дальше рисуется без модели. Сборка — платно (D36), рендер и ручная правка — бесплатно.
2. **Страница — запись с аспектом «страница»; её схема — её тело.** Второго формата схем нет; текст — каноническая форма.
3. **Функции приносят расширения, место — приложения.** Расширение включается и выключается целиком; приложение — оболочка и свои страницы над составом расширений. «View» и «модуль» растворяются в этой паре.
4. **П0: у наших расширений и приложений нет особых возможностей.** Хост и остальные различаются только доверием, никогда — API. Проверка: «может ли пользовательское приложение целиком заменить наш Бюджет?» — обязано быть «да».
5. **Механизм страниц — декларативный клиент над ядром, не единственный.** Нативный клиент со своей логикой интерфейса ходит в то же ядро тем же API; данные едины.

## 3. Ядро, клиенты, семь слоёв, расширение и приложение

### 3.0 Ядро и клиенты

Механизм страниц, шаблонов и оболочек — не единственный способ показать граф. Граница
проходит по семи слоям (§3.1): **ядро** — слои 1–3 и 7, **декларативный клиент** — слои
4–6. Хост в поставке — ядро плюс декларативный клиент. Рядом может стоять **нативный
клиент**: приложение на своём коде с интерфейсом, заточенным под предметную область и
работающим по своей логике («Orbis Питание» для iOS со сканированием еды камерой,
виджетами и HealthKit), которому ни страницы, ни шаблоны не нужны.

```
┌──────────────────────────────┐   ┌──────────────────────────────┐
│ Декларативный клиент         │   │ Нативный клиент              │
│ слои 4–6: блоки, страницы,   │   │ свой код, свой UX,           │
│ шаблоны, оболочка, рамка     │   │ своя логика интерфейса       │
└──────────────┬───────────────┘   └──────────────┬───────────────┘
               │        один и тот же API         │
┌──────────────┴──────────────────────────────────┴───────────────┐
│ Ядро: 1 граф · 2 словарь · 3 действия · 7 агент · доступ        │
└─────────────────────────────────────────────────────────────────┘
```

**Правило разделения: ядро хранит и решает, клиент показывает.**

| В ядре | В клиенте |
|---|---|
| Записи, включая тела страниц и записи-приложения как данные | Рендер тела в экран, рамка |
| Словарь: аспекты, свойства, контракты | Карточка аспекта, форма по типу свойства |
| Подписки и запросы как декларации, канон запросов (включая язык контрактов), компиляция на сервере | Форма показа: список, таблица, кольцо, лента по дням |
| Действия, конвейер, классификация риска, журнал, Undo | Плашка подтверждения как рисунок |
| Манифест и разрешения, маска включённых расширений, проверка на сервере | Экран установки, плашка «выключено» |
| Агент, авторство страниц, рутины | Показ предложения диффом |
| Адреса как идентификаторы мест; правило открытия — чистая функция над данными | Сопоставление адреса своим экранам |
| **Контракт каталога блоков**: имена, схемы свойств, привязки к данным | **Реализации** блоков под свою платформу |

Последняя строка — точная формулировка шва «одна декларация — все поверхности»: тело
страницы — данные в графе, грамматика блоков — спецификация ядра, а рисует блоки каждый
клиент своими примитивами (веб — веб-компонентами, нативный при желании — нативными
виджетами, как рендереры A2UI). Нативный клиент вправе не реализовывать каталог вовсе —
тогда пользовательские страницы для него просто документы. Компоненты яруса 2 — веб-код по
природе: нативный клиент их не исполняет и показывает плашку.

Следствия: **данные едины** — приём пищи, записанный в нативном клиенте, тут же виден
кольцом на «Утре» в декларативном; **нативный клиент — грант**: доступ как у внешнего
субъекта с разрешениями, тем же механизмом, что гранты внешних агентов (D34), проверяет
ядро; **расширение делится по той же границе** (§3.3); **П0 расширяется на клиентов**
(§3.4).

### 3.1 Семь слоёв системы

```
┌───────────────────────────────────────────────────────────────┐
│ 7. Агент (хост): чат, рутины, память, исполнитель               │  пишет страницы,
│    расширение приносит сюда рутины и инструкции аспектов        │  зовёт действия
├───────────────────────────────────────────────────────────────┤
│ 6. Оболочка: запись-приложение — домашняя, навигация, состав    │  ГДЕ показать
├───────────────────────────────────────────────────────────────┤
│ 5. Страницы: записи с аспектом «страница», тело = текст + блоки │  композиция
├───────────────────────────────────────────────────────────────┤
│ 4. Блоки: примитивы хоста + компоненты расширений; каталог общий│  КАК показать
├───────────────────────────────────────────────────────────────┤
│ 3. Действия: именованные рецепты, конвейер, журнал, Undo        │  ЧТО можно сделать
├───────────────────────────────────────────────────────────────┤
│ 2. Словарь: свойства, аспекты, роли связей, контракты, привязки │  ЧТО значат данные
├───────────────────────────────────────────────────────────────┤
│ 1. Граф: записи и связи (страницы и приложения тоже записи)     │  данные
└───────────────────────────────────────────────────────────────┘
```

Это слои **системы**, не расширения. Хост держит все семь и рантайм. Расширение приносит
строки в слои 2–5 и 7 по одному контракту; приложение — место в слое 6 и свои страницы;
агент как таковой принадлежит хосту, расширение приносит в седьмой слой только свои рутины
и инструкции своих аспектов.

### 3.2 Хост — только то, что обязано быть доверенным

- Граф, реестры, канон запросов, RLS.
- Агент: чат, рутины, память, исполнитель; журнал, Undo, классификатор; **доверенный UI**:
  плашки подтверждений, экран установки расширения, присутствие хоста в рамке.
- **Стандартная библиотека примитивов** (первый состав — спека 1а §7): список, таблица,
  плитка, кольцо, график, календарная сетка, прогресс, контролы форм, контейнеры; **блоки
  обвязки записи**: заголовок, теги, карточки аспектов, подзадачи, обратные ссылки, тред.
- Рантайм: рендер страниц и рамок, песочница компонентов, переключатель приложений,
  глобальный поиск, настройки аккаунта, marketplace.
- Две гарантии сверх рамки: **базовый вид записи** (заголовок, тело, карточки аспектов —
  не шаблон, а последний резерв, если шаблоны испорчены) и **лимит глубины встраивания**.

**Словарь ядра — только понятия, на которых стоят механизмы ядра**: заметка, задача,
расписание, исполнитель и прогон, рутина, память, страница, приложение, поставка;
**стандартные свойства** «сумма», «валюта», «направление», «дата» — исключение, чтобы любая
реализация «движения денег» пользовалась ими без Финансов. Проверка «ядро или расширение»:
ядро — если без понятия не работает механизм хоста; расширение — если кусок самодостаточен
и его выключение не вредит остальному.

**Хост — приложение не из маркетплейса.** Его страницы — записи поставки: «Домой»,
«Записи» (обзор записей одним блоком), **Повестка** — «всё, что во времени» по дням над
контрактом «когда», собранная из обычных блоков (§3.5), страницы-горизонты, шаблон хоста.
Всё остальное — расширения и приложения, включая наш Бюджет и Питание.

### 3.3 Расширение и приложение

Функции и место — две разные единицы (решение владельца 26.09).

**Расширение — функции без своего места:**

| # | Элемент | Что это | Пример (Питание) |
|---|---|---|---|
| 1 | **Манифест** | идентичность (имя, иконка) + разрешения: какие контракты читает, какие действия зовёт, нужна ли сеть до своего сервера, размер бандла | читает «когда»; зовёт «записать приём пищи»; сети нет |
| 2 | **Словарь** | свойства, аспекты, привязки `implements` к контрактам | аспект «приём пищи», свойство «калории»; «приём пищи implements „когда"» |
| 3 | **Действия** | именованные рецепты над `this` или без него | «записать приём пищи», «повторить вчерашний завтрак» |
| 4 | **Компоненты** | ярус 1 — композиция примитивов декларацией; ярус 2 — код в песочнице; пространство имён расширения, версия = версия расширения; **экспорт в общий каталог**; сюда же **свои карточки аспектов** с рангом | «питание/кольцо» = примитив «кольцо» + подписка «сумма калорий за сегодня» |
| 5 | **Страницы** | записи с аспектом «страница» | «Статистика» |
| 6 | **Рутины и инструкции** | рутины расширения, `ai_instructions` его аспектов | «недельный отчёт» пишет блок в «Статистику» |

**Приложение — место:**

| Элемент | Что это | Пример (Питание) |
|---|---|---|
| **Оболочка** | запись-приложение: имя, иконка, домашняя, навигация (разделы), форма навигации | домашняя «Сегодня», разделы «Дневник», «Продукты», «Статистика» |
| **Состав** | ссылки на расширения, которые приложение предлагает включать и выключать вместе с собой; маску само не меняет | расширение «Питание» |
| **Свои страницы и шаблоны** | страницы с домом — это приложение; шаблоны его аспектов | шаблон «приёма пищи» |

**Карточку приносит расширение, шаблон — приложение**: внутри приложения запись
показывается его шаблонами, дизайн согласован; содержимое из графа одно, раскладка — своя у
каждого приложения. Манифест, словарь, действия и рутины принадлежат ядру и общие для всех
клиентов; компоненты, страницы и оболочка — декларативному клиенту. Нативный клиент — не
новый элемент, а отдельный артефакт над ядровыми элементами расширения.

**Выключение расширения** — целиком: агент его не видит (ни тулов, ни фрагментов промпта,
ни строк индекса, ни свойств в каталоге); новых записей и аспектов нет; действия, движки и
его рутины стоят; правила его аспектов продолжают держать целостность; поля его свойств —
только чтение для всех акторов; карточка и блоки — плашкой «выключено — [включить]», никогда
пустотой; **язык (контракты, роли, стандартные свойства) работает**. Включение возвращает
всё. **Выключение приложения** — действие владельца: гаснет место, а расширения его состава,
которых нет в составе других включённых приложений, выключаются по галочкам диалога.
Включать и выключать расширения может только владелец.

### 3.4 П0 — у наших расширений и приложений нет особых возможностей

Любая возможность, которой пользуется наше расширение или приложение, доступна
пользовательскому через тот же контракт. Различие только в доверии: подпись, проверка,
предустановка.

1. Граница хост/остальное — список §3.2; всё, что не в нём, — расширения и приложения.
2. Наши расширения объявляют манифест с первого дня и идут через тот же конвейер действий,
   журнал и подтверждения.
3. Наши компоненты — ярус 1 по умолчанию; «особенное» — либо примитив хоста, доступный всем,
   либо ярус 2. **Прочтение строгое (В1, 2026-09-13): наш код яруса 2 исполняется в той же
   песочнице, что чужой.** Это заставляет сделать песочницу и библиотеку примитивов хорошими.
4. Пользовательское приложение вправе принести свои шаблоны для аспектов Финансов; в споре
   мест побеждает выбор владельца (§6.2) — так оно и заменяет наш Бюджет целиком.
5. **П0 действует и для клиентов** (2026-09-13): у нашего декларативного клиента нет особых
   возможностей — он ходит в ядро тем же API, что нативный клиент любого разработчика; у
   нашего нативного клиента тоже. Разница снова только в доверии.
6. **Временная особая возможность допустима, только если сразу записан адрес её снятия**
   (решение владельца 24.09): реестры временных отступлений ведут спеки срезов.

### 3.5 Язык между расширениями: контракт — отдельная единица

**Контракт не принадлежит ни одному расширению и не выключается вместе с ним.** Дублирование
между расширениями закрывают три механизма: аспекты разных расширений реализуют один
контракт; две вещи одной записи — два аспекта на ней; одинаковая величина — одно свойство
(поиск по каталогу до создания, слияние свойств). Чужой аспект или свойство расширение
напрямую не использует — только через контракт; исключение — стандартные свойства ядра. Тем
же правилам следуют **роли связей** и **глаголы контракта**. Публикация контракта как
единицы — маркетплейс.

**Язык контрактов в запросах** (срез 1в). Блок, агент и рутина спрашивают граф не только
по свойствам, но и по контрактам:

- **адрес слота** — «значения свойств, которые привязали к слоту аспекты записи»: `срок`
  контракта «когда», `сумма` контракта «движение денег» — из любого расширения и из
  собственных аспектов владельца;
- **значение контракта** — контракт вправе объявить своё значение из слотов и адресоваться
  целиком; «когда» объявляет **даты записи**: у сделанного — время закрытия; у закрытого без
  него — дат нет; иначе момент и срок. «У сделанного время — когда сделано».

Поэтому всё, что реализует «когда», появляется в Повестке и в любой странице с таким
запросом само, без правки страницы: «Питание объявило привязку — обеды стоят в дне рядом с
задачами». Условия, кванторы и края периодов — норматив спеки 1в §3 и спеки реформы.

### 3.6 Система сама не пишет

**Ни в граф, ни в журнал система сама не пишет** (решение владельца 24.09). Любое изменение
данных — действие владельца или агента под его правилами; обновления поставки приходят
только предложениями; разовые переводы данных — в прод-процедуре с явным словом владельца.
Следствия правил самого владельца — материализация заведённого им повтора, проводка плановых
платежей по сроку — это действие по его правилу, как у рутины, а не «система сама». Пока
других пользователей нет, изменения поставки в графе владельца вносятся прод-процедурой
сразу, без предложений и без видимого шума (решение владельца 27.09).

### 3.7 Версии единиц — черновик, который только открывает обсуждение

**Не решение** (решение владельца 26.09: записать, чтобы не потерять ход мысли; вернуться при
маркетплейсе). В одном графе стоит одна версия расширения; ссылки на единицы — линия и
минимум («Питание 1.x, не ниже 1.2»), точная версия — у эталона записи поставки и в журнале;
совместимые правки (новый необязательный слот, новое свойство, новая страница) ставятся сами,
несовместимые — с согласием и переездом данных через конвейер действий; записи поставки —
только предложениями. До маркетплейса есть только эталон записи поставки с отпечатком. Полный
черновик — приложение Б спеки 1б.

## 4. Страница

### 4.1 Определение

Страница — запись с аспектом «страница». По хранению от заметки не отличается, и это
намеренно: «это задача», «это расход», «это страница». Аспект добавляет:

- **дом** — свойство страницы: приложение, в рамке которого она открывается; пусто — хост;
  бездомная страница, поставленная домашней или разделом приложения, получает его домом
  («первое место задаёт дом»);
- **параметры** (§4.4) и, если есть `this`, роль **шаблона** (§5.3);
- **показ своим телом** — без обвязки записи; «открыть как запись» в
  меню «⋯» показывает ту же запись через шаблон хоста: версии, тред, обратные ссылки;
- **эталон** — у записей поставки (§5.5).

Где страница стоит разделом — видно обратными ссылками (навигация хранится у приложения,
§5.4). Аспекты складываются: конкретный проект может сам быть страницей, если его телу
навесили аспект «страница»; тогда его тело побеждает шаблон. Снял аспект — снова запись.

### 4.2 Тело: текст и блоки — соседи

Дерево узлов, где текст и блоки на равных правах (модель Notion): заголовок, абзац,
список, виджет запроса, плитка, форма, контейнер колонок с абзацами и виджетами внутри.
Дашборд — документ с малым числом абзацев; заметка — с малым числом виджетов.

**Схема = тело.** Агент пишет страницу текстом с грамматикой блоков, как любую заметку;
второго формата нет. Текст — каноническая форма: легко генерировать, проверять, показывать
диффом с правкой до принятия (Ш1), править руками. Контейнеры — блочный синтаксис с
открывающим и закрывающим маркером, глубина вложенности ≤ 2. Вкладки — контейнер в теле,
и только там.

```
# Утро
Сначала важное, потом деньги.
{{columns}}
  {{col}} {{query: задачи, срок=сегодня, не сделано, сортировка=приоритет}}
  {{col}} {{tile: конверт «Еда», остаток за неделю}}
{{/columns}}
{{query: заметки, связаны с this=проект «Переезд», последние 3}}
```

Требования к телу: блок хранит запрос, не данные; относительные токены дат, никогда
абсолютные; страница компилируется в одну пачку запросов.

### 4.3 Состав: пять слоёв страницы

| Слой | Суть | Пример просьбы | Статус |
|---|---|---|---|
| 1. Композиция блоков | окна в граф + раскладка; только чтение | «утренняя страница: задачи на сегодня, остаток конверта, три заметки по проекту» | принято |
| 2. Параметры и шаблоны | ручки, не меняющие граф; страница «для записи» с `this` | «страница расходов с выбором месяца»; «у каждого проекта своя страница» | принято |
| 3. Формы и действия | страница пишет в граф только действиями по имени: кнопки в блоках, формы | «форма: сумма, категория, кнопка „записать расход"» | принято |
| 4. Оболочка | место: домашняя, навигация, форма навигации, состав | «сделай „Утро" домашней, Бюджет убери из навигации» | принято, как оболочка приложения |
| 5. Логика | закрытый набор (§4.5) | «блок „Просрочено" только если есть просроченные» | принято (В2) |

### 4.4 Параметры

Параметр — ручка страницы, меняющая показ и не трогающая граф. Тип определяет контрол:
период даёт выбор периода или месяца, запись даёт пикер с фильтром по аспекту, выбор из
списка даёт переключатель. Есть значение по умолчанию. Блоки ссылаются на параметр по
имени: «расходы за $период». В теле хранятся имя, тип, варианты и умолчание; **текущее
значение — состояние экрана в истории**, в тело не пишется.

**Первый тип — «период»** (срез 1в): блок-объявление в теле рисует переключатель на своём
месте, варианты — токены дат («7 дней | 14 дней» у Повестки); все блоки со ссылкой
пересчитываются одной пачкой, подстановку делает ядро. Значение пока **не входит в адрес**:
«поделиться» даёт страницу с умолчанием. Следующие шаги с первым потребителем — Бюджет:
значение в адресе и готовое значение у раздела («Расходы: прошлый месяц»), типы «запись»,
«переключатель», «месяц ◀ ▶» (путь по осям — спека 1в §14).

Пример: страница «Расходы за месяц», параметр «месяц» (период, по умолчанию текущий), три
блока с «$месяц»; переключил месяц — все три пересчитались.

Особый параметр — `this`: «запись, о которой эта страница». Страница со `this` — шаблон
(§5.3). В шаблоне могут быть и обычные параметры сверх `this`.

### 4.5 Логика: закрытый набор

Правило: **страница показывает, блок считает, рутина реагирует.** В теле допустимы ровно
три конструкции.

- **Скрыть при пустом результате** — флаг на блоке; булев, над собственными данными блока.
- **Порог на блоке** — плитка, кольцо, прогресс принимают пороги как настройку («предупреждение
  при 80 %»); смысл порога знает сам блок.
- **Агрегаты канона** — плитка = агрегат над запросом; считает канон запросов.

Не допускаются: произвольные выражения, сравнения полей, ссылки блока на блок, вычисляемые
колонки. Выходы за пределы набора: новый блок расширения («дневной лимит» считает внутри
себя); расширение канона новым агрегатом (дорога хоста); рутина («если потрачено больше
80 % — напомни» — реакция во времени, не условие страницы). Многие «если» закрываются
параметрами без логики («показывать сделанные» — переключатель, привязанный к фильтру).
Параметр, группировка и язык контрактов (срез 1в) за набор не выходят: это ручки показа и
адреса данных, не условия.

### 4.6 Страница и запись на экране

Разница только в том, через что рисуется содержимое. **Запись без аспекта «страница» всегда
показывается через шаблон**; обвязка записи — заголовок, теги, карточки аспектов, подзадачи,
обратные ссылки, тред — это блоки стандартной библиотеки, а экран записи по умолчанию —
шаблон хоста. Страница показывается своим телом.

Открыта страница «Сегодня» (телефон, Питание):

```
┌──────────────────────────────┐
│ ‹  Сегодня            ⌂  ⋯   │  присутствие хоста: «‹», «⌂», «⋯»; шапка необязательна
├──────────────────────────────┤
│  ◯ 1 240 / 2 000 ккал        │  тело: блок «кольцо»
│  Белки ▓▓▓░  Жиры ▓▓░░       │  блок «полоски макросов»
│  Завтрак   овсянка     350   │  блок запроса: приёмы пищи сегодня
│  Обед      суп         420   │
│  [ Записать приём пищи ]     │  кнопка действия — блок в теле
│                  [🔍][💬][＋] │  кнопки хоста
└──────────────────────────────┘
```

Открыта запись «Переезд» через шаблон Проектов:

```
┌──────────────────────────────┐
│ ‹  Проект             ⌂  ⋯   │
├──────────────────────────────┤
│ Переезд                      │  блок «заголовок» — шаблон его включил
│ #дом #2026                   │  блок «теги»
│ Срок 30.09 · Бюджет 120 000  │  карточка аспекта «проект»
│ Задачи │ Доска │ Бюджет      │  вкладки — контейнер в теле шаблона
│ ☐ Заказать грузчиков         │
│ ☐ Собрать коробки            │
│ Запись │ Тред                │  тоже вкладки в теле
└──────────────────────────────┘
```

Открыта заметка через шаблон хоста:

```
┌──────────────────────────────┐
│ ‹  Запись             ⌂  ⋯   │
├──────────────────────────────┤
│ Идеи для отпуска             │  заголовок, редактируемый
│ #отпуск                      │  теги
│ Текст заметки…               │  тело
│ Аспекты: +                   │  карточки аспектов
│ Обратные ссылки (2)          │
└──────────────────────────────┘
```

Второй и третий экран различаются только шаблоном; первый — тем, что содержимое есть
собственное тело страницы. Режим настройки страницы — тот же редактор, что у тела записи,
плюс лист свойств аспекта «страница»: параметры, дом. Два глагола правки обязаны
различаться на экране: «изменить для всех проектов» правит шаблон (с баннером «вы правите
шаблон»), «изменить только эту» создаёт собственную страницу записи.

## 5. Блок, карточка аспекта, шаблон, навигация, оболочка, рамка

### 5.1 Блок

Блок = подписка (запрос или подписка на контракт) + форма показа + настройки. **Блок никогда
не содержит данных.** Подписчик — блок, не «поверхность»; страница — контейнер подписчиков.
Блок привязан к **контракту** («когда», «движение денег»), а не к аспекту: лента по дням
показывает обеды рядом с задачами, как только Питание объявило привязку (язык контрактов в
запросах, §3.5). Блоки всех включённых расширений образуют **один каталог**; стиль — токены
дизайн-системы хоста, акцент приложения красит только рамку. Форма показа (таблица, доска,
календарь, лента по дням над одним запросом) — свойство блока. Блок — та же вещь на любой
поверхности: на странице, карточкой в чате, в уведомлении (В8; детали — §12).

### 5.2 Карточка аспекта

Блок, показывающий данные аспекта на записи: по умолчанию собран из реестра автоматически
(поля по типам свойств, правка на месте, «снять аспект»); **расширение-хозяин аспекта
приносит свою карточку** с рангом (порядок среди своих карточек), например вкладки «Подзадачи
| Доска | Бюджет» у проекта. Экспортируется в каталог: чужой шаблон может поставить
`{{card: расход}}` у себя. Выключено расширение — его карточка плашкой, поля только чтение.

### 5.3 Шаблон

Страница с параметром `this`, объявляющая **набор аспектов**, для которых подходит:
«задача», «проект», «проект + задача». Один шаблон — сто рендеров. В теле шаблона особые
блоки: `{{card: X}}` — карточка конкретного аспекта, если он есть у записи, иначе ничего;
`{{cards: own}}` — свои карточки аспектов записи в порядке рангов; `{{cards}}` — карточки всех
остальных аспектов, которые шаблон не разместил сам. **Гарантия хоста: карточка аспекта, не
размещённая шаблоном, дописывается в конец экрана** — ни один аспект не бывает невидимым.
Шаблон хоста не называет расширений.

Пример шаблона «задача» из Проектов, покрывающий и «проект + задача»:

```
{{title}} {{tags}}
{{card: задача}}      срок, приоритет, блокировки
{{card: проект}}      вкладки «Подзадачи | Доска | Бюджет» — только если запись ещё и проект
{{cards}}             расход, заметка, что угодно от других расширений
{{backlinks}}
```

**Шаблона по умолчанию у аспекта нет** (ревизия 3): шаблон сам объявляет набор аспектов, для
которых подходит, и работает, как только набор задан. Где выбор между подходящими упирается в
ничью, решает владелец, и его выбор запоминается **для спора**, а не для записи (свойство
шаблона-победителя «главнее, чем»). Хранимого «главного аспекта» у записи **нет** — понятие
отвергнуто как скрытое состояние; выбор, запомненный на самой записи, отвергнут по той же
причине.

**Шаблоны принадлежат приложениям** (решение владельца 26.09): дом шаблона — его приложение.
**Выбор шаблона внутри места**: подходящие — шаблоны этого приложения, чей набор аспектов ⊆
аспекты записи; побеждает самый большой набор; ничья — запомненный выбор владельца, а если его
нет — показ детерминированно и вопрос; **шаблон хоста — запасной, только если подходящих нет**.
В каком месте открывать запись — правило открытия (§6.2).

Замечание к моделированию (уровень расширения, не концепции): если большинство записей несут
и «проект», и «задачу», это сигнал, что они — один аспект с иерархией, как в Linear и Jira.
Концепция работает в обоих вариантах.

### 5.4 Навигация и разделы

**Навигация хранится у приложения** (решение владельца 26.09; прежнее «размещение хранится у
страницы» перерешено): упорядоченный список **разделов** — ссылок на записи; порядок — забота
приложения, дом — явное свойство страницы. Агент меняет навигацию обычной правкой
записи-приложения. Страница одна, разделом может стоять в нескольких приложениях; в чужом —
ярлыком «↗ Дом». У раздела своя стопка экранов и видно, где вы остановились («Категории ·
Еда»). **Бейдж раздела** — число из первого блока данных его страницы; порядок блоков
определяет, что считает бейдж (у Повестки — просроченное).

**Форма навигации** — выбор приложения из закрытого набора хоста: «список из заголовка»
(разделы раскрываются сверху из заголовка), «домашняя как центр» (разделы — плитки на
домашней); «выдвижной список» и «вкладки сверху» — по нужде. На десктопе любая форма —
сайдбар. **Внизу экрана навигации нет ни в одной форме**: низ отдан действиям, а переходы
между разделами одной страницы — вкладки в теле.

### 5.5 Оболочка и записи поставки

Оболочка — **запись-приложение**: имя, иконка, домашняя, навигация, форма навигации, состав,
«открывать вместо» (запомненный выбор места в споре, §6.2), «выключено». Экрана записи в
оболочке нет — запись показывается шаблонами приложения (§5.3).

**Всё, что приносит поставка хоста, — записи владельца с эталоном**, созданные при заведении
графа: шаблон хоста, оболочка хоста, «Домой», «Записи», страницы-горизонты, Повестка. Агент
их правит по просьбе владельца, как любые записи. **Релизы записи поставки не трогают**: новый
эталон приходит предложением — [сравнить] [принять — прежняя версия сохранится] [оставить
своё]; новая запись поставки в существующем графе — тоже предложением; «вернуть как было» —
действие владельца. Пока других пользователей нет — прод-процедурой сразу (§3.6). Владелец
собирает **своё приложение** из своих страниц — запись-приложение без эталона.

### 5.6 Рамка: «Orbis как ОС телефона»

Оболочка у каждого приложения своя; **форму навигации приложение выбирает само**; присутствие
хоста рисует хост одинаково для всех, и приложение не может его спрятать или перекрыть —
иначе оно могло бы «запереть» пользователя.

**Правило зон** (решение владельца 25.09): **сверху — куда идти** (присутствие хоста «‹ ⌂ ⋯»,
навигация приложения); **снизу — частые дела** (кнопки хоста справа: поиск, чат, новая
запись; тулбар приложения слева — §11). Нижней навигации нет: у нижних вкладок не больше пяти
мест, а одно место не должно значить то «перейти», то «сделать».

- **Телефон:** вверху «‹» (если есть куда вернуться) и «⌂ ⋯»; навигация приложения — сверху в
  его форме; внизу справа — кнопки хоста на всех экранах.
- **Десктоп:** слева тёмная рейка хоста «куда» (⌂, иконки приложений, настройки), дальше —
  сайдбар навигации текущего приложения; внизу справа — те же кнопки хоста; чат — боковой.
- **Доверие:** кнопки хоста — тёмные сплошные; кнопки приложения — светлые с подписями.
  Приложение не может нарисовать кнопку в стиле хоста и подделать «спросить агента».
- **Шапка необязательна** (В7): приложение включает по умолчанию, страница вправе убрать
  (тренировка идёт, сканирование чека, дашборд на стене); присутствие хоста от шапки не
  зависит. **Меню «⋯» одно** — «этот экран» и «хост» (все приложения, приложения и
  расширения, настройки).
- **Гарантии рамки:** присутствие хоста и кнопки рисуются всегда; испорченная оболочка хоста —
  рамка по эталону; архивный раздел — плашка, не пустота.

Действия без тулбара живут в теле: кнопки и формы в блоках, действия внутри карточек
аспектов, пункты меню «⋯».

## 6. Адрес, открытие, переходы, история

### 6.1 Адрес

**Адрес = приложение + запись** (+ параметры — позже, место оставлено). Страница — тоже
запись; у встроенных экранов хоста (чат, поиск, настройки) — «хост + экран». Состояние экрана —
вкладка, параметры, прокрутка, разовое «открыть через X» — живёт в истории, не в адресе;
«поделиться» даёт адрес без состояния. Имя приложения в адресе — ключ эталона у приложений
поставки, id записи у своих.

**В данных — ссылки на записи по id, не адреса** (решение владельца 25.09): чип ссылки,
ссылочные свойства, связи. Адрес вычисляется при нажатии; вставленный в тело адрес Orbis
редактор превращает в ссылку на запись.

### 6.2 Правило открытия

Одна чистая функция ядра: «адрес → в какой рамке и каким шаблоном».

- **Страница** — своим телом в рамке **своего дома**, откуда бы ни пришла ссылка; дом выключен —
  хост с плашкой.
- **Запись с приложением A в адресе** — шаблоны A по правилу выбора (§5.3); у A подходящего
  нет — шаблон хоста **в рамке A** и плашка «открыть в [X]».
- **Запись из хоста** (чат, поиск, «Записи», ссылка из хоста) — кандидаты: **включённые
  приложения с подходящим шаблоном** (хост в споре мест не участвует):
  - ни одного — хост: шаблон владельца с пустым домом, иначе шаблон хоста;
  - одно — **сразу туда**, «‹» возвращает;
  - несколько — запомненный выбор («открывать вместо» у приложения-победителя, для набора мест,
    а не для записи), иначе вопрос «Где открывать такие записи?».
- Выключенное или архивное приложение в адресе — хост с плашкой «выключено — [включить]».
- Не отрисовался даже шаблон хоста — базовый вид записи.

Ссылка внутри страниц приложения несёт это приложение. Отвергнуто: «рамка зависит от
маршрута» (неявный вывод из истории). Адрес несёт приложение **явно**.

### 6.3 Переходы: что переносится

Переход — открытие адреса. Переносится только приложение (по правилу ссылки выше).
**Не переносятся**: `this` (открыл задачу — `this` стал задачей), параметры (если ссылка их
не передала явно), состояние предыдущего экрана (оно в истории). **Контекст из графа, не из
маршрута**: шаблон задачи показывает «проект: Переезд» из связи в графе. **Содержимое из
графа одинаково везде, раскладка принадлежит приложению** (ревизия 4; прежнее «выглядит
одинаково» перерешено шаблонами приложений): гарантия дописывания держит, что ни один аспект не
пропадает. Встроенные страницы внутри одного экрана получают `this` и параметры открытой
страницы — они содержимое.

Цепочка: Проекты, раздел «Проекты» → тап «Переезд» → адрес «Проекты / Переезд», шаблон
проекта → тап по задаче → «Проекты / задача», шаблон задачи, блок «проект» из графа
показывает Переезд → тап по расходу «Грузчики 12 000» → у Проектов нет шаблона расхода —
шаблон хоста в рамке Проектов с плашкой «открыть в Бюджете» → назад: задача → назад: Переезд
на той же вкладке → назад: список раздела.

### 6.4 Встраивание

Страница может встраивать страницу (со `this` и параметрами открытой). Глубина ≤ 2,
самовстраивание запрещено, хост ловит цикл (шаблон проекта встраивает «страницу проекта»,
та — шаблон проекта).

### 6.5 История

**Модель одна**: приложение → разделы → у каждого раздела своя стопка экранов, плюс общий
журнал переходов между приложениями; приложение помнит активный раздел. Повторное нажатие на
раздел — его корень. Экраны хоста, вызванные кнопками хоста (чат на телефоне, поиск, быстрый
ввод), ложатся поверх текущего раздела; боковой чат и окно поиска на десктопе — вне истории.

**Поведения два** — по способу запуска: «как приложение» (установленное, «назад» по стопке
раздела, системный «назад» перехвачен) и «как сайт» (вкладка браузера, «назад» браузера по
порядку, каждый переход — честная запись). Поведение — одна чистая функция «модель + действие
→ модель».

## 7. Доверие, компоненты, производительность

### 7.1 Модель браузерных расширений

| Слой в браузере | В Orbis |
|---|---|
| Изоляция: код расширения в своём мире, к DOM через посредника | компонент яруса 2 исполняется в песочнице; данные приходят результатом подписки блока, к графу напрямую не ходит |
| Манифест разрешений при установке; «только на этом сайте / по клику» | манифест: какие контракты читает, какие действия зовёт, нужна ли сеть; экран установки как экран согласия OAuth-гранта (D34); аналог «по клику» — доступ только к `this` открытой страницы |
| Опосредованный API | мутации только действиями по имени через общий конвейер; своей мутации у компонента нет |
| Никакого удалённого кода | пакет подписан, CSP запрещает догрузку; версия компонента = версия расширения |
| Магазин: проверка, подпись, рубильник | marketplace проверяет и подписывает; рубильник = выключение расширения с плашкой на месте блоков |
| Видимость | значок расширения на компоненте; в журнале у действия автор-расширение; права сужаются по наблюдениям (В6) |
| Доверенный UI: запрос разрешений рисует браузер | подтверждения, установка, присутствие хоста и кнопки хоста рисует хост; компонент только просит |

Инциденты случаются и у браузеров: остаточный риск принимается и держится рубильником;
фундамент — изоляция и опосредованный API, не доверие проверяющему. Песочница не решает
обман через интерфейс — его решает доверенный UI. Два яруса компонентов для всех расширений,
включая наши (В1): декларация по умолчанию, код в песочнице — законный второй ярус.

### 7.2 Экспорт и загрузка (В4)

Компоненты расширений экспортируются в общий каталог. Пачкой они не грузятся, потому что
«компонент» — три разные вещи:

- **каталог** — декларации (имя, схема свойств, контракты, инструкция агенту): маленькие
  данные, загружаются все, нужны редактору и агенту;
- **ярус 1** — композиция примитивов: кода нет, примитивы уже загружены;
- **ярус 2** — код: грузится лениво при первом рендере страницы, где он стоит; **песочница
  одна на расширение**, поднимается при первом использовании, гасится по бездействию.

Рендер страницы: список блоков → набор компонентов → недостающие грузятся параллельно, на
месте скелетоны (прогрессивный рендер). Манифест объявляет размер бандла, marketplace держит
лимит, хост измеряет загрузку и показывает на карточке расширения. Библиотека примитивов
хоста тоже режется на части. От числа установленных расширений зависят размер словаря и
подмножество каталога в промпте авторства; рендер зависит только от того, что на экране.

## 8. Агент в этой картине

- **Авторство.** Вход: просьба + каталог блоков + инструкции расширений + подмножество
  реестра под запрос. Выход: тело страницы текстом. Проверка: разбор → компиляция каждого
  запроса → сухой рендер по реестру (незнакомое свойство — отказ, не пустота). Доставка:
  предложение диффом с правкой до принятия (Ш1). Промпт авторства отдельный; каталог в общий
  промпт чата не попадает (проба P1).
- **Сопровождение.** Сломанный блок — сигнал; агент предлагает починку диффом. Новый эталон
  записи поставки при правленой записи — предложение «принять дифф?».
- **Рутины** действуют во времени, страницы — на экране. Рутина пишет блоки в страницу или
  предлагает правку. Инструкции аспектов и правила памяти влияют на авторство и разбор ввода, не на
  рендер.
- **Язык контрактов** агент получает тем же каноном, что блоки: «что у меня на этой неделе» —
  один запрос по «когда».
- **Экономика (D36):** сборка страницы — платно; рендер и ручная правка — бесплатно;
  страница — данные владельца, экспортируемые.
- **Модель никогда не рисует в рантайме.**

## 9. Проверка на сценариях (В6)

| Сценарий | Что ломается | Правило |
|---|---|---|
| Шаблон приложения не включил блок «теги» или «тело» | в этом приложении их не видно и не поправить | шаблон хоста всегда в меню «⋯» одним тапом |
| Пользователь испортил шаблон хоста, убрал «тело» | все заметки без тела | базовый вид записи — гарантия хоста, не шаблон; «вернуть как было» |
| Правка шаблона из открытой записи | пользователь думает, что правит эту запись | два глагола + баннер «вы правите шаблон» |
| Шаблон встраивает страницу, та — шаблон | бесконечный рендер | глубина ≤ 2, самовстраивание запрещено, хост ловит цикл |
| Чужое расширение поставило в шаблон блок «тело» | подозрение на чтение содержимого | «тело» — примитив хоста, расширению данных не отдаёт; ярус 2 получает только подписки по манифесту |
| Запись подходит шаблонам двух приложений | где открыть из чата | правило открытия: запомненный выбор места или вопрос; хост в споре не участвует |
| Запись с двумя аспектами, у приложения шаблоны для обоих | какой показать | больший набор аспектов побеждает; ничья — выбор владельца для спора |
| В приложении A нет шаблона для записи | чем показать в A | шаблон хоста в рамке A + плашка «открыть в X» |
| Расширение выключено | его данные и карточки | записи видны, поля только чтение, карточка и блоки плашкой; язык (контракты) живёт |
| Блок обвязки на обычной странице («подзадачи» на «Утре») | показывает подзадачи самой страницы | обвязка привязана к `this`; у страницы `this` — она сама; «скрыть при пустом» |
| Приложение хочет «заблокировать» пользователя | нет выхода | присутствие хоста и кнопки хоста рисует хост поверх любого содержимого |
| Релиз с новым эталоном шаблона хоста | правки владельца | релиз записи поставки не трогает — предложение «сравнить / принять / оставить своё» |
| Свой аспект владельца реализует «когда» | Повестка его не знает | язык контрактов: появляется в Повестке сам |
| Задача отменена | висит в Повестке | закрытое без времени закрытия дат «когда» не имеет — уходит |

## 10. Растворённые понятия и статус решений

**Уходят:** view → страница / форма показа блока / приложение; модуль → **расширение**
(функции), место → **приложение**; «поверхность подписывается» → блок подписывается;
размещение → раздел; экран записи в оболочке → шаблоны приложения; Hub Launcher → страницы
приложений; формула нового домена → «строки в реестрах + страницы»; «iframe-изоляция
сторонних views» → ярус 2 под манифестом; FAB, уровень, пространство, режим, секция, главный
аспект — отвергнуты по ходу диалога 2026-09-12…13.

| Решение | Статус |

## 11. Тулбар: место решено, сам тулбар отложен

**Решение владельца 2026-09-13: делать без него.** **Место решено 25.09** (правило зон §5.6):
тулбар приложения — **группа плавающих кнопок внизу слева**, светлых, с подписями, возможно с
аккуратной подложкой, не от края до края; справа — кнопки хоста. Что показывает тулбар и кто
им владеет — срез 2, с чистого листа.

Всё ниже — **грубые наброски**, а не дизайн: ни одно положение не принято; записано только
чтобы не потерять ход мысли. Набросок модели: список действий из реестра; держатели — оболочка
(по умолчанию) и страница (переопределение: свой список / добавить / скрыть); действию
передаются `this` и параметры; главное действие — выделенный пункт. Для записи с несколькими
аспектами сборка по тому же правилу, что содержимое: действия шаблона → действия размещённых
карточек аспектов в порядке размещения → действия неразмещённых карточек под «⋯» (гарантия,
что ничего не пропало) → тулбар приложения по умолчанию, если никто ничего не дал; дубли по
имени схлопываются; видимы первые N. Не склеилось: владение тулбаром при переходах и при
нескольких аспектах ощущалось перегруженным. До возврата к теме действия живут в теле (§5.6).
