## 0. Суть в четырёх фразах

1. **Модель работает в момент авторства, рендер детерминированный.** Агент собирает страницу
   один раз по просьбе, результат хранится версионируемым артефактом (не кэшем), дальше
   рисуется без модели. Сборка — платно (D36), рендер и ручная правка — бесплатно.
2. **Страница — запись графа с аспектом «страница»; её схема — её тело**, документ из текста
   и блоков; текст — каноническая форма.
3. **Приложение — семь элементов по одному публичному контракту**: манифест, словарь,
   действия, компоненты, страницы, оболочка, рутины. «View» и «модуль» как понятия
   растворяются в нём.
4. **П0: у наших приложений нет особых возможностей.** Хост и приложение различаются только
   доверием, никогда — API. Проверочный вопрос: «может ли пользовательское приложение целиком
   заменить наш Бюджет?» — обязано быть «да».

## 2. Хост и приложение: граница

### 2.1 Хост, «нулевое приложение» — только то, что обязано быть доверенным

- Граф, реестры, канон запросов, RLS.
- AI: чат, рутины, память, исполнитель; журнал, Undo, классификатор и **доверенный UI
  подтверждений**: плашку подтверждения рискованного действия рисует только хост, как
  браузер рисует запрос разрешений поверх страницы, и компонент подделать её не может.
- **Каталог примитивов** — стандартная библиотека для всех: список, таблица, плитка,
  кольцо/шкала, график, календарная сетка, прогресс, контролы форм, контейнеры раскладки.
- Рантайм приложений: рендер страниц и оболочек, песочница компонентов, переключатель
  приложений, глобальный поиск, настройки аккаунта, marketplace.

Всё остальное — приложения, включая обзор записей и наши Бюджет / Повестку / Питание.

### 2.2 Приложение — семь элементов, контракт один для наших и чужих

| # | Элемент | Что это | Пример (Питание) |
|---|---|---|---|
| 1 | **Манифест** | идентичность (имя, иконка, акцент) + **разрешения**: какие аспекты и контракты читает, какие действия зовёт, нужна ли сеть до своего сервера | читает «приём пищи», «продукт»; зовёт «записать приём пищи»; сети нет |
| 2 | **Словарь** | свойства, аспекты, роли связей, контракты, привязки `implements` | аспект «приём пищи», свойство «калории», связь «состоит из продукта»; «приём пищи implements „когда"» |
| 3 | **Действия** | именованные рецепты; подтверждение по риску, журнал, Undo | «записать приём пищи», «повторить вчерашний завтрак» |
| 4 | **Компоненты** | ярус 1: декларация — композиция примитивов хоста; ярус 2: код в песочнице под манифестом. Пространство имён приложения, версия = версия приложения, **экспорт в общий каталог** | «питание/кольцо» = примитив «кольцо» + подписка «сумма калорий за сегодня» |
| 5 | **Страницы** | записи с аспектом «страница»; копируются пользователю при включении с ссылкой на эталон | «Сегодня», «Дневник», «Продукты», «Статистика» |
| 6 | **Оболочка** | домашняя; навигация из размещений; FAB; экран записи для своих аспектов | нижняя панель из четырёх страниц, FAB «записать приём пищи» |
| 7 | **Рутины и инструкции AI** | рутины приложения, `ai_instructions` его аспектов | «недельный отчёт» пишет блок в «Статистику» |

Выключение приложения убирает все семь; данные остаются читаемыми; его блоки на чужих
страницах показывают плашку «приложение выключено» с кнопкой включить — никогда пустоту.

### 2.3 П0. У наших приложений нет особых возможностей

**Любая возможность, которой пользуется наше приложение, доступна пользовательскому
приложению через тот же контракт.** Хост и приложение различаются только доверием
(подпись, проверка, предустановка), никогда — API.

Следствия:

1. Граница хост/приложение зафиксирована списком §2.1; всё, что не в списке хоста, —
   приложение, включая обзор записей.
2. Наши приложения объявляют манифест с первого дня и идут через тот же конвейер действий,
   журнал и подтверждения, что и чужие.
3. Наши компоненты — ярус 1 по умолчанию. Всё «особенное» (кольцо калорий, таймер подходов)
   — либо примитив хоста, доступный всем, либо ярус 2 под теми же правилами песочницы.
   Давление дизайна намеренное: богатая стандартная библиотека примитивов вместо
   привилегированного кода.
4. Проверочный вопрос концепции: «может ли пользовательское приложение целиком заменить наш
   Бюджет?» Ответ обязан быть «да».
5. Открыто (В1): строгое прочтение — наш код яруса 2 исполняется в той же песочнице;
   контрактное — тот же API, но доверенный код вне песочницы.

## 3. Страница

### 3.1 Определение

Страница — запись графа с аспектом «страница». По хранению от заметки не отличается —
и это намеренно, по логике аспектов: «это задача», «это расход», «это страница». Аспект
добавляет:

- **дом** — приложение, в рамке которого страница открывается; для пользовательской —
  назначенное владельцем, по умолчанию хост;
- **параметры и роль шаблона** — типизированные параметры (период, запись, выбор из списка)
  и «шаблон для записей аспекта X» с подстановкой `this`: одна запись рисуется для сотни
  проектов;
- **размещения и переопределение FAB** — едут со страницей в любую рамку;
- **режим показа** — открывается как экран, без обвязки записи (заголовок на месте, теги,
  карточки аспектов, подзадачи, обратные ссылки, тред); «открыть как запись» показывает
  версии, тред и обратные ссылки той же записи;
- **эталон** — для страниц от приложения: «вернуть как было», обновление диффом.

Аспекты складываются: конкретный проект может сам быть страницей, если его тело сделали
его же дашбордом. Снял аспект — снова заметка; содержимое, версии и ссылки не тронуты.

### 3.2 Тело: текст и блоки — соседи

Дерево узлов, где текст и блоки на равных правах (модель Notion): заголовок, абзац,
список, а рядом виджет запроса, плитка, форма, контейнер колонок, внутри которого снова
абзацы и виджеты. Дашборд — документ с малым числом абзацев; заметка — с малым числом
виджетов. Границы нет, есть пропорция.

**Схема = тело.** Агент пишет страницу текстом с грамматикой блоков, как любую заметку.
Второго формата схем рядом с документами не появляется. Текст — каноническая форма: его
легко генерировать модели, проверять, показывать диффом с правкой до принятия (Ш1),
править руками в режиме «как markdown». Контейнеры — блочный синтаксис с открывающим и
закрывающим маркером; глубина вложенности ≤ 2 — этого хватает любому дашборду.

```
# Утро
Сначала важное, потом деньги.
{{columns}}
  {{col}} {{query: задачи, срок=сегодня, не сделано, сортировка=приоритет}}
  {{col}} {{tile: конверт «Еда», остаток за неделю}}
{{/columns}}
Заметки по переезду:
{{query: заметки, связаны с this=проект «Переезд», последние 3}}
```

Три места, где модель трещит, и как это закрыто: вложенные контейнеры в текстовой форме
(блочный синтаксис, глубина ≤ 2); много живых блоков на странице (страница компилируется в
одну пачку запросов — требование к компилятору, не к модели); страницы приложений по
умолчанию (эталон + копия пользователю, §4.3).

### 3.3 Состав: пять слоёв страницы

| Слой | Суть | Пример просьбы | Статус |
|---|---|---|---|
| 1. Композиция блоков | окна в граф + раскладка; только чтение | «утренняя страница: задачи на сегодня, остаток конверта, три заметки по проекту» | в фундаменте |
| 2. Параметры и шаблоны | ручки, не меняющие граф; страница «для записи» с `this` | «страница расходов с выбором месяца»; «у каждого проекта своя страница» | в фундаменте |
| 3. Формы и действия | страница пишет в граф только действиями по имени | «форма: сумма, категория, кнопка „записать расход"»; «кнопка „перенести просроченные на завтра"» | в фундаменте |
| 4. Навигация и оболочка | набор страниц, сайдбар, домашняя, FAB, вкладки записи | «сделай „Утро" домашней, Бюджет убери из сайдбара» | в фундаменте — как оболочка приложения (§4.3) |
| 5. Логика и условия | закрытый малый набор: скрыть при пустом результате, порог числом на блоке, вычисления только агрегатами канона; произвольных выражений нет | «блок „Просрочено" только если есть просроченные» | ограниченно |

Слой 5 ограничен сознательно: произвольные условия превращают схему в язык программирования,
где агент делает невидимые до наступления случая логические ошибки.

## 4. Блок, размещение, оболочка

### 4.1 Блок

Блок = подписка (декларация запроса или подписка на контракт) + форма показа + настройки.
**Блок никогда не содержит данных.** Подписчиком становится блок, а не «поверхность»;
страница — контейнер подписчиков. Блок привязан к **контракту** («когда», «движение денег»),
а не к аспекту, поэтому календарь на «Утре» показывает обеды рядом с задачами, как только
Питание объявило привязку. Блоки всех включённых приложений образуют **один каталог**;
стиль — токены дизайн-системы хоста, акцент приложения красит только рамку — иначе сборная
страница из трёх приложений стала бы лоскутным одеялом.

Раньше «view» значило и экран, и форму показа, и линзу домена. Форма показа (таблица,
доска, календарь над одним запросом) — свойство блока; старый «сохранённый список» —
страница из одного блока.

### 4.2 Размещение

Размещение — ярлык: «что» (страница / действие / запрос), «в каком приложении», «в каком
слоте», «на какой позиции». Страница одна, ярлыков много; страница без размещений
существует и достижима ссылкой или поиском. Размещение хранится у страницы (как
закреплённые списки), поэтому агент делает его обычной правкой записи. Размещённый запрос
даёт живые разделы навигации: «Проекты» в сайдбаре — запрос «активные проекты», каждая
строка ведёт на страницу-шаблон. Одно действие может быть размещено как FAB, кнопка в
блоке и подсказка в чате — три размещения, не три механизма.

### 4.3 Оболочка приложения

Декларация из четырёх слотов и идентичности: **домашняя** (какая страница открывается при
входе); **навигация** (упорядоченный список размещений двух родов — страница на позиции,
запрос на позиции); **главное действие, FAB** (действие приложения по умолчанию; страница
может переопределить, и переопределение едет с ней в любую рамку); **экран записи** (какая
страница-шаблон рисует записи своих аспектов и какие вкладки рядом — тред, версии).

Личная настройка — правки поверх: переставить, скрыть, добавить свою страницу, сменить
FAB. Оболочка и страницы приложения **копируются пользователю при включении** со ссылкой на
эталон; «вернуть как было» и обновление приложения работают сравнением с эталоном, обновление
при правленой странице — предложение агента «принять дифф?». Пользователь может собрать
**своё приложение** из своих страниц и одного FAB: та же декларация, без эталона.

### 4.4 Правило дома

У страницы ровно **один дом** и сколько угодно ярлыков. **Страница всегда открывается в
рамке своего дома**, откуда бы ни пришли — по ссылке из заметки, из поиска, по ярлыку в
чужом сайдбаре, — с кнопкой «назад» в место, откуда пришёл. Бездомная страница, положенная
в навигацию приложения, получает его как дом (иначе каждый клик выбрасывал бы в общую
оболочку); **первое размещение задаёт дом**, каждое следующее — ярлык. Ярлык на чужую страницу помечен «↗ Питание», чтобы переключение не было
сюрпризом. Записи — так же: у аспекта есть приложение-хозяин, проект из Бюджета
открывается шаблоном Проектов в рамке Проектов.

Отвергнуто: правило «рамка зависит от маршрута» (по ярлыку — в текущей рамке, по ссылке —
переключение). Требует помнить, как пришёл; владелец его не понял с первого раза — это
и есть довод.

## 5. Доверие и чужой код — модель браузерных расширений

| Слой в браузере | В Orbis |
|---|---|
| Изоляция: код расширения в своём мире, к DOM через посредника, нативный код запрещён | компонент яруса 2 исполняется в изолированном контексте, не в основном коде Orbis; данные приходят результатом подписки блока, к графу напрямую не ходит |
| Манифест разрешений при установке; с MV3 — «только на этом сайте / только по клику» | манифест: какие аспекты и контракты читает, какие действия зовёт, нужна ли сеть; экран установки как экран согласия OAuth-гранта (D34); аналог «только по клику» — доступ только к записям текущей страницы, к `this` |
| Опосредованный API: расширение не трогает сеть и систему напрямую | мутации только действиями по имени через общий конвейер (политика подтверждений, журнал, Undo, RLS); своей мутации у компонента нет |
| Никакого удалённого кода (MV3) | пакет подписан, CSP запрещает догрузку; версия компонента = версия приложения |
| Магазин: проверка, подпись, рубильник | marketplace проверяет и подписывает; рубильник = выключение приложения с плашкой на месте блоков |
| Видимость: иконка, предупреждения | значок приложения на компоненте; в журнале у каждого действия автор-приложение; права сужаются по наблюдениям (В6), а не угадываются заранее |
| Доверенный UI: запрос разрешений рисует браузер поверх страницы | подтверждения рискованных действий рисует хост; компонент только просит их вызвать |

Рынок сошёлся к этой же модели: MCP Apps и Apps SDK у OpenAI — расширения браузера для
AI-хостов. Две оговорки, которые браузеры знают: инциденты случаются, остаточный риск
принимается и держится рубильником; песочница не решает обман через интерфейс —
это закрывает доверенный UI хоста. И цена, которую браузерная модель не убирает:
изолированное окно не наследует дизайн-систему само, тяжелее и не ощущается родным —
поэтому **два яруса компонентов для всех приложений**: декларация по умолчанию (безопасна
по построению, выглядит родной), код в песочнице под манифестом — законный второй ярус,
а не исключение для длинного хвоста.

---

## 6. Агент в этой картине

- **Авторство.** Вход: просьба + каталог блоков + инструкции приложения + подмножество
  реестра под запрос. Выход: тело страницы текстом. Проверка: разбор → компиляция каждого
  запроса → сухой рендер по реестру (незнакомое свойство — отказ, не пустота). Доставка:
  предложение диффом с правкой до принятия (Ш1). Хранение: запись. Промпт авторства —
  отдельный; каталог в общий промпт чата не попадает (проба P1: бюджет промпта).
- **Сопровождение.** Сломанный блок (переименовано свойство, выключено приложение) —
  сигнал; агент предлагает починку диффом. Обновление приложения при правленой странице —
  предложение «принять дифф?».
- **Рутины** — время; страница — пространство. Рутина пишет блоки в страницу или
  предлагает правку; её вопросы и предложения показываются теми же блоками в треде и чате.
  Инструкции аспектов и правила памяти влияют на авторство и разбор ввода, не на рендер.
- **Экономика (D36):** сборка страницы агентом — платно; рендер и ручная правка —
  бесплатно; страница — данные владельца, экспортируемые.
- **Модель никогда не рисует в рантайме;** карточки чата остаются производными от журнала
  (см. вердикт по A2UI, точка входа А).

Требования к декларациям: относительные токены дат, никогда абсолютные (иначе страница
протухает через неделю); блок хранит запрос, не данные; страница компилируется в одну пачку
запросов.

## 7. Растворённые понятия и статус решений

**Уходят:** «View» → страница / форма показа блока / приложение; «модуль» → приложение;
«поверхность подписывается» → блок подписывается, а «поверхность» остаётся словом для «где
показано» (страница, чат, уведомление); Hub Launcher → страницы приложений; формула нового
домена → «строки в реестрах + страницы по умолчанию»; «iframe-изоляция сторонних views» →
ярус 2 компонентов под манифестом.

| Решение | Статус |
|---|---|
| Авторство моделью один раз, рендер детерминированный из сохранённой схемы | принято |
| Схема хранится как версионируемый артефакт, не кэш | принято |
| Слои 1–4 в понятии «страница», слой 5 закрытым набором | предложено, не оспорено |
| Страница = запись с аспектом «страница»; схема = тело; текст каноничен | принято |
| Страницы и оболочка приложения копируются пользователю с эталоном | предложено, не оспорено |
| «View» → «приложение»; семь элементов приложения | принято |
| Компоненты определяет приложение; экспорт в общий каталог | определяет — принято; экспорт — предложено, не оспорено |
| Правило дома: один дом, всегда открывается в нём | предложено, не оспорено |
| Модель доверия «как расширения браузера», два яруса компонентов | принято |
| Манифест разрешений — часть фундамента, для наших приложений тоже | **принято владельцем** |
| П0 «у наших приложений нет особых возможностей» | **задано владельцем**, следствия §2.3 |
| Цельная картина (этот документ) | **принята владельцем 2026-09-11** |
