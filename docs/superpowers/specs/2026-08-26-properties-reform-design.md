## Зачем

Кратко (полная мотивация — бриф §1, не пересказывается). Механизм аспектов негибок, и жёсткость сидит в модели данных, а не в UI: значение существует только внутри аспекта (`aspects['orbis/task'].status`), смысл вычисляется кодом из формы данных, функции привязаны к id аспектов и значениям enum — пользовательский аспект мёртв для всех функций (инвентарь, 568 мест в пяти зонах). Цель реформы: **перевести из кода в данные всё, что отвечает на «что существует, что это значит и что должно выполняться», оставив кодом только «чем это исполняется»** — потому что главный автор структуры — AI, а декларацию, в отличие от кода, можно провалидировать, показать диффом, принять пачкой и откатить. Каждое решение спеки проверяется принципами брифа §4 (одна истина; три слоя; дисциплина против inner-platform; модули не знают друг о друге; всё объяснимо и заменяемо; fail-closed; садовник; разрешимое ядро — один универсальный слой).

### §0.3 Словарь спеки

«Аспект» — термин продукта (В1); слово «роль» из ранних заметок здесь означает аспект, а «роль ребра» — всегда полностью. «Свойство» — факт с тождеством (id). «Контракт» — семантический интерфейс со слотами и классами. «Привязка» (`implements`) — реализация контракта аспектом. «Подписка» — потребление контракта поверхностью. «Декларация» — любая запись слоя A. Роды Q/D/C/T/V/E/P — по паспортам формальных свойств (§С1).

# ЧАСТЬ А — свойства, аспекты, роли рёбер, пересев мира

## §А1. Модель сущности: `core + body + tags + props + aspects[]`

**Решение А1-1 (Р1, Р6, Р14).** Сущность = core (`id`, `title`, `emoji`, `created_at`, `updated_at`, `archived`) + body (`body`, `body_doc`, `body_refs`, новое `query_refs`) + `tags` + **`props jsonb`** (`{ "<property-id>": значение }`, одно значение на свойство на сущность) + **`aspects text[]`** (массив id аспектов). Колонка `entities.meta` **удаляется** вместе с GIN-индексом `entities_meta_gin` (write-only во всех пяти зонах — inv §1 п.5; `db/schema.ts:72`, `0001_rls_and_indexes.sql:104`), абзацами о `meta` в промптах и `meta` в тулах/wire. `relations.meta` — живая (inverse/undo, `executor.ts:1731,1820`) и **остаётся системной**, пользователю не открывается (Ч10-С4, В2 инвентаря решён «оставить явно»).

**Решение А1-2 (Р14).** Извлечённый AI факт — свободное свойство (`orbis/amount` на записи без аспекта), а не мешок `meta`. Новый факт без подходящего свойства: AI заводит свойство в статусе `proposed` (§А2-7) либо оставляет текст в body. Жёсткий критерий заведения (украдено у стилмена (б), отчёт направления §1.2): **свойство — то, по чему будут фильтровать или считать; остальное — текст в body**. PRD §3.9 (соглашение meta-ключей) и §3.10 (ретро-миграция) в прежней форме отменяются: §3.9 становится свойством модели (факт живёт по одному id), §3.10 — жестом «навесь аспект — обязательные уже стоят» (Р9: свойства без аспекта видны и живы).

**Решение А1-3. Свойства ядра (core-проекции).** Core-колонки, адресуемые запросами и предусловиями (`archived`, `title`, `created_at`, `updated_at`), получают записи в реестре свойств с `storage: core` — id `orbis/archived`, `orbis/title`, `orbis/created_at`, `orbis/updated_at`: хранение остаётся колонкой, реестр даёт единый адрес для Q-AST, CAS и label. Псевдо-аспект `orbis/entity` (`executor.ts:858-897`) и второй несовместимый способ (`proposal-text.ts:95`: `aspect===''`) **удаляются** — их заменяет адресация по property-id (закрывает №10 и прецедент inv §4).

**Решение А1-4. Индексы `entities` (по замеру П2, не по привычке).**
- **Заводятся:** GIN (`props`) — потребители: `has(prop)` = `props ? '<id>'` и containment-фильтры селективных запросов Browser/смарт-листов (тот же класс, что сегодняшний GIN по `aspects`; выигрыш плоской карты против двухуровневой — inv §1 п.11); GIN (`aspects`) — `aspect=` (`aspects @> '{orbis/task}'`); btree (`owner_id`, `updated_at` DESC) WHERE NOT `archived`; GIN по `tags`, `body_refs`, FTS — как сегодня (01 §4.9); GIN (`query_refs`).
- **Не заводятся:** экспрессионные btree по `props` (`(props->>'…')`) — П2 §7 показал на 20k и 100k: ни одна ведомость Budget их не использует, агрегаты по природе сканируют корпус движений; частичные btree добавили только шум.
- **Приёмка против истории `entities_meta_gin`:** в первом срезе — EXPLAIN-подтверждение, что каждый заведённый GIN используется хотя бы одним горячим запросом (Browser-фильтр, смарт-лист); неиспользуемый индекс снимается той же задачей (§С8-А12).

**Обоснование.** Форма хранения проверена П2: прототип на `props`/`aspects[]`/`relations.role` даёт 1,14× к сегодняшним агрегатам при нуле расхождений семантики (480 конвертов, 12 периодов, посимвольное совпадение decimal).

**Решение А2-3. Переопределение пользователем label/description встроенного свойства — запись в его локали поверх системной (Р19); тип, key, обязательность — нет.

**Решение А2-4. Слаг при создании.** AI предлагает английский key (`user/effort`); без AI — транслитерация; коллизия — суффикс. Ставки низкие: key изменяем (Р3). Заведение свойства с reserved-словом грамматики (`limit`, `search`…) **разрешено** с подсказкой конструктора — коллизия невозможна по построению В11 (§А5-4).

**Решение А2-5. Служебные свойства** (`orbis/agent-run`, поля прогона) — в реестре (query по id обязан работать), с `system_writable: true`, вне `attach_*` и вне промпт-каталога (№33). Аспекты механики исполнителя (`agent-run`, `assignment`, `routine`) настраиваются только label/description (заметки, «Ограничения вслух»). **Гейт `system_writable` определён против источника, не актора** (В3 ревью): запись проходит для `MutationSource` из перечня §А4-4 — `hook`, `rule`, `materialize`, `seed`, `action-seed` (шаг встроенного действия-сида), `verb` (глагол исполнителя), `import`; запись из пользовательского действия, тула, UI и MCP — отказ семейства `COMPUTED_WRITE`. Примеры по §А8: `carryover` пишет правило rollover (`rule`), `bank_txn_id` — `import`, свойства прогона — `verb`.

**Решение А2-6. Default.** У значения по умолчанию **два дома, не три** (№13): безусловный — поле `default` в определении свойства (В5); условный — правило `default` каталога с `when` (§Б4). На уровне аспекта дефолта нет: при двух аспектах на сущности он ломал бы «одно значение на сущность» (Р6).

**Решение А2-7. Жизненный цикл `proposed`** (№23, С4 заметок). Автомат: `proposed → active | merged | deprecated`. Кап **20** неподтверждённых на владельца; 21-е предложение — отказ с подсказкой «разберите пачку». Подтверждение: в чате — дифф Ш1; от рутины — единица пачки D42; садовник (рутина раз в неделю, Р17) сводит дубли и приносит отчёт о сиротах (свойство без аспекта и без значений) и о `proposed` старше 14 дней. При отклонении значения на сущностях **остаются**, свойство скрыто (deprecated). `proposed` не входят в промпт — только в каталог-тул (§А9-3). Порог провала — П4 (§С9): >1 нового `proposed`/день устойчиво или >20 % несведённых дублей → Р14 сужается до «только существующие свойства + текст в body».

## §А3. Реестр аспектов: новая форма `aspect_definitions` и дельты

**Решение А3-1. Определение аспекта** — интерпретация, не владелец полей (Р5): `id`, `key`, `label`, `description` — та же четвёрка с той же семантикой, что у свойств (№27; имя тула `attach_*` — из key); `properties: [{property_id, required, rank}]` — ссылки на свойства с обязательностью и порядком; `ai_instructions`; `tag_mappings`; `implements` (привязки — §Б2; в части А поле пустует); `view_config` (подсказки рендера); `module`; служебность — колонка `service boolean` (сегодняшний `SERVICE_ASPECT_IDS` в коде — в реестр, №33/inv §3 «список служебных в трёх копиях»). JSON Schema аспекта — **генерируемая производная** для ajv-валидатора и тулов; `x-orbis-type` — копия типа свойства (ref-заметка Р1). Колонка `aggregations` (§4.3 PRD) — используется по назначению: материализация агрегатов (§Б5-5).

**Решение А3-2. Дельты, не правка (Ч2).** Системное определение неизменяемо и версионировано (из кода, через сид). Пользовательские изменения — строки таблицы `registry_deltas` (`owner_id`, `target_kind` — property|aspect|contract|relation_role|subscription|action, `target_id`, `base_version`, `delta jsonb`, `created_at`): label/description/иконка/порядок/скрытие свойства; добавленные к встроенному аспекту свойства (жест «+ свойство к задаче» — без аспекта-спутника); добавленные варианты `select`; ослабленная обязательность по явному списку мест, где код null-толерантен. Типы и key встроенных дельта не меняет. Эффективное определение = система ⊕ дельта (кеш — §А10).

**Решение А3-3. Обновление системы при живой дельте — трёхстороннее слияние (Ч2, №20).** `base_version` хранится на строке дельты. Drift на деплое при конфликте не роняет старт и не выбирает молча: конфликтные пары становятся **единицами пачки D42 в глобальном треде владельца**. Правила по типу поля: label/description — дельта побеждает; добавленный системой вариант рядом с пользовательским похожим — предложение слить; `bind`/`value_map` — дельта побеждает с проверкой типов; скрытие свойства, ставшего обязательным, — конфликт в пачку.

**Решение А3-4. Два механизма «где показывается свойство» разведены (П1 §4-4).** Основной жест — **дельта аспекта** (`+ свойство к задаче`): свойство входит в эффективный состав аспекта, попадает в `attach_*` и форму. `scope` (Р15) — второй механизм с одной фразой смысла: «показывать колонкой на всех сущностях по условию, без аспекта». Валидатор отклоняет двойное объявление (одно свойство и в дельте аспекта X, и со `scope: aspect=X`) с подсказкой убрать scope.

**Решение А3-5. «Удалить встроенное» (Ч3).** Удаление встроенного аспекта = выключить модуль (§Б8); удаление встроенного свойства из аспекта = скрыть дельтой (данные остаются, Р9); смена типа = форк. У свойства с контрактом — честные зависимости: «кто на нём стоит» читается из графа зависимостей (§С1-3, свойство 10), не из рукописного списка.

## §А5. Запросы: канонический AST, грамматика, `entity_query`

**Решение А5-1. Канон — булево дерево (В12, Р12).** Канон фильтра — дерево `and/or/not` произвольной вложенности над предикатами; параметры проекции (`sortBy`, `limit`, `display`, `title`) — отдельными полями, структурно отделены от предикатов. Предикаты одной сущности: `props` по id, core-свойства (§А1-3), `tags`, членство в аспекте, `has(prop)` (= `props ? id` — закрытие дыры inv §1 п.11), диапазоны и date-токены, `search`; с части Б — `class(contract)`. Реляционные предикаты по **одной роли**: `children_of`/`parents_of` (+ необязательное `via=<роль>`; без него — `role IN (иерархические)`, §А4-2), `has_relation`, `has_children`, `descendants_of`/`ancestors_of via=<роль>` — рекурсивный CTE по `(source_id, role)`, кап глубины **32** (Ч9); отрицание — через дерево (`!has_children via=subitem` = «терминальная задача»). Результат — обычные сущности: сортировка/лимит/smart list работают как везде. За границей Q (по построению): соединения двух свободных сущностей, агрегатные предикаты, обход по нескольким ролям, пути/циклы как результат, сходство (паспорт Q).

**Решение А5-2. Хранение — только AST (№18, суперсид Р12).** Сохранённый запрос (query-блок, `progress_source`, `ref.target`, `scope`, подписки) хранит `ast` с id свойств/аспектов/ролей/сущностей; поле `text` — только у неразобранного блока (показывается с ошибкой, как сегодня). Печать — проекция при чтении: **key для машин, label для человека** — два рендера одного AST (Р12); после переименования label устареть нечему. Дифф Ш1 меряет по канонической печати AST в key-форме (`collectText` через `attrs`, как сегодня `attrs.query` — `diff.ts:241`). `query_refs[]` на сущности — индекс «где используется» (по образцу `body_refs`). Экспорт — markdown-проекция + снимок реестра; импорт резолвит по снимку.

**Решение А5-3. Грамматика (Р13, В11, В12).** Текст — синтаксис ввода/вывода, не формат хранения. Правки: (а) машинная адресация свойств — **namespaced key** (`orbis/envelope_limit>1000`): слэш — встроенная пометка «свойство», коллизия с голыми reserved-словами невозможна по построению; квалификация «аспект.поле» — атавизм, отменена (В11); (б) label-форма — закавыченное имя всегда поле (`"дата оплаты">2026-08-01`), резолв по локали, при неоднозначности — уточнение `aspect=`; (в) `aspect=` принимает key и label аспекта; (г) `has=<key>`; (д) плоская текстовая грамматика v1 — сахар без скобок (OR-дерево строится формой/AI/AST-входом; скобки — возможное будущее расширение); (е) алиас `due` уходит (`parse.ts:343-346`) — пересев тел В9; (ж) `aspect=`, имена полей и ролей валидируются по реестру при сохранении — опечатка больше не даёт молчаливый ноль (закрывает inv §6 п.12, паспорт Q «валидность решается при сохранении»).

**Решение А5-4. `entity_query` — текст ИЛИ AST (№17, суперсид Р8).** Вход тула: `{query?: string, ast?: QueryAST}` (ровно одно). JSON Schema AST — рекурсивный `$ref`; приёмка первого среза — прогон схемы на OpenAI Responses при `strict:false` (D29). Шпаргалка промпта дополняется примерами дерева (генерация — §Б7). Reserved-слова остаются особенностью только текстового сахара — в AST предикаты и проекция разделены структурно (В11).

**Решение А5-5. Agenda — один запрос.** Три запроса `useAgenda.ts:37-53` со склейкой на клиенте заменяются одной подпиской с OR-деревом (серверный, индексируемый запрос) — сид Планировщика (§Б5); «просрочено по сроку ИЛИ по началу» становится выразимым. Решение размещено здесь как следствие В12; **исполнение — срез Б-1** (механизм — подписка §Б5-6), в срезе А Agenda не трогается (М7 ревью).

**Решение А5-6. Служебное прячется как сегодня** (02-core-os §3.9): компилятор добавляет отрицание служебных аспектов, пока запрос сам их не назвал; признак — колонка `service` реестра (§А3-1), не список в коде.

**Решение А5-7. Канонический перечень узлов Q-AST** (В6 ревью: нормативные эталоны не могут жить только в gitignored-пробах — исполнителю первого дня нужен канон в спеке). Фильтр — дерево `{and: […]}` / `{or: […]}` / `{not: узел}`; листья: `{prop: <id>, op: eq|ne|gt|lt|range|in|contains, value}` (value — литерал типа kind, список, либо `{token: today|overdue|next_7d|after_7d}` у date/timestamp-свойств); `{has: <prop-id>}`; `{aspect: <id>}`; `{tag: строка}` / `{not: {tag}}`; `{search: строка}`; `{class: {contract, set}}` (часть Б); реляционные `{rel: {kind: children_of|parents_of|has_relation|has_children|descendants_of|ancestors_of, via?: <role-id>, of?: uuid|"this"}}` (кап глубины 32 — константа компилятора, не поле узла); `{archived: "true"|"any"}`. Проекция — отдельными полями: `{sortBy: [{field: <prop-id|core>, dir}], limit, display, title}`. Полная JSON Schema — артефакт задачи «Q-AST» среза А; эталонные фикстуры — перенесённые файлы проб (§С9, задачи 0-серии).

## §А6. Тип `ref` и ссылочные kind

**Решение А6-1 (Р16).** По заметке `2026-08-23-property-ref-type-notes.md` с шапкой-поправками, плюс два суперсида (§0.2 п.2, п.10). Форма: `{kind:'ref', target?: Q-AST | Q-AST[], cardinality?: 'one'|'many', max?}`. `target` — **статическое подмножество** Q-AST (ref Р3): без относительных date-токенов, `search=`, `this`, sortBy/limit/display/title/archived; нарушение — `SCOPE_NOT_STATIC`. Проверка значения — потребитель query-движка №7 (ref Р4): компиляция цели + `AND id = $1` под RLS; для `many` — `id = ANY($1)` + сверка числа. Проверяется установка значения, не каждая запись сущности (ref Р5). Пикер и контрол — по kind, `CategoryField` уходит (ref Р6); `orbis/budget`-категория получает пикер автоматически.

**Решение А6-2. Зеркало в `relations`** (ref Р8 + Б4): установка/смена/снятие значения `ref` пишет/удаляет строку с ролью `ref` и `meta.property = <id свойства>`. Истина — свойство; строка — производная, пересоздаётся при расхождении (правило 3 §10). Обратный обход («кто ссылается на категорию») — по `(target_id, role)`, ручной SQL по jsonb (`import/review.ts:491-506`) уходит. Компиляция `ref` в соединении — **всегда с явным `::uuid`** (П2 §8.1-8: `props->>` — text, `entities.id` — uuid; без каста — ошибка оператора). Тип знает компилятор из реестра.

**Решение А6-3. Политика при архивации цели** (В3 ref-заметки — решается здесь): **вариант 3** — ссылки остаются, сущности-источники помечаются `needs-review`; ничего не теряется, видно в Browser; архивная цель выпадает из множества `target` (цель компилируется с `NOT archived`), поэтому пере-установка того же значения — честный отказ с именем причины. Запрет архивации и обнуление отклонены: первый замораживает граф, второе теряет факт. Удаление цели — `ON DELETE CASCADE` снимает зеркало; значение-сирота ловится той же пометкой.

**Решение А6-4. Другие ссылочные kind.** `grant` — `agent_grants` (инвариант существующий, `invariants.ts:296-327`); `registry_ref` — записи реестров (В3 инвентаря: `memory.scope` → `registry_ref → contract`); служебные uuid прогона (`action_id`, `pending_id`, `edited_from`) — НЕ `ref` (указывают на действия журнала, не на сущности; ref Р10). `backref`/`rollup`/`lookup` — очередь 2, форма совместима (ref Р9), named-future (§С11).

## §А7. Валидация записи и предусловия

**Решение А7-1 (Р7).** Валидация — композиционная над результатом слияния, как сегодня (`mergeAspects → validate → commit`): каждое свойство — по своему типу (ajv по сгенерированной схеме, кеш по тексту схемы сохраняется — `aspects-validate.ts:46-67`); каждый аспект сущности — обязательные присутствуют; неизвестных id в `props` нет. Атомарность — на операции: `attach_<аспект>` принимается целиком или отвергается. Семистадийный конвейер executor'а (01 §9.2) не меняется.

**Решение А7-2. Доменные инварианты в части А остаются кодом, переписанным на `props`,** с тестами-близнецами и golden-корпусом «сущность → вердикт» на старом и новом валидаторе до замены (Р7): `status ↔ completed_at` (`normalize.ts:57-69`), условный `occurred_on` (`normalize.ts:99-120`), `grant ⇔ executor=agent` (`invariants.ts:296-327`), XOR субъекта прогона, уникальность конверта, «один budget-parent» (→ `target_max_incoming` роли §А4-3 — единственный инвариант, переезжающий в реестр уже в части А, вместе с ролью). Перевод остальных в правила каталога — часть Б (§Б4), одновременно с контрактами (Ч4: «одна работа, не две»).

**Решение А7-3. Предусловия CAS — по свойству (№10).** Формы: `{property: <id>, in: [...]}` и `{property: <id>, absent: true}`; core-колонки — через свойства ядра (§А1-3), псевдо-аспект уходит. Сравнение — **по типу**: `decimal` — численно (`"10.0"` = `"10.00"`), не `JSON.stringify` (`executor.ts:898-901`, inv §6 п.7). Носитель отложенных единиц D42 (`policy/pending.ts`) и снятие предусловий `orbis_propose` переводятся на ту же форму — это часть Р20, названная явно.

**Решение А7-4. Журнал и undo — единица отката свойство.** Inverse хранит прежние значения затронутых **свойств** (и снятие/навешивание аспекта отдельной операцией), не аспект-ключ целиком (`executor.ts:1485-1490`, inv §6 п.4); `journal.ts`/`undo.ts`/`rollback.ts` правятся синхронно. `ai/escalation.ts` — единственное место, которое перенос не переживёт (читает журнал по аспект-ключам): переписывается в той же задаче, что журнал; его эвристика — остаток C (§С1-4).

## §А9. Тулы LLM, wire, MCP

**Решение А9-1 (Р8).** `attach_<key аспекта>` генерируются из эффективного набора аспекта (шов `tools/registry.ts:960-1008` остаётся, источник — реестр свойств); имена параметров — **key** свойств; `description` параметра — label + description в локали владельца + варианты select. Кириллица в именах параметров не возникает. `entity_query` — §А5-4. `entity_create`/`entity_update` принимают `props` (по key с резолвом в id на границе) и `aspects` (attach/detach); `meta` из контрактов тулов уходит.

**Решение А9-2. Wire-проекции — две, и асимметрия названа (В4 ревью).** Внутренний wire (web): `props` по **id** + `aspects[]` + core; дополнительно едут эффективные label/description/типы запрошенных свойств (реестровый ответ, кешируемый по `registry_version` — §А10) — форма и контролы строятся по реестру, а не по данным (M2; закрывает inv §6 п.10: скрытие не работало, незаполненного поля не было, boolean правился словом «true»). **LLM/MCP-проекция печатает `props` по key** — Р12 «key для машин»: модель пишет тем же именем, которым читала, uuid-ключи пользовательских свойств до модели не доезжают. Резолв на границе тулов принимает **и key, и id** (id — для машинных путей и журнала).

**Решение А9-3. Read-тул `property_catalog`** (№9; норматив П1 §4-6/П3 §7.4): фильтры по слову/аспекту/контракту/модулю; выдаёт key, label, description, тип, варианты, аспекты-носители. Единственный путь модели к свободным и `proposed` свойствам (у них нет `attach_*`); часть промпт-норматива §Б7. Доступен чату, рутинам и MCP (чтение).

**Решение А9-4. MCP** публикует по скоупу гранта как сегодня (D37): `full` — публичный реестр + `property_catalog`; `worker` — чтения/глаголы/`thread_post`; **тулов мутаций реестра у `worker` нет** (§С2). Пять глаголов исполнителя, `orbis_ask`/`orbis_propose` — без изменений.

## §А10. Кеш реестра, слияние, конкурентность

**Решение А10-1 (Б7).** `registry_version` на владельца (строка в `user_settings` или отдельная таблица версий — деталь реализации); инкремент **в той же транзакции**, что любая мутация его реестров; для system-сидов — глобальная версия. Процессный кеш эффективных определений (система ⊕ дельты, резолв контрактов) по ключу `(owner, version)`; чтение в tx сверяет версию одним запросом. Кеш ajv-валидаторов по тексту схемы — как есть. Кеши агрегатов (§Б5-5) несут `registry_version` и инвалидируются его сменой.

**Решение А10-2. Слияние свойств (№8, Р10; все операции реестра — через исполнителя, с журналом и undo — Ч6).** Три операции реестра: сослаться (данных не трогает), переименовать label/description (бесплатно), слить. Слить — **одно действие исполнителя** с одним inverse (карта «сущность → старый id → значение») под advisory-lock реестра владельца (образец — `lockBudgetContour`, `executor.ts:282`): проставить `merged_into`, переписать ключи в `props`, переписать AST-ссылки (query_refs ведут к местам), одна строка журнала, один undo. Конфликт значений на одной сущности — слияние **ждёт** разбора пачки D42, частичного слияния нет. При каждом слиянии указатели `merged_into` на поглощённое компактируются в один шаг (цепочка A→B→C не образуется). «Переименовать id/key» как операции не существует (Р10; key встроенных — №12).

**Решение А10-3. Правило удаления.** Строки реестров физически **не удаляются** — только `deprecated`/`merged` (№21): `registry_ref`, AST и данные не виснут никогда. Единственное исключение — `proposed`, отклонённое до первого использования (нет значений, нет ссылок — проверяется в той же tx).

## §А11. Миграция документа: `DOC_SCHEMA_VERSION` и контракт черновиков

**Решение А11-1.** Первое поднятие `DOC_SCHEMA_VERSION` («+1 к текущей», абсолютный номер не фиксируется — align, строка 11) делает эта реформа: query-блок получает атрибут `ast` (Q-AST по id), `text` остаётся только у неразобранных. Трансклюзии достанется следующее поднятие.

**Решение А11-2. Контракт офлайн-черновиков Т8-в исполняет эта реформа** (align, строка 12 и «Порядок работ» п.1 — межлинейное обязательство): черновик тела, набранный до выкатки новой версии, после выкатки **не досылается молча** — состав нод известен (наш случай: `ast` — новый атрибут существующей ноды, не новый тип) → перештамповка версии на клиенте и обычный поток сверки; неизвестный тип ноды → предложение выбором; текст не теряется ни в одной ветке. Контракт реализуется как общий для всех будущих поднятий; трансклюзия его наследует, не вводит.

## §Б2. Привязки: `implements` (bind + value_map)

**Решение Б2-1. Форма** (jsonb-поле в строке аспекта — НЕ таблица: привязка умирает с аспектом, Ч7 хранение): `implements: [{contract, bind: {слот → property_id}, value_map: {вариант → класс}, fixed: {слот → константа}}]`. `fixed` — для аспектов с постоянным значением слота (П1 №3: хотелка — `direction: expense`, `planned: false`). Проверка типов слот↔свойство на записи — `BIND_TYPE` (§С1-2, отказ 9).

**Решение Б2-2. Fail-closed вариантов (Б5).** Дельта, добавляющая вариант select-свойства, принимается **только** вместе с отнесением варианта к классу каждого контракта, где слот участвует; конструктор/AI спрашивают в момент добавления («„в ревью“ — это сделано, отменено или в работе?»); без полного отнесения — отказ `VARIANT_UNMAPPED`. `value_map` — обязательное поле схемы декларации, а не проверка валидатора постфактум: П1 показал, что требование уровня схемы модель не пропускает никогда (20/20). **Решение Б2-3. Частичная привязка — членство динамическое** (П1 §3-4, недоопределённость закрыта). Привязка аспекта валидна, даже если обязательный слот у конкретной сущности пуст: аспект прикреплён, но сущность **не входит в множества контракта**, пока все обязательные слоты без значения (`facts`, `spent`, Agenda её не видят). Вариант «fail-closed на записи» отклонён: он запретил бы завести хотелку без даты покупки. Видимость честная: Detail показывает «не участвует в Budget: нет даты» (честные зависимости Ч3); владелец, желающий жёсткости, добавляет правило `requires_when`.

**Решение Б2-4. Права.** Свои привязки (свой аспект реализует встроенный контракт) — главный пользовательский жест, уровень «показать» (Б1 §С2); у встроенных аспектов привязку можно только дополнять (map добавленных вариантов). Шаблон П1 подтверждён: модель ни разу не тронула чужую сторону контракта (подписку Agenda) при просьбе «чтобы тренировки попадали в Agenda».

**Решение Б4-1. Хранение.** Правила — jsonb-поля в строке владельца (свойство/аспект/роль), НЕ таблица (правило умирает с владельцем; извне ссылаются только на контракты и роли — Ч7). Каждое правило имеет `id` (для журнала, «отключить» и графа зависимостей), `template`, `when?` (E), параметры шаблона.

**Решение Б4-2. `when` у всех реактивных шаблонов** (П1 §4-5): `on_enter_class`, `default`, `mirror_relation` получают необязательное условие E — иначе любое правило владельца глобально по контракту («при закрытии писать в тред» срабатывало бы на каждой домашней задаче). **Решение Б4-3. Таблица каталога v1 «шаблон → форма ядра → экземпляры»** (§3-3 формальных свойств; принцип уточнён решением §7-4: «≥2 экземпляров ИЛИ generic по построению»):

**Решение Б4-4. Права.** Свои правила из каталога на своих свойствах/аспектах — да; правила модулей — смотреть (честные зависимости), не править; «запер сам себя» лечится честной ошибкой с именем правила и кнопкой «отключить» (Ч7).

## §Б6. Действия: `action_definitions`

**Решение Б6-1. Форма (Ч11 с поправкой Б2).** `{id, key, label/description (per-locale), params: [{name, type: kind|контракт}], precondition: E (CAS), steps: [{tool, input с подстановками E}], sensitivity: [факты], offered_by: [{surface, when: E, llm?: bool}], module, batch_cap}`. Поле `confirmation` **упразднено** (Б2): уровень подтверждения вычисляет политика §7.10 по объединению фактов чувствительности **резолвленных шагов** и фактов декларации; декларация факты может только добавлять; шаг с фактом выше задекларированных — отказ `SENSITIVITY_UNDERDECLARED`.

**Решение Б6-2. Действие = резолвленный batch (Б2).** Гейты полномочий (allowed_tools, режим рутины, скоуп гранта) и политика оценивают резолвленные шаги, а не имя действия: действие доступно актору, только если **каждый** его резолвленный шаг прошёл бы гейты этого актора; act-рутине действие-тул доступен, только если все шаги ∈ `allowed_tools` и уровень резолвленного batch = `execute`, иначе — отложенная единица D42. Запрет `batch_execute` рутинам сохраняет силу в этой форме (01 §7.10 «одна обёртка провозила бы что угодно» — закрыто по построению).

**Решение Б6-3. Границы (дисциплина Ч7, паспорт T).** Шаги — только вызовы существующих тулов исполнителя; выражения тотальные; ветвлений нет (`ACTION_BRANCH`); действие не вызывает действие (`ACTION_NESTED`); глубина вложенности 0. Контекст (П1 §4-3, №11): `$self` — сущность, к которой применяется действие; **все `{prop: …}` резолвятся ДО первого шага из состояния на момент CAS**; читать результаты предыдущих шагов нельзя (v1: сослаться на созданную шагом сущность — никак; нужно — это рутина). «Пакетное» — map действия по результатам Q механикой batch: **кап обязателен** в декларации (`BATCH_UNBOUNDED`), дефолт **100** (решение §7-2 формальных свойств); порог §7.10 «batch > 10 → подтверждение» действует поверх. Рецепту хочется «если/пока/подумать» — это рутина; AI обязан распознать форму при создании (Ч11-доп п.5; П1: обе ловушки `wrong_form` распознаны — поле конверта ответа сохраняется в контракте создания).

**Решение Б6-4. Исполнение.** Резолв id → CAS-precondition (нарушено — честный отказ, не двойное исполнение) → подстановка → шаги одной транзакцией → одна строка журнала, один inverse, один undo (механика batch_execute/D42/Т6 — в проде). Inverse существует ⇔ у всех шагов есть inverse; иначе действие объявлено необратимым **до** исполнения, с фактами `irreversible`/`external` и честным «отката нет» в журнале (рулинг V3).

**Решение Б6-5. Три пути создания** (Ч11-доп): модуль — сидом (Финансы: `plan-to-fact`; будущая трансклюзия: `extract-section`). **`rollover` — не действие: у вещи один дом** (В7 ревью, сквозное свойство 3): Ч11 перечислял его среди сжимаемого действиями, но позднее принятые формальные свойства описали rollover декларацией **перехода периода** — правилом каталога (§Б4-3), срабатывающим само; кейса «вызвать rollover вручную» нет, а появится — это будет отдельное действие, ссылающееся на правило; владелец — словами через AI, декларация приходит диффом Ш1 **до** появления; AI — по наблюдению повторов, в пачку D42. Создание = запись: кеш реестра, поверхности `offered_by` и реестр тулов подхватывают без кода и деплоя. Правка чужого действия — дельта label; шаги встроенных — форк.

**Решение Б6-6. Тулы из действий (№32).** Тулом LLM публикуются только действия с `offered_by.llm: true`; остальные доступны через один тул `run_action(id, params)` с каталогом (описание из description). Выбор из сотен тулов деградирует — рост капается по построению.

**Решение Б6-7. Судьба при удалении** (№21): deprecate действия при открытой отложенной единице D42 — единица при «Принять» отвечает «Устарело» (payload резолвлен, но декларация снята), не исполняется.

## §Б7. Генерация промпта и тулов (Ч5 + норматив П3)

**Решение Б7-1. Формула Ч5 читается как «перечни и числа — из реестра, политика — рукописная»** (П3 §7.3). Рукописная рамка: роль, «одна сущность на намерение», правило даты, правило свободных денег, «не выдумывай идентификаторы», протоколы результатов и чипов — примерно половина промпта, и это законный остаток C с названной границей (политика-проза). Генерируется из эффективного реестра: каталог аспектов, инструкции аспектов, перечни списков, все числа из констант.

**Решение Б7-2. Генерируемая часть — ИНДЕКС, а не каталог (П3 §7.4; выбор развилки П3 сделан).** Полный каталог не масштабируется: 28,5 токена/свойство, порог 1.5× пробивается на +33 свойствах. Норматив v1: **промпт-индекс** (id + описание аспекта; поля и правила — в слое тулов, `attach_*` уже несёт схему и `ai_instructions`) + **read-тул `property_catalog`** (§А9-3) для свободных/`proposed` свойств и уточнений. Замер индекса: 1 899 токенов = 0.62× сегодняшнего системного канала при полностью генерируемом содержании. Названный риск (П3: «измеренная возможность, не проверенный дизайн» — сценарии на индексе не гонялись): приёмка среза Б-3 прогоняет 12 сценариев П3 на индексе; регрессия против полного каталога, не лечимая рамкой, → откат к «каталог аспектов + индекс свойств» с релевантностной подгрузкой (второй вариант П1 §4-6 — подмножество под запрос). Дубль `ai_instructions` (тул + промпт — 1 167 токенов на вызов) снимается: инструкции остаются только в туле.

**Решение Б7-3. Три обязательных умения генератора** (П3 §7.1): рендер типа поля из словаря (`date` / `decimal-строка > 0` / `enum a|b|c`); рендер дискриминируемого союза из схемы (единственная конструкция, на которой модели исторически ошибались); детерминированный порядок полей — из `rank` (§А2-1), не из jsonb.

**Решение Б7-4. Гарды — семантические + снимок генератора (В10, подтверждено П3 §7.5).** Побайтный снимок промпта как приёмка отменяется (после первой дельты у каждого владельца свой промпт — эталона не существует). Два слоя: (а) **семь семантических гардов на собранном канале**, на четырёх состояниях реестра (эталон / выключенный модуль / пользовательский аспект с привязкой / переименованный label): ни слова о выключенных модулях; инструкции каждого активного аспекта присутствуют **ровно один раз — в его `attach_*`-туле, в системном канале — ноль** (проверка на паре «канал + реестр тулов»; прежняя формулировка В10 противоречила снятию дубля §Б7-2 — В2 ревью); числа из констант; ноль рукописных перечней полей; все key примеров существуют; нет ссылок на данные владельца; размер в бюджете. (б) **Побайтный снимок генератора на фиксированном мок-реестре** — регрессия шаблона, не зависящая от данных. 12 исполняемых гардов v4 переживают генерацию (12/12), 7/10 текстовых умирают вместе с рукописью.

**Решение Б7-5. Токен-бюджеты §7.1 PRD переписываются измеренными** (П3 §7.6): слой 1 — не «~800», а фактические 3 055 (прод) / цель ≤ 2 000 с индексом; слой 5 — не «~1.5K», а 5 521 с целью снижения за счёт снятия дубля. Числа — в §С10.

**Решение Б7-6. Четыре прод-дефекта П3 — задачи среза** (найдены пробой, предшествуют реформе): (1) **текущей даты в системном канале нет вовсе** — `buildContext`/`send-message.ts` не кладут; строка даты в таймзоне владельца добавляется в сборку канала (задача 0-серии, можно до реформы); (2) **инвариант «блок продолжений последний» нарушен в бою** — `buildContext` (`context.ts:355`) дописывает секции после промпта; порядок сборки меняется, гард переносится со строки промпта на собранный канал; (3) **дубль `ai_instructions`** — §Б7-2; (4) **порядок полей jsonb** — `rank` (§А2-1). Дефекты 1–2 — немедленные задачи вне гейта части Б.

## §Б8. Модули

**Решение Б8-1. Манифест — в коде** (Ч7): словарь (id записей всех пяти реестров), тулы (`budget_status`, `import_csv_start`, `memory_rule_suggestion` уезжают из CORE — В6), поверхности (реестр имён для `SURFACE_UNKNOWN`), промпт-фрагменты (политика-проза модуля), код-остаток с записью «почему в коде» (метрика — П5), место под коннектор/секреты/скоупы (V3 — named-future). Таблицы модулей нет; включённость — `user_settings` (расширение `installedViews`), но **вкл/выкл — действие исполнителя** с журналом и undo (№28): меняет всё, что видит владелец.

**Решение Б8-2. Состав v1.** Ядро (не выключается): note, свойства ядра, контракты ядра (§Б1-2), роли ядра, механика исполнителя (agent-run, assignment, routine — ядро-исполнитель, не модуль: рутины — субстрат D35, их выключение = выключение продукта). Модули: **Финансы** (financial, budget, category; Budget-поверхности, импорт, fast-path деньги), **Планировщик** (task, schedule; Agenda), **Цели** (goal), **ADE** (project, repo; + правило nearest_ancestor для parent_project), **Память** (memory; подписка контекста, memory-rules fast-path). Примечание: assignment/agent-run нужны ADE и рутинам одновременно — потому ядро-исполнитель, а не ADE (иначе «модуль требует модуль», которого нет — В6).

**Решение Б8-3. Выключение модуля** (№22, Ч1): аспекты, тулы, поверхности, подписки, промпт-фрагменты уходят; **определения остаются резолвимыми на чтение** — сохранённые AST с ролями/свойствами модуля работают (запросы не ломаются), создание нового — запрещено; UI показывает «модуль выключен» вместо подписи. Данные не трогаются (скрытое ≠ удалённое). Консервативность (§С1-3, свойство 9): выключение не меняет результат чужих подписок — снимки четырёх состояний.

**Решение Б8-4. Зависимостей модулей нет** (В6, принцип §4-4): желание «модуль требует модуль» = пропущенный контракт ядра (порог — два потребителя); присутствие на чужой поверхности — только подпиской (карточка план→факт = подписка Финансов на Detail); признак модуля — поле `module` на строках всех реестров (№14/№15).

## §С2. Безопасность и полномочия: класс подтверждения мутаций реестра (Б1, Б2, №1, №25)

**Решение С2-1 (Б1 — норматив).** Мутация реестра — категория чувствительности «меняет, что видит и делает владелец» (факт `changes_registry`). Молчаливых мутаций реестра не существует ни для какого актора:

| Мутация | Актор | Уровень §7.10 |
|---|---|---|
| Своё свойство / аспект / привязка своего аспекта | владелец через AI (чат) | `preview` («показать» — карточкой, как AI-действия) |
| Подписка, действие, правило, дельта поведения (`value_map`, скрытия, наборы) | любой | `explicit-confirmation` («обсудить»: дифф Ш1 в чате; у рутин — отложенная единица D42) |
| `implements` встроенных аспектов, роли `created_by: system`, `subscription_definitions`/`action_definitions` чужих модулей | рутина (фон) | **запрет по объекту** — не откладывается никогда (ряд §7.10 «запрещённое по объекту») |
| System-сиды | деплой | drift-отчёт; конфликты — пачка D42 в глобальный тред (§А3-3) |

В §7.10 добавляется вход классификации «**перенастраивает поверхность или права**»: любой не-владелец → `explicit-confirmation`; скоуп MCP `worker` — **без тулов реестра вовсе** (§А9-4). Точка исполнения — политика §7.10; V2 сделает её правила данными (тот же движок `assign_level` — §Б4-3), исполняя обещание D35-В4.

**Поставка двухэтапная (Б1 ревью — иначе на интервале «срез А сдан, Б-1 не начат» существуют молчаливые мутации реестра, которые Б1 запрещает).** **Минимальная правка §7.10 — задача среза А**: вход «перенастраивает поверхность или права» по имени тула и объекту — образец готов, ряд `grantsAutonomy` (`policy/confirmation.ts:57-63` реестра не знает — пробой ревью); плюс запрет по объекту для фона и отложенная единица. Она не требует движков части Б: в срезе А реестр мутируют `proposed` (Р14), слияние, дельты и садовник — все классифицируются по имени тула/объекту. **Полная версия** (уровень действий по фактам чувствительности резолвленных шагов) — срезы Б-1/Б-2, вместе с действиями. Приёмка: §С8-11 (срез А) и §С8-23 (Б-1).

**Решение С2-2 (Б2).** Действие оценивается по резолвленным шагам (§Б6-2) — «декларированный класс мог бы только повышать» устраняется полностью: поля класса в декларации нет, есть только факты. Тест: «действие с шагом вне `allowed_tools` актора → отказ» (приёмка паспорта T).

**Решение С2-3 (№25).** `created_by: system` — по `MutationSource`, не по актору (§А4-4). Act-рутина не может «тихо перенастроить, что видит владелец» (анти-цель 3): реестровые тулы для фона либо запрещены по объекту, либо дают отложенную единицу; прогоны/рутины/назначения — прежний запрет по объекту (01 §9.3) без изменений.

## §С4. Поверхности реестра v1 (№29)

Обычный путь — сказать AI словами; конструкторы — продвинутый слой (анти-цель 5). Минимум человеческих поверхностей — **три экрана**:

1. **«Свойства»** — список эффективного словаря: label/тип/аспекты-носители/модуль; фильтры «сироты» (без аспекта и значений), «`proposed`», «deprecated»; подсказка дублей при создании (Р4); операция «слить» с предпросмотром конфликтов.
2. **«Аспект»** — эффективное определение (система ⊕ дельта визуально различимы), редактор дельты (label, скрытие, порядок, + свойство, + вариант с обязательным отнесением к классам — Б5), панель **честных зависимостей** (из графа §С1-3 п.10: «статус использует Agenda, чекбокс, блокировки…»), привязки к контрактам.
3. **Дифф деклараций** — расширение Ш1: generic-рендер JSON-декларации (было/стало по полям, с label вместо id) для карточек подтверждения §С2-1; тот же рендер — в пачке D42.

Перечень ошибок валидации привязки, показываемых человеку (все — §С1-2): бинд не по типу (`BIND_TYPE`), слот не закрыт (обязательный слот без bind/fixed), вариант без класса (`VARIANT_UNMAPPED`), двойная реализация слота (`SLOT_AMBIGUOUS`), цикл правил (`REGISTRY_CYCLE`), подписка на несуществующую поверхность (`SURFACE_UNKNOWN`). Каждая — с именем декларации и предложением действия, не серой кнопкой (Ч3).

## §С5. Экспорт и версирование деклараций (№30)

Канонический экспорт = JSON строк всех реестров владельца (включая дельты, подписки, действия, привязки) + сущности + снимок соответствий id ↔ key ↔ label (Р12) — дамп §9.4 расширяется этим составом; встроенные определения не экспортируются (не пользовательские данные), но снимок несёт их id/key/label для резолва импорта. Версия декларации = номер действия журнала (отдельного version-стора нет — журнал и есть история); анти-цель 4 («не клетка») выполняется тем, что AST по id + снимок делают экспорт переносимым и читаемым.

## §С8. Приёмка

Нумерация — по срезам §С9. Формулировка: проверяемое действие → ожидаемый исход. Все `file:line`-сверки — на момент исполнения.

**Срез А (реестры, props, роли, AST):**
1. Golden-корпус «сущность → вердикт» (Р7): старый и новый валидатор дают одинаковые вердикты на корпусе всех 13 аспектов + негативные фикстуры.
2. `attach_*` для каждого неслужебного аспекта генерируется из реестра свойств; имена параметров — key; `description` — label+description локали; снимок реестра тулов совпадает с эталоном.
3. Q-AST: golden «AST → SQL → результат» для всех конструкций §А5-1/§А5-7, включая `descendants_of via` (кап 32), `has(prop)`, OR-дерево; фикстуры невыразимого (`QUERY_JOIN`, `QUERY_MULTI_ROLE`) — ошибка разбора, не пустота.

5. Слияние свойств: apply → undo → байт-в-байт (props, AST, `merged_into`); конфликт значений — единица пачки, слияние не применилось частично.

- **Контракт «полномочие», коннекторы/секреты в манифесте, провенанс-триггеры** — V3 (рулинг §8: пять мест расширяемости заложены — §Б1-4, §Б8-1, факты `external`/`irreversible` §Б6-4, `in`/группа §Б3-2, словарь триггеров открыт формой каталога).
- **Общий каталог приложений `<app>/`** (marketplace D36) — v1 копирует словарь приложения владельцу (§С6).
- **Теги** — остаются слоем без схемы (В2 заметок); embeddings-поиск — слой рядом (стилмен (б)).
- **Workspaces/шаринг** — все owner-скоупы спроектированы «owner → scope» (Б7-кеш, RLS-шаблон, namespace-автор); per-user переопределения label — named-future конфликта (§8 заметок).
