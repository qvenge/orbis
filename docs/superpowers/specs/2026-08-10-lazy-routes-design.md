# Ленивая загрузка экранов (`React.lazy`) — дизайн

| Поле | Значение |
|---|---|
| Дата | 2026-08-10 |
| Ветка | `backlog-lazy-split` от `main@1a3ff84` |
| Источник | `docs/superpowers/reviews/2026-08-04-bundle-diet.md`, «Работа 2» |
| Владелец | афк, распорядился делать работы по порядку; решения принимает контроллер |
| Разведка | 5 читателей + отдельный измеритель + экспериментатор с прототипом на живой сборке |

## Что разведка изменила в постановке

Разбор бандла называл трёх кандидатов и оценивал работу как «вторую половину диеты».
Замеры уменьшили обещание втрое и переставили приоритеты.

**Потолок ленивости — 24% бандла, а не бандл.** Наш код весит **62.7 кБ gzip из 263.9**;
остальные 201 кБ — вендоры (react 55.7, markdown 47.1, radix 32.5, auth-js 21.3, tanstack
11.7, trpc 11.2, lucide 6.3). `React.lazy` двигает только наш код и те вендорные поддеревья,
у которых единственный потребитель — ленивый экран.

**Оценка «24 кБ за трёх кандидатов» ложна: прототип дал 13.2 кБ.** Настоящая сборка с
`React.lazy` на четырёх экранах Budget и `ImportFlow` показала не то, что показывала подмена
модулей: rolldown вынес общий чанк (56.8 кБ gzip — query-core, trpc, zod, uuid, lucide, react,
zustand, общий `ui/*`), и **входной чанк импортирует его статически**, да ещё и с
`modulepreload`. Начальная загрузка = вход + общий чанк = 250.7 кБ против 263.9 базы, то есть
**−13.2 кБ (5.0%)**, а не −70, как читается по одному лишь входному чанку.

**Крупнейший кандидат в исходном списке отсутствовал.** `features/entity-detail/*` —
**32.4 кБ gzip** в одиночку, больше троих заявленных вместе. Из них **14.1 кБ — настоящие
вендоры**: `ui/DropdownMenu` тянет `@radix-ui/react-menu`, `react-dropdown-menu`,
`react-popper`, `react-arrow` и весь `floating-ui` (43.7 кБ сырых), и его единственный
потребитель — этот экран. Query-builder (6.8 кБ) лежит целиком внутри его поддерева и уезжает
с ним бесплатно — складывать эти две экономии нельзя.

**Две гипотезы разбора опровергнуты.**
- «Вкладку Budget вынести целиком» — нельзя: `useBudget` дёргают `TabBar` и `SidebarNav` на
  каждом рендере, а `categories`, `txQuery`, `EnvelopeCard`, `PlannedToFactCard`,
  `usePlanToFactPrompt` импортируются из `chat`, `entity-detail`, `agenda` и `import`.
  **568 строк Budget остаются в main при любом разрезе**; ленивы только четыре экрана.
- «CSV-импорт открывается из чата» — открывается nav-состоянием: карточка чата пушит
  `{kind:'budget-import'}` в стор, на `features/import/*` не ссылается. Разрез чистый:
  единственный статический импортёр — `app/router.tsx:13`.

**Ни один кандидат не тащит за собой тяжёлый пакет** — кроме `entity-detail`. У query-builder
и import вендорные чанки после выноса байт-в-байт те же; у Budget уезжает 556 Б иконок.

**Выгода для PWA — не трафик.** `globPatterns: ['**/*.{js,css,html,…}']` кладёт в precache
все эмитированные чанки: прототип дал 14 записей вместо 8 и **+3.9 KiB** общего объёма.
Пользователь с установленным SW качает столько же; экономится парсинг и исполнение первого
кадра, не байты по сети.

**CSS не режется.** Tailwind v4 отдаёт один глобальный лист: в прототипе файл CSS остался
побайтно тем же. Опасение «мерцание нестилизованного контента» снимается фактом.

## РЕШЕНИЕ Р1. Режем два узла, остальное не окупается

| узел | gzip | из них вендоры | почему |
|---|---|---|---|
| `features/entity-detail/*` (+ query-builder внутри) | 32.4 кБ | 14.1 кБ | push-экран, на первом кадре не монтируется |
| 4 экрана Budget + `ImportFlow` | 13.2 кБ | ~0.6 кБ | вкладка + разовый мастер |

Не режем — **не окупается**: settings 2.2 кБ, browser 1.8, agenda 1.6, onboarding 0.3.
Каждая граница лени стоит `Suspense`, fallback, теста и ~100 Б потерянного контекста gzip;
на этих величинах цена больше выигрыша.

Ожидание по сумме — **40–45 кБ gzip (15–17%)**, и это ожидание, а не обещание: два разреза
перекраивают общий чанк, поэтому итог обязан быть **замерен** тем же `gzip -c`, что и весь
исторический ряд в `2026-08-04-bundle-diet.md`. Число `gzip:` из вывода vite в ряд не годится
(врёт на ~1.2%).

## РЕШЕНИЕ Р2. Граница лени — в роутере, а не в самих компонентах

Ленивыми становятся **точки монтирования** в `app/router.tsx`; модули продолжают
экспортировать свои компоненты как сегодня.

Причина фактическая: `renderWithProviders` (`apps/web/src/test/harness.tsx:37-58`) не
оборачивает дерево в `<Suspense>`, а прямых рендеров кандидатов в сьюте десятки
(`ImportFlow.test.tsx:125…`, `BudgetScreen.test.tsx`, `query-form.test.tsx:23`). Ленивость
самого модуля уронила бы их все ошибкой React про отсутствие границы. Ленивость обёртки не
трогает ни один прямой рендер, а входы через `<App/>` уже асинхронные (`await waitFor`).

**Вторую границу внутри `entity-detail` не ставим.** `QueryBlockEditor` монтируется из
`DetailScreen.tsx:399`, то есть уже внутри ленивого чанка; отдельная граница ничего не
сэкономит (query-builder — эксклюзивное поддерево `DetailScreen`), но сломает синхронный
`editorField(dialog)` в `query-builder.test.tsx:68-70`.

`renderWithProviders` всё же получает `<Suspense>` — как страховку для будущих тестов, а не
ради текущих: обёртка ничего не меняет для синхронного дерева.

## РЕШЕНИЕ Р3. Fallback рисует шапку и скелетон, а не пустоту

`ScreenHeader` живёт **внутри** каждого экрана (`app/ScreenHeader.tsx:8` это документирует),
поэтому `fallback={null}` на такт убрал бы шапку — экран мигнул бы. В проекте уже есть
прецедент ровно этой формы: `entity-detail/DetailScreen.tsx:76-84` рендерит
`<ScreenHeader title="…" />` вместе со скелетоном.

Единый компонент `app/ScreenFallback.tsx`: шапка-заглушка + `<Skeleton>` в том же ритме, что
`SettingsScreen.tsx:44-49`. **Текст «Загрузка…» запрещён** — `browser.test.tsx:97-100` прямо
проверяет `queryByText(/Загрузка…/)` на отсутствие, а `ui/Skeleton.tsx` уже несёт
`role="status" aria-label="Загрузка"`.

Отдельный случай, который нельзя забыть: nav-стор персистится (`orbis:nav:v1`), поэтому при
старте приложения вершиной стека может оказаться `budget-import` — первый кадр после входа
окажется fallback'ом. Он обязан выглядеть как экран, а не как дыра.

## РЕШЕНИЕ Р4. Починка доставки чанков едет тем же заходом

Разбиение вводит новый класс отказа, которого у монолита не было: **ленивый чанк может не
загрузиться**. Сегодня это отказ в самой злой форме.

- `apps/server/src/app.ts:111-114` — на промах `/assets/xxx.js` второй `serveStatic` отдаёт
  `index.html` со статусом **200 и `text/html`**. Браузер отвергнет модуль по strict MIME,
  и в консоли будет не «файл не найден», а `Failed to fetch dynamically imported module`.
  Кейс отсутствующего ассета в `static.test.ts` не покрыт вовсе.
- Каждый деплой — новый контейнер с чистым `dist` (`render.yaml:7-13`, `Dockerfile:38`),
  персистентного диска нет: **старые чанки исчезают**.
- SW ставится с `registerType: 'autoUpdate'` → `skipWaiting` + `clientsClaim` +
  `cleanupOutdatedCaches`: новый SW активируется в уже открытой вкладке и вычищает её старый
  precache. То есть открытая вкладка теряет свои чанки штатно, а не в экзотике.

Три правки:

1. **Сервер: промах в `/assets/*` → 404.** Отдельный `app.get('/assets/*', …)` перед
   SPA-fallback, тест в `static.test.ts` на код и на то, что тело не HTML.
2. **Клиент: один автоматический перезаход.** Слушатель `vite:preloadError` (Vite эмитит его
   на `window` при провале динамического импорта): если флага в `sessionStorage` нет — ставим
   флаг и `location.reload()`; страница возьмёт свежий `index.html` с новыми именами чанков.
   Если флаг уже стоял — не перезагружаемся.
3. **ErrorBoundary вокруг `Suspense`** — экран «Не удалось загрузить экран» с кнопкой
   «Обновить» в тоне проекта (ср. `OnboardingGate.tsx:44,52`: «Не удалось загрузить
   настройки. Повторите позже.» + «Повторить»). Это ловушка для второго провала и для ошибок
   рендера ленивого поддерева; сегодня ErrorBoundary в проекте нет вовсе.

**Отклонено: автоматический reload по кругу.** Бесконечная перезагрузка при настоящей потере
сети хуже одной честной кнопки. Отсюда флаг на один заход.

## РЕШЕНИЕ Р5. Prefetch на idle — чтобы за ленивость не платил пользователь

`entity-detail` открывается тапом по сущности из обзора, повестки и чата — это частый жест,
а не редкий. Вкладка Budget тоже частая. Ленивость без подстраховки означает ожидание в
момент, когда пользователь уже нажал.

После монтирования `AppShell` — `requestIdleCallback` (с `setTimeout`-фолбэком) вызывает тот
же `import()` для `entity-detail` и `BudgetScreen`. Экспериментом проверено: повторный
`import()` из idle **не схлопывает** чанк обратно — все чанки остались байт-в-байт.

`ImportFlow` не префетчим: разовый сценарий, а его 7.7 кБ — как раз то, что незачем тянуть
всем.

**Мина, которую нельзя задеть:** статический импорт того же модуля рядом с динамическим
схлопывает чанк обратно во входной, молча и без предупреждений (проверено: `ImportFlow-*.js`
исчезал, вход рос на 22 кБ). Поэтому у ленивого модуля не должно остаться ни одного
статического импортёра — это проверяется замером, а не глазами.

## РЕШЕНИЕ Р6. Precache остаётся полным

Ленивые чанки остаются в precache. Альтернатива — `globIgnores` + `runtimeCaching` — дала бы
настоящую экономию трафика при обновлении, но урезала бы офлайн: экран, который пользователь
не открывал онлайн, офлайн не открылся бы вовсе. Для приложения с обещанием офлайн-работы
это плохой размен ради килобайтов.

Следствие записывается прямо, а не маскируется: **для установленного PWA эта работа не
экономит трафик**. Она уменьшает объём парсинга и исполнения на первом кадре и убирает из
перекачки при обновлении те чанки, которые не менялись.

## РЕШЕНИЕ Р7. Сьют стабилизируется ДО разрезов

Факт разведки: два прогона `bun run test` на одном и том же коммите дали **разные** падения
(3 упавших, затем 2) — все по таймауту ожидания, в разных файлах. Мои собственные два прогона
на том же коммите, но на незагруженной машине, дали 658/658 и затем одно падение
(`deep-link.test.tsx`, тот же класс). То есть **флак зависит от нагрузки машины**: под
параллельными сборками он был втрое чаще. Отличить регресс от шума в таком сьюте нельзя, а
`Suspense` добавляет каждому входу через `<App/>` лишний такт и флак усилит.

`configure()` в тестах нет ни разу, значит `waitFor`/`findBy` работают на дефолтном таймауте
Testing Library (**1 с**) при 57 файлах в параллель. Первая гипотеза — поднять
`asyncUtilTimeout` в `tests/setup.ts`; она **обязана быть проверена прогонами** (три подряд
до и три после), а не принята на веру. Если флак останется — искать причину дальше, а не
поднимать таймаут ещё раз: удвоение порога, которое не помогает, означает другую причину.

Это не маскировка: тест, который не дождётся никогда, упадёт и с большим порогом.

## Что НЕ входит

- **Ленивый markdown-стек (47.1 кБ)** — крупнейший оставшийся рычаг, но он нужен ленте чата
  на первом экране; ленивость даст мерцание. Разбор 2026-08-04 отверг это; появление
  prefetch'а на idle делает пересмотр осмысленным, но это отдельное UX-решение, а не эта
  работа.
- **Budget «целиком»** — невозможно (Р1).
- **Перевод чанков на runtime-кеш** (Р6).
- **Ленивость settings/browser/agenda/onboarding** — 0.3–2.2 кБ каждая.
- **Замена react на preact/compat** и прочая работа по вендорам — другой класс риска.

## Приёмка

1. `bun run test` из корня зелёный **три прогона подряд** (до работы — красный и плавающий).
   Lint зелёный.
2. Замер тем же `gzip -c`: число чанков, размер входного, размер каждого статически
   связанного с входом чанка, **сумма как начальная загрузка**, дельта против 263 909 Б.
   Ряд в `2026-08-04-bundle-diet.md` продлевается этим числом.
3. Проверка «ни одного статического импортёра у ленивого модуля» — фактом сборки: чанки
   `entity-detail`, `Budget*`, `ImportFlow` существуют отдельными файлами.
4. Тест сервера: `GET /assets/нет-такого.js` → 404, тело не `text/html`.
5. **Живой смоук** на прод-сборке: открыть сущность, вкладку Budget, экран импорта — экраны
   появляются, скелетон вместо мигания, консоль чистая; F5 на глубокой ссылке сущности;
   старт приложения с персистированным стеком `budget-import`.
6. **Смоук отказа**: удалить файл ленивого чанка из `dist` на живом стенде → сервер отвечает
   404, приложение делает один автоперезаход, второй провал даёт экран с кнопкой «Обновить».
