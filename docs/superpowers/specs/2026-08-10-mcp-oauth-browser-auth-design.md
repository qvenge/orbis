| Дата | 2026-08-10 |

| Источник | запрос владельца: «хочу аутентификацию через браузер из Claude Code через `/mcp`» |

Цель: подключение Orbis к Claude Code сводится к `claude mcp add --transport http orbis
<url>/mcp` и команде `/mcp` — вход происходит в браузере, секрет руками не переносится;
выданные доступы видны в настройках и отзываются одной кнопкой.

## Что не так сегодня (по коду, не по памяти)

`/mcp` пускает только по PAT: `apps/server/src/pat.ts` сверяет `sha256` предъявленного
токена с `ORBIS_PAT_HASH` из окружения и берёт владельца из `ORBIS_PAT_OWNER_ID`. Отсюда
три следствия:

1. **Подключение ручное.** Сырой токен печатается один раз (`scripts/issue-pat.ts`), и его
   надо самому перенести в конфиг агента заголовком.
2. **Отзыв — операция деплоя.** Сменить `ORBIS_PAT_HASH` в Render и передеплоить; отозвать
   доступ одному клиенту, не тронув остальных, нельзя — токен ровно один.
3. **Потеря невосстановима** — hash-only по построению.

При этом `apps/server/src/mcp/transport.ts:72-83` отдаёт 401 с голым
`WWW-Authenticate: Bearer` — без указания, где искать authorization server. Для MCP-клиента
это тупик: он видит «нужна авторизация», но не знает куда идти.

Проверено живьём на проде (`2026-08-09`): `POST /mcp` без токена → `401 UNAUTHORIZED` нашей
структурной формы, `/health` → `{"status":"ok"}`. Эндпоинт исправен, дело только в
отсутствии метаданных и самого authorization server.

## Чего требует спецификация

MCP 2025-06-18 (`/specification/2025-06-18/basic/authorization`) от **resource server**, то
есть от нас:

- **MUST** реализовать Protected Resource Metadata (RFC 9728) с полем `authorization_servers`;
- **MUST** в 401 отдавать `WWW-Authenticate` со ссылкой на эти метаданные;
- **MUST** проверять, что токен выпущен именно для нас (аудитория), и **MUST NOT** принимать
  чужие токены — «token passthrough» назван прямым запретом.

От **authorization server**: OAuth 2.1, метаданные RFC 8414, PKCE, ротация refresh-токенов
для публичных клиентов, точная сверка `redirect_uri`; поддержка DCR (RFC 7591) — SHOULD.

Со стороны Claude Code (`code.claude.com/docs/en/mcp`): «A custom server that returns a
`WWW-Authenticate` header pointing to its authorization server gets the same automatic
discovery as any other remote server»; вход — `/mcp` в сессии или `claude mcp login <name>`;
поддержаны DCR, `--client-id`/`--callback-port` и CIMD. Отдельно оговорено: если у сервера
задан `headers.Authorization`, при отказе клиент **не** откатывается на OAuth, а рапортует
о сбое соединения — то есть заголовочный и браузерный пути не смешиваются в одной записи
конфига, это два разных способа добавить сервер.

## РЕШЕНИЕ Р1. Три цели фазы: вход, отзыв, экран настроек

*Владелец выбрал напрямую.* Помимо самого входа фаза даёт отзыв доступа и раздел
«Подключённые агенты» в настройках со списком выданных грантов и кнопкой «Отозвать».

Это решение определяет всё остальное: одноразовость кода и отзыв невозможны без места,
где записано состояние выданного доступа.

## РЕШЕНИЕ Р2. Authorization server — сам Orbis, Supabase остаётся способом узнать владельца

Рассматривались два места.

**(а) Supabase как готовый AS.** Проба прода показала, что он **уже** отдаёт
`/auth/v1/.well-known/openid-configuration` с `oauth/authorize`, `oauth/token` и
`code_challenge_methods_supported: ["S256","plain"]`. Отклонено по двум причинам:

1. **`registration_endpoint` в метаданных отсутствует** — DCR не поддержан. Claude Code
   пришлось бы добавлять с ручным `--client-id`, предварительно заведя OAuth-приложение.
2. **Токен был бы выпущен не для нас.** Supabase выдаёт JWT с `aud: authenticated` для
   собственного API; принять его на `/mcp` — ровно тот token passthrough, который спека
   запрещает. Хуже того, это снесло бы границу, поставленную намеренно
   (`transport.ts:65-71`): сегодня Supabase-JWT на `/mcp` **не** аутентифицирует, чтобы
   владельческий токен из веб-клиента нельзя было переиспользовать под атрибуцией `agent`.

**(б) Orbis — собственный AS.** Принято. Выпускаем свои токены со своей аудиторией, DCR
поддерживаем, а Supabase остаётся тем, чем и был: способом узнать, кто сидит за браузером.
Второго логина у владельца не появляется — на экране согласия он уже залогинен.

## РЕШЕНИЕ Р3. Экран согласия — страница SPA, а не серверный HTML

После диеты auth веб-клиент держит сессию в `localStorage` под ключом `sb-<ref>-auth-token`
(формула воспроизведена в `apps/web/src/auth/config.ts`). Серверный HTML эту сессию не
видит — ему пришлось бы заводить отдельную куку и второй способ логина.

SPA видит её сразу, а `GET /oauth/authorize` уже сегодня доходит до SPA-fallback
(`apps/server/src/app.ts:114`) — отдельный серверный роут под страницу не нужен вовсе.
Незалогиненный владелец увидит обычный экран входа (`LoginScreen.tsx` — форма email +
пароль, `signInWithPassword`), после входа — согласие. Magic link здесь помянут был по
ошибке: `signInWithOtp`/`verifyOtp` в веб-клиенте отсутствуют, ссылкой входят только
операторским приёмом через админский API Supabase на смоуке.

## РЕШЕНИЕ Р4. PAT остаётся и переезжает из env в таблицу грантов

*Владелец выбрал напрямую.* `claude -p`, Agent SDK и CI интерактивный флоу не проходят —
документация Claude Code прямо отсылает за подписью в интерактивную сессию. Значит
заголовочный путь нужен.

Переезд из env в общую таблицу даёт один механизм отзыва и один экран на оба вида доступа,
а заодно снимает ограничение «ровно один PAT». `ORBIS_PAT_HASH` и `ORBIS_PAT_OWNER_ID`
после переезда уходят из Render и `render.yaml`.

## РЕШЕНИЕ Р5. Токены непрозрачные, в базе только `sha256` — не подписанный JWT

**(а) JWT с `aud`, подписанный секретом из env.** Проверяется без обращения к БД. Отклонено:
из-за Р1 отзыв всё равно требует сверки с базой на каждом вызове, поэтому выигрыш
испаряется; взамен появляется секрет подписи в Render и отзыв с задержкой до истечения
срока.

**(б) Непрозрачная случайная строка, в БД — `sha256`.** Принято. Отзыв мгновенный,
секретов в окружении не прибавляется, а контракт совпадает с тем, что PRD §9.3 уже
описывает для PAT: сервер хранит только хеш, сырой токен не восстановим. Префиксы —
`orbis_at_` (access), `orbis_rt_` (refresh), `orbis_ac_` (код), `orbis_pat_` (без изменений).

## РЕШЕНИЕ Р6. Скоупов нет — грант даёт то же, что PAT сегодня

*Владелец выбрал напрямую.* PRD §9.3 относит скоупы к Future. Разрушительные действия и
сейчас гейтит не ярлык доступа, а политика подтверждений §7.10 — batch из одиннадцати
архиваций возвращает `pending_confirmation` и ждёт владельца в чате (`mcp.test.ts:407`).
Колонка под будущие скоупы в таблице заводится, значение пока одно.

## РЕШЕНИЕ Р7. Одноразовость кода — атомарным UPDATE, а не проверкой в коде

`UPDATE agent_grants SET code_used_at = now() WHERE id = $1 AND code_used_at IS NULL
RETURNING …` — гонка двух обменов даёт строку ровно одному. Повторное предъявление
потраченного кода или ротированного refresh-токена отзывает грант целиком: по OAuth 2.1
это признак перехвата, а не невинная ошибка клиента.

**Поправка по факту реализации (Task 2).** Для кода сказанного достаточно — потраченный код
остаётся в строке с отметкой `code_used_at`. Для refresh — нет: ротация перезаписывает
`refresh_hash`, следа предъявленного токена не остаётся, и «повторный refresh гасит грант»
не срабатывает ровно в том случае, ради которого писалось. Реализатор опроверг это пробой,
а не рассуждением. Отсюда колонка `prev_refresh_hash`: при ротации текущий хеш переезжает в
неё, и предъявленный старый токен опознаётся как реплей. Гашение требует совпадения ещё и по
`client_id` — иначе сбитый конфиг одного клиента отзывал бы владельцу весь доступ.

## РЕШЕНИЕ Р8. `ORBIS_PUBLIC_URL` обязателен в production

Канонический URI ресурса (`<public>/mcp`) и база всех метаданных берутся из переменной
окружения. Выводить хост из заголовка `Host` в проде нельзя: подменённый `Host` увёл бы
клиента на чужой authorization server прямо через наши же метаданные. На локальном стенде,
где переменной нет, фолбэк на `Host` допустим — там нет ни владельца, ни данных.

## Данные

Две новые таблицы. PRD §4 фиксирует ровно восемь — правка PRD обязательна, решение
журнала — **D34** (последний занятый в `04-decision-log.md` — D33).

**`oauth_clients`** — регистрации DCR:

| Поле | Тип | Смысл |
|---|---|---|
| `client_id` | text PK | выданный при регистрации |
| `client_name` | text | из запроса DCR — то, что владелец увидит на экране согласия |
| `redirect_uris` | text[] | сверяются точным совпадением |
| `created_at` | timestamptz | |

`client_secret` не выдаём: Claude Code — публичный клиент, защита строится на PKCE.

**`agent_grants`** — весь жизненный цикл доступа одной строкой:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid PK | |
| `owner_id` | uuid | владелец, от чьего имени действует агент |
| `client_id` | text NULL | NULL у PAT |
| `kind` | text | `oauth` \| `pat` |
| `label` | text | для PAT — назначение («CI»), для OAuth — `client_name` на момент выдачи |
| `scope` | text | под Р6 одно значение; колонка — задел |
| `code_hash`, `code_challenge`, `code_expires_at`, `code_used_at`, `redirect_uri` | | одноразовый код (только у `oauth`) |
| `access_hash`, `access_expires_at` | | текущий access-токен |
| `refresh_hash`, `refresh_expires_at` | | текущий refresh (ротируется) |
| `prev_refresh_hash` | | след предыдущего refresh — без него детект реплея из Р7 невыполним (см. ниже) |
| `created_at`, `last_used_at`, `revoked_at` | timestamptz | питают экран настроек |

Сроки: access — 1 час, refresh — 30 дней с ротацией при каждом обмене, код — 60 секунд.

**RLS** по образцу `apps/server/src/db/migrations/0001_rls_and_indexes.sql` (ENABLE +
FORCE, политики через `(SELECT auth.uid())`). Тонкость этой таблицы: аутентификация ищет
строку по хешу **до** того, как владелец известен, а `withIdentity` ставит identity только
когда владелец уже есть (`db/with-identity.ts`). Поэтому политик две: владельцу под ролью
`authenticated` — свои строки (это питает экран настроек и отзыв), роли `orbis_app` —
SELECT/UPDATE для лукапа по хешу и отметки `last_used_at`. `scripts/test-rls.ts`
пополняется проверками «чужой владелец не видит чужие гранты» и «anon не видит ничего».

## Поверхности

| Метод и путь | Кто зовёт | Назначение |
|---|---|---|
| `GET /.well-known/oauth-protected-resource[/mcp]` | MCP-клиент | PRM: `resource` + `authorization_servers` |
| `GET /.well-known/oauth-authorization-server` | MCP-клиент | метаданные AS (RFC 8414) |
| `POST /oauth/register` | MCP-клиент | DCR: `redirect_uris`, `client_name` → `client_id` |
| `GET /oauth/authorize` | браузер владельца | страница SPA (серверного роута нет — SPA-fallback) |
| `POST /oauth/token` | MCP-клиент | обмен кода и refresh, `application/x-www-form-urlencoded` |
| tRPC `oauth.describeRequest` | SPA | проверить параметры до показа кнопки, вернуть имя клиента |
| tRPC `oauth.consent` | SPA | выдать код, вернуть URL редиректа |
| tRPC `oauth.listGrants` / `oauth.revokeGrant` | SPA | экран «Подключённые агенты» |

Все новые серверные роуты регистрируются **до** статики — порядок в `app.ts` определяет
приоритет, и это уже зафиксировано комментарием в его шапке.

Поток: 401 с `resource_metadata` → PRM → метаданные AS → DCR → браузер на `/oauth/authorize`
с PKCE-challenge, `state` и `resource` → согласие владельца → редирект на
`http://localhost:PORT/callback?code=…&state=…` → `POST /oauth/token` → `Bearer` в `/mcp`.
Дальше ничего не меняется: `dispatchTool` с `actorKind: 'agent'`, `source: 'mcp'`, аудит в
глобальный тред владельца, политика §7.10, rate-гейт `agents.requests_per_day`.

## Проверки на входе

`redirect_uri` — точное совпадение с зарегистрированным, схема только `http://localhost:*`
или `https`. PKCE — только `S256`; `plain` отвергается, хотя RFC его допускает. `resource`
сверяется с каноническим URI, иначе `invalid_target`. Ошибки OAuth-эндпоинтов отдаются
формой `{ error, error_description }` с кодами спеки; структурная форма `{ error: { code } }`
остаётся у `/mcp` и tRPC — это разные протоколы, смешивать их нельзя.

## Риски

- **Публичные эндпоинты растут.** `/oauth/register` открыт всему интернету по спеке DCR;
  без ограничений это дописывание строк в таблицу кем угодно. Регистрация ничего не даёт
  без согласия владельца, но запись мусора возможна — нужен потолок (rate-гейт по IP либо
  срок жизни неиспользованных регистраций). Решается на этапе задачи DCR.
- **Общий локальный Supabase.** Тесты двух параллельных сессий дерутся за одну базу через
  `truncateAll`; прогоны разносятся по времени.
- **Cold start Render free** (~минута) заметен на первом шаге браузерного входа — это
  латентность, не ошибка.
