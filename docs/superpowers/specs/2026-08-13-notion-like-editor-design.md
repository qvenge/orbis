| Поле | Значение |

| Ветка | создаётся при старте реализации, от свежего `main` |
| Источник | запрос владельца: «UI/UX работы с текстом как в Notion» |

## Что установила разведка

**`body` — источник правды сразу для двоих.** Сервер извлекает `body_refs` регэкспом из
текста при каждом create/update (`apps/server/src/executor/normalize.ts:14`), и на этом стоят
backlinks. Клиент держит КОПИЮ того же регэкспа (`apps/web/src/lib/markdown/Markdown.tsx:16`)
с комментарием: расхождение «соврало бы про связи записи». Модель пишет тем же текстом через
`entity_update{body}` (`packages/shared/src/contracts/tools.ts:27`).

**Граница режимов видна намеренно.** Просмотр — `Markdown` + живые `{{query:…}}`-виджеты
вперемежку через `bodySegments`; правка — голая `<textarea>` со всем текстом, виджеты уезжают
списком под неё (`apps/web/src/features/entity-detail/DetailScreen.tsx:298-323`). При входе в
правку чипы сущностей превращаются в `[[entity:uuid]]`, смарт-лист — в фигурные скобки. Это и
есть «схлопывание», которое требуется убрать.

**Байт-в-байт — действующий инвариант текстового хранения.** `replaceQueryBlock`
(`apps/web/src/features/browser/query.ts:84`) правит РОВНО подстроку блока срезами по длинам
обёртки, потому что «пересборка схлопнула бы многострочные блоки сидированных smart lists».

**Вставить смарт-лист из UI сегодня невозможно.** `QueryBlockEditor` открывается только на уже
существующем блоке (`onConfigure`); новый заводится лишь набором `{{query:` руками.

**Поиск сущностей — только по целому слову.** `search=` компилируется в
`plainto_tsquery('simple', …)` (`apps/server/src/query/compile.ts:226`): ни префиксов, ни
стемминга. Пикер блокировок признаёт это подсказкой «Поиск от 2 символов и по целому слову»
(`apps/web/src/features/entity-detail/Blocks.tsx:254`).

**Запись идёт единственным путём.** Роутер `entity` — «ТОЛЬКО трансляция», вся мутация через
`executor` с пятью стадиями, ajv-валидацией аспектов, инвариантами графа
(`apps/server/src/executor/invariants.ts`), append-only журналом в `chat_messages` и Undo через
inverse в том же tx (`apps/server/src/executor/undo.ts`). Каждое сохранение из detail дергает
`invalidateGraph` (`apps/web/src/features/entity-detail/useEntityDetail.ts:75`).

**Multi-user уже спроектирован как отложенный.** D11 (`docs/prd/04-decision-log.md:102`):
схема per-owner, workspace'ы и роли — Future, но с чек-листом из пяти пунктов, включая «RLS-
политики генерируются из одного шаблона — переход owner→membership правится в одном месте».
Принцип, которому подчинён весь этот дизайн, — оттуда же: «откладывать инфраструктуру можно,
но не ценой архитектуры, которую потом придётся переписывать».

**Проверено по докам библиотек.**
- Tiptap v3: markdown — официальный API (`editor.markdown.parse` / `.serialize`), кастомная
  нода объявляет `parseMarkdown` и `renderMarkdown`. Drag Handle, Table Kit, Bubble/Floating
  menu, Placeholder, List Kit, UniqueID, Collaboration — без ценовых тегов в листинге доков,
  то есть MIT; платны только Comments, AI, Import/Export docx, Pages, Version. **UniqueID в v3
  живёт в основном неймспейсе (`@tiptap/extension-unique-id`) — в v2 он был Pro; подтвердить
  при установке.**
- BlockNote: markdown-конверсия называется `blocksToMarkdownLossy`, документация прямо
  указывает использовать JSON для сериализации без потерь. Для Orbis, где markdown — язык
  общения с моделью, lossy на входе неприемлем. **Отклонён.**
- Lexical: `@lexical/yjs` официален, есть задокументированный headless-рецепт (`createHeadlessEditor`
  + `createBinding`). Против: markdown — самописные transformers, ключи нод не переживают
  сессию, и стабильную идентичность блоков пришлось бы строить самим.

## РЕШЕНИЕ Р1. Правда — структурная; markdown становится проекцией

Миграция `0007` добавляет `body_doc jsonb` **nullable**: `NULL` означает «тело ещё не
сконвертировано». Бэкфилл — скриптом через `bun scripts/ops.ts`; всё, что он не догнал, сервер
конвертирует лениво при первом чтении или записи. Forward-only, expand/contract.

`entities.body` остаётся `text NOT NULL` и становится **производной**. Это несущее: FTS-поиск,
фильтры Browser, промпт, экспорт, MCP-контракт `entity_update{body}` и бейджи pinned-сущностей
(`firstQueryBlock` по markdown) не меняются ни строкой. Единственный читатель `body`, который
меняется, — извлечение `body_refs`; оно переезжает на обход дерева отдельным решением Р6.

Направление конверсии:

- пришёл `bodyDoc` (UI) → сервер сериализует в `body`;
- пришёл `body` (модель, MCP, импорт) → сервер парсит в `body_doc`.

Обе конверсии — **общий код в `@orbis/shared`**. Два описания схемы разъехались бы так же, как
чуть не разъехались `BODY_REFS_RE` и `ENTITY_REF_RE`; один модуль на клиент и сервер.

**Почему не оставить markdown правдой.** Тогда блочные id (Р4) живут только в памяти вкладки:
записать их в текст, не замусорив то, что читает модель, нельзя. А переход к соредактированию
(Р10) становится разворотом направления правды плюс миграцией всех тел — то есть ровно той
переделкой, которой этот дизайн избегает.

## РЕШЕНИЕ Р2. Редактор — Tiptap (ProseMirror)

Выбран по трём причинам, каждая проверена по докам: markdown у него официальный и
расширяемый на уровне ноды (а markdown здесь не декорация, а интерфейс модели); UniqueID даёт
готовую стабильную идентичность блоков, на которой стоит будущий агентский контракт;
`y-prosemirror` — самая обкатанная CRDT-связка, что важно для Р10.

**Отклонённые альтернативы.** BlockNote — lossy markdown в обе стороны. Lexical — markdown
беднее, идентичность блоков пришлось бы строить самим. CodeMirror 6 с живым просмотром
(декорации поверх текста, как Obsidian Live Preview) — рассмотрен всерьёз и отклонён владельцем:
он честнее к тексту, но его потолок — не WYSIWYG, потому что каретка всегда стоит в символах, и
таблицы, вложенные структуры и перетаскивание блоков остаются работой с разметкой.

## РЕШЕНИЕ Р3. Схема документа: стандартный набор плюс три свои ноды

Стандартное: абзацы, заголовки, маркированные и нумерованные списки, задачи-чеклисты, цитаты,
блоки кода, разделитель, таблицы, переносы. Marks: жирный, курсив, зачёркнутый, код, ссылка.

Свои:

| Нода | Вид | Атрибуты | Markdown-проекция |
|---|---|---|---|
| `entity` | inline, atom | `{ id, label }` | `[[entity:uuid\|подпись]]` |
| `queryBlock` | block, atom | `{ query }` | `{{query:…}}` |
| `raw` | block | `{ markdown }` | дословно исходный кусок |

`raw` — страховка от тихой потери: то, что схема не разобрала, сохраняется как есть, а не
исчезает. Для приложения-памяти тихая потеря содержимого — худший класс ошибок, и терпеть её
нельзя даже ценой некрасивого блока.

Проекция ссылки и блока — существующий синтаксис: сервер, промпт и MCP продолжают понимать
тело без единой правки.

## РЕШЕНИЕ Р4. Стабильные id блоков — с первого дня

`@tiptap/extension-unique-id` вешает `id` на блочные ноды. Сегодня им никто не пользуется.

**Зачем тогда сейчас.** Завтра на них стоит агентский контракт: `body_replace_block(id, md)`
вместо перезаписи тела целиком (Р10). Добавить id потом — мигрировать все документы; добавить
сегодня — один параметр расширения.

В markdown-проекцию id **не печатаются** — модель продолжает читать чистый текст. Следствие,
принятое сознательно: пока модель пишет `body` целиком, парсинг выдаёт блокам новые id. Сшивать
их по содержимому — та самая placeholder-инфраструктура, которую запрещает D11: когда агент
станет блочным, он и будет писать блоками.

## РЕШЕНИЕ Р5. Путь записи не двоится: `bodyDoc` едет через executor

Контракт `entity_update` расширяется **одним** опциональным полем `bodyDoc` (JSON). Правила:

- `body` и `bodyDoc` одновременно — ошибка валидации;
- `expectedUpdatedAt` обязателен при любом из них, ровно как сегодня при `body`;
- конверсия встаёт перед стадией записи; стадии, ajv-валидация, инварианты графа, журнал и
  Undo не трогаются.

Отдельного эндпоинта «сохранить документ» не заводим. Второй путь записи пришлось бы потом
сливать с первым — и это была бы задача труднее, чем слияние текстов.

**Цена, которую надо знать заранее:** inverse для Undo станет хранить прежний `body_doc` вместо
прежней строки, и журнал в `chat_messages.metadata` потяжелеет примерно вдвое на правках тела.

## РЕШЕНИЕ Р6. `body_refs` считаются по дереву — это изменение поведения

Сейчас `extractBodyRefs` бежит регэкспом по сырому тексту и считает связью в том числе
`[[entity:…]]` внутри блока кода — наивность, зафиксированная в комментарии как намеренная
(«расхождение тут было бы хуже одинаковой наивности»).

Со структурной правдой связью считается **настоящая нода `entity`**. Рендер и граф сходятся по
построению — цель, ради которой и держалась зеркальная пара регэкспов. Цена: у записей, где
ссылка стоит внутри кода, backlink пропадёт. Случай редкий, но это изменение поведения, а не
рефакторинг, и оно фиксируется здесь явно.

`linkifyEntityRefs` и `ENTITY_REF_RE` в `Markdown.tsx` **остаются**: чат по-прежнему рендерит
ответы модели markdown'ом, и там ссылки текстовые.

## РЕШЕНИЕ Р7. Префиксный поиск — отдельной процедурой, грамматику не трогаем

Новая процедура `entity.suggest`: поиск по префиксу заголовка. Trigram-индекс на `title`
(`pg_trgm`) едет **той же миграцией `0007`**, что и `body_doc`: две миграции подряд ради одной
работы — лишний шаг в прод-процедуре, а откатывать их всё равно нечем (forward-only).

Грамматику `search=` **не меняем**: там семантика целого слова осмысленна и на неё завязаны
сидированные смарт-листы. Без префиксного поиска slash-меню бесполезно — набор `/куп` не нашёл
бы «Купить кроссовки».

Пикер блокировок переходит на ту же процедуру, и извиняющаяся подсказка «Поиск от 2 символов и
по целому слову» исчезает.

## РЕШЕНИЕ Р8. Экран — три таба: Сущность · Связи · Тред

«Сущность» становится чистым документом: emoji, заголовок (`NativeRow`), тело, карточки
аспектов. «Связи» забирает `Subtasks`, `Blocks`, `Backlinks` — данные приезжают тем же
`entity.get(include:['relations','backlinks'])`, ни одного нового запроса. «Тред» без изменений.

§3.5 PRD (`docs/prd/02-core-os.md:413`) нормирует секции 1–8 одним списком на вкладке
«Сущность» — правится в этой же работе. Документ, описывающий несуществующую раскладку, хуже
правки.

## РЕШЕНИЕ Р9. Пишем по паузе; 409 остаётся

Сохранение — по паузе в наборе ~2 с, плюс принудительно на уходе фокуса и на размонтировании.
Мутация уходит только при реальном изменении документа. Причина сдержанности конкретна:
`onSettled` зовёт `invalidateGraph(utils)` — инвалидацию всего графа, и при агрессивном
автосохранении она била бы по кэшу каждые несколько нажатий.

Шлём `bodyDoc` + `expectedUpdatedAt` с точной строкой `updatedAt` из кэша (как `saveBody`
сегодня). `applyPatch` расширяется на `bodyDoc`, и там же клиент кладёт в кэш markdown-проекцию,
посчитанную тем же сериализатором.

**409 остаётся как есть**: баннер «Изменено в другом месте — обновите» и кнопка «Обновить».
Документ в редакторе при конфликте не подменяется — §5.2 предлагает «повторить вручную», значит
повторять должно быть откуда.

Свежий серверный документ не подменяет содержимое, пока редактор в фокусе или есть
несохранённые изменения. Правило `key={entity.id}`, а не по `updatedAt`, сохраняется буквально:
ремоунт по ключу стирал бы набранное за время запроса.

`Ctrl+Z` — история редактора, не журнальный Undo. Ручную правку отменяют там же, где сделали;
«отмени последнее» остаётся про действия агента.

## РЕШЕНИЕ Р10. Швы под будущее заложены; инфраструктура не строится

Владелец подтвердил: совместное редактирование людьми И агентами будет обязательно. Здесь оно
**не реализуется**, но конструкция обязана его пережить без разворотов.

**Заложено этой работой:**

1. направление правды `документ → markdown` (Р1) — переворачивать потом было бы переписыванием
   обоих концов;
2. структурное хранение `body_doc` — превращается в Y.Doc готовой утилитой
   `prosemirrorJSONToYDoc`, схема нод при этом та же;
3. стабильные id блоков (Р4) — на них ляжет блочный контракт агента;
4. единственный путь записи через executor (Р5) — иначе к моменту CRDT сливать пришлось бы два
   пути записи, а не два текста;
5. общая схема документа в `@orbis/shared` — клиент, сервер и будущий агентский применятель
   понимают документ одинаково.

**Сознательно НЕ строится:** Y.js, WebSocket, Hocuspocus, awareness, курсоры присутствия;
membership и роли (D11); блочные инструменты модели (`body_replace_block` и родня); атрибуция
авторов; комментарии. `expectedUpdatedAt` с 409 остаётся нетронутым — полумеры вокруг конфликтов
сейчас только помешали бы снять их нормально потом.

**Проверка на отсутствие разворотов.** Переход к CRDT: `body_doc jsonb` → Y.Doc, схема та же,
id на месте, контракты те же. Агентские блочные инструменты: чистое добавление, id уже есть.
Люди: правило в `onAuthenticate` плюс RLS-шаблон из чек-листа D11. Ни один шаг не требует
переделать сделанное здесь.

## Состав редактора

- **Режим один.** `BodySection` с `editing`, `startEditing` и кнопкой «Редактировать» уходит
  целиком.
- **Slash-меню** (`@tiptap/suggestion`): заголовки, списки, задача, цитата, код, таблица,
  разделитель + «Смарт-лист» (открывает существующий `QueryBlockEditor` и вставляет
  `queryBlock` в каретку), «Ссылка на сущность», «Создать сущность» с подстановкой набранного
  текста в заголовок.
- **`@`** — упоминание сущности тем же механизмом и тем же поиском (Р7).
- **Чип сущности** (`entity` NodeView): актуальный заголовок из `entity.get` по id, иконка
  статуса, зачёркивание у закрытых задач. Клик — `openEntity`; Ctrl/Cmd/Shift-клик и средняя
  кнопка остаются штатными жестами браузера (`Markdown.tsx:62` — поведение терять нельзя).
- **`queryBlock` NodeView** — существующий `QueryBlock`; «Настроить» открывает существующий
  `QueryBlockEditor`. Правка блока становится правкой атрибута ноды: `replaceQueryBlock` и
  оптимистичная блокировка по номеру блока («Блок изменился в другом месте») исчезают.
  `bodySegments` / `queryBlocks` / `firstQueryBlock` остаются — они читают проекцию и питают
  бейджи pinned-сущностей.
- **Bubble-меню** по выделению, **drag handle** для перетаскивания блоков, плейсхолдер
  «Заметки…».
- **Markdown-тумблер** — пункт меню ⋮: показывает проекцию, правит текстом, на выходе парсит
  обратно. Не распарсилось — не сохраняем и говорим об этом.
- **Мобильный**: `/` работает и там, основной вход — кнопка «+» в панели над клавиатурой;
  drag handle по долгому нажатию.
- **Вес**: редактор теперь и есть просмотр, значит грузится при каждом открытии сущности и бьёт
  по достигнутым −18.7% бандла. Точка для двухфазного монтирования (первый кадр — нынешний
  `Markdown`, уже в бандле ради чата; редактор встаёт следом) закладывается, но **включается
  только по результату замера** на спайке.

**Необязательное, режется первым при нехватке объёма:** карточка сущности по наведению на чип.

## Спайк — до плана

Три замера, день максимум:

1. **Round-trip корпуса.** Снять `body` всех сущностей с прода (`ops.ts`), прогнать
   `serialize(parse(x))`, разобрать диффы. Результат — точный список нод, которые надо
   доописать, и подтверждение, что `raw` покрывает остальное.
2. **Вес чанка редактора** в gzip — от него зависит, нужно ли двухфазное монтирование.
3. **Схема и markdown-парсер на Bun без DOM.** Сервер обязан парсить текст модели в документ.
   Если Tiptap не заводится headless — запасной путь есть (документ пересобирается лениво при
   первом открытии в UI), но он некрасив, и знать про него надо до плана.

## Что НЕ входит

- Совместное редактирование, присутствие, курсоры, атрибуция авторов, комментарии (Р10).
- Membership, workspace'ы, роли (D11).
- Блочные инструменты для модели; контракт `entity_update{body}` остаётся строковым.
- Вложенные страницы, callout/toggle-блоки, «unlinked mentions», вставка ответа модели прямо в
  текст.
- Правка тегов и emoji на месте, кнопка «+аспект» — известные долги §3.5, к этой работе
  отношения не имеют.

## Приёмка

1. Тело записи правится без смены режима: чипы сущностей и виджеты смарт-листов остаются
   собой, пока идёт набор.
2. `/` открывает меню с поиском; поиск находит по префиксу заголовка.
3. Смарт-лист вставляется из UI в позицию каретки и настраивается на месте.
4. Ссылка на сущность вставляется через `/` и через `@`; чип показывает актуальный заголовок и
   статус; клик открывает сущность в текущей вкладке, Ctrl/Cmd-клик — в новой.
5. Тумблер markdown показывает ровно то, что лежит в `body`, и возвращает правку обратно в
   документ; неразбираемый текст не сохраняется молча.
6. Таб «Связи» показывает подзадачи, блокировки и backlinks; новых запросов не появилось.
7. Корпус реальных тел с прода переживает round-trip; расхождения либо объяснены `raw`, либо
   отсутствуют.
8. `body` в базе остаётся валидным markdown'ом: FTS-поиск, бейджи pinned-сущностей, промпт и
   MCP работают без правок.
9. Сохранение уходит по паузе и на уходе фокуса, 409 показывает баннер и не теряет черновик.
10. Сьюты web и server зелёные; страж ленивых чанков в CI не сломан.
