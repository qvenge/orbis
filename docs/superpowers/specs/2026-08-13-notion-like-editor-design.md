## Что установила разведка

**`body` — источник правды сразу для двоих.** Сервер извлекает `body_refs` регэкспом из
текста при каждом create/update (`apps/server/src/executor/normalize.ts:14`), и на этом стоят
backlinks. Клиент держит КОПИЮ того же регэкспа (`apps/web/src/lib/markdown/Markdown.tsx:16`)
с комментарием: расхождение «соврало бы про связи записи». Модель пишет тем же текстом через
`entity_update{body}` (`packages/shared/src/contracts/tools.ts:27`).

**Граница режимов видна намеренно.** Просмотр — `Markdown` + живые `{{query:…}}`-виджеты
вперемежку через `bodySegments`; правка — голая `<textarea>` со всем текстом, виджеты уезжают
списком под неё (`apps/web/src/features/entity-detail/DetailScreen.tsx:298-323`). При входе в
правку чипы сущностей превращаются в `[[entity:uuid]]`, смарт-лист — в фигурные скобки. Это и
есть «схлопывание», которое требуется убрать.

**Байт-в-байт — не пожелание, а инвариант с тестом.** Тела пяти сидированных смарт-листов
(`apps/server/src/seed/smart-lists.ts`) взяты из §3.3 PRD ДОСЛОВНО — с переносами строк и
девятипробельными отступами continuation-строк внутри `{{query:…}}`; `onboarding.test.ts:215`
сверяет их с markdown-блоками PRD по порядку. Тем же инвариантом объясняется устройство
`replaceQueryBlock` (`apps/web/src/features/browser/query.ts:84`): он правит РОВНО подстроку
блока срезами по длинам обёртки, потому что «пересборка схлопнула бы многострочные блоки».

**Вставить смарт-лист из UI сегодня невозможно.** `QueryBlockEditor` открывается только на уже
существующем блоке (`onConfigure`); новый заводится лишь набором `{{query:` руками.

**Поиск сущностей — только по целому слову.** `search=` компилируется в
`plainto_tsquery('simple', …)` (`apps/server/src/query/compile.ts:226`). Пикер блокировок
признаёт это подсказкой «Поиск от 2 символов и по целому слову»
(`apps/web/src/features/entity-detail/Blocks.tsx:254`).

**Заголовки связанных сущностей резолвятся по одному.** `Blocks.tsx:68` берёт их через
`trpc.useQueries` с per-id `entity.get` — там списки короткие; в теле записи ссылок может быть
много.

**`body` едет в КАЖДОМ ответе.** Wire-форма `entitySchema` всегда несёт `body`, `include`
управляет лишь дополнительными секциями (`apps/server/src/entity-read.ts:4`).

**Retry-буфер существует, но не для правок.** `apps/web/src/state/retry.ts` держит очередь в
localStorage и принимает ТОЛЬКО `entity.create` от fast-path; §2.6 PRD: «Fast-path работает без
сети как обычно — он единственный, кто пишет в буфер».

**Тесты web гоняются в jsdom** (`apps/web/vite.config.ts`), а ProseMirror опирается на
`Selection`, `Range` и contenteditable, которые там неполны.

**Запись идёт единственным путём.** Роутер `entity` — «ТОЛЬКО трансляция», вся мутация через
`executor`: пять стадий, ajv-валидация аспектов, инварианты графа
(`apps/server/src/executor/invariants.ts`), append-only журнал в `chat_messages`, Undo через
inverse в том же tx (`apps/server/src/executor/undo.ts`). Каждое сохранение из detail дергает
`invalidateGraph` (`apps/web/src/features/entity-detail/useEntityDetail.ts:75`).

**Multi-user уже спроектирован как отложенный.** D11 (`docs/prd/04-decision-log.md:102`):
схема per-owner, workspace'ы и роли — Future, но с чек-листом из пяти пунктов, включая «RLS-
политики генерируются из одного шаблона — переход owner→membership правится в одном месте».
Принцип, которому подчинён весь этот дизайн, — оттуда же: «откладывать инфраструктуру можно,
но не ценой архитектуры, которую потом придётся переписывать».

**Проверено по докам библиотек.**
- Tiptap v3: markdown — официальный API (`editor.markdown.parse` / `.serialize`), кастомная
  нода объявляет `parseMarkdown` и `renderMarkdown`. Drag Handle, Table Kit, Bubble/Floating
  menu, Placeholder, List Kit, UniqueID, Collaboration — без ценовых тегов в листинге доков,
  то есть MIT; платны только Comments, AI, Import/Export docx, Pages, Version. **UniqueID в v3
  живёт в основном неймспейсе (`@tiptap/extension-unique-id`) — в v2 он был Pro; подтвердить
  при установке.**
- BlockNote: markdown-конверсия называется `blocksToMarkdownLossy`, документация прямо
  указывает использовать JSON для сериализации без потерь. Для Orbis, где markdown — язык
  общения с моделью, lossy на входе неприемлем. **Отклонён.**
- Lexical: `@lexical/yjs` официален, есть задокументированный headless-рецепт. Против: markdown
  — самописные transformers, ключи нод не переживают сессию, стабильную идентичность блоков
  пришлось бы строить самим. **Отклонён.**

## РЕШЕНИЕ Р1. Правда — структурная; markdown остаётся аварийным дублем

Миграция `0007` добавляет `body_doc jsonb` **nullable**: `NULL` означает «тело ещё не
сконвертировано». Бэкфилл — скриптом через `bun scripts/ops.ts`; всё, что он не догнал, сервер
конвертирует лениво при первом чтении или записи. Forward-only, expand/contract. Той же
миграцией едет trigram-индекс для Р8: две миграции подряд ради одной работы — лишний шаг в
прод-процедуре, а откатывать их всё равно нечем.

Хранится **`{ v: <версия схемы>, doc: <ProseMirror JSON> }`**, а не голый документ.

`entities.body` остаётся `text NOT NULL` и становится **производной**. FTS-поиск, фильтры
Browser, промпт, экспорт, MCP-контракт `entity_update{body}` и бейджи pinned-сущностей
(`firstQueryBlock` по markdown) не меняются ни строкой. Единственный меняющийся читатель `body`
— извлечение `body_refs` (Р7).

**Почему markdown не выбрасывается, хотя правда уже структурная.** ProseMirror при загрузке
документа **молча выбрасывает узлы, которых нет в текущей схеме**. Для приложения-памяти это
худший класс ошибки: добавили ноду, откатили релиз — часть содержимого исчезла без следа.
Поэтому `body` — не «проекция ради совместимости», а **аварийный дубль**, и правило разрешения
записывается явно:

1. `body_doc` есть и его версия схемы понятна текущей сборке → правда в нём;
2. версия старше → прогоняются миграции документа до текущей;
3. версия незнакома (откат релиза) или документ не грузится → **документ пересобирается из
   `body`**, о чём пользователь извещается.

Худший исход деградации — потеря блочных id и части оформления, но **не текста**.

**Отклонённая альтернатива: хранить сразу Y.Doc (бинарём).** Тогда переход к соредактированию
не потребовал бы ни одной миграции формата. Отклонено: Y.Doc непрозрачен для SQL и
jsonb-операторов (ни посмотреть, ни запросить), тяжелее в чтении, и требует yjs на сервере уже
сегодня — а экономит ровно одну детерминированную миграцию `prosemirrorJSONToYDoc`. Это
инфраструктура ради будущего, запрещённая D11.

## РЕШЕНИЕ Р2. Редактор — Tiptap (ProseMirror)

Три причины, каждая проверена по докам: markdown официален и расширяем **на уровне ноды**
(а markdown здесь не декорация, а интерфейс модели); UniqueID даёт готовую стабильную
идентичность блоков, на которой стоит будущий агентский контракт; `y-prosemirror` — самая
обкатанная CRDT-связка.

**Отклонено, помимо BlockNote и Lexical:** CodeMirror 6 с живым просмотром (декорации поверх
текста, как Obsidian Live Preview). Рассмотрен всерьёз: он честнее к тексту и дал бы
markdown-тумблер даром. Отклонён владельцем — его потолок не WYSIWYG по устройству: каретка
всегда стоит в символах, поэтому таблицы, вложенные структуры и перетаскивание блоков остаются
работой с разметкой.

## РЕШЕНИЕ Р3. Схема документа: узел сам знает свой markdown

Стандартное: абзацы, заголовки, маркированные и нумерованные списки, задачи-чеклисты, цитаты,
блоки кода, разделитель, таблицы, переносы. Marks: жирный, курсив, зачёркнутый, код, ссылка.

Свои ноды:

| Нода | Вид | Атрибуты | Markdown-проекция |
|---|---|---|---|
| `entity` | inline, atom | `{ id, label }` | `[[entity:uuid\|подпись]]` |
| `queryBlock` | block, atom | `{ query }` (дословно, см. Р4) | `{{query:…}}` |
| `raw` | block | `{ markdown }` | дословно исходный кусок |

`raw` — страховка от тихой потери: непонятое схемой сохраняется как есть. В редакторе
показывается блоком кода с пометкой «не разобрано» и правится текстом.

**Как `raw` возникает (решение владельца 2026-08-13, после ревью плана).** Своего парсера у
него нет и быть не может: чтобы поймать «непонятое», нужно знать заранее, чего именно мы не
знаем. Поэтому механизм — **сверка round-trip при конверсии**: `parseBody` сериализует
результат обратно и сравнивает с исходником; **не сошлось — весь текст кладётся в один
`raw`-блок дословно**.

Проверено фактом: без такой сверки сноска GFM `текст[^1]` + `[^1]: сноска` превращается в
`текст[^1](сноска)` — определение исчезает. HTML в тексте экранируется. Схема беднее markdown, и
список «чего она не знает» неизвестен по построению.

Цена решения: запись с неподдерживаемой конструкцией открывается одним неразобранным блоком и
правится через markdown-тумблер, пока конструкция не будет добавлена в схему. Владелец выбрал
это против альтернативы «принять потери и записать в границы»: для приложения-памяти
«сохранили дословно, но некрасиво» лучше, чем «молча переписали».

> **ФАКТ СПАЙКА.** Необходимость `raw` подтверждена, а не предположена: в прогоне без
> `@tiptap/extension-table` таблица GFM превратилась в **пустую строку** — не в текст, не в
> искажённую разметку, а в ничто. Отдельно выяснилось, что чеклисты (`- [ ]`) **не входят** в
> StarterKit: нужны `@tiptap/extension-list` (TaskList/TaskItem) и `@tiptap/extension-table`.

**Принцип, ради которого всё это и делается: сериализация объявляется НА НОДЕ**
(`parseMarkdown`/`renderMarkdown`), а схема живёт в `@orbis/shared`. Тогда синтаксис Orbis —
это сумма нод, а не набор регэкспов по репозиторию. Сегодня знание о `[[entity:]]` живёт в двух
местах (серверный и клиентский регэкспы, которые держатся вместе только комментарием), о
`{{query:}}` — в трёх (`bodySegments`, `replaceQueryBlock`, серверный парсер грамматики). После
работы описание одно, и добавить блок в будущем = добавить один файл.

**Подпись в ссылке обновляется при сериализации.** `[[entity:uuid|подпись]]` вморожена в текст,
а чип показывает актуальный заголовок. Если подпись не обновлять, markdown — то есть ровно то,
что читает модель, — врёт про имена тем сильнее, чем дольше живёт запись. Заголовок неизвестен
(сущность удалена или недоступна) → прежняя подпись сохраняется.

## РЕШЕНИЕ Р4. Содержимое `{{query:…}}` хранится дословно

Атрибут `query` несёт содержимое блока **байт-в-байт**, включая переносы строк и отступы
continuation-строк, а не тримленным.

Иначе первое же сохранение Daily Planning схлопнет три многострочных блока в одну строку и
уронит `onboarding.test.ts` — тот самый инвариант байт-в-байт из §3.3 PRD. Этот тест, кстати,
и есть готовая проверка round-trip на самых злых телах в системе: сидированные списки
пересобираются точно или тест падает.

Редактор блока (`QueryBlockEditor`) по-прежнему показывает тримленный текст — то же, что видит
парсер грамматики, — а обрамляющие пробелы сохраняются при записи, ровно как сегодня делает
`replaceQueryBlock`.

> **ФАКТ СПАЙКА: инвариант держится, при двух условиях.** Все пять сидированных тел проходят
> round-trip буква в букву, идемпотентность — 20 из 20. Условия, добытые ошибками в пробе:
> 1. `renderMarkdown` ноды возвращает блок **без хвостовых переносов** — разделитель между
>    блоками ставит сериализатор, и свой `\n\n` давал двойной;
> 2. `start` токенизатора обязан искать **полное** совпадение обёртки, а не подстроку
>    `{{query:` — иначе незакрытая обёртка режет абзац пополам.

## РЕШЕНИЕ Р5. Стабильные id блоков — с первого дня

`@tiptap/extension-unique-id` вешает `id` на блочные ноды. Сегодня им никто не пользуется.

**Зачем сейчас.** Завтра на них стоит агентский контракт: `body_replace_block(id, md)` вместо
перезаписи тела целиком (Р13). Добавить id потом — мигрировать все документы; добавить сегодня
— один параметр расширения.

В markdown-проекцию id **не печатаются** — модель продолжает читать чистый текст. Следствие,
принятое сознательно: пока модель пишет `body` целиком, парсинг выдаёт блокам новые id. Сшивать
их по содержимому — placeholder-инфраструктура, запрещённая D11: когда агент станет блочным,
он и будет писать блоками.

## РЕШЕНИЕ Р6. Путь записи не двоится: `bodyDoc` едет через executor

`bodyDoc` — **одно** новое опциональное поле. Правила:

- `body` и `bodyDoc` одновременно — ошибка валидации;
- `expectedUpdatedAt` обязателен при любом из них, как сегодня при `body`;
- конверсия встаёт перед стадией записи; стадии, ajv-валидация, инварианты графа, журнал и
  Undo не трогаются.

Отдельного эндпоинта «сохранить документ» не заводим: второй путь записи пришлось бы потом
сливать с первым, и это было бы труднее слияния текстов.

**Где именно живёт `bodyDoc` (уточнено после ревью плана).** `entityUpdateInput` —
ОДНА схема на три входа: tRPC-роутер (`routers/entity.ts:125`), диспатч тулов модели и MCP
(`tools/dispatch.ts:636`) и executor (`executor.ts:965`). Расширив её, мы обязаны расширить и
рукописную `entityUpdateJsonSchema` (`tools/registry.ts:189`) — их парность проверяет тест
(`tools/registry.test.ts:257-285`), — а это показало бы `bodyDoc` модели, что раздел «Что НЕ
входит» прямо запрещает.

Поэтому схемы расходятся по входам, а не по путям записи:

- `entityUpdateInput` — **без `bodyDoc`**, как сегодня: контракт тула для модели и MCP;
- `entityUpdateUiInput = entityUpdateInput.extend({ bodyDoc })` — вход tRPC-роутера;
- executor принимает надмножество (`entityUpdateUiInput`) — он один на всех.

Тест парности сверяет узкую схему с JSON Schema тула, поэтому остаётся зелёным без правок.
То же симметрично для чтения: `entityGetUiInput` добавляет `'bodyDoc'` в `include`, тул-контракт
`entityGetInput` не растёт.

**Один путь записи, два входа с разными полномочиями** — та же конструкция, которой потом
воспользуется агент-соредактор (Р13).

**`bodyDoc` НЕ едет в каждом ответе** — только по явному `include`. Wire-форма всегда несёт
`body`; если рядом поедет документ, каждый список сущностей потяжелеет вдвое.

**Цена, известная заранее:** inverse для Undo станет хранить прежний `body_doc` вместо строки,
и журнал в `chat_messages.metadata` потяжелеет примерно вдвое на правках тела.

## РЕШЕНИЕ Р7. `body_refs` считаются по дереву — это изменение поведения

Сейчас `extractBodyRefs` бежит регэкспом по сырому тексту и считает связью в том числе
`[[entity:…]]` внутри блока кода — наивность, зафиксированная в комментарии как намеренная.

Со структурной правдой связью считается **настоящая нода `entity`**: рендер и граф сходятся по
построению — цель, ради которой и держалась зеркальная пара регэкспов. Цена: у записей, где
ссылка стоит внутри кода, backlink пропадёт — причём и внутри блока кода, и внутри inline-кода
(`` `[[entity:…]]` ``, проверено). Случай редкий, но это изменение поведения, а не рефакторинг,
и правило простое: что не кликабельно, то и не связь.

`linkifyEntityRefs` и `ENTITY_REF_RE` в `Markdown.tsx` **остаются**: чат по-прежнему рендерит
ответы модели markdown'ом, и там ссылки текстовые.

## РЕШЕНИЕ Р8. Поиск для меню и batch-резолвер для чипов

**`entity.suggest`** — поиск по префиксу заголовка (trigram-индекс на `title`, миграция `0007`).
Грамматику `search=` не трогаем: там семантика целого слова осмысленна и на неё завязаны
сидированные смарт-листы. Без префиксного поиска slash-меню бесполезно — набор `/куп` не нашёл
бы «Купить кроссовки». Пикер блокировок переходит на ту же процедуру, извиняющаяся подсказка
«по целому слову» исчезает.

**`entity.resolveRefs([ids])`** — заголовки для чипов одним запросом: `{id, title, emoji,
status, archived}` и ничего лишнего. Per-id `entity.get` в теле с десятками ссылок дал бы
шторм запросов, а тянуть полную сущность ради подписи расточительно.

## РЕШЕНИЕ Р9. Экран — три таба: Сущность · Детали · Тред

**«Сущность»** — чистый документ: emoji, заголовок (`NativeRow` с чекбоксом задачи), полоса
прогресса цели, тело.

**«Детали»** — всё, что известно о сущности помимо текста, секциями: карточки аспектов,
подзадачи, блокировки, связанное. Данные приезжают тем же `entity.get` — ни одного нового
запроса.

**«Тред»** — без изменений.

**Полоса прогресса цели остаётся на «Сущности»**, хотя сама карточка `orbis/goal` уезжает в
«Детали»: у цели прогресс — то, ради чего её открывают, и прятать «67%, 8 из 12 кг» во второй
таб значило бы ухудшить главный экран целей ради чистоты документа.

Четыре таба (со «Связями» отдельно от «Свойств») рассмотрены и отклонены: разделение чище по
смыслу, но на узком экране четыре вкладки тесны, и почти всегда одна пуста — у обычной заметки
нет ни аспектов, ни связей.

§3.5 PRD (`docs/prd/02-core-os.md:413`) нормирует секции 1–8 одним списком на вкладке
«Сущность» — правится в этой же работе.

## РЕШЕНИЕ Р10. Сохранение по паузе; говорим только о проблеме

Сохранение — по паузе в наборе ~2 с, плюс принудительно на уходе фокуса и на размонтировании.
Мутация уходит только при реальном изменении документа. Сдержанность не косметическая:
`onSettled` зовёт `invalidateGraph(utils)` — инвалидацию всего графа.

Шлём `bodyDoc` + `expectedUpdatedAt` с точной строкой `updatedAt` из кэша (как `saveBody`
сегодня). `applyPatch` расширяется на `bodyDoc`.

**Клиент markdown НЕ сериализует — вообще** (уточнено после ревью плана). Оптимистичный патч
кладёт в кэш только документ; `body` остаётся прежним до ответа сервера, который и есть
единственный автор проекции.

Две причины, обе весомые. Во-первых, вес: `serializeBody` тянет за собой всю схему документа
(~156 kB gzip — StarterKit, `@tiptap/markdown` с `marked`, списки, таблицы), и вызов её из
`applyPatch` затащил бы этот груз в чанк `DetailScreen`, то есть **до первого кадра** — ровно
то, что двухфазное монтирование и должно предотвратить. Во-вторых, единственность: пока
проекцию делает только сервер, клиентская и серверная версии не могут разойтись.

Следствие для состава: `@orbis/shared/doc` импортируется **только** из ленивого чанка редактора
(`features/entity-editor/*`), где Tiptap и так есть, и никогда — из эагерной части. Отдаётся
отдельным подпутём, а не через корневой баррель `@orbis/shared`: баррель собран из `export *` и
импортируется эагерными модулями web (`lib/markdown/Markdown.tsx` и другие).

**Индикатор состояния — только о проблеме.** Раньше момент сохранения был явным (ушёл фокус —
сохранилось), и обратная связь не требовалась. Автосохранение этот момент убирает, поэтому:
в норме тихо; «Сохраняем…» — только если запрос идёт дольше секунды; «Не сохранено» — висит,
пока не сохранится. Успех отдельно не празднуем: постоянный статус в углу — ровно та панель
инструментов над каждой заметкой, от которой экран отказывается сознательно
(`DetailScreen.tsx:373`).

**409 остаётся**: баннер «Изменено в другом месте — обновите» и кнопка «Обновить». Документ в
редакторе не подменяется — §5.2 предлагает «повторить вручную», значит повторять должно быть
откуда.

Свежий серверный документ подменяет содержимое, только если несохранённых правок нет. Правило
`key={entity.id}`, а не по `updatedAt`, сохраняется буквально: ремоунт по ключу стирал бы
набранное за время запроса.

`Ctrl+Z` — история редактора, не журнальный Undo. Ручную правку отменяют там же, где сделали;
«отмени последнее» остаётся про действия агента.

**Окно конфликта расширилось, и это принимается осознанно.** Раньше правка была коротким явным
эпизодом; теперь редактор открыт всё время, пока сущность на экране, а модель пишет в те же
тела через fast-path. Настоящее лекарство — слияние (Р13); до него работают 409 и черновик.

## РЕШЕНИЕ Р11. Офлайн: черновик переживает закрытие вкладки

PWA плюс всегда открытый редактор делают сценарий «пишу в метро» обыденным. Retry-буфер здесь
не помощник: он принимает только `entity.create` от fast-path, а у `update` есть
`expectedUpdatedAt`, который протухает — правка, пролежавшая час, приедет с 409, то есть
отложенная отправка обещала бы то, чего не может выполнить.

Поэтому: пока есть неотправленные правки, документ лежит в **localStorage** под ключом
сущности; при первом успешном сохранении запись стирается. Вернулась сеть:

- `updatedAt` на сервере не менялся → досылаем тихо;
- менялся → баннер «есть несохранённая правка» с возможностью посмотреть и применить.

Это персистенция содержимого сущности на диск браузера, и она принята владельцем явно (случай
отличается от истории чата: не архив, а собственный неотправленный черновик, живущий до первого
успеха). Для приложения-памяти потеря набранного текста — тот же худший класс ошибки, ради
которого заведены `raw`-нода и правило `key={entity.id}`.

Правило разрешения при возврате нарочно грубое и честное (сравнили `updatedAt`, спросили
пользователя). Именно его потом заменит слияние — не переделывая ничего вокруг.

## РЕШЕНИЕ Р12. HTML в документ не попадает

`react-markdown` не парсит HTML вовсе (`rehype-raw` не подключён) — это записано как эшелон
обороны, потому что разметку в тело приносит ответ модели. Tiptap же по умолчанию принимает HTML
при вставке и при парсинге, поэтому правило фиксируется явно и **тремя конкретными настройками**
(уточнено после ревью плана — «схема сама всё отбросит» оказалось недостаточным):

1. **Протоколы ссылок** — `Link` из StarterKit конфигурируется белым списком
   (`protocols`, `isAllowedUri`): `javascript:` и родня ссылкой не становятся.
2. **Вставка из буфера** — `editorProps.transformPastedHTML` снимает разметку, оставляя текст:
   вставленный из письма или с сайта фрагмент проходит тот же путь, что и текст модели.
3. **Схема** принимает только объявленные ноды и marks; всё прочее не создаётся.

## РЕШЕНИЕ Р13. Швы под будущее заложены; инфраструктура не строится

Владелец подтвердил: совместное редактирование **людьми и агентами** будет обязательно. Здесь
оно не реализуется, но конструкция обязана его пережить без разворотов.

**Заложено этой работой:**

1. направление правды `документ → markdown` (Р1) — переворачивать потом значило бы переписать
   оба конца;
2. структурное хранение `body_doc` — превращается в Y.Doc готовой утилитой
   `prosemirrorJSONToYDoc`, схема нод при этом та же;
3. версия схемы в документе (Р1) — миграции формата возможны без потери содержимого;
4. стабильные id блоков (Р5) — на них ляжет блочный контракт агента
   (`body_replace_block`/`body_insert_after`/`body_delete_block` вместо перезаписи тела);
5. единственный путь записи через executor (Р6) — иначе к моменту CRDT сливать пришлось бы два
   пути записи, а не два текста;
6. общая схема документа в `@orbis/shared` (Р3) — клиент, сервер и будущий агентский
   применятель понимают документ одинаково;
7. грубое правило разрешения при возврате из офлайна (Р11) — точка, куда встанет слияние.

**Сознательно НЕ строится:** Y.js, WebSocket, Hocuspocus, awareness, курсоры присутствия;
membership и роли (D11); блочные инструменты модели; атрибуция авторов; комментарии.
`expectedUpdatedAt` с 409 остаётся нетронутым — полумеры вокруг конфликтов сейчас помешали бы
снять их нормально потом.

**Проверка на отсутствие разворотов.** CRDT: `body_doc jsonb` → Y.Doc, схема та же, id на
месте, контракты те же. Агентские блочные инструменты: чистое добавление. Люди: правило в
`onAuthenticate` плюс RLS-шаблон из чек-листа D11. Ни один шаг не требует переделать сделанное
здесь.

## Состав редактора

- **Режим один.** `BodySection` с `editing`, `startEditing` и кнопкой «Редактировать» уходит
  целиком.
- **Slash-меню** (`@tiptap/suggestion`): заголовки, списки, задача, цитата, код, таблица,
  разделитель + «Смарт-лист» (открывает существующий `QueryBlockEditor`, вставляет
  `queryBlock` в каретку), «Ссылка на сущность», «Создать сущность» с подстановкой набранного
  текста в заголовок.
- **`@`** — упоминание сущности тем же механизмом и тем же поиском.
- **Чип сущности** (`entity` NodeView): актуальный заголовок из `entity.resolveRefs`, иконка
  статуса, зачёркивание у закрытых задач, серая пометка у удалённой или недоступной. Клик —
  `openEntity`; Ctrl/Cmd/Shift-клик и средняя кнопка остаются штатными жестами браузера
  (`Markdown.tsx:62` — поведение терять нельзя).
- **`queryBlock` NodeView** — существующий `QueryBlock`; «Настроить» открывает существующий
  `QueryBlockEditor`. Правка блока становится правкой атрибута ноды: `replaceQueryBlock` и
  оптимистичная блокировка по номеру блока исчезают. `bodySegments` / `queryBlocks` /
  `firstQueryBlock` остаются — они читают проекцию и питают бейджи pinned-сущностей.
- **Bubble-меню** по выделению — форматирование плюс действия над блоком («удалить»,
  «превратить в…»), которые в Notion живут на drag handle.
- **Перемещение блока — `Alt+↑/↓`** (команды ProseMirror, вес ~0). Drag handle мышью в работу
  не входит — см. «Что НЕ входит».
- **Плейсхолдер** «Заметки…».
- **Markdown-тумблер** — пункт меню ⋮: показывает проекцию, правит текстом, на выходе парсит
  обратно. Не распарсилось — не сохраняем и говорим об этом.
- **Мобильный**: `/` работает и там, основной вход — кнопка «+» в панели над клавиатурой.
  Перетаскивания блоков нет (drag handle исключён); порядок меняется `Alt+↑/↓` с внешней
  клавиатуры и действиями bubble-меню.
- **Двухфазное монтирование — ОБЯЗАТЕЛЬНО** (было «по результату замера»). Первый кадр рисует
  нынешний `Markdown` (react-markdown уже в бандле ради чата), редактор монтируется по idle или
  по первому касанию тела.

  > **ФАКТ СПАЙКА.** Чанк редактора — **~160 kB gzip** в составе без drag handle (205 kB с ним)
  > при том, что вся начальная загрузка приложения сегодня 219.3 kB. Ленивый чанк ленивым и
  > остаётся — начальная загрузка не растёт, — но открытие сущности без двухфазности удваивало
  > бы трафик первого захода на detail. Разбивка по слоям — в отчёте спайка.

**Необязательное, режется первым при нехватке объёма:** карточка сущности по наведению на чип.

## Инварианты, которые проверяются, а не подразумеваются

1. **Идемпотентность проекции:** `serialize(parse(serialize(doc))) === serialize(doc)` —
   property-тест. Без него «байт-в-байт» держится на честном слове.
2. **Тождественность на сиде:** пять сидированных тел переживают round-trip буква в букву
   (`onboarding.test.ts` уже это проверяет — достаточно не отключать).
3. **Согласованность пары:** после любой записи `body` равен сериализации `body_doc`. Прямая
   запись `body` в БД мимо конвертера запрещена; конверсия живёт в одном месте перед стадией
   записи.
4. **`body` всегда валидный markdown** — на нём стоят FTS, промпт, MCP и бейджи pinned.

## Известные границы

- Каждое автосохранение шлёт **весь документ**. При длинных заметках на мобильном это заметно;
  снимается переходом на CRDT (дельты), не раньше.
- Журнал действий тяжелеет примерно вдвое на правках тела (Р6).
- Ссылка внутри блока кода перестаёт давать backlink (Р7).
- **Экранирование текста при сериализации** (ФАКТ СПАЙКА): `due_date` → `due\_date`,
  `a&b` → `a&amp;b`. Сидит в приватных методах сериализатора, опций нет; переопределение
  `renderMarkdown` у ноды `Text` не помогает. **На FTS не влияет** — проверено на живой БД:
  `to_tsvector('simple', …)` даёт идентичный вектор для обеих форм, а
  `plainto_tsquery('simple','due_date')` находит обе. Экранирование идемпотентно (добавляется
  один раз, не накапливается) и появляется только в телах, которые правил человек — правило
  «без изменений — без записи» оставляет нетронутые тела нетронутыми. Остаётся косметический
  шум в тексте, который читает модель.
- **Таблицы нормализуются по ширине столбцов** (`| a | b |` → `| a   | b   |`): байт-в-байт для
  тел с таблицами не держится. В сидированных телах таблиц нет. Тело, состоящее только из
  таблицы, поэтому уедет в `raw` (сверка round-trip не сойдётся) — приемлемо: текст цел, а
  редактируется он тумблером.
- **`UniqueID` не входит в схему сервера.** Документы, которые сервер собирает из строкового
  `body` модели, приезжают БЕЗ блочных id — расширение живёт только в редакторе. Это не изъян:
  id понадобятся, когда агент станет писать блоками, и тогда же он начнёт слать документ, а не
  строку.

## Спайк — проведён 2026-08-13

Полные результаты — `docs/superpowers/reviews/2026-08-13-editor-spike.md`. Коротко:

| Вопрос | Ответ |
|---|---|
| Tiptap в jsdom | **Да**, 8/8 зелёные — но без полифилов прогон падает с кодом 1 при зелёных тестах |
| Парсер на Bun без DOM | **Да**, без оговорок — запасной путь не нужен |
| Round-trip сидов | **Буква в букву**, идемпотентность 20/20 |
| Вес чанка | **~160 kB gzip** без drag handle (205 с ним) при бандле 219 |
| Мобильный ввод | **Не проверен** — нужно живое устройство |

**Первая задача плана — полифилы ProseMirror в `tests/setup.ts`**, до любого кода редактора.
ProseMirror зовёт `Range.prototype.getClientRects` и `document.elementFromPoint`, которых в
jsdom нет; вызовы уходят в uncaught exception, тесты при этом остаются зелёными, а **прогон
падает** — красный CI без единого упавшего теста. Кандидат готов:
`apps/web/src/spike/prosemirror-jsdom-polyfill.ts`.

**Осталось непроверенным:**

1. **Мобильный ввод** — IME, автокоррекция, голосовой набор. Проверяется только на живом
   устройстве (jsdom не воспроизводит, эмуляция DevTools тоже). Риск не блокирующий, но
   ненулевой; проверка за владельцем.
2. **Round-trip на корпусе тел с прода.** В белом списке `scripts/ops.ts` шесть команд, выгрузки
   тел среди них нет. Проверены сидированные тела (самые злые по форматированию) и 15
   синтетических случаев. Полный корпус потребует новой ops-команды — решение владельца.

## Что НЕ входит

- Совместное редактирование, присутствие, курсоры, атрибуция авторов, комментарии (Р13).
- Membership, workspace'ы, роли (D11).
- Блочные инструменты для модели; контракт `entity_update{body}` остаётся строковым.
- Панель свойств в стиле Notion над телом: карточки аспектов — формы по JSON-схеме реестра, и
  свёртка их в строки — отдельный редизайн сопоставимого объёма. Вместо этого — таб «Детали»
  (Р9).
- **Drag handle (перетаскивание блоков мышью)** — решение владельца от 2026-08-13 по итогам
  замера. Стоит 40 kB gzip, из них ~25 kB — `@tiptap/extension-collaboration` + `y-tiptap` +
  `yjs`: расширение тянет Y.js, то есть ровно ту инфраструктуру, которую откладывает Р13.
  Платить за неё, не используя ни одной её возможности, — D11 наизнанку. Сценарий для Orbis
  редкий (тела короткие, значительную часть пишет модель, главный жест — «записать и потом
  прочитать»), на мобильном жест заведомо хуже десктопного. Полезное из трёх его функций —
  меню блока — уезжает в bubble-меню. **Решающее: после перехода на CRDT yjs будет в бандле по
  любому, и drag handle подешевеет с 40 kB до ~15** — вернуться к нему стоит вместе с
  курсорами и присутствием. Взамен сейчас — `Alt+↑/↓`.
- Вложенные страницы, callout/toggle-блоки, «unlinked mentions», вставка ответа модели прямо в
  текст, повышение пункта чеклиста до сущности-подзадачи.
- Правка тегов и emoji на месте, кнопка «+аспект» — известные долги §3.5, к работе отношения
  не имеют.

## Приёмка

1. Тело правится без смены режима: чипы и виджеты остаются собой, пока идёт набор.
2. `/` открывает меню с поиском; поиск находит по префиксу заголовка.
3. Смарт-лист вставляется из UI в позицию каретки и настраивается на месте.
4. Ссылка вставляется через `/` и через `@`; чип показывает актуальный заголовок и статус;
   клик открывает сущность в текущей вкладке, Ctrl/Cmd-клик — в новой; заголовки резолвятся
   одним запросом.
5. Тумблер markdown показывает ровно то, что лежит в `body`, и возвращает правку в документ;
   неразбираемый текст не сохраняется молча.
6. Таб «Детали» показывает аспекты, подзадачи, блокировки и связанное; полоса прогресса цели
   осталась на «Сущности»; новых запросов не появилось.
