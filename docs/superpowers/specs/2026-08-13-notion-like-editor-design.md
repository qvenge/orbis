> нумерации Р1–Р13, но текст каждого приведён к коду ветки. Там, где реализация разошлась с
> первоначальным замыслом, разница названа прямо, а не затёрта.
>
> **Что решил не владелец, а контроллер.** Владелец в цикле по этим пунктам не высказывался, и
> перечислены они затем, чтобы документ никому не приписывал чужого слова:
>
> - **`body` хранится каноном, а «непонятое» ловится по токенам и поблочно** (Р1, Р3) — три
>   меры по блокеру Б1 второго круга ревью, прямо названные решением контроллера в шапке плана
>   v2. Владельцу принадлежит решение ДРУГОЕ и более раннее: «лучше сохранить дословно, чем
>   молча переписать» — то есть сам факт существования `raw`, а не механизм его появления;
> - **снятие мёртвого индекса из самой миграции**, а не `DROP`-ом (Р1);
> - **поиск по вхождению вместо префикса и имя поля `term`** (Р8);
> - **`archived` фильтруется в `suggest` и НЕ фильтруется в `resolveRefs`** (Р8);
> - **обещание «подпись ссылки обновляется при сериализации» снято** (Р3);
> - **редактор смарт-листа показывает текст дословно, а не тримленным** (Р4) — вместе с
>   принятым долгом про позицию в плашке ошибки;
> - **цена строкового Undo принята**: отмена правки тела теряет блочные id (Р6);
> - **«Удалить блок» убирает ПУНКТ списка, а ячейка таблицы — исключение** с удалением всей
>   таблицы («Состав редактора»);
> - **мобильная панель «+» отложена** (там же).
>
> Перечень — не перепись: он собран проходом по этому документу, и решения такого же класса
> помечены ещё и по месту. Каждое — с ценой, названной там же, где само решение.

## Что установила разведка (состояние ДО работы)

**`body` — источник правды сразу для двоих.** Сервер извлекал `body_refs` регэкспом из
текста при каждом create/update (`apps/server/src/executor/normalize.ts`, `extractBodyRefs`), и
на этом стояли backlinks. Клиент держит КОПИЮ того же регэкспа
(`apps/web/src/lib/markdown/Markdown.tsx:16`) с комментарием: расхождение «соврало бы про связи
записи». Модель пишет тем же текстом через `entity_update{body}`
(`packages/shared/src/contracts/tools.ts`, `entityUpdateInput.body`).

**Граница режимов видна намеренно.** Просмотр — `Markdown` + живые `{{query:…}}`-виджеты
вперемежку через `bodySegments`; правка — голая `<textarea>` со всем текстом, виджеты уезжали
списком под неё. При входе в правку чипы сущностей превращались в `[[entity:uuid]]`, смарт-лист —
в фигурные скобки. Это и есть «схлопывание», которое требовалось убрать.

**Байт-в-байт — не пожелание, а инвариант с тестом.** Тела пяти сидированных смарт-листов
(`apps/server/src/seed/smart-lists.ts`) взяты из §3.3 PRD ДОСЛОВНО — с переносами строк и
девятипробельными отступами continuation-строк внутри `{{query:…}}`; `onboarding.test.ts` (тест
«body всех пяти списков — байт-в-байт равен блокам 02 §3.3») сверяет их с markdown-блоками PRD
по порядку. Тем же инвариантом объяснялось устройство `replaceQueryBlock`: он правил РОВНО
подстроку блока срезами по длинам обёртки, потому что «пересборка схлопнула бы многострочные
блоки». (Этой функции больше нет — см. Р4.)

**Вставить смарт-лист из UI было невозможно.** `QueryBlockEditor` открывался только на уже
существующем блоке (`onConfigure`); новый заводился лишь набором `{{query:` руками.

**Поиск сущностей — только по целому слову.** `search=` компилируется в
`plainto_tsquery('simple', …)` (`apps/server/src/query/compile.ts:226`). Пикер блокировок
признавал это подсказкой «Поиск от 2 символов и по целому слову».

**Заголовки связанных сущностей резолвились по одному** — через `trpc.useQueries` с per-id
`entity.get`: там списки короткие, а в теле записи ссылок может быть много.

**`body` едет в КАЖДОМ ответе.** Wire-форма `entitySchema` всегда несёт `body`, `include`
управляет лишь дополнительными секциями (`apps/server/src/entity-read.ts:4-5`).

**Retry-буфер существует, но не для правок.** `apps/web/src/state/retry.ts` держит очередь в
localStorage и принимает ТОЛЬКО `entity.create` от fast-path; §2.6 PRD: «Fast-path работает без
сети как обычно — он единственный, кто пишет в буфер».

**Тесты web гоняются в jsdom** (`apps/web/vite.config.ts`), а ProseMirror опирается на
`Selection`, `Range` и contenteditable, которые там неполны.

**Запись идёт единственным путём.** Роутер `entity` — «ТОЛЬКО трансляция», вся мутация через
`executor`: пять стадий, ajv-валидация аспектов, инварианты графа
(`apps/server/src/executor/invariants.ts`), append-only журнал в `chat_messages`, Undo через
inverse в том же tx (`apps/server/src/executor/undo.ts`). Каждое сохранение из detail дергает
`invalidateGraph` (`apps/web/src/features/entity-detail/useEntityDetail.ts`, `onSettled`).

**Multi-user уже спроектирован как отложенный.** D11 (`docs/prd/04-decision-log.md:102`):
схема per-owner, workspace'ы и роли — Future, но с чек-листом из пяти пунктов, включая «RLS-
политики генерируются из одного шаблона — переход owner→membership правится в одном месте».
Принцип, которому подчинён весь этот дизайн, — оттуда же: «откладывать инфраструктуру можно,
но не ценой архитектуры, которую потом придётся переписывать».

**Проверено по докам библиотек.**
- Tiptap v3: markdown — официальный API (`editor.markdown.parse` / `.serialize`), кастомная
  нода объявляет `parseMarkdown` и `renderMarkdown`. Drag Handle, Table Kit, Bubble/Floating
  menu, Placeholder, List Kit, UniqueID, Collaboration — без ценовых тегов в листинге доков,
  то есть MIT; платны только Comments, AI, Import/Export docx, Pages, Version. **UniqueID в v3
  живёт в основном неймспейсе (`@tiptap/extension-unique-id`)** — подтверждено установкой.
- BlockNote: markdown-конверсия называется `blocksToMarkdownLossy`, документация прямо
  указывает использовать JSON для сериализации без потерь. Для Orbis, где markdown — язык
  общения с моделью, lossy на входе неприемлем. **Отклонён.**
- Lexical: `@lexical/yjs` официален, есть задокументированный headless-рецепт. Против: markdown
  — самописные transformers, ключи нод не переживают сессию, стабильную идентичность блоков
  пришлось бы строить самим. **Отклонён.**

## РЕШЕНИЕ Р1. Правда — структурная; markdown остаётся аварийным дублем

Миграция `0007` добавляет `body_doc jsonb` **nullable** — и больше НИЧЕГО: `NULL` означает
«тело ещё не сконвертировано». Forward-only, expand/contract.

**Индекса под поиск в этой миграции нет, и это не забывчивость.** Планировавшийся btree по
`lower(title)` (тогда — под префиксный поиск Р8) убран из самой миграции ещё до её выезда, а не
снят потом `DROP`-ом: под RLS не-leakproof квал нельзя вычислить раньше security-квала политики,
поэтому в index cond он не превращается. Замерено EXPLAIN'ом: от роли `postgres` тот же запрос
идёт `Bitmap Index Scan`, от роли приложения — `Seq Scan` даже при `enable_seqscan = off`. Индекс
был бы мёртв и дорожал бы на каждой правке заголовка. (Та же участь у живущего в проде GIN
`entities_title_fts` под `search=` — это свойство схемы, а не беда конкретной процедуры.)

Хранится **`{ v: <версия схемы>, doc: <ProseMirror JSON> }`**, а не голый документ;
`DOC_SCHEMA_VERSION = 1` (`packages/shared/src/doc/types.ts`).

`entities.body` остаётся `text NOT NULL` и становится **производной**. FTS-поиск, фильтры
Browser, промпт, экспорт, MCP-контракт `entity_update{body}` и бейджи pinned-сущностей
(`firstQueryBlock` по markdown) не меняются ни строкой.

**`body` в БД — всегда КАНОН**, то есть `serializeBody(parseBody(x))`, а не «как написала
модель». Так пишут обе ветки executor'а и бэкфилл. Следствие видно глазом: `__жирный__` станет
`**жирный**`, маркер `*` — `-`, `1)` — `1.`, голый URL — автолинком `[url](url)`, setext-заголовок
— ATX, код с отступом — забором (всё замерено `canonicalizeBody`). Это цена единственности:
сравнивать «как написала модель» с «как хранит документ» бессмысленно, а сравнивать канон с
каноном — дёшево и однозначно.

**Судьба существующих тел.** Порядок прод-процедуры жёсткий и его шаги не взаимозаменяемы:
`bun scripts/ops.ts migrate` → READ-ONLY `bun scripts/ops.ts audit-bodies` → и только если его
числа приемлемы, `bun scripts/ops.ts backfill-body-doc`. Бэкфилл — **обязательный** шаг, а не
факультативный: пока колонка пуста, сервер собирает документ из `body` **при КАЖДОМ чтении**
c `include: ['bodyDoc']` и обратно в БД не пишет (`apps/server/src/entity-read.ts` — «чтение
обязано оставаться чтением»). То есть «ленивая конверсия» — не разовое действие, а постоянная
плата, пока тело не пересохранено или не прогнан бэкфилл.

**Почему markdown не выбрасывается, хотя правда уже структурная.** ProseMirror при загрузке
документа **молча выбрасывает узлы, которых нет в текущей схеме**. Для приложения-памяти это
худший класс ошибки: добавили ноду, откатили релиз — часть содержимого исчезла без следа.
Поэтому `body` — не «проекция ради совместимости», а **аварийный дубль**, и правило разрешения
записано явно (`readBodyDoc`):

1. форма верна и версия схемы равна текущей → правда в `body_doc`;
2. иначе (версия из будущего после отката релиза, битая форма, `NULL`) → **документ
   пересобирается из `body`**.

Худший исход деградации — потеря блочных id и части оформления, но **не текста**. Симметрично на
записи: `bodyDoc` чужой версии executor отвергает `VALIDATION`, а не сохраняет «на будущее», —
принять его значило бы записать заведомо обречённое, и потерялось бы СОДЕРЖИМОЕ: незнакомая нода
выпадает уже из проекции.

**Отклонённая альтернатива: хранить сразу Y.Doc (бинарём).** Тогда переход к соредактированию
не потребовал бы ни одной миграции формата. Отклонено: Y.Doc непрозрачен для SQL и
jsonb-операторов (ни посмотреть, ни запросить), тяжелее в чтении, и требует yjs на сервере уже
сегодня — а экономит ровно одну детерминированную миграцию `prosemirrorJSONToYDoc`. Это
инфраструктура ради будущего, запрещённая D11.

## РЕШЕНИЕ Р2. Редактор — Tiptap (ProseMirror)

Три причины, каждая проверена по докам: markdown официален и расширяем **на уровне ноды**
(а markdown здесь не декорация, а интерфейс модели); UniqueID даёт готовую стабильную
идентичность блоков, на которой стоит будущий агентский контракт; `y-prosemirror` — самая
обкатанная CRDT-связка.

**Отклонено, помимо BlockNote и Lexical:** CodeMirror 6 с живым просмотром (декорации поверх
текста, как Obsidian Live Preview). Рассмотрен всерьёз: он честнее к тексту и дал бы
markdown-тумблер даром. Отклонён владельцем — его потолок не WYSIWYG по устройству: каретка
всегда стоит в символах, поэтому таблицы, вложенные структуры и перетаскивание блоков остаются
работой с разметкой.

## РЕШЕНИЕ Р3. Схема документа: узел сам знает свой markdown

Схема живёт в `@orbis/shared/doc` (`packages/shared/src/doc/schema.ts`, `DOC_EXTENSIONS`) и одна
на сервер и клиент. Стандартное — из StarterKit плюс два отдельных пакета: абзацы, заголовки,
маркированные и нумерованные списки, **задачи-чеклисты (`@tiptap/extension-list`)**, цитаты,
блоки кода, разделитель, **таблицы (`@tiptap/extension-table`)**, переносы. Marks: жирный,
курсив, зачёркнутый, код, ссылка.

Свои ноды (имена — те, что в коде; прежние рабочие имена дизайна `entity`/`raw` не пережили
реализацию). **Ниже по тексту `raw` — сокращение для ноды `rawBlock`**, а не второе имя: в схеме
ноды с именем `raw` нет.

| Нода | Вид | Атрибуты | Markdown-проекция |
|---|---|---|---|
| `entityRef` | inline, atom | `{ entityId, label }` | `[[entity:uuid\|подпись]]` |
| `queryBlock` | block, atom | `{ query }` (дословно, см. Р4) | `{{query:…}}` |
| `rawBlock` | block, atom | `{ markdown }` | дословно исходный кусок |

Две настройки StarterKit сделаны В САМОЙ схеме и переопределять их в составе редактора нельзя:
`link.isAllowedUri` (Р12) и **`trailingNode: false`** — иначе StarterKit дописывает пустой абзац
в конец любого документа, не кончающегося абзацем: все пять сидов «менялись» при простом
открытии, и автосейв слал фантомный `entity_update` (ревью Б4).

`rawBlock` — страховка от тихой потери: непонятое схемой сохраняется как есть.

**Как `raw` возникает: токен-детекция, ПОБЛОЧНО** (решение контроллера по блокеру Б1, вместе с
канонизацией `body` из Р1). Своего парсера у ноды нет и быть не может:
чтобы поймать «непонятое», нужно знать заранее, чего именно мы не знаем. Поэтому `parseBody`
лексирует текст лексером СВОЕГО менеджера (в нём зарегистрированы токенайзеры `queryBlock` и
`entityRef`) и сверяет типы токенов с белыми списками `KNOWN_BLOCK` / `KNOWN_INLINE`
(`packages/shared/src/doc/convert.ts`). Токен, для которого обработчика в схеме нет, уводит в
`rawBlock` **только свой блок**. Обход рекурсивный: `items` списков, `tokens` вложенных
конструкций и — отдельно — `header`/`rows` таблицы, потому что ячейки лежат не там, где всё
остальное, и без их обхода картинка в ячейке молча пропадала при сериализации.

Тело уезжает в один `raw` ЦЕЛИКОМ, каким бы оно ни было, в двух случаях:
**reference-определения** (`[^1]: …`, `[ссылка]: …` — marked складывает их в
`lexer.tokens.links`, и восстановить форму нечем) и **исключение парсера**. Третьего такого
случая нет, но результат «весь документ — один `rawBlock`» достижим и по обычному поблочному
правилу: у тела из ОДНОГО непонятого блока блок и есть всё тело. Так выходит с таблицей, у
которой в ячейке стоит черта `|` (сериализатор её не экранирует, и повторный разбор развалил бы
ячейку надвое — единственное найденное нарушение инварианта канона) или картинка: обе уводят
таблицу в `raw` целиком, а если таблица одна во всём теле — `parseBody` отдаёт
`content: [rawBlock]` (проверено пробой).

**Почему не сверка round-trip, как задумывалось.** Первоначальный механизм — «сериализовать
результат обратно, не сошлось — всё тело в один `raw`» — проверял КАНОНИЧНОСТЬ, выдавая себя за
проверку целостности. На пробе ревью (корпус из 38 реалистичных тел) в `raw` уезжали **18, то
есть 47%**, и почти все — из-за нормализаций из Р1: `1)` → `1.`, `*` → `-`, `__` → `**`, голый
URL → автолинк. Тело, которое схема понимает полностью, объявлялось непонятым (вердикт ревью Б1).

Проверено фактом (замер `canonicalizeBody` на ветке): сноска GFM `текст[^1]` + `[^1]: сноска`,
картинка `![alt](…)` и HTML в тексте действительно уезжают в `raw` — то есть страховка нужна и
срабатывает, — а таблицы, чеклисты, ссылки на сущности, смарт-листы и `{{query:}}` внутри забора
кода разбираются штатно.

Цена решения: блок с неподдерживаемой конструкцией показывается неразобранным и правится через
markdown-тумблер, пока конструкция не будет добавлена в схему. Владелец выбрал это против
альтернативы «принять потери и записать в границы»: для приложения-памяти «сохранили дословно,
но некрасиво» лучше, чем «молча переписали».

**Как `raw` выглядит в редакторе.** Нода атомарная и своего NodeView не имеет: она рисуется
элементом `<pre data-raw>` с исходным текстом внутри. Пометки «не разобрано» на самом блоке нет,
и править его на месте нельзя — правка идёт через markdown-тумблер, который перед сохранением
НОВОГО неразобранного текста требует второго «Применить» (см. «Состав редактора»). Это
расхождение с первоначальным замыслом («блок кода с пометкой, правится текстом») названо здесь, а
не затёрто: пометка на блоке — незакрытый долг, а не сделанное.

> **ФАКТ СПАЙКА.** Необходимость `raw` подтверждена, а не предположена: в прогоне без
> `@tiptap/extension-table` таблица GFM превратилась в **пустую строку** — не в текст, не в
> искажённую разметку, а в ничто. Отдельно выяснилось, что чеклисты (`- [ ]`) **не входят** в
> StarterKit: нужны `@tiptap/extension-list` (TaskList/TaskItem) и `@tiptap/extension-table`.

**Принцип, ради которого всё это и делается: сериализация объявляется НА НОДЕ**
(`parseMarkdown`/`renderMarkdown`), а схема живёт в `@orbis/shared`. Тогда синтаксис Orbis —
это сумма нод, а не набор регэкспов по репозиторию. До работы знание о `[[entity:]]` жило в двух
местах (серверный и клиентский регэкспы, которые держались вместе только комментарием), о
`{{query:}}` — в трёх (`bodySegments`, `replaceQueryBlock`, серверный парсер грамматики). После
работы `replaceQueryBlock` нет вовсе, а описание синтаксиса — одно.

**Подпись в ссылке НЕ обновляется при сериализации — обещание снято.** `[[entity:uuid|подпись]]`
вморожена в текст на момент вставки; актуальное имя показывает чип (Р8), а markdown хранит то,
что было. Причина отказа не в цене, а в классе ошибки: обновление `label` атрибутом ноды — это
изменение документа при ОТКРЫТИИ записи, то есть ровно та фантомная запись, из-за которой
выключен `trailingNode` (ревью Б4). Один и тот же дефект нельзя лечить в одном месте и заводить
в другом. Вернуться к обновлению подписи следует вместе с блочным контрактом агента (Р13), когда
у записи появится путь «поправить один блок», не трогающий остальное.

## РЕШЕНИЕ Р4. Содержимое `{{query:…}}` хранится дословно

Атрибут `query` несёт содержимое блока **байт-в-байт**, включая переносы строк и отступы
continuation-строк, а не тримленным. Иначе первое же сохранение Daily Planning схлопнуло бы три
многострочных блока в одну строку и уронило инвариант §3.3 PRD.

Правка блока стала правкой АТРИБУТА ноды: `replaceQueryBlock`, адресация блока по порядковому
номеру в тексте и её оптимистичная блокировка «Блок изменился в другом месте» исчезли целиком
(Задача 16). Адрес правки — сама нода, промахнуться мимо неё нечем.

**Редактор блока показывает текст ДОСЛОВНО** (не тримленный, как задумывалось): в поле лежит
внутренность обёртки как есть, обёртку приставит сериализация. Иначе подстриженный край
переписал бы многострочный сид одной строкой при первой же правке. Принятый долг, записанный в
коде (`QueryTextEditor.tsx`): позиция в плашке ошибки грамматики считается по ТРИМЛЕННОМУ тексту,
а человек видит нетримленный, — у блоков с ведущим переносом позиция смещена на длину края.
Лечится сдвигом позиции, не тримом.

> **ФАКТ СПАЙКА: инвариант держится, при двух условиях.** Все пять сидированных тел проходят
> round-trip буква в букву, идемпотентность — 20 из 20. Условия, добытые ошибками в пробе:
> 1. `renderMarkdown` ноды возвращает блок **без хвостовых переносов** — разделитель между
>    блоками ставит сериализатор, и свой `\n\n` давал двойной;
> 2. `start` токенизатора обязан искать **полное** совпадение обёртки, а не подстроку
>    `{{query:`.
>
> Реализация добавила к этому третье условие, которого спайк не видел: обёртка считается блоком
> **только с начала строки**. Без него `смотри {{query: a=b}} тут` разваливалось на три блока, а
> `x{{query:…}}` — на абзац и блок. Тот же рубеж повторён в `bodySegments`, который рисует первый
> кадр, и совпадение двух правил стережёт тест, а не рассуждение.

## РЕШЕНИЕ Р5. Стабильные id блоков — с первого дня

`@tiptap/extension-unique-id` вешает `id` на блочные ноды — шесть типов, перечисленных в
`apps/web/src/features/entity-editor/strip-ids.ts` (`paragraph`, `heading`, `queryBlock`,
`rawBlock`, `listItem`, `taskItem`). Сегодня их не читает никто.

**Зачем сейчас.** Завтра на них стоит агентский контракт: `body_replace_block(id, md)` вместо
перезаписи тела целиком (Р13). Добавить id потом — мигрировать все документы; добавить сегодня
— один параметр расширения.

Расширение живёт ТОЛЬКО в составе редактора и в `DOC_EXTENSIONS` его НЕТ. Это безопасно ровно
потому, что оно **атрибутное**: серверный гейт спрашивает схему документа напрямую, и любая
лишняя НОДА или МАРКА редактора сделала бы нерабочим каждое сохранение, а незнакомый `attrs.id`
разбор молча отбрасывает до проверки схемы (проверено Задачей 4). Из этого же следует правило
записи: в БД едет ВХОД, а не `nodeFromJSON().toJSON()` — второй теряет незнакомые схеме атрибуты,
то есть стирал бы блочные id при каждом сохранении.

В markdown-проекцию id **не печатаются** — модель продолжает читать чистый текст. Следствие,
принятое сознательно: пока модель пишет `body` целиком, парсинг выдаёт блокам новые id. Сшивать
их по содержимому — placeholder-инфраструктура, запрещённая D11.

Второе следствие, стоившее отдельной работы: `UniqueID` проставляет id ОТДЕЛЬНОЙ транзакцией
после монтирования, поэтому по строковому равенству документ «менялся» при каждом открытии
записи. Поэтому и редактор, и автосохранение сравнивают документы **по смыслу** — с точностью до
блочных id и порядка ключей (`sameDoc`, там же). Без этого открытие любой записи через две
секунды писало бы в базу.

## РЕШЕНИЕ Р6. Путь записи не двоится: `bodyDoc` едет через executor

`bodyDoc` — **одно** новое опциональное поле. Правила:

- `body` и `bodyDoc` одновременно — ошибка валидации (`refine` на UI-схеме);
- `expectedUpdatedAt` обязателен при любом из них — гейт executor'а смотрит на ОБА поля;
- конверсия встаёт перед стадией записи; стадии, ajv-валидация, инварианты графа, журнал и
  Undo не трогаются.

Отдельного эндпоинта «сохранить документ» не заводим: второй путь записи пришлось бы потом
сливать с первым, и это было бы труднее слияния текстов.

**Где именно живёт `bodyDoc`.** `entityUpdateInput` — ОДНА схема на три входа: tRPC-роутер,
диспатч тулов модели и MCP (`tools/dispatch.ts:636`) и executor. Расширив её, мы обязаны были бы
расширить и рукописную `entityUpdateJsonSchema` (`tools/registry.ts:189`) — их парность проверяет
тест (`tools/registry.test.ts`, describe «парность zod-envelope ↔ рукописная JSON Schema»), — а
это показало бы `bodyDoc` модели, что раздел «Что НЕ входит» прямо запрещает.

Поэтому схемы расходятся по входам, а не по путям записи
(`packages/shared/src/contracts/tools.ts`):

- `entityUpdateInput` — **без `bodyDoc`**, как сегодня: контракт тула для модели и MCP;
- `entityUpdateUiInput = entityUpdateInput.extend({ bodyDoc }).refine(…)` — вход tRPC-роутера
  (`routers/entity.ts`, процедура `update`);
- executor принимает надмножество (`entityUpdateUiInput`) — он один на всех.

Форму документа контракт не моделирует (дублирующая zod-модель дерева ProseMirror разъехалась бы
со схемой при первой же новой ноде), но и не пропускает что угодно: верхний уровень (`v`, `doc`
с массивом `content`) проверяется явно и `.passthrough()` обязателен. Структурную целость
спрашивают У СХЕМЫ уже в executor'е — `bodyDocError` зовёт `check()` ProseMirror, а не смотрит на
косвенный след «проекция пуста»: в пустую строку законно сериализуются пустой абзац, пустой
ЗАГОЛОВОК, абзац с одним hardBreak и абзац из пробелов.

Тест парности сверяет узкую схему с JSON Schema тула, поэтому остаётся зелёным без правок.
То же симметрично для чтения: `entityGetUiInput` добавляет `'bodyDoc'` в `include`, тул-контракт
`entityGetInput` не растёт.

**Один путь записи, два входа с разными полномочиями** — та же конструкция, которой потом
воспользуется агент-соредактор (Р13).

**`bodyDoc` НЕ едет в каждом ответе** — только по явному `include`. Wire-форма всегда несёт
`body`; если рядом поедет документ, каждый список сущностей потяжелеет вдвое. Detail просит его
всегда (`DETAIL_INCLUDE`), и цена — примерно двойной вес ответа ОДНОЙ записи — принята: иначе
редактор пришлось бы собирать из markdown на клиенте, и блочные id до него бы не доезжали.

**Цена, известная заранее — и она не та, что предполагалась.** Undo остался **строковым**:
inverse несёт прежний `body` (`prior.body = current.body`), `body_doc` в него не пишется, и
журнал в `chat_messages.metadata` вдвое не тяжелеет. Плата другая: отмена правки тела
восстанавливает текст, но **теряет блочные id** — документ пересобирается из строки (ревью И3).
Сегодня id не читает никто, поэтому цена невидима; она станет видимой ровно тогда, когда на id
встанет блочный контракт агента, — и тогда же inverse придётся учить документу.

## РЕШЕНИЕ Р7. `body_refs` считаются по дереву — это изменение поведения

До работы `extractBodyRefs` бежал регэкспом по сырому тексту и считал связью в том числе
`[[entity:…]]` внутри блока кода — наивность, зафиксированная в комментарии как намеренная.

Со структурной правдой связью считается **настоящая нода `entityRef`** (`bodyRefsFromDoc`) —
рендер и граф сходятся по построению. Цена: у записей, где ссылка стоит внутри кода, backlink
пропадёт — и внутри блока кода, и внутри inline-кода (`` `[[entity:…]]` ``, проверено). Правило
простое: что не кликабельно, то и не связь.

**Но `raw`-блоки — исключение, и это не оговорка, а несущая деталь** (ревью Б2). По ним
`bodyRefsFromDoc` проходит РЕГЭКСПОМ: непонятая схемой конструкция не должна стоить записи её
связей — иначе одна картинка в теле рвала бы backlinks всего абзаца молча. Итого: связь — это
нода `entityRef` ∪ находки регэкспа внутри `rawBlock`; код и inline-код — не связь.

Обе ветки записи (строковый `body` от модели и `bodyDoc` из UI) считают `body_refs` одинаково —
из ДЕРЕВА, иначе правка модели и правка из UI считали бы связи по разным правилам.

`linkifyEntityRefs` и `ENTITY_REF_RE` в `Markdown.tsx` **остаются**: чат по-прежнему рендерит
ответы модели markdown'ом, и там ссылки текстовые. `extractBodyRefs` на боевом пути записи
больше не зовётся — он остался в `normalize.ts` и используется тестом бэкфилла как независимый
взгляд на текст.

## РЕШЕНИЕ Р8. Поиск для меню и batch-резолвер для чипов

**`entity.suggest`** — поиск сущности по заголовку: его зовут `@`-меню и пикер блокировок.
(В `/`-меню поиска сущностей нет вовсе — пункт «Ссылка на сущность» просто набирает `@`, чтобы
механизм поиска и вставки был один.) Грамматику `search=` не трогаем: там семантика целого слова
осмысленна и на неё завязаны сидированные смарт-листы, а меню, не находящее по началу набранного
слова, бесполезно — набор `@куп` через `search=` не нашёл бы «Купить кроссовки» (проверено
пробой).

Сопоставление — **по ВХОЖДЕНИЮ** (`lower(title) LIKE '%фрагмент%'`), а не по префиксу, как
задумывалось. Причина: якорь отнимал бы находимость, которую давал прежний путь («Отчёт за
квартал» обязан находиться набором «квартал»), а платы за снятие якоря нет — индекса под этот
запрос всё равно нет (Р1), а при Seq Scan оба шаблона стоят одинаково. Релевантность держит
ПЕРВЫЙ ключ сортировки: совпавшие с начала заголовка выше вхождений в середине, затем свежесть,
затем id (тай-брейк обязателен — `updated_at` у всего, созданного одним `batch_execute`, один).

Поле входа зовётся `term`, а не `prefix`: имя `prefix` обещало бы читателю не то, что делает
код. Не `query` — это слово в кодовой базе занято смарт-листами. Архивные из выдачи
отфильтрованы (их прячет весь UI), закрытые задачи — НЕТ (упомянуть сделанное — валидный
сценарий, а чип сам зачёркивает `done`). Вход только tRPC, модели процедура не раздаётся.

Пикер блокировок перешёл на ту же процедуру, извиняющаяся подсказка «по целому слову» исчезла.

**`entity.resolveRefs({ ids })`** — заголовки для чипов одним запросом: `{id, title, emoji,
status, archived}` и ничего лишнего. Потолок — `ENTITY_RESOLVE_REFS_MAX = 200`, вынесен
константой, потому что его читает и клиент: тело со ссылками режется на пачки ровно по нему
(`RefTitlesContext.tsx`). Список НЕ обрезается — обрезание было бы молчаливой потерей заголовков
у хвоста тела; тело с 201 упоминанием платит одним лишним запросом. Оговорка честности: пачки
уходят одновременно, но `httpBatchLink` склеивает их обратно в ОДИН HTTP-запрос, поэтому
«параллельно» обещать нельзя — обещано только «не запрос на ссылку».

**Архивные `resolveRefs` НЕ фильтрует — намеренно** (ревью И14): ссылка на архивную сущность в
теле остаётся ссылкой, и спрятать заголовок значило бы показать вместо названия обрубок id.
Признак `archived` отдаётся, рисовать решает чип. Ненайденные (в т.ч. чужие под RLS) просто
отсутствуют в ответе.

Секция «Блокировки» на вкладке «Детали» переехала с per-id `entity.get` на ту же процедуру —
шторм запросов исчез и там.

## РЕШЕНИЕ Р9. Экран — три таба: Сущность · Детали · Тред

**«Сущность»** — чистый документ: emoji, заголовок (`NativeRow` с чекбоксом задачи), полоса
прогресса цели, тело.

**«Детали»** — всё, что известно о сущности помимо текста, секциями: карточки аспектов,
подзадачи, блокировки, связанное. Данные приезжают тем же `entity.get` — разделение на вкладки
не завело ни одного нового запроса.

**«Тред»** — без изменений.

`keepMounted` — опция ВКЛАДКИ, а не поведение по умолчанию. Он поднят у «Сущности» (иначе уход
на «Детали» уничтожил бы несохранённый текст и всю историю Ctrl+Z, а заодно гонял бы двухфазное
монтирование заново) и у «Деталей» (её секции и раньше жили на единственной вкладке, то есть
живыми обходятся в те же запросы). У «Треда» его НЕТ: `ChatThread` на монтировании заводит
`chat.listMessages`, и держать его живым значило бы платить запросом за вкладку, которую не
открывали.

**Полоса прогресса цели остаётся на «Сущности»**, хотя сама карточка `orbis/goal` уезжает в
«Детали»: у цели прогресс — то, ради чего её открывают.

Четыре таба (со «Связями» отдельно от «Свойств») рассмотрены и отклонены: разделение чище по
смыслу, но на узком экране четыре вкладки тесны, и почти всегда одна пуста.

§3.5 PRD (`docs/prd/02-core-os.md`, раздел «§3.5 Detail-экран») нормировал секции 1–8 одним
списком; он приведён к трём вкладкам этой же работой (Задача 16), включая перестановку пунктов
и сверку всех ссылок на нумерацию §3.5 в коде и документах.

## РЕШЕНИЕ Р10. Сохранение по паузе; говорим только о проблеме

Сохранение — по паузе в наборе **2 с** (`SAVE_DEBOUNCE_MS`), плюс принудительно `flush()` с
экрана и на размонтировании. Мутация уходит только при реальном изменении документа — сравнение
по смыслу (Р5). Сдержанность не косметическая: `onSettled` зовёт `invalidateGraph(utils)` —
инвалидацию всего графа.

Шлём `bodyDoc` + `expectedUpdatedAt` с точной строкой `updatedAt`, которую клиент видел. Из двух
известных берётся ПОЗДНЯЯ — подтверждённая последним ответом сервера или из кэша: кэш узнаёт
новое значение только с перечитывания, а оно может опоздать, и второе сохранение подряд ловило бы
409 без всякой чужой правки. `applyPatch` расширен на `bodyDoc`.

**Клиент markdown НЕ сериализует — вообще.** Оптимистичный патч кладёт в кэш только документ;
`body` остаётся прежним до ответа сервера, который и есть единственный автор проекции.
Две причины, обе весомые. Во-первых, вес: `serializeBody` тянет за собой всю схему документа
(**154.48 кБ gzip** отдельным чанком, замер ниже), и вызов её из `applyPatch` затащил бы этот
груз в чанк `DetailScreen`, то есть **до первого кадра**. Во-вторых, единственность: пока
проекцию делает только сервер, клиентская и серверная версии не могут разойтись.

Следствие для состава: `@orbis/shared/doc` импортируется **только** из ленивого чанка редактора
(`features/entity-editor/*`), где Tiptap и так есть, и никогда — из эагерной части; в эагерных
файлах допустим лишь `import type`. Отдаётся отдельным подпутём, а не через корневой баррель
`@orbis/shared`: баррель собран из `export *` и импортируется эагерными модулями web. Ровно по
этой причине сравнение документов и список типов блочных id живут в отдельном ЛИСТОВОМ файле
(`strip-ids.ts`): их зовёт автосохранение, а его монтирует экран detail.

**Индикатор состояния — только о проблеме.** Раньше момент сохранения был явным (ушёл фокус —
сохранилось), и обратная связь не требовалась. Автосохранение этот момент убирает, поэтому:
в норме тихо; «Сохраняем…» — только если запрос идёт дольше секунды (`SLOW_SAVE_MS`);
«Не сохранено» — висит, пока не сохранится, и гасит его только успех. Успех отдельно не
празднуем: постоянный статус в углу — ровно та панель инструментов над каждой заметкой, от
которой экран отказывается сознательно.

**Один запрос за раз.** Пока сохранение в полёте, второй не уходит — ни по паузе, ни по
`flush()`: `@tanstack/query` снимает наблюдателя с прежней мутации, и у первого запроса пропали
бы ВСЕ поштучные колбэки разом. Отложенное досылается по оседанию первого. У полёта есть выдержка
30 с: промис `fetch` при оборванном соединении может не оседать никогда, и без неё одна такая
отправка запирала бы запись до перезагрузки.

**Два отказа различаются, и это несущее правило.** `STALE_VERSION` (409) — «перечитайте и
повторите»: баннер «Изменено в другом месте — обновите» и кнопка «Обновить». `VALIDATION`
(приезжает как `BAD_REQUEST`) — ТЕРМИНАЛЕН: тот же документ будет отвергнут снова, автосейв
обязан остановиться, а черновик на диске получает пометку `rejected` и сам больше не досылается.
Документ в редакторе при 409 не подменяется — §5.2 предлагает «повторить вручную», значит
повторять должно быть откуда.

Свежий серверный документ подменяет содержимое, только если редактор не в фокусе. Правило
`key={entity.id}`, а не по `updatedAt`, сохраняется буквально: ремоунт по ключу стирал бы
набранное за время запроса.

`Ctrl+Z` — история редактора, не журнальный Undo. Ручную правку отменяют там же, где сделали;
«отмени последнее» остаётся про действия агента.

**Окно конфликта расширилось, и это принимается осознанно.** Раньше правка была коротким явным
эпизодом; теперь редактор открыт всё время, пока сущность на экране, а модель пишет в те же
тела через fast-path. Настоящее лекарство — слияние (Р13); до него работают 409 и черновик.

## РЕШЕНИЕ Р11. Офлайн: черновик переживает закрытие вкладки

PWA плюс всегда открытый редактор делают сценарий «пишу в метро» обыденным. Retry-буфер здесь
не помощник: он принимает только `entity.create` от fast-path, а у `update` есть
`expectedUpdatedAt`, который протухает — правка, пролежавшая час, приедет с 409, то есть
отложенная отправка обещала бы то, чего не может выполнить.

Поэтому: пока есть неотправленные правки, документ лежит в **localStorage** под ключом
`orbis:body-draft:<entityId>` вместе с меткой версии, поверх которой он набран, и признаком
`rejected`. Запись на диск идёт ПЕРЕД всеми причинами не отправлять — страховка обязана работать
именно тогда, когда отправка не работает. При первом успешном сохранении запись стирается, и
делает это обвязка уровня мутации, а не хук: самый важный досыл уходит на размонтировании, когда
наблюдателя уже отцепили и поштучных колбэков не будет вовсе.

Вернулись к записи с черновиком на диске:

- документ совпал с телом записи по смыслу → черновик стирается молча (частый сюжет: успех дошёл
  до сервера, ответ потерялся);
- `updatedAt` не менялся и приговора нет → досылаем тихо;
- менялся или стоит `rejected` → баннер с выбором «оставить моё» / «выбросить». «Оставить моё»
  кладёт правку ПОВЕРХ чужой сознательно (уйди она со старой меткой — сервер ответил бы 409, то
  есть кнопка не делала бы ничего); «выбросить» стирает ровно ПОКАЗАННЫЙ черновик, а не «тот,
  что лежит на диске сейчас».

Это персистенция содержимого сущности на диск браузера, и она принята владельцем явно (случай
отличается от истории чата: не архив, а собственный неотправленный черновик, живущий до первого
успеха). Разрешение не переносится ни на что другое.

Правило разрешения при возврате нарочно грубое и честное (сравнили `updatedAt`, спросили
пользователя). Именно его потом заменит слияние — не переделывая ничего вокруг.

## РЕШЕНИЕ Р12. HTML в документ не попадает

`react-markdown` не парсит HTML вовсе (`rehype-raw` не подключён) — это записано как эшелон
обороны, потому что разметку в тело приносит ответ модели. Tiptap же по умолчанию принимает HTML
при вставке и при парсинге, поэтому правило фиксируется явно и **тремя конкретными настройками**:

1. **Протоколы ссылок** — `Link` внутри StarterKit конфигурируется **`isAllowedUri`**
   (`https`, `http`, `mailto` и относительные пути): `javascript:` и родня ссылкой не становятся.
   Опции `protocols` здесь нет намеренно — она РАСШИРЯЕТ базовый список, а не сужает (проверено
   ревью). Настраивать надо ИМЕННО StarterKit: `Link` живёт внутри него, элемента с
   `name === 'link'` в массиве расширений нет, и `map` по имени молча не нашёл бы никого — так в
   плане v1 умер белый список протоколов.
2. **Вставка из буфера** — `editorProps.transformPastedHTML` снимает разметку, СОХРАНЯЯ границы
   блоков: `<style>`, `<script>`, `<head>`, `<noscript>` вырезаются целиком, `<br>` и закрытия
   блочных элементов становятся переносами, результат собирается абзацами. Голое
   `html.replace(/<[^>]*>/g, '')` из плана v1 склеивало всё в одну строку и тащило в документ
   текст, которого на экране не было (ревью И11).
3. **Схема** принимает только объявленные ноды и marks; всё прочее не создаётся.

## РЕШЕНИЕ Р13. Швы под будущее заложены; инфраструктура не строится

Владелец подтвердил: совместное редактирование **людьми и агентами** будет обязательно. Здесь
оно не реализуется, но конструкция обязана его пережить без разворотов.

**Заложено этой работой:**

1. направление правды `документ → markdown` (Р1) — переворачивать потом значило бы переписать
   оба конца;
2. структурное хранение `body_doc` — превращается в Y.Doc готовой утилитой
   `prosemirrorJSONToYDoc`, схема нод при этом та же;
3. версия схемы в документе (Р1) — миграции формата возможны без потери содержимого;
4. стабильные id блоков (Р5) — на них ляжет блочный контракт агента
   (`body_replace_block`/`body_insert_after`/`body_delete_block` вместо перезаписи тела);
5. единственный путь записи через executor (Р6) — иначе к моменту CRDT сливать пришлось бы два
   пути записи, а не два текста;
6. общая схема документа в `@orbis/shared` (Р3) — клиент, сервер и будущий агентский
   применятель понимают документ одинаково;
7. грубое правило разрешения при возврате из офлайна (Р11) — точка, куда встанет слияние.

**Сознательно НЕ строится:** Y.js, WebSocket, Hocuspocus, awareness, курсоры присутствия;
membership и роли (D11); блочные инструменты модели; атрибуция авторов; комментарии.
`expectedUpdatedAt` с 409 остаётся нетронутым — полумеры вокруг конфликтов сейчас помешали бы
снять их нормально потом.

**Проверка на отсутствие разворотов.** CRDT: `body_doc jsonb` → Y.Doc, схема та же, id на
месте, контракты те же. Агентские блочные инструменты: чистое добавление (плюс долг Р6 — научить
inverse документу). Люди: правило в `onAuthenticate` плюс RLS-шаблон из чек-листа D11. Ни один
шаг не требует переделать сделанное здесь.

## Состав редактора

- **Режим один.** `BodySection` с `editing`, `startEditing` и кнопкой «Редактировать» ушла
  целиком.
- **Slash-меню** (`@tiptap/suggestion`, `slash/items.ts`) — двенадцать пунктов: заголовки 1–3,
  список, нумерованный список, задача (подсказка «чеклист»), цитата, код, таблица 2×2,
  разделитель, «Смарт-лист», «Ссылка на сущность». Фильтруется по подписи И подсказке.
  - «Смарт-лист» **вставляет блок** с осмысленной заготовкой
    (`{{query: sortBy=updated_at:desc, limit=10, title=Новый список}}`), а не открывает
    `QueryBlockEditor`, как задумывалось: настроить свежий блок можно тут же кнопкой «Настроить»
    на его виджете, и это единственный путь, у которого есть начало.
  - «Ссылка на сущность» просто набирает `@` — второй пикер разошёлся бы с первым при первой же
    правке.
  - **Пункта «Создать сущность» в `/`-меню НЕТ**: создание из набранного живёт в `@`-меню
    последней строкой «Создать «…»» — там, где уже набран текст будущего заголовка.
- **`@`** — упоминание сущности тем же механизмом и тем же поиском (`entity.suggest`, поле
  `term`). Строки «Создать «…»» нет, пока поиск не ОТВЕТИЛ про этот самый набор: Enter, нажатый
  быстрее ответа, молча заводил бы дубль уже существующей сущности. Вместо неё — немая строка
  состояния («Поиск…», «Поиск недоступен»): меню не мигает, Enter не проваливается в редактор
  переносом строки.
- **Чип сущности** (`entityRef` NodeView): актуальный заголовок из `entity.resolveRefs`, emoji,
  зачёркивание у закрытых задач, серая пометка у ненайденной или недоехавшей. Пока резолв едет —
  показывается вмороженная подпись из текста, нет и её — обрубок id. Клик — `openEntity`;
  Ctrl/Cmd/Shift/Alt-клик и не-основная кнопка остаются штатными жестами браузера.
- **`queryBlock` NodeView** — существующий `QueryBlock`; «Настроить» открывает существующий
  `QueryBlockEditor` и правит АТРИБУТ ноды. `bodySegments` / `queryBlocks` / `firstQueryBlock`
  остаются — они читают проекцию и питают бейджи pinned-сущностей.
- **Bubble-меню** по выделению — четыре действия форматирования (жирный, курсив, зачёркнутый,
  код) и одно над блоком: **«Удалить блок»**. Пункта **«превратить в…» НЕТ** — задумывался, но в
  работу не вошёл; смена типа блока остаётся за `/`-меню, чьи пункты применяют
  `setNode`/`toggle*` к текущему блоку (сам `/` при этом набирается в начале строки или после
  пробела — таково умолчание `@tiptap/suggestion`). Кнопки «ссылка» в панели тоже нет, хотя
  марка `link` в схеме есть.
  - **Гранулярность «Удалить блок»: ПУНКТ, а не весь список.** Цель — ближайший предок, чей
    родитель документ ЛИБО список (список опознаётся ГРУППОЙ схемы `list`, а не перечнем имён).
    Снести чеклист из двадцати пунктов из-за каретки в седьмом — потеря данных за иконкой в
    четырнадцать пикселей и без подтверждения. Диапазон считается по ОБОИМ краям выделения.
  - **Ячейка таблицы — НАЗВАННОЕ исключение:** `tableRow` и `tableCell` групп не объявляют,
    поиск проходит их насквозь — и каретка в ячейке с обычным текстом убирает ВСЮ таблицу. Так
    и оставлено: удалять ячейку бессмысленно (таблица обязана оставаться прямоугольной), а
    удаление строки — другая семантика, которой в задаче нет. Решение закреплено тестом.
    Оговорка, без которой правило читается шире, чем работает: если в ячейке лежит СПИСОК,
    родитель-список находится раньше глубины 1, и жест убирает пункт (а когда он единственный —
    список), оставляя таблицу целой. Это не исключение из исключения, а то же правило
    гранулярности; на трёх формах табличных вложений оно закреплено тестами.
- **Перемещение блока — `Alt+↑/↓`** (команды ProseMirror, вес ~0). Drag handle мышью в работу
  не входит — см. «Что НЕ входит».
- **Плейсхолдер** «Заметки…» — та же константа, что рисует первый кадр, и только на ПУСТОМ теле.
- **Markdown-тумблер** — пункт меню ⋮ (у записи без документа пункта нет вовсе): показывает
  проекцию — ровно то, что лежит в `body`, — правит текстом, на выходе парсит обратно.
  Не распарсилось молча не бывает: `parseBody` не бросает, он уводит непонятое в `rawBlock`
  дословно, поэтому появление НОВОГО неразобранного блока требует второго «Применить» с
  предупреждением. О том, что было неразобранным ДО правки, не спрашиваем — иначе подтверждение
  требовалось бы на каждую опечатку в соседнем абзаце и его перестали бы читать.
- **Мобильный**: `/` работает и там, и это единственный вход в вставку блоков. Кнопка «+» в
  панели над клавиатурой **отложена — решением контроллера, ждёт подтверждения владельца** (в
  цикле владелец по этому пункту не высказывался; контроллер принял умолчание плана). Отдельной
  задачи не заведено. Перетаскивания блоков нет (drag handle исключён); порядок меняется
  `Alt+↑/↓` с внешней клавиатуры и действиями bubble-меню.
- **Двухфазное монтирование — ОБЯЗАТЕЛЬНО.** Первый кадр рисует нынешний `Markdown` вперемежку
  с живыми виджетами через `bodySegments` (голый `<Markdown>` показал бы `{{query:…}}` строкой,
  которая через мгновение прыгнула бы на виджет — у сида All Tasks тело и есть один такой блок).
  Редактор монтируется по простою (`requestIdleCallback`, запасной таймер 1500 мс для Safari и
  jsdom) ИЛИ по первому касанию тела — не по `setTimeout(0)`: иначе чанк схемы тянулся бы при
  каждом чисто читательском открытии записи. Событие — `click`, а не `pointerdown`: последний
  приходит и в начале протяжки выделения, и в начале тач-прокрутки, то есть любая прокрутка по
  телу тянула бы 182 кБ gzip.

  > **ЗАМЕР НА ВЕТКЕ** (`bun run --filter @orbis/web build` на HEAD ветки; числа — как их
  > печатает vite): первый кадр (`index` + `trpc` + `Button` по `dist/index.html`) —
  > **218.86 кБ gzip**; отдельными ленивыми чанками `doc` (схема документа) **154.48**,
  > `BodyEditor` **27.88**, `DetailScreen` **18.49**, `MarkdownToggle` **0.90**. Схемы в чанке
  > detail нет — проверено чтением статических импортов собранного чанка (`doc-*.js` лежит
  > только в списке динамических зависимостей).
  >
  > **Числа «до работы» этой командой получены быть НЕ МОГУТ** — они сняты на `main` и здесь не
  > перепроверялись (ветку в этом дереве не переключают): первый кадр **219.49**, чанк
  > `DetailScreen` **30.07** — замер Задачи 15 той же командой. Вывод «первый кадр не вырос»
  > стоит на ЭТОЙ паре, 218.86 против 219.49, и надёжен ровно настолько, насколько надёжен
  > чужой замер; своими глазами здесь проверено только левое число.
  >
  > Спайковые «~160 кБ» — это был ОДИН чанк редактора вместе со схемой; сегодня то же хозяйство
  > разделено на два чанка и весит 182.36 кБ на двоих: к схеме добавились чип, виджет
  > смарт-листа, оба меню и блочные id. Ленивым оно быть не перестало.

**Необязательное, срезано:** карточка сущности по наведению на чип — не сделана.

## Инварианты, которые проверяются, а не подразумеваются

1. **Канон идемпотентен и не меняет смысла.** Проверяются два разных утверждения на наборе
   фикстур (`packages/shared/src/doc/convert.test.ts`): `canonicalizeBody` от канона даёт тот же
   канон, и повторный разбор канона даёт ТУ ЖЕ структуру документа — канон вправе переписать
   буквы, но не вправе переписать документ. У обоих тестов стоит страж вакуумности: тело,
   уехавшее в `raw`, выполняет любой такой инвариант тождественно и не утверждает ничего.
2. **Каноничность сидов:** `canonicalizeBody(seed).body === seed` для всех пяти сидированных тел,
   и ни одного `rawBlock` в разборе — `apps/server/src/seed/seed-canon.test.ts`. Это ОТДЕЛЬНЫЙ
   тест, и он заведён именно этой работой: `onboarding.test.ts` сверяет константы сида с
   markdown-блоками PRD и конвертер не зовёт вовсе, то есть страховкой round-trip не был никогда
   (ревью И4).
3. **Согласованность пары:** после любой записи `body` равен сериализации `body_doc`. Прямая
   запись `body` в БД мимо конвертера запрещена; конверсия живёт в одном месте перед стадией
   записи (`executor.ts`) и в бэкфилле.
4. **`body` всегда валидный markdown** — на нём стоят FTS, промпт, MCP и бейджи pinned.
5. **Схема редактора равна схеме документа.** Множество нод и марок редактора ⊆ `DOC_EXTENSIONS`:
   серверный гейт спрашивает схему напрямую, и любая лишняя нода или марка сделала бы нерабочим
   КАЖДОЕ сохранение. Добавки редактора — только атрибутные (`UniqueID`) и плагинные
   (Placeholder, MoveBlock, bubble-меню, `/`- и `@`-меню); равенство стерегут тесты на живом
   экземпляре.
6. **Открытие записи не пишет в базу.** Ни `trailingNode`, ни простановка блочных id, ни эхо
   редактора на монтировании не считаются правкой: сравнение идёт по смыслу. Закреплено тестом
   «размонтирование без набранного в сеть не ходит вовсе».

## Известные границы

- Каждое автосохранение шлёт **весь документ**. При длинных заметках на мобильном это заметно;
  снимается переходом на CRDT (дельты), не раньше.
- **Undo теряет блочные id** (Р6): inverse строковый, документ пересобирается из текста.
- **Ссылка внутри блока кода и inline-кода не даёт backlink** (Р7). Ссылка внутри `raw`-блока —
  даёт: там работает регэксп.
- **Экранирование текста при сериализации** есть, но набор символов ýже, чем записал спайк.
  Замерено на ветке: экранируются `*`, `[`, `]`, `` ` `` (`звезда * тут` → `звезда \* тут`);
  `_` и `&` НЕ экранируются (`due_date` остаётся собой), а HTML-сущность на входе, наоборот,
  разворачивается (`x &amp; y` → `x & y`). Экранирование идемпотентно. **На FTS не влияет** —
  проверено на живой БД: `to_tsvector('simple', …)` даёт идентичный вектор для обеих форм всех
  трёх случаев. Остаётся косметический шум в тексте, который читает модель.
- **Таблицы нормализуются по ширине столбцов** (`| a | b |` → `| a   | b   |`) и получают
  собственные переносы по краям, из-за чего между таблицей и соседним абзацем в каноне стоит
  `\n\n\n`. Идемпотентно, инвариант пары цел, но в diff шумит. В `raw` тело с таблицей при этом
  НЕ уходит (в отличие от того, что предполагал первоначальный дизайн со сверкой round-trip):
  таблица — понятая схемой нода. В `raw` уезжает только таблица с чертой `|` внутри ячейки либо
  с непонятой схемой конструкцией в ячейке (картинка) — и уезжает целиком, ячейками нода не
  дробится.
- **`UniqueID` не входит в схему сервера.** Документы, которые сервер собирает из строкового
  `body` модели, приезжают БЕЗ блочных id — расширение живёт только в редакторе.
- **Гранулярность двух жестов над блоком не согласована.** «Удалить блок» работает на уровне
  ПУНКТА списка, `Alt+↑/↓` — на уровне СПИСКА целиком (каретка во вложенном списке двигает весь
  список верхнего уровня). Разница осознанная и разная по цене ошибки: у удаления цена —
  потерянные данные, у перемещения — лишнее движение, которое видно и отменяется тем же жестом.
  Сведение к одному правилу — отдельная работа с собственными тестами; до тех пор одно правило в
  другое не переносить.
- **`Alt+↑/↓` на macOS спорит с системной навигацией по абзацам.** Жест работает при фокусе в
  редакторе; обхода не изобретаем.
- **Смарт-лист внутри забора кода виден по-разному в двух кадрах.** Первый кадр разбирает тело
  регэкспом (`bodySegments`) и рисует виджет; схема разбирает забор раньше нашей грамматики и
  считает то же место кодом. Расхождение записано тестом, а не подразумевается. Правило колонки
  (обёртка только с начала строки) в обоих разборах одно — расходится только знание о заборах.
- **Первый кадр рисуется из серверного `body`, а редактор — из документа (локального или
  серверного).** Поэтому «Применить» в markdown-тумблере до подъёма редактора экран не меняет:
  документ уже новый, а показанный текст ещё старый. Окно достижимо в Safari (там редактор ждёт
  запасного таймера 1500 мс).
- **Баннеры конфликта и черновика и индикатор сохранения живут ВНУТРИ вкладки «Сущность».**
  Отказ, случившийся на «Деталях» или «Треде», не виден до возврата на «Сущность».
- **Бэкфилл не пересчитывает `body_refs`.** Колонка остаётся такой, какой её посчитал прежний
  регэксп по тексту; тест бэкфилла стережёт то, что канон не портит сами ссылки в тексте на
  двенадцати формах их размещения. Расхождение правил (код-блок) выправится при первом
  сохранении тела.
- **Мобильный ввод не проверен** — IME, автокоррекция, голосовой набор. Только живое устройство.

## Спайк — проведён 2026-08-13

Полные результаты — `docs/superpowers/reviews/2026-08-13-editor-spike.md`. Коротко:

| Вопрос | Ответ спайка | Что показала реализация |
|---|---|---|
| Tiptap в jsdom | **Да**, 8/8 зелёные — но без полифилов прогон падает с кодом 1 при зелёных тестах | подтвердилось; полифилы — первая задача плана |
| Парсер на Bun без DOM | **Да**, без оговорок | подтвердилось |
| Round-trip сидов | **Буква в букву**, идемпотентность 20/20 | подтвердилось (`seed-canon.test.ts`) |
| Вес чанка | **~160 кБ gzip** одним чанком без drag handle при бандле 219 | 154.48 (схема) + 27.88 (редактор) двумя чанками; первый кадр 218.86 |
| Мобильный ввод | **Не проверен** — нужно живое устройство | так и остался непроверенным |

**Первая задача плана — полифилы ProseMirror в тестовой обвязке**, до любого кода редактора.
ProseMirror зовёт `Range.prototype.getClientRects` и `document.elementFromPoint`, которых в
jsdom нет; вызовы уходят в uncaught exception, тесты при этом остаются зелёными, а **прогон
падает** — красный CI без единого упавшего теста. Реализовано в
`apps/web/tests/prosemirror-polyfill.ts`.

**Осталось непроверенным:**

1. **Мобильный ввод** — IME, автокоррекция, голосовой набор. Проверяется только на живом
   устройстве (jsdom не воспроизводит, эмуляция DevTools тоже). Риск не блокирующий, но
   ненулевой; проверка за владельцем.
2. **Round-trip на корпусе тел с прода.** Заведена read-only команда `bun scripts/ops.ts
   audit-bodies`: она печатает только агрегаты (сколько тел изменит канон, сколько получат
   `raw`-блоки, у скольких ссылки внутри `raw`, сколько нетривиальных, сколько упало на парсе) —
   сами тела не покидают процесс. **Её прогон на проде — стоп-кран перед бэкфиллом**, и он за
   владельцем: локальные числа бесполезны, на стенде тела пусты. Гейт: заметная доля `raw` или
   ненулевые «ссылки внутри raw» означают, что до конверсии надо расширять белые списки токенов,
   а не гнать конверсию.

## Что НЕ входит

- Совместное редактирование, присутствие, курсоры, атрибуция авторов, комментарии (Р13).
- Membership, workspace'ы, роли (D11).
- Блочные инструменты для модели; контракт `entity_update{body}` остаётся строковым.
- Панель свойств в стиле Notion над телом: карточки аспектов — формы по JSON-схеме реестра, и
  свёртка их в строки — отдельный редизайн сопоставимого объёма. Вместо этого — таб «Детали»
  (Р9).
- **Drag handle (перетаскивание блоков мышью)** — решение владельца от 2026-08-13 по итогам
  замера. Стоит 40 кБ gzip, из них ~25 кБ — `@tiptap/extension-collaboration` + `y-tiptap` +
  `yjs`: расширение тянет Y.js, то есть ровно ту инфраструктуру, которую откладывает Р13.
  Платить за неё, не используя ни одной её возможности, — D11 наизнанку. Сценарий для Orbis
  редкий (тела короткие, значительную часть пишет модель, главный жест — «записать и потом
  прочитать»), на мобильном жест заведомо хуже десктопного. Полезное из трёх его функций —
  меню блока — уехало в bubble-меню. **Решающее: после перехода на CRDT yjs будет в бандле по
  любому, и drag handle подешевеет с 40 кБ до ~15** — вернуться к нему стоит вместе с
  курсорами и присутствием. Взамен сейчас — `Alt+↑/↓`.
- **Панель «+» над клавиатурой на мобильном** — отложена решением контроллера (см. «Состав
  редактора»), ждёт подтверждения владельца.
- **Пометка «не разобрано» на `raw`-блоке и правка его на месте** — не сделаны (Р3).
- **Пункт «превратить в…» в bubble-меню** — не сделан.
- Вложенные страницы, callout/toggle-блоки, «unlinked mentions», вставка ответа модели прямо в
  текст, повышение пункта чеклиста до сущности-подзадачи, карточка сущности по наведению на чип.
- Правка тегов и emoji на месте, кнопка «+аспект» — известные долги §3.5, к работе отношения
  не имеют.

## Приёмка

1. Тело правится без смены режима: чипы и виджеты остаются собой, пока идёт набор.
2. `/` открывает меню блоков с фильтром по набранному; `@` ищет сущность и находит её по
   ВХОЖДЕНИЮ набранного фрагмента в заголовок, совпадения с начала — выше.
3. Смарт-лист вставляется из UI в позицию каретки и настраивается на месте.
4. Ссылка вставляется через `@` напрямую и через `/` пунктом «Ссылка на сущность» (он набирает
   тот же `@`); чип показывает актуальный заголовок и статус; клик открывает сущность в текущей
   вкладке, Ctrl/Cmd-клик — в новой; заголовки резолвятся пачками не больше 200 и без обрезания
   списка.
5. Тумблер markdown показывает ровно то, что лежит в `body`, и возвращает правку в документ;
   новый неразобранный текст не сохраняется без явного подтверждения.
6. Таб «Детали» показывает аспекты, подзадачи, блокировки и связанное; полоса прогресса цели
   осталась на «Сущности»; новых запросов не появилось.
7. Пять сидированных тел канонические: `canonicalizeBody(seed).body === seed` и ни одного
   `rawBlock`; `onboarding.test.ts` зелёный без послаблений; `serialize(parse(x))` идемпотентен
   на фикстурах.
8. `body` в базе остаётся валидным markdown'ом: FTS, бейджи pinned, промпт и MCP работают без
   правок.
9. Сохранение уходит по паузе и на уходе с записи; «Не сохранено» видно при отказе; 409
   показывает баннер и не теряет черновик; терминальный отказ останавливает автосейв и метит
   черновик.
10. Правка, набранная офлайн, переживает закрытие вкладки и доезжает при возврате сети; при
    разошедшейся версии пользователю показывают выбор, а не молча затирают.
11. Документ с незнакомой версией схемы пересобирается из `body` и не теряет текст; такой
    документ не принимается на запись.
12. **Открытие сущности не отправляет ни одной мутации** — ни от `trailingNode`, ни от блочных
    id, ни от эха редактора.
13. Открытие сущности не тянет чанк редактора в первый кадр: просмотр рисуется сразу, редактор
    монтируется следом. Чанк `BodyEditor` существует отдельным файлом, и страж
    `scripts/check-lazy-chunks.ts` знает его поимённо — в списке `LAZY_EDITOR_MODULES` (не в
    `LAZY_SCREENS`: это не экран роутера), вместе с `MarkdownToggle`.
14. Сьюты web и server зелёные **по коду возврата, а не по счётчику тестов** (полифилы
    ProseMirror на месте); страж ленивых чанков в CI не сломан.
