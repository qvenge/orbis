# Три кандидата фазы E — план реализации

> **Для агентных исполнителей:** ОБЯЗАТЕЛЬНАЯ СУБ-СКИЛЛ: `superpowers:subagent-driven-development`.

**Цель:** параллельные сливы retry-буфера перестают слать одну операцию дважды, а индикатор
«Ждут отправки» получает способ досыла; отказы расчёта прогресса цели перестают быть
безмолвными и незадросселированными; перф-гейт получает седьмую операцию — чтение цели.

**Архитектура:** три независимых по файлам задачи. Порядок — по наблюдаемому вреду
(решение Р1 спеки `docs/superpowers/specs/2026-08-09-phase-e-candidates-design.md`):
web-буфер → серверные логи → перф-гейт.

**Стек:** React 19 + zustand + Vitest (web), bun/Hono/tRPC/drizzle + bun test (server).

## Глобальные ограничения

- Тесты ТОЛЬКО через `bun run test`; web-пакет — `bunx vitest run` из `apps/web` для одного
  файла (там vitest, не bun test); серверный файл — `bun run --filter @orbis/server test -- <файл>`.
  Код возврата линта снимать отдельным вызовом.
- **Серверный сьют делает `truncateAll`** — не гонять одновременно с ручными проверками БД.
- **Дроссель логов обязан быть строго in-memory:** `apps/server/src/goals/progress.test.ts:571-572`
  пинит счётчиком драйвера ровно 6 запросов на обычную сущность и 10 на цель; любая
  реализация, читающая или пишущая состояние в БД, добавит запрос и уронит этот тест.
- Тесты не полагаются на системные часы (carried-решение проекта) — дроссель не должен
  зависеть от времени.
- Локальный Supabase поднят: `postgresql://postgres:postgres@127.0.0.1:54322/postgres`.
- Факты плана проверены разведкой, но **могут быть неверны** — проверяй пробоем и опровергай.

- [ ] **Шаг 3: Сериализовать слив**

В `apps/web/src/state/retry.ts` завести модульную переменную `inFlight: Promise<number> | null`
и переписать `flushNow`:

```ts
  flushNow: async () => {
    if (!sendImpl) return 0;
    // Слив сериализован: два параллельных вызова видели ОДИН снимок очереди
    // (retry-buffer/index.ts:51) и слали каждую операцию дважды. Сервер идемпотентен
    // по client-UUID, поэтому дублей сущностей не возникало, но лишние запросы и второй
    // invalidateGraph приходились ровно на момент, когда сети нет.
    if (inFlight) return inFlight;
    inFlight = (async () => {
      let total = 0;
      try {
        // Перезапуск, а не один проход: очередь могла пополниться, пока шёл слив
        // (fast-path кладёт запись и тут же зовёт flush). Без цикла такая запись ждала бы
        // следующего триггера, а их всего два — старт приложения и событие 'online'.
        for (;;) {
          const before = buffer.size();
          if (before === 0) break;
          total += await buffer.flush(sendImpl);
          // Ничего не ушло (сеть по-прежнему лежит) — не крутимся вхолостую.
          if (buffer.size() >= before) break;
        }
        set(snapshot());
        return total;
      } finally {
        inFlight = null;
      }
    })();
    return inFlight;
  },
```

- [ ] **Шаг 3: Дроссель + логи конфигурационных отказов**

В `apps/server/src/goals/progress.ts` завести in-memory дроссель:

```ts
// Дроссель логов — строго in-memory: progress.test.ts пинит счётчиком драйвера ровно
// 6 запросов на обычную сущность и 10 на цель, поэтому любое состояние в БД (таблица,
// advisory lock) уронило бы этот тест лишним запросом.
//
// Ключ — САЙТ лога плюс цель, а не ярлык отказа: оба compute_failed-теста идут с одним
// thisEntityId в одном процессе, и ключ по ярлыку схлопнул бы их, погасив ассерт второго.
const seenFailures = new Map<string, number>();

function logFailure(site: string, goalId: string | null, message: string, cause?: unknown): void {
  const key = `${site} ${goalId ?? ''}`;
  const seen = (seenFailures.get(key) ?? 0) + 1;
  seenFailures.set(key, seen);
  // Первый раз — целиком; дальше молчим, но каждую сотню печатаем счётчик, чтобы шторм
  // был виден, а поток логов не рос линейно с числом чтений.
  if (seen === 1) console.error(message, cause ?? '');
  else if (seen % 100 === 0) console.error(`${message} (повторов: ${seen})`);
}
```

Провести через него оба существующих `console.error` и добавить логи для молчащих ярлыков
(`array_field`, `invalid_query`, `invalid_field`) — тем же дросселем, с текстом, называющим
ярлык и цель. Точные формулировки пиши сам, по-русски, в стиле соседних строк файла.

**Заодно**: докблок около `:122-125` обосновывает синтаксический детект `[]` тем, что
«каталог типизирует любой массив как строку» — это перестало быть правдой (в каталоге теперь
есть тип `array`). Приведи обоснование к факту, не меняя поведение.

### Task 3: Перф-гейт получает седьмую операцию — чтение цели

**Files:**
- Modify: `apps/server/src/test/perf.ts` (id-хелперы около :69-71; фикстура около :148-159; докблок :128-136)

- Modify: `docs/prd/02-core-os.md` (приёмка §9 п.1, около :652)
- Modify: `docs/implementation/02-ops-runbook.md` (около :564-566)

**Мотивировка — честная, а не переписанная из бэклога.** Бэклог требовал седьмой порог,
чтобы «увидеть +4 запроса, ~+4…6 мс». Он их не увидит: дельта уже запинена точнее любого
порога (`goals/progress.test.ts:571-572` — ровно 6 и 10 запросов), а разброс раннера CI
доходит до ×3. Седьмой порог нужен, чтобы у goal-пути появилось перф-покрытие против
**грубых** регрессий: потерянного индекса на агрегате, чтения всего графа.

- [ ] **Шаг 1: Цель в фикстуре — отдельной сущностью**

В `apps/server/src/test/perf.ts` завести детерминированный id цели рядом с `perfHubId`
(тем же uuidv5-паттерном) и создать цель в фикстуре.

**Нельзя навешивать `orbis/goal` на существующий хаб:** по хабу меряется порог
`entity.backlinks`, и добавление аспекта молча превратило бы его в замер другой операции.

Источник прогресса выбери сам и объясни выбор в отчёте: `count` по задачам (~их 1200)
или `sum` по транзакциям (~1000). Второй дороже и потому чувствительнее к регрессии —
но реши сам, посмотрев, что именно даёт более честное покрытие goal-пути.

- [ ] **Шаг 2: Замер и седьмой порог**

Добавить седьмую запись в замеры (`measureMedian`, число прогонов — как у соседних чтений)
и седьмую строку в `BUDGETS_MS`. Сверка ключей на `perf.test.ts:200` сама заставит порог
и замер приехать вместе.

**Порог откалибруй прогоном**, а не на глаз: запусти гейт, посмотри медиану, возьми запас
того же порядка, что у соседей (у существующих строк ×3–4). Фактические медианы на CI
и выбранное число впиши в отчёт.

- [ ] **Шаг 3: Сторож — прогресс обязан быть посчитан**

`computeGoalProgress` fail-soft: на `array_field`/`invalid_query`/`invalid_field` он выходит
**до** savepoint и агрегата, поэтому сломанная фикстурная цель дала бы дешёвый замер при
зелёном гейте. Добавь в тест-сторож фикстуры (около `:126-159`, там уже есть сторожи
fast-path и backlinks) проверку, что у прочитанной цели прогресс **посчитался** —
`current`/`target` присутствуют, а не `unsupported`.
