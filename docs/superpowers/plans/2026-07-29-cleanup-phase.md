# Уборочная фаза (между слайсом 2 и слайсом 3) — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** закрыть живые долги бэклогов слайса 2 (фазы A–D) до того, как их подхватит слайс 3:
ловушку релиза реестра аспектов (слайс 3 вводит `orbis/goal` — она сработает гарантированно),
рассогласование формата и сопоставления memory-правил (фича «система учится на исправлениях»
сегодня работает не полностью), горячий запрос backlinks на каждом открытии detail,
Important-хвосты фаз A/B/C и механизм измерения метрики покрытия транзакций (00-product §8).

**Architecture:** правки точечные, новых подсистем не вводится. Три принципа:
одна нормализация на обоих концах контракта (правило пишется и читается одним кодом shared);
проверка ловушки — на старте процесса, а не в голове релизящего; форма ответов
`readEntity`/карточек не меняется (контракт общий с LLM/MCP-диспатчем и запиннен тестами).

**Tech Stack:** тот же — Bun-монорепо, Hono + tRPC + Drizzle + PostgreSQL, React + TanStack Query,
`bun test` / vitest, RLS — pgTAP.

## Глобальные ограничения

- Проверки перед каждым коммитом: `bun run typecheck && bun run lint && bun run test` (из корня;
  голый `bun test` в корне уходит в `node_modules`/`spikes` и висит).
- Серверные тесты идут строго по одному против общей локальной БД (`truncateAll` в `beforeAll`);
  браузерный смоук и серверные тесты одновременно гонять нельзя.
- `bun run test:rls` требует `set -a && . ./apps/server/.env && set +a` перед прогоном.
- Деньги — только decimal-строки; любая запись в граф — только через executor.
- `packages/shared` не импортирует React/Hono/Drizzle/tRPC-server/AI SDK.
- Коммиты — conventional commits с русским описанием, footer
  `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>`.
- Схема аспектов НЕ меняется ни одной задачей этой фазы (иначе фаза сама наступит на ловушку,
  которую чинит; задача E1 при этом делает такую ошибку видимой на старте).

## Решения фазы (приняты автономно, требуют sign-off владельца постфактум)

1. **Разделитель правила: разбор принимает синонимы, запись остаётся канонической.**
   `parseRuleTitle` понимает `→`, `->`, `-->`, `=>`; `formatRuleTitle` по-прежнему пишет только
   U+2192. Причина асимметрии цены: стрелку U+2192 с клавиатуры не набрать, а правило,
   набранное руками или созданное моделью, сегодня молча мертво в детерминированных путях —
   но живо в системном промпте, поэтому на вопрос «что ты помнишь» AI его перечисляет.
   Отменяет пиннинг-тест «суррогаты не принимаются» (`memory/rule.test.ts`).
2. **Паттерн правила — неподвижная точка `normalizeCounterparty`.** `rulePatternFromTitle`
   прогоняет нормализацию повторно после снятия числовых токенов: «1234 CARD ПЯТЁРОЧКА» даёт
   «пятерочка», а не «card пятерочка». Иначе гейт эквивалентности и потребитель правила меряют
   разными линейками (и заголовок правила показывает пользователю служебный мусор).
3. **Сопоставление правила — по границе токенов**, а не подстрокой: «бар → Развлечения»
   больше не перехватывает «барбершоп». Согласуется с резолвом по алиасам (целое слово).
4. **Эскалация запускается и на пути `explicit-confirmation`** (батч 11+ операций исполняет
   `approvePending` мимо `runMutation`). Без этого «перенеси все 12 покупок» — самый
   естественный путь групповой рекатегоризации — не даёт предложения правила никогда.
5. **Три одинаковых исправления в ОДНОМ батче повтором НЕ считаются** — оставлено как есть.
   §7.8 говорит о повторности во времени; батч — одно намерение пользователя, а не два
   независимых исправления.
6. **Валюта импорта — свойство выписки, а не строки** (пробел спеки, бэклог фазы C, Important):
   в форме маппинга появляется «Валюта выписки» (дефолт — валюта владельца), выбранное значение
   пишется в аспект КАЖДОЙ созданной транзакции явно. Смешанная выписка остаётся вне скоупа
   (Future — вместе с multi-currency). PRD 03-budget §5 приводится в соответствие.
7. **CONFLICT в retry-буфере перестаёт быть «успехом»**: сервер отвечает CONFLICT на «id занят»,
   в том числе чужой строкой, а честный повтор владельца сервер отдаёт replay-успехом (200).
   Буферизованная операция получает ровно один повтор со свежим UUID, после чего — обычный
   маппинг ошибки.
8. **Шов подмены «сегодня» (`localToday`) и enforce «шаблон без occurred_on» в объём НЕ входят** —
   решения записаны в бэклог фазы с готовым дизайном: первый бессмысленно вводить без
   приёмочного теста-потребителя (слайс 3), второй ломает поддержанный флоу «Сделать
   повторяющейся» и требует продуктового решения.

# Блок 1 — ловушка релиза реестра аспектов

### Task E1: стартовая проверка дрейфа схем аспектов

Бэклог фаз C и D, единственный **Important** операционного раздела. Исполнитель валидирует
аспекты по JSON Schema из таблицы `aspect_definitions`, которую заполняет `scripts/seed-aspects.ts`,
не вызываемый ни Dockerfile, ни Render: релиз, изменивший поле аспекта, выкатывается со старой
схемой, и фича приезжает мёртвой (fail-closed, данные целы). Сегодня ловушку ловит только
ручная операция `bun scripts/ops.ts check` с ноутбука владельца.

- [ ] `packages/shared/src/aspect-registry.ts`: `canonicalJson` (перенос `canonical()` из
      `scripts/ops.ts` — сортировка ключей объектов, порядок массивов значим для `enum`/`required`)
      и `diffBuiltinAspects(rows)` → `{ missing, drifted }`. Сравниваются `schema` и
      `ai_instructions` (последняя уезжает в описания `attach_*`-тулов, §7.6); косметика
      (`name`/`icon`/`description`/`tag_mappings`/`view_config`) не сверяется — паритет с `ops check`.
- [ ] `apps/server/src/db/aspect-drift.ts`: `checkAspectDrift(db)` — своя транзакция с
      `SET LOCAL ROLE authenticated` (роль приложения NOINHERIT; `withIdentity` не подходит —
      требует UUID актора), `SELECT id, schema, ai_instructions FROM aspect_definitions
      WHERE owner_id IS NULL`, дальше `diffBuiltinAspects`.
- [ ] `apps/server/src/index.ts`: вызов на старте, НЕ fail-fast — громкий `console.error` со
      списком расхождений и точной командой починки. Падать нельзя: дрейф одного аспекта не
      повод не поднимать приложение (остальное работает), а `healthCheckPath` Render превратил бы
      наблюдаемость в отказ деплоя.
- [ ] `/health` отдаёт поле `aspectDrift` ТОЛЬКО при расхождении (форма `{status:'ok'}` без
      дрейфа не меняется — она запиннена `static.test.ts`).
- [ ] `scripts/ops.ts check` переходит на общий `diffBuiltinAspects` (дублирующий `canonical()`
      удаляется).
- [ ] Тесты: unit в shared (канонизация порядка ключей vs порядок массивов; missing/drifted/оба)
      + серверный интеграционный (живая БД: чистый реестр → пусто; подмена схемы админ-соединением
      → drifted; отсутствие роли/грантов ловится этим же тестом).
- [ ] `docs/implementation/02-ops-runbook.md` §1: раздел «пересев» дополняется строкой про
      стартовый лог — теперь ловушка сама себя объявляет.

## Осознанно НЕ входит (чтобы не всплывало ревью-сюрпризом)

- Шов подмены «сегодня» (`clock` в агрегатах) — вводится вместе с приёмочным тестом слайса 3.
- Enforce «recurring-шаблон без `occurred_on`» — ломает флоу «Сделать повторяющейся».
- Markdown-рендер ответов модели и body — сквозной продуктовый пробел, отдельное решение.
- Ревизия retry-буфера целиком (flush-семантика, business_rejection) — в объёме только CONFLICT.
- Унификация двух ключей кэша категорий — задевает `useFastPath`, отдельный заход.
- Смешанная валюта в одной выписке — вместе с multi-currency (Future).
