# V1 «Рутины и внутренний исполнитель» — план реализации

> **Для агентных исполнителей:** ОБЯЗАТЕЛЬНЫЙ САБ-СКИЛЛ — `superpowers:subagent-driven-development`
> (рекомендуется) либо `superpowers:executing-plans`. Шаги размечены чекбоксами (`- [ ]`).
> Исполнитель задачи видит ТОЛЬКО свою задачу — каждый бриф самодостаточен, все имена и типы
> соседних задач продублированы в блоке «Интерфейсы». Модели: имплементеры и разведка — opus,
> гейт-ревью задачи и финальное ревью ветки — fable; sonnet/haiku не использовать.

**Цель:** владелец словами в чате заводит рутину («каждое утро в 7 собери план дня, объясни и
предложи»); планировщик в процессе сервера по бакетам создаёт прогоны-сущности; внутренний AI
серверным циклом читает граф, предлагает план одним `orbis_propose` (или действует по белому
списку в режиме `act`), задаёт вопросы чекпойнтом; владелец принимает/отклоняет предложение на
экране прогона, отвечает на вопрос, «прогоняет сейчас»; сбои раскладываются по видам, три подряд —
пауза; всё откатывается.

**Архитектура:** ни одной новой таблицы — один новый аспект `orbis/routine`, аддитивное расширение
`orbis/agent-run`, форма предусловия `absent`, новое значение источника `routine` в журнале,
одна RLS-миграция (список владельцев для служебной роли). Раннер — свой цикл из существующих
кирпичей (`provider.chat`, `buildToolDefs`, `dispatchTool`, `recordUsage`, `gateAiEntitlements`),
свой системный слой промпта, история прогонов вместо треда. Прогон рутины — тот же
`orbis/agent-run` с субъектом «рутина» вместо гранта; глаголы среза 1 обобщаются по субъекту
(`RunSubject`). `orbis_propose` — терминальный глагол над существующим pending (`createPending` /
`approvePending` / `rejectPending`) с автоснятыми предусловиями. Планировщик — `setInterval` в
`index.ts`, включаемый `ORBIS_ROUTINE_SCHEDULER=1`, тик идемпотентен по детерминированному
`batchId` бакета. Экраны — те же три таба detail-экрана; список «Рутины» — шестой сидируемый
смарт-лист.

**Стек:** Bun 1.2.7, Hono, tRPC 11, drizzle-orm/postgres (Supabase Postgres 17), zod +
zod-to-json-schema + ajv (валидация аспектов по реестру ИЗ БД), Vercel AI SDK-провайдеры
(anthropic/openai) + `ScriptedProvider` в тестах, React 19 + TanStack Query, `bun:test` (server,
shared), vitest 4 (web), pgTAP (RLS), biome.

**Спека:** `docs/superpowers/specs/2026-08-18-v1-routines-internal-runner-design.md` (ревизия 2,
решения V1.1–V1.15, инварианты 1–14, приёмка 1–15, «Открытые вопросы к планированию» 1–5 —
все закрыты разделом «Развилки» ниже). Рамка видения — `docs/superpowers/specs/2026-08-17-vision-autonomous-spheres-design.md`
(В1–В7); субстрат — `docs/superpowers/specs/2026-08-14-orbis-ade-slice1-design.md` (С5–С8, С12) и
план среза 1 `docs/superpowers/plans/2026-08-17-ade-slice1-loop.md` (форма задач, глобальные
ограничения). Предусловие спеки выполнено: срез 1 в проде (main `e4731a8`, миграции 0010/0011
накачены, реестр пересеян).

## Развилки

### Решения плана (владелец может отменить, но план под них написан)

1. **Значения** (открытый вопрос спеки 3): тик `60 000` мс; окно догона `6 ч`; дедлайн прогона
   `10 мин`; максимум `3` попытки на бакет; паузы ретрая нарастающие `[5 мин, 15 мин]` (после 1-й и
   2-й неудачи); стоп-кран — `3` подряд `failed` среди плановых прогонов (ручные не считаются);
   хвост истории `7`; потолок предложения `50` операций. Все — константы `apps/server/src/routines/constants.ts`,
   тесты инжектируют.
2. **`days` и `at`** (вопрос 1): `days` — массив строк `'mo'|'tu'|'we'|'th'|'fr'|'sa'|'su'` (алфавит
   `byweekday` из `recurrence.ts`, единая нотация на продукт), `WEEKDAYS`/`WEEKDAY_INDEX` переезжают в
   `packages/shared/src/date.ts` и реэкспортируются; `at` — `z.string().regex(/^([01]\d|2[0-3]):[0-5]\d$/)`,
   разбор — `parseHHMM` (две `Number()`), парсер не пишем. Локальное время владельца — экспортируемый
   `wallClockIn`/`instantOfLocal` из `recurring/materialize.ts` (там уже DST-корректно).
3. **Форма пометки «заменено»** (вопрос 4): **оба** — причина в `rejectPending({reason: 'superseded'})`
   (метаданные reject-сообщения) **и** поле `proposal.status: 'superseded'` на прогоне; вопрос — исход
   `stale`. Причины отказа: `'owner' | 'superseded' | 'stale'`.
4. **Подписи полей карточки предложения** (вопрос 5): плоский `fieldLabel(key)` + `aspectLabel(id)`;
   заголовки сущностей и «было/станет» резолвит **сервер** в `routine.proposal` (клиент ничего не читает
   из графа для карточки).
5. **Объём обобщения `VerbCtx`** (вопрос 2): `RunSubject = {kind:'grant', grant} | {kind:'routine', routineId}`;
   актор/источник выводятся из субъекта; обобщаются 8 функций (`readRun`, `savedRunMatches`,
   `runStillMine`, `runStep`, `closeRun` + обёртки, `myQueue`/`claimTask` — fail-closed отказ на рутине);
   `closeRun` для рутины пропускает тикетную операцию и принимает исход `failed`.
6. **Аспект `orbis/agent-run` расширяется сверх спеки** аддитивно: `attempt` (номер попытки бакета),
   `fail_note` (почему `failed`), `proposal {pending_id, status, decided_at?, mismatches?}` — иначе
   ретраи, стоп-кран и статус карточки после перезагрузки невыразимы запросом.
7. **Набор инструментов рутины**: чтение — всё; `orbis_checkpoint` — всегда (единственный способ
   спросить, V1.5/V1.9); режим `propose` — плюс `orbis_propose`; режим `act` — плюс ровно
   `allowed_tools`. `orbis_run_step`/`orbis_finish` модели не показываются (шаги пишет раннер).
   `thread_post` — только если в `allowed_tools`; периметр треда для рутины не сужается (владелец —
   единственный пользователь; записать в границы).
8. **`runNow`** — создаёт ручной прогон и запускает раннер **fire-and-forget** в процессе, отвечает
   `{runId}` сразу; экран прогона поллит, пока `outcome === 'running'`. Одновременно у рутины — не
   больше одного `running` прогона (тик и `runNow` пропускают/отказывают).
9. **Тик однопоточный**: рутины и владельцы обходятся последовательно; следующий тик, заставший
   предыдущий, пропускается (флаг). `ScriptedProvider` с глобальной очередью ответов это переживает.
10. **Эскалация категорий (`dispatch.ts:625`) для `source='routine'` не срабатывает** — оставлено
    осознанно: рутина не «повторяет ошибку владельца».
11. **Служебные аспекты**: `orbis/routine` — не служебный; прогоны рутины — служебные как были.
12. **Карточка предложения живёт в треде рутины** (pending кладётся в `entityThreadId(owner, routine)`),
    экран прогона показывает ту же карточку по `routine.proposal({runId})`.
13. **`orbis/routine` в `HIDDEN_ASPECT_CARDS` не добавляется** — сырая карточка остаётся единственным
    UI-редактором `at`/`days`/`allowed_tools` (см. Р-9).
14. **Имя каталога** — `apps/server/src/routines/` (по домену, как `recurring/`, `agent-loop/`); тесты рядом.

## Глобальные ограничения

- **Ветка `v1-routines` от свежего `origin/main`, работа только в отдельном worktree**
  (`.claude/worktrees/v1-routines`); основное дерево не трогать (владелец пушит туда параллельно);
  в новом дереве — свой `bun install`; **абсолютные пути — только внутрь worktree**. Параллельные
  имплементеры **в одном дереве запрещены**; параллельность — только по непересекающимся файлам в
  отдельных worktree.
- **Мутации графа — ТОЛЬКО через executor**; роутеры, MCP и раннер — трансляция. Раннер и планировщик
  собирают batch существующих операций; собственных `INSERT/UPDATE` в `entities`/`relations` нет.
  Единственные прямые записи вне executor'а — сообщения тредов (как `thread_post`, `rejectPending`).
- **Ни одной новой таблицы.** Единственная миграция — `0013_routine_scheduler_rls.sql` (рукописная,
  без снимка, запись в `_journal.json` руками); накат на прод — только `bun scripts/ops.ts migrate`.
- **Пересев реестра аспектов** локально (`bun run db:prepare` или `bun scripts/seed-aspects.ts`) —
  после Задачи 1 и перед любым серверным сьютом; на проде — обязательный шаг деплоя.
- **TDD.** Полный прогон — `bun run test` из корня (голый `bun test` из корня ЗАВИСАЕТ). Один серверный
  файл — `cd apps/server && bun test src/<путь>` (нужны `DATABASE_URL`, `DATABASE_URL_ADMIN`, локальный
  Supabase — `bunx supabase start`); web — `cd apps/web && bunx vitest run <путь>`. Зелёный сьют — по
