## Б11-R4 · P2 · Изменение массива queryKey обходит проверку неизменности options

Перепривязка options, прямое присваивание свойства через алиас и передача объекта неизвестному коду теперь отвергаются. Однако после доказательства неизменности внешнего объекта `inspectOptions` передаёт его `queryKey` в общий `inspectKey`. Тот разрешает идентификатор массива по initializer. Изменение его первого элемента через отдельную ссылку остаётся невидимым.

```ts
declare const runtimeFamily: string;
const mutableKey = ['registry'];
const stableOptions = { queryKey: mutableKey, queryFn: async () => [] };
mutableKey[0] = runtimeFamily;
void client.fetchQuery(stableOptions);
```

Этот код добавлен в штатный типизированный mutant на изолированной копии. Проверка TypeScript semantic diagnostics прошла. Ожидаемый дополнительный `<unresolved>` не появился, поэтому произвольный фактический namespace проходит production guard как зарегистрированный `registry`. Та же проверка без добавленного фрагмента прошла. Для options нужно проверять неизменность источника семейства внутри `queryKey` и сохранять положительные варианты с неизменяемым алиасом и последним явно заданным ключом. [Разрешение ключа](/private/tmp/orbis-b11-fix1.jefl2e/scripts/cache-dependencies.test.ts:171), [проверка внешнего алиаса](/private/tmp/orbis-b11-fix1.jefl2e/scripts/cache-dependencies.test.ts:237), [передача ключа в inspectKey](/private/tmp/orbis-b11-fix1.jefl2e/scripts/cache-dependencies.test.ts:272), [mutant](/private/tmp/orbis-b11-rereview1.CAQRjT/scripts/cache-dependencies.test.ts:479), [RED](/private/tmp/orbis-b11-rereview1.CAQRjT/nested-key-mutant.log), [контроль](/private/tmp/orbis-b11-rereview1.CAQRjT/original-typed-control.log).

## Закрытые замечания

- **Б11-R1.** `openTxId` получен в той же `withIdentity`, один дополнительный SQL read без дополнительного HTTP. Транспорт сохраняет исходный read watermark. Runtime связывает доказательство с исходным receipt и конкретным серверным ID. Подавляется только совпавший локальный структурный INSERT. При получении POST после feed допустим лишь непрерывный суффикс с одним доказанным INSERT и без других событий. Неизвестный xid, mixed/oversized, поздний INSERT либо delete/reinsert того же ID сохраняют catchup. Отдельные message и journal события перечитывают хвост. Источник и обе очередности проверены целевым Vitest. Тест исполнителя на Hono/PostgreSQL связал настоящий POST xid с реальным INSERT из `changes.reconcile`. [Сервер](/private/tmp/orbis-b11-fix1.jefl2e/apps/server/src/routers/chat.ts:78), [проверка события](/private/tmp/orbis-b11-fix1.jefl2e/apps/web/src/lib/freshness/runtime.ts:101), [суффикс](/private/tmp/orbis-b11-fix1.jefl2e/apps/web/src/lib/freshness/runtime.ts:568), [лог PostgreSQL](/Users/birzhan/.codex/worktrees/853d/orbis/.superpowers/sdd/2026-11-03-speed-plan-b/b11-fix1-server-local.log).
- **Б11-R2.** Сетевой `chatOpen` сохраняется с исходным receipt даже после продвижения курсора при наличии настоящего watermark. Это право касается только binding. Хвост без доказательства остаётся stale и перечитывается, а epoch и reset проверяются до принятия результата. Изменение чужого треда теперь оставляет исходную запись binding на диске. [Принятие receipt](/private/tmp/orbis-b11-fix1.jefl2e/apps/web/src/lib/freshness/runtime.ts:672), [проверка исходного watermark](/private/tmp/orbis-b11-fix1.jefl2e/apps/web/src/features/chat/useEnsuredThread.test.tsx:261).

Уход во время уже начатого POST сохраняет оба результата, а повторное открытие в offline использует готовую привязку. Смена scope и reset по-прежнему отменяют публикацию. Независимо проверены поздние hit и miss предыдущего поколения после reset. Первый не вернул binding, второй не начал POST, а попытка нового поколения открыла чат ровно один раз. Проверка позднего POST после reset и исходная проверка удаления также прошли.
