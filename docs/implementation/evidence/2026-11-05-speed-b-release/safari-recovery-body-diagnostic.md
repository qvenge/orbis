# Safari recovery · Адресная диагностика по исходникам

Срез `356a610f`. Прочитаны accepted source review, W3C request/response 108–110, snapshot перед выбором и storage/DOM/visibility после timeout. Продукт, тесты, браузер и закрытый fixture не запускались и не менялись.

W3C запрос 108 находит кнопку по точному XPath баннера, запрос 109 вызывает element click, ответ HTTP 200/value null. Это доказывает успешный ответ драйвера, но не содержит запись DOM click или React callback. До выбора и после timeout единственный живой документ B имеет nonce `01a1aa8e-d07e-7002-838d-ed8edd4397bd`, writer/sequence неизменны, basis revision 2, submitted null. Cache и сервер содержат C rev 3. Текст B сохранён. Нет наблюдаемой попытки body POST или завершения ACK после выбора.

В `EntityBody.tsx:501–507,623–624` кнопка синхронно вызывает `save.applyPendingDraft`. `ui/Button.tsx` передаёт обычный onClick и type button, у этого использования нет disabled или focus guard. `save` не проверяет document.hasFocus или visibility. Наблюдавшийся focus=false не является причиной отказа внутри этого пути по прочитанным исходникам.

`applyPendingDraft` сначала проверяет null/retired offer, затем снимает баннер, устанавливает pending и exact recovery token, захватывает основу и вызывает save. Отсутствие POST при видимом баннере допускает как недоставленный callback, так и немедленное повторное предложение. В частности, `save:856–861` при held+confirmed+несовпадении вызывает `offerConflictDraft`. Последний снова устанавливает баннер без HTTP. Обычный re-offer вызывает managed.stage, поэтому у нового writer ожидался бы новый nonce. Неизменный durable nonce слабее поддерживает этот конкретный путь, однако не показывает рефы и in-memory состояние writer.

В `capturePendingBasis:1119–1144` при history 0 явный жест не берёт confirmedBody как explicit basis. Он может повторно использовать shownUnconfirmedRef или показанную ревизию. Это гипотеза для короткой пробы. Из raw нельзя доказать, был ли этот ref живым на момент click. В `BodyEditor:419–468` onAccept вызывается после посадки doc, однако событие может пройти до подтверждения того же структурно разделяемого объекта в QueryCache. Само видимое C ещё не доказывает, какую основу захватил хук. Коррекция одного условия без воспроизведения пока не обоснована.

Минимальный эксперимент требует нового fixture и нового срока авторизации. Один supported click после подтверждённого C с пассивными capture markers pointer/mouse/click, target/composedPath/isTrusted и focus/visibility разделит отсутствие DOM click и доставленный click. MutationObserver баннера может показать remove/re-add, но синхронно сбатченный re-offer React может дать тот же DOM. Если click присутствует, для окончательного вывода нужен callback-boundary trace либо короткая независимая проба штатного хука.

Минимальная проба хука должна начинаться с managed persisted B basis2 и настоящего disk A2, публиковать network C3 в обычной history0, оставлять B предложенным и нажимать публичную кнопку recovery. Проверять ожидаемую ревизию 3, ровно один entity.update, исходный exact token/ACK и исчезновение предложения только после подтверждения. Варианты должны различать onShown до и после network confirmation того же объекта. Отрицательный контроль удерживает GET и неподтверждённую основу, ввод и предложение сохраняются без отправки. Это небольшой сценарий, он не требует аудита всего хранилища или повторения истёкшего сеанса.

Reset/basis часть последней правки принадлежит `49a43220` и исходному Б5. Если проба остановится на terminal/suppressed/retired admission или восстановлении managed writer, соответствующая граница принадлежит Б12 `5adf545a`. До такого наблюдения смена владельца исправления не обоснована.
