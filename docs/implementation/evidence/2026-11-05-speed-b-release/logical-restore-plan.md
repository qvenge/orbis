# Локальная репетиция логического восстановления после 0027

> Проект для ревью координатором и прежним независимым ревьюером. Предлагаемые команды и SQL пока не исполнялись. Исполнение открывается отдельной передачей двух кластеров и окна. Постоянный runbook §4.3 сохраняет STOP до фактического результата.

**Цель.** На штатном SQL-дампе с синтетическим графом воспроизвести, что прежний порядок теряет эксплуатационные зависимости и переносит несовместимую историю ленты. Отдельно проверить восстановление каталога и атомарное создание новой истории ленты в целевом кластере. Зафиксировать, что остаётся проверить при переводе живых браузеров.

**Основания.** Точное дерево `356a610f5ae92efe429bdb6891c5bde6f9c09e9f` и неизменённый runtime `a0bff516`. Порядок А в `docs/implementation/02-ops-runbook.md` §4.3, `scripts/backup.sh`, `scripts/ops.ts::dumpOp/migrateOp`, `scripts/setup-db.ts`, миграции `0024_perf_samples.sql` и `0027_change_feed.sql`, `apps/server/src/freshness/{feed,stream,listener}.ts`, `routers/changes.ts`, `freshness/{feed,watch-http}.test.ts`. Функциональный пример настоящего сокета и MCP: `docs/implementation/evidence/2026-11-03-speed-plan-b/native-functional/native-source/native-mcp-feed.test.ts`.

## 2. Воспроизвести прежний порядок и два независимых отказа

- [ ] До DROP проверить, что target disposable, каталог приложения отсутствует, managed auth готов, а `public` не имеет неожиданных внешних зависимостей. Снять managed auth/extension baseline. В цель подавать только неизменённый штатный `orbis-backup-source.sql`, после stock `setup-db.ts`. На целевом кластере удалить только его исходную пустую для приложения схему public в одной транзакции с импортом. Старый runbook делает DROP и импорт раздельно. Обёртка транзакцией здесь ограничивает последствия пробного отказа. Если найден внешний managed dependency, несовместимый extension или ошибка импорта, сохранить SQLSTATE и остановить этот вариант; не удалять строки из дампа и не «отключать» зависимости до ревью.

```sh
# Из корня worktree, после передачи цели, инвентаризации и pin дампа.
RESTORE_APPROVED_PHASE=stock-import bash   "$runner" stock-import
```

Runner проверяет хеши перед копированием и внутри TARGET, затем через `docker exec` по точному TARGET ID использует один `psql --single-transaction` с последовательностью `assert-target.sql` → проверка Unix socket → `stock-drop.sql` → неизменённый дамп. Все файлы целиком скопированы до соединения. SQL не читается из канала, который мог бы оборваться между statements. Отдельное подключение для внешней сверки не заменяет in-session guard. Сначала отрицательный `identity` с заведомо другим допустимым числом и без SQL-последствий, затем положительный `identity` с проверенными значениями. Никакие неверные проверки не исправлять автоматическим выбором ответившего сервера.

- [ ] Сразу после импорта сравнить business manifest с source (полное равенство) и отдельно показать, что feed rows и floor побайтно перешли из другой XID-истории. Проверить роль захвата, definer owner, SELECT-only ACL, cron jobs, и `changes.reconcile` под настоящей runtime-ролью. Не предсказывать единственный SQLSTATE: штатные default privileges могут дать неожиданный доступ, а некоторые поля могут быть недоступны. Сам факт наличия FORCE RLS не исправляет отсутствующие ACL, owner или scheduler.
- [ ] Воспроизвести именно шаг A с выпиской GRANT/REVOKE/default privileges из эталона (source того же SHA) и применением с `psql -1 -v ON_ERROR_STOP=1`. Сохранить оригинальный результат: ожидается отсутствие роли захвата либо неполнота восстановления даже если команда прошла. Показать, что старый ACL-дифф не проверяет владельца definer, cron и XID, а column ACL следует проверять явно. Стандартный local `db:migrate` с теми же миграциями сверить по равному хешу Drizzle ledger и каталогу до/после: ledger уже содержит 0027, соответствующие зависимости не восстанавливаются.
- [ ] Перейти к исправлению каталога. Затем, **до исправления ленты**, выполнить обычную контролируемую запись в целевой A, зафиксировать её настоящий `targetWitnessXid < sourceFloor` и присутствие metadata row. Открыть `changes.reconcile` от свежего target watermark ниже floor и от исходного курсора, зафиксировать reset reason/phase, cursor и отсутствие доставки точного нового XID. В первой ветке ожидается `floor/provisional` при `from < floor` и `W2 < floor`. С исходного большого курсора первый ответ может быть `future-cursor`, а повтор уже с пониженного target W2 попадает в `floor/provisional`. Проверять оба перехода, а не предполагать один порядок. Один прямой LISTEN/NOTIFY может доказать wake, но не доставку page. Зафиксировать новое состояние бизнес-данных после только этой контрольной записи. Отдельный хеш этого снимка нужен, чтобы доказать, что rebase ленты сам не менял данные.

## 3. Восстановить каталог, оставив старую ленту для XID RED

- [ ] В том же изолированном target, без сервиса и не на source, создать ограниченную кластерную роль ровно как 0027: `CREATE ROLE orbis_change_feed_owner NOLOGIN NOINHERIT BYPASSRLS`. Сравнить остальные флаги, отсутствие её membership в других ролях и отсутствие членства `orbis_app/authenticated/anon/service_role` в ней. Никакой ротации секретов управляемой базы. Установить pg_cron в цель под локальным `supabase_admin`, проверить те же version/preload и target `cron.database_name`.
- [ ] Восстановить владельцев по собранному allowlist и сверить полный inventory. Обязательный SQL локального администратора — `ALTER FUNCTION public.orbis_capture_change_feed() OWNER TO orbis_change_feed_owner`. При разных владельцах public/drizzle и их объектов согласовать точные дополнительные `ALTER … OWNER` по source-каталогу, без широкого `REASSIGN OWNED`. В локальной репетиции истинный superuser может передать owner напрямую без временного grant SET ROLE/CREATE. Это допустимое сужение административной membership относительно 0027, а не новое право. Чужие неожиданные owners/объекты — остановка для ревью. Definer остаётся с исходным `search_path`; функции helper остаются invoker. Проверить все четыре statement triggers каждого производителя, RLS/FORCE RLS и политики, включая SELECT-only доступ к ленте/порогу.
- [ ] Из source schema archive сформировать TOC с разрешёнными ACL / DEFAULT ACL (не исполнять весь архив поверх существующей схемы). Например оставить только строки регулярного вида `^[0-9]+; [0-9]+ [0-9]+ (ACL |DEFAULT ACL )`, затем проверить точные объекты и роли из manifest. Сгенерировать SQL в SOURCE через `RESTORE_APPROVED_PHASE=render-acl bash "$runner" render-acl` с точными SHA исходного архива и проверенного ACL-only TOC. Режим исполняет PG17 `pg_restore --use-list=acl.toc --file=acl.sql source-schema.dump` и возвращает SQL с проверенным хешем. Просмотреть SQL до исполнения. Сверить ожидаемые privileges с отсутствующими или лишними target defaults до запуска. При лишних effective grants собрать точные `REVOKE` для конкретного объекта/колонки/grantee по catalog diff и добавить только после ревью; простой повтор GRANT не снимает лишнее. Сохранить рассмотренный SQL как `acl-reviewed.sql`, закрепить его digest и применить в TARGET через `RESTORE_APPROVED_PHASE=acl-replay bash "$runner" acl-replay`, затем сравнить нормализованные grantor/grantee ACL, default ACL, schema USAGE, закрытые capture/helpers и identity sequence. Никакого PUBLIC EXECUTE или широкого GRANT для починки отказа.
- [ ] Восстановить обе именованные задачи, которые уносятся из дампа: `orbis_perf_samples_cleanup` из 0024 и `orbis_change_feed_cleanup` из 0027. Использовать точные statements `SELECT cron.schedule(...)` этих файлов, под выделенным локальным scheduler owner, который совпадает с зафиксированным source owner; записать hash command, schedule, database, username и единственность каждой job. Не переписывать команду cleanup вручную и не копировать cron.job_run_details. Для целевого кластера реальный запуск 0027 проверяется позже.
- [ ] Доказать под собственным runtime login `orbis_app` + `withIdentity`: граф A читает только A и глобальный floor, B видит только B, нет claims → отказ, на сырых `INSERT/UPDATE/DELETE` ленты/порога и вызове helper нет прав. Эффективные гранты definer ограничены только колонками и командами 0027. Подписанный owner JWT идёт в HTTP headers, не в URL. Результат catalog-only не объявлять приёмкой пока сохраняется провал low-XID в шаге 2.

## 4. Атомарно начать target XID-историю

- [ ] Отключить доступ приложений к target на уровне стенда, закрыть probes/LISTEN и проверить, что нет чужих target writers, удержанных snapshots и подготовленных транзакций. Source больше не подключать. Снять копию исходного дампа и хеши target business manifest перед rebase. Ещё раз сверить target system identifier и роли. Убедиться, что импортированный floor больше текущего target W2: в репетиции намеренно сбрасываем чужую границу, а не выполняем обычное продвижение retention.
- [ ] Единственная data-операция исправления на цели очищает только метаданные `change_feed` и меняет singleton floor на следующий XID текущей транзакции цели. Старый feed identity может остаться выше старых номеров, поскольку клиентская закладка — `tx_id`, а `id` используется как внутристраничный порядок. `CONTINUE IDENTITY` оставляет последовательность. Остановка при отсутствии singleton; исполнитель — проверенный local superuser. Не использовать `GREATEST(oldFloor,...)` и не вызывать TRUNCATE бизнес-таблиц, не «чинить» это повышением target XID.

```sh
# После stop writers и фиксации старого floor/target witness XID.
RESTORE_APPROVED_PHASE=rollback-control bash   "$runner" rollback-control
# Ожидается именно контрольная ошибка после TRUNCATE. Проверить сохранность feed/floor.
RESTORE_APPROVED_PHASE=rebase bash   "$runner" rebase
```

Runner выполняет `assert-target.sql` → `rebase-target.sql` в одной транзакции. Второй файл проверяет живые соединения и prepared xacts, точный прежний floor и наличие закоммиченного witness XID ниже порога. Затем он блокирует изменение истории на время операции, делает `TRUNCATE public.change_feed CONTINUE IDENTITY` и ставит `floor=pg_current_xact_id()+1`. Намеренный отказ между TRUNCATE и UPDATE в первом режиме должен откатить обе части.

Проверить `feed=0`, singleton, `floor=repairXid+1 <= current target W2` при отсутствии удержанных XID, и полный business manifest равен target непосредственно до rebase. Source dump и source snapshot не менялись. Проверку rollback-control проводить до rebase с закрытым приложением. Реальную рабочую цель повторно чистить ради одного контроля запрещено после допуска клиентов.
- [ ] Никакой автоматической трансляции старых cursors. Через настоящий Bun/Hono `Bun.serve({hostname:'127.0.0.1',port:0})`, `makeDb/startChangeListener/createApp` и тестовые HS256 JWT с version header 0.7.0 открыть A/B `changes.watch` и `changes.reconcile`. Probe повторяет принятый pattern `native-mcp-feed.test.ts`, но читает SSE frames Node/Bun без браузера. Старый фактический source cursor получает `future-cursor/complete` с новым target W2 (проверить `oldCursor > W2 >= floor`), нулевой cursor получает `floor/complete`. Открыть продолжение от принятого target W2. С тем же A выполнить новую штатную запись через существующий MCP `entity_update` (PAT, localhost). До mutation дождаться подтверждённого подключения слушателя. Получить настоящий точный `targetNewTxId` через feed/journal и сравнить со SSE tracked page и независимой reconcile: `floor <= targetNewTxId < oldSourceFloor`, правильные graph/entity IDs, B его не видит. Старые row keys и старый контрольный XID отсутствуют, no-op/rolled-back контроль не оставляет metadata row и соответствующей application page. Отсутствие NOTIFY здесь не утверждается без отдельного сырого LISTEN с причинным барьером. Проверка доставки функциональная, без критериев задержки.

## 5. Граница перевода живых клиентов и итог

- [ ] SQL/Hono репетиция доказывает восстановление данных и новой ленты. Старые XID могут также численно попасть **внутрь** диапазона новой БД, тогда протокол не обязан распознать чужую историю; его тестовая ветка с высоким старым курсором этого не устраняет. Перевод требует подтверждённого прекращения прежних документов, соединений и уже начатых навигаций, запуска актуальной оболочки, нового чтения без переноса старой закладки и недопуска старых дисковых ответов. Зафиксировать, как допускаются конкретные устройства/вкладки. Прежний удержанный pre-protocol navigation остаётся отдельным блокером. Недоступные устройства не считать очищенными.
- [ ] Черновики живут в клиентах, не в дампе PostgreSQL. Перед переводом не удалять input stores и Web Storage вместе с кешем ответов. Снять/сохранить точные synthetic tokens (writer/nonce/generation/basis, исходный срок, payload hash; отдельно legacy numeric) под прежней безопасной областью. После перевода проверить восстановление/явное применение и отсутствие автоматического body POST, пока основа не установлена. Отдельный обязательный отрицательный случай: old numeric draft с тем же числом `bodyRevision`, но другим содержимым/историей, после hard reload без наблюдавшегося rewind. Current codec не несёт server incarnation, поэтому этот случай нельзя объявить решённым reset или перезапуском. До проверки отдельно согласованного способа изолировать неподтверждённый ввод и дать явное восстановление на новой основе запись живых клиентов остаётся заблокированной. Не использовать destructive logout/shared-on/clear-site как способ «доказать» сохранность. Не менять продуктовую схему/codec в этой репетиции.
- [ ] Только после отдельной передачи браузерного окна подготовить локальный check cutover с synthetic old profile и exact app artifacts. Сначала удержать target writes, сверить pre/post токены и наличие предложения восстановления; затем пользовательский явный жест на подтверждённой основе. При обнаружении silent resend или невозможности сохранить старый ввод сохранить RED и стоп. SQL PASS отдельно от client PASS. Внешние auth/pooler, backup реальных аккаунтов, установленная PWA и реальные устройства вне этого локального результата.
- [ ] Передать координатору обе неизменённые ветви RED, хеши синтетического дампа/ACL, source/target system identifiers и XID-цепочку, manifests бизнес-данных, catalog/SSE/reconcile/cron logs, список выходов и ожидаемых отказов, остаток client cutover. Закрыть сокеты, остановить только два выделенных контейнера по имени+label, сохранить их до решения о повторе. Документацию §4.3 не заменять до независимого ревью фактически пройденной процедуры; при частичном результате обновить только доказанный статус.

**Решение на ревью.** Минимально восстанавливаем security/cron из точного эталона и заново инициализируем только производную ленту. Отклонены варианты продвинуть XID цели до значения исходника, править журнал миграций для повторного 0027 или оставить сырой XID-dump под новым owner. Они либо подменяют разные истории одинаковыми числами, либо трогают уже восстановленную схему. Раздельное восстановление каталога и feed reset даёт причинный контроль, но требует полного stop/writer fence до открытия сервиса. Если отдельный ACL replay не доказывает канонические effective permissions, остановка и новая рассмотренная процедура безопаснее частичного восстановления.
