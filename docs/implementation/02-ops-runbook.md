# 02 — Ops Runbook (прод Orbis)

Операционный справочник прод-контура: деплой, секреты, подключение внешних агентов и отзыв
их доступа, бэкап/восстановление, keep-warm против сна Render, пауза Supabase Free,
health-мониторинг и перф-чек-лист релиза.

Топология (слайс 1c-2): один Render free web-сервис (Docker, Bun 1.2.7) раздаёт API
(Hono: `/trpc`, `/mcp`, `/health`) и статику веб-клиента (`apps/web/dist`) с одного origin.
БД — Supabase Free (eu-central-1) через Supavisor-пулер. Бэкап — `pg_dump` по cron GitHub Actions.

Плейсхолдеры: `<PROD_REF>` — reference прод-проекта Supabase (факт: `ceovqtdibalxnqkgedrl`);
`<pwd>` — пароль роли; `<prod-host>` — публичный хост Render-сервиса (факт: `orbis-64q4.onrender.com`);
`<POOLER_HOST>` — хост Supavisor-пулера проекта, смотреть в Supabase Dashboard → Connect
(факт для прода: `aws-0-eu-central-1.pooler.supabase.com`; кластер зависит от проекта — НЕ хардкодить:
spike-проект, например, жил на `aws-1-eu-central-1`).

## 1. Деплой (Render Blueprint)

Источник истины конфигурации — `render.yaml` в корне репозитория. Деплой описан как Blueprint,
секреты не хранятся в git (`sync: false` — значения задаются в Render UI).

> **Статус (Фаза B, 2026-07-08):** `render.yaml` — прод (main, same-origin, merge `f26fed7`);
> сервис задеплоен: https://orbis-64q4.onrender.com. Раздел описывает текущую конфигурацию.

### Первичная настройка

1. `dashboard.render.com → New → Blueprint` → выбрать репозиторий Orbis и ветку `main`.
2. Render читает `render.yaml`, создаёт web-сервис (`runtime: docker`, `plan: free`,
   `region: frankfurt`, `healthCheckPath: /health`, `dockerfilePath: ./Dockerfile`).
3. Задать `sync: false`-секреты (см. §2) в Render UI перед первым деплоем.
4. `Apply` — Render собирает образ по корневому `Dockerfile` (web build + API) и запускает.

### Обновления

Push в `main` → Render авто-деплоит новый образ. Проверка после деплоя:

```bash
curl -fsS https://<prod-host>/health          # {"status":"ok"}
curl -fsS https://<prod-host>/ | head -c 200   # index.html веб-клиента (same-origin)
```

Роллбэк: в Render UI сервиса → `Deploys` → выбрать предыдущий зелёный деплой → `Redeploy`.

**Ключ LLM — ДО деплоя.** `render.yaml` объявляет `ORBIS_LLM_PROVIDER` (сейчас `openai`),
и ключ именно этого провайдера обязан лежать в Render UI до выкатки: без него старт
падает намеренно (§2, `llm/provider.ts`), healthcheck не проходит и новый деплой живым
не становится. Смена провайдера — это правка значения в `render.yaml` плюс ключ в UI;
схем аспектов она не касается, пересев реестра (ниже) для неё НЕ нужен.

> **Смена LLM-провайдера: чек-лист деплоя.** Случай, которого в проекте раньше не было:
> `ORBIS_LLM_PROVIDER` объявлена в блюпринте строкой `value:` (не `sync: false`), и релиз
> OpenAI **меняет её значение**, а не заводит новую переменную. Все прежние релизы только
> добавляли переменные — там «синк блюпринта не отработал» означало «сервис не поднялся»,
> отказ был громким. Здесь он тихий: если новое значение не доедет, сервис останется со
> старым `ORBIS_LLM_PROVIDER=anthropic`, ключ Anthropic в проде есть → фабрика построится,
> процесс поднимется, `/health` ответит `{"status":"ok"}` — а чат будет отдавать
> «AI-провайдер недоступен», ровно тот симптом, ради которого релиз и делался.
>
> **1. ДО выкатки — посмотреть глазами, что сейчас стоит на сервисе.** Render UI →
> `Service → Environment`: есть ли там `ORBIS_LLM_PROVIDER` и какое у неё значение.
> Пять секунд, и вся неопределённость про синк снимается заранее — видно исходное
> состояние, с которым потом сравнивать.
>
> **2. Положить `OPENAI_API_KEY` в Render UI. Порядок «ключ раньше кода» безопасен —
> это проверено по коду, а не предположено.** Добавление переменной в UI само по себе
> запускает редеплой, и пойдёт он на СТАРОМ коде `main`. Старый код про OpenAI не знает
> вовсе: в `git show b87333a:apps/server/src/llm/provider.ts` тип `LLMProviderEnv`
> перечисляет `ORBIS_LLM_PROVIDER`, `ORBIS_LLM_MODEL`, `ANTHROPIC_API_KEY`, `NODE_ENV` —
> `OPENAI_API_KEY` там нет, и отказа «оба ключа, выбор неоднозначен» в той фабрике тоже
> нет (его вводит как раз этот релиз). Сверх того `git show b87333a:render.yaml` уже
> задаёт `ORBIS_LLM_PROVIDER: anthropic` явным `value:`, то есть даже гипотетическая
> неоднозначность не возникла бы. Лишний ключ старый процесс просто игнорирует.
>
> **3. Мерж в `main` → Render выкатывает новый образ.** Ключ к этому моменту уже на месте,
> иначе старт падает намеренно и деплой живым не становится (абзац выше).
>
> **4. `/health` подтверждением переключения НЕ является.** Он отвечает `{"status":"ok"}`
> и на непереключившемся `anthropic` с пустым счётом: про LLM он не знает ничего —
> в ответе только `status` и, при расхождении реестра аспектов, `aspectDrift`
> (`apps/server/src/app.ts`), а фабрика на старте лишь проверяет наличие ключа выбранного
> провайдера и в сеть не ходит. Зелёный `/health` здесь означает ровно «процесс
> поднялся» и ничего — про то, к какой модели он пойдёт. Это тот же класс ловушки, что
> «пустой „Год“ подтверждением пересева быть не может» в чек-листе фазы E ниже.
>
> **5. Подтверждают два наблюдения, и оба — после ЖИВОГО сообщения в чат.**
>
> Отправить в чат то, что fast-path заведомо не возьмёт (он берёт только «сумма +
> категория»): подойдёт любой вопрос, например «что у меня сегодня по задачам?». Ответ
> по существу вместо карточки «AI-провайдер недоступен» — первое наблюдение: вызов
> провайдера прошёл. На непереключившемся `anthropic` с пустым счётом он бы не прошёл.
>
> Второе наблюдение называет модель поимённо — строка в `ai_usage`. Метеринг пишет туда
> `provider.modelId` (`ai/send-message.ts`: `makeAiDeps` → `ai/metering.ts`:
> `recordUsage`), колонка называется `model`, ключ строки — `(owner_id, date, model)`,
> где `date` — календарный день в UTC. Для дефолта OpenAI там будет `gpt-5.5`
> (`DEFAULT_OPENAI_MODEL`), для Anthropic — `claude-sonnet-5`. Строка пишется ТОЛЬКО при
> `requestCount > 0`, то есть после успешного ответа провайдера, — отсюда её
> доказательная сила: она не появляется «просто потому что процесс жив».
>
> **Готовой операции для этого в `bun scripts/ops.ts` НЕТ**, и выдумывать её не надо:
> белый список — `check`, `migrate`, `seed-aspects`, `coverage`, `census`, `audit-bodies`,
> `backfill-body-doc`, `ping`, `issue-pat`, произвольного
> SQL там нет по замыслу. Запрос идёт тем же админским DSN, которым `psql` ходит в §4.3, а секрет
> берётся из Ключницы — из неё же читает и `ops.ts`, так что открытым текстом в историю
> команд DSN не попадает:
>
> ```bash
> psql "$(security find-generic-password -a orbis -s orbis-prod-admin -w)" -c \
>   "SELECT date, model, request_count FROM ai_usage \
>    WHERE date >= (now() AT TIME ZONE 'utc')::date ORDER BY model"
> ```
>
> Строка `gpt-5.5` за сегодня — переключение доехало. Строки нет вовсе — вызов провайдера
> не прошёл, и первое наблюдение это уже показало: вернуться к п. 1 и сверить значение
> `ORBIS_LLM_PROVIDER` на сервисе. Строка `claude-sonnet-5` за сегодня — сервис отвечает
> старым провайдером, п. 1 туда же.
>
> Если такая проверка станет рутиной — заводить операцию в объекте `OPS`
> (`scripts/ops.ts`), а не размножать голый DSN по чек-листам.

#### Пересев реестра аспектов — обязателен при изменении схемы аспекта

Исполнитель валидирует аспекты сущностей (стадия 2) не по zod-схеме из кода, а по
JSON Schema, лежащей в таблице `aspect_definitions` в БД. Эту таблицу заполняет
`scripts/seed-aspects.ts`, и он **НЕ вызывается ни Dockerfile, ни Render** — только
локальным/CI-шагом `bun run db:prepare`.

Значит: релиз, который добавил или изменил поле в `packages/shared/src/schemas/aspects.ts`,
без пересева выкатывается со **старой** схемой в проде. Схемы аспектов строгие
(`additionalProperties: false`), поэтому запись с новым полем не «просто игнорируется»,
а отклоняется ошибкой валидации — фича приезжает мёртвой (fail-closed, данные целы).

```bash
# один раз после деплоя релиза, изменившего схему аспекта
# (скрипт читает ИМЕННО DATABASE_URL_ADMIN — без неё падает «DATABASE_URL_ADMIN не задан»)
DATABASE_URL_ADMIN="$DATABASE_URL_ADMIN_PROD" bun scripts/seed-aspects.ts
```

Скрипт идемпотентен — повторный запуск безопасен. Тот же реестр читает сборщик
LLM-контекста (`ai_instructions` аспектов), так что один пересев закрывает обе стороны.

**«После деплоя» — умолчание, а не правило.** Если релиз только **добавляет опциональное**
поле, пересев безопаснее сделать **до** выкатки кода: старый код нового поля не пишет, поэтому
новая схема ничего в проде не меняет, зато фича приезжает живой с первой секунды (пример —
чек-лист деплоя Ш1 ниже). «После» обязательно там, где новая схема **сузила** допустимое
(поле стало обязательным, enum потерял значение): такой пересев, сделанный раньше кода, начнёт
отклонять записи ещё работающего старого кода.

**Ловушка объявляет себя сама (уборочная фаза, E1).** Забыть пересев больше не значит
узнать о нём по мёртвой фиче: сервер на старте сверяет `schema` и `ai_instructions`
встроенных аспектов в БД с кодом и при расхождении печатает в лог Render

```
[aspects] РЕЕСТР АСПЕКТОВ В БД РАСХОДИТСЯ С КОДОМ — часть записей будет отклоняться…
  ✗ orbis/memory: в реестре БД НЕТ
Починить (идемпотентно): DATABASE_URL_ADMIN=… bun scripts/seed-aspects.ts
```

Старт при этом НЕ падает (дрейф одного аспекта — не повод не поднимать приложение,
а красный `healthCheckPath` превратил бы наблюдаемость в отказ деплоя). Второй сигнал —
`/health`: при расхождении к прежнему `{"status":"ok"}` добавляется поле `aspectDrift`
со списком аспектов. Без расхождения форма ответа не меняется.

```bash
curl -fsS https://<prod-host>/health
# {"status":"ok"}                                  — реестр совпадает с кодом
# {"status":"ok","aspectDrift":["orbis/goal"]}     — пересев забыт, фича приедет мёртвой
# {"status":"ok","aspectDrift":"unknown"}          — проверка НЕ выполнилась (БД была
#                                                    недоступна на старте): состояние
#                                                    реестра неизвестно, сверить вручную
```

Третье значение появилось не для красоты: недоступность БД в первые секунды холодного
старта Render+Supabase — обычное дело, и выдавать её за «расхождений нет» значит тихо
снять ловушку. Стартовая проверка повторяет чтение трижды (1 с, 5 с, 15 с), и лишь затем
объявляет `unknown`.

Ручная проверка `bun scripts/ops.ts check` осталась и считает то же самое тем же кодом
(`diffBuiltinAspects` в `@orbis/shared`) — на одном и том же состоянии БД две проверки
не разойдутся по построению.

**Но состояние они видят разное, и это важно для чек-листов ниже.** `ops.ts check`
читает реестр **живьём, в момент вызова**. Поле `aspectDrift` в `/health` — **снимок,
снятый один раз на старте процесса** (`apps/server/src/index.ts`: результат кладётся
в переменную; повторы 1/5/15 с существуют только для неудачного чтения) и после этого
не пересчитываемый ничем. Поэтому пересев, сделанный на **уже поднятом** сервисе,
`ops.ts check` увидит сразу, а `/health` будет повторять прежнее расхождение до
перезапуска сервиса. Прав в этот момент `ops.ts check`; `/health` снова становится
показателем только после рестарта.

#### Обёртка прод-операций `scripts/ops.ts`

Чтобы не подставлять DSN руками (и не светить его в истории команд), есть обёртка
с **белым списком** операций. Секрет она берёт из Ключницы macOS, наружу не отдаёт
и в сообщениях об ошибках вырезает пароль.

Разложить секрет один раз — команду выполнять в своём терминале, не через ассистента:

```bash
security add-generic-password -a orbis -s orbis-prod-admin -U -w '<DSN роли postgres>'
```

Дальше:

```bash
bun scripts/ops.ts check                     # только чтение: расхождение реестра прода с кодом
bun scripts/ops.ts migrate                   # накатить неприменённые миграции схемы (§1.1)
bun scripts/ops.ts seed-aspects              # тот же upsert, что seed-aspects.ts
bun scripts/ops.ts coverage                  # только чтение: покрытие транзакций за 90 дней (§8)
bun scripts/ops.ts census                    # только чтение: сколько тел перенос изменит сильнее прочих
bun scripts/ops.ts audit-bodies              # только чтение: агрегаты по корпусу тел перед конверсией
bun scripts/ops.ts backfill-body-doc         # конверсия тел в body_doc — ТОЛЬКО после audit-bodies
bun scripts/ops.ts ping                      # связность и версия PostgreSQL
bun scripts/ops.ts issue-pat <owner> [метка] [--scope worker]   # headless-токен агента (§3.2)
```

`issue-pat` появилась здесь не для удобства, а потому что иначе выпуск PAT на проде остался
бы **без санкционированного пути**: до переезда токена в базу (D34) скрипт выдачи базы не
касался вовсе — печатал хеш, который человек руками клал в Render. Теперь он пишет строку,
то есть требует прод-DSN, а голый прод-DSN оператору не выдаётся по той же причине, по
которой заведена эта обёртка. Это единственная операция белого списка, которая **печатает
секрет** (сырой токен, один раз): её вывод не логировать и не коммитить.

Почему белый список, а не просто `DATABASE_URL_ADMIN` в окружении: этот DSN умеет
и `DROP TABLE`. Обёртка ограничивает радиус до перечисленных операций, поэтому её
безопасно разрешить ассистенту (правило `Bash(bun scripts/ops.ts:*)` в
`.claude/settings.json`) — в отличие от голого доступа к проду.

Новая операция добавляется в объект `OPS` в `scripts/ops.ts`; всё, чего там нет,
скрипт отклоняет.

> ```

> **Фаза E слайса 3: чек-лист деплоя.** Единственная фаза слайса 3, деплой которой требует
> ручного действия на проде. Пример дрейфа в блоке `/health` выше написан буквально про
> этот релиз — после него он перестаёт быть гипотетическим.
>
> **1. Пересев реестра — сразу после того, как Render объявил деплой живым.**
>
> ```bash
> DATABASE_URL_ADMIN="$DATABASE_URL_ADMIN_PROD" bun scripts/seed-aspects.ts
> # либо, без DSN в истории команд:  bun scripts/ops.ts seed-aspects
> ```
>
> Без него `orbis/goal` в проде НЕТ, и фича приезжает мёртвой: исполнитель валидирует
> аспекты по таблице `aspect_definitions`, а не по zod-схемам, поэтому цель, созданная
> через чат, отклоняется ошибкой `VALIDATION`.
>
> **Отказ при этом ТИХИЙ со стороны списка.** Сидированный «Год» фильтрует по
> `aspect=orbis/goal`, но имя аспекта в фильтре против каталога полей не сверяется
> (проверено пробоем: `parseQuery` на каталоге без `orbis/goal` возвращает `ok`) — блок
> разберётся, скомпилируется и честно отдаст **пустой список**. Пустой «Год» у аккаунта
> без целей выглядит ровно так же, поэтому «список открылся и он пустой» **не является
> подтверждением пересева**. Подтверждают только п. 2 и создание цели в п. 5.
>
> **2. Проверить, что пересев доехал, — живым чтением БД. `/health` здесь НЕ судья.**
>
> ```bash
> bun scripts/ops.ts check     # ждём строку «✓ orbis/goal»; это авторитетная проверка
> ```
>
> `✗ orbis/goal: в проде НЕТ` — пересев не выполнен или выполнен не в ту базу:
> вернуться к п. 1 (скрипт идемпотентен, повтор безопасен).
>
> **`/health` в этот момент соврёт, и это ожидаемо.** Его `aspectDrift` — снимок, снятый
> на старте процесса (§1 выше): сервис поднялся ДО пересева, зафиксировал расхождение
> и будет повторять `{"status":"ok","aspectDrift":["orbis/goal"]}`, сколько его ни
> спрашивай. Это не признак незакрытого п. 1 — повторять пересев бессмысленно.
>
> **3. Перезапустить сервис** (Render → `Manual Deploy` → `Restart service`). Фиче рестарт
> не нужен — исполнитель валидирует по таблице и уже видит новый реестр; нужен он
> **ловушке**: пока процесс несёт старый снимок, `/health` показывает расхождение,
> которого нет, и следующий релиз проверять этим сигналом нельзя. После рестарта:
>
> ```bash
> curl -fsS https://<prod-host>/health     # теперь ждём ровно {"status":"ok"}
> ```
>
> **Спрашивать не сразу:** процесс начинает отвечать раньше, чем стартовая проверка успела
> сходить в БД, и до её ответа честно говорит `"aspectDrift":"unknown"`. Обычно это доли
> секунды, но на холодном Supabase проверка повторяет чтение по 1/5/15 с — то есть до ~21 с.
> Выждать несколько секунд и, если пришёл `unknown`, повторить **curl**, а не рестарт.
>
> `{"status":"ok","aspectDrift":["orbis/goal"]}` **после рестарта** — вот это уже отказ:
> пересев ушёл не в ту базу. `"aspectDrift":"unknown"`, не уходящий и через полминуты
> повторных curl'ов, — проверка не выполнилась (БД была недоступна на старте), состояние
> реестра неизвестно: перезапустить сервис и посмотреть снова, «unknown» за «ok» не считать.
>
> **4. Досев горизонтов существующему аккаунту — происходит сам, но знать, чего ждать.**
> Онбординг-сидирование одноразовое: его сторож выходит из процедуры до всех вставок,
> поэтому «просто повторить сидирование» ничего бы не досеяло. Недостающие «Год» и «Жизнь»
> вставляет отдельный идемпотентный бэкфилл в ветке этого сторожа, и вызывается он тем же
> `user.seedOnboarding`, который клиент безусловно шлёт при старте сессии. Действие
> владельца — **открыть приложение и перезагрузить страницу**; ручной команды нет.
> Повторные старты дублей не создают, тела уже существующих списков не перезаписывают,
> пользовательские закрепления не двигают.
>
> **5. Убедиться глазами (это же — приёмка 02-core-os §9 п. 9).**
>
> - в сайдбаре появился **«Год»** — **последней строкой**, а не обязательно четвёртой: бэкфилл
>   дописывает закрепление в конец (`order = max(order)+1`), поэтому у аккаунта со своими
>   закреплениями «Год» встанет после них. Бейдж у него — число целей, и **у пустого графа
>   это «0», а не отсутствие бейджа**: `entity.count` возвращает `{count: 0}`, клиент печатает
>   строку «0». «Год (0)» сразу после деплоя — нормальное состояние, а не поломка;
> - в Browser по тегу `smart-list` находится **«Жизнь»** — она намеренно НЕ закреплена;
> - завести через чат цель («хочу накопить 300 000 на отпуск») и открыть её: сущность
>   создалась, на карточке аспекта `orbis/goal` есть полоса прогресса. **Это единственная
>   проверка пересева, которую видно из UI** — отказ `VALIDATION` на этом шаге означает
>   вернуться к п. 1;
> - открыть «Год»: заведённая цель в нём есть.
>
> **6. Заполнить строку истории перф-замера** (§8 ниже). Строка там до сих пор пуста:
> внести четыре клиентских числа обязан был ещё первый релиз слайса 3 (фаза A), но
> фазы A–D уехали в прод, её не заполнив. Деплой фазы E — последний релиз слайса,
> то есть последняя возможность закрыть это в его границах. Условия замера — там же;
> пропущенный замер помечать прочерком, а не пустотой.

#### Деплой ADE-среза 1: порядок шагов

Релиз редкий тем, что требует **обоих** ручных шагов — и миграции, и пересева. Код среза при
этом уже в `main` и на Render: задачи мержились по одной, каждая своим деплоем, — то есть шаг
«выкатить код» к моменту этого чек-листа выполнен, и остаток чисто операционный.

Порядок оставшихся шагов **безопасен в любую сторону**, и это стоит знать явно, чтобы не ждать
окна: миграции 0010/0011 аддитивны (новая таблица `entity_versions` и её RLS, ничего
существующего не трогают), а обращается к таблице только код роутера `version.*` — до первого
его вызова её никто не читает. Пересев реестра берёт схемы аспектов **из локального чекаута**
(`scripts/ops.ts` импортирует их из `@orbis/shared`), а не из задеплоенного кода, поэтому его
правильность определяется веткой, из которой он запущен, — но запускать его после Live всё равно
разумнее: так исключается окно, в котором свежие схемы уже в базе, а кода под них ещё нет.

```bash
# 1. схема: entity_versions + её RLS (миграции 0010, 0011) — аддитивны
bun scripts/ops.ts migrate

# 2. реестр: четыре новых аспекта среза (запускать из ветки с кодом среза)
bun scripts/ops.ts seed-aspects

# 3. сверка: расхождений реестра с кодом нет
bun scripts/ops.ts check

# 4. Restart сервиса в Render — сверка реестра выполняется НА СТАРТЕ,
#    и без рестарта /health продолжит показывать дрейф, посеянный до шага 2
```

Проверки после:

- `GET /health` — `{"status":"ok"}` **без** ключа `aspectDrift` (значения и их смысл — §1 выше);
- смоук круга живьём: выдать доступ (`--scope worker`, §3.2), назначить тикет, пройти
  `orbis_my_queue → orbis_claim_task → orbis_run_step → orbis_finish` и убедиться, что тикет
  ушёл в `waiting`, а **не** в `done`.

Если пересев забыт, отказ выглядит так: назначение агенту (`orbis/assignment`) отклоняется
валидацией `VALIDATION`, потому что исполнитель проверяет аспекты по таблице
`aspect_definitions`, а не по схемам кода, — фича приезжает мёртвой при целых данных
(fail-closed, 01-architecture §3).

#### Деплой V1 (рутины и внутренний исполнитель): порядок шагов

Релиз того же редкого класса, что ADE-срез 1 (оба ручных шага — и `migrate`, и `seed-aspects`),
плюс **третий, которого раньше не было**: переменная окружения, включающая фон. Её порядок
обратный привычному (`ORBIS_PUBLIC_URL`, ключ LLM — «сначала переменная, потом код», §1, §2):
здесь **сначала всё остальное, потом переменная**. Причина — в том, что она включает не проверку,
а работу: планировщик, поднятый до миграции `0013`, получит `42501` (нет прав на `user_settings`
у роли `orbis_app`) на **каждом** тике — не «увидит пустой список», а упадёт на первом же запросе;
поднятый до пересева — не создаст ни одного прогона (реестр отклонит `routine_id` валидацией).
Поэтому в `render.yaml` она объявлена `sync: false` **без значения**: иначе Blueprint-sync привёз
бы `1` ближайшим авто-деплоем из `main`, то есть раньше всего остального.

**Код среза уже в `main` и на Render** — задачи мержились по одной, каждая своим деплоем, как в
ADE-срезе 1; шаг «выкатить код» к моменту этого чек-листа выполнен, и остаток чисто операционный.
Отсюда и текущее состояние прода: **код новый, реестр старый**, и `/health` несёт `aspectDrift`
с `orbis/routine` (нет записи) и `orbis/agent-run` (схема разошлась). Переменной планировщика на
сервисе ещё нет, поэтому фон молчит, а всё остальное работает как прежде. Шаги 2–3 закрывают
дрейф в базе, шаг 5 (Restart) убирает его и из `/health` — снимок снимается на старте процесса, —
а шаг 6 включает фон.

```bash
# 0. связность и версия PostgreSQL (без неё дальше идти незачем)
bun scripts/ops.ts ping

# 1. что в проде сейчас: ожидаемо покажет orbis/routine «в проде НЕТ» и дрейф orbis/agent-run
bun scripts/ops.ts check

# 2. схема: политика scheduler_reads_owner_list + GRANT SELECT на user_settings (миграция 0013)
bun scripts/ops.ts migrate

# 3. реестр: orbis/routine + ИЗМЕНЁННАЯ схема orbis/agent-run (запускать из ветки с кодом среза)
bun scripts/ops.ts seed-aspects

# 4. сверка: расхождений реестра с кодом больше нет
bun scripts/ops.ts check
```

5. **Restart сервиса в Render** — сверка реестра выполняется **на старте**, и без рестарта
   `/health` продолжит показывать дрейф, посеянный до шага 3 (§1: прав в этот момент `ops.ts
   check`, а не `/health`).

6. **Включить планировщик** — Render UI → `Service → Environment` → `Add Environment Variable`
   → `ORBIS_ROUTINE_SCHEDULER` = `1`. Добавление само запускает редеплой; после него — отдельным
   docs-коммитом проставить `value: "1"` в `render.yaml`, чтобы блюпринт и сервис не разошлись
   (сценарий тихого отказа из §1). **Выполнено 2026-08-19** (переменная поставлена через Render
   API, `render.yaml` обновлён тем же днём); выключать — одновременно в UI и в `render.yaml`.
7. **Внешний пингер** — обязателен для рутин, а не «если нужно 24/7»: §5 ниже.

Проверки после:

- `GET /health` — `{"status":"ok"}` **без** ключа `aspectDrift` и с `"routineScheduler"`;
  до шага 6 там `"off"`, сразу после — `"pending"`, а через минуту-две — ISO-время начала
  последнего тика. Застрявшее `"pending"` дольше пары минут означает, что таймер не сработал
  ни разу (отставание уже стоящего времени на ~13 мин на каждый идущий прогон — норма: тик
  гонит модель синхронно и несколько наступивших прогонов гонит ПОСЛЕДОВАТЕЛЬНО, см. §7). Свежее время **не** означает, что тик отработал (отметка ставится до его тела):
  вторая половина проверки — `Logs` без строк `[routines] тик планировщика упал` и
  `[routines] рутина … — сбой тика`;
- прод-смоук рутины живьём: завести рутину словами в чате, нажать «Прогнать сейчас», принять
  предложение и откатить его; отдельно — дождаться планового бакета, чтобы проверить сам таймер.

Если пересев забыт, отказ **громкий и наблюдаемый ещё до первой рутины**: стартовая сверка
кладёт в `/health` `"aspectDrift":["orbis/routine","orbis/agent-run"]` — тем самым ключом, ради
которого этот чек-лист велит смотреть на `/health` (§1). Дальше: рутина не создаётся (`VALIDATION`
на неизвестный аспект), а если в проде осталась только старая схема `orbis/agent-run` — рутина
создастся, но её **прогон не создастся вовсе**: `entity_create` прогона отклоняется валидацией по
реестру, планировщик поднимает доменную ошибку, и в `Logs` идёт строка
`[routines] рутина <id> владельца <owner> — сбой тика: прогон рутины не создан: …`, повторяясь
каждую минуту, пока слот держится в окне догона. Сущности прогона при этом нет — значит нет ни
исхода `failed`, ни попыток, ни стоп-крана: считать ему нечего, и рутина на паузу **не встаёт**.
Данные целы (fail-closed, 01-architecture §3), лечение — шаг 3 и Restart.

#### Деплой Ш1 (дифф предложения и правка до принятия): порядок шагов

Релиз **самого простого** класса из всех, что здесь описаны: **миграций у среза нет** — ни таблиц,
ни политик, ни индексов, `bun scripts/ops.ts migrate` в нём не нужен вовсе (`plan(46)` pgTAP не
двигается). Ручной шаг ровно один — **пересев реестра аспектов**: схема `orbis/agent-run` получила
опциональное поле `proposal.edited_from` (01-architecture §3.15, решение D41). Новых переменных
окружения тоже нет.

**Порядок обратный тому, что написано у самого пересева выше** («один раз после деплоя релиза»):
здесь пересев идёт **ДО** выкатки кода — как миграции (§1.1) и по той же причине. Схема аспекта
`.strict()`, а валидирует не zod, а ajv по схеме **из базы**: выкатив код раньше реестра, получаем
`VALIDATION` на каждой правке предложения, то есть фичу, приехавшую мёртвой. Обратной опасности
нет — пересев безопасен заранее, потому что поле **опционально**, а старый код его не пишет: прод
до деплоя продолжает работать на новой схеме без единого изменения поведения. Бэкфилла тоже нет:
прогоны, созданные до среза, поля не несут и остаются валидными.

```bash
# 0. связность (без неё дальше идти незачем)
bun scripts/ops.ts ping

# 1. что в проде сейчас: если код уже выкачен, ожидаемо покажет дрейф orbis/agent-run
bun scripts/ops.ts check

# 2. реестр: ИЗМЕНЁННАЯ схема orbis/agent-run (запускать из ветки с кодом среза) — ДО деплоя кода
bun scripts/ops.ts seed-aspects

# 3. сверка: расхождений реестра с кодом нет
bun scripts/ops.ts check
```

4. **Выкатить код.** Если он уже в `main` и на Render (задачи мержились по одной, каждая своим
   деплоем, — как в ADE-срезе 1 и V1), вместо выкатки нужен **Restart сервиса**: сверка реестра
   снимается на старте процесса, и без рестарта `/health` продолжит показывать дрейф, посеянный
   до шага 2.

Проверки после:

- `GET /health` — `{"status":"ok"}` **без** ключа `aspectDrift`;
- прод-смоук живьём: дождаться (или запустить кнопкой «Прогнать сейчас») прогон рутины с
  предложением и открыть **саму запись**, а не тред, — над телом обязана стоять плашка
  предложения; развернуть её, поправить значение поля и текст тела, нажать «Принять». В графе
  должно оказаться то, что набрал владелец; в треде рутины — исходная карточка с подписью
  «Заменено правкой владельца — правленое предложение ниже» и под ней правленая с «Принято
  (с правками)». Отдельно проверить путь «Устарело»: правка предложения, чью запись успели
  тронуть, не применяется вовсе;
- **старые вкладки PWA — ожидаемая ошибка, а не регресс.** Решение по предложению теперь
  адресуется конкретным `pendingId`, и вкладка, открытая **до** этого деплоя, на «Принять» /
  «Отклонить» получит ошибку валидации до перезагрузки страницы. Окно — **время жизни вкладки**
  (ассеты кешируются иммутабельно), а не секунды. Цена принята осознанно: громкий отказ
  безопаснее тихого применения предложения, которого владелец не читал. Лечение — перезагрузка.

Если пересев забыт, отказ громкий и наблюдаемый: `/health` несёт `"aspectDrift":["orbis/agent-run"]`,
а приём предложения **с правкой** падает `VALIDATION` (fail-closed — данные целы). Обычный приём
без правок при этом продолжает работать, поэтому на дрейф здесь смотрят по `/health`, а не по
жалобе. Лечение — шаг 2 и Restart.

**Долг, вынесенный владельцу этим срезом (лечения в срез не входят).** Слой предложения на записи
ищет открытые предложения containment-пробой по jsonb (`metadata @> …`), и под RLS такая проба
**не берёт GIN-индекс**: `jsonb_contains` не leakproof (`pg_proc.proleakproof = f`), поэтому
планировщик не вправе опустить её в `Index Cond` ниже security-квала — план выходит Seq Scan
(замер на локальной базе: 39 тыс. сообщений, ~50 мс на три условия; в обход RLS тот же запрос
идёт `BitmapOr` по `chat_messages_metadata_gin` за ~0.3 мс, то есть форма пробы верна). Свойство
**общерепозиторное**, а не этого среза: так же сканируются чтение отложенного действия
(`storedProposal` / `findPendingMessage`) и `entity_query` по `aspects` — со дня включения RLS.
Сегодня цена незаметна (сообщений в проде на порядки меньше, показ ≤ 1 на рутину, кеша нет именно
поэтому), но растёт с объёмом переписки. Оба лечения требуют решения владельца:
`ALTER FUNCTION … LEAKPROOF` — это решение **по безопасности** (leakproof-функция может раскрыть
строку через сообщение об ошибке мимо RLS), скалярный столбец с btree вместо пробы по jsonb —
**миграция**.

#### 1.1 Миграции на ЖИВОЙ прод: команда и порядок относительно деплоя

**Порядок: сначала миграции, потом деплой кода.** Не наоборот.

```bash
bun scripts/ops.ts migrate     # идемпотентно: на актуальной базе не делает ничего
```

Затем — обычная выкатка Render (push в `main` или Manual Deploy).

**Почему именно так.** Миграции этого комплекта чисто аддитивны (`0004` — две новые
таблицы, `0005` — RLS и гранты на них, `0006` — одна новая колонка в новой же таблице):
работающий в проде СТАРЫЙ код о них не знает и от их появления не меняется, поэтому
опережающий накат безопасен. Обратный порядок — нет: новый код на первом же запросе к
`/mcp` зовёт `verifyBearer` (`oauth/grants.ts`), тот бьёт в ещё несуществующую
`agent_grants`, а вызов не обёрнут в try/catch (`mcp/transport.ts:74`) — вместо честного
401 эндпоинт отдаёт 500, «Настройки → Агенты» падает на `listGrants`, и всё это при
**зелёном `/health`**: проверка здоровья новых таблиц не касается. Тихая поломка ценой
неверного порядка двух команд.

**Почему нужна отдельная команда, а не `bun run db:prepare`.** `db:prepare` написан про
**новую или восстановленную** базу и для живого прода не годится по двум причинам:

- он зовёт `scripts/setup-db.ts`, а тот делает `ALTER ROLE orbis_app PASSWORD` из
  `ORBIS_APP_PASSWORD` — на проде это **ротация пароля боевой роли**, то есть обрыв
  `DATABASE_URL`, если в окружении оператора лежит не то же значение;
- он завершается `bun run test:rls`, а тот ставит расширение `pgtap` и льёт фикстуры —
  на проде им не место, пусть и в откатываемой транзакции.

Голый `db:migrate` тоже не подходит: ему нужен админский DSN в окружении, а голый прод-DSN
оператору не выдаётся — по той же причине, по которой заведена обёртка `ops.ts` (§1).
Поэтому накат добавлен в белый список операцией `migrate`: секрет остаётся в Ключнице,
радиус — ровно «применить неприменённые файлы миграций из репозитория».

**Контейнер миграции не катит.** `Dockerfile` сразу запускает сервер (`CMD ["bun",
"apps/server/src/index.ts"]`), шага миграции в образе нет и заводить его не планируется:
на Render с free-планом это означало бы гонку миграций между экземплярами при рестартах.

Роль `orbis_app` операция не создаёт — на проде она есть с самого первого релиза. Отказ
`role "orbis_app" does not exist` означает, что база не подготовлена вовсе; это случай
`db:prepare` (блок ниже), а не этой команды.

#### Миграции схемы на НОВОЙ базе: штатный путь только `bun run db:prepare`

**Голый `bun run db:migrate` на базе, где нет роли `orbis_app`, теперь падает.** Причина —
`0005_oauth_rls.sql`: это **первая** миграция комплекта, называющая роль поимённо
(`CREATE POLICY … TO orbis_app`, `GRANT … TO orbis_app`), а PostgreSQL проверяет
существование роли в момент DDL и отвечает `role "orbis_app" does not exist`. Прежние
миграции обходились ролью `authenticated` (членство в ней роли `orbis_app` выдаёт
`setup-db.ts`), поэтому раньше `db:migrate` на голой базе проезжал — и привычка «накатить
миграции отдельно» была безопасной. Больше нет.

Роль создаёт `scripts/setup-db.ts`, и `db:prepare` зовёт его **первым**:

```
setup-db.ts  →  db:migrate  →  seed-aspects.ts  →  test:rls
```

Практический вывод один: новую базу (локальный стенд, CI, БД после восстановления §4.3)
готовить только `bun run db:prepare`. Порядок здесь не стилистический — переставив шаги,
получишь отказ на середине с частично накатанной схемой.

## 2. Секреты (Render Environment, `sync: false`)

**Секреты** (в `render.yaml` помечены `sync: false`) задаются в Render UI
(`Service → Environment`) и в git не хранятся. Но не всё в таблице ниже — секрет:
`PG_PREPARE`, `ORBIS_LLM_PROVIDER` и `ORBIS_PUBLIC_URL` объявлены в блюпринте строкой
`value:`, то есть их источник истины — `render.yaml`, а на сервис они приезжают синком
блюпринта. `ORBIS_ROUTINE_SCHEDULER` тоже не секрет, но помечена `sync: false`
намеренно — по порядку ввода, а не по чувствительности (см. её строку ниже).
Разница не формальная: при смене провайдера искать `ORBIS_LLM_PROVIDER` глазами надо
именно в UI (что реально стоит на сервисе), а менять — в `render.yaml`; расхождение
между этими двумя местами и есть сценарий тихого отказа из чек-листа §1. Перечень:

| Ключ | Назначение | Формат / источник |
|---|---|---|
| `DATABASE_URL` | боевой пул API (роль `orbis_app`) | `postgresql://orbis_app.<PROD_REF>:<pwd>@<POOLER_HOST>:5432/postgres` (session-пулер) |
| `PG_PREPARE` | prepared statements для session-пулера | `true` (не секрет; для transaction-режима `:6543` было бы `false`) |
| `ORBIS_PUBLIC_URL` | публичный адрес сервиса: база всех абсолютных URL в метаданных OAuth (§9.3) | `https://orbis-64q4.onrender.com` (не секрет — задана в `render.yaml` строкой `value:`). **Обязательна в production**, см. предупреждение ниже |
| `ANTHROPIC_API_KEY` | ключ Anthropic | нужен при `ORBIS_LLM_PROVIDER=anthropic` |
| `OPENAI_API_KEY` | ключ OpenAI | нужен при `ORBIS_LLM_PROVIDER=openai` |
| `ORBIS_LLM_PROVIDER` | явный выбор провайдера (в `render.yaml` = `openai`) | без него: один ключ → он и выбран, ОБА ключа → отказ при старте, ключей нет → echo (в production отказ) |
| `ORBIS_ROUTINE_SCHEDULER` | включает планировщик рутин (V1, 01-architecture §9.3): тик раз в минуту внутри процесса | `1` — включён, любое другое значение и отсутствие — выключен. **Не секрет**, но в `render.yaml` стоит `sync: false` без значения: порядок ввода обратный обычному — переменная ставится руками **после** миграции `0013`, пересева реестра и кода (чек-лист «Деплой V1» §1). После включения — docs-коммит с `value: "1"` (выполнено 2026-08-19: в `render.yaml` теперь `value: "1"`; выключать — одновременно в UI и в yaml) |
| `ORBIS_LLM_MODEL` | (опц.) модель по умолчанию | иначе дефолт провайдера: `claude-sonnet-5` (`DEFAULT_ANTHROPIC_MODEL`) либо `gpt-5.5` (`DEFAULT_OPENAI_MODEL`, `apps/server/src/llm/openai.ts`) |
| `SUPABASE_URL` | база JWT-верификации: issuer-пиннинг + из него выводится JWKS-адрес (`auth.ts`) | `https://<PROD_REF>.supabase.co` (без завершающего слэша) |
| `SUPABASE_JWT_SECRET` | верификация JWT (HS256, fallback к JWKS) | из Supabase `Project Settings → API`. Если проект на асимметричных ключах (ES256/JWKS) — **не задавать**: путь мёртв, а знающий секрет подделает токен владельца. Срабатывание фолбэка в проде пишет предупреждение в лог |
| `SUPABASE_JWKS_URL` | (опц.) явный override JWKS; в `render.yaml` НЕ задаётся — дефолт `{SUPABASE_URL}/auth/v1/.well-known/jwks.json` | обычно не нужен |
| `VITE_SUPABASE_URL` | build-env web-клиента | `https://<PROD_REF>.supabase.co` |
| `VITE_SUPABASE_ANON_KEY` | build-env web-клиента | anon-ключ прод-проекта |

`VITE_API_URL` не задаётся (режим A same-origin: клиент бьёт в относительный `/trpc`).
`PORT` тоже не задаётся: его инжектит Render, а `index.ts` имеет дефолт `3001`.

Отдельно для бэкапа — GitHub Actions secret `ADMIN_DSN` и переменная `BACKUP_PUBLIC_KEY`
(см. §4), НЕ в Render.

Правила: секреты не логируются и не коммитятся; ротация — заменить значение в UI и
передеплоить (Render перезапускает процесс с новым env).

> **`ORBIS_PUBLIC_URL` обязана стоять на сервисе ДО выкатки ветки браузерного входа.**
> Без неё в `NODE_ENV=production` процесс **не поднимается вовсе** — стартовый гейт
> (`apps/server/src/index.ts` → `assertPublicOriginConfigured`) бросает до старта сервера,
> healthcheck не проходит, и Render объявляет деплой неудачным. Со стороны дашборда это
> выглядит как упавший релиз, а не как забытая переменная, поэтому сказано здесь прямо:
> **сначала переменная, потом код** — тот же порядок и та же причина, что у ключа
> LLM-провайдера (§1, D28).
>
> **Как она туда попадает — руками, и строка в `render.yaml` этого не заменяет.** Здесь
> легко ошибиться ровно потому, что переменная объявлена `value:`: увидев её в блюпринте,
> естественно решить, что делать нечего. Но синк блюпринта приезжает **вместе с кодом** —
> то есть в тот самый деплой, который без переменной и не поднимется. Поэтому до мержа
> её выставляют **вручную**: Render UI → `Service → Environment` → `Add Environment
> Variable` → `ORBIS_PUBLIC_URL` = `https://orbis-64q4.onrender.com`. Добавление само
> запускает редеплой на старом коде — тот про переменную не знает и молча её игнорирует
> (весь `oauth/` приезжает этой же веткой), так что порядок безопасен. Когда синк
> блюпринта потом привезёт то же значение, он совпадёт с выставленным вручную, и
> расхождения «UI против `render.yaml`», которым опасен `ORBIS_LLM_PROVIDER` (§1), здесь
> не возникнет — при условии, что руками выставлено ровно значение из `render.yaml`.
>
> Значение — **только чистый origin**, без пути, query и фрагмента. Кривое значение
> (`https://host/mcp`, `http://host/?x=1`, не-http-схема) роняет старт **в любом
> окружении**, не только в production: локально «всё работает, а в проде рвётся» — худший
> из возможных исходов для переменной, из которой собираются адреса метаданных.
> Хвостовой слэш прощается: `https://host/` и `https://host` — одно и то же.
>
> Почему отказ такой резкий. База метаданных не выводится из заголовка `Host`: подменённый
> `Host` увёл бы MCP-клиента на чужой authorization server прямо через наши же метаданные.
> А мягкий откат тут невозможен по механике: указатель на метаданные собирается **на пути
> отказа** (401 на `/mcp`), поэтому бросок из-за конфигурации превратил бы 401 в 500 —
> вход агента ломался бы молча при зелёном `/health`.
>
> Проверка после деплоя — метаданные обязаны называть боевой адрес, а не что-то ещё:
>
> ```bash
> curl -fsS https://<prod-host>/.well-known/oauth-protected-resource/mcp
> # {"resource":"https://<prod-host>/mcp","authorization_servers":["https://<prod-host>"],…}
> ```
>
> `ORBIS_PAT_HASH` и `ORBIS_PAT_OWNER_ID` из этой таблицы **убраны**: с переездом PAT
> в таблицу грантов (D34) их не читает ни одна строка кода. Если они ещё лежат на сервисе
> в Render UI — удалить, чтобы мёртвая переменная не выглядела живой конфигурацией.

## 3. Подключение внешнего агента (Claude Code) и отзыв доступа

Путей два, и они не смешиваются: **браузерный вход** (основной, для интерактивной сессии)
и **headless-токен** (для `claude -p`, Agent SDK и CI). Оба ведут в одну таблицу грантов,
у обоих один экран отзыва. Контракт хранения общий — **hash-only**: в базе только `sha256`,
сырой токен показывается ОДИН раз и не восстановим (потерял — выпусти новый).

### 3.1 Браузерный вход — основной путь

Ничего не переносится руками, переменных окружения не появляется:

```bash
claude mcp add --transport http orbis https://<prod-host>/mcp
```

Затем в сессии агента — команда `/mcp`, и вход откроется в браузере: Claude Code упрётся
в 401, по `WWW-Authenticate` найдёт метаданные, зарегистрируется сам и приведёт на экран
согласия. **На экране согласия владелец должен быть залогинен в веб-клиенте Orbis** — если
нет, сначала покажется обычный экран входа (форма email + пароль, `LoginScreen.tsx`), и
только потом согласие. Второго способа логина слайс не заводит; magic link — операторский
приём для смоука через админский API Supabase, в веб-клиенте его нет. Ту же команду
подключения показывает и само приложение: «Настройки → Агенты».

Что стоит знать заранее:

- **Область доступа выбирается прямо на экране согласия** — радио «Полный доступ» /
  «Только исполнитель (worker)» (PRD 01 §4.14). Выбор владельца; значение `scope`, которое
  прислал сам клиент, игнорируется. Область гранта потом не меняется — нужна другая, значит
  отозвать и подключиться заново; в «Настройки → Агенты» она видна бейджем.
- **Первый шаг может думать ~минуту.** Render free усыпляет сервис (§5), и холодный старт
  приходится ровно на первый запрос браузерного входа. Это латентность, а не отказ.
- **Строка «согласие дано» без «подключён» — не то же самое, что подключённый агент.**
  Грант заводится в момент нажатия «Разрешить», ДО обмена кода на токены; агент, который
  до обмена не дошёл (упал, окно закрыли), оставляет такую строку навсегда. В списке она
  подписана «Агент не забрал доступ — повторите подключение в агенте», и кнопка «Отозвать»
  у неё есть — сервер отозванному гранту код обменять не даст.

### 3.2 Headless-токен (PAT) — для `claude -p`, Agent SDK и CI

Интерактивный вход эти режимы не проходят, поэтому остаётся заголовочный путь.
Выдача требует **записи в базу** — с переездом PAT из окружения в таблицу грантов (D34)
скрипт больше не «печатает хеш», а создаёт строку.

**На проде — только через белый список `scripts/ops.ts`** (§1, секрет в Ключнице macOS;
голый прод-DSN оператору не выдаётся):

```bash
bun scripts/ops.ts issue-pat <owner-uuid> "CI"                    # метка необязательна
bun scripts/ops.ts issue-pat <owner-uuid> "прогон" --scope worker # фоновый исполнитель
```

`<owner-uuid>` — из Supabase → `Authentication → Users`. Операция сначала проверяет, что
такой пользователь существует, и отказывается выдавать токен «в никуда»: опечатка в UUID
иначе дала бы живой токен несуществующего владельца, который молча видел бы пустой граф.

`--scope worker` сужает доступ до фонового исполнителя (PRD 01 §4.14): чтения и глаголы задач,
никакой прочей записи в граф. Без флага выдаётся полный доступ — прежнее поведение.
Опечатка в области (`--scope wroker`) — **отказ** кодом 2, а не откат на полный доступ:
токен печатается один раз, и «выдал не то» отменяется только отзывом.

**На локальном стенде** — тот же выпуск без Ключницы, обычным скриптом (читает
`DATABASE_URL`, продуктовая роль `orbis_app`):

```bash
bun scripts/issue-pat.ts <owner-uuid> [метка] [--scope worker]
```

Оба печатают сырой токен `orbis_pat_<hex>` — **один раз**. Его НЕ логировать и НЕ коммитить.
Подключение агента этим токеном:

```bash
claude mcp add --transport http orbis https://<prod-host>/mcp \
  --header "Authorization: Bearer <токен>"
```

> **Заголовок и браузерный вход — две разные записи конфига, а не запасные пути одной.**
> Если у сервера задан `headers.Authorization`, при отказе Claude Code **не** откатывается
> на OAuth, а рапортует о сбое соединения. То есть протухший или отозванный PAT выглядит
> как «сервер недоступен», а не как «нужно войти».

### 3.3 Отзыв доступа

**«Настройки → Агенты» → «Отозвать»** — для обоих видов доступа. Действует немедленно и
по одному гранту: остальные агенты продолжают работать. Передеплой не нужен и ничего
не отзывает (это было верно, пока хеш жил в окружении; теперь — нет).

Отозванные строки из списка **не исчезают** — они остаются с отметкой «отозван ‹дата›».
Поэтому список никогда не станет пустым после первого отзыва, и команда подключения
показана в разделе всегда, а не только при пустом списке.

Ротация: отозвать старый грант и выпустить новый — восстановить сырой токен нельзя
по построению.

## 4. Бэкап БД

> **Репозиторий `qvenge/orbis` — публичный.** Artifact любого Actions-рана в публичном
> репозитории скачивается посторонними, поэтому дамп выгружается **только зашифрованным**
> (OpenPGP, публичный ключ владельца). Незашифрованный дамп на раннер не попадает: гейт
> ключа стоит до `pg_dump`, а plain-файл удаляется сразу после шифрования.
> Альтернатива, снимающая проблему в корне, — сделать репозиторий приватным (решение владельца).

### 4.1 Автоматический (GitHub Actions cron)

Workflow `.github/workflows/backup.yml`: `pg_dump` прод-БД через session-пулер `:5432`
ежедневно в 03:00 UTC + ручной запуск (`workflow_dispatch`). Зашифрованный дамп грузится
как artifact `orbis-db-backup` (файл `orbis-backup-<ts>.sql.gpg`, retention 30 дней).

**Гейт 1 — секрет `ADMIN_DSN`** (Фаза B): `Settings → Secrets and variables → Actions →
Secrets → New repository secret`, значение — session-пулерный DSN роли `postgres`
(не `orbis_app` — для дампа нужна роль-владелец):

```
postgresql://postgres.<PROD_REF>:<pwd>@<POOLER_HOST>:5432/postgres
```

**Гейт 2 — переменная `BACKUP_PUBLIC_KEY`**: armored OpenPGP **публичный** ключ владельца
(`Settings → Secrets and variables → Actions → Variables`). Приватный ключ на GitHub не
хранится — компрометация аккаунта GitHub не раскрывает бэкапы, но и **потеря приватного
ключа делает все дампы нечитаемыми**: экспортируй его в надёжное место сразу.

```bash
# одноразово, на машине владельца
gpg --quick-generate-key "orbis-backup" default default never
gpg --armor --export orbis-backup > backup-pub.asc     # содержимое → в BACKUP_PUBLIC_KEY
gpg --armor --export-secret-keys orbis-backup > backup-priv.asc   # хранить офлайн, не в репо
```

Без любого из гейтов первый шаг workflow падает с явной ошибкой, а не молча.
Ручной прогон: `Actions → backup → Run workflow`.

### 4.2 Ручной бэкап

```bash
ADMIN_DSN='postgresql://postgres.<PROD_REF>:<pwd>@<POOLER_HOST>:5432/postgres' \
  BACKUP_DIR=./backups \
  bash scripts/backup.sh
```

Скрипт: `pg_dump --no-owner --no-privileges` через session-пулер; требует `pg_dump >= PG17`
(иначе автоматически дампит через `docker run postgres:17-alpine`); проверяет, что дамп непуст
и содержит таблицу `entities` (маркер целостности прод-схемы); печатает путь строкой `dump: <path>`.
Пароль/DSN в вывод не попадают. Шифрование здесь не выполняется (это делает workflow):
`./backups` и `orbis-backup-*.sql` внесены в `.gitignore`/`.dockerignore`, но локальный
дамп — это открытые прод-данные, храни его соответственно.

### 4.3 Восстановление

Artifact из Actions расшифровывается приватным ключом владельца (§4.1):

```bash
gpg --decrypt orbis-backup-<ts>.sql.gpg > orbis-backup-<ts>.sql
```

Плейн-SQL дамп (`.sql`) восстанавливается через `psql`. Восстанавливать в ЧИСТУЮ БД
(новый Supabase-проект или пересозданная схема), иначе конфликты по существующим объектам.

> **`psql` обязан понимать `\restrict`.** Начиная с релизов 17.6 / 16.10 / 15.14 / 14.19 / 13.22
> (август 2025) `pg_dump` обрамляет дамп директивами `\restrict` … `\unrestrict`. Более старый
> `psql` встретит их как неизвестные мета-команды и с `ON_ERROR_STOP=1` оборвёт восстановление
> на первой же строке. Проверить: `psql --version`. Если версия ниже — восстанавливать через
> контейнер: `docker run --rm -i -v "$PWD:/in" postgres:17-alpine psql "<DSN>" -v ON_ERROR_STOP=1 -f /in/orbis-backup-<ts>.sql`.

```bash
psql 'postgresql://postgres.<TARGET_REF>:<pwd>@<POOLER_HOST>:5432/postgres' \
  -v ON_ERROR_STOP=1 -f orbis-backup-<ts>.sql
```

Проверка после восстановления — все 11 таблиц прод-схемы на месте:

```bash
psql "$ADMIN_DSN" -c "\dt public.*"
# ожидаемо: entities, relations, aspect_definitions, user_settings,
#           chat_threads, chat_messages, ai_usage, entity_origins,
#           oauth_clients, agent_grants, entity_versions
```

**Владелец получит НОВЫЙ UUID.** `owner_id` логически ссылается на `auth.users` (FK нет —
схемой auth владеет Supabase), а дамп её не содержит: после регистрации в новом проекте
RLS спрячет все восстановленные строки — база выглядит пустой при полных таблицах.
Перепривязать нужно **семь** таблиц. Колонка `owner_id` есть у восьми (`entities`,
`aspect_definitions`, `user_settings`, `chat_threads`, `ai_usage`, `entity_origins`,
`entity_versions`, `agent_grants`), но `agent_grants` в скрипт намеренно не входит — почему,
сказано сразу после запроса. `user_settings.owner_id` — PK, поэтому строки нового пользователя
не должны существовать; у `aspect_definitions` встроенные записи несут `owner_id IS NULL` и
условием `WHERE owner_id = :'old'` не задеваются.

```bash
psql "$ADMIN_DSN" -v ON_ERROR_STOP=1 <<'SQL'
\set old '<старый-uuid>'
\set new '<новый-uuid-из Authentication → Users>'
BEGIN;
UPDATE entities           SET owner_id = :'new' WHERE owner_id = :'old';
UPDATE aspect_definitions SET owner_id = :'new' WHERE owner_id = :'old';
UPDATE user_settings      SET owner_id = :'new' WHERE owner_id = :'old';
UPDATE chat_threads       SET owner_id = :'new' WHERE owner_id = :'old';
UPDATE ai_usage           SET owner_id = :'new' WHERE owner_id = :'old';
UPDATE entity_origins     SET owner_id = :'new' WHERE owner_id = :'old';
UPDATE entity_versions    SET owner_id = :'new' WHERE owner_id = :'old';
COMMIT;
SQL
```

> **`entity_versions` в списке не для полноты.** Таблица закреплённых версий тела
> (PRD 01 §4.15) несёт собственный `owner_id` и живёт под собственной RLS: пропустив её,
> получаем целые строки, которых владелец не видит, — то есть «версии пропали» при
> восстановленных телах. Колонка `actor_user_id` там же — историческая атрибуция «кто
> закрепил»; RLS её не касается, и перепривязывать её не обязательно.

> **Чего в этом списке нет и почему — проверено пробой, а не выведено из PRD.** Прежняя
> версия блока звала `UPDATE relations SET owner_id` и `UPDATE chat_messages SET owner_id`,
> а такой колонки у обеих таблиц **нет**: владение там резолвится транзитивно — у `relations`
> через обе связанные `entities`, у `chat_messages` через `chat_threads.owner_id` (PRD 01
> §4.10). PostgreSQL отвечает на них `column "owner_id" does not exist`, а с
> `ON_ERROR_STOP=1` psql обрывается на втором `UPDATE` **до `COMMIT`** — то есть скрипт
> не перепривязывал НИЧЕГО, молча и посреди восстановления после аварии. Зеркальная
> половина той же ошибки: `entity_origins` с настоящей колонкой `owner_id` в списке
> отсутствовал, и provenance импорта остался бы на старом владельце, уйдя под RLS, —
> дедуп повторного импорта (§4.8) перестал бы срабатывать. Перепривязывать `relations`
> и `chat_messages` не нужно и не надо: они поедут за родителями сами.

**Доступы агентов после восстановления — выдать заново, а не перепривязывать.** Таблица
`agent_grants` (§3) тоже несёт `owner_id` и тоже попадает в дамп, но перепривязка ей
противопоказана: сырые токены у агентов на руках, их `sha256` в восстановленных строках
совпадёт, и `UPDATE owner_id` **воскресил бы** доступ, выданный в другом проекте, — включая
тот, который к моменту аварии могли отозвать. Оставленная как есть строка тоже плоха, но
иначе: аутентификация пройдёт по старому `owner_id`, агент получит **пустой граф** вместо
отказа — тихая поломка, которую легко принять за потерю данных. Поэтому — погасить всё
и подключиться заново (§3.1 для браузерного входа, §3.2 для headless):

```bash
psql "$ADMIN_DSN" -v ON_ERROR_STOP=1 \
  -c "UPDATE agent_grants SET revoked_at = now() WHERE revoked_at IS NULL"
```

Переменных Render этот шаг больше не касается: `ORBIS_PAT_HASH`/`ORBIS_PAT_OWNER_ID`
не существует с D34 (§2).

**Про права. Автоматически они НЕ появляются — после restore их придётся выдать руками.**

Дамп снят без owner/privileges (`--no-owner --no-privileges`), и переприменить гранты
некому: журнал `drizzle.__drizzle_migrations` попадает в дамп, миграции считаются
применёнными, поэтому `db:migrate` (и `db:prepare` вместе с ним) проходит вхолостую.

Прежде здесь было написано, что права на таблицы даёт `alter default privileges` самого
Supabase, автоматически объектам роли `postgres`. **Это неверно**, проверено каталогом:
у default ACL роли `postgres` в схеме `public` для `anon`/`authenticated`/`service_role`
стоит `Dxtm` — TRUNCATE, REFERENCES, TRIGGER, MAINTAIN, и ни одного DML-права. Полный
набор `arwdDxtm` раздаёт только default ACL роли `supabase_admin`, а restore и миграции
идут под `postgres`. Видно на живой таблице:

```
entities | {postgres=arwdDxtm/postgres,anon=Dxtm/postgres,
            authenticated=arwdDxtm/postgres,service_role=Dxtm/postgres}
```

`authenticated=arwdDxtm` здесь — не от default ACL, а от явных `GRANT` в миграциях:
`0001_rls_and_indexes.sql:95,97` (схема + DML на все таблицы) и `0005_oauth_rls.sql:47,49`
(две таблицы §9.3). Их и не станет после restore.

Цена — не «частично не работает», а **не работает вообще**: приложение ходит в данные
через `SET LOCAL ROLE authenticated` (`db/with-identity.ts:23`, роль `orbis_app`
объявлена `NOINHERIT`), то есть опирается ровно на те гранты, которых после restore нет.
`orbis_app` собственных прав на восемь старых таблиц не имеет вовсе — в их ACL его нет.

Поэтому после restore, **до** `db:prepare`, выдать гранты заново — это те же строки, что
в миграциях, дословно:

```bash
psql "$ADMIN_DSN" -v ON_ERROR_STOP=1 <<'SQL'
GRANT USAGE ON SCHEMA public TO authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON agent_grants, oauth_clients TO orbis_app;
SQL
```

Затем `bun run db:prepare` против целевой БД — он создаёт роль `orbis_app` и членство
в `authenticated` (`scripts/setup-db.ts`) и завершается RLS-тестом (40 pgTAP-проверок).
Тест остаётся страховкой: если гранты забыть, он упадёт — но искать причину надо здесь,
а не в RLS.

На **чистую** базу (не restore, а пустой проект) это не распространяется: там журнала нет,
миграции применяются целиком вместе со своими `GRANT`, и ручной шаг не нужен. Нужен
только `setup-db.ts` первым — без него миграции дойдут до `0005_oauth_rls.sql` и упадут
на несуществующей роли `orbis_app` (разбор в §1).

> **Ловушка: `bun run test:rls` из корня не видит `DATABASE_URL_ADMIN`** (обнаружено
> на приёмке фазы D слайса 2). Переменная лежит в `apps/server/.env`, а корневой скрипт
> её не подхватывает — прогон падает на «`DATABASE_URL_ADMIN` не задан», хотя файл есть.
> Экспортировать окружение явно:
>
> ```bash
> set -a && . ./apps/server/.env && set +a && bun run test:rls
> ```
>
> То же относится к отдельному запуску `bun scripts/seed-aspects.ts` (§1) — он читает
> ИМЕННО `DATABASE_URL_ADMIN`.

## 5. Keep-warm (сон Render free)

Render free усыпляет сервис после ~15 минут без HTTP; cold start ~1 минута (SPIKE-05).
Supavisor штатно переживает переустановку пула, данные не теряются — это только латентность
первого запроса.

Стратегии (по возрастанию стоимости):

1. **Polling агентной петли (по умолчанию).** Приёмочный агент днём периодически бьёт в `/mcp`
   (`entity_query` по `updated_at`) — эти запросы держат сервис тёплым в рабочие часы.
2. **Внешний keep-warm пинг** (если нужно 24/7 без апгрейда): любой бесплатный uptime-пингер
   раз в 10–14 минут дёргает `GET https://<prod-host>/health` (лёгкий, без БД). Ставить ниже
   15-минутного окна сна. Компромисс — держит free-инстанс занятым близко к лимиту часов.
3. **Апгрейд без сна:** Render Starter $7/мес (без сна, та же топология) ЛИБО миграция на
   Fly.io ~$2.24/мес (always-on, нужна карта). Решение по стоимости — владельческий гейт.

> **С V1 стратегия 2 перестала быть опциональной.** Планировщик рутин (01-architecture §9.3) —
> таймер **внутри процесса**: спящий сервис не тикает, а значит не создаёт прогонов. Догон
> в окне 6 часов спасает утренний слот, если сервис проснулся от чего угодно до полудня, — но
> «проснулся» на free-плане означает «кто-то постучался», и без пингера этим кем-то будет сам
> владелец, открывший приложение. Рутина, чей смысл в том, чтобы план был готов **до** прихода
> владельца, так не работает. Поэтому: **пингер раз в 10 минут — часть поставки V1**, а не
> оптимизация латентности. Интервал именно 10, а не 14: 14 минут оставляют слишком мало запаса
> до 15-минутного окна сна, и один пропущенный пинг уже роняет сервис в сон.
>
> **Арифметика лимита, чтобы не упереться в него молча.** Круглосуточный пинг держит инстанс
> занятым практически всё время: ≈ 720 часов в месяц при бесплатном лимите **750 часов** —
> запас около **4 %**, то есть примерно сутки. Он съедается вторым сервисом на том же аккаунте
> или длинным месяцем, и тогда сервис останавливается до начала следующего расчётного периода.
> Если рутины окажутся нужны надёжно, честный ответ — не более редкий пинг (он вернёт сон),
> а стратегия 3.
>
> **Адрес пингера (V1, включён 2026-08-19):** `.github/workflows/keep-warm.yml` — GitHub Actions
> cron `*/10 * * * *`, шаг `curl -fsS -m 90 https://orbis-64q4.onrender.com/health` (прецедент
> бесплатного cron'а — `backup.yml`). Расписание GitHub задерживается на минуты — принято, догон
> 6 ч страхует слот. Проверка, что пингер жив: вкладка Actions → workflow «keep-warm», зелёные
> раны каждые ~10 мин; `/health` без задержки cold start.
>
> **Что пинговать: `/health` и смотреть на его тело.** С V1 ответ несёт поле `routineScheduler`
> (§7): `"off"` — фон выключен переменной, `"pending"` — включён, но не тикал ни разу,
> ISO-время — момент **начала** последнего тика. Пингер, который смотрит только на код 200, не
> отличит живой фон от процесса, в котором планировщик молча не поднялся. Обратное тоже верно и
> важнее: свежее время говорит только о том, что **таймер сработал**, — упавший тик (нет прав,
> отказ записи) отметку ставит такую же, и «фон жив» подтверждается только логами.

Замер cold-start фиксируется в приёмке (Task 12): первый запрос после 15+ мин простоя.

## 6. Пауза Supabase Free (неактивность ~7 дней)

Supabase Free ставит проект на паузу после ~7 дней без активности к БД. На паузе API/пулер
недоступны — сервис отдаёт ошибки подключения.

- **Профилактика:** ежедневный backup-cron (§4.1) сам обращается к БД и сбрасывает счётчик
  простоя; polling агента днём — тоже активность.
- **Снятие с паузы:** `dashboard.supabase.com → проект <PROD_REF> → Restore/Resume project`.
  После восстановления проверить связность: `psql "$ADMIN_DSN" -c 'select 1'` и `/health` сервиса.

> **Оба механизма отказывают вместе.** GitHub отключает cron-workflow в публичном репозитории
> после **60 дней без активности в репозитории** (прогоны cron активностью не считаются —
> нужны коммиты). Тихий проект: 60 дней → бэкапы прекращаются → ещё ~7 дней → БД на паузе,
> а artifacts старше 30 дней уже истекли. Перед отключением GitHub шлёт уведомление;
> включить обратно: `Actions → backup → Enable workflow`. Раз в пару месяцев стоит проверять,
> что последний прогон backup зелёный.

## 7. Health-мониторинг

`GET /health` — liveness процесса без обращения к БД (`app.ts`: `{"status":"ok"}`). Используется
Render (`healthCheckPath: /health`) и внешним пингером (§5).

```bash
curl -fsS https://<prod-host>/health           # 200 {"status":"ok"} — процесс жив
```

Сверх `status` в ответе бывают два диагностических поля, оба — снимки состояния процесса, а не
проверки на лету: `aspectDrift` (расхождение реестра аспектов с кодом, §1) и `routineScheduler`
(планировщик рутин V1, 01-architecture §9.3). Второе присутствует **всегда**, когда сервис
собран боевыми зависимостями:

```bash
curl -fsS https://<prod-host>/health
# {"status":"ok","routineScheduler":"off"}                       — ORBIS_ROUTINE_SCHEDULER не выставлена
# {"status":"ok","routineScheduler":"pending"}                   — включён, первого тика ещё не было
# {"status":"ok","routineScheduler":"2026-08-19T07:00:04.113Z"}  — НАЧАЛО последнего тика
```

Норма для включённого фона — время не старше пары минут (тик раз в 60 с), **кроме времени
идущих прогонов**: тик гонит модель синхронно (создатель прогона и есть его раннер), а
наложение тиков пропускается, поэтому во время прогона отметка отстаёт на его длину — до
дедлайна 10 мин плюс один шаг и ретраи, то есть до ~13 мин **на один прогон**. Наступивших
прогонов в одном тике может быть несколько (несколько рутин одного владельца или несколько
владельцев на одно утро; после сна сервера — догон бакетов в окне 6 ч), и тик гонит их
**последовательно**: предел отставания — **N × ~13 мин**, где N — число прогонов, стартовавших
этим тиком. Диагностика: в `Logs` у каждого прогона есть строка
`[routines] прогон <id> рутины <id> (<бакет>): <исход>` — посчитать строки за отстающий
интервал и сверить с отставанием; отставание, не покрытое N × ~13 мин, либо застрявшее
`pending`, либо отстающее на часы время при отсутствии таких строк означает, что таймер не
отрабатывает, — при зелёном `status` и работающем приложении.

**Это отметка таймера, а не отчёт о работе.** Она ставится в момент запуска тика, до его тела,
поэтому упавший тик (нет прав на список владельцев, отказ записи прогона) даёт ровно такое же
свежее время, как успешный. Вторая половина ответа на «фон жив?» — `Logs` сервиса: строки
`[routines] тик планировщика упал`, `[routines] рутина … — сбой тика`,
`[routines] рутины владельца … не прочитаны` означают, что таймер крутится, а работа нет.
Строка `[routines] рутина <id> владельца <owner> поставлена на паузу стоп-краном` — пауза,
поставленная **тиком по графу** (три подметённых провала подряд — крэш-луп процесса), а не
раннером после живого сбоя: у такой рутины в `Logs` нет строк `прогон … : failed` за последние
попытки, и искать причину надо в причине смерти процесса (OOM, SIGKILL), а не в провайдере.

Диагностика по симптому:

| Симптом | Вероятная причина | Действие |
|---|---|---|
| `/health` таймаут ~1 мин, затем 200 | Render уснул (cold start) | норма для free; keep-warm §5 |
| `/health` 200, но операции с данными падают | Supabase на паузе / DSN | §6 (resume) + сверить `DATABASE_URL` |
| 502/503 от Render стабильно | краш процесса / битый деплой | Render `Logs`; роллбэк §1 |
| backup-job красный | нет `ADMIN_DSN` / пауза Supabase | завести секрет §4.1 / resume §6 |
| `/health` 200, но рутины не срабатывают | `routineScheduler: "off"` — переменная не выставлена; сервис спал (нет пингера); реестр без `orbis/routine` (тогда в ответе есть и `aspectDrift`) | §1 чек-лист «Деплой V1» (шаги 3 и 6), пингер §5, `ops.ts check` |
| `routineScheduler` тикает, прогонов нет | тик падает внутри: `42501` (миграция `0013` не накачена) либо отказ валидации при создании прогона | `Logs` → строки `[routines] …`; §1 чек-лист «Деплой V1» (шаги 2–3) |

Логи прод-сервиса — Render UI `Service → Logs` (retention 7 дней на free).

## 8. Перф-чек-лист перед релизом

Разделение труда — решение D21. **Сервер** закрыт автоматикой: `apps/server/src/perf.test.ts`
меряет семь горячих операций на засеянном объёме (2000 сущностей, 1000 транзакций,
12 конвертов) и роняет CI при превышении порога; медианы печатаются строками `perf: …`
в каждом прогоне, в том числе зелёном, — дрейф видно до того, как он пробьёт порог.
**Клиент** автоматикой не закрыт: headless-замер в CI дал бы цифры раннера, а не телефона.
Поэтому четыре числа ниже владелец снимает руками перед выкаткой релиза.

**Коды возврата сьюта снимаются на незанятой машине.** Под нагрузкой (параллельный прогон,
сборка, второй сьют на той же базе) стабильно флачат **четыре** места: `apps/server/src/perf.test.ts`,
`apps/server/src/recurring/post-due.test.ts`, `apps/server/src/routers/agent-run.test.ts` и
перф-гейт web. Все четыре падают **таймаутом**, а не превышением измеренного порога, и все четыре
зелёные при изолированном перепрогоне одного файла (замерено многократно за срез Ш1, 2026-08-21).
Поэтому красный из этих четырёх — повод перепрогнать файл отдельно, а не вывод о регрессии; вывод
о регрессии делается по строкам `perf: …`, которые печатаются и в зелёном прогоне.

Условия замера (иначе числа несравнимы между релизами):

- телефон владельца, обычная мобильная сеть, а не Wi-Fi рядом с роутером;
- сервис **прогрет** — сначала открыть приложение, дождаться отклика, только потом мерить.
  На холодном Render free первый запрос стоит ~1 минуту (§5) и меряет сон, а не приложение;
- боевой аккаунт с накопленными данными, а не свежий: пустой граф всегда быстрый;
- каждое число — медиана 5 повторов, а не один замер.

| Что меряем | Как | Цель | Откуда цель |
|---|---|---|---|
| time-to-log расхода, fast-path | от нажатия «отправить» в чате до появления карточки «⚡ без AI» | < 2 сек | 00-product §8 |
| time-to-log расхода, путь LLM | от отправки формулировки, которую fast-path не берёт, до карточки | < 5 сек | 00-product §8 |
| Первая отрисовка Budget Overview | от тапа по вкладке Budget до появления конвертов с суммами | < 2 сек | фаза A слайса 3, D21 |
| Первая отрисовка Agenda | от тапа по вкладке Agenda до появления дневных секций | < 2 сек | фаза A слайса 3, D21 |

Две нижние цели в §8 не заданы: там из перфа только time-to-log. Числа для экранов введены
