## Открытая граница перехода со старых клиентов

03.11.2026, подготовка Б7: обнаружен критический вопрос совместимости физической очистки с документами прежней сборки, которые ещё не знают протокол поколений. Поэтому по условию владельца результат останется в отдельной ветке без слияния в локальный main. Реализация и локальные проверки продолжаются; выпуск не разрешён. Это не закрытое замечание и не PASS критерия Р5.

Изолированный браузерный прототип на Chrome 156.0.8078.80 и Bun 1.2.7 проверил реальный BFCache (`pageshow.persisted` и события CDP), смену контроллера и отложенную навигацию. Повторный `clients.claim()` того же worker не вытесняет скрытый старый документ. Новый контроллер вытесняет его, но возврат должен получить актуальную оболочку: одной смены контроллера недостаточно против HTTP history cache. Даже с актуальной оболочкой остаётся воспроизведённый обход: начатая ранее навигация не входит в обе переписи `clients.matchAll`, получает старый HTML после очистки и пишет legacy localStorage уже под новым контроллером. Активный старый JavaScript также не заменяется одним claim.

Решение координатора: не принимать ротацию service worker и подтверждения видимых вкладок за универсальную гарантию удаления. Поколения и блокировка писателей обязательны для клиентов Б; неподтверждённая или заблокированная очистка не объявляется успешной. Для перехода с клиентов до протокола нужно отдельно доказать прекращение всех прежних документов и начатых навигаций, например полным перезапуском браузера с актуальной оболочкой. Этот операционный переход ещё должен быть проверен на настоящей предыдущей сборке. До такой проверки выпуск заблокирован. Не меняем разделение ролей: service worker хранит оболочку и код, данные — в своих хранилищах.

Альтернатива — считать смену контроллера достаточной — отвергнута фактическим отрицательным сценарием. Более широкий пересмотр совместимости или происхождения клиентского кода требует отдельного решения, а не скрытой уступки приватности. Цена ошибки — возвращение удалённого локального ввода или auth старым документом; поэтому ограничение сохраняется даже при зелёных модульных тестах новой сборки.

Доказательства: [прототип](evidence/2026-11-03-speed-plan-b/shared-legacy-probe.ts), [итоговый журнал](evidence/2026-11-03-speed-plan-b/shared-legacy-probe.jsonl), [первый прогон со старой HTTP-оболочкой](evidence/2026-11-03-speed-plan-b/shared-legacy-stale-shell.txt). Код 0 итогового прототипа означает, что он подтвердил и положительные сценарии, и ожидаемый контрпример; это не PASS приватности приложения. Личные данные, рабочий профиль Chrome, продуктовый код и БД в прототипе не использовались.

Выборы и их основания:

- RLS строки ленты недостаточно: payload может нести чужой ID через каскад или якорь. Принадлежность доказывается текущим родителем либо последним подходящим событием этой транзакции без преждевременной фильтрации по графу. Неизвестный и чужой родитель обрабатываются одинаково; недоказуемый каскад даёт reset без IDs. Альтернативу с новым полем графа в модели отношений не вводили. Частичный индекс доказательства родителя проверен на 30 тыс. откатываемых строк: generic plan использовал индекс, около 0,034 мс/4 hits; влияние дополнительной записи индекса на целую команду ещё измеряется в Б13.
- Сверка использует один SQL-снимок, полуинтервал `[from, xmin)` и цель `xmax − 1`. Xid на границе API остаётся канонической десятичной строкой. 1001 строка означает reset без разрезания транзакции. Provisional и complete reset имеют разные токены, даже при одинаковом watermark; `max(from,floor)` не применяется. Невидимый floor без читаемого гранта означает 403, отсутствие singleton при читаемом графе — 500, а не выдуманный floor 0 или logout.
- HTTP watermark — минимум чтений конкретной пачки. Клиентский receipt относится к конкретной операции и поколению; отдельный порядок начала нужен для доказательства чтения после ACK. Глобальный «последний заголовок» отвергнут, потому что смешивает конкурентные ответы. Квитанция тела берёт `txId` из фактического UPDATE RETURNING; наличие txId у no-op само по себе не позволяет подавлять событие тела.
- Реальный браузер выявил несовместимые ESM/CJS символы `tracked` при старом Hono-адаптере на Bun 1.2.7. Использован единый публичный ESM `fetchRequestHandler`; обычные batch, body limits, watermark и Server-Timing сохранены. Отдельный fork или обновление библиотек для обхода дефекта не потребовались. EventSource 3.0.7 закреплён напрямую, не обновлён без причины.
- Supabase SDK удалял сессию при временном 429 до обработки ошибки транспортом. Общий адаптер refresh классифицирует временные и неопределённые ответы до побочного эффекта SDK; известные терминальные коды сохраняют прежнюю семантику выхода. Разбор modern/legacy полей следует закреплённому SDK, включая числовой legacy code. Нормальный 401 защищённого API не заменён повтором. Внешний Supabase не проверен: настоящему SDK подавались локальные HTTP-ответы.
- Зависимости наблюдаются в действующих компиляторах и пути материализации, без второй реализации Q-AST в web. Даже фиксированная дата может впервые войти в скользящий горизонт после полуночи; поэтому отсутствие `$today` в SQL не доказывает отсутствие календарной зависимости. `graphEstablished` зависит от фактической оболочки графа; архивная оболочка существует, удалённая — нет. Денежные семейства используют серверный дедлайн владельца.

Решения выше ограничены обратимыми локальными контрактами и интеграцией; пользовательская модель графа и правила Undo не заменялись. Критический вопрос совместимости старых документов выделен отдельно выше. Дополнительные полные прогоны на промежуточном дереве не объявлены зелёными: они были остановлены с сохранением отказов и логов. Синтетический Server-Timing тест дважды дал 429/438 мс при пределе 420 под параллельной нагрузкой; нужен повтор без неё, предел не повышался.

Независимое ревью воспроизвело исторический `America/St_Johns`: 01.11.2009 первая смена даты в 02:30 UTC и возврат в 02:31 UTC пропускаются двоичным поиском. `user.getSettings` использует текущие серверные часы; `queryContext` также берёт текущие часы по умолчанию и допускает внутренний переданный `now`. Затронутый современный рабочий сценарий не установлен. Цена решения — возможный пропуск первой границы при таком искусственно заданном времени; расширение области часов потребует пересмотра helper. Финальное ревью ещё должно подтвердить эту границу либо потребовать исправление. Все современные зоны и произвольный исторический `now` не объявлены проверенными.

## Принятый клиентский runtime Б5

## Принятый код Б7 и модуль хранения ввода

Б7 принят локально коммитом `7e87856dce1021f079ad9996f10b5f6dab12a45f` после полного независимого ревью и трёх адресных волн исправлений. Предшествующий `68aab8d284a7425392973ae4c1cd3e92e6230fa6` содержит только три leaf-файла exact-token input store, необходимые lifecycle. Это приёмка модуля Б12, а не полной интеграции асинхронных черновиков и ритмов сохранения. Все 43 хеша кандидата совпали с точной изолированной сборкой; коммиты сделаны по отдельным спискам 3 и 40 путей без соседней работы.

Lifecycle захватывает ввод перед отзывом текущих писателей, отделяет обратимую подготовку от разрушительной очистки и выдаёт новое поколение после отмены. Старый lease не оживляется. Смена аккаунта, подтверждённый 401, 412, текущий `seeded:true`, выход и общий компьютер используют разные правила сохранения ввода. Поздний password/refresh ответ проверяется до записи сессии и внутри auth lock; авторизация нового владельца не перезаписывается старым ответом.

Выключение общего режима переносит только ввод инициатора. Другая вкладка, даже того же аккаунта, сохраняет собственный вкладочный сеанс и ввод до своего явного переноса. Право удалить источник связывается с generation и живым tabKey, а не только account ID или наблюдением чужого завершения. Автоматический перенос всех соседних вкладок был отвергнут: он менял срок хранения и мог открыть чужую normal-сессию. Пересмотр этой политики потребует явного изменения UX и повторения всей матрицы handoff; исправление локально обратимо.

Несколько аварийных копий одного документа хранятся независимо по writer/slot. При применении recovery исходный exact token становится токеном отправленного текста. Успешный HTTP сам по себе не скрывает единственную копию: marker ставится после строгого durable body commit Б6. Quota, abort, отсутствие durable sink и response-off оставляют источник доступным. Shared input не попадает в response IDB. Это сохраняет прежнюю гарантию до полной миграции Б12; физическая очистка включает payload и markers.

В общем режиме внутренние адреса и состояние истории непрозрачны, а маршруты остаются в памяти; явное копирование канонической ссылки сохранено. При BFCache корень скрыт до сверки текущих auth/device и React layout commit. Совместимость неизвестной сборки доказывает одна ограниченная credential-free tRPC-проба за version gate; обычный proxy 401 не подходит. Положительный результат сохраняется для точного build ID и поколения явного отказа. Новый 412 отзывает proof, отвергнутый ID не делает product/probe HTTP. Устаревшая проба не допускает runtime; явный Retry перечитывает актуальное durable состояние и работает без reload, включая заблокированный IDB delete. События вкладок сами не возобновляют очистку.

Независимое ревью закрыло десять воспроизведённых дефектов: потерю ввода при поздней отмене, поздний вход A поверх B, потерю подписанного ранее ввода B при OFF, приватные URL в Chrome History, взаимное затирание двух редакторов, повторный допуск отвергнутой сборки, потерю ввода соседней вкладки того же аккаунта, ранний recovery marker, повторный сетевой барьер ранее проверенной сборки и бездействующий Retry после stale proof. Последний полный адресный набор — 251/251 плюс typecheck; заключительное узкое ревью — 43/43 по пяти файлам и три native Chrome-сценария. Авторские и независимые native прогоны используют production bundles, временные профили и локальные синтетические серверы. Строгий IDB abort/complete и Web Locks настоящие; quota внедряется исключением Storage API.

## Принятые ритмы и сохранность ввода Б12

Полный Б12 принят локальным коммитом `5adf545a6330328f15fa3cb8798165d02102c0d6` после трёх раундов исправлений. Предыдущий input-store leaf `68aab8d2` остаётся отдельной ранней зависимостью Б7. В итоговый индекс вошли ровно 15 файлов; изменения канонического detail input из уже принятого Б10 сохранены, Б11 и документы исключены. Последний независимый отчёт `b12-rereview-3.md`, SHA-256 `3b9cfc7a0a891e794da83cbff7879ca59a8a5caba39559757baa907dbaafc4fa`, даёт PASS оставшемуся P1 и шестифайловой дельте; пять исходных замечаний и P2 закрыты предыдущими проходами.

Память редактора меняется сразу, checkpoint сохраняется каждые 300 мс набора, отправка — после 1 с паузы и не реже 5 с непрерывного ввода. Одновременно выполняется один запрос; если ответ не пришёл за 30 с, попытка получает состояние неопределённого исхода. `pagehide` сохраняет аварийную копию. Черновик остаётся привязанным к точному writer/token, scope и исходному сроку 30 дней. Получение ACK, надёжная запись ответа и снятие страховки — разные стадии. Вернувшийся к подтверждённому тексту ввод снимает собственные неподтверждённые копии, включая native puts с уже совершённым commit и ещё удержанным callback.

Нативный слот содержит текущий снимок и максимум одного подтверждённого предшественника. Снятие B оставляет страховку A, точное снятие A оставляет B; у них независимые исходные TTL. Один metadata-only токен реально отправленного A допускает поздний первый ACK после checkpoint B. Если собственная запись этой отметки оборвалась, B может перенести доказательство из активного writer внутри своей транзакции, только когда прежнее состояние ещё до A либо содержит точный живой A. Tombstone, более позднее недоказанное состояние, иной scope/generation/basis и истёкший срок не допускают воскрешения. Это ограниченная страховка, без третьей копии текста и общей очереди команд; HTTP не ждёт IDB.

В Web Storage подтверждённый текст хранится отдельно от одного переиспользуемого pending head writer. Атомарная замена и отказ quota сохраняют прежние байты. Старый формат ACK в head заменяется только после сохранения страховки. Точное объединение одинаковых токенов не смешивает разных writers. Shared OFF переносит подтверждённую копию перед pending и сохраняет прежние правила явного согласия вкладки. Этот дополнительный формат входит в обязательное чтение совместимого fallback Б13.

Импорт повторно проверяет scope и точные маркеры между list/put/публикацией и перед досылом. Живой более новый head может скрыть старый неподтверждённый ввод от автодосыла, но не разрешает физически удалить подтверждённую страховку. «Оставить моё» меняет показанный документ только после принятия точного предложения. Flush сверяет состав редакторов и версии после всех ожиданий, включая raw Markdown: правка во время ожидания другого редактора требует нового барьера перед Undo/restore.

Независимый Chrome подтвердил оба окна отмены B — перед его импортом и после реального native commit до callback — с сохранением A. Отрицательные контроли точного снятия до/после B, чужого nonce/basis/generation и истёкшего доказательства не восстановили A и сохранили B. В заново собранном приложении отдельно оборвана только запись input-отметки A, затем реальный редактор записал B до ответа A. Abort строгого response cache, отмена B и перезагрузка с заблокированным GET оставили точный ACK A доступным без автодосыла; последующий успешный strict commit снял именно A без лишних detail/chat reads. Модульные shared handoff/quota проверки дополнены прежними прикладными Б7/Б12, но не заменяют финальную полевую матрицу.

На окончательных байтах автор проверил 20 input-store и 6 hook тестов, TypeScript и Biome. Набор 117/117 относится к отозванному промежуточному снимку; он не выдаётся за полный финальный PASS. Широкий прогон, объединённый бюджет, after-B, физические устройства и внешний Supabase остаются за Б13. Первое совпавшее GET в одном probe сохранило A; подтверждённое снятие доказано через строгий sink мутации. Полезная страховка не удаляется ради уменьшения счётчика. Выпуск и merge в main не выполнялись.

Первое [повторное ревью reset](evidence/2026-11-03-speed-plan-b/b13-reset-rereview-1.md) подтвердило устранение исходных сценариев на отдельном совмещённом архиве: 56/56 web и 8/8 native IndexedDB. Оба были отправлены на исправление; этот промежуточный архив не принимался.

Отдельная граница восстановления унаследована от А: после перезапуска один numeric draft автоматически досылается при равной ревизии, а codec не хранит incarnation сервера или fingerprint основы. Если вкладка никогда не наблюдала откат истории либо все способы сохранить новую метку отказали и перезапуск оставил только старые байты, равенство номера не доказывает общую историю. Живой runtime с наблюдавшимся rewind блокирует такую отправку; hard reload после отказа обоих способов checkpoint не воспроизводился. Исправление не заявляет устранение этой унаследованной неоднозначности.

Последующий [тихий диагностический профиль «Повестки»](evidence/2026-11-03-speed-plan-b/b13-agenda-phase-profile.md) не воспроизвёл большой перерасход: медианы 113,9 мс у исходного кода и 119,0 мс у кандидата, по пять вызовов. Подготовка/deadline отличались на 0,54 мс, материализация на 0,08 мс, выполнение блоков (SQL/savepoints/layout вместе) на 4,45 мс. Сохранены [сырые фазы](evidence/2026-11-03-speed-plan-b/b13-agenda-profile-summary.json) и журналы [исходного](evidence/2026-11-03-speed-plan-b/b13-agenda-profile-before.log) и [текущего](evidence/2026-11-03-speed-plan-b/b13-agenda-profile-candidate.log) кодов. Диагностические timestamps добавлялись только в TEMP, история двух БД различается. Этот PASS не заменяет неизменённые красные запуски и не обосновывает повышение порога: обязательный обычный тихий замер финального SHA ещё впереди.

Общее ревью также [подтвердило отдельный дефект shared-ссылок](evidence/2026-11-03-speed-plan-b/b13-shared-native-link-review.md): средняя кнопка и Cmd-click из текущего поиска открывают анонимный экран входа с ID записи в URL, а UUID остаётся в SQLite History закрытого Chromium.
