## §1. Навигация

Детализация принципов 00-product §6.1.

### §1.1 Карта экранов

Четыре вкладки нижней панели; поверх каждой — собственный стек push-экранов:

```
нижняя панель:   [ Chat ]        [ Browser ]        [ Agenda ]         [ Budget ]
                 [слайс 1]       [слайс 1]          [слайс 2]          [слайс 2]
                    │                 │                  │                  │
корень вкладки:  глобальный       список сущностей    список дней       Overview
                 тред             + сайдбар pinned   (сегодня → +7)    (03-budget.md)
                    │                 │                  │                  │
push-стек         detail            detail             detail             detail
(внутри своей        │                 │                  │                  │
 вкладки):         detail            detail             detail             detail
                     ⋮                 ⋮                  ⋮                  ⋮
```

Экраны слайса 1: **Chat** (глобальный тред + треды сущностей, §2), **Browser-lite** (список, сайдбар pinned, три сидированных smart lists — в слайсе 3 к ним прибавились два горизонта, §3.3, — минимальный detail-экран, §3), настройки (§1.6). **Agenda** (§4) целиком приходит в слайсе 2 — её ценность держится на recurring-инстансах. **Budget** как вкладка (Overview с конвертами, 03-budget.md) — тоже слайс 2, но fast-path-ввод расходов через Chat работает уже в слайсе 1: расходы копятся с первого дня без Budget-view (00-product §2, боль 5 — «данные существуют до views»), Overview покажет накопленную историю, когда появится.

Вертикальные связи под корнем — push-стек **внутри своей вкладки** (общий паттерн: detail-экран сущности пушится поверх, из него можно перейти в следующий detail), а не переходы между вкладками: между колонками стрелок нет, вкладки переключаются нижней панелью (обратный шаг по уже пройденным переключениям делает back — §1.2).

- Detail-экран сущности (§3.5) — единый для всех вкладок: тап по сущности в любом списке (чат-карточка, Browser, Agenda, Budget) пушит его поверх текущего экрана той же вкладки.
- Каждая вкладка хранит **свой** стек: переключение вкладок не сбрасывает стеки — вернувшись на Browser, пользователь видит тот же открытый detail.
- Повторный тап по активной вкладке сворачивает её стек до корня.

### §1.2 Правила back

Навигацию ведёт история браузера (D18): системный жест «назад», кнопка «назад» браузера и кнопка «Назад» в шапке экрана — одно и то же действие.

- Back закрывает верхний push-экран активной вкладки — «назад» всегда возвращает туда, откуда пришёл (00-product §6.1).
- На **корне вкладки** back возвращает на вкладку, с которой на неё переключились: переключение вкладок — такой же шаг пути, как push-экран. Из приложения back уводит только в конце пути, когда возвращаться уже некуда.
- **Отменено решением D18:** прежнее правило «на корне вкладки back НЕ переключает вкладки, жест отдаётся системе». История браузера линейна, и сохранить букву этого правила можно было бы только обратной перемоткой `popstate` — ценой дёргающегося жеста на телефоне (04-decision-log D18).

### §1.3 Deep links

Любую вещь в Orbis можно открыть по ссылке (00-product §6.1). Внешний URL-контракт — стабильные маршруты, пункт «Скопировать ссылку» и открытие извне — сделан в слайсе 3 (незакрытые долги перечислены в конце секции); внутренняя навигация между экранами (карточка → detail-экран, тред → задача) — инфраструктура слайса 1 и работает с первого дня. Канонический формат и фактические маршруты PWA:

| Ссылка | Маршрут PWA | Поведение |
|---|---|---|
| — | `/chat`, `/browser`, `/agenda`, `/budget` | Корень вкладки: вкладка активируется, её стек сворачивается до корня |
| `orbis://entity/<id>` | `/entity/<id>` | Активируется вкладка Browser, поверх корня пушится detail-экран сущности |
| `orbis://thread/<id>` | `/thread/<id>` | `<id>` — это `chat_threads.id` (01-architecture §4.5). Тред сущности → Browser + detail-экран с открытой вкладкой «Тред»; глобальный тред → вкладка Chat |
| `orbis://budget/category/<id>` | `/budget/category/<id>` | Вкладка Budget + экран категории (03-budget.md) |

- Открытие deep link **сбрасывает стек целевой вкладки** и пушит целевой экран поверх её корня — прежний стек этой вкладки не сохраняется; стеки **остальных** вкладок вход по ссылке переживают (§1.4). Корень целевой вкладки остаётся под целевым экраном: первый «назад» у пришедшего по ссылке ведёт на корень, а не из приложения.
- **Перезагрузка страницы входом по ссылке не считается**: адрес экрана бывает и у нашей же открытой вкладки браузера, состояние там восстанавливается по §1.4. Различие — по наличию собственной записи навигации в истории браузера, а не по виду адреса.
- Чужой или неразбираемый путь (включая корень сайта `/`, который маршрутом не считается) не разбирается догадкой: показывается восстановленное состояние (§1.4).
- Источник ссылок — пункт **«Скопировать ссылку»** в меню ⋮ detail-экрана (§3.5); ссылка абсолютная, вида `https://<origin>/entity/<id>`.
- Несуществующий или чужой `id` (запрос вернул «не найдено») → экран **«не найдено»**: заголовок «Не найдено», пояснение «Запись удалена или недоступна», кнопка **«На главную»** сворачивает стек текущей вкладки до корня; рядом — обычная кнопка «Назад» в шапке. Прочие ошибки (сеть, 5xx) этим экраном не подменяются. Частичное открытие невозможно. Схлопывание **восстановленного** стека вокруг недоступной сущности — другое правило, §1.4.
- `orbis://` — каноническая нотация документов; фактический URL-формат PWA — https-маршруты из таблицы, поведение идентично.

**Ещё не реализовано** — три долга фазы B слайса 3; контракт выше в силе, факт пока другой:

- ссылка на **глобальный** тред открывается во вкладке Browser, как тред сущности: различить треды можно только по данным треда, а вход по ссылке этого не делает;
- `/thread/<id>` показывает самостоятельный экран «Тред», а не detail-экран сущности с открытой вкладкой «Тред»;
- экран «не найдено» есть только у сущности: `/budget/category/<id>` на удалённую категорию даёт строку «Не удалось загрузить категорию», `/thread/<id>` — пустой тред без ветки ошибки вовсе.

### §1.4 Восстановление состояния

После перезапуска PWA восстанавливаются **активная вкладка и стеки всех вкладок**. Состояние навигации хранится локально на устройстве и не синхронизируется между устройствами (это не данные графа). Если сущность из сохранённого стека недоступна (запрос сущности вернул «не найдено» — удалена или недоступна), стек схлопывается до ближайшего валидного экрана; архивные сущности открываются нормально (мягкое удаление — 01-architecture §2.1).

### §1.6 Экран настроек

Точка входа — иконка ⚙ в хедере корневого экрана каждой вкладки. Разделы MVP:

| Раздел | Содержимое |
|---|---|
| Общие | `timezone`, `defaultCurrency`, `weekStartDay` (хранение — `user_settings`, 01-architecture §4.4) |
| Память AI | Экран памяти (§2.7) — со слайса 2 |
| Аспекты | Список реестра встроенных и кастомных аспектов (все active в MVP — 01-architecture §3.8) |
| Views | Установленные views (`installedViews` — 01-architecture §4.4) |
| Экспорт данных | JSON-дамп всего графа одной кнопкой (контракт — 01-architecture §9.4) — слайс 1 |
| Агенты | Выданные доступы внешним агентам: подпись клиента, вид доступа (браузерный вход / токен для CI), даты выдачи и последнего вызова, кнопка «Отозвать»; там же — команда подключения (01-architecture §9.3) — слайс 4b |

**Отзыв доступа агента живёт здесь и только здесь** (D34): это единственный интерфейс, которым выданный агенту доступ гасится, — без него он не отзывается ничем, кроме SQL. Строка гранта заводится в момент согласия владельца, **до** того как агент забрал токены, поэтому список различает «согласие дано» и «подключён»: агент, который до обмена не дошёл, не должен выглядеть подключённым. Отозванные строки из списка не исчезают — остаются с датой отзыва. **Выдача** браузерного доступа кнопки не имеет и иметь не будет: её инициирует сам агент, а владелец лишь подтверждает согласие; headless-токен по-прежнему выдаётся из CLI (01-architecture §9.3). **Область доступа выбирается при выдаче** (D37, 01-architecture §4.14): `full` — весь граф владельца, `worker` — фоновый исполнитель (чтения, пять глаголов исполнителя и `thread_post` в свой периметр). Выбор делается на экране согласия (браузерный вход) или флагом CLI (headless-токен); в списке доступов область видна строкой рядом с подписью.

## §2. Chat

### §2.1 Глобальный тред

Главная вкладка Chat — мессенджер-UI: один бесконечный диалог с AI, поле ввода внизу, история — скроллом вверх.

- **История не теряется.** Все сообщения сохраняются полностью и доступны скроллом (append-only хранение — 01-architecture §4.6). Rolling-окно и сжатие старых сообщений в summary касаются только контекста, передаваемого модели (01-architecture §7.1, слой 4; §7.3) — в UI ничего не «схлопывается» и не исчезает.
- Содержимое треда по умолчанию никуда не утекает: знания переносятся в граф только явными действиями — memory-факт, дозапись в body, note-сущность (01-architecture §7.2).
- **Состояние «AI отвечает».** Пока модель формирует ответ, в ленте показывается typing-индикатор; поле ввода остаётся активным. Сообщения, отправленные в это время, встают в очередь за текущим и обрабатываются последовательно, каждое со своим индикатором «обрабатывается» — это лента ожидания ответа модели, не retry-буфер (§2.6): все эти сообщения уже приняты сервером, ждёт своей очереди только ответ. Fast-path-вводы (§2.5) исполняются немедленно даже пока LLM думает. В MVP ответ приходит целиком; стриминг токенов — Future.

```
┌──────────────────────────────────────────┐
│  …история (скролл вверх)…                │
│                                          │
│              обед 340  ◄── пользователь  │
│  ┌────────────────────────────────────┐  │
│  │ ⚡ без AI                          │  │
│  │ 🍔 Обед — 340 ₽ → Еда             │  │
│  │ → Еда · осталось 8 060 ₽          │  │
│  │ не то? → разобрать с AI           │  │
│  └────────────────────────────────────┘  │
│ ┌──────────────────────────────────────┐ │
│ │ ⏳ ждут отправки: 2                  │ │  ← retry-буфер (§2.6)
│ └──────────────────────────────────────┘ │
│  [ поле ввода…                    ➤ ]    │
└──────────────────────────────────────────┘
```

### §2.2 Тред сущности — слайс 1

У любой сущности есть персистентный тред — вкладка «Тред» на её detail-экране (§3.5).

- Заголовок треда = `title` сущности; при переименовании сущности заголовок следует за ней.
- Сущность — **контекст-якорь**: она автоматически входит в рабочий контекст модели (01-architecture §7.1, слой 3; §7.3). «Обсудим детали» в треде сущности «План питания» — про план питания, без уточнений.
- Тулы не скоупятся: из треда сущности доступен весь граф (01-architecture §7.3) — скоупится разговор, не способности.
- Тред создаётся лениво — при первом отправленном сообщении; до этого вкладка показывает пустое состояние с полем ввода. ID детерминирован как `uuidv5(ORBIS_NAMESPACE, "<owner_id>:entity-thread:<entity_id>")`, поэтому открытие сущности с нескольких вкладок или устройств одновременно не порождает два треда — конкурентные попытки создания сходятся к одной и той же строке (01-architecture §4.5, §5.4).

**Тред задачи в агентной петле.** Пересмотрено под агентную петлю (`04-decision-log.md`, D9): для сущностей-задач, которыми занимается внешний агент, тред сущности — рабочее место совместной работы человека и агента. Агент пишет сюда заметки о ходе и результате задачи («поправил индекс, запрос ускорился в 4 раза»); владелец обсуждает постановку и отвечает агенту из этого же треда — в том числе с телефона, не открывая ноут. Сообщения владельца в треде задачи — это и есть инструкции, которые агент находит паттерном **«что нового»** при следующем опросе (01-architecture §9.3, сценарий 9 в §5).

**Архитектурная гарантия.** Чат-компонент — лента + поле ввода + карточки — один и тот же во всей системе: тред сущности на detail-экране **не отдельная реализация**, а тот же компонент, что рендерит глобальный тред (§2.1), с другим `thread_id` и включённым контекст-якорем. Мокап — §3.5.

### §2.3 Типы карточек MVP

Карточки — структурированные блоки в ленте чата; привязаны к сообщениям (хранение — 01-architecture §4.6, формат действий и Undo — §7.8).

| Тип | Когда появляется | Содержимое и действия |
|---|---|---|
| `entity_card` | Сущность создана или обновлена — AI-путём, fast-path или внешним агентом (01-architecture §9.3) | `title` + иконки аспектов + ключевые поля (для financial — сумма и категория, для task — статус и срок). **Inline-правка полей** прямо в карточке; кнопка **Undo**. Тап по заголовку → detail-экран |
| `entity_list` | Ответ на запрос-перечисление («покажи задачи на неделю») | Заголовок + список сущностей в native-рендеринге (§3.6); тап по строке → detail-экран |
| `query_result` | Ответ-агрегация: сумма, остаток, количество | Число + подпись («Еда в июне: 12 430 ₽ из 30 000 ₽»); действие «показать список» разворачивает в `entity_list` |
| `import_review` | CSV-импорт выписки | Содержимое и флоу — 03-budget.md |
| `confirmation_card` | Tool-call получил от политики подтверждений уровень `preview` или `explicit-confirmation` (01-architecture §7.10) | Превью действия (например, diff изменяемых полей). При `explicit-confirmation` действие ещё не исполнено: кнопки **«Подтвердить»** / **«Отменить»** решают его судьбу — до тапа ничего не записано ни в граф, ни в журнал. При `preview` действие уже исполнено (предпросмотр информационный, не блокирующий) — карточка показывает результат постфактум с обычным Undo вместо кнопок подтверждения |
| `error_card` | Действие не удалось | Что не получилось и почему (ошибка валидации, лимит, ошибка парсинга запроса — 01-architecture §6.4, §9.2) + предложение следующего шага |

```
┌────────────────────────────────────┐
│ ⚠ Требует подтверждения             │
│ Архивировать 5 задач с тегом #old   │
│ [ Подтвердить ]   [ Отменить ]      │
└────────────────────────────────────┘
```

Поведение карточек:

- Inline-правка поля в `entity_card` — то же действие, что любая правка: проходит через executor и пишется в журнал (01-architecture §7.8), то есть само подлежит Undo.
- После Undo карточка переходит в состояние «отменено» (визуально погашена, поля заблокированы); повторная отмена недоступна (01-architecture §7.8).
- Действия внешних MCP-агентов отображаются в **глобальном** треде системным сообщением («🤖 агент: закрыл задачу X») с обычной `entity_card` и Undo; записываются они тем же журналом действий (01-architecture §7.8, §9.3), под той же политикой подтверждений (§7.10), что и действия внутреннего AI.
- **Карточка переживает перезагрузку страницы** — она лежит в самом сообщении (01-architecture §4.6), а не в памяти вкладки. Так живут карточки ответа AI и карточка fast-path-записи: её несёт audit-сообщение действия (01-architecture §7.8). Серверная карточка fast-path беднее живой — заголовок, «Отменить» и переход в detail-экран, без пометки «⚡ без AI», ключевых полей и «разобрать с AI» (§2.5). Действия из UI, quick-capture и внешнего агента карточки в ленте не имеют вовсе — только строку о действии (см. долги ниже).

**Ещё не реализовано** — контракт выше в силе, факт пока другой:

- **inline-правки полей в карточке чата нет:** `entity_card` в ленте read-only — заголовок (тап → detail-экран), ключевые поля и «Отменить». Правка полей живёт на карточках аспектов detail-экрана (§3.5 п. 5). Отсюда же: у отменённой карточки блокировать нечего — она гасится целиком, а обещание «те же inline-правка и Undo» в §2.5 тоже пока не выполнено;
- **иконок аспектов на карточке нет** — рисуются заголовок и ключевые поля;
- **`entity_list` отдельным типом не реализован:** ответ-перечисление приходит той же карточкой `query_result` без агрегата, а её строки — заголовки сущностей с переходом в detail-экран, не native-рендеринг (§3.6); **действия «показать список» у агрегата нет вовсе** — единственный производитель агрегатной карточки (`aggregateCard`, `apps/server/src/tools/dispatch.ts`) кладёт `entityIds: []` литералом, то есть разворачивать нечего ни при какой выдаче (**D30**);
- **действие внешнего MCP-агента карточки в ленте не получает:** его audit-сообщение — строка о действии, без `entity_card` и без кнопки «Отменить» (журнал действий и политика подтверждений при этом те же, что у внутреннего AI). Пометку «🤖 агент» при этом несут **оба** признака: и заметка, которую агент написал сам (`author_kind`, §2.2), и его мутация графа — по `actions[0].actor_kind` audit-записи (ADE-срез 1, приёмка 14). Считать один признак вместо другого нельзя: audit-запись пишет сервер от системы, и `author_kind` там не агентский;
- **у `confirmation_card` уровня `preview` кнопки Undo нет** — карточка показывает сводку и diff; отменить действие можно обычным путём отмены (01-architecture §7.8), но своей кнопки у неё пока нет.

### §2.4 Suggestion chips

Под последним ответом ассистента — **2–4 контекстных продолжения**, сгенерированных AI вместе с ответом: после записи расхода — «что по бюджету?», после создания задачи — «поставить срок». Отдельного обращения к модели ради чипов нет — продолжения приезжают тем же ответом. Тап по чипу отправляет его текст как обычное сообщение пользователя в текущий тред — тем же путём, что и поле ввода этого экрана (в глобальном чате это значит и fast-path). Чипы привязаны к последнему ответу: ряд гаснет сразу после тапа, скрыт, пока модель отвечает, и не переживает следующее отправленное сообщение. У fast-path-карточек чипов нет (LLM не вызывался).

**Ряда может не быть и у обычного ответа.** Продолжать разговор нечем — решает сама модель, и тогда чипов нет; пустой ряд не показывается и ничем не подменяется. Это штатное поведение, а не сбой.

### §2.5 Fast-path UX

Механика парсера — 01-architecture §7.5; здесь — наблюдаемое поведение.

- Уверенный паттерн («обед 340») → `entity_card` появляется **мгновенно**, с пометкой **«⚡ без AI»**. Карточка того же типа, что AI-карточка (§2.3): заголовок с переходом в detail-экран и ключевые поля записи — сумма, категория и остаток конверта после неё (03-budget §4, сценарий 1).
- Рядом с карточкой — действие **«не то? → разобрать с AI»**: тап архивирует записанную fast-path сущность (мягкое удаление — 01-architecture §2.1) и отправляет исходную строку LLM-путём. Одна строка не порождает две сущности.
- **Кнопки «Отменить» у живой fast-path-карточки нет** — её роль играет «разобрать с AI». Обычное Undo появляется у серверной карточки, которая встаёт на место живой после перезагрузки страницы (§2.3).
- Если парсер не уверен — строка молча уходит LLM-путём; пользователь не выбирает режим (00-product §5).
- **Без сети** create-действие fast-path не пропадает: карточка появляется сразу же, но с пометкой **«⏳ ждёт отправки»** вместо «⚡ без AI» — попало в retry-буфер (§2.6, 01-architecture §5.3). Inline-правка и «не то? → разобрать с AI» недоступны до ответа сервера — отменить запись до отправки можно только из списка буфера (§2.6). Когда сервер подтвердил create, пометка сменяется на «⚡ без AI», карточка становится обычной.

```
┌────────────────────────────────────┐
│ ⏳ ждёт отправки                    │
│ 🍔 Обед — 340 ₽ → Еда             │
└────────────────────────────────────┘
```

**Ещё не реализовано** — контракт выше в силе, факт пока другой: подтверждение сервера ленту не переписывает, поэтому пометка «⏳ ждёт отправки» сама на «⚡ без AI» не сменяется. Запись при этом отправлена и учтена, но карточка так и висит с «⏳» до тех пор, пока лента не будет перечитана с сервера целиком — то есть до перезагрузки страницы или до возврата на экран чата с протухшими данными ленты. **Следующий ответ модели ленту не перечитывает** — он дописывается в уже загруженную и висящей карточки не касается. Перечитанная лента отдаёт карточку в серверной форме из §2.3. Про недоступную до ответа сервера inline-правку — см. долг §2.3: её нет и у подтверждённой карточки. Отмена «из списка буфера», на которую ссылается тот же пункт, тоже недоступна: списка нет — долг §2.6.

### §2.6 Retry-буфер

Поведенческий контракт буфера — 01-architecture §5.3; деградация продукта при потере сети целиком — §7.9. Здесь — то, что видно в UI.

- Над полем ввода — видимый индикатор **«ждут отправки: N»** (N = число create-операций fast-path в буфере, §2.5). Индикатор появляется при первой записи в буфере и исчезает, когда он пуст.
- Тап по индикатору → список ожидающих записей (распознанная сущность + время постановки); каждую можно **отменить до отправки** — запись удаляется из буфера и на сервер не уходит.
- **Удаление из буфера — только после подтверждения сервера.** Пока не пришёл ответ (успех или окончательный business-отказ), запись остаётся в буфере даже при видимом восстановлении сети — потеря сетевого пакета в процессе не повод считать её отправленной (01-architecture §5.3).
- **Business rejection.** Если сервер отклонил запись по бизнес-правилу (не транспортная ошибка), она покидает буфер с явной ошибкой на карточке — что не получилось и почему, тем же `error_card` (§2.3); повторной автоматической отправки нет, только «не то? → разобрать с AI» (если применимо) или ручной повтор.
- **LLM-запросы в буфер не встают.** Упрощение относительно PRD v3: без сети LLM-путь **честно недоступен**, а не копится в очереди-ленте — поле ввода показывает явное объяснение («нет сети — доступен только быстрый ввод»). Fast-path работает без сети как обычно (01-architecture §7.5) — он единственный, кто пишет в буфер.
- Если сеть есть, но AI недоступен (сбой провайдера, исчерпан лимит) — буфер тут ни при чём: явное сообщение о причине прямо в чате, без очереди (01-architecture §7.9).

**Ещё не реализовано** — контракт выше в силе, факт пока другой: **списка ожидающих записей нет, и отменить запись до отправки нельзя**. Отмена в буфере есть кодом (`cancel()` в `apps/web/src/state/retry.ts`), но ни одно место UI к ней не привязано — долг тянется с приёмки слайса 1 (`docs/superpowers/plans/2026-07-05-slice1c2-prod-acceptance.md`, `docs/superpowers/reviews/2026-07-09-review-backlog.md`). **Жест тапа при этом занят другим действием:** индикатор сегодня — кнопка «Ждут отправки: N. Отправить сейчас», и тап **досылает буфер вручную**; это средство от вернувшейся сети, о которой браузер не сообщил событием `online` (спящий Wi-Fi, прокси, ожившее API при живом линке), а о неудаче досыла говорит строка под индикатором — но только когда не прошло **ничего**: частично удачный слив (одна запись ушла, другая упала) не даёт ни строки, ни подтверждения, счётчик просто уменьшается. Поэтому список с отменой — не просто «ещё не сделано»: жест под него занят, и вернуть обещание придётся другим аффордансом (**D32**).

### §2.7 UI памяти — слайс 2

Экран «Память AI» в настройках — это **Browser, отфильтрованный по аспекту `orbis/memory`** (§3.8), с кратким поясняющим текстом сверху: что AI помнит, как факты и правила влияют на ответы и как их редактировать. Отдельного хранилища и отдельного редактора нет:

- правка памяти = правка обычной сущности (title, поля аспекта, body);
- архивация memory-сущности исключает её из инжекции в контекст (01-architecture §7.4);
- сюда же попадают правила, рождённые из повторных исправлений (01-architecture §7.8).

## §3. Entity Browser

Слайс 1 доставляет **Browser-lite**: список сущностей, сайдбар pinned с тремя сидированными smart lists (§3.3, §7.2; в слайсе 3 к ним закрепился горизонт «Год» — у нового аккаунта четвёртым, у существующего последней строкой: бэкфилл дописывает закрепление в конец, `order = max(order)+1`, и пользовательские закрепления не двигает), quick-capture бар (§3.7) и минимальный detail-экран — title, теги, body, аспекты, подзадачи и тред сущности (§3.5). Полный detail-экран — блокировки и backlinks — слайс 2 (§3.5); визуальная форма query-builder поверх грамматики достроена в слайсе 3 (§3.4).

### §3.1 Структура экрана

```
┌─────────────┬────────────────────────────────────┐
│ САЙДБАР     │  [ поиск… ]  [ фильтры ▾ ]         │
│             │                                    │
│ 📌 Pinned   │  ◉ Закончить API   ‹high› 13.06   │
│ ☀️ Daily…(4)│  ◯ Купить кроссовки 👟  сб        │
│ 🗓 Upcoming…│  🔒 Задеплоить       ‹ждёт API›    │
│ 📋 All Tasks│  📄 Идея про отпуск               │
│ 🎯 Год  (3) │  …                                 │
│ (drag ⇅)    ├────────────────────────────────────┤
│             │  [ + быстрая запись…           ➤ ] │  ← quick-capture (§3.7)
└─────────────┴────────────────────────────────────┘
```

На узких экранах сайдбар — выдвижная панель. Корень вкладки — список всех сущностей (по умолчанию неархивные, без служебных — §3.9) с поиском и фильтрами; тап по строке пушит detail-экран (§3.5). Сортировка по умолчанию — `updated_at:desc`; список подгружается порциями по 50 по мере скролла (infinite scroll); фильтры §3.8 применяются поверх.

### §3.2 Сайдбар: pinned-сущности

- Сайдбар показывает закреплённые сущности в пользовательском порядке (хранение порядка — `pinnedEntities`, 01-architecture §4.4).
- **Бейдж** у каждой pinned-сущности — число результатов **первого** query-блока её body: у Daily Planning это размер Inbox, у Upcoming — «Ближайшие 7 дней», у All Tasks — все незакрытые, у «Года» — число целей, у «Рутин» — число прогонов, ждущих ответа владельца (§3.3: первым блоком там стоит «Ждут ответа» именно ради этого — бейдж обязан убывать от того, что человек ответил, — и убывает от любого ответа: и на вопрос рутинного прогона, и на чекпойнт тикета — оба переводят исход в `answered`, 01-architecture §3.15). Считается count-запросом **без учёта `limit`** (`limit` — параметр отображения, не подсчёта); при значении больше 99 отображается «99+», при нуле — **«0»**, а не пустое место (пустой результат — такой же ответ, как любой другой, и «бейджа нет» означало бы «блока нет»). Бейдж пересчитывается count-запросом через tRPC при инвалидации server-state-кэша (01-architecture §6.3, §5.1); если первого query-блока нет или он невалиден — бейдж не показывается.
- **Drag-перестановка** строк сайдбара меняет порядок.
- Действие **«закрепить»** — в меню detail-экрана любой сущности (§3.5); обратное действие «открепить» там ещё не реализовано (§3.5). Закрепить можно любую сущность, не только smart lists.

### §3.3 Преднастроенные сущности

Шесть преднастроенных сущностей создаются при онбординге (§7): три исходных списка (Daily Planning, Upcoming, All Tasks), два верхних горизонта планирования («Год» и «Жизнь») и «Рутины». В сайдбаре закрепляются пять из них; не закрепляется одна «Жизнь» — её открывают раз в год, и она живёт в Browser по тегу `smart-list` (§7.2). Это обычные сущности с query-блоками в body — пользователь может править их и удалять; система их не «защищает» (открепление — §3.2, в UI ещё не реализовано). Все query-блоки — строго по грамматике 01-architecture §6.1.

**Daily Planning** — title `Daily Planning`, emoji `☀️`, tags `["smart-list"]`. Body:

```markdown
Утренний обзор: разобрать Inbox, пройтись по списку «Сегодня».

{{query: aspect=orbis/task, status=inbox,
         sortBy=created_at:desc, display=list, title=Inbox}}

{{query: aspect=orbis/task, due_date=today|overdue, status=!done&!cancelled&!waiting,
         excludeBlocked=true, sortBy=priority:desc|due_date:asc,
         display=list, title=Сегодня}}

{{query: aspect=orbis/task, status=waiting,
         sortBy=updated_at:asc, display=compact, title=Ожидание}}
```

Семантика секций: Inbox — неразобранное, свежее сверху; «Сегодня» — фокус-список: срок сегодня или просрочен, незакрытые и не ожидающие, **заблокированные исключены** (`excludeBlocked=true`); «Ожидание» — делегированное и ждущее, давно ждущие сверху. Пересечение секций намеренно: inbox-задача со сроком сегодня видна и в Inbox, и в «Сегодня» — это две линзы на одну сущность, а не дубль.

**Upcoming** — title `Upcoming`, emoji `🗓️`, tags `["smart-list"]`. Body:

```markdown
Горизонт планирования: неделя и дальше.

{{query: aspect=orbis/task, due_date=next_7d, status=!done&!cancelled,
         sortBy=due_date:asc|priority:desc, display=list, title=Ближайшие 7 дней}}

{{query: aspect=orbis/task, due_date=after_7d, status=!done&!cancelled,
         sortBy=due_date:asc, limit=30, display=compact, title=Позже}}
```

В обоих блоках **намеренно нет** `excludeBlocked=true`: Upcoming — горизонт планирования, заблокированные задачи здесь остаются видимыми с lock-иконкой (§3.6), чтобы не выпасть из поля зрения. Фокус-фильтрация — задача списка «Сегодня», а не горизонта (см. §6, случай 3).

**All Tasks** — title `All Tasks`, emoji `📋`, tags `["smart-list"]`. Body:

```markdown
{{query: aspect=orbis/task, status=!done&!cancelled,
         sortBy=updated_at:desc, display=list, title=Все незакрытые задачи}}
```

Страховочный список: всё незакрытое, недавно тронутое сверху. Задача, не попавшая ни в один smart list, всегда находится здесь.

**Горизонты планирования** (слайс 3, решение **D24**). Лестница «день → неделя → месяц → год → жизнь» доставляется тем, чего в ней **не хватает**, а не новыми списками рядом с существующими:

| Горизонт | Чем доставлен |
|---|---|
| День | **Daily Planning** — «Сегодня» плюс Inbox и «Ожидание» (выше в этой секции) |
| Неделя | **Upcoming**, блок «Ближайшие 7 дней» |
| Месяц | **Upcoming**, блок «Позже» (`after_7d` — «дальше недели»; календарной границы месяца грамматика не знает) |
| Год | **«Год»** — цели (ниже) |
| Жизнь | **«Жизнь»** — вопросы ревизии (ниже) |

Отдельные сущности «День», «Неделя», «Месяц» **не сидируются**: их запросы отличались бы от блоков Daily Planning и Upcoming одним лишь параметром `title=` (`display=` виджет не читает — §3.4), то есть добавляли бы в сайдбар пункты с нулевой информационной дельтой. Сидируются два недостающих верхних горизонта. Относительных date-токенов в грамматике ровно четыре (`today`, `overdue`, `next_7d`, `after_7d` — 01-architecture §6.1); годового и «жизненного» масштаба она не выражает, а абсолютные даты в сиде протухли бы через неделю после деплоя — поэтому оба горизонта держатся не датами, и их тела говорят об этом прямо. В сайдбар из двух попадает только «Год» (§7.2).

**Год** — title `Год`, emoji `🎯`, tags `["smart-list"]`. Body:

```markdown
Горизонт «год»: цели. Годовой срок задачи грамматика не выражает, поэтому длинный горизонт держится целями — сущностями с аспектом orbis/goal, прогресс которых считает сервер. Недавно тронутые сверху.

Лестница горизонтов целиком: день — список «Daily Planning», неделя и месяц — список «Upcoming», год — этот список, жизнь — список «Жизнь». «Жизнь» не закреплена в сайдбаре: её находит Browser по тегу smart-list.

{{query: aspect=orbis/goal, sortBy=updated_at:desc, display=list, title=Цели}}
```

Единственный горизонт не про задачи: `due_date` годового масштаба грамматика не выражает, и год держится целями — сущностями с аспектом `orbis/goal` (01-architecture §11.3), чей прогресс считает сервер и рисует полосой detail-экран (§3.5). Заголовок «Год» называет горизонт, а не фильтр по дате: что именно показано, сказано первой строкой тела. Вторая строка тела — само отображение лестницы на списки: без него «где у меня неделя» пришлось бы угадывать.

**Жизнь** — title `Жизнь`, emoji `🧭`, tags `["smart-list"]`. Body:

```markdown
Горизонт «жизнь»: не список задач, а вопросы ревизии. Перечитывать раз в год.

- **Ценности** — что должно остаться правдой про меня через десять лет?
- **Зоны ответственности** — что я обязан держать в порядке: здоровье, семья, деньги, работа, дом?
- **Отказы** — от чего отказываюсь в этом году, чтобы освободить место остальному?

Ответы держите отдельными сущностями и вешайте на них тег life — блок ниже соберёт их. Пока такого тега нет ни на одной сущности, блок честно покажет «ничего не найдено».

{{query: tags=life, sortBy=updated_at:desc, display=list, title=Ценности и зоны ответственности}}
```

Единственный список, который в основном текст: «жизнь» — вопросы ревизии, а не выборка, и запросом такой горизонт не выражается вовсе. Блок по тегу `life` собирает ответы, когда пользователь их заведёт; до этого он показывает «ничего не найдено» (01-architecture §6.4) — это ожидаемое состояние списка, а не поломка. В сайдбаре «Жизнь» не закрепляется: её открывают раз в год, а каждая pinned-сущность стоит count-запроса на каждой инвалидации кэша (§3.2).

**Рутины** (V1 «Рутины и внутренний исполнитель») — title `Рутины`, emoji `⏰`, tags `["smart-list"]`. Body:

```markdown
Рутины — то, что Orbis делает сам по расписанию, и то, что ждёт вашего ответа.

{{query: aspect=orbis/agent-run, outcome=checkpoint, sortBy=started_at:asc, display=list, title=Ждут ответа}}

{{query: aspect=orbis/routine, stage=active, sortBy=updated_at:desc, display=list, title=Активные рутины}}
```

Вся навигация к рутинам — этот список: отдельного экрана «Рутины» в продукте нет, а «то, что ждёт моего ответа» не заведено сущностью — это выборка прогонов по исходу (`orbis/agent-run.outcome = checkpoint`, 01-architecture §3.15). Отсюда два блока в одном теле, и **порядок между ними нормативен**: бейдж закреплённой сущности считает **первый** query-блок (§3.2), поэтому первым стоит «Ждут ответа» — единственное, что требует действия владельца. Числом активных рутин бейдж быть не может: оно не убывает от того, что человек что-то сделал, и постоянная ненулевая цифра в сайдбаре перестала бы читаться вовсе.

Оба блока называют аспект **явно**, и в каждом случае по своей причине. `orbis/agent-run` — служебный аспект (§3.9): пока запрос его не назвал, компилятор вычитает такие сущности из выдачи. Строго говоря, назвать его умеет и само поле фильтра — `outcome=checkpoint` разрешается в служебный аспект и снимает исключение (§3.9), — но явный `aspect=` в сидируемом теле обязателен как норма читаемости: владелец, открывший блок «Настроить», должен видеть, ПО ЧЕМУ идёт выборка, а не выводить это из имени поля. `stage=` — поле сразу двух аспектов, `orbis/project` и `orbis/routine` (01-architecture §6.1): без `aspect=` имя неоднозначно и запрос не компилируется. Сортировки тоже разные по смыслу: ожидающие идут по времени старта **по возрастанию** — дольше всех висящий вопрос сверху, как в секции «Ожидание» Daily Planning, — а рутины по недавней правке.

Первый блок ловит **все** прогоны с исходом `checkpoint`, а не только рутинные, — и это норма, а не граница: вопрос внешнего исполнителя по тикету ждёт того же владельца, и в блоке ему место наравне с вопросом рутины. Ответ на любой из них переводит исход в `answered` (01-architecture §3.15; для тикетного чекпойнта — начиная с V1) и убирает прогон из блока и из бейджа. Разделить блок по субъекту грамматика **не позволяет**: предиката «поле присутствует» у неё нет, а `routine_id` фильтруется только по конкретному значению (01-architecture §6.1) — так что «только рутинные» потребовало бы новой формы запроса; за ненадобностью её нет.

### §3.4 Query-builder

Принцип «визуальный builder в обе стороны»: query-блок ↔ форма, без второго хранилища — строка блока в body и есть состояние. Рендеринг query-блоков (первый пункт ниже) работает с первого дня слайса 1 — на нём стоят сидированные smart lists (§3.3, §7.2); визуальный редактор-форма, сериализация и режим «редактировать как текст» из формы достроены в слайсе 3.

Правка блока формой живёт прямо в теле: режимов «просмотр» и «правка» у body больше нет (§3.5 п. 4), виджет остаётся виджетом и во время набора, и кнопка «настроить» на нём — там же. Кнопки нет ровно в двух состояниях, и оба временны либо явны: в первом кадре записи, пока редактор ещё не смонтирован, и в режиме «править как markdown» (пункт меню ⋮), где то же тело правится текстом. Одновременно эти два пути к блоку не открыты — второй путь записи на том же экране дал бы две мутации подряд.

- **Рендеринг** (слайс 1). Каждый `{{query:...}}`-блок в body рендерится виджетом: заголовок (из `title=`; нет параметра — без заголовка), список результатов в native-рендеринге (§3.6), счётчик, кнопка «настроить». Пустой результат валидного запроса — «ничего не найдено» (01-architecture §6.4). **Режим отображения виджет не различает:** `display=compact|list|table` сохраняется в блоке как подсказка рендереру (01-architecture §6.1), но на вид выдачи сегодня не влияет — все три режима рисуются одинаково.
- **Редактор-форма.** «Настроить» парсит строку и открывает форму по полям грамматики (01-architecture §6.1): теги (включение/исключение), аспекты, поля выбранных аспектов (значения, отрицания, сравнения, диапазоны), даты (относительные токены и конкретные значения), relation-фильтры (`children_of`/`parents_of`), `excludeBlocked`, `archived`, сортировка (упорядоченный список «поле + направление»), полнотекстовый поиск, лимит, режим отображения, заголовок. **Пикера сущности у relation-фильтров нет:** выбирается `this` либо вводится id руками; про `this` форма поясняет, что это запись, **в теле которой лежит блок** — там он и разрешается, а вынесенный из тела (Browser, бейдж закреплённого списка) ответит ошибкой «this вне контекста сущности», которой на экране не видно (долг в конце секции). Контекст туда не передаётся **намеренно** — не потому, что его негде взять: `this` в переехавшем блоке означал бы «запись, из чьего тела его скопировали», а не «текущий экран» (01-architecture §6.1).
- **Что форма не создаёт, то она не теряет.** Состояние формы — сам разобранный AST, узлы правятся на месте, порядок конструкций сохраняется. Поэтому конструкции, которых её контролы не заводят, — вторая AND-группа тегов (`tags=a, tags=b`) и несколько узлов по одному полю (`amount>100, amount<500`) — видны в форме отдельными строками и доезжают до сохранения нетронутыми.
- **Сериализация.** Сохранение формы сериализует её обратно в строку блока (включая правила кавычек и экранирования грамматики — 01-architecture §6.1) и кладёт её в **атрибут той самой ноды** документа; остальной текст тела не пересобирается вовсе. Дальше это обычное автосохранение тела со всеми обычными следствиями (optimistic-check при конкурентной правке — 01-architecture §5.2). Отдельной сверки блока больше нет и не нужно: адрес правки — сама нода, а не её порядковый номер в тексте, поэтому приехавшая под открытой модалкой чужая версия документа не может подставить под правку соседний блок.
- **Сохранение без изменений ничего не переписывает.** Открыл форму, ничего не тронул, сохранил — строка блока остаётся **байт-в-байт** прежней: форма сравнивает печать текущего AST с печатью исходного и при равенстве отдаёт исходную строку дословно, а экран не шлёт мутацию вовсе, если текст блока не изменился. Поэтому многострочные блоки сидированных smart lists (§3.3, §7.2) переживают открытие и сохранение без переформатирования.
- **Что нельзя честно записать — не записывается.** Правка формы, которую сериализатор напечатать не может или чей результат не разбирается обратно (пустой список значений, `limit` не целым числом больше нуля, неоднозначное имя поля без `aspect=`, пустая граница сравнения), гасит кнопку «Сохранить» и объясняется сообщением под формой; неразбираемая строка в body не попадает.
- **Ошибки парсинга** (слайс 1). Невалидный блок рендерится **красной плашкой с текстом ошибки и указанием места** — никогда не пустым списком (различие нормативно — 01-architecture §6.4). Кнопка «настроить» есть и на плашке — она открывает строковый редактор (форма требует валидного парса): чинить битый блок правкой всего body руками не нужно.
- **Ручное редактирование.** Режим «редактировать как текст» доступен из формы — для продвинутых, опционален; знание синтаксиса не требуется для базовых сценариев (сидированные smart lists уже содержат готовые рабочие блоки, §3.3, §7.2). Переход **односторонний**: в текст уезжает текущая сериализация формы, обратно из текста в форму хода нет — правка руками выражает и то, чего форма не показывает, и возврат выбрасывал бы это молча. В строковом редакторе «Сохранить» доступно всегда, в том числе у невалидной строки: 01-architecture §6.4 нормирует битый блок как состояние продукта, а не как запрет на запись — иначе из блока, который правится в несколько приёмов, нельзя было бы выйти.

**Ещё не реализовано** — четыре долга слайса 1 в рендеринге виджета; контракт выше в силе, факт пока другой:

- **native-рендеринг §3.6 к виджету не применён:** строка результата — только заголовок сущности, без глифа задачи, отметки приоритета, суммы и срока, которые в списке Browser рисует общая «живая строка», и без перехода в detail-экран по тапу — строки виджета не кликабельны;
- **подписи «ничего не найдено» нет:** пустой результат валидного запроса рисуется пустым списком со счётчиком «0»;
- **отказ исполнения виджет не показывает:** упавший запрос рисуется тем же пустым списком со счётчиком «0», что и пустой результат, — отличить их на экране нечем. Так выглядит и блок с `this`, вынесенный из тела записи (скопированный в закреплённый список, открытый из Browser): он валиден, разбор проходит, контекст записи туда не передаётся намеренно (01-architecture §6.1), сервер отвечает ошибкой «this вне контекста сущности», а на экране — пустота. В самом теле записи `this` разрешается: detail-экран передаёт контекст сущности (01-architecture §6.1), а заготовка проекта подставляет uuid и вовсе (01-architecture §3.12). Нормативное «пустота ≠ ошибка» (01-architecture §6.4) держится сегодня только в одну сторону: пустоту за ошибку не выдают, ошибку за пустоту — да. Ошибки парсинга это не касается: битый блок красную плашку получает всегда (буллет выше);
- **отказ реестра аспектов выглядит как загрузка:** пока реестр полей едет, виджет показывает «Загрузка…» — и он же остаётся на экране, если запрос реестра упал: состояния ошибки у этого пути нет.

### §3.5 Detail-экран

Минимальный detail-экран (вкладки «Сущность» и «Детали» без пунктов 7–8 ниже) — слайс 1, самодостаточен: title, теги, body, аспекты, подзадачи, quick-capture и тред. Блокировки и backlinks достраивают его до полного detail-экрана в слайсе 2.

```
┌────────────────────────────────────────────┐
│ ←   👟 Купить кроссовки               ⋮    │  ⋮ = меню действий (ниже)
│ [ Сущность ]◄ [ Детали ]  [ Тред ]         │  ← три вкладки (мокапы — ниже)
│ ────────────────────────────────────────── │
│  👟                                        │  ← emoji страницы
│  Купить кроссовки                          │  ← title, правится на месте
│  #task  #expense  #running                 │
│  ▓▓▓▓▓▓▓░░░  67% · 8 из 12 кг              │  ← полоса прогресса, только у целей
│ ────────────────────────────────────────── │
│  body: единый редактор — [[entity:…]]      │
│  чипами, {{query:…}} живыми виджетами,     │
│  вставка по «/» и «@»                      │
├────────────────────────────────────────────┤
│  [ + быстрая запись…                  ➤ ]  │  ← quick-capture (§3.7)
└────────────────────────────────────────────┘
```

Вкладка «Детали» — всё остальное, что известно о записи:

```
┌────────────────────────────────────────────┐
│ ←   👟 Купить кроссовки               ⋮    │
│ [ Сущность ]  [ Детали ]◄ [ Тред ]         │
│ ────────────────────────────────────────── │
│  Аспекты:  [Task ▾] [Financial ▾]  [+аспект]│
│  Подзадачи (2/5):  ◉ … ◯ … [+ подзадача]  │
│  Блокировки:  блокирует · заблокирована    │  [слайс 2]
│  Связанное (backlinks):  …                 │  [слайс 2]
└────────────────────────────────────────────┘
```

Тред сущности — тот же чат-компонент, что и глобальный тред (§2.1: лента + поле ввода + карточки), с другим `thread_id` и включённым контекст-якорем (§2.2):

```
┌────────────────────────────────────────────┐
│ ←   👟 Купить кроссовки               ⋮    │
│ [ Сущность ]  [ Детали ]  [ Тред ]◄        │  ← вкладка «Тред» активна
│ ────────────────────────────────────────── │
│  …история треда (скролл вверх)…            │
│                                            │
│         не забудь примерочный размер ◄──── │  владелец, с телефона
│                                            │
│  🤖 агент: добавил задачу «выбрать размер» │
│  ┌────────────────────────────────────┐   │
│  │ ◯ Выбрать размер — inbox           │   │
│  │ [статус ▾] [срок] [Undo]           │   │
│  └────────────────────────────────────┘   │
├────────────────────────────────────────────┤
│  [ поле ввода…                     ➤ ]     │
└────────────────────────────────────────────┘
```

Меню ⋮ — три пункта: **«Закрепить»** (§3.2); **«Архивировать»** — у архивной сущности вместо него **«Разархивировать»**; **«Скопировать ссылку»** — в буфер обмена кладётся абсолютный адрес `https://<origin>/entity/<id>` (каноническая нотация того же — `orbis://entity/<id>`, §1.3), с тостом «Ссылка скопирована»; если буфер недоступен или отказал, ссылка показывается прямо на экране для копирования руками. **Открепление из этого меню ещё не реализовано:** пункт всегда зовётся «Закрепить» и всегда добавляет сущность в pinned (повторное нажатие кладёт дубль) — долг, зафиксированный в бэклоге фазы B слайса 3.

Порядок вкладок и секций внутри них (пустой список секция не показывает; но у «Подзадач» заголовок со счётчиком и строка создания, а у «Блокировок» — заголовок и кнопка «+», остаются и на пустоте: иначе связь неоткуда завести). Вкладки живут ОДНОВРЕМЕННО: уход с «Сущности» и обратно не роняет ни несохранённый текст тела, ни историю отмены.

**Вкладка «Сущность»** — чистая страница записи и ничего сверх неё:

1. **Title + emoji** — редактируются на месте.
2. **Теги** — добавление/снятие чипами.
3. **Полоса прогресса цели** [слайс 3] — над телом, у сущностей с аспектом `orbis/goal` и только у них: процент, «достигнуто / цель» с единицей и отметка «цель достигнута» при перевыполнении; число считает сервер на каждом чтении (01-architecture §11.3), клиент его не пересчитывает. Посчитать не вышло — вместо полосы стоит фраза о причине, разная для четырёх причин: нулевая полоса читалась бы как «пока ничего не накоплено» — утверждение о данных, которого никто не проверял. Стоит она здесь, а не среди карточек аспектов на «Деталях», осознанно: у цели прогресс — то, ради чего её открывают, и второй вкладкой он ухудшил бы главный экран целей ради чистоты раскладки.
4. **Body** — единый WYSIWYG-редактор, режима «просмотр» и «правка» больше нет: `[[entity:…]]`
   рисуются чипами с актуальным заголовком и статусом, `{{query:…}}` — живыми виджетами (§3.4),
   и они остаются собой во время набора. Вставка блоков, ссылок и новых сущностей — через `/`
   (упоминание — ещё и через `@`). Форматирование выделения — всплывающей панелью, порядок
   блоков — `Alt+↑/↓`. Сохранение автоматическое: по паузе в наборе и на уходе фокуса; экран
   молчит, пока всё хорошо, и говорит «Не сохранено», когда нет. Правка, набранная без сети,
   переживает закрытие вкладки и досылается при возврате. Пункт меню ⋮ **«Править как
   markdown»** показывает то, что лежит в `body`, и принимает правку текстом.

   **Правда тела — структура.** `entities.body_doc` хранит документ (`{v, doc}`), `body`
   остаётся markdown-проекцией: её читают FTS, промпт, MCP и бейджи pinned-сущностей. Проекция
   же служит аварийным дублем — документ с незнакомой версией схемы пересобирается из неё, так
   что худший исход отката релиза — потеря оформления, но не текста. Текст, который схема не
   может разобрать без потерь (например, сноски GFM), сохраняется одним неразобранным блоком
   дословно и правится через markdown. Модель и MCP по-прежнему пишут строковый `body`;
   документ из него собирает сервер.

**Тикет остановился и ждёт человека** [ADE-срез 1] — блок над телом, у задач с назначением (`orbis/assignment`, 01-architecture §3.14): вопрос чекпойнта, итог работы «готово, проверь» или разбор оборванного прогона — с полем ответа прямо здесь. Ответ и возврат тикета в очередь — **одним действием**: тикет уходит в `planned` (за работу берётся следующий захват исполнителя, а не сервер), ответ ложится на прогон, и обе половины пишутся одной записью журнала. Одним, а не двумя, потому что иначе неясно, был ли комментарий в треде ответом на вопрос. Кнопка «Закрыть тикет» — там же. Место на «Сущности», а не в «Деталях», по тому же прецеденту, что и полоса прогресса цели (п. 3): тикет в `waiting` открывают ради ответа, это не свойство записи.

**Лента прогона** [ADE-срез 1] — у сущностей с аспектом `orbis/agent-run` (01-architecture §3.15): шаги по порядку с пометкой «внешнее», вопрос и ответ, отчёт, заметка о подметании, расход, ссылка на сессию — и кнопка отката прогона с подтверждением (недоступна, пока прогон идёт). Место — то же и по той же причине: у прогона нет «свойств», ради которых его открывают, есть работа, которую он проделал. Пока прогон идёт, экран перечитывает его сам раз в несколько секунд (V1: «Прогнать сейчас» приводит владельца на прогон, созданный до первого шага модели); откаченный рутинный прогон показывается «в архиве» — след отката, инвертирующего только работу прогона (01-architecture §9.3), — а карточка его принятого предложения говорит «Принято, затем откачено».

**Состояние рутины** [V1] — блок над телом, у сущностей с аспектом `orbis/routine` (01-architecture §3.16). Показывает четыре вещи: работает рутина или на паузе; когда сработает в следующий раз (у рутины на паузе — прочерк, а не выдуманная дата: планировщик её не берёт); во сколько и по каким дням; в каком режиме и, если режим `act`, каким белым списком инструментов. Плюс итог последнего прогона строкой. Два жеста владельца — **«Прогнать сейчас»** (создаёт ручной прогон и сразу открывает его экран; исчерпанный дневной лимит и уже идущий прогон дают внятный отказ, а не второй прогон) и **«Пауза» / «Возобновить»**. Место — «Сущность», рядом с телом-инструкцией, по тому же доводу, что у полосы прогресса цели: рутину открывают ради того, что она делает и делает ли вообще.

Правка расписания и прав — на «Деталях», общей карточкой аспекта, и отдельного редактора формы у рутины нет. Разделение намеренное: у `at` один смысл («во сколько»), у паузы — совсем другой («работает ли»), и текстовое поле рядом с кнопкой означало бы, что выключить рутину можно опечаткой. Обычный путь правки — всё равно слова в чате.

**Предложение рутины по этой записи** [Ш1 — шов V1, решение D41] — плашка над телом у любой записи, которую трогает открытое предложение рутины. До Ш1 путь к предложению был один — открыть тред рутины и найти сообщение; но правит предложение **записи**, и владелец, открывший задачу, обязан увидеть, что по ней есть неотвеченный план, а не узнать об этом случайно. Свёрнутая плашка называет рутину и число правок; развёрнутая показывает разбор целиком: объяснение прозой, строку на каждое правимое поле (у полей аспектов «было» берётся из **снятого предусловия**, а не из графа сейчас: именно с ним предложение сверится на «Принять»; у полей вне аспектов предусловия нет, и «было» там не показывается) и **дифф тела по блокам** — какие блоки добавлены, какие удалены, какие изменены, а внутри изменённого различие по словам; сторона «было» у тела — текущий текст записи. Кнопки — те же **«Принять»** и **«Отклонить»**, что на карточке предложения (ниже), и судьбу по-прежнему решает сервер, а не часы вкладки.

Плашка — **своя у каждого** предложения, а не одна на запись: одну запись законно трогают предложения разных рутин, и решение по каждому своё. Стоит она и там, где предложение трогает запись только связью: у связи затронуты оба конца, и «связать эту задачу с проектом» — событие и для проекта тоже. Решённое предложение из списка уходит: на записи живёт только то, по чему ещё не решено. Развёрнутая плашка **прячет тело записи** — не ради раскладки: тело правится автосохранением, и штрих под чужим текстом сдвинул бы `updated_at`, то есть предложение устарело бы само от себя.

**Правка предложения до принятия** [Ш1] — третий жест владельца рядом с «Принять» и «Отклонить», и живёт он только здесь, на записи: в ленте треда негде показать, что именно правишь. Значение поля правится прямо в строке разбора, текст — кнопкой **«Править»** у строки тела: тот же редактор, что и у самой записи, но без автосохранения и черновиков — слой не пишет в граф ничего, граф двигает только «Принять». В режиме правки дифф пересчитывается по паузе в наборе, и владелец видит **своё** различие с телом записи, а не текст рутины. Не набрано ничего — «Принять» работает ровно как прежде. Границы: правятся значения в **уже предложенном** наборе ключей — правка прав не расширяет; строки создания записи и строки связей не правятся вовсе (у создания нет предусловий, а правка заголовка ещё не существующей записи — это правка записи, которой нет); нескалярные значения не правятся, как и на самой записи. Тело правится там, где сервер довёл предложенный текст до документа и где сторона «было» есть на этом же экране, — в остальных случаях кнопки нет и рядом стоит строка о том, почему.

Правка **не переписывает** предложение рутины: она порождает **новое**, а исходное гасится своей причиной — отличимой и от отказа владельца, и от гашения новым прогоном (01-architecture §7.10, §9.3; подписи — ниже, вместе с остальными судьбами). Владелец принимает ровно то, что видел: решение адресует конкретное предложение, и если оно сменилось между показом и нажатием (правка из другой вкладки, новый прогон), не применяется ничего — экран говорит, чем именно оно заменено, и показывает живое. Расхождение графа с предложением по-прежнему даёт **«Устарело»** со списком расхождений, и правка гибнет вместе с предложением: применять уже нечего. Правленый текст при этом остаётся карточкой в треде рутины — перенести его в запись владелец должен сам.

**Вопрос рутины и карточка предложения** [V1] — на экране **прогона**, там же, где лента шагов. Прогон, кончившийся вопросом, показывает его с полем ответа: ответ переводит исход в `answered` и учитывается следующим прогоном (вопрос, который успел снять новый прогон, помечен «снят новым прогоном» и поля ответа не имеет; у прогона **в архиве** — след отката либо рука владельца — вопрос помечен «снят: прогон в архиве», и поля ответа нет ни при каком исходе: под архивом сервер прогон не находит). Прогон, кончившийся предложением, показывает **карточку предложения**: объяснение прозой, затем **перечисленные** правки — по строке на поле, с заголовком сущности, прежним и предлагаемым значением, — и две кнопки, **«Принять»** и **«Отклонить»**. «50 операций» одной строкой здесь недопустимы: разговора за этим предложением не было, владелец видит его утром, и принять непрочитанное значит отдать граф модели. Та же карточка лежит в треде рутины — это одна карточка на два места, а не две. Карточка — **сводка**, подробность живёт на записи [Ш1]: у строки тела она показывает счётчики различия (сколько блоков добавлено, удалено, изменено) и первые три различающихся блока, а дальше — переход на саму запись, где стоит полный дифф и живёт правка. Неизменённые блоки в карточку не едут вовсе: в ленте у различия нет места на контекст, и три неизменённых строки вытеснили бы единственную изменённую.

Судьбу предложения решает сервер, а не часы вкладки: после «Принять» карточка показывает дату решения, после «Отклонить» — отказ, а если состояние графа изменилось с момента составления плана, — **«Устарело»** со списком расхождений («срок задачи уже другой»), и не применяется ничего. Предложение, погашенное следующим прогоном, помечено «Заменено новым прогоном» — отличимо от отказа владельца. У прогона **в архиве** кнопок нет ни при каком статусе: откат гасит открытое предложение (`stale`, подпись «Устарело — прогон в архиве»), а у записи, убранной в архив с ещё открытым предложением, подпись «Прогон в архиве — решение недоступно».

Предложение, погашенное **правкой владельца**, помечено «Заменено правкой владельца — правленое предложение ниже» [Ш1]. «Ниже» — не оборот речи: правленое приходит следующим сообщением того же треда и стоит прямо под исходным, поэтому указатель — подпись на соседнюю карточку, а не ссылка. Обратный указатель у правленой карточки — «Правка владельца — исходное предложение выше», и он же отличает её от предложения, составленного рутиной: принятая правленая карточка говорит «Принято (с правками)», а не «Принято». На экране прогона, где ленты нет, обе подписи идут без хвоста «ниже» / «выше» — обещать соседа там нечего. Различает карточки не статус, а адрес: каждая знает, **какое именно** предложение показывает, и карточка, чьё предложение уже не живое, не притворяется живой и кнопок не показывает.

**Вкладка «Детали»** — всё остальное, что известно о записи:

5. **Карточки аспектов** — по карточке на каждый аспект сущности: поля по схеме реестра, inline-правка. На карточке — действие **«снять аспект»** (detach: `null` вместо объекта аспекта в `entity_update` — 01-architecture §9.2). Кнопка **«+аспект»** — добавление аспекта из реестра (выбор по имени/иконке/описанию — 01-architecture §4.3).
6. **Подзадачи** — дети по relation `parent` (01-architecture §4.2): дети-задачи — чеклистом (native-рендеринг §3.6), прочие дети — обычными строками; счётчик «2/5» — закрытые/все среди детей-задач; «+ подзадача» создаёт child прямо из секции.
7. **Блокировки** [слайс 2] — два списка: «блокирует» (исходящие `blocks`) и «заблокирована» (входящие `blocks` от незакрытых задач); кнопка **«+»** создаёт `blocks`-связь с выбором сущности.
8. **Связанное (backlinks)** [слайс 2] — объединённая секция: явные `related_to`-связи и автоматические backlinks по `body_refs` (01-architecture §4.1), с пометкой источника.

Ещё три секции «Деталей» приехали с ADE-срезом 1 — все три про состояние записи, а не про то, ради чего её открыли: **«Назначение»** (карточка `orbis/assignment` у любой задачи — исполнитель, доступ агента, право закрывать тикет; именно этим жестом задача становится тикетом); **«Версии»** (закреплённые снимки тела, 01-architecture §4.15 — закрепить и восстановить; грузятся только на открытой вкладке); **«Прогоны»** (история прогонов тикета таблицей с исходом и длиной, а не строками общих связей: открытие — тем же push поверх стека вкладки, что и у подзадач; V1 показывает ту же секцию на рутине — без колонки доступа агента, которого у рутины нет, и с пометкой «ждёт решения» у прогона с открытым предложением). Служебных детей секция «Подзадачи» не показывает — прогон в ней не строка (§3.9).

**Вкладка «Тред»**:

9. **Тред** — тот же чат-компонент с контекст-якорем (§2.2), слайс 1; мокап выше. Единственная вкладка, которую держат размонтированной, пока её не открыли: чат на монтировании заводит запрос списка сообщений.

**Ещё не реализовано** — контракт выше в силе, факт пока другой:

- **секции тегов на экране нет** (п. 2, перечисление выше и строка `#task #expense #running` в мокапе «Сущности»): теги сущности участвуют в запросах и фильтрах Browser (§3.8, 01-architecture §6.1), но с detail-экрана не добавляются и не снимаются;
- **emoji на месте не редактируется** (п. 1): заголовок правится инлайн, emoji только показывается;
- **кнопки «+аспект» нет** (п. 5 и мокап «Деталей»): аспект с экрана можно снять, а навесить новый — только через чат;
- **подзадачи не чеклист** (п. 6): дети-задачи и прочие дети идут одинаковыми строками без чекбокса (native-рендеринг §3.6 к секции не применён), а счётчик показывает общее число детей, а не «закрытые/все»;
- **быстрой записи на экране нет** (§3.7 и строка в мокапе «Сущности»): бар quick-capture заведён только в Browser, а контекстное создание с detail-экрана (таблица §3.7) недоступно — из секций работает лишь строка «Новая подзадача» на «Деталях».

### §3.6 Native-рендеринг в списках

Применяется во всех списках: Browser, query-виджеты, `entity_list`-карточки чата, Agenda.

**`orbis/task`:**

| Элемент | Поведение |
|---|---|
| Чекбокс | Цвет по `priority` (high — акцентный/красный, medium — жёлтый, low — серый, не задан — нейтральный). Тап → `status=done` с проставлением `completed_at` (01-architecture §3.2); повторный тап откатывает |
| Статус-бейдж | Для статусов кроме дефолтного потока: `inbox`, `waiting` (с `waiting_for`, если задан), `cancelled` |
| Lock-иконка 🔒 | Есть живая входящая `blocks`-связь от незакрытой задачи (семантика — как у `excludeBlocked`, 01-architecture §6.1). Тап по иконке — подсказка «кем заблокирована» |
| Счётчик детей | «2/5» — закрытые/все дети-задачи; показывается при наличии детей-задач |
| Срок | `due_date`; просроченный — красным |

**`orbis/schedule`:** дата/время `start_at` в строке (диапазон, если задан `end_at`; «весь день» при `all_day`); иконка recurrence 🔁 у шаблонов (задано `recurrence` — 01-architecture §3.1).

**`orbis/financial`:** сумма со знаком и цветом по `direction` (расход — `−340 ₽`, красным; доход — `+150 000 ₽`, зелёным) + бейдж категории по `category_ref` — те же ключевые поля, что у `entity_card` в чате (§2.3).

**Generic-карточка** (остальные аспекты, включая будущие): строка/карточка «ключ — значение» по 2–3 ключевым полям аспекта (подсказки — `view_config` реестра, 01-architecture §4.3) + действие **«Открыть в [view]»**, если для аспекта установлен view (`installedViews` — 01-architecture §4.4). Новый аспект получает читаемое представление без кода в Browser.

**`orbis/goal` в строках списков — прогресса нет** (слайс 3, решение **D23**). Решение D22 обещало цели «представление на detail-экране и в списках (generic-строка §3.6)»; сделана только первая половина. Причины две, и обе — не про цели: generic-карточка сама по себе всё ещё не реализована ни в одном списке (долг слайса 1 — запись в конце секции), а прогресс в строке стоил бы **четырёх лишних запросов на каждую строку-цель** (измерено и запиннено тестом: чтение обычной сущности — 6 запросов, цели — 10: каталог полей, таймзона, savepoint, агрегат) — он считается обходом графа, а не читается из поля. Места, читающие сущности по одной (строки карточки чата, подзадачи, блокировки, закреплённое), эти четыре запроса на цель платят уже сегодня — списки через `entity.query` не платят их вовсе. Цель в списке выглядит обычной строкой с title; её прогресс виден на detail-экране (§3.5) и, для целей целиком, в списке «Год» (§3.3).

Сущность с несколькими аспектами комбинирует элементы: «Купить кроссовки» = чекбокс + сумма + день недели.

**Ещё не реализовано** — **восемь долгов**; контракт выше в силе, факт пока другой. «Живая строка» списка сегодня устроена так: слева глиф состояния (или emoji сущности, если он задан), посередине заголовок, справа **одна** мета из аспекта. Отсюда и весь список:

- **Generic-карточки нет ни в одном списке** (долг слайса 1). Строка списка разбирает ровно три аспекта — `orbis/task`, `orbis/financial`, `orbis/schedule`; всё остальное (`orbis/budget`, `orbis/category`, `orbis/memory`, `orbis/goal` и любой будущий) рисуется строкой из emoji и title, без «ключ — значение» по `view_config` и без действия «Открыть в [view]». Обещание «новый аспект получает читаемое представление без кода» сегодня держится только на detail-экране (§3.5 п. 5), где карточки аспектов строятся по схеме реестра. Это и есть первая из двух причин, по которым прогресс цели не поехал в списки (D23).
- **Строка не переключает статус.** Чекбокс задачи в списке — глиф состояния, а не контрол: «тап → `status=done`, повторный тап откатывает» из таблицы выше не работает нигде, кроме detail-экрана, куда тап по строке и ведёт. У сущности с emoji глифа нет вовсе — его место занимает emoji, так что у задачи с emoji в строке не остаётся и признака задачи.
- **Приоритет не красит чекбокс.** `high` отмечается отдельной красной точкой у заголовка, `medium` и `low` не показываются никак.
- **Трёх элементов задачи нет вовсе:** статус-бейджа (`inbox`, `waiting`, `cancelled`), lock-иконки 🔒 и счётчика детей «2/5». Строка их не рисует и данных для них не запрашивает — в отличие от detail-экрана, где блокировки и подзадачи есть (§3.5).
- **Просроченный срок не краснеет:** `due_date` печатается одним и тем же приглушённым цветом, прошёл он или нет. Просрочку сегодня показывает только секция «Просроченное» в Agenda (§4.2).
- **Расписание — только день `start_at`:** без времени, без диапазона `end_at`, без пометки «весь день» при `all_day` и без иконки 🔁 у шаблонов повторения. Время в Agenda печатает сама Agenda отдельной колонкой, а не строка.
- **У финансовой строки нет бейджа категории:** сумма со знаком и цветом есть, `category_ref` в строке не показывается — бейдж живёт только на detail-экране и в списках транзакций Budget (03-budget §3.3).
- **Элементы аспектов не комбинируются.** Справа печатается ровно одна мета, по правилу «сумма → срок задачи → дата начала»: «Купить кроссовки» (задача + расход) показывает сумму и не показывает срок — пример в конце секции пока не воспроизводится.

Отдельно — **граница применения**: перечисленное выше относится к спискам, которые рисуют строку общим компонентом, — Browser, Agenda и «Память AI» (§2.7). Query-виджеты (§3.4) и карточки чата (§2.3) печатают только заголовки сущностей; это записано долгами в их собственных секциях, а фраза «применяется во всех списках» в начале §3.6 описывает контракт, а не факт.

### §3.7 Quick-capture бар — слайс 1

Главный не-чатовый путь ввода Browser-lite. Строка быстрой записи внизу экрана списка и detail-экранов. Создаёт сущность из введённого текста (текст → `title`) **без интерпретации**: AI и fast-path-грамматика здесь не применяются — интерпретация свободного текста живёт в Chat. Quick-capture не тождественен пути ввода №3 из 00-product §5 («Quick-add в views») — тот структурирует ввод контекстно (например, бар расхода в Budget) и относится к слайсу 2; quick-capture — отдельный не-чатовый путь без AI и без структурирования, инфраструктура Browser-lite слайса 1.

**Smart list** — сущность с тегом `smart-list`: все шесть преднастроенных сущностей §3.3 (Daily Planning, Upcoming, All Tasks, «Год», «Жизнь», «Рутины») и списки, сохранённые через §3.8. Дискриминатор поведения quick-capture — именно тег, а не наличие `{{query:...}}`-блоков в body: проект с query-блоком — не smart list, его quick-capture создаёт детей.

Поведение контекстное:

| Где вызван | Что создаётся |
|---|---|
| Корень Browser | Сущность без аспектов (заметка/идея) |
| Detail-экран smart list (тег `smart-list`) | Сущность с `orbis/task`, `status=inbox` — **без relation** к smart list: smart list — линза, а не родитель, задачу находят его query-блоки (в Daily Planning — мгновенно в Inbox-блоке; в All Tasks — в общем списке; в Upcoming — после простановки `due_date`) |
| Detail-экран любой другой сущности (проект, категория — любая сущность без тега `smart-list`, даже с `{{query:...}}`-блоками в body) | Child этой сущности через relation `parent`; вызов из секции «Подзадачи» дополнительно вешает `orbis/task` (`status=inbox`) |

### §3.8 Фильтры и smart lists

Панель фильтров над списком: **теги, аспекты, статус, приоритет, диапазон дат** + переключатель «показать служебные» (§3.9). «Диапазон дат» фильтрует по `created_at` (core-поле — 01-architecture §6.1); фильтры по аспектным датам (`due_date`, `start_at`) — через query-builder (§3.4). Фильтры — потребитель №3 единого query-движка (01-architecture §6.3): любое состояние панели выразимо строкой грамматики.

Кнопка **«Сохранить как smart list»**: запрашивает имя → создаётся обычная сущность (title = имя, body = query-блок, сериализованный из текущих фильтров, тег `smart-list`) → автоматически закрепляется в сайдбаре. Дальше это просто сущность: правится query-builder'ом (§3.4) и удаляется (открепление — §3.2, в UI ещё не реализовано).

### §3.9 Служебные сущности

Сущности, порождаемые системой как побочный артефакт, исключены из списков Browser и результатов фильтров **по умолчанию**. Первый и пока единственный служебный аспект — **`orbis/agent-run`**, прогон исполнителя (ADE-срез 1, 01-architecture §3.15); следующими сюда встанут чекины привычек (future, при появлении домена привычек, 01-architecture §11.2). Recurring-**инстансы** служебными не считаются — это полноценные пользовательские сущности, видимые в списках наравне с остальными.

**Механизм — неявное исключение в компиляторе запроса, пока запрос сам не назвал служебный аспект.** Компилятор добавляет к каждому запросу условие «служебных аспектов на сущности нет» и снимает его, если запрос **назвал** такой аспект — либо прямо (`aspect=orbis/agent-run`), либо любым полем фильтра, которое разрешается в служебный аспект (`outcome=running` — уже назвал, и выдача не пуста). Сортировка по такому полю названием **не считается**: `sortBy` не отбирает. Условие индексом не ускоряется (GIN отрицания не покрывает) — это дешёвый построчный фильтр поверх остальной выборки.

Отсюда форма переключателя **«показать служебные»** (§3.8): он показывает **одни служебные** (`aspect=orbis/agent-run`), а не «все и служебные заодно» — грамматика такой формы не даёт, и заводить её ради одного переключателя означало бы расширять язык запросов под кнопку. **Переключателя на панели пока нет:** прогоны открываются с экранов тикета (секция «Прогоны»), проекта (блок «Последние прогоны» в теле) и рутины (та же секция «Прогоны», §3.5, V1), а также явным запросом по аспекту — первый блок списка «Рутины» (§3.3) и есть такой запрос; секция «Подзадачи» служебных детей не показывает вовсе.

Границы механизма названы прямо: подсказки @-упоминаний в редакторе идут сырым поиском мимо компилятора, и прогон там виден — упоминание прогона в тексте законно; агрегат (`count`/`sum`/`latest`) по полю служебного аспекта **без фильтра по этому аспекту** даёт молчаливый ноль, а не ошибку.

## §4. Agenda-lite — слайс 2

Один экран, без push-подэкранов собственных — тап по строке пушит обычный detail-экран (§3.5).

```
┌──────────────────────────────────────────┐
│  ⚠ Просроченное (2)            ← красный │
│   ◉ Закончить API        срок был 11.06  │
│   ◉ Подтвердить созвон    был вчера 📅   │
│ ──────────────────────────────────────── │
│  Сегодня · сб, 13 июня                   │
│   весь день   Отпуск: день 1     ✈️      │
│   09:00   Стендап                📅 🔁   │
│   14:00   Врач                   📅 💊   │
│ ──────────────────────────────────────── │
│  Вс, 14 июня                             │
│   — день свободен —                      │
│ ──────────────────────────────────────── │
│  Пн, 15 июня …                           │
└──────────────────────────────────────────┘
```

### §4.1 Состав и группировка

- Горизонт: **Сегодня → +7 дней**, группировка по дням, каждый день — секция с заголовком.
- Дни наполняются сущностями с `orbis/schedule` по `start_at`. Строка = время `start_at` (диапазон при `end_at`) + `title` + иконки аспектов (native-рендеринг — §3.6). `all_day`-сущности — в начале дня, с пометкой «весь день», до строк со временем.
- Задачи без `orbis/schedule` в дневные секции **не попадают** — их место в Daily Planning и Upcoming (§3.3); Agenda показывает время. Единственное исключение — секция «Просроченное» (§4.2). Объединённое представление «срок + время» — задача полного Calendar view (Future).
- **Recurring:** показываются инстансы (связь `derived_from` от шаблона — 01-architecture §3.1, §5.4); сами шаблоны (сущности с заданным `recurrence`) в Agenda скрыты — иначе шаблон ежемесячного платежа висел бы строкой без даты исполнения. Открыть шаблон можно с detail-экрана инстанса.
- Пустой день — строка «день свободен»; секция дня не скрывается, чтобы горизонт читался целиком.

### §4.2 Секция «Просроченное»

Всегда сверху, с красным акцентом. Содержит:

1. **Незакрытые задачи с просроченным сроком** — `orbis/task`, `due_date` раньше сегодня, статус не `done`/`cancelled`. Без ограничения давности: задача закрывается или переносится — и уходит из секции.
2. **Незакрытые scheduled-задачи, время которых прошло** — сущность одновременно имеет `orbis/task` и `orbis/schedule`, `start_at` раньше начала сегодняшнего дня, статус не `done`/`cancelled`. Если у неё также есть `due_date`, в секции она показывается один раз по более ранней из дат.

Чистые события с одним `orbis/schedule` в «Просроченное» **не попадают**: в MVP у события нет статуса посещения, поэтому прошедшее время не означает «пропущено». Такие события остаются историей в Browser/поиске. Статус посещения и отдельный missed-events UX требуют нового аспектного поля и отложены до полного Calendar view.

Внутри секции — сортировка по релевантной дате, старейшие сверху. Элемент покидает секцию при закрытии задачи, переносе даты/времени или архивации. Счётчик секции — бейдж вкладки Agenda (§1.5).

### §4.3 Граница компонента

Agenda-lite — это список, сознательно без календарной механики: **сетка месяца/недели, drag-перенос между днями и слотами — это полный Calendar view**, отнесённый в Future Directions (00-product §10). Данные времени уже в графе — Calendar станет ещё одной линзой без миграций.

## §5. AI-сценарии ядра

Двенадцать эталонных сценариев: одиннадцать «реплика → ожидаемое поведение» в чате и один — инструкция владельца в треде задачи для внешнего агента (слайс 1). Два (№10 и №11) пришли со слайсом 3 вместе с аспектом целей и блоком «Цели и горизонты» системного промпта, последний (№12) — с V1 вместе с рутинами. Механика тулов — 01-architecture §9.2, журнала — §7.8, fast-path — §7.5, политика подтверждений — §7.10, MCP и «что нового» — §9.3.

**1. «купи продукты»** (глобальный тред)
→ Создаётся сущность с `orbis/task`, `status=inbox` (дефолт — 01-architecture §3.2). В чате — `entity_card` с Undo. Задача немедленно появляется в Inbox-блоке Daily Planning (§3.3) — без какого-либо связывания: её находит query.

**2. «закончить API к пятнице»**
→ Задача со `status=planned` и `due_date` = ближайшая будущая пятница (если сегодня пятница — сегодня); дата вычисляется в таймзоне пользователя. `entity_card` показывает срок — ошибка распознавания даты правится inline.

**3. Из треда сущности «План питания»: «обсудим детали»**
→ Диалог идёт во вкладке «Тред» этой сущности; якорная сущность уже в контексте модели (§2.2), уточнять «детали чего» не нужно. Глобальный чат не засоряется: история скоупнута тредом (01-architecture §7.2–§7.3); выводы переносятся в граф только явно — memory-факт, дозапись в body, note-сущность.

**4. «запомни: не ем свинину»**
→ AI предлагает сохранить memory-факт — карточка предложения с кнопками **[Запомнить]** / **[Не надо]**. По [Запомнить] создаётся сущность с `orbis/memory` (`kind=fact`) — видимая и редактируемая в Browser и на экране «Память AI» (§2.7). Факт начинает инжектиться в контекст (01-architecture §7.4) и влияет на будущие предложения (например, рецепты в «Плане питания»).

**5. «отмени последнее»**
→ Отменяется последнее ещё не отменённое действие — механика Undo по журналу действий (01-architecture §7.8). В чате — подтверждение с указанием, что именно отменено; соответствующая карточка гаснет (§2.3). Работает и для действий fast-path и внешних агентов.

**6. «что я сделал на этой неделе?»**
→ AI вызывает `entity_query` (например, `aspect=orbis/task, status=done, sortBy=completed_at:desc, limit=100`), отбирает попавшие в текущую неделю по `completed_at` и отвечает карточкой `entity_list` с кратким резюме. Отбор недели — на стороне AI: относительные токены грамматики (01-architecture §6.1) не включают «прошедшую неделю», и расширять грамматику для этого не требуется.

**7. «обед 340»**
→ Fast-path (01-architecture §7.5): мгновенная `entity_card` с пометкой «⚡ без AI» (§2.5) — сущность с `orbis/financial`, категория «Еда» по alias. Работает офлайн; LLM не вызывается.

**8. «перенеси встречу с Димой на четверг»**
→ `entity_query` (`aspect=orbis/schedule, search=Дима`) — поиск кандидата; при нескольких совпадениях AI уточняет, какую встречу. Затем `entity_update` аспекта `orbis/schedule` (новый `start_at`). В чате — `entity_card` с новым временем и Undo; Agenda отражает перенос немедленно.

**9. Агент через MCP ведёт проект «Orbis» (слайс 1)**
→ Внешний агент (Claude Code через MCP, 01-architecture §9.3) создаёт сущность-проект и задачи внутри неё (`entity_create` + relation `parent`), переносит документацию note-сущностями и пишет заметки о ходе и результате в тред каждой задачи (§2.2). Назначенные ему тикеты он двигает **глаголами исполнителя** (`orbis_claim_task` → `orbis_run_step` → `orbis_checkpoint` / `orbis_finish`), а не сырым `entity_update`: каждый глагол несёт правило, которое сырая правка обошла бы. **Закрыть тикет сам он не может** — `orbis_finish` уводит тикет в `waiting` «готово, проверь», а `done` возможен только при `may_close` в назначении (01-architecture §3.14, §9.3); у гранта с областью `worker` сырая правка статуса отклоняется сервером вовсе. Инструкцию владельца из треда агент находит паттерном **«что нового»**: `entity_query` по `updated_at` новее курсора прошлого опроса плюс `entity_get(include: ["thread"])` — без нового серверного механизма, курсор агент хранит у себя (01-architecture §9.3). Все действия агента идут через тот же executor в журнал действий (01-architecture §7.8), под той же политикой подтверждений (§7.10), что и у внутреннего AI: рутинная смена статуса — `execute`, действие шире по масштабу или менее обратимое — `preview`/`explicit-confirmation` (`confirmation_card`, §2.3). В глобальном треде появляется системное сообщение о каждом действии агента (§2.3); владелец наблюдает статусы и заметки и отвечает из тредов задач — в том числе с телефона (§2.2). Это и есть сценарий приёмки слайса 1: работа над Orbis ведётся в Orbis (00-product §8–§9).

**10. «хочу накопить 300 000 на отпуск» (слайс 3)**
→ Одна сущность с аспектом `orbis/goal`: `target_value` — целевое число decimal-строкой, `progress_source` — запрос грамматики §6.1 плюс агрегат (например `aggregate=sum`, `field=amount` по отложенным). `current_value` модель не заполняет никогда — прогресс считает сервер обходом графа при каждом чтении (01-architecture §11.3), и полосу на detail-экране рисует он же (§3.5). Цель немедленно попадает в список «Год» (§3.3) — без связывания, её находит query.

**11. «спланируй неделю» / «как идут цели» (слайс 3)**
→ Сначала `entity_query` — что уже заведено на нужный срок (`due_date=next_7d`) или какие цели есть (`aspect=orbis/goal`), и только потом предложение. Дублей уже существующих целей и задач AI не заводит — правит найденное (§3.3, «одна сущность на намерение»). Отдельных списков «День», «Неделя», «Месяц» в продукте нет: лестницу горизонтов несут Daily Planning, Upcoming, «Год» и «Жизнь» (§3.3), и промпт знает именно эту раскладку — предложить открыть несуществующий список он не может.

**12. «каждое утро в 7 собери план дня, объясни почему так и предложи» (V1)**
→ Рутина заводится **словами в чате**, отдельной формы для неё в продукте нет. AI создаёт одну сущность с аспектом `orbis/routine` (01-architecture §3.16): «что делать» ложится в тело обычным текстом, в аспект — только `at=07:00`, режим и, если владелец попросил действовать самостоятельно, белый список инструментов. Умолчания у режима нет — поле обязательно (01-architecture §3.16); что без явного «делай сам» рутина заводится в `propose`, модели говорят `ai_instructions` аспекта (они уезжают в описание `attach_orbis_routine`), а гарантирует не промпт, а гейт: просьба «делай сам» даёт `mode: act`, и такая рутина **требует явного подтверждения владельца** прямо в чате (01-architecture §7.10) — карточка называет рутину, режим и белый список; это единственное действие AI, которое раздаёт право писать в граф без спроса. Тем же подтверждением защищена правка инструкции уже автономной рутины (тела/заголовка при `mode: act`) не-владельцем. Рутина немедленно видна во втором блоке списка «Рутины» (§3.3).

→ Дальше её ведёт сервер. В 7:00 по местному времени владельца планировщик создаёт прогон, внутренний исполнитель читает граф и заканчивает работу одним из двух: **предложением** (карточка с перечисленными правками — в треде рутины и на экране прогона, §3.5) или **вопросом** («какой из двух проектов сегодня главный?»), и тогда прогон попадает в первый блок списка «Рутины» и считается его бейджем (§3.2). Кнопка **«Прогнать сейчас»** на экране рутины делает то же немедленно, не дожидаясь утра.

→ Владелец принимает предложение — правки применяются одной группой, попадают в журнал действий и откатываются кнопкой на экране прогона или словами «отмени последнее» (01-architecture §7.8, §9.3); отклоняет — граф не тронут; отвечает на вопрос — ответ учтён следующим прогоном. Если за ночь владелец поправил что-то сам, вчерашнее предложение не применяется, а показывает **расхождение**: «срок задачи уже другой». Не принятое до следующего утра предложение новый прогон гасит как «заменено». Три сорванных прогона подряд ставят рутину на паузу с записью в её тред — это тоже видно на экране рутины.

## §6. Edge cases

| Ситуация | Поведение |
|---|---|
| **Завершение родителя с активными детьми** (чекбокс на проекте, у которого есть незакрытые дети-задачи) | UI (и AI — уточняющим вопросом до вызова тулов) спрашивает, что сделать с детьми: **завершить вместе с родителем** / **отменить действие** / **завершить только родителя** (дети остаются активными и видимыми в списках). Молчаливого каскада нет |
| **Циклическая блокировка** (создание `blocks`-связи, замыкающей цикл) | Связь не создаётся; пользователь видит **путь цикла** («A → B → C → A») — плашкой в UI или `error_card` в чате. Инвариант ацикличности `blocks`-графа и серверный отказ с путём цикла — 01-architecture §4.2 |
| **Заблокированная задача с `due_date` сегодня** | Скрыта в «Сегодня» Daily Planning — там `excludeBlocked=true` (§3.3); остаётся видимой в Upcoming (срок «сегодня» попадает в `next_7d`: диапазон включает сегодня — 01-architecture §6.1) и в All Tasks, с lock-иконкой (§3.6). Задача не «исчезает из системы» — она уходит только из фокус-списка |
| **Правка инстанса recurring** | Меняется **только инстанс** — это отдельная сущность, связанная `derived_from` с шаблоном (01-architecture §3.1, §5.4). Серия правится отдельным действием **«править серию»** на detail-экране инстанса (открывает шаблон); правка шаблона влияет на будущие инстансы, уже созданные не трогает |
| **Правка `body` с устаревшей версией** (конкурентная правка — две вкладки или устройства редактируют один и тот же `body`) | Optimistic-check по `updated_at` (01-architecture §5.2) отклоняет правку структурированной ошибкой вместо тихой перезаписи или merge. UI показывает `error_card` (§2.3) и предлагает **перезагрузить сущность и повторить правку** вручную. Автоматического слияния нет — это осознанный компромисс онлайн-первого разреза (01-architecture §12) |
| **Сущность без аспектов** | Полностью валидна — заметка, идея, черновик мысли. Видна в Browser обычной строкой (title + теги, без native-элементов §3.6); аспекты добавляются позже через «+аспект» или чат |

## §7. Онбординг и сидирование — слайс 1

При создании пользователя система создаёт стартовый набор данных (онбординг-сидирование — роутер `user`, 01-architecture §9.1). Сидирование выполняется один раз; повторный вызов дублей не создаёт. Состав: категории (§7.1), сидированные smart lists (§7.2), настройки (§7.3) и глобальный тред (§7.3) — весь набор нужен уже в слайсе 1: без него агентная петля и fast-path не с чем сверяться в первый день.

### §7.2 Pinned-сущности

Создаются шесть сущностей — **Daily Planning, Upcoming, All Tasks, «Год», «Жизнь», «Рутины»** — с полными body и тегом `smart-list` из §3.3, в этом порядке. В сайдбаре закрепляются пять из шести (`pinnedEntities` — 01-architecture §4.4), в порядке **Daily Planning, Upcoming, All Tasks, «Год», «Рутины»**; не закрепляется одна «Жизнь» (§3.3: открывают раз в год, а каждое закрепление стоит count-запроса на каждой инвалидации кэша). Порядок закреплений не совпадает с порядком создания: «Жизнь» создаётся пятой, но выпадает из сайдбара, и пятым закреплением становятся «Рутины».

Два горизонта приехали позже остальных — в слайсе 3, — а «Рутины» ещё позже, в V1: у уже существующего аккаунта их не было, потому что **сидирование одноразовое**, его сторож выходит до вставок, и повторный вызов ничего не досевает сам по себе. Недостающее доставляют идемпотентные досевы в той же ветке сторожа — свой на каждую поставку (горизонты с закреплением «Года»; «Рутины» с их закреплением). Досев вставляет только отсутствующее (по детерминированным id), не перезаписывает тела, которые владелец успел поправить, и не двигает пользовательские закрепления — новое дописывается в конец. Адресность — намеренная: общий проход «досеять всё, чего не хватает» воскрешал бы Daily Planning или All Tasks, удалённые владельцем осознанно, — сид не отличает «никогда не было» от «удалено». Цена — по копии механизма на поставку. Обратная сторона названа прямо: удалённый владельцем преднастроенный список следующий запуск сидирования воскресит — «удалить навсегда» в этом механизме не выражается. Чек-лист деплоя — `docs/implementation/02-ops-runbook.md` §1.

## §8. Приёмочные проверки Agenda — слайс 2

1. Прошедшая чистая сущность с одним `orbis/schedule` не появляется в «Просроченном» и остаётся доступна в Browser.
2. Незакрытая task-сущность с просроченным `due_date` появляется в «Просроченном» независимо от наличия schedule; после `done`, переноса или архивации исчезает.
3. Task + schedule с прошедшим `start_at` показывается в «Просроченном» один раз, даже если одновременно просрочен `due_date`.
4. Задача с одним `due_date` видна в Daily Planning/Upcoming, но не в дневной секции Agenda; после добавления `orbis/schedule` появляется в соответствующем дне.

## §9. Приёмочные проверки слайса 3

Все проверки ниже исполняются **на живом проде, на боевом аккаунте** — как §8 и 03-budget §7. Финансовая часть фазы A (границы дат, сторож recurring-шаблонов) проверяется там же, где остальной финансовый контур, — 03-budget §7, пункты 7–8; здесь — гейты, навигация, чат, query-builder и цели. Порядок пунктов — по фазам слайса.

1. **Перф-гейт (фаза A).** Порог одной из семи измеряемых операций, будучи заведомо занижен, роняет CI; медианы печатаются строками `perf: …` и на зелёном прогоне. Клиентские числа §8 сняты по чек-листу перед выкаткой и записаны в историю замеров (`docs/implementation/02-ops-runbook.md` §8) — автоматикой они не закрыты осознанно (04-decision-log D21).
2. **Вход по ссылке (фаза B).** Ссылка на сущность, открытая с ноута, приводит на её detail-экран в свёрнутом стеке нужной вкладки; чужой или несуществующий `id` даёт экран «не найдено» с возвратом на корень вкладки — частичного открытия нет.
3. **Жест «назад» (фаза B).** На телефоне системный жест снимает push-экран, а на корне вкладки возвращает на вкладку, с которой на неё переключились (D18); кнопка «Назад» в шапке делает то же самое. После перезапуска PWA стеки вкладок восстановлены (§1.4), и «назад» с восстановленного экрана работает сразу, а не после первого перехода.
4. **Чат: форматирование и ссылки (фаза C).** Ответ модели с заголовками, списками и кодом отрисован форматированием, а не сырым текстом; `[[entity:…]]` в `body` открывает сущность внутри приложения; `{{query:…}}`-блоки остаются живыми виджетами.
5. **Чипы (фаза C).** Под последним ответом модели появляются 2–4 продолжения, тап отправляет текст чипа обычным сообщением, после следующего сообщения чипы исчезают; у карточки fast-path чипов нет (LLM не вызывался). Долю ответов без чипов считаем нормой, а не дефектом (D19).
6. **История после перезагрузки (фаза C).** После F5 карточка в ленте остаётся карточкой, а не голой строкой.
7. **Query-builder (фаза D).** «Настроить» на сидированном smart list открывает форму; сохранение без изменений оставляет строку блока **байт-в-байт** прежней; правка через форму меняет выдачу списка; невалидный блок открывается строковым редактором, а не формой.
8. **Прогресс цели (фаза E).** Цель с `progress_source` показывает на detail-экране прогресс, посчитанный из графа, и обновляет его после добавления подходящей сущности — без правки самой цели. Цель со сломанным источником открывается и объясняет причину словами, а не показывает ноль и не отказывается открываться.
9. **Горизонты у существующего аккаунта (фаза E).** После деплоя и первого старта сессии в сайдбаре появился «Год» (последней строкой закреплений, а не обязательно четвёртой), в Browser по тегу `smart-list` — «Жизнь»; повторные старты дублей не создают, ранее закреплённое не сдвинуто. Пересев реестра аспектов выполнен: `bun scripts/ops.ts check` показывает `✓ orbis/goal`, и созданная через чат цель не отклоняется валидацией. Именно `ops.ts check`, а не `/health`: поле `aspectDrift` — снимок, снятый на старте процесса, и после пересева на живом сервисе оно повторяет прежнее расхождение до перезапуска (чек-лист деплоя — `docs/implementation/02-ops-runbook.md` §1).
