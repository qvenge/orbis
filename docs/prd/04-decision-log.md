## Решения v3.1 (2026-07-02)

### D1. Онлайн-первый разрез

- **Решение:** PostgreSQL (Supabase) — единственный источник истины; клиент тонкий, мгновенность UX — оптимистичные обновления и server-state-кэш. Из MVP вырезаются: PowerSync, клиентский SQLite/WASM/OPFS, матрица конфликтов, `server_revision`, `sync_log`, tombstone-связи, конфликтные копии body, второй SQLite-бэкенд query-движка и тест-сьют эквивалентности бэкендов.
- **Статус:** принято 2026-07-02
- **Обоснование:** реальная среда владельца (телефон + ноут) почти всегда онлайн; цена честного offline-first (PowerSync + SQLite + матрица конфликтов + двухбэкендный движок) выше его ценности для этой среды. Полный offline-first — Future; при возврате отправная точка — готовый sync-движок класса PowerSync, а не рукописный протокол репликации (обе прошлые итерации сошлись: самописная синхронизация — худший вариант).
- **Заменяет:** «полный offline-first» спеки v3 целиком; PROD-01 леджера
- **Детали:** 01-architecture §5.1, §12

### D2. Офлайн = retry-буфер ввода, а не режим работы

- **Решение:** Буферизуются только create-операции fast-path (client-generated UUIDv7, идемпотентная досылка); офлайн-правки существующих сущностей недоступны. Контракт буфера — три пункта: (1) серверная идемпотентность по client-UUID обязательна и онлайн (повторы браузера, упавшие вкладки, разрыв после отправки до ответа — не офлайн-специфичное свойство); (2) буфер различает transport failure (ретраится автоматически) и business rejection (не ретраится, показывается пользователю как ошибка); (3) удаление записи из очереди — только после подтверждения сервера (успех или показанный пользователю business-отказ), а не по факту отправки пакета. Корректность не зависит от service workers / Background Sync.
- **Статус:** принято 2026-07-02
- **Обоснование:** полный offline write-back снят вместе с D1, но потеря набранного пользователем текста при разрыве связи недопустима — узкий буфер только на входе закрывает главный риск дёшево, без протокола репликации.
- **Заменяет:** офлайн-режим полного доступа на запись, предполагавшийся спекой v3
- **Детали:** 01-architecture §5.3

### D3. Конкурентность: LWW + optimistic-check

- **Решение:** Last-write-wins на уровне API для большинства полей; для правок `body` — optimistic-check по `updated_at` (правка с устаревшей версией отклоняется структурированной ошибкой, UI предлагает перезагрузить сущность и повторить правку вручную — автоматического merge нет).
- **Статус:** принято 2026-07-02
- **Обоснование:** без CRDT нужен предсказуемый и дешёвый в реализации механизм; известный компромисс — две одновременно открытые вкладки/устройства, правящие один `body`, могут получить отказ — фиксируется как осознанное ограничение.
- **Заменяет:** Yjs-решение леджера §18 (CRDT для совместного редактирования body)
- **Детали:** 01-architecture §5.2

### D4. Модель данных: JSONB v3 сохраняется + черри-пик из леджера

- **Решение:** Четыре слоя сущности и aspects-JSONB остаются без изменений — мотивация нормализации была в основном PowerSync-специфичной и умерла вместе с ним (DATA-01…08 → superseded). Из леджера переносятся: **`entity_origins`** — таблица provenance импорта с уникальностью `(owner, namespace, external_id)` вместо `meta.import_ids` (Undo импорта физически удаляет строки origins, повторный импорт возможен); **`raw_input`** живёт в `content` сообщения чата, не в `meta` сущности. Реестр тегов остаётся вычислимым.
- **Статус:** принято 2026-07-02
- **Обоснование:** причина нормализации (DATA-01…08) — совместимость с PowerSync-репликацией — отпала вместе с D1; переписывать модель данных без этой причины избыточная работа без ценности.
- **Заменяет:** DATA-01…08 леджера (нормализация модели под PowerSync)
- **Детали:** 01-architecture §2, §4.8

### D5. MCP возвращается в MVP — слайс 1

- **Решение:** Агентная петля — якорный сценарий продукта, MCP — её транспорт. MVP: один PAT полного доступа (hash-only хранение, constant-time сравнение, сырой токен показывается один раз), тот же реестр тулов, действия — через executor в журнал. Дополнение контракта — паттерн **«что нового»** для polling-петли агента, без нового серверного механизма, только комбинация существующих тулов: `entity_query` с фильтром по `updated_at` (core-поле, уже в грамматике) находит сущности, изменённые с момента прошлого опроса; `entity_get(include: ["thread"])` читает новые инструкции, оставленные владельцем в тредах изменённых сущностей; курсор «момент прошлого опроса» агент хранит у себя, не на сервере Orbis.
- **Статус:** принято 2026-07-02 (отменяет отсрочку MCP до фазы 2, принятую ранее в этой же переработке; подтверждает исходное решение спеки v3 новым обоснованием)
- **Обоснование:** без продакшена и MCP агентная петля не запускается день в день с владельцем; второй якорный сценарий (человек + агенты) требует MCP с первого слайса, а не фазы 2.
- **Заменяет:** промежуточную отсрочку MCP до фазы 2, принятую в начале этой переработки
- **Детали:** 01-architecture §9.3

### D6. Политика подтверждений AI-действий — включается, обязательна

- **Решение:** Уровень `execute / preview / explicit-confirmation / forbidden` определяет серверная политика Orbis после структурной валидации tool-call, не модель. Входы классификации — пять: явность намерения (прямая команда vs самостоятельная инициатива модели), обратимость (есть ли у операции `inverse` и восстанавливает ли он состояние полностью), масштаб (`single` / `bounded` / `bulk`), внешние эффекты (за пределами графа Orbis), чувствительность данных и операций. Одобрение действия уровня `explicit-confirmation` исполняет сохранённый неизменяемый payload, провалидированный в момент запроса подтверждения, — после ревалидации текущего состояния, но без повторного вызова модели. Правила едины для внутреннего AI и MCP-агентов.
- **Статус:** принято 2026-07-02 (перенос AI-09…14 леджера в PRD), обязательна к реализации в слайсе 1
- **Обоснование:** агентная петля (D5) увеличивает автономность действий без владельца рядом; без явной серверной политики риск непредсказуемых bulk- или необратимых операций растёт вместе с автономностью агентов.
- **Заменяет:** AI-09…14 леджера как неформализованный (вне PRD) статус — политика становится частью PRD, а не только внутренним соглашением
- **Детали:** 01-architecture §7.10

### D7. Транспорт чата

- **Решение:** Обычная tRPC-мутация — клиент отправляет сообщение, ждёт и получает ответ целиком одним пакетом. Ни `useChat`, ни SSE, ни другой потоковый транспорт в MVP не используется. Шов для будущего стриминга остаётся в интерфейсе `LLMProvider` (реализован поверх Vercel AI SDK, но типы SDK наружу не протекают).
- **Статус:** принято 2026-07-02 (закрывает открытый вопрос AI-08 леджера)
- **Обоснование:** соответствует контракту v3 «стриминг — Future»; простая мутация дешевле в реализации, чем потоковый транспорт, а UX-цена (typing-индикатор вместо токен-за-токеном рендера) приемлема для MVP.
- **Заменяет:** открытый вопрос AI-08 леджера (транспорт чата не был выбран)
- **Детали:** 01-architecture §7.7

### D8. Экспорт данных — в слайс 1

- **Решение:** JSON-дамп всего графа пользователя (сущности, relations, треды и сообщения чатов, настройки, кастомные аспекты) — одна ручка в `user`-роутере и кнопка в настройках. При любом будущем CSV-экспорте обязателен formula-injection escaping значений, начинающихся с `=`, `+`, `-`, `@`.
- **Статус:** принято 2026-07-02
- **Обоснование:** система, претендующая на роль единственного хранилища жизни владельца, обязана иметь выход с первого дня — не ждать более зрелых итераций продукта.
- **Заменяет:** отсутствие экспорта в спеке v3
- **Детали:** 01-architecture §9.4

### D9. Треды сущностей — слайс 1; Agenda-lite — слайс 2

- **Решение:** Заметки агента по задаче и обсуждение задачи с ИИ живут в треде сущности — треды сущностей переносятся в слайс 1. Чат-компонент строится переиспользуемым (лента + ввод + карточки); тред сущности на detail-экране — тот же компонент, что рендерит глобальный тред, с другим `thread_id` и включённым контекст-якорем. Agenda-lite остаётся в слайсе 2: она дёшева, но её ценность держится на recurring-инстансах, которые приходят вместе с ней.
- **Статус:** принято 2026-07-02
- **Обоснование:** агентная петля (D5) требует места для переписки владелец↔агент по конкретной задаче с первого слайса; Agenda-lite без recurring-инстансов малоценна, переносить её раньше времени незачем.
- **Заменяет:** прежний порядок слайсов спеки v3 (треды сущностей позже Agenda-lite)
- **Детали:** 02-core-os §2.2

### D10. Консолидация источников истины

- **Решение:** `docs/implementation_old/00-decision-ledger.md`, объявивший себя source of truth и конфликтовавший с PRD, получает шапку «superseded»; `docs/implementation_old/` целиком помечается архивом. Создаётся компактный `docs/prd/04-decision-log.md` (этот документ) — единственный действующий журнал решений: D1–D11 плюс carried-решения леджера.
- **Статус:** принято 2026-07-02
- **Обоснование:** два конкурирующих source of truth (леджер и PRD) создают риск рассинхронизации при любой будущей правке; один документ с явным статусом каждого решения устраняет двусмысленность.
- **Заменяет:** `docs/implementation_old/00-decision-ledger.md` как source of truth
- **Детали:** этот файл (04-decision-log.md)

### D11. Multi-user: граница без инфраструктуры

- **Решение:** Схема остаётся per-owner; workspace'ы, шаринг и роли — Future (владелец подтвердил: реализуем обязательно, но позже). Каждое решение MVP обязано сохранять границу — workspace-ready чек-лист, все пять пунктов: (1) нейминг `owner_id` / `actor_user_id` — двусмысленный `user_id` запрещён; (2) identity течёт только через request-контекст, бизнес-логика нигде не предполагает «единственного пользователя системы»; (3) RLS-политики генерируются из одного шаблона — будущий переход owner→membership правится в одном месте; (4) детерминированные uuidv5-формулы, включающие `user_id` (глобальный тред, entity-треды), помечаются «workspace-scoped при введении workspace'ов»; (5) entitlements-резолвер принимает субъекта параметром.
- **Статус:** принято 2026-07-02
- **Обоснование:** принцип границы — формулировка леджера: «Deferral means implementation must preserve the boundary, not add placeholder infrastructure» — откладывать инфраструктуру можно, но не ценой архитектуры, которую потом придётся переписывать. Отвергнутые альтернативы: `workspace_id` с первого дня (налог на каждый инвариант/тест/спайк при нулевой сегодняшней ценности); полные роли в MVP (та же преждевременная платформенность, что породила всю переработку, §1 спеки).
- **Заменяет:** расширяет AUTH-04 леджера (общий тезис «будущий sharing не меняет владение» без чек-листа) в явный workspace-ready чек-лист
- **Детали:** 01-architecture §4.10, §5.4

### D12. Хостинг и регион (итог фазы 0)

- **Решение:** Supabase Free, регион **eu-central-1 (Франкфурт)** — выбран владельцем без замера; Data API проекта отключён (один путь мутаций, 01-architecture §9.1). API-хостинг — **Render free (Frankfurt)**, Docker-деплой Blueprint'ом из GitHub; принятый компромисс free-тарифа: сон через 15 мин простоя, cold start ~1 мин (polling агентной петли держит сервис тёплым; путь апгрейда — Render Starter $7/мес или Fly.io ~$2.24/мес). Статика PWA — решится в Слайсе 1 (кандидат — Cloudflare Pages). Подключение к БД — только через Supavisor `aws-1-eu-central-1`: session `:5432` для персистентного пула API; transaction `:6543` требует `prepare:false`. Прямое подключение `db.<ref>.supabase.co` — IPv6-only, не используется.
- **Статус:** принято 2026-07-03
- **Обоснование:** матрица провайдеров по фактам 07.2026 (Koyeb закрыт для новых, Fly.io без free, Railway без Франкфурта и с недостаточным free-кредитом, Cloud Run троттлит idle-пул) — Render единственный «free + без карты + Франкфурт + открытый egress». Прод-проверки: латентность API↔DB 3.9–4.2 мс (co-location), RLS-механика подтверждена с хостинга.
- **Заменяет:** конкретизирует carried DEPLOY-03/04 леджера (минус PowerSync Cloud)
- **Детали:** docs/implementation/01-phase0-findings.md; матрица — spikes/spike-05-deploy/README.md

## Решения уборочной фазы (2026-07-29)

Каждое меняет наблюдаемое поведение продукта, поэтому фиксируется здесь, а не только

### D13. Формат memory-правила: пишем канон, читаем и суррогаты

- **Решение:** заголовок правила записывается всегда со стрелкой U+2192 («`паттерн` → `категория`»), но разбор дополнительно принимает клавиатурные суррогаты `->`, `-->`, `=>`. Нераспознанный заголовок правилом не считается и помечается в UI (detail и список «Память AI»).
- **Статус:** принято 2026-07-29 (владелец подтвердил 2026-07-31)
- **Обоснование:** источников заголовка два, и оба не могут дать U+2192 — рука владельца (правка памяти есть обычная правка сущности, 02-core-os §2.7; стрелку с клавиатуры не набрать) и модель, которой формат нигде не предписан. Асимметрия цены: до решения такое правило было мертво во всех детерминированных путях (fast-path, резолв импорта, гейт эскалации) и одновременно живо в слое 2 контекста — то есть AI перечислял его как работающее. Принятая цена: правила с суррогатами, лежащие в графе, оживают после релиза без действия владельца и начинают влиять на категоризацию.
- **Заменяет:** решение K19.4 фазы D в части «суррогаты не принимаются» (запрет был запиннен тестом; тест отменён осознанно)
- **Детали:** 01-architecture §7.8

### D14. Повторность исправлений считается по действиям, но путь подтверждения эскалирует

- **Решение:** три одинаковых исправления внутри одного batch — одно намерение, а не три повтора (§7.8 «после двух одинаковых исправлений» читается по действиям журнала). При этом групповая мутация, ушедшая на явное подтверждение по размеру batch (§7.10), после одобрения эскалацию **запускает**. Путь `source='mcp'` эскалацию по-прежнему не запускает.
- **Статус:** принято 2026-07-29 (владелец подтвердил 2026-07-31)
- **Обоснование:** «система учится на повторных исправлениях» — про повтор во времени, а не про размер выделения; иначе одна групповая правка порождала бы правило. Обратная сторона: до решения батч из 11+ операций не эскалировал никогда, хотя «перенеси все 12 покупок в Пятёрочке из Еды в Развлечения» — самый естественный способ групповой рекатегоризации. Внешний агент не «исправляет свою категоризацию», он выполняет поручение, поэтому MCP исключён.
- **Заменяет:** уточняет §7.8 (прежняя формулировка о повторности допускала оба прочтения)
- **Детали:** 01-architecture §7.8, §7.10

### D15. Сопоставление правила — по границе токенов

- **Решение:** паттерн правила ищется во вводе как непрерывная последовательность токенов, а не как подстрока; критерий един для fast-path и для резолва строк CSV-выписки.
- **Статус:** принято 2026-07-29 (владелец подтвердил 2026-07-31)
- **Обоснование:** подстрочное сравнение делало канонический пример спеки вредным: «бар → Развлечения» перехватывал «барбершоп», то есть правило активно портило категоризацию вместо улучшения; соседняя ступень той же категоризации (резолв по алиасам) всегда сравнивала по целому слову. Принятая цена: правила, работавшие за счёт склеек («wildberries» в «WILDBERRIESRU»), перестают срабатывать — молча, сигнала владельцу нет (записано в бэклог фазы).
- **Заменяет:** прежнее (неявное) подстрочное сопоставление
- **Детали:** 01-architecture §7.5

### D16. `CONFLICT` в retry-буфере — «id непригоден», и повтор идёт детерминированной производной

- **Решение:** `CONFLICT` перестаёт означать «идемпотентный успех». Буфер и онлайн-путь быстрого ввода делают один повтор с id, детерминированно выведенным из исходного (`uuidv5`), и только второй `CONFLICT` подряд считают окончательным отказом. Карточка в ленте переписывается на id фактически созданной записи.
- **Статус:** принято 2026-07-29 (владелец подтвердил 2026-07-31)
- **Обоснование:** семантика сервера прямо противоположна прежней клиентской конвенции: честный повтор владельца с тем же UUID исполнитель отдаёт replay-успехом, а `CONFLICT` кидает ровно тогда, когда id занят строкой, невидимой владельцу под RLS, — то есть записи владельца нет, и успех фабриковался на пустом месте (карточка «⚡ без AI» вела на чужую сущность, «Разобрать с AI» архивировал бы её). Производная, а не случайный id: иначе потерянный ответ на повтор оставлял в очереди прежний payload, следующая досылка снова получала `CONFLICT` и брала ЕЩЁ один id — вторая сущность на один ввод.
- **Заменяет:** конвенцию «CONFLICT = confirmed» клиентского retry-буфера (бэклоги слайса 1 и фазы B)
- **Детали:** 01-architecture §5.3

### D17. Валюта импорта — свойство выписки; сводка импорта — запись журнала

- **Решение:** (а) валюта задаётся один раз на выписку на шаге маппинга (дефолт — валюта владельца, свободный трёхбуквенный код) и пишется в аспект каждой созданной транзакции явно; смешанная выписка остаётся вне скоупа (multi-currency — Future). (б) каждый `import.confirm` пишет в журнал системную сводку (строк выписки / создано / привязано к ручным записям / уже было) — включая случай «выписка известна целиком», когда импортировать нечего.
- **Статус:** принято 2026-07-29 (владелец подтвердил 2026-07-31)
- **Обоснование:** (а) пробел спеки: выписка в чужой валюте молча ложилась в валюту владельца, и исправить это можно было только вручную по каждой строке; принятая цена — валютные транзакции честно остаются Unbudgeted, пока нет конверта в их валюте (§2.3 сравнивает комбинацию точно). (б) метрика покрытия транзакций (00-product §8) объявлена с 2026-07-02, но считать её было нечем: строки выписки, которые Orbis уже знал, не оставляют в графе никакого следа — сущностей по ним не создаётся. Принятая цена: раз в неделю в ленте чата появляется служебная строка, и она уходит в контекст модели.
- **Заменяет:** умолчание «валюта импортируемой транзакции = валюта владельца» (03-budget §5); объявление метрики §8 без механизма измерения
- **Детали:** 03-budget §5, 00-product §8

## Решения слайса 3 (2026-07-31)

Решения приняты владельцем при утверждении спеки слайса 3
(`docs/superpowers/specs/2026-07-31-slice3-polish-depth-design.md` §3) и переносятся сюда
по мере того, как соответствующая фаза становится фактом продукта. Каждое меняет
наблюдаемое поведение, поэтому фиксируется здесь, а не только в спеке; что осознанно НЕ
чинилось в фазе — в бэклоге этой фазы (`docs/superpowers/reviews/`).

### D18. Back идёт по фактическому пути

- **Решение:** введение URL-контракта делает историю браузера носителем навигации: back снимает верхний push-экран активной вкладки, а на корне вкладки — возвращает на вкладку, с которой на неё переключились; из приложения back уводит только в конце пути. Системный жест, кнопка браузера и кнопка «Назад» в шапке — одно действие.
- **Статус:** принято 2026-07-31 (владелец подтвердил при утверждении спеки слайса 3)
- **Обоснование:** §1.2 писался как описание нативного поведения таб-навигации, но история браузера линейна, и сохранить букву правила можно только перехватом `popstate` с обратной перемоткой — приём хрупкий и дёргающий жест на телефоне. Выигрыш большой: до решения системный жест «назад» вообще не работал как back приложения, и каждый выход из detail-экрана требовал прицельного тапа по стрелке в углу. Принятая цена: на телефоне back с корня вкладки больше не сворачивает PWA сразу — сначала откатывает по пути переключений.
- **Заменяет:** правило 02-core-os §1.2 «на корне вкладки back НЕ переключает вкладки, жест отдаётся системе»
- **Детали:** 02-core-os §1.2, §1.3

### D19. Suggestion chips приходят маркером в ответе модели

- **Решение:** системный промпт предписывает завершать ответ служебной строкой с 2–4 продолжениями; сервер вырезает её из текста и кладёт в `metadata.suggestions` assistant-сообщения. Второго вызова LLM нет. Маркер отсутствует или разобран не полностью — чипов у этого ответа просто нет, а текст остаётся чистым.
- **Статус:** принято 2026-07-31 (владелец подтвердил при утверждении спеки слайса 3)
- **Обоснование:** альтернативы (отдельный тул `suggest_followups`, второй дешёвый вызов) добавляют раунд на каждое сообщение чата — задержку, деньги и второй источник сбоев — ради необязательного украшения. Деградация без чипов невидима и безопасна, поэтому строгий контракт здесь не окупается. Принятая цена: доля ответов останется без чипов; поведение модели пиннится тестом промпта, но не гарантируется.
- **Заменяет:** уточняет 02-core-os §2.4, который до решения не фиксировал источник чипов вовсе
- **Детали:** 02-core-os §2.4, 01-architecture §7

### D20. Recurring-шаблоны прячутся, а не запрещаются

- **Решение:** шаблон с `occurred_on` остаётся валидным состоянием; сокрытие обеспечивается клиентским фильтром в списках транзакций и серверными регресс-тестами «шаблон не входит ни в один агрегат». Жёсткий инвариант в `assertFinancialInvariant` отклонён.
- **Статус:** принято 2026-07-31 (владелец подтвердил при утверждении спеки слайса 3)
- **Обоснование:** запрет ломает поддержанный флоу «Сделать повторяющейся» (конверсия транзакции с `occurred_on` в шаблон) и требует продуктового решения о судьбе исходной транзакции — это отдельная работа, а не механическая правка. Практическая дыра (шаблон посчитан как факт) закрывается сторожем полностью. Принятая цена: состояние остаётся выразимым, и защита держится на тесте, а не на инварианте БД.
- **Заменяет:** отклоняет предложенный инвариант «шаблон не имеет `occurred_on`» в `assertFinancialInvariant` (03-budget §2.8)
- **Детали:** 03-budget §2.8, §7 п. 8; 01-architecture §3.3

### D21. Перф-бюджеты: сервер — гейт в CI, клиент — чек-лист перед релизом

- **Решение:** серверные операции получают пороги, проверяемые автотестом на засеянном объёме данных; превышение роняет CI. Клиентские метрики §8 (time-to-log, первая отрисовка на телефоне) измеряются вручную по чек-листу в runbook перед релизом. Пороги задаются с запасом кратно текущим замерам, измеренные числа печатаются в лог всегда — в том числе на зелёном прогоне.
- **Статус:** принято 2026-07-31 (владелец подтвердил при утверждении спеки слайса 3)
- **Обоснование:** headless-замер клиента в CI даёт цифры раннера, а не телефона, и склонен флейкать — то есть гейт, которому не верят. Серверная часть, наоборот, детерминирована и ловит именно то, что ломается на практике (потерянный индекс, N+1): в уборочной фазе регрессию backlinks 15.6→5.6 мс меряли руками. Принятая цена: клиентская деградация между релизами автоматикой не ловится — её видно только на замере перед выкаткой.
- **Заменяет:** конкретизирует carried-решение «Перф-бюджеты» (ниже), которое объявляло перф-бюджеты гейтами релиза в слайсе 3, не разделяя сервер и клиент
- **Детали:** 00-product §8, 02-core-os §9 п. 1, `docs/implementation/02-ops-runbook.md` §8

### D22. `orbis/goal` без собственного view; горизонты — сценарии поверх существующего

- **Решение:** аспект `orbis/goal` с `progress_source` даёт серверный расчёт прогресса и представление на detail-экране (карточка аспекта с прогресс-баром) и в списках (generic-строка §3.6). Отдельного экрана/вкладки «Цели» в слайсе 3 нет. Горизонты планирования (день/неделя/месяц/год/жизнь) доставляются сидированными smart lists на существующей грамматике и AI-сценариями в системном промпте.
- **Статус:** принято 2026-07-31 (владелец подтвердил при утверждении спеки слайса 3); **исполнено с двумя отступлениями**, оформленными решениями D23 и D24 — их владелец ещё не подтверждал
- **Обоснование:** механизм 01-architecture §11.3 проектировался так, чтобы новый домен = запись в реестре + view; ценность даёт именно расчёт прогресса из графа, а не ещё один экран. Отдельный view сопоставим по объёму с фазой Budget UI и в «полировку» не помещается. Принятая цена: цели живут в Browser и на detail-экранах, сводного экрана целей нет (кандидат в Future).
- **Заменяет:** уточняет 01-architecture §11.3 (механизм был описан как проверка масштабируемости на бумаге, теперь это реализация) и границу целей в 00-product §9
- **Детали:** 01-architecture §3.11, §11.3; 02-core-os §3.5, §3.6, §3.3

Формулировка выше сохранена в том виде, в котором решение принималось, — переписывать её задним числом значило бы спрятать расхождение. Два куска решения фактом не стали, и каждый превратился в отдельное решение фазы:

- «представление … **и в списках (generic-строка §3.6)**» — не сделано; см. **D23**;
- «горизонты **(день/неделя/месяц/год/жизнь) доставляются сидированными smart lists**» — сделано частично; см. **D24**.

### D23. Прогресс цели живёт только на detail-экране

- **Решение:** сущность с `orbis/goal` в строках списков остаётся обычной строкой с заголовком; прогресс-бар показывается только на detail-экране. Часть D22 про представление «в списках (generic-строка §3.6)» в слайсе 3 не исполняется.
- **Статус:** принято 2026-08-05 контроллером фазы E в отсутствие владельца — **ждёт валидации владельцем**
- **Обоснование:** обе опоры этой части D22 оказались не на месте. Generic-строка §3.6 не реализована ни в одном списке — это открытый долг слайса 1, и «цели показываются generic-строкой» означало бы сначала построить generic-строку целиком, то есть работу другой фазы. Второе: прогресс не читается из поля, а считается обходом графа. Измерено на `entity.get`: цель стоит 10 запросов против 6 у обычной сущности — четыре лишних НА СУЩНОСТЬ. Числа не на слово: их пиннит тест `apps/server/src/goals/progress.test.ts` («обычная сущность не платит за расчёт цели ни одним запросом») — он считает запросы на уровне драйвера, поэтому подорожавшее чтение уронит его, а не тихо разойдётся с этой записью. Списки, которые идут через `entity.query`, этой цены сегодня не платят вовсе — прогресс там не считается, — а платили бы линейно по числу строк-целей: экран из 50 целей — плюс 200 запросов, при том что перф-гейт D21 меряет `entity.query` списком ровно на 50. Оговорка, без которой довод был бы шире факта: места, читающие сущности **по одной** через `entity.get` — строки карточки `query_result` в чате, подзадачи, блокировки, закреплённое в сайдбаре, — четыре лишних запроса на цель платят уже сегодня; карточка чата, перечисляющая N целей (а её порождает как раз новый сценарий промпта «как идут цели»), стоит N×10 запросов вместо N×6. Блокером это не считаем — путь N+1 там предсуществующий и выборка ограничена лимитом, — но цена решения на эту величину меньше, чем звучало бы без оговорки. Принятая цена: список «Год» показывает цели без чисел, и чтобы увидеть прогресс, цель надо открыть.
- **Заменяет:** часть D22 «представление … и в списках (generic-строка §3.6)»
- **Детали:** 02-core-os §3.6, §3.5 п. 4; 01-architecture §11.3

### D24. Лестница горизонтов доставляется тем, чего в ней не хватает

- **Решение:** сидируются два новых smart list — «Год» (цели) и «Жизнь» (вопросы ревизии); отдельных сущностей «День», «Неделя», «Месяц» не создаётся. День закрывает существующий Daily Planning, неделю и месяц — существующий Upcoming (его тело так и озаглавлено: «Горизонт планирования: неделя и дальше»). Само отображение лестницы на списки не подразумевается, а сказано словами — в теле «Года», в 02-core-os §3.3 и в системном промпте. В сайдбаре закрепляется «Год»; «Жизнь» находится в Browser по тегу `smart-list`.
- **Статус:** принято 2026-08-05 контроллером фазы E в отсутствие владельца — **ждёт валидации владельцем**
- **Обоснование:** пять новых списков означали бы, что три из них отличаются от уже существующих блоков одним лишь параметром `title=` (у «Недели» — дословно им; `display=` виджет сегодня не читает вовсе, 02-core-os §3.4), то есть добавляли бы в продукт сущности с нулевой информационной дельтой и второе имя для той же выборки: сайдбар получил бы два пункта про сегодня и два про неделю. Грамматика при этом всё равно не выражает ни года, ни жизни — относительных date-токенов в ней ровно четыре, а абсолютные даты в сиде протухли бы через неделю после деплоя; значит верхние два горизонта в любом раскладе держатся не датами, и именно их не хватало. Принятая цена: лестница перестала быть механически видимой (пять списков — пять строк сайдбара) и держится на словах в телах списков и в промпте; читатель, который их не откроет, соответствия «неделя → Upcoming» не увидит.
- **Заменяет:** часть D22 «горизонты (день/неделя/месяц/год/жизнь) доставляются сидированными smart lists» и §4 спеки слайса 3, где перечислены пять сидируемых списков
- **Детали:** 02-core-os §3.3, §7.2; 00-product §9

## Решения второго LLM-провайдера (2026-08-06, дополнено 2026-08-08)

### D25. Второй LLM-провайдер: OpenAI поверх общего слоя AI SDK

- **Решение:** рядом с Anthropic встаёт второй боевой провайдер — OpenAI. Провайдеро-независимая механика Vercel AI SDK (маппинг результата и стоп-причины, конвертация tool defs, таймаут шага, один шаг `generateText`) вынесена в общий слой `llm/ai-sdk.ts`; оба провайдера — тонкие обёртки над ним. Выбор — env `ORBIS_LLM_PROVIDER`; в `render.yaml` задан `openai`.
- **Статус:** принято 2026-08-06 контроллером в отсутствие владельца; **подтверждено владельцем 2026-08-08**
- **Обоснование:** на счёте Anthropic нет средств, и путь модели в проде не деградировал, а мёртв целиком — второй провайдер тут не про архитектурную красоту, а про работающий продукт. Расслоение выбрано вместо второй копии кода потому, что `anthropic.ts` уже был построен на AI SDK: собственно anthropic-знания в нём — какой клиент создать, как называется модель по умолчанию, каким транспортом ходить, — на десяток строк, всё остальное одинаково для любого провайдера SDK. Принятая цена: у AI-слоя стало на уровень больше, и ошибка в общем слое ломает обоих провайдеров сразу, а не одного.
- **Заменяет:** формулировку 01-architecture §7.7 «стриминг и мульти-провайдерность … это **шов**, оставленный для будущего … провайдер один (Claude)» — в части мульти-провайдерности шов стал реализацией (швом остаётся только стриминг)
- **Детали:** 01-architecture §7.7, §1.1; `apps/server/src/llm/ai-sdk.ts`, `openai.ts`, `anthropic.ts`

### D26. Транспорт OpenAI — только Chat Completions; strict-режим не включается

- **Решение:** OpenAI-провайдер ходит `createOpenAI(...).chat(modelId)` — Chat Completions, — а не голым `createOpenAI(...)(modelId)`, то есть не в Responses API, куда `@ai-sdk/openai` ходит по умолчанию. Strict-режим структурированного вывода не включается ни на каком транспорте.
- **Статус:** принято 2026-08-06 контроллером в отсутствие владельца; **ОТМЕНЕНО 2026-08-08** — владелец оспорил решение, проба его опровергла, замена — **D29**
- **Обоснование:** Responses API отвергает схемы двух тулов реестра (`attach_orbis_financial`, `attach_orbis_goal`) при любой строгости — дословно «`Invalid JSON schema: regex lookaround is not supported`»: негативный lookahead стоит в `positiveDecimal` (`packages/shared/src/schemas/aspects.ts`) у `orbis/financial.amount` и `orbis/goal.target_value`. Два тула из девятнадцати — это все финансы и все цели. Отказ безусловен: `strictJsonSchema: false` его не снимает, это свойство эндпоинта, а не настройки строгости. Strict отдельно: потульный прогон дал 6 из 19 — он потребовал бы объявить обязательным всё необязательное, то есть менять схемы аспектов и пересевать реестр на проде, и не дал бы ничего, потому что вход тула всё равно валидирует ajv по реестру. Обе части доказаны пробой, а не рассуждением. Принятая цена: возможности Responses API нам недоступны, и выбор транспорта компилятор не стережёт (`SdkModel` принимает оба) — его держит тест на подмену `.chat()` голым вызовом.
- **Заменяет:** ничего из прежних решений — ограничение новое, порождено внешним поведением OpenAI
- **Детали:** `docs/superpowers/reviews/2026-08-06-openai-probe.md` §1.2 (матрица «транспорт × строгость») и §1.4 (почему не strict); 01-architecture §7.7; `apps/server/src/llm/openai.ts`

Формулировка выше сохранена в том виде, в котором решение принималось, — переписывать её задним числом значило бы спрятать расхождение. Центральное её утверждение («Responses API отвергает наши схемы при ЛЮБОЙ строгости») **неверно**: оно шире того, что было измерено. Что именно было измерено, где ошибка обобщения и что стоит вместо D26 — в **D29**. Уцелела ровно одна часть D26 — «strict-режим не включается»: она подтверждена и повторена в D29.

### D27. Имя модели для метеринга отдаёт провайдер

- **Решение:** `LLMProvider` объявляет `readonly modelId`, и `ai_usage` метится этим значением; `makeAiDeps` берёт имя у провайдера вместо того, чтобы вычислять его из env.
- **Статус:** принято 2026-08-06 контроллером в отсутствие владельца; **подтверждено владельцем 2026-08-08**
- **Обоснование:** прежняя формула `ORBIS_LLM_MODEL || DEFAULT_ANTHROPIC_MODEL` верна ровно до тех пор, пока провайдер один. С OpenAI и незаданной `ORBIS_LLM_MODEL` в `ai_usage` уезжало бы `claude-sonnet-5` — счётчик расхода врал бы про модель молча, и задним числом такие записи неисправимы: настоящего имени в них просто нет. Принятая цена: правка интерфейса `LLMProvider` и всех четырёх его реализаций (боевые получают `modelId` наследованием от `AiSdkProvider`, `Echo` и `Scripted` — полем).
- **Заменяет:** уточняет 01-architecture §7.7 «имя модели … это конфиг»: конфиг по-прежнему выбирает модель, но метеринг читает её имя у провайдера, а не пересчитывает по той же env со своим дефолтом
- **Детали:** 01-architecture §7.7, §4.7; `apps/server/src/ai/send-message.ts`, `apps/server/src/llm/ai-sdk.ts`

### D28. Неоднозначный выбор провайдера — отказ при старте

- **Решение:** если в env заданы оба ключа, а `ORBIS_LLM_PROVIDER` не задан, фабрика бросает ошибку при создании — процесс не поднимается. Один ключ без явной переменной по-прежнему выбирает свой провайдер; ключей нет — `echo` в dev и отказ в production.
- **Статус:** принято 2026-08-06 контроллером в отсутствие владельца; **подтверждено владельцем 2026-08-08**
- **Обоснование:** доктрина `llm/provider.ts` уже запрещала неявный `echo` в production по тому же принципу — молча отвечать не тем, чего ждут, хуже, чем не подняться. Неоднозначность двух живых ключей хуже вдвойне: ответы будут настоящие, поэтому дефект не виден вовсе, а расход уедет на чужую модель и чужой счёт — заметят по счёту, а не по логу. Разрешать выбор порядком веток в файле значило бы закрепить случайность реализации как контракт. Принятая цена: стенд, где по любой причине лежат оба ключа (например, разработчик не убрал старый), без явной `ORBIS_LLM_PROVIDER` не поднимется вовсе.
- **Заменяет:** ничего из прежних решений — расширяет правило «неявный echo в production запрещён» на вторую неоднозначность, появившуюся вместе со вторым провайдером
- **Детали:** 01-architecture §7.7; `apps/server/src/llm/provider.ts`; `apps/server/.env.example`, `render.yaml`, `docs/implementation/02-ops-runbook.md` §2

### D29. Транспорт OpenAI — Responses API с явным `strict: false` на тулах и `store: false`

- **Решение:** OpenAI-провайдер ходит голым `createOpenAI(...)(modelId)` — то есть в **Responses API**, транспорт `@ai-sdk/openai` по умолчанию и тот, который OpenAI рекомендует новому коду. Каждый тул запроса несёт `strict: false`, а в `providerOptions.openai` задан `store: false`. Схемы аспектов не меняются. Strict-режим структурированного вывода по-прежнему не включается — эта часть D26 подтверждена и остаётся в силе.
- **Статус:** принято 2026-08-08 владельцем — он же оспорил D26
- **Обоснование:** три вещи, по порядку. **(а) Чем на самом деле управляет `strictJsonSchema` — и почему прежний вывод был ошибкой обобщения.** Этот переключатель — единственный рычаг, который проверялся при D26, — кормит только `response_format` (`@ai-sdk/openai@4.0.31/dist/index.js:1025` на chat, `:6583` на responses) и к тулам не относится ни на одном транспорте. Строгость тула берётся из поля самого тула и уходит в запрос **условно**: `...tool.strict != null ? { strict: tool.strict } : {}` (`:906` chat, `:6275` responses) — не задан, значит не отправлен, и дальше решает дефолт эндпоинта: `/v1/chat/completions` нестрогий, `/v1/responses` строгий. То, что D26 назвала свойством эндпоинта, было свойством **чужого умолчания**, которое мы молча приняли. Ошибка методическая: получив отказ на одном рычаге, контроллер обобщил его на «любую строгость», не проверив второй. Проба круга 6 (`.superpowers/probe/responses-strict.ts`) обобщение опровергла: сырой `/v1/responses` со всеми 19 тулами реестра отдаёт 400 при непереданном `strict`, **200 при `strict: false`** и 400 при `strict: true`; через SDK тул без `strict` — 400, `strict: false` полем тула — **принято**, `providerOptions.openai.strict` — 400 (не тот рычаг). Приняты все 19 тулов, включая оба поля с lookahead-паттерном (`orbis/financial.amount`, `orbis/goal.target_value`) и единственный в реестре `anyOf` (`orbis/goal.progress_source`) — про союз, впрочем, доказано только то, что он **принят**: причиной отказа он не был никогда. И самое неприятное здесь не то, что круг 6 нашёл новое, а то, что **находить было нечего: опровержение лежало в собственной таблице первого отчёта**. Строка `responses | false | HTTP 200, принято` в §1.2 `docs/superpowers/reviews/2026-08-06-openai-probe.md` — прямое измерение, противоречащее выводу «отвергает при любой строгости», — была напечатана в том же документе, на котором D26 и стояла. Её не проверили, а **объяснили**: в §1.3 под неё подведена выдуманная теория, будто SDK «приводит схемы к своему виду» и оттого срабатывает валидатор регекспов. Такого механизма нет — расхождение давало ровно то, что сырая проба слала `strict: false` явно, а SDK не слал ничего. Поэтому методическая ошибка двойная: проверен один рычаг из двух, а измерение, которое об этом кричало, лежало под рукой и было закрыто догадкой вместо прогона, стоившего одного запуска скрипта. **(б) `strict: false` теперь задан явно, и это лучше прежнего молчания.** Прежняя конфигурация строгость не задавала вовсе и жила на дефолте `/v1/chat/completions` — на умолчании, которое OpenAI вправе поменять и о котором в коде не было ни слова. Теперь значение написано в запросе буквально; путь типобезопасен без единого каста (`ai` реэкспортирует `tool`/`Tool`/`ToolSet` из `@ai-sdk/provider-utils`, где `strict?: boolean` объявлен, `index.d.ts:1759`), а держит его тест, читающий **тело HTTP-запроса** (`apps/server/src/llm/openai.test.ts`): пропажа `strict: false` краснеет офлайн, а не 400-м в проде на всех финансах и всех целях. **(в) `store: false` обязателен для приложения с личными финансами.** На Responses SDK по умолчанию ставит `store: true` (`index.js:6533`) — OpenAI сохраняет запрос вместе с ответом у себя; на Chat Completions такого дефолта не было, поэтому смена транспорта **без этой строки молча включила бы хранение**. Через чат Orbis идут банковские выписки, суммы и личные заметки — оставлять их на стороне провайдера мы не согласились; пин смотрит в тело запроса ровно потому, что тут важно перебить чужой дефолт, а не записать `false` где-то у себя. Принятая цена: выигрыша от Responses сегодня нет — `LLMProvider.chat()` одношаговый и без состояния, а результаты тулов возвращаются модели текстом (`[tool_result:<тул>] <JSON>` — ограничение MVP плана 1b), поэтому перенос рассуждений между шагами через `previous_response_id` потребовал бы правки самого интерфейса; мы платим за смену транспорта двумя строками настроек и одним классом рисков (чужие дефолты вроде `store`) ради того, чтобы стоять на рекомендованном эндпоинте, а не ради возможностей, которыми пока некому пользоваться.
- **Заменяет:** отменяет **D26** в обеих транспортных частях — «только Chat Completions» и «отказ Responses безусловен»; часть D26 «strict-режим не включается» сохраняется и повторена в решении выше. Переписывает абзац про транспорт в 01-architecture §7.7.
- **Детали:** `apps/server/src/llm/openai.ts` (оба «почему» в комментариях), `apps/server/src/llm/openai.test.ts` (три пина: транспорт, `strict: false`, `store: false`); `docs/superpowers/reviews/2026-08-06-openai-probe.md` §1.2 (врезка круга 6); 01-architecture §7.7. Живой гейт `scripts/llm-smoke.ts` шлёт настоящий реестр и печатает, что именно проверено, — число тулов (19, из них 8 `attach_*`) и стоп-причину.

### D30. Разворот списка у агрегатной карточки снят, а не спрятан

- **Решение:** у `query_result` с агрегатом действия «показать список» больше нет: сняты состояние `open`, кнопка и её `<ul>`. Не «показывать только при непустом `entityIds`», а удалить механизм целиком — вместе с видимой пользователю кнопкой. Вместо кода в карточке остался докблок с фактом и условием возврата.
- **Статус:** принято 2026-08-08 контроллером в отсутствие владельца, ждёт валидации
- **Обоснование:** разворот был недостижим **ни при какой серверной выдаче**. Единственный производитель агрегатной карточки — `aggregateCard` (`apps/server/src/tools/dispatch.ts`) — ставит `entityIds: []` **литералом** с первого коммита: агрегат id не выбирает по замыслу, список приезжает отдельным `entity_query`. То есть кнопка либо разворачивала пустоту, либо (по первоначальному плану Р4 — «прятать под условием `entityIds.length > 0`») не отрисовывалась бы никогда. Прятать было **хуже**, чем снимать: условие оставило бы мёртвую ветку рендера — код, который нельзя ни увидеть, ни проверить тестом на настоящей фикстуре, но который читается как рабочий и просит сопровождения. У проекта на это записанная политика в самом коде карточек (`apps/web/src/features/chat/cards/types.ts`: «мёртвая ветка рендера уже стоила фикс-раунда фазе C» — там же два типа карточек намеренно объявлены без компонентов), и платить второй раз за ту же ошибку контроллер не стал. **Принятая цена, названная прямо:** снято действие, обещанное контрактом §2.3 `02-core-os.md` и `design-brief.md` — то есть обещание пользователю живёт дальше самой кнопки. Если сервер когда-нибудь начнёт отдавать `entityIds` вместе с агрегатом, разворот придётся возвращать **осознанно** — вместе с тестом на непустой список, который сегодня написать не на чем. Вторая часть цены — тест карточки держит отрицательную ассерцию на **намеренно невозможной** фикстуре (агрегат + непустой `entityIds`): только она отличает «снято» от «спрятано за условием», но такой фикстуры сервер не пришлёт никогда, и читать её надо именно так.
- **Заменяет:** отменяет решение Р4 спеки (`docs/superpowers/specs/2026-08-08-empty-cards-and-auth-diet-design.md`) — «показывать кнопку только при непустом `entityIds`». Контракт §2.3 `02-core-os.md` и `design-brief.md:124` **не заменяет и не сужает**: там описано целевое поведение, оно остаётся в силе (Р14). Приводит к факту описание в блоке «ещё не реализовано» `02-core-os.md` §2.3.
- **Детали:** Р11 и Р14 спеки `docs/superpowers/specs/2026-08-08-empty-cards-and-auth-diet-design.md`; `apps/web/src/features/chat/cards/QueryResultCard.tsx` (докблок с фактом и условием возврата), `apps/web/src/features/chat/cards/cards.test.tsx`; производитель — `aggregateCard` в `apps/server/src/tools/dispatch.ts`

## Решения фильтра по полю-массиву (2026-08-09)

### D31. Тип поля в грамматике перестаёт быть эвристикой над строкой: массив фильтруется вхождением, объект/union отвергается

- **Решение:** каталог полей (`packages/shared/src/query/catalog.ts`) получает два новых типа. **Массив скаляров** (`orbis/category.aliases`) фильтруется containment'ом `aspects @> jsonb_build_object(аспект, jsonb_build_object(поле, jsonb_build_array(значение)))` — `=` означает для него «содержит», `|` — «содержит любое из», `!` — «не содержит» (сущности без аспекта проходят). **Нефильтруемое** поле — объект (`orbis/schedule.recurrence`), разнотипный union (`orbis/goal.progress_source`), массив не-скаляров — отвергается парсером с позицией ключа, одинаково для равенства, отрицания, диапазона и `>`/`<`. Сортировка запрещена по обоим типам. Грамматика §6.1 получает конструкцию «вхождение в поле-массив», §6.4 — четвёртый класс отказа парсинга.
- **Статус:** принято 2026-08-09 контроллером — владелец делегировал ему решения по этой работе; главный гейт (живой смоук настоящей моделью) пройден; **ждёт валидации владельцем**, как и D30
- **Обоснование:** каталог возвращал для `array` и `object` финальный `'string'` с комментарием «фильтрация по ним грамматикой не определена». Комментарий был неверен: фильтрация была определена и работала **неправильно**. `aliases=такси` компилировалось в `aspects->'orbis/category'->>'aliases' IN ($1)`, где левая часть — текст **всего** массива, поэтому равенство не выполнялось никогда (тихий ноль), а `aliases=!такси` матчило **все 12** категорий — то есть активно неверный ответ, а не пустой. Починка текстом инструкции («тяни все категории и выбирай сама») была отклонена трижды: она требует пересева реестра на проде (`ai_instructions` читаются из `aspect_definitions` на каждый запрос, а код едет на Render автоматически — возникает окно рассинхрона), платит полным payload'ом 12 категорий и лишним round-trip'ом на каждом ходу, и **не чинит активный баг отрицания**. Механика же не требует пересева вовсе: она делает уже задеплоенную инструкцию `orbis/financial` («резолви по aliases категорий через `entity_query`») истинной, не меняя в ней ни символа, и JSON Schema аспектов не трогает — `diffBuiltinAspects` чист, `/health` не краснеет. Форма предиката выбрана не по вкусу: путь строится **заново от корня** `aspects`, потому что GIN-индексом `entities_aspects_gin` покрыт только containment по самой колонке — подпутевые формы (`aspects->'A'->'f' ? $1`, `aspects->'A'->'f' @> '[…]'`) дают Seq Scan даже при `enable_seqscan=off` (проверено EXPLAIN на живой базе). **Принятая цена, названная прямо:** (а) сохранённые query-блоки с `recurrence=`/`progress_source=` теперь рендерятся ошибкой вместо списка — раньше они показывали мусор, но показывали; локально таких блоков ноль, на проде проверяется грепом по `body` перед выкатом; (б) отрицание по массиву индекс снимает и остаётся seq-scan'ом — сознательно, отрицание редко и обычно стоит рядом с сужающим условием; (в) сравнение **регистрозависимое**: `aliases=Такси` не найдёт `такси`, и модель, «причесавшая» ввод пользователя, получит пустую выдачу без подсказки почему — нормализация регистра внутри containment требует функционального GIN-индекса, то есть новой миграции, и вынесена в бэклог, а до тех пор про регистр сказано в описании тула `entity_query`; (г) класс отказа теперь зависит от схемы в БД: если на проде у `orbis/category.aliases` окажется схема без `items`, поле станет нефильтруемым, и запрос, которому описание тула активно учит модель, будет отвергнут — поэтому `bun scripts/ops.ts check` перед выкатом обязателен.
- **Заменяет:** ничего из прежних решений не отменяет. Расширяет §6.1 новой строкой таблицы грамматики и §6.4 — четвёртым классом ошибки парсинга; приводит к факту комментарий каталога («не определена» → «определяется здесь»).
- **Детали:** спека `docs/superpowers/specs/2026-08-09-alias-filter-design.md` (решения Р1–Р8), план `docs/superpowers/plans/2026-08-09-alias-filter.md`; `packages/shared/src/query/catalog.ts` (типы и `fieldTypeLabel`), `packages/shared/src/query/parse.ts` (`ensureFilterable`, отказ `sortBy`), `apps/server/src/query/compile.ts` (`arrayContains`, `containsEncoded`, `sortCast`), `apps/server/src/tools/registry.ts` (пример резолва по алиасу в описании `entity_query`); golden-фикстуры `apps/server/test/golden/query-sql.json` (§6.2); живой смоук — `docs/superpowers/reviews/2026-08-08-cards-auth-backlog.md`, раздел от 2026-08-09

## Решения кандидатов фазы E (2026-08-09)

### D32. Тап по индикатору буфера — ручной досыл; список с отменой остаётся долгом и меняет аффорданс

- **Решение:** индикатор «ждут отправки: N» становится кнопкой «Ждут отправки: N. Отправить сейчас», и тап по нему **досылает буфер**, а не открывает список ожидающих. Неудача досыла (ноль подтверждённых) говорит о себе строкой под индикатором. Контракт §2.6 `02-core-os.md` — «тап по индикатору → список ожидающих; каждую можно отменить до отправки» — **не отменяется и не сужается**: он остаётся невыполненным обещанием и записан долгом в §2.6, в §2.5 (ссылка «отменить можно только из списка буфера») и в `design-brief.md`. Когда список будут делать, он получит **другой аффорданс** — тап занят.
- **Статус:** принято 2026-08-09 контроллером в отсутствие владельца, ждёт валидации владельцем — как D30 и D31
- **Обоснование:** четыре вещи, по порядку. **(а) Зачем кнопка.** Индикатор был пассивной надписью, а автослив случается ровно дважды — на старте приложения и по событию `online`. Вернувшаяся сеть **без** этого события (спящий Wi-Fi, прокси, ожившее API при живом линке — во всех трёх `navigator.onLine` уже говорит «сеть есть») оставляла человека с записями, о которых сказано «ждут отправки», и без единого способа их послать, кроме перезагрузки страницы. Это тот же пользовательский вред, ради которого в бэклоге лежал таймер бэкоффа, — закрытый десятком строк и без расхождения с 01-architecture §5.3, который обещает досыл «при следующем открытии приложения с сетью», а не по расписанию. **(б) Почему именно тап.** У таблетки размером с два слова один аффорданс — нажатие; долгое нажатие на неё не обнаруживается ничем, а второй видимый элемент рядом с индикатором стоил бы постоянного места на экране ради средства, которое нужно в редкой аварии. **(в) Цена названа прямо: жест занят.** Список ожидающих с отменой каждой записи — открытый долг с приёмки слайса 1 (`docs/superpowers/plans/2026-07-05-slice1c2-prod-acceptance.md`, `docs/superpowers/reviews/2026-07-09-review-backlog.md`), и он не исчез, а **подорожал**: тот же тап его больше не откроет, значит понадобится другой аффорданс — долгое нажатие с обучающей подсказкой, отдельная стрелка-раскрытие или свой экран, — и это уже дизайн-работа, а не привязка `cancel()` к готовому жесту. Вторая часть цены: пока списка нет, отменить офлайн-запись до отправки нельзя **ничем** — обещание §2.5 «отменить запись до отправки можно только из списка буфера» указывает в пустоту, и это тоже помечено в тексте, а не оставлено читателю на догадку. **(г) Почему решение заводится вообще.** Ветка ради куда более мелкого расхождения — «шесть измеряемых операций» стало «семь» — правила и PRD, и runbook; занять жест, обещанный живым контрактом, и не написать об этом нигде значило бы держать в одной ветке два разных стандарта честности.
- **Заменяет:** ничего из прежних решений не отменяет. Контракт §2.6 `02-core-os.md` и `design-brief.md` **не заменяет и не сужает** — целевое поведение остаётся в силе (тот же принцип, что в D30). Приводит к факту §2.6 и §2.5 `02-core-os.md` и абзац про retry-буфер в `design-brief.md`.
- **Детали:** `apps/web/src/features/chat/ChatScreen.tsx` (компонент `PendingFlush`: кнопка, строка неудачи и её время жизни), `apps/web/src/state/retry.ts` (`useFlushBuffer` возвращает число подтверждённых — по нему и решается «не вышло»), `apps/web/src/features/chat/ChatScreen.test.tsx`; спека Р2 `docs/superpowers/specs/2026-08-09-phase-e-candidates-design.md`, план `docs/superpowers/plans/2026-08-09-phase-e-candidates.md`

## Решения ленивой загрузки экранов (2026-08-10)

### D33. Приложение едет несколькими чанками: первый кадр легче на 18.7%, но у PWA появился отказ доставки, от которого экран сам не восстанавливается

- **Решение:** web перестаёт быть одним чанком. Шесть точек монтирования в `app/router.tsx` — четыре экрана Budget, `ImportFlow` и `entity-detail/DetailScreen` — переведены на `React.lazy`; начальная загрузка (входной чанк + всё, что он тянет статически) падает с **263 909 до 214 471 Б gzip, −49 438 Б (−18.73%)**, ленивых чанков девять на 62 759 Б. Три следствия принимаются вместе с выигрышем и записываются прямо, а не выводятся читателем. **(1) Для установленного PWA это не экономия трафика:** предкеш остаётся полным (`globPatterns` кладёт туда все чанки, 8 записей → 18, 931.84 → 938.41 KiB), экономится парсинг и исполнение первого кадра, а не байты по сети. **(2) Появился новый класс отказа — провал загрузки чанка,** которого у монолита не было в принципе; он закрывается тремя вещами: честный **404** на промах `/assets/*` вместо `index.html` с кодом 200, **ровно один автоматический перезаход на сессию вкладки** по `vite:preloadError` (флаг в `sessionStorage`) — **и только при доступном сервере**: живой смоук показал, что безусловный перезаход при недоступном сервере уносит вкладку на страницу ошибки браузера, поэтому перед перезагрузкой проверяется `/health` (гейт по `navigator.onLine` для этого не годится — на спящем инстансе при живом Wi-Fi он `true`); и **граница ошибок** `ChunkErrorBoundary` с кнопкой «Обновить» — до этой работы границ ошибок в приложении не было вовсе. **(3) `React.lazy` после отказа попытку не повторяет:** экран, чей чанк не приехал, не восстановится сам **никогда** — ни при вернувшейся сети, ни при возврате на него, — только перезагрузкой страницы. Ретрай-обёртка над `lazy` сознательно не написана.
- **Статус:** принято 2026-08-10 контроллером в отсутствие владельца, ждёт валидации владельцем — как D30, D31 и D32
- **Обоснование:** четыре вещи, по порядку. **(а) Почему разбиение вообще, если трафика оно не экономит.** Единственный чанк в 916 кБ сырых парсится и исполняется целиком до первого кадра — на телефоне это самая дорогая часть старта, и она платится каждый раз, даже когда всё уже в Cache Storage. Разбиение снимает с этого пути 179 675 Б сырых (−19.6%) навсегда, независимо от сети. Выигрыш измерен настоящим `gzip -c` на двух сборках одной машины и одного vite (число `gzip:` из вывода vite систематически завышено на ~1.2% и в ряд не годится), база пересобрана во временном worktree, а не взята из отчёта. **Сравнивать по одному входному чанку нельзя:** rolldown выносит из ленивых экранов общее поддерево, и вход импортирует его **статически**, с `modulepreload` — у нас это `Input-*.js`, 56 799 Б, которые с первого кадра не уходят никуда. Именно на этом обожглась разведка: прототип на живой сборке дал 13.2 кБ там, где подмена модулей в песочнице обещала 24. **(б) Почему предкеш остаётся полным.** Альтернатива — `globIgnores` + `runtimeCaching` — дала бы настоящую экономию трафика при обновлении, но урезала бы офлайн: экран, который пользователь не открывал онлайн, офлайн не открылся бы **вовсе**. Для приложения с обещанием офлайн-работы (D2) это плохой размен ради килобайтов. Побочно полный предкеш стал единственной грелкой ленивых чанков: `registerSW.js` регистрирует воркер по `load` первого же визита, и install-событие workbox тянет все 18 записей — то есть тот, кто вернётся к `globIgnores` ради трафика, снимет заодно и грелку. **(в) Почему автоперезаход ровно один и почему он вообще нужен.** Каждый деплой — новый контейнер с чистым `dist` (`render.yaml`, `Dockerfile`), персистентного диска нет: **старые чанки исчезают**, а SW с `registerType: 'autoUpdate'` (`skipWaiting` + `clientsClaim` + `cleanupOutdatedCaches`) активируется в уже открытой вкладке и вычищает её старый предкеш. То есть открытая вкладка теряет свои чанки **штатно**, а не в экзотике, и перезагрузка со свежим `index.html` чинит именно этот, главный сценарий. Второй провал подряд — уже не про устаревший `index.html`, это сеть или сервер, и повторный `reload()` превратился бы в цикл; поэтому флаг живёт в `sessionStorage`, переживает перезагрузку и намеренно не снимается. Отдельная правка сервера обязательна для всей связки: без неё промах `/assets/*` уходил `index.html`'ом с кодом 200 и `text/html`, браузер отвергал модуль по strict MIME, и в консоль приходило `Failed to fetch dynamically imported module` вместо «файла нет». Отсечка намеренно **узкая** — только `/assets/*`; хешированный `workbox-<хеш>.js` в корне `dist` промахом по-прежнему отдаёт HTML, улик вреда нет, и расширять правило «всё с хешем в имени», которое некому проверять, не стали. **(г) Самая неприятная часть, названная прямо: отказ ленивого экрана необратим внутри сессии.** Механика проверена по установленному React 19.2.7: инициализация выполняется только при `_status === -1` (`react/cjs/react.development.js:461`), при отказе загрузчика ставится `_status = 2` (`:478-486`), и дальше на каждом рендере синхронно перебрасывается **сохранённая** ошибка (`:513`) — загрузчик не зовётся больше ни разу. Значит «сеть отвалилась → чанк не приехал → сеть вернулась» не лечится ничем, кроме перезагрузки, сколько бы пользователь ни ходил по вкладкам; `resetKey` границы разблокирует **другие** экраны (иначе один провал запирал бы Чат, Обзор и Повестку, которые грузятся статически), но упавший не чинит. Ретрай-обёртку не писали сознательно: это новая способность со своей политикой повторов и своим риском циклов, а не доделка разреза, — но обещать, что её нет, дороже, чем записать. **Принятая цена целиком:** (1) заглушка `ScreenFallback` мелькает на первом открытии каждого ленивого экрана в сессии — воркер греет байты в Cache Storage, но не модули, а у пользователей без SW (приватные окна Safari и Firefox) чанки холодные вовсе; (2) обошедший все экраны скачает 277 230 Б против 263 909 — **+13 321 Б (+5.05%)**, цена границ разреза; (3) фоновая догрузка чанков, которой эту цену собирались закрыть (Р5 спеки), **реализована и снята** — `vite:preloadError` шлётся на любой провалившийся `import()` и не отличает фоновый от пользовательского, поэтому перезаход по фоновому забирает страницу у того, кто ничего не нажимал, а обратный гейт съедает провал пользователя на входе по ссылке `/entity/<id>`; вдобавок провал `import()` навсегда оседает в module map, и моргнувшая сеть ломала бы экран до конца сессии.
- **Заменяет:** ничего из прежних решений журнала не отменяет; D2 («офлайн = retry-буфер», обещание офлайн-работы) — прямое основание пункта (б). Отменяет **Р5** спеки `docs/superpowers/specs/2026-08-10-lazy-routes-design.md` («prefetch на idle»): решение реализовано, проверено ревью и снято целиком.
- **Детали:** спека `docs/superpowers/specs/2026-08-10-lazy-routes-design.md` (Р1–Р7), план `docs/superpowers/plans/2026-08-10-lazy-routes.md`; замер и таблица «до/после» — `docs/superpowers/reviews/2026-08-04-bundle-diet.md`, «Работа 2»; что осознанно не чинилось — `docs/superpowers/reviews/2026-08-10-lazy-split-backlog.md`. Код: `apps/web/src/app/router.tsx` (шесть `lazy` + `Suspense`), `apps/web/src/app/ScreenFallback.tsx`, `apps/web/src/app/ChunkErrorBoundary.tsx` (докблок с механикой кэша `lazy`), `apps/web/src/app/chunk-reload.ts` (докблок с разбором снятой догрузки), `apps/server/src/app.ts` (отсечка `/assets/*` → 404); тесты `apps/web/src/app/lazy-screens.test.tsx`, `apps/server/src/static.test.ts`

## Решения браузерного входа MCP (2026-08-12)

### D34. Orbis становится собственным authorization server; PAT переезжает из окружения в таблицу грантов, а PRD §4 — с восьми таблиц на десять

- **Решение:** подключение внешнего агента перестаёт быть переносом секрета руками. Orbis реализует **OAuth 2.1 целиком сам**: метаданные ресурса (RFC 9728) и authorization server (RFC 8414), динамическую регистрацию клиентов (RFC 7591), `GET /oauth/authorize` (страница SPA, серверного роута под ней нет) и `POST /oauth/token` с обменом кода и ротацией refresh. Токены **непрозрачные**, в базе живёт только `sha256`: `orbis_at_` (access, 1 час), `orbis_rt_` (refresh, 30 дней, ротируется при каждом обмене), `orbis_ac_` (одноразовый код, 60 секунд), `orbis_pat_` (headless, бессрочен — гасится строкой, а не временем). Состояние доступа — две новые таблицы, `oauth_clients` и `agent_grants`, то есть **PRD §4 расширен с восьми таблиц до десяти**. **PAT остаётся** — `claude -p`, Agent SDK и CI интерактивный вход не проходят, — но переезжает из переменных окружения `ORBIS_PAT_HASH`/`ORBIS_PAT_OWNER_ID` в ту же таблицу грантов: один механизм отзыва и один экран на оба вида доступа, и ограничение «ровно один токен» исчезает. Отзыв — кнопка в «Настройки → Агенты», мгновенный и по одному доступу.
- **Статус:** принято 2026-08-12; Р1, Р4, Р6 дизайна владелец выбрал напрямую, остальное принял контроллер — **ждёт валидации владельцем**, как D30–D33
- **Обоснование:** пять вещей, по порядку. **(а) Почему свой authorization server, а не Supabase.** Supabase-как-AS проверялся не рассуждением, а пробой прода: он **уже** отдаёт `/auth/v1/.well-known/openid-configuration` с `oauth/authorize`, `oauth/token` и `code_challenge_methods_supported: ["S256","plain"]` — то есть выглядел готовым решением. Отклонён по двум причинам, и вторая непреодолима. Первая: `registration_endpoint` в его метаданных **отсутствует** — динамической регистрации нет, и Claude Code пришлось бы добавлять с ручным `--client-id`, предварительно заведя OAuth-приложение, то есть ровно тот перенос конфигурации руками, ради устранения которого затевалась работа. Вторая: **выданный им токен имеет чужую аудиторию** — Supabase подписывает JWT с `aud: authenticated` для собственного API, и принять такой на `/mcp` значит сделать в точности то, что спека MCP 2025-06-18 называет прямым запретом («token passthrough», MUST NOT). Хуже того, это снесло бы границу, поставленную намеренно (`mcp/transport.ts`): сегодня владельческий JWT из веб-клиента на `/mcp` **не** аутентифицирует — иначе токен вкладки браузера переиспользовался бы под атрибуцией `agent`, и журнал перестал бы отличать владельца от агента. Свой AS выпускает токены со своей аудиторией и поддерживает DCR; Supabase остаётся ровно тем, чем и был, — способом узнать, кто сидит за браузером, и второго логина у владельца не появляется: на экране согласия он уже залогинен. **(б) Почему непрозрачные токены, а не подписанный JWT.** JWT с `aud`, подписанный секретом из окружения, проверялся бы без обращения к БД — единственное его преимущество. Оно испаряется от первого же требования фазы: отзыв (Р1) обязан действовать немедленно, значит на **каждом** вызове всё равно нужна сверка с базой, — а взамен появились бы секрет подписи в Render и отзыв с задержкой до истечения срока. Непрозрачная случайная строка (32 байта, 256 бит) с `sha256` в базе даёт мгновенный отзыв, не прибавляет ни одного секрета в окружении и совпадает с контрактом, который PRD §9.3 уже описывал для PAT: сервер хранит только хеш, сырой токен показывается один раз и не восстановим. **(в) Почему две таблицы, а не одна и не ноль.** Ноль невозможен по построению: одноразовость кода и отзыв — это состояние, а состояния вне базы у нас нет. Одноразовость сделана атомарным `UPDATE … WHERE code_used_at IS NULL RETURNING`, а не проверкой в коде: гонка двух обменов отдаёт строку ровно одному. Регистрации DCR вынесены отдельной таблицей, потому что клиент на момент регистрации **ничей** — владельца у него ещё нет, и класть его в таблицу с `owner_id` значило бы выдумывать владельца. **(г) Чего стоила честность про реплей — и почему это записано.** Первоначальная формулировка Р7 («повторное предъявление ротированного refresh отзывает грант целиком») была **неверна для refresh и верна только для кода**: ротация перезаписывает `refresh_hash`, следа предъявленного токена не остаётся, и правило не срабатывало ровно в том случае, ради которого писалось. Опроверг это реализатор пробой, а не рассуждением; отсюда колонка `prev_refresh_hash` и требование совпадения по `client_id` — иначе сбитый конфиг одного клиента отзывал бы владельцу весь доступ. **(д) Почему `ORBIS_PUBLIC_URL` роняет старт, а не запрос.** Канонический URI ресурса и база всех абсолютных URL метаданных берутся из переменной окружения, а не из заголовка `Host`: подменённый `Host` увёл бы MCP-клиента на чужой authorization server прямо через наши же метаданные. Указатель на метаданные собирается **на пути отказа** (401 на `/mcp`), поэтому бросок из-за конфигурации превращал бы 401 в 500 — вход агента ломался бы молча при зелёном `/health`. Отказ вынесен на старт процесса в манере **D28**: кривое или отсутствующее значение не даёт контейнеру подняться, и 500 из-за конфигурации становится недостижим. Кривое значение (путь, query, не-http) бракуется при любом `NODE_ENV` — опечатка вроде `https://host/mcp` обязана падать одинаково всюду, иначе локально «всё работает», а в проде рвётся.
- **Принятая цена, названная прямо:** **(1)** PRD §4 вырос с восьми таблиц до десяти — это прямая цена одноразового кода и отзыва, которых без состояния в базе не бывает; заодно у §4.10 появилось исключение из шаблона `owner_owns_row`: у обеих новых таблиц политик две, потому что лукап по хешу происходит **до** того, как владелец известен, и `withIdentity` там неприменим. **(2)** Каждый агентский вызов теперь ходит в базу: прежняя проверка была constant-time-сравнением с переменной окружения без единого запроса, новая — `UPDATE … RETURNING` с отметкой `last_used_at`, то есть **запись** на каждый вызов. Отметка куплена сознательно — она питает экран настроек и делает видимым доступ, о котором владелец забыл. **(3)** Публичных неаутентифицированных поверхностей стало больше: два документа метаданных и `POST /oauth/register`, открытый всему интернету по спеке DCR. Регистрация без согласия владельца не даёт ничего, но засорять таблицу можно — отсюда суточный потолок в 50 регистраций на сервис и лимит тела в 16 КиБ (единственный публичный POST без лимита до этого). **(4)** `ORBIS_PUBLIC_URL` обязана стоять в Render **до** выкатки ветки: иначе деплой выглядит упавшим релизом, а не забытой переменной. **(5)** Выпуск PAT на проде потерял санкционированный путь: скрипт, который раньше базы не касался, теперь в неё пишет — то есть требует прод-DSN у оператора. Возвращён он операцией `issue-pat` в белом списке `scripts/ops.ts` (секрет — в Ключнице macOS), `scripts/issue-pat.ts` остаётся для локального стенда. **(6)** Голый `bun run db:migrate` на базе без роли `orbis_app` теперь **падает**: `0005_oauth_rls.sql` — первая миграция, называющая эту роль поимённо (`CREATE POLICY … TO orbis_app`), а PostgreSQL проверяет существование роли в момент DDL. Штатный путь остался единственным — `bun run db:prepare`, который сначала зовёт `scripts/setup-db.ts`.
- **Заменяет:** ни одного решения журнала не отменяет. **Уточняет D5** («MVP: один PAT полного доступа»): токен больше не один и живёт не в окружении — контракт hash-only и «показывается один раз» остаётся в силе дословно, а вот **constant-time-сравнение из D5 снимается**: сравнивать хеш с секретом из окружения больше не с чем, предъявленный токен хешируется и ищется уникальным индексом по `access_hash` (разбор — §9.3). Отменяет решение плана слайса 1b «PAT — env, без новой таблицы» (`docs/superpowers/plans/2026-07-04-slice1b-ai-mcp.md`), принятое под ограничение «PRD фиксирует ровно 8 таблиц» — снимается именно это ограничение. Приводит к факту 02-core-os §1.6 («экран управления PAT в настройках отсутствует» — теперь есть вкладка «Агенты») и строку Future Directions 00-product §10: экран отзыва доставлен, **скоупы остаются Future** (Р6 — колонка `scope` в таблице заведена, значение пока одно; разрушительные действия гейтит не ярлык доступа, а политика подтверждений §7.10).
