### §1.2 Граница документа

PRD фиксирует **контракты и поведение** — схемы данных, протоколы, грамматику запросов, реестр тулов, инварианты, — но **не реализацию**. Структура кода, выбор библиотек, сигнатуры процедур, организация модулей живут в implementation-планах фаз и в самом коде. Если деталь не влияет на наблюдаемое поведение системы или на совместимость данных — её здесь нет намеренно.

### §1.3 Сквозные принципы

**Принцип 1: данные существуют до views.** Сущности и их связи — первичны; views (Budget, Agenda, Browser, будущие Fitness и Habits) — линзы поверх одного графа. Удаление или замена view не теряет ни одной записи: расход, заведённый через Budget, останется сущностью с `orbis/financial` и будет виден в Browser и в любых будущих views. Следствие для проектирования: ни один view не имеет собственного хранилища данных — только настройки отображения (`user_settings.viewPreferences`).

**Принцип 2: один канон запроса — один компилятор.** Канон запроса — булево дерево `and/or/not` над предикатами (Q-AST, §6); текстовая грамматика — синтаксис ввода и вывода, не форма хранения. Компилятор один, бэкенд один (Postgres), а точек его вызова сегодня **семь в четырёх модулях** — от `{{query:...}}`-блоков в body до проверки значения ссылочного свойства; любая новая фильтрующая возможность добавляется в канон один раз и автоматически доступна всем. Полный список — §6.3.

**Принцип 3: правила слоёв сущности.**

- **props — всё, по чему фильтруют и считают** [D43]. Значение факта живёт под id свойства из реестра (§4.16), одно значение на свойство на сущность. Критерий, заводить ли свойство: по нему будут фильтровать или считать — иначе это текст в body. Никакого application state: координаты досок, настройки отображения, кэши — не сюда; исходная фраза ввода живёт в `chat_messages.content` (§4.6), provenance импорта — в `entity_origins` (§4.8).
- **body — текст и живые запросы.** Markdown, ссылки на сущности, `{{query:...}}`-блоки. Smart lists — это сущности с query-блоками в body, а не отдельный механизм. Из body извлекаются два индекса: `body_refs[]` (кого упоминает текст) и `query_refs[]` (кого адресуют его запросы).
- **aspects — интерпретация, а не владелец полей** [D43]. Аспект говорит, чем сущность является («это задача»), и приносит свой набор свойств с обязательностью и порядком; сами значения лежат в `props` и переживают снятие аспекта. Свойство без аспекта — законное состояние (свободное свойство), и оно видно, фильтруется и считается наравне с остальными.

## §2. Модель данных: сущность

### §2.1 Пять слоёв

Сущность — универсальная единица графа. Все домены (задачи, финансы, заметки, бюджеты, память AI) выражаются одной структурой из пяти слоёв [D43]:

```
┌──────────────────────────────────────────────────────────────────┐
│  СУЩНОСТЬ                                                        │
│                                                                  │
│  ┌ 1. Core ────────────────────────────────────────────────────┐ │
│  │  id (UUIDv7, генерируется клиентом), title, emoji,          │ │
│  │  created_at, updated_at, archived                           │ │
│  └─────────────────────────────────────────────────────────────┘ │
│  ┌ 2. Body ────────────────────────────────────────────────────┐ │
│  │  markdown + [[entity:uuid|text]] + {{query:...}}            │ │
│  │  body_doc — структурная правда тела                         │ │
│  │  body_refs[] — UUID, упомянутые телом                       │ │
│  │  query_refs[] — id, адресованные запросами тела             │ │
│  └─────────────────────────────────────────────────────────────┘ │
│  ┌ 3. Tags ────────────────────────────────────────────────────┐ │
│  │  tags[] — нормализованные ярлыки (от AI и пользователя)     │ │
│  └─────────────────────────────────────────────────────────────┘ │
│  ┌ 4. Props ───────────────────────────────────────────────────┐ │
│  │  { "orbis/task_status": "planned", "orbis/amount": "8000" } │ │
│  │  плоская карта «id свойства → значение», одно на свойство   │ │
│  └─────────────────────────────────────────────────────────────┘ │
│  ┌ 5. Aspects ─────────────────────────────────────────────────┐ │
│  │  [ "orbis/task", "orbis/financial" ]                        │ │
│  │  список id аспектов — чем сущность является                 │ │
│  └─────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

- **Core** — минимум, который есть у всего: `id` (UUIDv7, генерируется на клиенте — время в префиксе даёт естественную хронологическую сортировку и нужно retry-буферу fast-path-ввода, §5.3, для идемпотентной досылки ещё не подтверждённых create-мутаций), `title`, опциональный `emoji`, таймстемпы, флаг `archived` (мягкое удаление; жёсткого удаления сущностей в MVP нет). Четыре core-колонки — `archived`, `title`, `created_at`, `updated_at` — вдобавок имеют записи в реестре свойств (`storage: core`, §4.16): хранение остаётся колонкой, а реестр даёт им единый адрес для запросов, предусловий и подписей.
- **Body** — markdown с двумя расширениями: inline-ссылка `[[entity:uuid|текст]]` и живой query-блок `{{query:...}}` (§6). Из body при каждом сохранении извлекаются два индекса: `body_refs[]` — UUID упомянутых сущностей (быстрые backlink-запросы без парсинга markdown) — и `query_refs[]` — id свойств, аспектов, ролей и сущностей, которые **адресуют запросы** этого тела (по образцу `body_refs`; отсюда операция слияния свойств знает, какие тела переписать, §4.16).
- **Tags** — слой без схемы: сквозная фильтрация ярлыками, которые ставит и владелец, и AI. Схемы у тегов нет намеренно, и реформа их не трогает.
- **Props** — плоская карта `id свойства → значение`, одно значение на свойство на сущность. Тип, ограничения и подпись значения приходят из реестра свойств (§4.16), а не из аспекта. Свойство может стоять на сущности **без аспекта-носителя** — «свободное свойство»: так живёт факт, извлечённый AI, до того как для него появилась интерпретация.
- **Aspects** — список id аспектов: чем сущность **является**. Одна сущность может иметь несколько: «купить кроссовки 8000₽ к субботе» = одна сущность с `orbis/task` + `orbis/financial` + `orbis/schedule`. Аспект приносит набор свойств с обязательностью и порядком (§3), но владельцем значений не является: снятие аспекта значения не удаляет.

### §2.2 Что является сущностью, а что нет

| Сущности (живут в `entities`) | Не сущности (отдельные таблицы) |
|---|---|
| Задачи | `user_settings` |
| Расходы и доходы (транзакции) | Реестры структуры: `property_definitions`, `aspect_definitions`, `relation_role_definitions`, `contract_definitions`, `subscription_definitions`, `action_definitions` (§4.16) |
| Заметки | Персональные правки реестров (`registry_deltas`) и версия system-реестра (`registry_system`) — §4.16 |
| Проекты | История чатов (`chat_threads`, `chat_messages`) |
| Конверты бюджета | Метеринг (`ai_usage`) |
| Категории | Provenance импорта (`entity_origins`) |
| Memory-факты и правила AI | Версии тела (`entity_versions`) |
| Smart lists (query-блоки в body) | Кэш `spent` по конвертам (`envelope_spent_cache` — часть Б; в срезе А не реализовано) |
| Recurring-шаблоны и их инстансы | |
| Чекины привычек (future) | |

Правило деления реформа не меняет — меняется только то, что таблиц-реестров стало шесть вместо одной: **декларация — не сущность**. Определение свойства или роли ребра нельзя связать relation'ом, обсудить в его треде и заархивировать; правится оно диффом, а не как запись графа (§4.16, §7.10).

### §2.3 Правило идентичности

**Сущность — то, на что пользователь ссылается как на вещь с собственной судьбой.** У неё есть имя, её можно открыть, связать с другими, заархивировать, обсудить в её треде. Категория «Еда» — сущность: пользователь переименовывает её, пишет в её body правила категоризации, смотрит её транзакции. Настройка `weekStartDay` — не сущность: это параметр поведения системы, у него нет собственной жизни в графе. Этим правилом проверяется каждый новый тип данных: если объект нужно показывать в Browser, связывать relations или обсуждать — это сущность; если это конфигурация или журнал — это таблица.

### §2.4 Сквозной пример

Сущность из ввода «купить кроссовки 8000₽ к субботе» — все пять слоёв в одном JSON (служебный столбец `owner_id` опущен; свойства — по §3.1–§3.3). Это форма **хранения**: ключи `props` — id свойств; у встроенных свойств id и key совпадают, а наружу к модели и в MCP та же карта едет по key (§9.2):

```json
{
  "id": "019ea8b1-4778-7f3d-9a5c-6a521fa1cc24",
  "title": "Купить кроссовки",
  "emoji": "👟",
  "body": "К субботней пробежке. Модель выбрана в [[entity:019e4466-1000-7e07-b5d4-64be9721da51|Wishlist: бег]].",
  "body_refs": ["019e4466-1000-7e07-b5d4-64be9721da51"],
  "query_refs": [],
  "tags": ["task", "expense", "running"],
  "props": {
    "orbis/task_status": "planned",
    "orbis/priority": "medium",
    "orbis/due_date": "2026-06-13",
    "orbis/start_at": "2026-06-13T00:00:00+03:00",
    "orbis/all_day": true,
    "orbis/timezone": "Europe/Moscow",
    "orbis/amount": "8000.00",
    "orbis/currency": "RUB",
    "orbis/direction": "expense",
    "orbis/finance_category": "019d48ea-2e00-7a52-876a-c301529b0456",
    "orbis/occurred_on": "2026-06-13",
    "orbis/planned": true
  },
  "aspects": ["orbis/task", "orbis/schedule", "orbis/financial"],
  "created_at": "2026-06-08T19:24:11Z",
  "updated_at": "2026-06-08T19:24:11Z",
  "archived": false
}
```

Здесь: `body_refs` извлечён из `[[entity:...]]`-ссылки в body, `query_refs` пуст (запросов в теле нет); `orbis/finance_category` указывает на категорию-сущность «Одежда»; `orbis/schedule` делает покупку видимой в Agenda на субботу; `orbis/occurred_on` задаёт ожидаемую дату финансового события; `orbis/planned: true` не даёт списать сумму до подтверждения факта (§3.3, §3.5). Карта плоская, и это её главное свойство: `orbis/due_date` (срок задачи) и `orbis/start_at` (момент в календаре) — два разных факта под двумя разными id, а не два одинаково названных поля в двух аспектах. Исходная фраза «купить кроссовки 8000₽ к субботе» сохранена как `content` инициировавшего создание сообщения чата (§4.6) — отдельного слоя «сырьё до структурирования» у сущности нет.

## §3. Аспекты и свойства MVP

Тринадцать встроенных аспектов и **77 встроенных свойств**: 73 доменных (`storage: props`) плюс 4 core-проекции адресации (`storage: core` — `orbis/archived`, `orbis/title`, `orbis/created_at`, `orbis/updated_at`, §3.17). Все тринадцать аспектов активны для каждого пользователя с первого дня: passive-состояния в v3 нет.

**Аспект — интерпретация, а не владелец полей** [D43]. Норматив значения — строка реестра свойств (§4.16): у свойства один id, один тип и одни ограничения на всю систему. Аспект ссылается на свойства тройкой `{propertyId, required, rank}` — «какие свойства входят в эту интерпретацию, какие из них обязательны и в каком порядке показывать». Отсюда три следствия, которых до реформы не было: одно и то же свойство несут два аспекта (`orbis/finance_category` — и транзакция, и конверт; `orbis/currency` — оба; `orbis/grant` — назначение и прогон), значение переживает снятие аспекта, а свойство живёт и без аспекта вовсе (§3.10). JSON Schema аспекта — **генерируемая производная** его набора свойств: её собирают валидатор и генератор тулов, отдельного норматива «схема аспекта» больше нет.

Нумерация подразделов историческая: восьмой аспект `orbis/goal` приехал в слайсе 3 и описан в **§3.11**, после реестра (§3.8) и служебных подразделов, — вставлять его между §3.7 и §3.8 значило бы сдвинуть номера, на которые уже ссылаются 00-product и 02-core-os. Четыре аспекта ADE-среза 1 (`orbis/project`, `orbis/repo`, `orbis/assignment`, `orbis/agent-run` — D37) приехали тем же порядком и описаны в **§3.12–§3.15**; тринадцатый, `orbis/routine` среза V1 (D38), — в **§3.16**. Свойства, у которых аспекта-носителя нет вовсе, собраны в **§3.17**.

**Реестры — рантайм-источник валидации, и их рассинхронизация с кодом наблюдаема.** Исполнитель (§9.2, стадия 2) проверяет значения по типам свойств из реестра, а не по схемам из кода: релиз, изменивший тип или состав без пересева реестров, выкатывается со старой формой, и новая запись отклоняется валидацией — фича приезжает мёртвой (fail-closed, данные целы). Поэтому сервер **на старте** сверяет строки встроенных определений в БД с кодом и объявляет результат: расхождение — громкой строкой лога с командой починки и полем `registryDrift` в `/health`; недоступность БД на старте — отдельным состоянием «неизвестно» (выдавать её за «расхождений нет» нельзя, иначе проверка тихо снимается). Сверка **двусторонняя**: лишняя system-строка в базе — тоже дрейф. Старт при этом не падает: дрейф одной строки не повод не поднимать приложение.

Условные обозначения: ✓ в колонке Req — свойство обязательно при наличии аспекта на сущности. Имена свойств даны как `id` (= `key` у встроенных): по этому же имени они адресуются в запросах (§6.1) и в параметрах тулов (§9.2). Соответствие «поле аспекта до реформы → id свойства» — таблица перевода §А8 спеки D43; в данных старых имён полей не осталось (пересев мира, §А12).

### §3.1 `orbis/schedule` — время

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/start_at` | timestamp (ISO 8601) | ✓ | Начало события / момент привязки ко времени |
| `orbis/end_at` | timestamp (ISO 8601) | | Конец события; если задан — должен быть ≥ `orbis/start_at` |
| `orbis/duration_min` | number {integer, min: 1} | | Длительность в минутах (альтернатива `orbis/end_at`; если заданы оба — приоритет у `orbis/end_at`) |
| `orbis/all_day` | boolean | | Событие на весь день; отсутствие значения читается как «нет» |
| `orbis/recurrence` | json {schema} | | Правило повторения: `{freq: daily\|weekly\|monthly, interval: int, byweekday?: string[], until?: date}`. Наличие = сущность является recurring-шаблоном |
| `orbis/location` | text | | Место |
| `orbis/timezone` | text {format: iana-tz} | | Таймзона события; по умолчанию — таймзона пользователя |

`tag_mappings`: `["schedule", "event", "meeting", "appointment"]`

Recurrence живёт только здесь — единый источник истины «когда повторяется» для любых доменов (платежи, тренировки, привычки). Инстансы порождаются от шаблона ребром роли `instance-of` (§4.2) с детерминированными ID (§5.4).

### §3.2 `orbis/task` — задача

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/task_status` | select: `inbox` \| `planned` \| `in_progress` \| `waiting` \| `done` \| `cancelled` | ✓ | Состояние задачи |
| `orbis/priority` | select: `low` \| `medium` \| `high` | | Приоритет |
| `orbis/due_date` | date (ISO 8601) | | Срок. **Не то же, что `orbis/start_at`**: срок ≠ начало события — это разные факты, потому и разные свойства |
| `orbis/completed_at` | timestamp | | Момент завершения; проставляется при переходе в `done`, при откате задачи из `done` — очищается |
| `orbis/effort_min` | number {integer, min: 1} | | Оценка трудозатрат в минутах |
| `orbis/waiting_for` | text | | Кого/чего ждём (для `orbis/task_status=waiting`) |

`tag_mappings`: `["task", "todo", "action", "deadline"]`

Умолчание «новая задача попадает в `inbox`» живёт **инструкцией аспекта для AI** (`ai_instructions` строки реестра), а не механизмом записи: безусловный `default` в определении свойства в срезе А есть только у `boolean` и применяется **читателем, а не записью** — иначе `has(orbis/planned)` был бы истинным у каждой транзакции [рулинг РП-9 ветки D43]. Условный дефолт правилом каталога (`default` с условием) — часть Б; в срезе А не реализовано. Переходы `orbis/task_status` ↔ `orbis/completed_at` держит инвариант-код исполнителя (§9.2, стадия 4); правило `on_enter_class` вместо него — тоже часть Б.

### §3.3 `orbis/financial` — финансовая операция

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/amount` | decimal {exclusiveMin: 0} | ✓ | Сумма в единицах валюты, канонический формат base-10 без экспоненты (`"340.00"`, `"127.50"`). Всегда положительная; знак задаёт `orbis/direction`. Граница «строго больше нуля» — конфиг типа, не регулярка с lookahead: схема свойства экспортируема в не-ECMA движки (§7.7) |
| `orbis/currency` | text {format: currency, ровно 3 символа} | | Валюта (ISO 4217); отсутствие — валюта владельца. **Одно свойство на транзакцию и конверт** (слито с валютой бюджета) |
| `orbis/direction` | select: `income` \| `expense` | ✓ | Направление операции |
| `orbis/finance_category` | ref {target: `aspect=orbis/category`} | ✓ | Ссылка на **категорию-сущность**. **Одно свойство на транзакцию и конверт** (слито с категорией бюджета) |
| `orbis/occurred_on` | date (ISO 8601) | условно ✓ | Дата фактической или ожидаемой операции в таймзоне пользователя. Обязательна для фактов, planned-операций и recurring-инстансов; отсутствует только у recurring-шаблона |
| `orbis/planned` | boolean {default: false} | | `true` = запланированная операция (ещё не факт): видна в прогнозах и секции planned, не списывается из конверта как фактический расход |
| `orbis/recurring` | boolean | | `true` = сущность является шаблоном регулярной операции (период — в `orbis/recurrence` той же сущности); инстансы связываются ролью `instance-of` |
| `orbis/payment_method` | text | | Способ оплаты (карта, наличные, счёт) |
| `orbis/counterparty` | text | | Контрагент (магазин, работодатель, человек) |
| `orbis/bank_txn_id` | text {maxLength: 128} | | Стабильный идентификатор операции из выписки банка; `system_writable` — пишет только импорт выписки (03-budget §3.4), и участвует в дедуп-критерии 03-budget §3.4.1: совпавший ID закрывает пункт 3 критерия независимо от текста counterparty |

`tag_mappings`: `["expense", "income", "payment", "cost"]`

Категория — ссылка на сущность (`orbis/finance_category` типа `ref`), а не строка: переименование категории не требует массового обновления транзакций, категория несёт иерархию (роль `category-parent`, §4.2), body-правила и собственный тред. Тип `ref` знает своё множество целей (`aspect=orbis/category`) и проверяет его при установке значения — пикер и валидация строятся по типу, а не по коду домена (§4.16).

**Инвариант повторяемости.** Канонический источник — `orbis/recurrence` на сущности-шаблоне (§3.1). `orbis/recurring=true` — информационный маркер для прогнозов (Coming up, прогноз баланса), валидный только на шаблоне с `orbis/recurrence` или на его экземплярах (ребро роли `instance-of`, §4.2). Шаблон не имеет `orbis/occurred_on`; каждый экземпляр получает его из своей даты. Будущий экземпляр создаётся с `orbis/planned=true`; в дату `orbis/occurred_on` локальный системный transition атомарно меняет неархивный экземпляр на `orbis/planned=false` и выполняет авто-привязку к конверту. Его `batch_id` детерминирован: `uuidv5(ORBIS_NAMESPACE, "post-financial:<instance_id>")`, поэтому конкурентные выполнения перехода не создают повторных действий. Несогласованность — `orbis/recurring=true` без `orbis/recurrence` и без ребра `instance-of`, либо не-шаблон без `orbis/occurred_on` — отклоняется валидацией при записи.

**Денежная арифметика.** `amount` и все денежные поля других аспектов хранятся JSON decimal-строками со схемой `{type: "string", format: "decimal"}` и вычисляются библиотекой точной base-10 арифметики; преобразование в IEEE-754 `number` запрещено. Масштаб при сохранении нормализуется по minor-unit валюты (для RUB/USD/EUR — 2 знака), правила округления — half-away-from-zero только на границе ввода/импорта. Query-движок принимает числовые литералы как decimal и сравнивает их без потери точности.

### §3.5 `orbis/budget` — конверт бюджета

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/finance_category` | ref {target: `aspect=orbis/category`} | ✓ | Категория-сущность, к которой относится конверт. То же свойство, что у транзакции (§3.3) |
| `orbis/limit` | decimal {min: 0} | ✓ | Лимит конверта на период; денежная арифметика — по правилу §3.3 |
| `orbis/currency` | text {format: currency, ровно 3 символа} | | Валюта; то же свойство, что у транзакции |
| `orbis/period_start` | date (ISO 8601) | ✓ | Начало периода (включительно) |
| `orbis/period_end` | date (ISO 8601) | ✓ | Конец периода (включительно) |
| `orbis/carryover` | decimal | | Остаток, перенесённый из предыдущего периода (может быть отрицательным — перерасход). `system_writable` — пишет правило переноса. Доступно в периоде = `orbis/limit + orbis/carryover − spent` |

`tag_mappings`: `["budget", "envelope", "limit"]`

Слияние `category_ref` и `currency` конверта с одноимёнными полями транзакции — осознанная цена: конверт и транзакция **на одной сущности** с разными категориями перестали быть выразимыми. Это не сценарий продукта, а артефакт прежней карты полей.

**`spent` не хранится** — потраченное вычисляется из фактических расходных транзакций, привязанных к конверту ребром роли `envelope-binding` (§4.2); полный состав условий и формула — 03-budget §2.2. Это единственный источник истины: правка, перенос или архивация транзакции немедленно и без рассинхрона меняет состояние конверта. Любое отображаемое значение `spent` — вычисление на лету или кэш по правилу 3 (§10).

Пример пары «конверт + транзакция» (показаны значимые слои; остальные поля — как в §2.4):

```json
{
  "id": "019e81fb-7180-7306-ad8f-842ad8efb58d",
  "title": "Еда — июнь 2026",
  "tags": ["budget"],
  "props": {
    "orbis/finance_category": "019d48ea-4188-765d-8e96-93a0ad9c262a",
    "orbis/limit": "30000.00",
    "orbis/currency": "RUB",
    "orbis/period_start": "2026-06-01",
    "orbis/period_end": "2026-06-30",
    "orbis/carryover": "-1200.00"
  },
  "aspects": ["orbis/budget"]
}
```

```json
{
  "id": "019eac7a-5980-7fa8-8425-8b14dfcbba25",
  "title": "Обед",
  "tags": ["expense", "food"],
  "props": {
    "orbis/amount": "340.00",
    "orbis/currency": "RUB",
    "orbis/direction": "expense",
    "orbis/finance_category": "019d48ea-4188-765d-8e96-93a0ad9c262a",
    "orbis/occurred_on": "2026-06-13",
    "orbis/planned": false
  },
  "aspects": ["orbis/financial"]
}
```

Их связывает ребро роли `envelope-binding` (§4.2): `source_id` = конверт `019e81fb-…`, `target_id` = транзакция `019eac7a-…`. Роль названа не «родитель»: конверт транзакции не родитель, он её счётчик — и именно у этой роли стоит ограничение «у цели не больше одного входящего ребра» (§4.2, §13 п.7). Оба `orbis/finance_category` указывают на одну категорию-сущность «Еда» — и это буквально одно и то же свойство на двух записях. `spent` на лету = сумма фактических расходных транзакций конверта в его валюте (состав и формула — 03-budget §2.2); доступно = `30000.00 + (−1200.00) − spent`.

### §3.7 `orbis/memory` — память AI

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/memory_kind` | select: `fact` \| `rule` | ✓ | `fact` — знание о пользователе («работаю из дома по пятницам»); `rule` — правило обработки ввода («бар → категория Развлечения») |
| `orbis/rule_scope` | registry_ref {target: contract} | | Область действия записи: ссылка на **контракт** реестра (`orbis/money-movement` — записи о движении денег). Отсутствие = глобально, и глобальная запись входит в выборку любой области |
| `orbis/rule_pattern` | text | | Левая часть правила: паттерн, который ищется во вводе («бар») |
| `orbis/rule_target` | ref {target: `aspect=orbis/category`} | | Правая часть правила: сущность-категория, в которую правило кладёт ввод |

`tag_mappings`: `["memory", "preference", "rule"]`

Memory-факты — обычные сущности: видимы и редактируемы в Browser, пользователь курирует свою память напрямую (§7.4).

**Правило больше не разбирается из заголовка** [D43]. Обе половины правила — свойства: `orbis/rule_pattern` и `orbis/rule_target`; `title` стал **генерируемой подписью** («`бар` → Развлечения»), которую никто не парсит. Отсюда исчезает целый класс «записанное, но молча мёртвое правило»: правило без цели незаписываемо (fail-closed на записи), а не тихо игнорируется всеми потребителями. Цель — ссылка, поэтому правило переживает переименование категории, а backlinks категории показывают правила, которые в неё кладут.

Область названа `rule_scope`, хотя применяется и к `fact`, и к `rule`: имя нормативно (§А8 спеки D43), и трение с принципом «id называет смысл» названо вслух, а не спрятано. Ссылка идёт **на контракт**, а не на аспект: «запись о движении денег» — это интерфейс, который может реализовать и встроенный `orbis/financial`, и будущий пользовательский аспект. В срезе А контрактов ещё нет (`contract_definitions` создана пустой, §4.16), поэтому множество допустимых значений — строки таблицы **плюс закрытый список id контрактов ядра**; этот шим живёт ровно на интервале до сида контрактов в срезе Б-1 и снимается вместе с ним. Область правила при подборе сравнивается **прямым равенством** значения — Q-AST-областью она не является ни сейчас, ни по замыслу.

### §3.8 Реестры структуры: встроенные аспекты и словарь свойств

Реестров структуры **шесть**, и это таблицы, а не одна (§4.16): свойства, аспекты, роли рёбер, контракты, подписки, действия. Пять из них сидируются манифестами модулей; шестой — реестр действий — устроен так же, но действия приходят вместе с языком выражений части Б, поэтому спека реформы в перечне «сидируемых пяти» его не считает. В срезе А засеяны **три**: 77 свойств, 11 ролей рёбер, 13 аспектов; таблицы контрактов, подписок и действий созданы **пустыми** — их сид открывает срез Б-1. Рядом живут журнал персональных правок (`registry_deltas`) и однострочная таблица версии system-реестра (`registry_system`).

### §3.9 Одно тождество факта

Прежнее содержание раздела — «соглашение об именах meta-ключей» — **снято реформой D43** (§А1-2 спеки) вместе с колонкой `meta`: у факта больше нет двух домов, между которыми надо было согласовывать имена. Соглашение заменено свойством модели: **факт живёт под одним id**. «Потратил 500 на такси» кладёт `orbis/amount: "500.00"` и `orbis/direction: "expense"` в `props` — те же самые id, что несёт аспект `orbis/financial`, независимо от того, навешен он уже или нет. Согласовывать нечего: имя одно по построению, и запрос `orbis/amount>1000` находит запись и со `orbis/financial`, и без него.

Правило, которое осталось от прежнего соглашения и стало жёстче: **свойство заводят под то, по чему будут фильтровать или считать; остальное — текст в body**. Заводя свойство от себя, AI ставит ему статус `proposed` — так велит инструкция тула, и такие свойства ждут разбора владельцем, не попадая в промпт (§4.16); неразобранных у владельца не больше 20. Серверного запрета на `active` при этом нет — но и уровень у него другой: свойство, заведённое сразу активной строкой, требует **явного подтверждения** владельца, а не предпросмотра (§7.10), потому что кап на неразобранные считает только `proposed`.

### §3.10 Свободные свойства и жест «навесь аспект»

Прежнее содержание раздела — пятишаговая ретроактивная миграция — **снято реформой D43** (§А1-2 спеки): механизма, который переносил бы `meta` в поля аспекта по совпадению имён, больше нет, потому что нет и переноса. Подключение накопленных данных к новому аспекту стало одним жестом, и работает он так:

1. **Свойства уже стоят.** Факт, извлечённый AI до появления интерпретации, лежит в `props` под своим id — «свободное свойство». Оно видно на карточке, фильтруется запросом и участвует в агрегатах наравне с остальными: аспект для этого не нужен.
2. **Навесить аспект** — обычная операция (`attach_*`, §9.2). Валидация проверяет ровно одно: все ли **обязательные** свойства этого аспекта на записи есть. Ничего никуда не переносится — значения уже на месте.
3. **Не хватило обязательного** — операция отклоняется с именем недостающего свойства; владелец дозаполняет руками или через чат («у этих пяти тренировок не хватает даты — расставь по описанию»).

Идемпотентность бесплатна: повторный `attach_*` на записи, где аспект уже есть, ничего не меняет. Обратный жест тоже честный: снятие аспекта **не удаляет значения** — сущность возвращается к свободным свойствам, и повторное навешивание не требует ввода заново.

Цена решения названа прямо: `tag_mappings` (§4.3) перестал быть входом миграции и остался тем, чем был всегда, — подсказкой «этот тег намекает на такой аспект» для AI и конструктора.

### §3.11 `orbis/goal` — цель (слайс 3)

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/progress_source` | json {schema} | ✓ | Откуда берётся факт: `query` — **разобранный запрос деревом** (Q-AST, §6), `aggregate` — `count` \| `sum` \| `latest`, `field` — id агрегируемого свойства. Форма объекта — **дискриминированное объединение по `aggregate`** (ниже) |
| `orbis/target_value` | decimal {exclusiveMin: 0} | ✓ | Целевое значение, **строго больше нуля** (на него делят при расчёте доли) |
| `orbis/current_value` | decimal {min: 0} | | Кэш достигнутого (правило 3, §10). `model_writable: false` — модели путь к нему закрыт отказом, а не уговором; сегодня его **не пишет никто**: прогресс считается на каждом чтении и в запись не возвращается |
| `orbis/unit` | text | | Подпись единицы («₽», «книг», «кг»); заданная — **непустая**: пустая строка приехала бы хвостом за числом |

`tag_mappings`: `["goal"]`

**Дискриминированное объединение, а не «field для sum и latest».** Различие нормативно, потому что схема значения строгая и исполнитель валидирует по ней:

- `aggregate: "count"` — считает СУЩНОСТИ; ключ `field` в этой ветке **запрещён**, лишний `field` отклоняется валидацией, а не игнорируется;
- `aggregate: "sum" | "latest"` — `field` **обязателен**.

Правило выражено формой объекта, а не `refine`-проверкой поверх него: схема значения свойства типа `json` уезжает в реестр (§4.16) и генерируется в JSON Schema для ajv и для тулов — всё, что не пережило бы генерацию, до рантайм-валидатора не доехало бы. Проверяет его ajv по записи реестра — см. §11.3 про расчёт и §12 п.6 про границу механизма.

**Запрос внутри `progress_source` хранится деревом** [D43]: `query` — это Q-AST по id свойств и аспектов (§6), а не строка грамматики; переименование подписи свойства цели больше не ломает. Ветка «неразобранный текст» у поля осталась осознанно: цель, чей запрос разобрать не удалось, остаётся открываемой и чинится в UI, а расчёт по ней отдаёт честный `invalid_query` — иначе сломанную цель нельзя было бы починить, не удалив [рулинг Р-10b-2 ветки D43; сужение до голого Q-AST — вместе с движком части Б]. У дерева есть кап глубины **64 уровня JSON**, проверяемый **на записи**: без него цепочка отрицаний в 10 000 уровней принималась записью и роняла чтение записи навсегда.

### §3.12 `orbis/project` — проект (ADE-срез 1)

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/project_stage` | select | ✓ | Жизненный цикл затеи: `active` \| `paused` \| `done` |

`tag_mappings`: `["project", "проект"]`

**Маркер затеи, и только он** (С4 дизайна ADE). Всё содержательное про проект живёт в `body`: проза процесса плюс живые `{{query:…}}`-блоки по его тикетам. Тикеты — дочерние сущности с `orbis/task` через ребро роли `ticket` (§4.2); отдельного типа «тикет» нет.

**Стадия проекта — отдельный факт от статуса задачи** [D43]. До реформы имена полей были голыми, и второе поле `status` в реестре сделало бы запрос `status=…` без `aspect=` неоднозначным — отсюда и родилось имя `stage`. Namespaced key снял саму причину: `orbis/project_stage` и `orbis/task_status` не пересекаются по построению, уточнение `aspect=` для однозначности больше не требуется. Имена при этом сохранены, а не «исправлены обратно»: разные enum — разные факты (у задачи `done`/`cancelled`, у проекта `done`/`paused`), и одно свойство на двоих сделало бы «закрытую задачу» и «законченный проект» одним значением. По той же причине у прогона исход называется `orbis/run_outcome`, а у рутины — `orbis/routine_stage`.

**Заготовку тела засевает сервер**, когда аспект на сущности *появляется* (не правится), текущее тело записи пусто И своего тела вход не несёт: путь один для чата, MCP и UI — раздел «Процесс» прозой (его читает исполнитель при захвате тикета) и четыре query-блока: «в работе», «ждут меня», «бэклог», «последние прогоны». В первые три подставляется **uuid проекта** (`children_of=<uuid>`), а не `this`: проект известен в момент засева, а текст блока живёт дольше своего места — его копируют в закреплённый список и открывают из Browser, где контекст записи не передаётся намеренно (§6.1). Четвёртый блок адресует прогоны **вычисляемым свойством** `orbis/parent_project` (§3.17): прогон — внук проекта, и `children_of` его не достаёт. Пустая или пробельная строка `body` телом не считается — модель присылает `body: ""` сплошь и рядом, и считать её телом значило бы отдавать пустой проект вместо заготовки; пустой `bodyDoc` из редактора телом считается всегда (это осознанное «я стёр всё»). Условие «текущее тело пусто» — третье и не лишнее: `attach orbis/project` к уже написанной заметке заготовку НЕ засевает, иначе она затёрла бы написанное владельцем.

**Кодовой специфики здесь нет** — она вынесена в `orbis/repo` (§3.13) на той же сущности: круг «тикет → прогон → чекпойнт» есть общий механизм делегирования сферы, и кодовое не врастает в общее понятие проекта (D35, D37).

### §3.13 `orbis/repo` — репозиторий проекта (ADE-срез 1)

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/repo_url` | text {format: url, 1–512} | ✓ | Адрес репозитория |
| `orbis/default_branch` | text {1–128} | ✓ | Ветка по умолчанию |

`tag_mappings`: `["repo", "репозиторий"]`

**Формат адреса теперь проверяется** [D43]: `format: url` — новое ужесточение реформы (до неё стояла только длина). Следствие названо честно, потому что оно наблюдаемо: scp-подобный SSH-адрес `git@host:owner/repo.git` — не URI и отклоняется валидацией; тот же репозиторий подключается полной формой `ssh://git@host/owner/repo.git`.

Ставится на ту же сущность, что и `orbis/project`, и **только если проект про код**. Отдельный аспект, а не поля проекта, — по С4: сфера жизни, делегированная агенту, может не иметь репозитория вовсе.

### §3.14 `orbis/assignment` — назначение исполнителя (ADE-срез 1)

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/executor` | select | ✓ | Кто исполнитель: `human` \| `agent` |
| `orbis/grant` | grant | | Ссылка на `agent_grants.id` (§4.14) — конкретный доступ агента. **Обязателен при `orbis/executor=agent`** и запрещён при `human` (доменный инвариант executor'а, стадия 4 §9.2) |
| `orbis/assignee` | text {maxLength: 200} | | Кто именно, текстом — при `orbis/executor=human` |
| `orbis/may_close` | boolean {default: false} | | Разрешено ли исполнителю самому переводить тикет в `done`. Отсутствие значения = **запрет** (§9.3, С8): «не сказано» значит «нельзя» |

`tag_mappings`: `["assignee", "исполнитель"]`

**Отдельный аспект на сущности тикета, а не поле в `orbis/task`**: `orbis/task` живёт в личной ОС, где про исполнителей-агентов знать незачем. Аспект допустим на любой задаче — именно этим жестом задача становится тикетом.

**Плоский набор свойств, а не дискриминированное объединение по `orbis/executor`.** Свойство — единица словаря: у него один тип на всю систему, и «поле, которого при другом значении соседа не бывает» этим языком не выражается. Условная обязательность `orbis/grant` держится доменным инвариантом executor'а — в срезе А кодом (перевод его в правило каталога `requires_when` — часть Б, вместе с языком выражений).

**Инвариант проверяется, когда назначение затронуто.** При `entity_create` и `attach_*` — всегда при наличии аспекта; при `entity_update` — **только если патч трогает свойства назначения**. Иначе отзыв гранта замораживал бы тикет целиком (даже переименование), а отзыв закрывает доступ агенту, не сущность. Живость гранта (существует, принадлежит владельцу, не отозван) проверяется в тот же момент; захват тикета защищён отдельным CAS-предусловием по `orbis/grant` (§9.2).

Доступ агента адресуется **одним свойством** `orbis/grant` и здесь, и у прогона (§3.15) — до реформы это были два разных поля `grant_id` двух аспектов, и запрос по ним требовал уточнения `aspect=`. Теперь `orbis/grant=<id>` находит и назначения, и прогоны этого доступа одним условием, а разделить их можно аспектом — по желанию, а не по необходимости.

Плоского поля `project_id` у прогона больше нет [D43]: ручная денормализация «проект тикета» заменена **вычисляемым свойством** `orbis/parent_project` (§3.17), которое сервер считает по иерархическим рёбрам. Блок «Последние прогоны» в заготовке проекта (§3.12) адресует именно его.

**Прогон — сущность, дочерняя тикету ребром роли `run`, а не запись в треде** (С5): прогонов на тикет бывает несколько, по ним нужны запросы («что упало за неделю», «сколько стоил тикет»), и это данные, а не переписка. Роль `run` — системная: `relation_create` с ней из тула любого актора отклоняется (§4.2). «Чем было, чем стало» здесь не хранится второй раз — за это отвечает журнал действий §7.8 через `action_id` шага; прогон переживает его retention как долгоживущая сводка.

**Служебный (см. §3.8):** сущности с этим аспектом исключены из основных выдач, пока запрос сам его не назвал (02-core-os §3.9) — иначе каждый шаг прогона поднимал бы его в топ «свежего».

**Пишет прогон только сервер — глаголами исполнителя** (§9.2, §9.3): `attach_orbis_agent_run`-тула не существует, потому что аспект помечен колонкой `service` (§3.8). Сверх этого **18 из 19** его свойств несут флаг `system_writable`: запись пропускается только по **источнику мутации** — глагол исполнителя, хук, правило, материализация, сид, импорт (§4.2), — а не по актору; запись из тула, UI или MCP отклоняется отказом семейства `COMPUTED_WRITE`, кем бы вызов ни пришёл. Удерживает границу теперь механизм, а не текст `ai_instructions` [D43]. Девятнадцатое — `orbis/grant`, и исключение названо вслух: свойство общее с назначением (§3.14), а там грант выдаёт **владелец** кнопкой на экране тикета, то есть обычным источником; флаг живёт на свойстве, и `system_writable` сделал бы законный жест назначения агента невыполнимым. Служебность прогона держат остальные 18 свойств и XOR-инвариант субъекта. Скоуп `worker` (§4.14) такого пути не имеет вовсе. У рутинного прогона (V1) и этого пути нет: бухгалтерию пишет раннер, а внутреннему исполнителю круг глаголов закрыт целиком, кроме `orbis_checkpoint` (§9.3).

**Субъект прогона — ровно одно из `orbis/grant` / `orbis/run_routine`** [V1]. Тикетный прогон принадлежит доступу агента, рутинный — расписанию; прогона без субъекта не бывает (некому его отнести), прогона с двумя — тем более (неясно, чья это работа и чей откат). Языком реестра это **не выражается** намеренно: свойство несёт свой тип и свои границы, а «одно из двух» — межсвойственное условие, то есть правило каталога (`forbidden_when` — часть Б). В срезе А инвариант держит executor на стадии 4 (§9.2) — единственный путь записи в граф, — и проверяется он при `entity_create`, при `attach_*` и при `entity_update`, чей патч трогает свойства прогона.

Уточнения `aspect=` ради однозначности имени запросы к прогону больше не требуют: имена свойств namespaced, и `orbis/grant=…` — одно условие про один факт (кому принадлежит работа), какой бы аспект его ни нёс. Назвать аспект в запросе по-прежнему полезно — но как **отбор** («только прогоны»), а не как снятие двусмысленности.

### §3.16 `orbis/routine` — рутина внутреннего исполнителя (V1)

| Свойство | Тип | Req | Описание |
|---|---|---|---|
| `orbis/routine_stage` | select | ✓ | `active` — рутина работает, планировщик берёт её слоты; `paused` — временно выключена (стоп-краном §9.3 или рукой владельца) |
| `orbis/routine_at` | time (`ЧЧ:ММ`) | ✓ | Время срабатывания в **локальном времени владельца** (`user_settings.timezone`), не в UTC: «каждое утро в 7» обязано пережить перевод часов и переезд. Формат жёсткий — `07:00`, не `7:00`. Тип `time` заведён реформой ровно под этот случай |
| `orbis/routine_days` | select {cardinality: many, minItems: 1} | | Дни недели: `mo` \| `tu` \| `we` \| `th` \| `fr` \| `sa` \| `su` (та же нотация, что у `byweekday` recurring-правил `orbis/recurrence`, §3.1). **Свойства нет = каждый день**; пустой список — не «никогда», а ошибка валидации |
| `orbis/routine_mode` | select | ✓ | `propose` — рутина **предлагает** правки владельцу карточкой предложения и сама граф не трогает; `act` — применяет сама, инструментами из `orbis/allowed_tools`. Обязателен и **без умолчания**: умолчание `act` раздавало бы право писать в граф молча, умолчание `propose` — тихо разоружало бы уже заведённую автономную рутину |
| `orbis/allowed_tools` | text {cardinality: many, maxItems: 50} | | Белый список инструментов режима `act` — ровно те имена тулов (§9.2), которыми рутине разрешено писать. При `orbis/routine_mode=propose` смысла не имеет |

`tag_mappings`: `["routine", "рутина"]`

**«Что делать» лежит в теле сущности, а не в аспекте.** Инструкция рутины — обычный текст body («собери план дня, объясни почему так и предложи»), как постановка задачи в тикете и как описание процесса в проекте; в аспекте только расписание и права. Отдельного поля `instruction` нет намеренно: инструкция — это текст, который владелец правит редактором и версионирует снимками (§4.15), и загонять его в строку JSON-схемы значило бы завести второй, худший редактор.

**`orbis/routine` — не служебный** (в отличие от `orbis/agent-run`, §3.8: у него `service: false`): рутина видна в обычных выдачах, потому что это запись владельца, а не побочный артефакт системы. Прогоны её — служебные, как были.

**Стадия рутины — свой факт, и уточнять аспект ради однозначности больше не нужно** [D43]: `orbis/routine_stage=active` не пересекается с `orbis/project_stage` по построению. Запросы к рутинам аспект называют по-прежнему — `aspect=orbis/routine, orbis/routine_stage=active`, — но теперь ради **отбора**, а не ради снятия двусмысленности.

**Автономия выдаётся только рукой владельца** (§7.10): создание рутины с `mode: act` и правка `mode` / `allowed_tools` не-владельцем — уровень `explicit-confirmation` на любом транспорте, чат он или MCP. **Сама себе и другой рутине рутина ничего не выдаёт**: и `attach_orbis_routine`, и правка сущности с этим аспектом из фонового прогона отклоняются доменным инвариантом executor'а (§9.3) — иначе рутина в режиме `act` заводила бы себе вторую с любыми правами.

**`attach_orbis_routine` в реестре есть** — колонки `service` у аспекта нет, и тул генерируется ему наравне с остальными (§7.6, §9.2). Кто им воспользуется — вопрос отдельный: у владельца и чат-AI он есть (со ступенью подтверждения выше), у фонового прогона рутины — нет.

### §3.17 Свойства без аспекта-носителя

Аспект — не единственный способ существования свойства (§3.10). Шесть встроенных свойств аспекта не имеют вовсе, и это не пробел словаря, а два разных механизма.

**Вычисляемые проекции иерархии** — пишет их сервер, правило одно на оба:

| Свойство | Тип | Кто пишет | Описание |
|---|---|---|---|
| `orbis/parent_project` | ref {target: `aspect=orbis/project`}, computed | сервер | Ближайший проект вверх по иерархическим ролям рёбер (§4.2). Заменяет прежнюю ручную денормализацию `project_id` прогона (§3.15) |
| `orbis/root_project` | ref {target: `aspect=orbis/project`}, computed | сервер | Корневой проект той же цепочки |

Оба несут `model_writable: false` — попытка записи из тула, UI или MCP отклоняется отказом, а не игнорируется молча. Кэш пересчитывается **в той же транзакции**, что правка рёбер (правило 3 §10): при переносе поддерева пересчёт идёт по затронутому поддереву, а не по всему графу. Аспекта у них нет намеренно: «ближайший проект» — не интерпретация сущности, а проекция её места в графе; носитель-аспект пришлось бы навешивать на всё подряд.

**Core-проекции адресации** (§2.1) — четыре записи реестра поверх колонок `entities`:

| Свойство | Тип | Колонка |
|---|---|---|
| `orbis/archived` | boolean | `archived` |
| `orbis/title` | text | `title` |
| `orbis/created_at` | timestamp | `created_at` |
| `orbis/updated_at` | timestamp | `updated_at` |

У них `storage: core`: хранение остаётся колонкой, реестр даёт единый адрес для запросов (§6.1), CAS-предусловий (§9.2) и подписей. Флагов у них нет намеренно — запись идёт не через `props`, а путём ядра; **класть core-ключ в `props` запрещено на записи** общим валидатором: иначе под тем же именем у записи появилась бы вторая правда, которую не читает ни один боевой путь.

В счёт словаря (73 доменных свойства) core-проекции не входят — это отдельная категория адресации. Общие понятия будущих модулей (`orbis/date`, `orbis/weight`) заранее не заводятся: свойство без потребителя — сирота с первого дня, и садовник словаря (§4.16) начал бы приносить о нём отчёт.

## §4. Таблицы БД

**Восемнадцать таблиц** [D43]. Всё, что является сущностью (§2.2), живёт в `entities`; остальные — связи, шесть реестров структуры с журналом их персональных правок, конфигурация, чаты, журналы, доступы внешних агентов и закреплённые версии тела.

Восемь исходных описаны в §4.1–§4.8, две таблицы доступа агентов (D34) — в §4.13–§4.14, версии тела (D37) — в §4.15, реестры реформы — в §4.16, **после** сквозных подразделов §4.9–§4.12. Номера подряд за §4.8 не заняты по недосмотру: §4.9 (индексы) и §4.10 (RLS) — самые цитируемые адреса комплекта, на них ссылаются код, миграции, pgTAP-сьют и спайки, и перенумерация ради красивого порядка порвала бы эти ссылки молча. По той же причине реестры реформы дописаны в конец главы, а не вставлены рядом с `aspect_definitions` (§4.3).

### §4.2 `relations`

| Столбец | Тип | Описание |
|---|---|---|
| `id` | uuid PK | Генерируется клиентом |
| `source_id` | uuid NOT NULL | FK → `entities.id`, ON DELETE CASCADE |
| `target_id` | uuid NOT NULL | FK → `entities.id`, ON DELETE CASCADE |
| `role` | text NOT NULL | **Единственная истина ребра** [D43] — id строки реестра ролей (§4.16) |
| `meta` | jsonb NOT NULL default `{}` | Системное поле: `{source: "body_ref", auto: true}` у неявных связей из body, `{property: "<id свойства>"}` у зеркала ссылочного значения. Пользователю не открывается — свойств на рёбрах в v1 нет |
| `created_at` | timestamptz NOT NULL | |
| `updated_at` | timestamptz NOT NULL | Время правки для UI/диагностики |

**Одиннадцать системных ролей v1** — прежние четыре типа связи расщеплены по смыслу [D43]. `parent` был одним словом на пять разных отношений, и из-за этого «дети конверта» и «дети проекта» приходилось разделять доменными условиями:

| Роль | Стороны (source → target) | Иерархическая | Ограничения | Кто создаёт |
|---|---|---|---|---|
| `subitem` | Родитель → Подпункт | да | — | любой |
| `ticket` | Проект → Тикет | да | `target_contract` (часть Б) | любой |
| `run` | Субъект прогона → Прогон | да | — | только система |
| `envelope-binding` | Конверт → Транзакция | нет | `target_max_incoming: 1` | только система |
| `category-parent` | Родительская категория → Подкатегория | да | `acyclic` | любой |
| `dependency` | Блокирующая работа → Заблокированная | нет | `acyclic` | любой |
| `mention` | Упоминает → Упомянуто | нет | — | любой |
| `instance-of` | Шаблон → Экземпляр | нет | — | только система |
| `ref` | Откуда ссылка → Цель ссылки | нет | — | только система |
| `alternative-of` | Альтернатива → Исходный вариант | нет | — | любой |
| `supersedes` | Замена → Замещённое | нет | — | любой |

**Иерархических ролей четыре** — `subitem`, `ticket`, `run`, `category-parent`: именно их разворачивает `children_of`/`descendants_of` без `via=` (§6.1). `envelope-binding` в семейство иерархии **не входит**: конверт не родитель транзакции, он её счётчик. Две последние роли — `alternative-of` и `supersedes` — засеяны заранее, под карту работ; кода-потребителя у них пока нет, и это чистые записи реестра.

**«Только система» — про источник мутации, а не про актора** [D43]: роль с ограничением `created_by: system` ставят хук, правило, материализация, глагол исполнителя, сид или импорт; `relation_create` такой роли из тула — отказ `ROLE_SYSTEM_ONLY`, кем бы вызов ни пришёл, включая владельца.

**Терминологическая сноска.** Перечень источников мутации — `user`, `hook`, `rule`, `materialize`, `seed`, `action-seed`, `verb`, `import` — спека реформы называет `MutationSource`; в коде он называется `mechanism`, потому что имя `MutationSource` там уже занято другой осью — **каналом** вызова (`ui`, `chat`, `fast_path`, `quick_capture`, `mcp`, `routine`, `system` — §7.8). Оси две и они независимы: «чем сделано» и «откуда пришло». Гейты `created_by` и `system_writable` смотрят на первую [пометка РП-4 плана D43].

Стороны ребра подписаны в реестре (`source_label` / `target_label`), и подписи едут в UI: backlinks показывают «Конверт» и «Транзакция», а не «источник» и «цель».

Constraints: `CHECK (source_id != target_id)` (запрет связи с самим собой); unique index `UNIQUE (source_id, target_id, role)`. Пара сущностей может нести рёбра **разных ролей** одновременно. Удаление связи — обычный `DELETE`; пересоздание удалённой связи — новая строка с новым `id`, как и любая другая вставка.

**Ограничения ролей — данные, а не код.** `target_max_incoming` и `acyclic` объявлены в строке реестра (`constraints`), и проверяет их исполнитель, читая порог оттуда. Третье поле там же — `target_contract` у роли `ticket` («цель тикета обязана быть завершаемой»): оно **лежит, но не работает** — проверять его нечем, пока нет контрактов (**часть Б; в срезе А не реализовано**). Первым в реестр переехал доменный инвариант финансов: «одна транзакция списывается максимум из одного конверта» — это `target_max_incoming: 1` у роли `envelope-binding`, а не отдельное правило про budget-parent'ов (§13 п.7). Перенос второй партии инвариантов в правила каталога — часть Б; в срезе А **работают** ровно эти два generic-ограничения, остальное остаётся кодом.

**Ацикличность зависимостей.** Граф рёбер роли `dependency` обязан оставаться ацикличным: сервер отклоняет создание ребра, замыкающего цикл, со структурированной ошибкой, содержащей путь цикла («A → B → C → A»). То же ограничение объявлено у `category-parent` — и это **новое поведение реформы**: до неё цикл в дереве категорий ничем не запрещался. Поведение UI при отказе — 02-core-os.md §6.

### §4.3 `aspect_definitions`

| Столбец | Тип | Описание |
|---|---|---|
| `id` | text NOT NULL | Тождество, не меняется никогда: `orbis/task`, `user/sleep` (уникальность — см. ниже) |
| `owner_id` | uuid | NULL = встроенный аспект; иначе — владелец кастомного |
| `key` | text NOT NULL | Машинная ручка: ASCII-слаг в namespace автора. Из него строится имя тула `attach_*` (§9.2). У встроенных изначально равен `id` |
| `label` | jsonb NOT NULL | Подпись per-locale `{ru, en}` — то, что видит человек |
| `description` | jsonb NOT NULL | Смысл per-locale; обязателен — это единственный носитель смысла для AI и основание «одно и то же?» при разборе дублей |
| `properties` | jsonb NOT NULL default `[]` | Состав интерпретации: `[{propertyId, required, rank}]` — ссылки на строки реестра свойств с обязательностью и порядком |
| `implements` | jsonb NOT NULL default `[]` | Привязки к контрактам (часть Б). В срезе А **пусто у всех тринадцати** |
| `service` | boolean NOT NULL default `false` | Служебный аспект: сущности с ним прячутся из выдач, `attach_*`-тул не генерируется (§3.8) |
| `ai_instructions` | text | Фрагмент описания тула: когда и как AI применяет аспект |
| `tag_mappings` | text[] NOT NULL default `{}` | Теги, намекающие на аспект (подсказки AI и конструктора) |
| `aggregations` | jsonb default `{}` | Клапан под декларацию материализации агрегатов (§12 п.1). Часть Б; в срезе А не используется |
| `view_config` | jsonb default `{}` | Подсказки рендеринга для generic-views: `keyFields` (ключевые свойства строки), иконка |
| `module` | text | Модуль-владелец; NULL = ядро |
| `rank` | integer NOT NULL | Порядок объявления — им же упорядочены `attach_*`-тулы |
| `created_at` | timestamptz NOT NULL | |

Колонки `schema` у аспекта **нет** [D43]: JSON Schema — генерируемая производная набора свойств (§3), а хранимая копия неизбежно расходилась бы с реестром свойств. Прежние `name` + `namespace` заменены парой `key` + `label`: машинная ручка и человеческая подпись — разные вещи с разными судьбами (одну меняет только релиз системы, вторую — владелец в своей локали).

Уникальность — два partial unique index, без surrogate PK: встроенные аспекты (`owner_id IS NULL`) — глобально уникальный `id` (`UNIQUE (id) WHERE owner_id IS NULL`); кастомные — `UNIQUE (owner_id, id)`. Два пользователя могут завести каждый свой `user/sleep`, не конфликтуя; в видимости одного пользователя (встроенные + свои) `id` однозначен, поэтому id в `entities.aspects` резолвятся без коллизий. Тот же приём и та же пара индексов — у всех реестров реформы (§4.16).

| `agent_grants` | UNIQUE (`access_hash`), UNIQUE (`refresh_hash`), UNIQUE (`code_hash`) | Аутентификация агента — лукап строки по хешу предъявленного токена (§4.14) |
| `agent_grants` | b-tree (`owner_id`) | Список выданных доступов на экране «Настройки → Агенты» |
| `entity_versions` | b-tree (`entity_id`, `created_at` DESC) | Версии одной сущности, свежие сверху (§4.15) — покрывает и фильтр, и порядок |

**Честная оговорка про GIN на `entities`** [D43]. Замер планов под ролью приложения (2026-08-27, локальный Postgres, корпус 50 000 сущностей) показал: **ни один** GIN на `entities` планировщиком не выбирается и не становится пригодным даже при выключенном seqscan — ни новые (`props`, `aspects`, `query_refs`), ни пять существовавших до реформы (`tags`, `meta`, старая карта аспектов, оба FTS). Под админским подключением те же запросы GIN берут: 0,5 мс против 44 мс на 50 000 строк. Причина найдена до корня и лежит вне реформы: политика RLS `owner_owns_row` (§4.10) — это security qual, а операторы containment (`@>`, `?`) не помечены `leakproof`, поэтому планировщик обязан применить политику до них. Это **свойство модели доступа, а не реформы**, и «индекс не выбран» само по себе не означает «снять его»: индексы на `relations` по паре `(source_id, role)` выбираются и несут рекурсивный обход. Судьба конкретных GIN решается вердиктом отдельного скрипта планов (`docs/implementation/02-ops-runbook.md` §8.1), а не догадкой; сам вердикт пиннится тестом, чтобы «стало лучше» и «сломалось» не выглядели одинаково.

### §4.10 Row Level Security

Принцип один: **каждая строка принадлежит ровно одному пользователю, и видит/меняет её только владелец**. Политика-шаблон для всех таблиц с `owner_id`:

```sql
CREATE POLICY owner_owns_row ON <table>
  FOR ALL
  USING (owner_id = auth.uid())
  WITH CHECK (owner_id = auth.uid());
```

Особые случаи:

- `relations` (нет своего `owner_id`) — чтение и изменение разрешены, только если **обе** связанные сущности принадлежат `auth.uid()`; это одновременно запрещает межпользовательские связи;
- `chat_messages` (нет своего `owner_id`) — доступ только через `chat_threads.owner_id = auth.uid()` по `thread_id`; вставка дополнительно проверяет принадлежность треда текущему пользователю;
- **шесть реестров структуры** (§4.16) — один шаблон на все: встроенные записи (`owner_id IS NULL`) читаемы всеми, изменяемы только service-role (сидом); свои строки владельца — по шаблону владельца, четырьмя политиками `read_builtin_or_own` / `write_own` / `update_own` / `delete_own`. Каждой таблице выдан **явный** `GRANT SELECT, INSERT, UPDATE, DELETE … TO authenticated`: общий грант «на все таблицы» из первой миграции на созданные позже не распространяется, и без своего гранта запрос упёрся бы в `42501` **до** всякой политики;
- `registry_deltas` (§4.16) — чисто владельческая таблица: одна политика `owner_owns_row` по шаблону выше, встроенных строк у неё не бывает;
- `registry_system` (§4.16) — одна глобальная строка версии system-реестра: политика только на чтение (`USING (true)`), политик записи нет **намеренно** — под `FORCE ROW LEVEL SECURITY` это отказ `42501` для всех, кроме service-role, которая ходит мимо;
- **третья категория строк — приложения** (`<app>/`, D36): решение записано заранее, самих приложений в v1 ещё нет. Установка приложения **копирует его словарь владельцу** под его `owner_id`, то есть третьей политики не заводится вовсе — строка приложения выглядит как своя строка владельца. Глобального неймспейса приложений до marketplace нет, и это названо как временное решение, а не как модель;
- `entity_versions` (§4.15) — `WITH CHECK` **шире** `USING`: к владению строкой на записи добавлено владение самой сущностью (`EXISTS` по `entities`). Одного `owner_id = auth.uid()` мало — RI-проверка внешнего ключа идёт мимо RLS и чужую сущность прекрасно видит, поэтому прошла бы вставка строки со своим `owner_id`, но `entity_id` чужой записи, то есть «версия чужого тела». Читаемость строки при этом определяется владением самой строкой, и `USING` не сужается;
- `agent_grants` и `oauth_clients` (§4.13–§4.14) — **первое из двух мест, где одной политики недостаточно**, и причина названа прямо: аутентификация агента ищет строку **по хешу токена, пока владелец ещё неизвестен**, то есть до того, как транзакционная identity вообще может быть установлена. Поэтому политик две: владельцу под ролью `authenticated` — его строки по шаблону выше (это питает экран настроек и отзыв), серверной роли `orbis_app` — доступ для лукапа по хешу, отметки `last_used_at` и регистрации клиентов. У `oauth_clients` политики для `authenticated` нет вовсе: регистрация DCR не принадлежит никому, и владелец видит клиента только через свой грант;
- `user_settings` — **второе такое место, и по той же природе** (V1, D38): планировщик рутин (§9.3) просыпается по таймеру, и владельца у него нет **по построению** — он должен сначала узнать, кого обходить. Поэтому к политике владельца добавлена вторая, `scheduler_reads_owner_list`: `FOR SELECT TO orbis_app USING (true)` плюс `GRANT SELECT ON user_settings TO orbis_app` (миграция `0013`). Грант нужен наравне с политикой: `orbis_app` — `NOINHERIT`-член `authenticated`, а гранты на таблицы висят именно на `authenticated`, и без своего гранта запрос упёрся бы в `42501` **до** всякой политики. Три вещи, которыми эта дыра ограничена: (1) источник — `user_settings`, а не `entities`: то же множество владельцев, но у́же по данным — тела рутин и всего остального служебной роли не открываются; (2) только `SELECT` — настройки пишет владелец под `authenticated`, там всё по-прежнему; (3) `BYPASSRLS` не вводится, у `orbis_app` стоит `NOBYPASSRLS` — обход владельцев остаётся единственным действием без identity, а **всё дальнейшее** (отбор активных рутин, создание прогона, любая мутация) планировщик делает уже под `withIdentity(владелец)` и обычной `owner_owns_row`. `USING (true)` сузить нечем: под `orbis_app` `auth.uid()` пуст, и предикат `owner_id = auth.uid()` был бы всегда ложным, то есть закрыл бы сам обход. Границу здесь держит не предикат, а то, что DSN роли `orbis_app` не покидает сервер — тот же размен, что у `server_manages_grants` выше.

Все внешние ключи, которые косвенно задают владельца (`chat_messages.thread_id`, `relations.source_id/target_id`), покрыты индексами, чтобы RLS-проверка не превращала чтение в полный scan. Политики генерируются из одного шаблона — будущий переход owner→membership правится в одном месте (D11).

RLS проверяется **pgTAP-сьютом до деплоя схемы**, а не наблюдением на проде: с реформой сьют покрывает все восемнадцать таблиц. Это прямой урок слайса MCP-OAuth — политику, написанную в миграции и не проверенную тестом, легко объявить работающей.

### §4.11 Реестр тегов — вычислимый

Отдельной таблицы тегов нет. Реестр тегов (для автокомплита, фильтров, цветов) — агрегация `SELECT unnest(tags), count(*) FROM entities GROUP BY 1` плюс клиентский кэш (TanStack Query, §5.1), обновляемый при записи сущностей. Цвета тегов — `user_settings.tagColors`.

### §4.12 Клиент vs сервер

Клиент — тонкий: вся модель данных §4 существует только на сервере (PostgreSQL), собственной базы данных у клиента нет. Server-state-кэш (TanStack Query) — деталь реализации фронтенда, а не хранилище: он держит в памяти последние прочитанные данные для мгновенного рендера и инвалидируется после мутаций (§5.1), но не является источником истины и не переживает предназначенный ему жизненный цикл вкладки. Единственные персистентные клиентские данные — retry-буфер неотправленных create-мутаций fast-path-ввода (§5.3): небольшая очередь, переживающая перезагрузку страницы до подтверждения сервером. Любые другие данные, видимые в UI без сети, — это то, что успел закэшировать TanStack Query до потери соединения, а не гарантированный офлайн-доступ.

### §4.14 `agent_grants`

| Столбец | Тип | Описание |
|---|---|---|
| `id` | uuid PK | |
| `owner_id` | uuid NOT NULL | Владелец, от чьего имени действует агент |
| `client_id` | text NULL FK → `oauth_clients` | NULL у PAT; `ON DELETE cascade` |
| `kind` | text NOT NULL | `oauth` \| `pat` (CHECK) |
| `label` | text NOT NULL | Подпись в списке доступов: у PAT — назначение («CI»), у OAuth — имя клиента на момент выдачи |
| `scope` | text NOT NULL default `'full'` | Область доступа: `full` — весь граф владельца, `worker` — фоновый исполнитель (D37, ниже) |
| `code_hash`, `code_challenge`, `code_expires_at`, `code_used_at`, `redirect_uri` | | Одноразовый код авторизации (только у `oauth`) |
| `access_hash`, `access_expires_at` | | Текущий access-токен |
| `refresh_hash`, `refresh_expires_at` | | Текущий refresh (ротируется при каждом обмене) |
| `prev_refresh_hash` | text | След предыдущего refresh — без него предъявленный повторно старый токен не с чем связать |
| `created_at`, `last_used_at`, `revoked_at` | timestamptz | Питают экран «Настройки → Агенты» |

Весь жизненный цикл доступа внешнего агента одной строкой (§9.3, D34) — и браузерного, и headless: один механизм отзыва и один экран на оба вида.

Инварианты: в базе хранятся **только `sha256`** токенов, сырые значения не восстановимы (контракт hash-only, §9.3); одноразовость кода обеспечивается атомарным `UPDATE … WHERE code_used_at IS NULL RETURNING`, а не проверкой в коде — гонка двух обменов отдаёт строку ровно одному; отзыв — проставление `revoked_at`, действует немедленно и по одному доступу. Сроки: access — 1 час, refresh — 30 дней с ротацией, код — 60 секунд; у PAT срока нет (гасится строкой, а не временем).

**Семантика `scope` (D37).** Значений два — `full` и `worker`.

- `full` — сегодняшнее поведение и DEFAULT колонки: весь граф владельца под политикой подтверждений §7.10.
- `worker` — фоновый исполнитель: **чтения целиком**, пять глаголов исполнителя (§9.2) и `thread_post` в свой периметр (ниже); любая другая запись в граф отклоняется на сервере структурированным отказом. **Тулов реестра у него нет вовсе** [D43] — ни на запись, ни на чтение каталога свойств: перенастраивать устройство системы фоновому исполнителю нечем даже с подтверждением. Чтение не сужено осознанно — риск полного чтения личного графа фоновым исполнителем принят владельцем явно (граница названа в спеке среза).

**Периметр `thread_post` у `worker`** — треды **назначенных этому гранту тикетов** и **их прямых родителей по иерархическим ролям** (проект или родительская задача — периметр задаёт ребро, а не тип родителя). Всё остальное — отказ `FORBIDDEN_LEVEL`, и он одинаков для чужой и для несуществующей сущности: исполнителю не с чего узнавать, что за пределами его назначений вообще что-то есть, поэтому существование не раскрывается даже кодом ошибки. Проверка идёт **до** создания треда и записи.

Гейт **fail-closed по факту, а не по имени**: доступ сужается при любом значении, кроме `full`, — колонка текстовая, и незнакомое значение обязано сужать, а не открывать. Стоит он в диспатче тулов, до классификатора §7.10: скоуп — ось доступа, а классификатор по актору сознательно не ветвится (§7.10). Код отказа один на обе проверки — `FORBIDDEN_LEVEL`: во внутреннем API он едет как 403, во внешнем MCP — ответом с `isError`, а не транспортной ошибкой.

Область выбирается **при выдаче доступа** и после этого не меняется: на экране согласия — радио «Полный доступ» / «Только исполнитель (worker)», у headless-токена — `bun scripts/ops.ts issue-pat … --scope worker` (опечатка в области — отказ, а не откат на полный доступ; `docs/implementation/02-ops-runbook.md` §3.2). Параметр `scope` в запросе клиента **игнорируется** — область назначает владелец, не агент; метаданные authorization server объявляют `scopes_supported: ["full", "worker"]`, а `/oauth/token` отдаёт область выданного гранта на обоих путях. В «Настройки → Агенты» область видна бейджем.

### §4.15 `entity_versions`

| Столбец | Тип | Описание |
|---|---|---|
| `id` | uuid PK | UUIDv7, генерирует сервер |
| `owner_id` | uuid NOT NULL | Владелец снимка |
| `entity_id` | uuid NOT NULL FK → `entities` | `ON DELETE cascade`: снимок тела без своей записи ничего не значит |
| `label` | text NOT NULL | Подпись версии — своими словами, её пишет человек |
| `body` | text NOT NULL | markdown-проекция на момент снимка — **всегда**: она читаема без редактора и переживает смену схемы документа |
| `body_doc` | jsonb | Документ, если он у сущности на момент снимка уже был |
| `actor_user_id`, `actor_kind` | uuid NOT NULL, text NOT NULL | Кто закрепил (`owner` \| `agent`) — нейминг по D11 |
| `created_at` | timestamptz NOT NULL default `now()` | |

Индекс `(entity_id, created_at DESC)` — выдача версий одной сущности всегда «свежие сверху»: он покрывает и фильтр, и порядок.

**Версию создаёт человек по решению, с подписью** (D37, С11): сплошной автоматической истории правок нет и не откладывается — сохранение в редакторе идёт по паузе в наборе, и автоматическая история дала бы версию на каждую паузу. Снимок и откат — **только тело**: значения свойств в снимок не входят (у тикета статус — состояние процесса, и его откат вернул бы работу назад мимо правил §9.3), связи не входят по той же причине. Откат пишет восстановленное тело **через executor тем же конвейером** (§9.2), что обычная правка, — содержание возвращается канонично эквивалентным, не побайтно.

Версии — не сущности (§2.2): на них не ссылаются связями, и по снимку на сущность они засорили бы Browser. RLS — особый случай §4.10.

### §4.16 Реестры структуры [D43]

Шесть таблиц одного устройства плюс две служебные. Устройство общее: **код → сид → таблица → drift-сверка → RLS → кеш**; колонки `module`, `rank`, `created_at` и та же пара partial unique index (§4.9) — у всех шести. Четвёрка имён `id` / `key` / `label` / `description` с одинаковой семантикой (§4.3) — у **пяти**. У подписки из четырёх есть только `id` (тождество строки, им её адресуют дельта и журнал); `key`, `label` и `description` у неё **отсутствуют**, и это не пробел: подписку не показывают человеку списком и не адресуют из текста запроса — её строка отвечает на два вопроса, `surface` (на какой поверхности) и `definition` (что показывать), а подписывать отдельно нечего.

| Таблица | Что описывает | Состояние в срезе А |
|---|---|---|
| `property_definitions` | Свойство: тип, статус, хранение, область показа | 77 встроенных строк |
| `aspect_definitions` | Аспект: набор свойств, инструкции, служебность (§4.3) | 13 встроенных строк |
| `relation_role_definitions` | Роль ребра: стороны, иерархичность, ограничения (§4.2) | 11 встроенных строк |
| `contract_definitions` | Контракт: слоты, классы, наборы | **создана пустой** (часть Б) |
| `subscription_definitions` | Подписка поверхности на контракт | **создана пустой** (часть Б) |
| `action_definitions` | Действие: параметры, шаги, чувствительность | **создана пустой** (часть Б) |
| `registry_deltas` | Персональные правки владельца поверх системных определений | живая |
| `registry_system` | Одна строка: версия system-реестра и время последнего сева | живая |

Реестров, сидируемых манифестами модулей, спека реформы считает **пять** — действия приезжают вместе с языком выражений части Б. Таблиц-реестров при этом шесть, и по шести идёт сверка с кодом; расхождение в счёте — терминологическое, а не дефект: `action_definitions` устроена как реестр и создаётся вместе с остальными, просто её сид отложен.

**Строка свойства** — норматив значения на всю систему:

| Столбец | Описание |
|---|---|
| `id` | Тождество, не меняется никогда. У встроенных — читаемая строка (`orbis/task_status`), у пользовательских и приложений — uuid. Показывать id человеку — баг |
| `owner_id` | NULL = встроенное; иначе владелец |
| `key` | Машинная ручка: имя в тексте запроса, имя параметра тула, ключ канонического экспорта. У встроенных изначально равен `id`; меняется **только релизом системы** — ни дельта, ни владелец `key` встроенного не трогают. Алиасов у `key` нет |
| `label`, `description` | Подпись и смысл per-locale. `description` обязателен: он уезжает в описание параметра тула и в каталог, и он же — основание «одно и то же?» при разборе дублей |
| `type` | `{kind, …конфиг}` из закрытого словаря (ниже). Тип у свойства **один**; смена типа — не правка, а форк нового свойства |
| `status` | `active` \| `proposed` \| `deprecated` |
| `storage` | `props` (значение в карте) \| `core` (значение в колонке `entities`, §3.17) |
| `scope` | Статический Q-AST: «показывать колонкой на сущностях, подходящих под условие, без аспекта». Заполнено — часть Б: в срезе А значение читается только графом зависимостей и в запрос не компилируется |
| `merged_into` | Указатель слияния: резолвер следует по нему **в один шаг**, цепочек `A→B→C` не бывает по построению |
| `module`, `rank`, `flags`, `created_at` | Модуль-владелец (NULL = ядро); порядок в каталоге и в форме; флаги записи; время создания |

**Словарь типов закрыт**: `text` (с `pattern`, `format`, границами длины), `number`, `decimal`, `boolean`, `date`, `timestamp`, `time`, `select` (варианты со стабильным ASCII-ключом, подписью per-locale и порядком), `ref` (ссылка на сущность с Q-AST-множеством целей), `json` (вложенный объект со схемой), `grant` (ссылка в `agent_grants`), `registry_ref` (ссылка на строку реестра). Сквозные конфиги — `cardinality: many` с обязательным `maxItems` у списков скаляров и границы `min`/`max`/`maxLength`. Расширять словарь можно только по правилу «форма понадобилась ≥ 2 раз»: новый kind под один случай — это второй язык. Паттерны проверяются на принадлежность классу RE2 при записи (`PATTERN_NOT_REGULAR`): регулярка с lookaround не переживает экспорт схемы в не-ECMA движок — ровно это когда-то вынудило `strict: false` у одного из LLM-провайдеров (§7.7).

**Флаги записи** — три, и все проверяются механизмом, а не уговором: `model_writable: false` (запись из тула, UI или MCP — отказ), `system_writable: true` (запись проходит только по источнику мутации: хук, правило, материализация, сид, глагол исполнителя, импорт), `computed: {rule}` (значение выводится сервером — §3.17).

**Системное определение неизменяемо; правки владельца — дельты.** Строка реестра, приехавшая из кода сидом, не правится на месте: персональные изменения (подпись, описание, порядок, скрытие свойства, добавленное к встроенному аспекту свойство, добавленный вариант `select`) живут строкой `registry_deltas` с `target_kind`, `target_id` и `base_version`. Эффективное определение = система ⊕ дельта, и держит его процессный кеш (ниже). Типы и `key` встроенных дельта не меняет никогда. Когда релиз меняет системное определение, поверх которого лежит живая дельта, система **не выбирает молча**. Разбирает это **пересев реестров** (не старт процесса: у старта нет актора, и писать владельцу он не вправе), и разбирает по трём правилам §А3-3 — но единицей пачки решений (§7.10) становится **только один конфликт из трёх** [отклонение от буквы спеки, рулинг ветки D43]: тот, где выбор ещё есть, — система завела вариант, похожий по подписи на пользовательский, и слить их может только владелец. Два других правило решает само и решает правильно: вариант, совпавший по ключу, снимается (иначе применение упало бы на дубле), а скрытие свойства, ставшего обязательным, отменяется (иначе аспект нельзя было бы записать) — о них владельцу идёт заметка, а не карточка с кнопкой, которая ничего не меняет.

**Версия реестров — две половины.** `registry_system.version` двигает системный сид, `user_settings.registry_version` — любая мутация реестров владельца, **в той же транзакции**, что сама мутация. Процессный кеш эффективных определений живёт по ключу «владелец + пара версий»: смену версии не переживает ни он, ни кеши, построенные поверх него. Версия едет наружу в ответе чтения сущности — клиент по ней понимает, что форму надо перечитать.

**Строки реестров физически не удаляются** — только `deprecated` или `merged`: иначе повисли бы ссылки в сохранённых запросах, в дельтах и в данных. Единственное исключение — `proposed`, отклонённое до первого использования (ни значений, ни ссылок — проверяется в той же транзакции).

**Три операции над свойством, и все — через исполнителя, с журналом и undo:** сослаться (данных не трогает), переименовать подпись (бесплатно, данных не трогает), **слить** два свойства в одно. Слияние — одно действие с одним inverse: проставить `merged_into`, переписать ключи в `props` затронутых записей, переписать ссылки в сохранённых деревьях запросов (их адреса даёт `query_refs`, §4.1) — и всё это под замком реестра владельца. Конфликт значений на одной сущности слияние **не решает молча**: оно ждёт разбора пачки, частичного слияния не бывает. Операции «переименовать id» или «переименовать key» не существует вовсе.

**Жизненный цикл `proposed`.** Свойство, заведённое AI от себя, приходит со статусом `proposed`; неразобранных таких у владельца не больше **20** — двадцать первое предложение получает отказ с подсказкой «разберите пачку». Разбирает их владелец: в чате — диффом, у фоновой рутины — единицей пачки решений (§7.10). Раз в неделю (понедельник, 09:00 по локальному времени владельца) по ним проходит **садовник словаря** — рутина, засеваемая онбордингом (02-core-os §7.4): сводит дубли и приносит отчёт о сиротах (свойство без аспекта и без значений) и о `proposed` старше двух недель. Правит он не молча: его белый список — ровно один тул слияния, а слияние от рутины политика поднимает до явного подтверждения и кладёт отложенной единицей (§7.10). Отклонённое свойство скрывается, а значения на сущностях **остаются**.

**Как выглядит дрейф.** Сервер на старте сверяет системные строки всех шести реестров с кодом (§3) — сверка двусторонняя, лишняя строка в базе тоже дрейф — и объявляет результат полем `registryDrift` в `/health`. Строка дрейфа несёт **имя реестра**: `aspects:orbis/task` и `properties:orbis/task` — разные вещи, и без имени их было бы не отличить. Персональные дельты стартовая проверка не видит по построению: она ходит без актора, а дельты закрыты RLS владельца; расхождения по ним показывает операторская команда сверки (`docs/implementation/02-ops-runbook.md` §1).

## §5. Персистентность и конкурентность

### §5.1 Источник истины и кэш

PostgreSQL (Supabase) — единственный источник истины: все чтения и записи в конечном счёте идут через tRPC в Postgres, собственной базы данных у клиента нет (§4.12). Мгновенность UX обеспечивают два механизма фронтенда, оба — детали клиентской реализации, не протокол: **server-state-кэш** (TanStack Query) — данные, однажды прочитанные с сервера, рендерятся мгновенно при повторной навигации и **инвалидируются после любой мутации**, вызывая перечитывание с сервера; и **оптимистичные обновления** — UI показывает результат мутации сразу, не дожидаясь ответа сервера, и откатывает изменение, если сервер вернул ошибку. Сервер не знает и не обязан знать о состоянии кэша конкретного клиента.

### §5.2 Конкурентность

Разрешение конфликтов — **last-write-wins (LWW) на уровне API**: из двух конкурентных мутаций одного ресурса побеждает та, что сервер обработал последней. Для правок `body` — поля, где тихая перезапись стирала бы набранный пользователем текст, — действует **optimistic-check по `updated_at`**: мутация обязана передать `updated_at` версии, которую клиент прочитал перед правкой; если серверное значение уже другое, правка **отклоняется структурированной ошибкой**, а не применяется поверх более новых данных. UI на отказ предлагает перезагрузить сущность и повторить правку вручную — автоматического merge нет. Известный компромисс: две вкладки или устройства, одновременно правящие один и тот же `body`, могут получить отказ — это осознанное ограничение (§12).

### §5.3 Retry-буфер ввода

Офлайн в Orbis — не режим работы, а буфер на входе. Буферизуются **только** create-операции fast-path-ввода (§7.5): каждая создаётся с client-generated UUIDv7 (§2.1) и складывается в локальную очередь, если запрос не смог уйти на сервер. Контракт буфера:

- **Идемпотентность по client-UUID обязательна и онлайн.** Повтор браузера, упавшая вкладка, разрыв соединения после отправки запроса, но до получения ответа — сервер обязан принимать повторный create с тем же UUID как один и тот же результат, а не создавать дубль. Это не офлайн-специфичное свойство.
- **Буфер различает transport failure и business rejection.** Обрыв соединения, таймаут — ретраится автоматически. Отказ сервера по бизнес-правилу (валидация, доменный инвариант, entitlement) — не ретраится, показывается пользователю как ошибка.
- **Удаление из очереди — только по подтверждению сервера.** Запись покидает буфер, когда сервер вернул успех или окончательный business-отказ, показанный пользователю; потеря сетевого пакета в процессе — не повод считать мутацию отправленной.
- **`CONFLICT` — «id непригоден», а не «уже сохранено».** Честный повтор владельца с тем же UUID сервер отдаёт replay-успехом (§9.2, идемпотентность create), поэтому `CONFLICT` означает ровно одно: id занят строкой, невидимой владельцу, — записи владельца на сервере НЕТ. Буфер делает один повтор с **детерминированной производной** исходного id (`uuidv5` от него), а не со случайным: потерянный ответ на такой повтор оставляет в очереди прежний payload, и следующая досылка берёт ТУ ЖЕ производную — сервер отвечает replay-успехом на свою же строку вместо второй сущности. Второй `CONFLICT` подряд — окончательный отказ (запись покидает очередь, ошибка показана).
- **Корректность не зависит от service workers / Background Sync.** Буфер — обычное персистентное клиентское состояние (единственное, §4.12); он досылает накопленное при следующем открытии приложения с сетью, но не полагается на фоновые браузерные API, недоступные на всех платформах.

Офлайн-**правки** существующих сущностей недоступны: буфер работает только для create fast-path, не для update/delete и не для LLM-пути.

### §5.4 Детерминированные ID порождаемых сущностей

Все сущности, которые система порождает по расписанию от шаблона, получают ID не случайно, а детерминированно. Формула byte-точная:

```
id = uuidv5(ORBIS_NAMESPACE, name)

ORBIS_NAMESPACE = "cb339e97-82d7-4d16-91c6-942d42df7054"   // фиксированная константа проекта
name            = "<template_id>:<YYYY-MM-DD>"
```

где `template_id` — UUID шаблона **в lowercase**, `<YYYY-MM-DD>` — дата экземпляра, вычисленная в таймзоне `orbis/timezone` шаблона, а при её отсутствии — в таймзоне пользователя из `user_settings.timezone`.

Пример вычисления: шаблон `019ded47-d100-717a-8307-a5b7a5be722f`, инстанс на 1 июля 2026 →

```
name = "019ded47-d100-717a-8307-a5b7a5be722f:2026-07-01"
id   = uuidv5("cb339e97-82d7-4d16-91c6-942d42df7054", name)
     = "e7d0bfa4-f62a-59c1-b560-1c17cb32e89f"
```

**Порождает только сервер.** uuidv5-инстансы вычисляет исключительно сервер при материализации; клиент их не порождает. Конкурентные запросы материализации одного шаблона на одну дату (несколько вкладок, повторные вызовы) сходятся к одному и тому же ID — дубль невозможен по построению, независимо от того, сколько раз материализация была запрошена.

**Материализация инстансов.** Инстансы recurring-шаблонов создаются лениво: любой запрос диапазона дат потребителем канона (Agenda, query-блоки, Budget) материализует инстансы видимого диапазона, но не дальше горизонта **14 дней вперёд** от сегодня. Финансовый инстанс получает `orbis/occurred_on=<дата инстанса>` и `orbis/planned=true`, пока дата не наступила; переход в факт определён в §3.3. Идемпотентность гарантирована детерминированными ID: уже созданные инстансы не пересоздаются и не перезаписываются.

Применения: экземпляры повторяющихся операций и событий (`orbis/recurring` + `orbis/recurrence`), чекины привычек (future, §11). Это правило 2 проектирования аспектов (§10).

**Формулы, включающие идентификатор пользователя.** Помимо инстансов от шаблона, детерминированные ID использует ещё пара сущностей — глобальный тред и тред сущности (§4.5), обе построены от `owner_id`. При введении workspace'ов (D11) эти формулы становятся **workspace-scoped**: пространство имён переезжает на `workspace_id`; формула для инстансов от шаблона (выше) уже не завязана на пользователя и не меняется.

## §6. Query-движок

Единый канон фильтрации сущностей. **Канон — дерево, а не строка** [D43]: фильтр это `and` / `or` / `not` произвольной вложенности над предикатами, а параметры проекции (`sortBy`, `limit`, `display`, `title`) вынесены из фильтра отдельными полями. Текстовая грамматика (§6.1) — синтаксис ввода и вывода поверх того же дерева: плоский сахар без скобок, где условия соединяются логическим AND, а `|` внутри значения даёт OR. Сохраняется **дерево** (§6.2); текст печатается из него при чтении.

Отсюда асимметрия, названная вслух: дерево, которое плоским текстом не выражается — OR между **разными** свойствами, вложенные группы, — построить формой, AI или AST-входом тула можно, а набрать текстом v1 нельзя. Печать такого дерева даёт текст со скобками, и парсер v1 его честно отвергает. Скобки в грамматике — возможное расширение, а не долг.

### §6.1 Текстовая грамматика

| Возможность | Синтаксис | Пример / семантика |
|---|---|---|
| Теги (OR внутри) | `tags=a\|b` | Сущности с тегом `work` ИЛИ `personal` |
| Исключение тегов | `excludeTags=x` | Исключить сущности с тегом |
| Наличие аспекта | `aspect=orbis/task` | Аспект должен присутствовать. Принимается и `key` аспекта, и его подпись в кавычках |
| Значение свойства (OR) | `<свойство>=v1\|v2` | `orbis/task_status=planned\|in_progress`. Имя свойства — **namespaced key**: слэш и есть встроенная пометка «это свойство», поэтому коллизия с зарезервированными словами грамматики невозможна по построению |
| Подпись вместо ключа | `"дата оплаты">2026-08-01` | Закавыченное имя — **всегда свойство**, резолв по подписи в локали владельца; при неоднозначности подписи запрос уточняется `aspect=` |
| **Присутствие свойства** | `has=<свойство>` | `has=orbis/due_date` — у записи есть срок, каким бы он ни был. Раньше предиката «поле есть» не было вовсе, и его отсутствие приходилось обходить записью `false` |
| Отрицание | `<свойство>=!v1&!v2` | `orbis/task_status=!done&!cancelled` — НЕ эти значения |
| Вхождение в список | `<свойство-список>=v` | Свойство с `cardinality: many` (`orbis/aliases`): условие истинно, когда список **содержит** значение целым элементом. `orbis/aliases=такси` — среди синонимов категории есть «такси»; `orbis/aliases=такси\|метро` — есть хотя бы одно из; `orbis/aliases=!такси` — нет ни одного. Сравнение точное и **регистрозависимое**: `Такси` не найдёт `такси`, подстрока не ищется |
| Относительные даты | `<date-свойство>=today\|overdue\|next_7d\|after_7d` | Токены применимы к **любому** свойству типа date/timestamp: `orbis/due_date=today`, `orbis/start_at=next_7d`. `today` — сегодня; `overdue` — строго «значение < сегодня»; `next_7d` — диапазон [сегодня; сегодня + 7 дней], **включительно с обеих сторон**; `after_7d` — строго после этого диапазона |
| Числовое сравнение | `orbis/amount>1000` | Значение больше (аналогично `<`) |
| Числовой диапазон | `orbis/amount=500..2000` | Между значениями включительно |
| Сравнение timestamp | `orbis/updated_at>2026-07-02T09:00:00Z` | Операторы `>`, `<` и диапазон `..` применимы к core-свойствам (§3.17) с абсолютным значением ISO 8601 |
| Дети сущности | `children_of=<uuid\|this>[ via=<роль>]` | Вернуть детей X. Без `via=` — по **семейству иерархических ролей** (§4.2); с `via=` — по одной названной роли: `children_of=<uuid> via=envelope-binding` — транзакции конверта |
| Родители сущности | `parents_of=<uuid\|this>[ via=<роль>]` | Вернуть родителей X, та же логика `via=` |
| Наличие ребра | `has_relation via=<роль>` | У сущности есть ребро названной роли |
| Наличие детей | `has_children[ via=<роль>]` | У сущности есть хотя бы один ребёнок; отрицание через дерево даёт «терминальная задача» |
| Потомки и предки | `descendants_of=<uuid\|this> via=<роль>`, `ancestors_of=…` | Рекурсивный обход по одной роли, **кап глубины 32**. Роль здесь обязательна: обход сразу по нескольким ролям — за границей канона, и он даёт отказ, а не молчаливый выбор одной |
| Исключение заблокированных | `excludeBlocked=true` | Исключить сущности с входящим ребром роли `dependency` от **незакрытой** работы |
| Архивные | `archived=true\|any` | Токен отсутствует — только неархивные; `archived=true` — только архивные; `archived=any` — все |
| Сортировка multi-field | `sortBy=orbis/priority:desc\|orbis/due_date:asc` | Упорядоченный список свойств с направлением |
| Полнотекстовый поиск | `search=API` | По `title` + `body` |
| Лимит | `limit=20` | Максимум результатов |
| Режим отображения | `display=compact\|list\|table` | Подсказка рендереру query-блока |
| Заголовок | `title=My Tasks` | Заголовок над результатами query-блока |

Лексика и экранирование:

- Значения, содержащие `,`, `|`, `&` или пробелы по краям, заключаются в двойные кавычки: `title="My Tasks, важное"`. Внутри кавычек `"` экранируется как `\"`, а `\` — как `\\` (без экрана хвостовой `\` перед закрывающей кавычкой был бы невыразим); одиночный `\` перед прочими символами остаётся литералом (обратная совместимость). Переводы строк внутри `{{query:...}}`-блока эквивалентны пробелам.
- Кавычки обязательны и там, где список выше их не называет: значение с `"` (без кавычек оно не разбирается вовсе), пустое значение (`""` — единственная его форма, `search=` — ошибка), а в позиции значения — ещё значение с `..` (иначе `orbis/task_status=a..b` читается как диапазон) и значение с ведущим `!` (иначе `orbis/task_status=!foo` — это отрицание, то есть **тихо другой** AST). **Печать квотирует надмножеством**: в кавычки берётся любое значение со служебным символом (`=`, `>`, `<`, `!`, `(`, `)`, пробел, запятая, `|`, `&`, `\`, `"`), с `..`, со словом относительного date-токена, с обрамляющими пробелами — и, отдельно, значение с `}`: без кавычек оно закрыло бы блок `{{query:…}}` раньше времени и порвало бы тело записи. Лишние кавычки безвредны, недостающие меняли бы смысл запроса или ломали документ.
- Числовые сравнения и диапазоны применимы к свойствам типа `number` и `decimal`; у `decimal` бэкенд (Postgres) приводит значение к `numeric` через ту же арифметику, что денежные операции (§3.3). Лексикографическое сравнение строк запрещено.
- Для core-свойств типа timestamp (`orbis/created_at`, `orbis/updated_at`) те же операторы `>`, `<` и `..` принимают абсолютное значение ISO 8601 и сравнивают моменты времени: `orbis/updated_at>2026-07-02T09:00:00Z` — изменено строго после этого момента (паттерн курсора агента, §9.3).
- Вхождение в список — единственная конструкция, где `=` означает не равенство, а «содержит». Семантика — containment в JSONB (`props @> {id свойства: [значение]}`), поэтому приведения регистра, нормализации «ё» и поиска подстроки в ней нет, а элемент сопоставляется целиком. Единственное отступление от буквальной формулы: для литерала, который выглядит числом, компилятор проверяет **обе** кодировки (`"5"` и `5`) — containment в JSONB строго типизирован, и без этого фильтр по списку чисел давал бы тот же тихий ноль, ради устранения которого конструкция и введена. Операторы `>`, `<`, `..` и относительные date-токены к списку неприменимы, сортировка по нему запрещена (линейного порядка у списка нет) — и то и другое ошибка разбора (§6.4).
- Смешивание `|` и `&` в одном значении (`orbis/task_status=a|b&!c`) — ошибка парсинга (§6.4).
- Алиаса `due` больше нет: срок адресуется полным именем `orbis/due_date` [D43]. Сокращённые имена были ровно тем, ради чего заведён namespaced key, — и вторым способом назвать одно и то же.
- `overdue` — чистое сравнение дат, **без доменной логики задач** («и не закрыто» в семантику токена не входит): для «просроченных и незакрытых» задач условия комбинируются явно — `orbis/due_date=overdue, orbis/task_status=!done&!cancelled`.
- Относительные date-токены комбинируются через `|` как обычные значения: `orbis/due_date=today|overdue` — срок сегодня ИЛИ просрочен.
- Сортировка `select`-свойств — по **порядку вариантов (`rank`) в определении свойства** (§4.16), не по алфавиту. NULL-значения — всегда в конце, независимо от направления.

**Резолв имени решает слэш** [D43]. Имя со слэшем — всегда свойство (`orbis/due_date`, `user/effort`), и никакой очерёдности проверок для него не нужно: зарезервированные слова грамматики (`tags`, `limit`, `search`, `title`…) — голые, и пересечься с namespaced key не могут по построению. Закавыченное имя — тоже всегда свойство, но резолвится по **подписи** в локали владельца, и вот там неоднозначность возможна: две подписи «Статус» у двух свойств требуют уточнения `aspect=`. Квалификация «аспект.поле» отменена как атавизм: она решала проблему, которой больше нет. Core-свойства (§3.17) участвуют в фильтрах и сортировке наравне с прочими: `orbis/created_at=today`, `sortBy=orbis/updated_at:desc`; исключение — `orbis/title` в позиции фильтра, где ключ `title=` занят параметром заголовка, поэтому отбор по заголовку идёт через `search=`. `display` и `title` — параметры представления, на отбор не влияют.

**Имена валидируются при сохранении, а не при исполнении** [D43]. Опечатка в имени свойства, аспекта или роли — отказ с кодом и позицией в момент записи запроса, а не молчаливый ноль в выдаче через неделю. Это главное практическое следствие того, что канон — дерево по id: чтобы построить дерево, имя надо резолвить, и нерезолвленное имя дальше не проходит.

Пример полного запроса в body проекта:

```
{{query:aspect=orbis/task, orbis/task_status=!done&!cancelled, excludeBlocked=true,
         children_of=this, sortBy=orbis/priority:desc|orbis/due_date:asc, limit=20,
         display=compact, title="Активные задачи проекта"}}
```

Тот же запрос деревом — форма, в которой он **хранится** и в которой его принимает тул (§9.2):

```json
{
  "filter": { "and": [
    { "aspect": "orbis/task" },
    { "not": { "prop": "orbis/task_status", "op": "in", "value": ["done", "cancelled"] } },
    { "rel": { "kind": "children_of", "of": "this" } }
  ] },
  "sortBy": [ { "field": "orbis/priority", "dir": "desc" },
              { "field": "orbis/due_date", "dir": "asc" } ],
  "limit": 20, "display": "compact", "title": "Активные задачи проекта"
}
```

А это — дерево, которого **текстом не написать**: «просрочено по сроку ИЛИ по началу». Плоская грамматика соединяет условия только «и», OR внутри одного значения не помогает — нужны разные свойства:

```json
{ "filter": { "and": [
    { "aspect": "orbis/task" },
    { "or": [ { "prop": "orbis/due_date", "op": "eq", "value": { "token": "overdue" } },
              { "prop": "orbis/start_at", "op": "eq", "value": { "token": "overdue" } } ] }
] } }
```

Оговорка к `children_of=this`: токен резолвится только у потребителя, передавшего контекст сущности (`thisEntityId` в контракте `entity.query`). Detail-экран его передаёт — блоки в **теле записи** получают id этой записи и `this` в них разрешается; вне тела контекст не передаётся намеренно (Browser, бейджи закреплённых списков, конструктор запросов), и там блок с `this` отвечает ошибкой «this вне контекста сущности» (02-core-os §3.4). Именно «не передаётся», а не «нечего передать»: у бейджа закреплённого списка id сущности известен, и `thisEntityId` контракт `entity.count` принимает, — но `this` в вынесенном из тела блоке означал бы «та запись, из чьего тела блок скопировали», а не «то, на что человек смотрит», и подстановка сделала бы счётчик тихо неверным. Диспетчер тулов контекст по-прежнему НЕ передаёт: `entity_query` из чата и MCP на `this` отвечает той же ошибкой. Остальные конструкции примера разбираются, а `display=` остаётся подсказкой рендереру, которую query-виджет сегодня не читает (02-core-os §3.4).

Иллюстрация семантики (псевдо-SQL):

```sql
SELECT * FROM entities
WHERE owner_id = :uid AND NOT archived
  AND aspects @> ARRAY['orbis/task']::text[]
  AND props->>'orbis/task_status' NOT IN ('done', 'cancelled')
  AND id IN (SELECT target_id FROM relations
             WHERE source_id = :this AND role IN ('subitem','ticket','run','category-parent'))
  -- excludeBlocked: NOT EXISTS входящего ребра роли dependency
  --                 от сущности с orbis/task_status NOT IN ('done', 'cancelled')
ORDER BY CASE props->>'orbis/priority'   -- порядок вариантов select в определении свойства
           WHEN 'low' THEN 0 WHEN 'medium' THEN 1 WHEN 'high' THEN 2
         END DESC NULLS LAST,
         (props->>'orbis/due_date') ASC NULLS LAST
LIMIT 20;
```

Две детали иллюстрации существенны. `children_of` без `via=` разворачивается в перечень **иерархических ролей** из кеша реестра (§4.2), а не в один зашитый тип связи — добавление роли в семейство не требует правки компилятора. И сравнение ссылочного свойства с `entities.id` компилируется **всегда с явным приведением к uuid**: `props->>` отдаёт текст, а `id` — uuid, и без каста запрос упал бы на операторе.

### §6.2 Хранение, печать и один бэкенд

**Хранится дерево, печатается текст** [D43]. Сохранённый запрос — query-блок тела, источник прогресса цели (§3.11), множество целей ссылочного свойства, область показа свойства — держит **разобранный AST по id**; текст получается из него проекцией при чтении, и проекций две: **key — для машин** (промпт, MCP, дифф, канонический экспорт) и **подпись — для человека** (конструктор запросов). Отсюда главное практическое свойство: переименование подписи свойства не устаревает нигде — устаревать нечему.

Практика оказалась чуть шире принципа. Query-блок тела хранит **оба** атрибута: `ast` — истину, и `text` — печатную key-форму того же дерева; при `ast = null` блок не разобран, и `text` — исходная строка владельца, показываемая с ошибкой [рулинг Р-21-2 ветки D43]. Причина названа: markdown-проекция тела печатается из ноды документа, куда реестр передать нечем, — а без реестра дерево не напечатать. Инвариант, который это держит: `text` при живом `ast` — не независимое поле, а его печать.

Единственный SQL-бэкенд движка — **PostgreSQL**. Спецификация канона — одна (эта глава); компилятор транслирует дерево в SQL для одного диалекта, без слоя абстракции «диалект A / диалект B».

**Приёмочный критерий — golden-тесты.** Корректность компиляции проверяется юнит-тестами на golden-фикстурах: набор пар «AST → ожидаемый SQL» плюс эталонный датасет сущностей и рёбер, на котором запрос обязан вернуть ожидаемый по составу и порядку результат. Любая новая конструкция канона добавляется в набор фикстур одновременно с реализацией. Результат запроса детерминирован одной реализацией на одном движке БД — сверять больше не с чем.

### §6.3 Потребители канона

Компилятор один, и все его потребители исполняют один и тот же SQL на одном бэкенде — PostgreSQL, через tRPC (§9.1); отдельного клиентского движка нет. Точек вызова компилятора **семь, в четырёх модулях**:

| # | Точка вызова | Что через неё ходит |
|---|---|---|
| 1 | Процедура запроса сущностей | Body-блоки `{{query:...}}`, smart lists (02-core-os §3.3), фильтры Browser/Budget/Agenda, конструктор запросов, fast-path чата |
| 2 | Процедура счёта | Бейджи закреплённых сущностей (02-core-os §3.2) — тот же вход, другой ответ |
| 3 | Тул `entity_query` | Вызовы чат-LLM и MCP-агентов (§9.2) |
| 4 | Тул `user_query`, ветка счёта | Вопрос-агрегация «сколько задач по проекту» |
| 5 | Тул `user_query`, ветка суммы | Вопрос-агрегация «сколько потрачено на еду за месяц» |
| 6 | Расчёт прогресса цели | `orbis/progress_source` (§3.11, §11.3) — три агрегата над одним деревом |
| 7 | **Проверка значения ссылочного свойства** [D43] | Множество целей `ref` (§4.16): компиляция цели + сверка конкретного id под RLS |

Седьмая точка — новая и небесплатная концептуально: она означает, что тип `ref` не «uuid с подсказкой пикера», а **множество, заданное запросом**, и попытка сослаться вне множества получает отказ с причиной, а не проходит молча.

Ещё три потребителя названы решением, но кода в срезе А не имеют: **область показа свойства** (`scope`, §4.16) — значение хранится и читается графом зависимостей, но в SQL не компилируется; **подписки поверхностей** и **правила каталога** — часть Б целиком. Прежний пункт «авто-чекины привычек» из списка убран: аспекта `orbis/habit` в системе нет, и потребителем он не был никогда.

### §6.4 Поведение при ошибках

- **Невалидный запрос** (синтаксическая ошибка, неизвестное свойство, неоднозначная подпись без `aspect=`, нефильтруемое свойство) — это **ошибка разбора, отображаемая пользователю**: query-блок рендерится с сообщением об ошибке и указанием места; AI-тул получает структурированную ошибку. Запрос с ошибкой никогда не выполняется частично. У отказа есть **код**, а не только текст: неизвестное свойство, неизвестный аспект, неизвестная роль, неоднозначная подпись, несовпадение типа, синтаксис, обход по нескольким ролям, соединение двух свободных сущностей, зарезервированное слово, недоступный класс контракта — десять разных причин, и по коду видно, чинить запрос или ждать части Б.
- **Момент проверки сдвинут на сохранение** [D43]. Раньше имя резолвилось при исполнении, и опечатка жила в теле, пока кто-нибудь не заметил пустой блок. Теперь запрос разбирается и валидируется по реестру **при записи**; неразобранным блок остаётся только осознанно — с сохранённым текстом и видимой ошибкой.
- **Нефильтруемое свойство — отказ, а не пустая выдача.** Свойство, значение которого не сводится ни к скаляру, ни к списку скаляров — `json` (`orbis/recurrence`, `orbis/progress_source`), — фильтру недоступно: запрос отвергается с позицией **имени**, причём одинаково для равенства, отрицания, диапазона и `>`/`<` — причина у них одна. Сортировка отвергается тем же классом и по нефильтруемым свойствам, и по спискам. Класс введён потому, что альтернатива ему — не пустая выдача, а **неверная**: пока такие значения выдавались за строки, `recurrence=weekly` сравнивал текст сериализации всего объекта и давал тихий ноль, а `recurrence=!weekly` возвращал всю таблицу.
- **Пустой результат ≠ ошибка**: валидный запрос без совпадений рендерится как пустой список («ничего не найдено»). Различие принципиально: тихая пустота вместо сообщения об ошибке — главный способ потерять доверие к живым документам.

## §7. AI-слой

### §7.1 Пятислойная модель контекста

Каждый LLM-вызов собирает контекст из пяти слоёв:

```
┌ 1. System prompt ── статика: правила, дата владельца, аспектные   ┐
│                     инструкции из реестра                         │ глобальный
├ 2. Память ───────── активные orbis/memory-сущности, кап 50        ┤ глобальная
├ 3. Рабочий контекст─ активный view, открытая сущность             ┤ ситуативный
├ 4. История диалога ─ ТОЛЬКО текущий тред (rolling + summary)      ┤ скоупнутая
└ 5. Доступ к графу ── через тулы (§9.2), по необходимости          ┘ весь граф
```

| Слой | Содержимое | Бюджет |
|---|---|---|
| 1. System prompt | Правила поведения, текущая дата в таймзоне владельца, инструкции активных аспектов из реестра | **факт 3 055**, цель ≤ 2 000 |
| 2. Память | До 50 активных memory-фактов и правил (с учётом области действия) | ~1–2K |
| 3. Рабочий контекст | Текущий view, открытая сущность (title, tags, свойства, превью body) | ~500 |
| 4. История треда | Последние сообщения текущего треда + summary более старых | ~4K |
| 5. Доступ к графу | Через тулы (§9.2): в контекст входят полные определения всех активных тулов (§7.6), сами данные графа приходят ответами тулов. Бюджет строки — стоимость определений тулов | **факт 5 521** |

Числа слоёв 1 и 5 — **измеренные, а не целевые** [D43], и у них есть условия: замер снят **2026-08-25** на прод-канале с промптом **v4**, то есть **до** реформы; на действующей линейке v5 он не переснимался — перезамер идёт вместе с закрытием среза. Прежние ориентиры «~800» и «~1.5K» оказались занижены втрое-вчетверо, и это ровно тот случай, ради которого числа меряют, а не назначают.

Цель «≤ 2 000» для слоя 1 достигается **промпт-индексом** — генерируемым перечнем аспектов без полей, с уходом полей в схемы тулов (часть Б; в срезе А промпт остаётся статическим текстом линейки v5). Оттуда же берётся половина экономии: сегодня инструкции аспектов едут **дважды** — в системном канале и в описаниях `attach_*`-тулов, — и дубль снимается вместе с генерацией.

**Каталог свойств в промпт не печатается вовсе.** Замер показал 28,5 токена на свойство: словарь из 77 свойств стоит дороже, чем весь остальной слой 1, а расти он будет с каждым `proposed`. Модель узнаёт свойства двумя путями: набор аспекта — из схемы его `attach_*`-тула, всё остальное — read-тулом каталога (§9.2). Остальные бюджеты — целевые значения для контроля стоимости, не жёсткие константы; их механическое воплощение — капы в коде (50 памятей, окно из 30 сообщений, превью тела 200/500 символов), и расход метрится через `ai_usage`.

### §7.2 Диалоги эфемерны, знания живут в графе

Принцип: **история тредов — рабочая поверхность, а не хранилище знаний**. То, что должно пережить разговор, переносится в граф — тремя путями:

1. **Memory-факт** — AI предлагает сохранить факт/правило, пользователь подтверждает → создаётся `orbis/memory`-сущность (§7.4).
2. **Дозапись в body якорной сущности** — вывод разговора в треде сущности дописывается в её body («добавь это резюме в проект»).
3. **Note-сущность** — отдельная заметка, связанная с обсуждавшейся сущностью ребром роли `mention` (§4.2).

По умолчанию — изоляция: содержимое треда никуда не утекает без явного действия.

### §7.3 Треды

- **Глобальный тред** (`chat_threads.entity_id = NULL`) — мессенджер-модель: один бесконечный диалог, rolling window + summary. Это главная вкладка Chat.
- **Тред сущности** — персистентный диалог, привязанный к сущности; живёт вкладкой на её детальном экране. Контекст слоя 3 автоматически содержит эту сущность.
- **Тулы не скоупятся.** Из любого треда доступен весь набор тулов и весь граф: **скоупится разговор, а не способности**. В треде категории «Еда» можно спросить про задачи — AI дотянется через `entity_query`.

### §7.4 Память

Память AI — это `orbis/memory`-сущности (§3.7), а не скрытое состояние:

- **Видимы и редактируемы в Browser**: пользователь курирует память напрямую — правит формулировки, архивирует устаревшее.
- **Инжекция**: активные (не archived) memory-сущности попадают в слой 2; записи с заданной областью (`orbis/rule_scope`, §3.7) — приоритетно в контексте своей области, а записи без области входят в выборку любой. Кап 50 фактов; при превышении — приоритет правилам (`orbis/memory_kind=rule`) и недавно использованным.
- **Пополнение**: пользователь просит запомнить; AI предлагает сохранить факт из разговора (по подтверждению); эскалация исправлений (§7.8) порождает правила.

### §7.5 Fast-path: детерминированный парсер

Клиентский парсер на грамматике (без LLM) перехватывает частотные паттерны ввода до отправки в LLM. Мгновенно, бесплатно, **работает офлайн**: сам разбор не требует сети, а результат уходит на сервер через retry-буфер (§5.3), если сети сейчас нет. Пользователь не выбирает «режим» — fast-path прозрачен: если парсер уверен, карточка появляется немедленно; нет — ввод молча уходит LLM-путём.

Паттерны MVP:

| Паттерн | Пример | Результат |
|---|---|---|
| `<текст> <число>` | «обед 340» | Сущность с `orbis/financial`: `orbis/direction=expense`, `orbis/amount="340.00"`, `orbis/occurred_on` = сегодня в таймзоне пользователя, валюта по умолчанию; `orbis/finance_category` — резолв «обед» по `orbis/aliases` категорий-сущностей |
| `+<число> <текст>` | «+150000 зарплата» | `orbis/direction=income`, `orbis/amount="150000.00"`, `orbis/occurred_on` = сегодня; категория — по `orbis/aliases` |
| `<текст> <число> <валюта>` | «кофе 4 usd» | Как расход, но с явным `orbis/currency` |

Числа — целые и десятичные с точкой или запятой («340», «127.50», «99,90»). Валютные токены MVP: `₽`, `руб`, `р`, `$`, `€`, `USD`, `EUR`, `RUB` (без учёта регистра); без явного токена — валюта пользователя (`user_settings.defaultCurrency`).

Правила передачи в LLM (парсер обязан уступить при любой неуверенности):

- **Неизвестная категория** — текст не разрезолвился ни в один alias ни одной категории;
- **Множественные суммы** — в строке больше одного числа («обед 340 и такси 200»);
- **Вопросительная форма** — `?`, вопросительные слова («сколько я потратил на еду?») — это запрос, а не ввод.

Fast-path **применяет correction-правила из памяти** (`orbis/memory` c `orbis/memory_kind=rule` и областью «движение денег»): правило «бар → Развлечения» работает и в детерминированном пути, без LLM — и берёт оно теперь свойства правила (`orbis/rule_pattern`, `orbis/rule_target`), а не разбирает заголовок (§3.7). Карточка результата fast-path идентична AI-карточке: inline-правка и Undo работают одинаково (§7.8).

Паттерн правила сопоставляется с вводом **по границе токенов**, а не подстрокой: «бар → Развлечения» ловит «бар 1500» и «вечером бар», но не «барбершоп 1500». Многословный паттерн («яндекс такси») требует непрерывной последовательности токенов. Тот же критерий действует в резолве строк CSV-выписки (03-budget §3.4) — путей сопоставления два, реализация одна.

### §7.6 Динамические тулы из реестра

Набор тулов LLM генерируется из реестров: **core-набор** (§9.2) + по одному тулу `attach_<key аспекта>` на каждый неслужебный аспект. Служебность читается из **колонки `service`** строки реестра (§3.8), а не из списка в коде: сегодня служебный один — `orbis/agent-run` (§3.15), и attach-тула он не получает вовсе.

**Схему параметров собирает реестр свойств** [D43]. Раньше входом тула была хранимая JSON Schema аспекта; теперь это склейка схем **тех свойств, на которые аспект ссылается**: имя параметра — `key` свойства (`orbis/task_status`), описание параметра — его подпись плюс описание в локали владельца плюс перечень вариантов у `select`, порядок параметров — `rank` ссылки. Отсюда два следствия. Первое: кириллица в именах параметров не возникает никогда — подпись человеку и ручка машине разведены, и переименование подписи схему тула не трогает. Второе: описание тула (`ai_instructions` аспекта) и описания его параметров приходят из одного места, и «поле есть в схеме, но модель о нём не знает» перестаёт быть возможным состоянием.

Новый аспект или новое свойство в реестре автоматически даёт AI способность работать с ним — без изменения кода AI-слоя.

**В MVP тулы загружаются всегда, полным составом** — но состав у каждого пути свой (D37): внутреннему чату уходят core-тулы и `attach_<aspect>` каждого активного неслужебного аспекта, кроме `agentOnly` (глаголы исполнителя, §9.3); MCP публикует список **по скоупу гранта** (`full` — весь публичный реестр, `worker` — чтения, глаголы и `thread_post`, §4.14). Внутри своего состава схемы передаются целиком, в каждый вызов. Условная частичная загрузка схем по релевантности контекста разговора — Future, актуальна при заметном росте числа кастомных аспектов.

### §7.7 Модель и транспорт чата

**Модель.** Модель одна на инсталляцию, без роутинга по типу операции. Разделение на классы моделей (дешёвая — для нормализации тегов, категоризации транзакций, summary тредов; основная — для создания сущностей из свободного текста, cross-aspect рассуждений, диалога) остаётся архитектурно возможным через `LLMProvider`, но не реализуется в MVP — Future Directions. Имя конкретной модели в PRD не фиксируется — это конфиг (`ORBIS_LLM_MODEL`, иначе дефолт выбранного провайдера). Каждый вызов метрится в `ai_usage` с указанием модели, и имя для метеринга **отдаёт сам провайдер** (`LLMProvider.modelId`), а не вычисляется из env с дефолтом одного из них: иначе второй провайдер без явной `ORBIS_LLM_MODEL` записывал бы расход на чужую модель (D27).

**Транспорт.** Чат — обычная tRPC-мутация: клиент отправляет сообщение, ждёт и получает ответ целиком одним пакетом. Ни `useChat`, ни SSE, ни любой другой потоковый транспорт в MVP не используется; UI показывает состояние ожидания (индикатор набора текста), а не токен-за-токеном рендер.

**Реализация LLM-слоя.** Интерфейс `LLMProvider` реализуется поверх **Vercel AI SDK**, но **типы AI SDK не протекают через интерфейс**: наружу возвращаются только наши типы, AI SDK остаётся заменяемой деталью реализации.

**Провайдеров два — Anthropic и OpenAI** (плюс `echo`-заглушка для dev). Всё, что одинаково для любого провайдера SDK — маппинг результата и стоп-причины, конвертация tool defs, таймаут шага, сам вызов `generateText`, — живёт в общем слое `llm/ai-sdk.ts`; в провайдере остаётся только его собственное знание: какой клиент создать, как называется модель по умолчанию, каким транспортом ходить. Выбор — env `ORBIS_LLM_PROVIDER` (`anthropic` | `openai` | `echo`), и он **явный**: при двух ключах и незаданной переменной сервис не поднимается — неоднозначность разрешает человек, а не порядок веток в фабрике (D28). Тем же принципом запрещён и неявный `echo` в production: молча отвечать заглушкой хуже, чем не подняться. Стриминг через AI SDK доступен, но в MVP не используется: ответ приходит целиком (`generateText`, не `streamText`) — вот это остаётся швом на будущее.

**Транспорт OpenAI — Responses API** (голый `createOpenAI(...)(modelId)`): это транспорт `@ai-sdk/openai` по умолчанию и тот, который OpenAI рекомендует новому коду. Условие приёма наших схем одно, и оно выполняется явно: **на каждом туле запроса стоит `strict: false`**. Иначе действует дефолт эндпоинта `/v1/responses` — строгий, — а строгий режим не берёт regex lookaround: «`Invalid JSON schema: regex lookaround is not supported`». Негативный lookahead жил в проверке «строго положительной decimal-строки» у сумм и целевых значений, то есть ронял бы все тулы финансов и целей. Реформа сняла саму причину: граница «строго больше нуля» стала конфигом типа свойства (`exclusiveMin`, §4.16), а паттерны реестра проверяются на принадлежность классу RE2 при записи — так что новые свойства этого рычага уже не требуют. Поле `strict: false` остаётся выставленным явно: снимать его — отдельное решение с перепроверкой всех схем, а не побочный эффект реформы. Рычаг здесь именно поле тула, а **не** опция `strictJsonSchema`: та кормит только `response_format` и к тулам не относится ни на одном транспорте. Вторая обязательная настройка — **`store: false`** в `providerOptions.openai`: на Responses SDK по умолчанию ставит `store: true`, и тогда OpenAI хранит запрос с ответом у себя, а через чат Orbis идут банковские выписки, суммы и личные заметки. Strict-режим структурированного вывода при этом не включается: он потребовал бы объявить обязательным всё необязательное, то есть менять определения свойств, и ничего не дал бы — вход тула всё равно валидирует ajv по реестру (§9.2). Матрица «транспорт × строгость» и воспроизведение — `docs/superpowers/reviews/2026-08-06-openai-probe.md` §1.2 (включая врезку круга 6) и §1.4; решение — D29, отменившее D26.

### §7.8 Corrections & Undo

- **Карточка действия.** Каждое AI- или fast-path-действие порождает карточку в чате с inline-редактированием полей (поменять категорию, сумму, дату — прямо в карточке) и кнопкой Undo.
- **Журнал действий.** Каждый одиночный вызов executor'а или атомарный batch записывает один action в `chat_messages.metadata.actions`. Формат элемента:

```json
{
  "id": "0190a3c2-8e51-7b04-b21f-3d9e7a44c615",
  "type": "entity_created",
  "entity_id": "018f...",
  "operations": [{ "op": "entity_create", "payload": { "id": "018f..." } }],
  "inverse": [{ "op": "entity_archive", "payload": { "id": "018f..." } }]
}
```

  Для одиночного действия массивы содержат один элемент. Для импорта, rollover, рекатегоризации и переноса лимитов — все операции группы; `inverse` хранится в обратном порядке исполнения. Обратные операции: создание → архивация; обновление → восстановление старых значений (`payload` = прежние поля); создание relation → её удаление. Журнал общий для внутреннего чата, fast-path и MCP-агентов (§9.3). Каждая запись фиксирует актора действия — владелец, внутренний AI или MCP-агент. Поля атрибуции: `actor_user_id` (нейминг по D11, 04-decision-log) — от чьего имени сделана мутация; `actor_kind` — владелец, внутренний AI или агент; `source` — каким путём (`ui` \| `chat` \| `fast_path` \| `quick_capture` \| `mcp` \| `system` \| `routine`); `actor_grant_id` — конкретный доступ агента (§4.14), которым пришёл вызов; `run_id` — прогон исполнителя (§3.15), в рамках которого сделана мутация; `edited_from` — исходное предложение рутины, которое владелец поправил перед принятием (§9.3) [Ш1]: по нему видно, что действие воплощает не дословный план рутины, а правку владельца. Последние три — только у действий, у которых они есть: ключ с `null` у каждой записи раздул бы `metadata` без пользы. Отложенное действие (`explicit-confirmation`, §7.10) грант **не теряет**: `actor_grant_id` сохраняется вместе с payload'ом и доезжает до журнала в момент одобрения — иначе подтверждённое владельцем действие агента выглядело бы в журнале действием без агента. То же и с прогоном: применённое предложение рутины несёт `run_id` того прогона, который его составил, хотя кнопку нажал владелец часом позже, — иначе откат прогона не нашёл бы главного, что прогон сделал. `run_id` — **обратная ссылка**: по ней собираются все действия прогона для его отката (§9.3), и ищется она containment-пробой `metadata @> {"actions":[{"run_id": …}]}` — единственным предикатом, который берёт jsonb-индекс.
- **Атрибуция рутинного прогона расщеплена надвое** [V1]. Всё, что прогон делает **сам о себе** — создание сущности прогона с ребром роли `run`, запись шагов, закрытие исходом, дозапись расхода, пометки `stale` / `superseded` на предыдущем предложении, пауза стоп-крана, — идёт с `actor_kind: ai` и **`source: system`** (плюс `run_id` у создания, шагов, закрытия и расхода; пометки `stale`/`superseded` и пауза идут **без** `run_id` — они про предыдущий прогон и про рутину, а не про текущий прогон). Всё, что прогон делает **с графом владельца** — мутации модели через тулы и применённое предложение, — идёт с `actor_kind: ai`, **`source: routine`** и `run_id`. Решения владельца о прогоне тоже расщеплены: ответ на вопрос — `owner`/`ui` + `run_id` (его реплика), пометка судьбы предложения (`approved`/`rejected`/`stale`) — `owner`/`system` + `run_id` (бухгалтерия: само решение воплощено батчем принятого предложения). Разделение не косметическое: «отмени последнее» (ниже) пропускает `system` и потому после утреннего прогона снимает правку модели, а не запись его собственного шага, а после «Принять» — сам план, а не пометку статуса; откат рутинного прогона (§9.3) инвертирует **только** `source: routine` и помечает прогон архивом. Ровно по этой же границе проходит и запрет по объекту (§9.3): `source: routine` рутин, прогонов и назначений не касается, а бухгалтерия под `system` спокойно пишет прогон и его связь с рутиной. Заметка прогона в тред несёт в метаданных `author_kind` (`ai` \| `agent`), `run_id` и — у рутинного прогона — `routine_id`: по ним лента отличает голос исполнителя от голоса владельца и знает, чей это прогон.
- **Атомарность группы.** `batch_execute` (§9.2) валидирует все операции до записи и применяет их одной PostgreSQL-транзакцией. Ошибка любого элемента откатывает всю группу; карточка и журнал появляются только после полного успеха. Action получает `id=batch_id`, а системное audit-сообщение — детерминированный `uuidv5(ORBIS_NAMESPACE, "batch:<owner_id>:<batch_id>")`; уникальность PK сообщения делает повтор batch проверяемым: повторный вызов с тем же `batch_id` конфликтует по PK вместо создания дубля и возвращает сохранённый результат, ничего не применяя повторно.
- **Состояние Undo при append-only журнале.** `chat_messages.metadata` неизменяема (§4.6), поэтому отмена не правит записанное действие, а добавляет **новое системное сообщение** `{type: "undo", undoes: "<action_id>"}` (где `action_id` — `id` элемента журнала). Действие считается отменённым, если в журнале существует undo-запись с его `id`; повторная отмена отклоняется по этой же проверке. «Отмени последнее» сканирует журнал с конца, пропуская уже отменённые действия, и применяет `inverse` первого неотменённого. Словами в чате это делает тул `undo_last` (§9.2, `internalOnly`): у чат-модели он единственный рычаг отмены — без него она «отменяла» второй правкой поверх первой; нового action undo не порождает (undo неотменяем), а «отменять нечего» уходит модели штатным ответом, не ошибкой.
- **Эскалация в правило.** После **двух одинаковых исправлений** (например, пользователь дважды переложил «бар» из «Еды» в «Развлечения») AI предлагает создать memory-правило; по подтверждению появляется `orbis/memory` (`orbis/memory_kind=rule`, область — «движение денег»), которое применяется и LLM-путём, и fast-path-парсером. Счётчик одинаковых исправлений не хранится отдельным состоянием — он вычисляется сканом журнала действий за последние 30 дней. Повторность считается **по действиям**: три исправления внутри одного batch — одно намерение, а не три повтора. Групповая рекатегоризация, ушедшая на явное подтверждение по размеру batch (§7.10), эскалирует после одобрения — иначе самый естественный путь («перенеси все 12 покупок») правил бы не порождал никогда.
- **Правило хранится свойствами, а заголовок его не задаёт** [D43]. Обе половины — `orbis/rule_pattern` (образец) и `orbis/rule_target` (ссылка на категорию, §3.7); `title` — **генерируемая подпись** вида «`бар` → Развлечения» с канонической стрелкой U+2192, и **разбирать её незачем и некому**: детерминированные пути (fast-path, резолв импорта, гейт эскалации) читают свойства. Прежний формат «правило в заголовке» со стрелкой и клавиатурными суррогатами `->`/`=>` снят вместе с четырьмя независимыми парсерами заголовка. Отсюда исчезли два класса дефектов сразу: «записанное, но молча мёртвое правило» (заголовок без разделителя проходил запись и не работал ни в одном пути) — теперь правило без образца **незаписываемо**, отказ приходит владельцу сразу; и «переименование категории отвязало правило» — правая часть стала ссылкой, а не текстом.
- **Retention журнала** (carried-решение RET-02). Полные записи действий (`chat_messages.metadata.actions` и связанные системные сообщения) хранятся **90 дней**, после чего вычищаются; диагностика отклонённых команд (структурированные ошибки валидации и бизнес-отказов) — **30 дней**; идемпотентные receipts команд — минимальная запись «эта мутация с этим client-UUID/`batch_id` уже выполнена и вот её результат», переживающая полную запись действия, — **180 дней**, чтобы повторная отправка (§5.3, идемпотентность по client-UUID) оставалась безопасной дольше срока жизни полной записи.

### §7.9 Деградация

| Состояние | Работает | Не работает |
|---|---|---|
| Офлайн | Fast-path-ввод (уходит в retry-буфер, §5.3, досылается при восстановлении сети); чтение уже загруженных данных из server-state-кэша (§5.1) | Правки существующих сущностей; LLM-путь; данные, не попавшие в кэш до потери сети |
| Сеть есть, AI недоступен (сбой провайдера, исчерпан лимит) | Всё, кроме LLM-пути, работает как обычно | LLM-путь — явная ошибка с указанием причины и кнопкой «повторить»; запрос не встаёт в очередь |

Инвариант изменился по сравнению с полным offline-first: Orbis больше не остаётся полнофункциональным инструментом без сети — офлайн честно покрыт только вводом (буфер) и тем, что уже в кэше; это осознанная цена онлайн-первого разреза (§12). AI при этом не становится точкой отказа для остального продукта: сбой провайдера или исчерпанный лимит — явная ошибка с возможностью повторить, не тихая деградация и не очередь.

### §7.10 Политика подтверждений AI-действий

Каждый tool-call — внутреннего чата или MCP-агента (§9.3) — после структурной валидации input'а (§9.2) получает от **политики Orbis**, не от модели, один из четырёх уровней подтверждения:

| Уровень | Поведение |
|---|---|
| `execute` | Выполняется немедленно; карточка и запись в журнале (§7.8) появляются постфактум |
| `preview` | Действие исполняется без явного клика пользователя, но результат сопровождается предпросмотром (например, diff изменяемых полей) — предпросмотр информационный, не блокирующий |
| `explicit-confirmation` | Действие не исполняется, пока пользователь не подтвердил его на карточке-запросе; до подтверждения ничего не записано ни в граф, ни в журнал |
| `forbidden` | Tool-call отклоняется до исполнения структурированной ошибкой; ни модель, ни агент не могут обойти запрет переформулировкой вызова |

**Уровень определяет политика после валидации, не модель.** LLM не решает, насколько его действие рискованно, — решает серверный слой политики, которому на вход идут типизированные признаки вызова, а не текст рассуждения модели. Входы классификации:

- **явность намерения** — прямая команда пользователя («удали задачу X») классифицируется мягче, чем самостоятельная инициатива модели в рамках более широкой просьбы;
- **обратимость** — есть ли у операции `inverse` в журнале (§7.8) и восстанавливает ли он состояние полностью;
- **масштаб** — `single` (одна сущность), `bounded` (заранее известный конечный список, например batch с явным списком ID), `bulk` (открытый диапазон — «архивируй все задачи с тегом X»);
- **внешние эффекты** — затрагивает ли действие что-то за пределами графа Orbis (в MVP таких тулов нет, но политика на них рассчитана заранее). `orbis_run_step` (§9.2) исключением не является: сам он внешних эффектов не производит, а лишь **фиксирует флаг** «этот шаг тронул внешнее» — по нему сервер решает судьбу оборванного прогона (§9.3);
- **чувствительность** — типы данных и операций с повышенной ценой ошибки (например, безвозвратные операции с финансовыми записями).
- **перенастраивает поверхность или права** [D43] — меняет ли вызов не запись в графе, а само **устройство** системы: словарь свойств, определения аспектов, их подписи и области показа (§С2-1 спеки реформы). Признак отвечает по **объекту** вызова, а не по имени тула: одно и то же имя трогает то свою строку владельца, то системную. Три ответа: `own-property` — своя строка заводится **предложением** (`status: proposed`) или получает новую подпись/место показа; `behavior-delta` — меняется поведение (статус свойства, слияние двух свойств, дельта аспекта: скрытия, состав, наборы вариантов), **и сюда же попадает заведение строки сразу активной** (`property_create` со `status: active`): итог у него тот же, что у смены статуса, а замок стоит по итогу, а не по форме вызова; `system-object` — объект принадлежит не владельцу (встроенное свойство, встроенный аспект, а дальше — привязки `implements`, роли `created_by: system`, определения чужих модулей).

**Одобрение исполняет сохранённый payload, не повторяет вызов модели.** Когда пользователь подтверждает действие уровня `explicit-confirmation`, executor применяет тот же неизменяемый payload, который был провалидирован в момент запроса подтверждения, — после ревалидации текущего состояния (данные могли измениться за время ожидания), но без обращения к LLM повторно. Подтверждение — это разрешение исполнить уже собранный план, не новый раунд рассуждения.

**Правка владельца payload не трогает** [Ш1]. Владелец, поправивший предложение рутины перед принятием (§9.3, 02-core-os §3.5), не переписывает сохранённое отложенное действие: сервер собирает из правки **новое** отложенное действие, валидирует его тем же контрактом тула и гасит исходное отдельной причиной («правка владельца» — не отказ владельца и не гашение новым прогоном). Id нового выводится **детерминированно** из исходного и содержимого правки, поэтому двойное нажатие — replay, а не второе применение. Предусловия переносятся **как есть**, а не переснимаются: пересъём молча узаконил бы состояние, которого владелец не видел, — а расхождение обязано дать «Устарело», как и у неправленого предложения. Инвариант при этом не ослаблен, а усилен: каждый payload по-прежнему неизменяем, исполняется всегда ровно тот, который владелец читал, и решение адресуется конкретному предложению — предложение, сменившееся между показом и нажатием, не применяется вовсе.

**Глаголы исполнителя — всегда `execute`.** Пять глаголов (`orbis_my_queue`, `orbis_claim_task`, `orbis_run_step`, `orbis_checkpoint`, `orbis_finish`) и `thread_post` классифицируются уровнем `execute` — одиночная неархивирующая мутация. Инвариант: **глагол исполнителя никогда не возвращает `pending`** — фоновому прогону некому подтверждать, и вызов, вставший в очередь на подтверждение, повис бы навсегда. Он закреплён на трёх уровнях: классификатором, диспатчем и проводом ответа. `orbis_my_queue` попадает сюда несмотря на читающий смысл: по дороге он подметает брошенные прогоны (§9.3), то есть пишет. **`orbis_ask` инварианта не нарушает** [D42], хотя и возвращает `{pending_id}`: это id созданной карточки-вопроса — результат самого действия «спросить», а не `pending`-ответ глагола. Сам вызов исполнен уровнем `execute`, шаг записан, прогон идёт дальше и ничьей подписи не ждёт; висеть навсегда такой карточке не даёт не подтверждение, а гашение следующим прогоном (§9.3). Различие проверяемо: у `pending`-ответа действие **не** исполнено до нажатия, у `orbis_ask` исполнено целиком — карточка и есть его результат.

**Выдача автономии рутине — всегда `explicit-confirmation`** [V1]. Создание сущности с `orbis/routine` в режиме `mode: act`, а равно правка `mode` или `allowed_tools` у существующей рутины, поднимается до явного подтверждения владельца, **кем бы ни пришёл вызов**, кроме самого владельца: чат-AI, MCP-агент — всё равно. Признак вызова здесь не «масштаб» и не «обратимость», а то, что действие **раздаёт право писать в граф без спроса**: отменить его потом можно, но прогоны, случившиеся до отмены, уже случились. Правило стоит **выше** правила «группа операций — `preview`»: рутина с `mode: act`, спрятанная внутрь `batch_execute`, получает подтверждение, а не предпросмотр, — иначе обёртка была бы обходом. Карточка такого подтверждения называет **рутину, режим и белый список** («Автономия рутины «…»: режим act, инструменты: …»), а не имя тула — подтверждать «attach_orbis_routine» вслепую значило бы отдать замок модели. Тем же уровнем защищена и **инструкция** act-рутины: правка её тела или заголовка не-владельцем (чат-AI, MCP-агент) — `explicit-confirmation` (проверка по БД в диспатче: цель — рутина с `mode: act`), потому что текст задания и есть содержание автономии.

**Мутация реестра не бывает молчаливой ни для какого актора** [D43]. Признак «перенастраивает поверхность или права» даёт два ряда таблицы, и стоят они порознь, потому что работают в разные стороны. Ряд `behavior-delta` ∨ `system-object` → `explicit-confirmation` стоит **сразу под** рядом архивации: перенастройка поведения обсуждается с владельцем, кем бы ни пришёл вызов, включая его самого через AI. Ряд `own-property` → `preview` для не-владельца стоит **ниже всех** рядов, дающих `explicit-confirmation`: он единственный из новых **понижает** уровень, и наверху он гасил бы и подтверждение по масштабу, и замок автономии — пачка «завести своё свойство + выдать автономию рутине» проехала бы предпросмотром. Сам владелец правит свой реестр **мимо этой политики**: прямые действия идут UI-роутерами, минуя диспатч. Поставка правила двухэтапная: минимальная правка (по имени тула и объекту) — срез А реформы, полная версия (уровень по фактам чувствительности резолвленных шагов действия) — срез Б-1.

**В фоне небезопасное — отложенное действие, а не отказ** [D42]. Одиночный вызов из прогона рутины (`source: routine`), которому политика назначила `explicit-confirmation`, прогон **не останавливает и отказом не кончается**: сервер снимает с цели предусловия («применить, пока значения те же, какими я их видел», §9.2), кладёт неизменяемый payload **отложенным действием** в тред рутины и возвращает модели честное «поставлено на решение владельца». Модель продолжает тем, что можно сделать без него. Открытые отложенные действия и нетерминальные вопросы одного прогона — его **пачка решений** (§9.3): прогон доделывает всё, что может, завершается обычным исходом с флажком `undecided` (§3.15), а владелец разбирает пачку постфактум — поштучно или разом.

Инвариант в новой формулировке: **в фоне небезопасное откладывается с продолжением работы; запрещённое — по уровню или по объекту — отклоняется и не откладывается никогда.** Запрещено по уровню всё, что не `execute` и не одиночное `explicit-confirmation` либо одиночный `preview` **своей строки реестра** (`own-property`): `forbidden` и всякий прочий `preview` — прежде всего групповой. Запрещено по объекту то, до чего фоновому прогону нет хода ни отложкой, ни напрямую: **рутины, прогоны и назначения** (`orbis/routine`, `orbis/agent-run`, `orbis/assignment` — запрет по объекту §9.3), **системные строки реестра** (`system-object` правила выше: встроенные свойства и встроенные аспекты — устройство системы меняет владелец, а не прогон) [D43], а также два повода, которые смотрят не на аспект цели, а на смысл правки, — **выдача автономии** (правило выше) и **правка инструкции act-рутины**. Свои строки владельца сюда не попадают: их правка фоном **откладывается** штатной единицей пачки, и владелец решает её постфактум. Отказ по объекту называет выход — `orbis_ask` открыт рутине в любом режиме, и сказать владельцу «предлагаю переименовать аспект» она может всегда. Стоит этот запрет отдельным пре-чеком **в диспатче, до постановки**, и раньше ветки отложки: карточка, которую доменный инвариант executor'а всё равно убьёт на «Принять», рождаться не должна — отказ прилетел бы владельцу, который ни в чём не виноват; а карточка «снять замок автономии», попавшая под «Принять все», сделала бы кнопку обходом самого замка. Ни один из этих поводов не становится безопаснее оттого, что владелец разберёт его позже.

Довод, снятый этим решением, назван прямо: до D42 отказ обосновывался тем, что «`pending`, созданный в 7 утра автономной рутиной, повис бы навсегда». Для **глагола** исполнителя он в силе (правило выше), для отложенного действия — нет, потому что у пачки есть и контекст, и срок. Контекст — отчёт завершившегося прогона рядом с карточками: владелец читает не одинокий вопрос без истории, а итог работы и то, на чём она остановилась. Срок — следующий прогон той же рутины: он **гасит** всё нерешённое (§9.3), поэтому вечно висящего `pending` не бывает по построению. Третье добавляют предусловия, снятые при постановке: отложенное действие не может молча затереть правку, которую владелец сделал сам, — расхождение даёт «Устарело» со списком, а не тихое применение.

`batch_execute` рутине по-прежнему закрыт **всегда**, даже вписанный владельцем в `allowed_tools`, и отложка этого не ослабляет: откладывается только **одиночное** действие. Группа получает `preview`, то есть заведомо не `execute`, а `preview` в фоне не исполняется и не откладывается — показывать модели инструмент, которому гарантирован отказ, значит нарушить «показанное исполнимо». Второй довод прежний и с приходом отложки стал весомее: гейт режима сверяет только внешнее имя вызова, а вложенные операции группы им не проверяются — одна обёртка провозила бы внутрь что угодно, в том числе мимо пре-чека по объекту.

**Скоуп гранта — ось доступа ДО классификатора.** `worker` (§4.14) отсекает недопустимые тулы структурированным отказом раньше, чем вызов доходит до классификации уровня: классификатор по актору сознательно не ветвится (см. ниже), и вплетать в него права доступа значило бы смешать «насколько это рискованно» с «кому это вообще позволено».

**Правила едины для внутреннего AI и MCP-агентов.** Один и тот же классификатор уровня применяется к вызовам из чата и к вызовам через MCP (§9.3): внешний агент не может получить более широкие права, обойдя политику через другой транспорт.

## §8. Entitlements & metering

Шов для будущей монетизации, закладываемый сейчас, чтобы потом не переписывать проверки по всему коду. Модель, под которую шов закладывается, зафиксирована D36: бесплатный слой — детерминированный захват без LLM, подписка — AI, связка приложений и делегированные сферы; ключи вида `apps.linked_max` добавляются конфигом.

- **Entitlements-резолвер** — один серверный модуль, отвечающий на вопрос «что можно этому пользователю и с какими лимитами» по строковым ключам фич. Резолвер **принимает субъекта параметром**, а не подразумевает единственного пользователя системы — это фиксирует workspace-ready границу (D11) на будущий переход owner→membership. **Все** проверки лимитов в системе идут только через него.

| Ключ | Что ограничивает | Значение для plan `'dev'` |
|---|---|---|
| `ai.requests_per_day` | LLM-запросов в день | не ограничено |
| `ai.tokens_per_day` | Токенов (input+output) в день | не ограничено |
| `aspects.custom_max` | Кастомных аспектов в реестре | не ограничено |
| `import.csv` | Доступность CSV-импорта | разрешено |
| `history.depth_days` | Глубина истории в запросах | не ограничено |
| `agents.requests_per_day` | Запросов внешних агентов (MCP) в день | не ограничено |
| `routines.max` | Сколько рутин (§3.16) владелец может завести | не ограничено |
| `routines.runs_per_day` | Плановых прогонов одной рутины в её локальные сутки | не ограничено |

- **`user_settings.plan`** — строка (сейчас у всех `'dev'`); маппинг план → значения ключей живёт в серверном конфиге, не в БД.
- **`ai_usage`** (§4.7) — метеринг с первого дня: резолвер сравнивает дневные счётчики с лимитами; владельцу метеринг полезен и лично (сколько стоит AI-слой).
- **Два ключа рутин считаются в разных местах и разными сутками** [V1]. `routines.max` гейтится в диспатче тулов **до записи**: завести рутину можно тремя тулами (`entity_create`, `attach_orbis_routine`, группой), и считать их по одному в каждом значило бы три копии одного правила; считаются **заводимые** сущности, а не только существующие, — иначе группа из пяти рутин проходила бы лимит в одну. `routines.runs_per_day` читает планировщик и кнопка «прогнать сейчас» (§9.3), и день здесь — **локальные сутки рутины по дате бакета**, а не сутки, в которые проснулся сервер: бакет 23:30, догнанный в 00:15, и его ретрай относятся ко вчерашнему дню и не съедают сегодняшний слот. Ручной запуск в счёт не идёт (за ним стоит рука владельца), но в исчерпанный лимит упирается — кнопка его не обходит. Календарь `ai_usage` при этом остаётся **UTC-сутками**: два разных дня в одной системе — осознанная цена, названная прямо.
- **Rate limits** (частотные ограничения AI- и agent-запросов) — тоже через резолвер, по тем же ключам.
- **НЕ делаем** в этой итерации: платёжную интеграцию, состояния подписки, тарифную сетку, paywall-экраны. Когда понадобятся — добавится конфиг планов и UI, но ни одна проверка в коде не изменится.

## §9. API и внешние агенты

### §9.1 Внутренний API (tRPC)

Транспорт клиент ↔ сервер — tRPC-роутеры:

| Роутер | Назначение |
|---|---|
| `entity` | CRUD сущностей, выполнение запросов движка (§6) |
| `relation` | Создание/удаление связей, чтение графа связей |
| `aspect` | Чтение реестров, дельты аспектов, заведение и слияние своих свойств (§4.16) |
| `user` | `user_settings`, онбординг-сидирование, экспорт (§9.4) |
| `ai` | LLM-диалог: сборка контекста (§7.1), исполнение тулов, журнал действий |
| `chat` | Треды и сообщения (`chat_threads`, `chat_messages`) |
| `agentRun` | Владельческая половина круга исполнителя (§9.3, D37): ответ на чекпойнт, подметание брошенных прогонов с экрана, откат прогона |
| `version` | Закреплённые версии тела (§4.15, D37): закрепить, список, восстановить |
| `routine` | Владельческая половина рутин (§3.16, §9.3, D38): «прогнать сейчас» (`runNow`), ответ на вопрос прогона (`answerCheckpoint`), чтение предложения (`proposal`), открытых предложений записи (`proposalsForEntity`) [Ш1], решение по нему (`decideProposal`), сводка состояния для экрана (`overview`) |

Отдельного роутера категорий **нет** — категории суть сущности и ходят через `entity`.

Принципы: входы/выходы валидируются Zod-схемами из shared-пакета (одни типы у клиента и сервера, end-to-end типизация); все мутации — `protectedProcedure` (аутентифицированный пользователь); мутации клиента — оптимистичные (§5.1): UI применяет результат сразу, откатывает при ошибке сервера; создание сущностей и fast-path-create **идемпотентно по client-generated `id`** (UUIDv7) — повторный запрос с тем же UUID не создаёт дубль и возвращает исходный результат (контракт retry-буфера, §5.3).

**Один путь мутаций.** PWA никогда не обращается к Supabase Data API напрямую — все мутации идут только через tRPC → executor (§9.2). Прямой доступ к БД в обход executor'а исключает журнал, Undo и валидацию инвариантов, поэтому архитектурно запрещён на уровне того, какие клиенты и ключи вообще имеют доступ к Data API.

**Min-compatible-version.** Сервер объявляет минимальную совместимую версию клиента; запрос от клиента старше этой версии получает структурированную ошибку с требованием обновиться, а не пытается работать в неопределённо совместимом режиме. Это защищает от разъезда контрактов схем/грамматики между устаревшей закэшированной PWA и текущим сервером.

Точные сигнатуры процедур в PRD не фиксируются — этот контракт живёт в коде и проверяется типами. Единственное место, где API специфицируется как внешний контракт, — реестр тулов (§9.2).

### §9.2 Реестр тулов — единый публичный контракт

Один реестр тулов с одним tool-executor'ом и **двумя потребителями**: внутренний чат-LLM (§7) и внешние агенты через MCP (§9.3). Любое действие любого потребителя проходит через executor → попадает в журнал действий (§7.8) → подлежит Undo.

Core-тулы (нотация input-схем: `*` после типа — обязательное поле, `?` после имени — опциональное):

| Тул | Назначение | Input-схема |
|---|---|---|
| `entity_query` | Поиск/фильтрация сущностей | `{ query?: string, ast?: QueryAST }` — **ровно одно из двух**: строка грамматики §6.1 (включая `sortBy`, `limit`) **или** готовое дерево §6 [D43]. Дерево — единственный способ выразить OR между разными свойствами и вложенные группы; JSON Schema дерева рекурсивна и проверена на приём провайдером (§7.7). Возвращает список сущностей (core + tags + props + aspects) |
| `entity_get` | Полное чтение одной сущности | `{ id: uuid*, include?: ("body" \| "relations" \| "backlinks" \| "thread")[] }` — по умолчанию `body` + `relations`; `backlinks` — кто ссылается через `body_refs`; `thread` — сообщения треда сущности |
| `entity_create` | Создание сущности | `{ id?: uuid, title: string*, emoji?: string, body?: string, tags: string[]*, props?: object, aspects?: string[] }` [D43] — `id` опционален (идемпотентность повторов); `props` — значения по `key` свойства (id тоже принимается), `aspects` — **список id аспектов**; значения валидируются по типам реестра |
| `entity_update` | Частичное обновление | `{ id: uuid*, title?, emoji?, body?, tags?, props?: object, unset?: string[], aspects?: { attach?: string[], detach?: string[] }, archived? }` [D43] — передаются только изменяемые поля. `props` **ставит** значения, `unset` — **снимает** их отдельным списком (а не `null` внутри `props`: `null` — законное значение json-свойства). Снятие аспекта значения **не удаляет**: аспект не владелец поля (§3.10) |
| `relation_create` | Создание ребра | `{ source_id: uuid*, target_id: uuid*, role: string* }` [D43] — id роли из реестра (§4.2). Роль с ограничением «создаёт только система» из тула — отказ `ROLE_SYSTEM_ONLY` |
| `relation_delete` | Удаление ребра | `{ source_id: uuid*, target_id: uuid*, role: string* }` — та же адресация, что в `relation_create` |
| `property_catalog` | Справка по словарю свойств | `{ q?: string, aspect?: string, module?: string, contract?: string, status?: ("active" \| "proposed" \| "deprecated"), orphans?: boolean, olderThanDays?: number }` — фильтр `contract` схема принимает, но в срезе А он **инертен**: контрактов ещё нет (§4.16), и выдачу он не сужает. [D43] — read-тул: отдаёт `key`, подпись, описание, тип, варианты, аспекты-носители и число записей, где свойство заполнено. **Единственный путь модели к свободным и `proposed` свойствам** — у них нет `attach_*`-тула, а в промпт словарь не печатается (§7.1). Доступен полному гранту и рутинам; фоновому исполнителю по скоупу `worker` — нет |
| `thread_post` | Заметка в тред сущности | `{ entity_id: uuid*, content: string* }` — добавляет сообщение в тред сущности (§4.5); без него сценарий MCP-агента «оставить заметку в треде» невыполним (02-core-os §5). Единственный **core**-тул, доступный скоупу `worker` на запись (глаголы исполнителя — таблицей ниже), — и **только в его периметре**: треды назначенных гранту тикетов и их прямых родителей по иерархическим рёбрам (§4.14) |
| `batch_execute` | Атомарная группа мутаций с единым Undo | `{ batch_id: uuid*, operations: { tool: string*, input: object* }[]* }`. Допустимы мутирующие core- и `attach_*`-тулы, кроме самого `batch_execute`; порядок значим, весь batch валидируется до начала и выполняется одной транзакцией (§7.8) |

Внутренний хелпер `user_query` (вопрос-агрегация «сколько потрачено на еду за месяц») в публичный реестр **не входит** — это внутренний инструмент чат-LLM; MCP-агенты используют `entity_query` и агрегируют результаты сами. Тем же признаком `internalOnly` помечены `import_csv_start` (открыть экран импорта: у внешнего агента экрана нет) и `undo_last` (`{}` — «отмени последнее» словами в чате, обёртка над Undo §7.8: снимает последнее видимое действие журнала владельца; внешний агент отменяет своё обратными операциями, а рутине он закрыт наглухо, как `batch_execute`, — фоновый прогон не вправе снимать действия владельца; диспатч принимает его только от чата). Отсечение стоит в диспатче, а не только в списке тулов MCP-адаптера, — фильтрация списка вторая линия, не единственная.

**`precondition` — серверное расширение `entity_update`, не поле его контракта.** CAS-предусловие сверяется со строкой, прочитанной под замком, и применяется в той же транзакции (стадии 3–5 конвейера ниже); провал даёт `CONFLICT` с `details: {reason: "precondition_failed", precondition, actual, mismatches}`. Форм у пункта две, и адресуется он **свойством**, а не парой «аспект + поле» [D43]: `{property: <id>, in: [...]}` — «значение сейчас одно из перечисленных» — и `{property: <id>, absent: true}` — «свойства сейчас нет вовсе» (V1). Core-колонки адресуются через свойства ядра (§3.17); псевдо-аспект, которым они адресовались раньше, снят вместе со вторым несовместимым способом делать то же самое. Сравнение идёт **по типу свойства**: у `decimal` `"10.0"` и `"10.00"` — одно значение, а не разные строки. Неизвестный id свойства — отказ валидации, а не «расхождение»: предусловие, которое не с чем сверить, обязано падать громко. Вторая появилась не для симметрии: главный класс правок, которые предлагает рутина, — **проставить поле, которого не было** (срок у задачи без срока), и без формы отсутствия такое предложение было бы невыразимо, а «отсутствующее поле — всегда конфликт» отклоняло бы его всегда. `absent` выполнено ровно тогда, когда свойства нет; `in` по отсутствующему свойству по-прежнему конфликт. Расхождения собираются **все**, а не только первое: `details.mismatches[]` (`property`, `expected` — список значений либо `'absent'`, `actual`) — иначе владелец, которому предложение отказало, чинил бы расхождения по одному, не зная, сколько их. Первое несовпадение дублируется в `precondition`/`actual` для совместимости. Именно предусловие делает захват тикета исполнителем атомарным (§9.3): два конкурентных `planned → in_progress` не могут оба увидеть `planned`. Ни тул, ни tRPC-процедура его не принимают — схему расширяет только вход executor'а: это рычаг серверных путей (захват тикета, подметание, ответ на чекпойнт, `orbis_finish` с `may_close`, применение предложения рутины), а не поле, которое модель или клиент подставляют сами.

Глаголы исполнителя (§9.3, D37) — пять тулов с признаком **`agentOnly`**: тому, у кого есть **субъект прогона** — грант внешнего агента или рутина (§3.16, V1), — они отдаются, реестру обычного чата нет (у чата субъекта нет, и прогон ему не к чему отнести). Внутреннему исполнителю рутины из этих пяти открыт один `orbis_checkpoint`: остальные — про круг тикета, которого у рутины не бывает. Вторым вопросом рутины рядом с ним стоит `orbis_ask` (ниже) — тул не из этой пятёрки и не `agentOnly`.

| Тул | Назначение | Input-схема |
|---|---|---|
| `orbis_my_queue` | Что мне назначено: тикеты этого доступа со статусом, проектом и сводкой последнего прогона; по дороге подметает брошенные прогоны | `{}` — адресат берётся из гранта, а не из аргумента |
| `orbis_claim_task` | Атомарный захват: тикет → `in_progress`, создан прогон. Возвращает задание, `body` проекта с процессом и историю прошлых прогонов | `{ ticket_id: uuid*, session_url?: uri, id?: uuid }` — `id` (ключ идемпотентности) делает повтор безопасным |
| `orbis_run_step` | Зафиксировать шаг прогона | `{ run_id: uuid*, summary: string*, external?: boolean, id?: uuid }` — `external` = «шаг тронул внешнее» (ветка, файлы, сеть) |
| `orbis_checkpoint` | Встать с вопросом и остановиться: тикет → `waiting`, прогон терминален | `{ run_id: uuid*, question: string*, usage?, session_url?, id?: uuid }` |
| `orbis_finish` | Итог «готово, проверь»; прогон терминален | `{ run_id: uuid*, report: string*, usage?, session_url?, id?: uuid }` |
| `orbis_ask` [D42] | **`routineOnly`**: спросить владельца и **работать дальше** — вопрос ложится карточкой-единицей в тред рутины, прогон не останавливается и не становится терминальным. Ответа в этом прогоне не будет: владелец разбирает вопрос постфактум, а ответ приезжает историей прогонов в следующий (§9.3). Возвращает модели `{pending_id}` — id созданной карточки; повтор того же вопроса в том же прогоне отдаёт **ту же** карточку (ключ идемпотентности выводится из содержимого, а не берётся с входа: модель вольна выдумать его заново, а содержимое — нет) | `{ run_id: uuid*, question: string* (≤ 4000), options?: string[] }` — до **4** готовых ответов кнопками (≤ 200 символов каждый); список, не помещающийся на экран, — требование довериться, а не выбор |
| `orbis_propose` [V1] | **`routineOnly`**, а не `agentOnly`: предложить владельцу правки одной группой и закончить прогон — единственный способ рутины в режиме `propose` тронуть граф. Предусловия сервер снимает сам с текущих значений; прогон после вызова терминален. Цели операций — не рутины, не прогоны и не назначения (запрет по объекту §9.3, статически и по БД); правка тела сущности — единственная операция по ней в предложении; цель обязана существовать на момент вызова (сослаться на сущность из соседнего `entity_create` того же предложения нельзя) | `{ run_id: uuid*, explanation: string*, operations: { tool: string*, input: object* }[]*, id?: uuid }` — `operations` до **50**, `tool` только `entity_create` \| `entity_update` \| `relation_create` \| `relation_delete`; `explanation` (≤ 4000) — прозой, зачем это нужно: владелец читает объяснение, а не список операций |

`orbis_ask` и `orbis_propose` вынесены отдельными строками, потому что они **не глаголы исполнителя**: круг тикета они не расширяют и внешнему агенту не отдаются ни при каком скоупе. Признак у обоих свой — `routineOnly`: чат и MCP их не видят (фильтры списков) и не зовут (гейт диспатча) — и предложение, и вопрос адресуются прогону, а вне прогона их некуда положить. У `orbis_ask` гейт **временный, с названным условием снятия** [D42]: в самом контракте вопроса нет ничего рутинного, но петлю «спросил → получил ответ → продолжил» Orbis сегодня замыкает только у внутреннего раннера — внешний агент вправе задать вопрос и умереть, оставив тикет без сигнала, а запустить его заново Orbis не умеет. Гейт снимается вместе с запуском исполнителя.

**Пять тулов мутации реестра** [D43] — ими AI и владелец правят устройство системы, а не записи графа: `property_create` (завести своё свойство — статусом `active` либо `proposed`), `property_update` (подпись, описание, статус), `property_merge` (слить два свойства в одно — §4.16), `aspect_delta_set` и `aspect_delta_remove` (персональная дельта аспекта: скрыть свойство, добавить своё, переименовать подпись). Все пять — мутации, все пять доступны только полному гранту (у скоупа `worker` тулов реестра нет вовсе), и ни один из них не исполняется молча: класс подтверждения таких вызовов задан отдельным входом политики (§7.10).

**Статус нового свойства — не запрет схемы, а РАЗНЫЙ ЗАМОК** [D43]. Схема `property_create` принимает оба значения от любого вызывателя, и «заводя свойство от себя, ставь `proposed`» — это **инструкция модели в описании параметра**, а не серверный отказ. Границу держит политика подтверждений, и с ревизии по итогам финального ревью ветки она классифицирует ветки **по-разному**: `proposed` — `own-property` (предпросмотр для не-владельца), `active` — `behavior-delta` (явное подтверждение, §7.10). Довод — не симметрия ради симметрии: `proposed` не попадает в промпт и ждёт разбора, а неразобранных таких у владельца не больше **20**, и кап считает **только** `proposed` — то есть строка, заведённая сразу активной, проходит мимо разбора пачки вовсе. Живой замер Задачи 17 показал, что предпосылка §А2-7 «инициатива AI ⇒ `proposed`» промптом не держится (2 свойства из 2 модель завела со `status: active`), и рычаг, который её удерживает, — серверный: тот же замок, что у перехода «`proposed → active`».

Реестр целиком — **37 тулов**: 13 core (девять из таблицы выше плюс `user_query`, `budget_status` — сводка конвертов, 03-budget, — `import_csv_start` и `undo_last`), 5 тулов мутации реестра, 5 глаголов исполнителя, `orbis_ask`, `orbis_propose` и 12 `attach_<key аспекта>`. В MCP по гранту `full` отдаются **32** (37 минус три `internalOnly` — `user_query`, `import_csv_start`, `undo_last` — и два `routineOnly`), по гранту `worker` — **9**: три чтения (`entity_query`, `entity_get`, `budget_status`), пять глаголов исполнителя и `thread_post`. `attach_*` служебные аспекты не получают (§3.8), поэтому их 12, а не 13.

Отдельной строкой — то, чего в срезе А **нет**: тула `run_action`, который публиковал бы декларированные действия каталогом вместо тула на каждое (**часть Б**, вместе с самой таблицей действий). Пока действий нет, реестр тулов растёт только аспектами, и это его единственная ось роста.

Динамические тулы: **`attach_<key аспекта>`** — по одному на каждый неслужебный аспект реестра, генерируются автоматически (§7.6):

| Тул | Input-схема |
|---|---|
| `attach_orbis_task`, `attach_orbis_financial`, … | `{ entity_id: uuid*, data: object* }` — `data` описывает **свойства аспекта по их `key`**, схема склеена из их типов (§7.6) |

**Конвейер executor'а.** Любая мутация — от одиночного тула, batch'а (§7.8), fast-path-ввода или MCP-вызова (§9.3) — проходит один и тот же семистадийный конвейер:

1. **validate envelope** — структурная валидация входного payload по Zod-схеме тула/операции;
2. **validate props** — валидация значений по **типам свойств** из реестра (§4.16) и проверка, что у каждого аспекта сущности есть все его обязательные свойства; неизвестный id свойства — отказ;
3. **load state** — чтение текущего состояния затронутых сущностей/связей из Postgres;
4. **validate all before first write** — проверка доменных инвариантов (§4.2, §3.3 и др.) над загруженным состоянием; при любой ошибке — отказ до единственной записи в БД;
5. **apply in transaction** — применение всех операций одной PostgreSQL-транзакцией;
6. **inverse ops + cards** — вычисление обратных операций для Undo и данных для карточки чата (§7.8);
7. **audit** — запись одного action в журнал (§7.8).

Стадии 1–4 гарантируют «всё или ничего» до первой записи: мутация, провалившая структурную валидацию, доменный инвариант или проверку состояния, не оставляет частичного следа в БД — ни для одиночного тула, ни для элемента batch'а.

Контрактные гарантии сверх самого конвейера: ошибки на любой стадии — структурированные (код + сообщение); `batch_execute` идемпотентен по `batch_id` (повтор конфликтует по PK и возвращает сохранённый результат, §7.8); лимиты — через entitlements-резолвер (§8); уровень подтверждения (§7.10) применяется до стадии 5 — `explicit-confirmation`-действие не доходит до apply без подтверждения пользователя.

### §9.3 MCP-сервер

**Статус: MVP, слайс 1; браузерный вход — слайс 4b (D34); круг исполнителя и скоуп `worker` — ADE-срез 1 (D37); внутренний исполнитель рутин — V1 (D38, в конце раздела).** MCP-сервер — **тонкий адаптер** над тем же tool-executor'ом, что у внутреннего чата: транслирует MCP-вызовы в тулы §9.2 один в один, без собственной бизнес-логики. Способности внешнего агента при этом **не равны** способностям внутреннего AI, и разница идёт в обе стороны (D37): грант `full` получает те же core-тулы, что чат, **плюс** пять глаголов исполнителя (§9.2, признак `agentOnly`); грант `worker` — только глаголы, `thread_post` в свой периметр и чтения, и **ни одного тула реестра** (§9.2); а обычный чат глаголов не видит вовсе — реестр чата отсекает `agentOnly` (прогон адресуется субъекту — гранту или рутине, — а у чата субъекта нет). Общее у всех путей одно: конвейер мутаций §9.2, журнал §7.8 и политика подтверждений §7.10.

- **Аутентификация: OAuth 2.1 с браузерным входом — основной путь** (D34). Orbis выступает собственным authorization server: отдаёт метаданные ресурса (RFC 9728) и authorization server (RFC 8414), поддерживает динамическую регистрацию клиентов (RFC 7591), PKCE (только `S256`), точную сверку `redirect_uri` и ротацию refresh. Подключение агента — одна команда `claude mcp add --transport http orbis <url>/mcp` плюс `/mcp` в сессии: 401 с `WWW-Authenticate` приводит клиента к метаданным, дальше он регистрируется сам и открывает браузер на экране согласия. Владельца там узнаёт Supabase-сессия веб-клиента — **но выпущенный Supabase токен на `/mcp` не принимается**: у него чужая аудитория, и спека MCP называет приём такого токена прямым запретом. Секрет руками не переносится, выданные доступы видны в настройках и отзываются кнопкой (02-core-os §1.6).
- **PAT остаётся — для headless.** `claude -p`, Agent SDK и CI интерактивный вход не проходят, поэтому заголовочный путь (`Authorization: Bearer <токен>`) сохранён; выдача — CLI (операция белого списка на проде, `docs/implementation/02-ops-runbook.md` §3). Заголовочный и браузерный пути **не смешиваются в одной записи конфига агента**: при заданном `headers.Authorization` клиент на OAuth не откатывается, а рапортует о сбое соединения.
- **Контракт хранения — hash-only, для обоих путей**: в базе живёт только `sha256` (§4.14), сырой токен показывается **один раз** и не восстановим повторно. Токены непрозрачные, а не подписанные: отзыв обязан действовать немедленно, значит сверка с базой нужна на каждом вызове — и выигрыш самопроверяемого JWT испаряется, оставляя лишний секрет в окружении. Прежнее требование **constant-time-сравнения снято вместе с тем, что его вызывало**: сравнивать хеш с секретом из окружения больше не с чем — предъявленный токен хешируется и ищется уникальным индексом по `access_hash`. Тайминг индексного поиска говорит о хранимых `sha256`, а не о токене, и полезен атакующему только после обращения sha256.
- **Отзыв — в настройках**, мгновенный и по одному доступу («Настройки → Агенты»); несколько токенов на владельца — норма, а не исключение. **Область доступа выбирается при выдаче** — `full` или `worker` (§4.14, D37): `worker` открывает чтения, пять глаголов исполнителя и `thread_post` в свой периметр (треды назначенных тикетов и их прямых родителей — §4.14), всё остальное отклоняет структурированным отказом. Скоуп — ось доступа; разрушительность внутри разрешённого гейтит политика подтверждений §7.10, одна для внутреннего AI и агентов.
- **Аудит**: действия агентов пишутся в тот же журнал действий (§7.8) — пользователь видит карточки агентских действий, inline-правка и **Undo работают и для агентов**; политика подтверждений (§7.10) применяется одинаково к внутреннему AI и MCP-агентам.
- **Лимиты**: `agents.requests_per_day` и rate limits через entitlements-резолвер (§8).

Первый эталонный сценарий — «найди среди моих задач X и выполни»:

1. `entity_query({ query: "aspect=orbis/task, orbis/task_status=!done&!cancelled, search=X" })` → агент получает кандидатов, выбирает нужную задачу;
2. `entity_get({ id, include: ["body", "relations", "thread"] })` → агент читает постановку из body, контекст из связей (блокеры, родительский проект) и обсуждение из треда;
3. агент выполняет работу своими средствами (вне Orbis);
4. `entity_update({ id, props: { "orbis/task_status": "done" } })` → задача закрыта; момент завершения (`orbis/completed_at`) проставляет сам сервер инвариантом перехода (§3.2), агенту его передавать не нужно. Действие — в журнале, пользователь видит карточку и может отменить.

Это путь **полного** гранта: агент действует по просьбе владельца, как внутренний AI. Исполнитель, которому тикет назначен (третий сценарий), тикет не закрывает — `orbis_finish` уводит его в `waiting` «готово, проверь», а `done` возможен, только если владелец заранее разрешил это назначением (`may_close`, §3.14).

Второй эталонный сценарий — polling-петля агента **«что нового»** (без нового серверного механизма, только комбинация существующих тулов):

1. `entity_query({ query: "orbis/updated_at>2026-07-02T09:00:00Z" })` — сравнение по core-свойству `orbis/updated_at` (§3.17) с абсолютным ISO-8601-значением курсора (§6.1) находит задачи и другие сущности, изменённые с момента прошлого опроса;
2. `entity_get({ id, include: ["thread"] })` — агент читает новые инструкции, оставленные владельцем в треде каждой изменённой сущности;
3. курсор — «момент прошлого опроса» — агент хранит **у себя** (не на сервере Orbis); следующий цикл передаёт в `entity_query` актуальный курсор.

Третий эталонный сценарий — **круг исполнителя** (D37, ADE-срез 1): агент с грантом `worker` ведёт назначенные ему тикеты.

1. `orbis_my_queue({})` → тикеты, назначенные **этому доступу** (`orbis/grant` назначения = грант вызова, §3.14), с пометкой `claimable` (взять можно `inbox` и `planned`) и сводкой последнего прогона. По дороге сервер помечает брошенные прогоны владельца и возвращает их тикеты в очередь — в ответе это `swept`;
2. `orbis_claim_task({ ticket_id, id })` → **атомарно**: тикет уходит в `in_progress` и создаётся сущность-прогон (§3.15), дочерняя тикету. Одним batch'ем с CAS-предусловиями (§9.2) — второй агент на тот же тикет получает `CONFLICT`, а не второй прогон. В ответе — задание, `body` проекта с описанием процесса и история прошлых прогонов с вопросами и ответами владельца;
3. `orbis_run_step({ run_id, summary, external, id })` — по шагу на осмысленную единицу работы: сводка для ленты и флаг «тронул внешнее». Шаг — CAS по счётчику `step_count`: конкурентная запись не теряется молча, а превращается в перечитывание. Ретраит **сервер сам**, до трёх раз; агент видит `CONFLICT` только после трёх проигранных попыток — снаружи параллельные шаги успешны, а порядок `seq` строгий. Прогон без шагов дольше порога считается брошенным;
4. развилка: `orbis_checkpoint({ run_id, question, id })` → прогон терминален, тикет в `waiting` с вопросом в `waiting_for` — то же состояние, что при любом другом ожидании человека; либо `orbis_finish({ run_id, report, id })` → прогон терминален, тикет в `waiting` «готово, проверь» (в `done` — только при `may_close`, §3.14);
5. владелец отвечает на чекпойнт **кнопкой на экране тикета**: ответ ложится на прогон, тикет возвращается в `planned` — одним действием и одной записью журнала. Следующий `orbis_claim_task` читает ответ в истории и не начинает разговор заново.

Оборванный прогон (агент упал, ноутбук закрыли) чинит **подметание**: прогон без шагов дольше порога (**30 минут** — серверная константа; между шагами агент гоняет тесты и думает, поэтому порог щедрый) помечается `abandoned` при чтении очереди, при открытии экранов проекта и тикета и на тике планировщика рутин. Рутинный прогон подметается в `failed`, а не в `abandoned` (V1): у него нет ни тикета, чтобы вернуть его в очередь, ни человека за спиной — для него «оборвался» и есть «упал», и ретрай бакета опирается именно на этот исход. Статус тикета выбирается по признаку эффекта — шагов с `external` не было, значит перезапуск безопасен и тикет уходит в `planned`; эффект был — в `waiting` с описанием остатков, и решает человек. Возврат брошенного прогона с эффектом в `planned` запрещён: он стёр бы факт, что работа велась, и следующий агент наткнулся бы на чужую недоделанную ветку. **Статус тикета правит только его последний прогон**: у тикета бывает два `running`-прогона (владелец вернул статус руками при живом прогоне, и следующий захват завёл второй), и подметание старого хвоста не вправе выбить из работы тикет, над которым уже работает новый прогон. Архив подметанию не помеха — инвариант «тикет не висит `in_progress` навсегда» про состояние графа, а не про видимость на экране.

Всю работу прогона можно **откатить одной кнопкой** на его экране: сервер собирает действия прогона по обратной ссылке `run_id` в журнале (§7.8) и применяет их `inverse` в обратном порядке существующей механикой Undo — нового механизма отмены нет. Перед первой отменой идёт **предпроверка**: если те же сущности правил кто-то ещё — начиная с **первого** действия прогона, а не с последнего, — откат не выполняется, а возвращает список конфликтов: затирать чужие решения молча он не вправе. Окно считается от первого действия потому, что правка владельца лежит между действиями прогона, а обратная операция возвращает прежние значения затронутых свойств. Ветку и коммиты в репозитории откат не трогает, и на экране это написано прямо: смешение двух механизмов дало бы «отменил в Orbis, а код остался».

Все три сценария используют один и тот же реестр тулов (§9.2); специального push-канала к агенту в MVP нет — агентная петля работает на polling, инициируемом самим агентом. Запуск **внешнего** исполнителя остаётся **ручным**: «агент приходит сам» значит «когда владелец запустил его сам» — из интерфейса Orbis запуск не инициируется. Исполнителя **внутреннего** запускает сам Orbis — по расписанию рутины (ниже).

**Внутренний исполнитель — четвёртый путь к тому же executor'у** [V1, D38]. Рутина (§3.16) — это работа, которую Orbis делает сам по расписанию владельца, без MCP и без внешнего агента: сервер в назначенный час создаёт прогон (§3.15) и сам гоняет по нему цикл модели.

- **Раннер — свой цикл из существующих кирпичей.** Провайдер, реестр тулов, диспатч, метеринг и гейт лимитов (§8) — те же, что у чата; своё у него три вещи. Первая — **системный слой**: отдельная версионированная линейка промптов (`routine-v2`), потому что чат-промпт учит завершать ход ответом собеседнику, а у фонового прогона собеседника нет. Вторая — **история вместо треда**: контекстом идут последние **7** прогонов этой рутины с их отчётами, вопросами и ответами владельца, а не переписка (у ежедневной рутины тред рос бы линейно). Третья — **терминальные инструменты**: `orbis_propose` и `orbis_checkpoint` заканчивают прогон, шаги пишет раннер сам, и `orbis_run_step` / `orbis_finish` модели не показываются вовсе. Различать терминальное и нетерминальное — работа промпта, а не сервера: рядом с чекпойнтом у рутины стоит `orbis_ask`, который прогон **не** заканчивает [D42], и выбор между ними делает модель.
- **Пределы прогона.** Дедлайн **10 минут**, проверяемый **между шагами** (внешнего сигнала транспорт провайдера не принимает, поэтому в худшем случае прогон живёт дедлайн плюс один шаг — цена сборки из готовых деталей), **свой** потолок шагов — **12** против восьми у чата [D42], и шаг здесь считается обращением к модели, а не вызовом тула (несколько вызовов одним ответом — один шаг). Числа разведены не для запаса: у чата за каждым шагом сидит человек, и оборванный разговор он продолжает репликой, — а фоновый прогон, упёршийся в потолок, оставит утро без плана до следующего слота. Настоящая верхняя граница прогона при этом всё равно дедлайн, потолок шагов страхует от зацикливания модели. Плюс два разных лимита §8, которые не стоит смешивать: **`routines.runs_per_day`** проверяет планировщик **до создания прогона** (исчерпан — слот пропускается, прогона и `fail_note` нет), а **дневной гейт `ai.*`** проверяет раннер **уже созданного** прогона перед первым обращением к модели (исчерпан — прогон закрывается `failed` с причиной «дневной лимит»). Сбой раскладывается по видам и пишется в `fail_note`: провайдер, дедлайн, дневной лимит `ai.*`, отказ модели, «предложил ничего», **упёрся в потолок шагов**, **внутренняя ошибка раннера** (в том числе до цикла модели — в гашении прошлого, гейте или сборке контекста), остановка процесса. **Три подряд** плановых прогона с исходом `failed` ставят рутину на `paused` с записью в её тред — стоп-кран: рутина, ломающаяся каждое утро, перестаёт жечь токены и молчать. Ручные запуски в счёт стоп-крана не идут. Считаются только провалы **после последней записи стоп-крана** (она несёт `run_id` последнего учтённого): снятая владельцем пауза — счёт с нуля, иначе первый же новый сбой возвращал бы паузу по старым провалам, и ретраи бакета не случались бы. Стоп-кран оценивается не только раннером после своего сбоя, но и **тиком планировщика по графу** (после подметания, до решения о запуске): три провала, закрытые подметанием (крэш-луп процесса), ставят паузу тем же тиком, а не ждут первого «живого» сбоя.
- **Планировщик — таймер в процессе сервера**, тик раз в **60 с**, включается переменной окружения `ORBIS_ROUTINE_SCHEDULER=1`; выключенный фон — штатное состояние стенда и тестов. Логика **догоняющая**, а не «сработать ровно в момент»: тик смотрит, какие слоты наступили и ещё не исполнены, и берёт их в окне догона **6 часов** — сервер, проспавший ночь на free-плане, догоняет утренний слот и молча пропускает вчерашний вечерний. Неудача бакета ретраится до трёх попыток с нарастающими паузами **5 и 15 минут**. Состояние фона видно в `/health` полем `routineScheduler`: `off` (не включён), `pending` (включён, первого тика ещё не было) или ISO-время **начала последнего тика** — по нему внешний пингер (`docs/implementation/02-ops-runbook.md` §5) отличает «процесс отвечает» от «таймер жив». Именно **таймер**, а не работа: отметка ставится в момент запуска тика, до его тела, и свежее время означает «фон крутится», а не «обход владельцев удался» — сбой внутри тика (нет прав на список владельцев, отказ записи) виден только в логах.
- **Один слот — ровно один прогон, даже если тиков два.** Прогон создаётся группой `[entity_create, relation_create]` с **детерминированным `batch_id`**, выведенным из рутины, слота и номера попытки, — то есть идемпотентность группы (§7.8, PK audit-сообщения) и есть защита от гонки. Проигравший узнаёт себя по одному из трёх ответов — сохранённый результат повтора, конфликт занятого `id`, конфликт уже существующей связи — и модель не гонит. Второго механизма блокировок под это не заведено.
- **Планировщику нужен список владельцев — единственное, что он делает без identity** (§4.10, миграция `0013`): он читает `owner_id` из `user_settings` под служебной ролью, а всё дальнейшее — под `withIdentity(владелец)` и обычной RLS.
- **Права внутреннего исполнителя.** Чтения — все; писать в режиме `propose` он может только предложение, в режиме `act` — ровно инструментами из `allowed_tools`. Запрет по объекту абсолютен и не зависит от белого списка: **рутины, прогоны и назначения** (`orbis/routine`, `orbis/agent-run`, `orbis/assignment`) фоновый прогон не создаёт, не правит и не связывает — ни тулом, ни операцией внутри предложения (прогоны — чтобы рутина не подделала «ответ владельца», не закрыла чужие прогоны в обход стоп-крана и не завела фальшивый вопрос; свою бухгалтерию прогон ведёт источником `system`). Рядом с этими тремя целями стоят ещё два повода того же отказа — **выдача автономии** и **правка инструкции act-рутины**: с D42 всё прочее небезопасное фоновый прогон откладывает, а эти поводы остаются отказом и не откладываются никогда (§7.10). Проверок три, и все нужны: глагол `orbis_propose` отсекает такие операции статически и чтением целевых сущностей из БД (по `id` чужой рутины форму не отличить); объектный пре-чек диспатча стоит **до постановки отложенной единицы** — иначе карточка родилась бы и умерла на «Принять» в руках владельца; инвариант executor'а стоит последним рубежом на применении — предложение применяется мимо диспатча, одной группой.
- **Предложение и его судьба.** `orbis_propose` кладёт операции в отложенное действие (§7.10) с автоматически снятыми предусловиями — «применить, пока значения те же, какими я их видел», включая форму `absent` для полей, которых не было (§9.2). Владелец видит карточку с **перечисленными** правками в треде рутины и на экране прогона; «Принять» применяет всё одной группой с `run_id` прогона, «Отклонить» закрывает, ничего не тронув, расхождение предусловий даёт отказ **со списком расхождений**, а не молчаливое «конфликт» (у правки тела — расхождение по CAS `updated_at`, показанное словами «тело изменено после составления»; правка тела в предложении — единственная операция по своей сущности). Незакрытое предложение предыдущего прогона новый прогон **гасит**: `superseded` — отличимо от отказа владельца; незакрытый вопрос чекпойнта становится `stale`. Третий жест владельца — **правка до принятия** [Ш1]: значения полей и текст тела правятся в слое предложения на самой записи (02-core-os §3.5), и «Принять» применяет правленое. Правка исходный payload не переписывает — она порождает **новое** отложенное действие (§7.10), а исходное гасится причиной `edited`, отличимой и от отказа владельца, и от гашения новым прогоном. Отдельного статуса правка не заводит (статусов по-прежнему пять): признак на живом предложении — `edited_from` (§3.15), по нему же читается цепочка предыдущих, а указатель прогона всегда стоит на **текущем** предложении — и открытых у прогона не бывает больше одного. Применённое правленое действие несёт `edited_from` и в журнал (§7.8), а следующему прогону в историю едет «предложение: принято с правками владельца» вместо «принято»: «текст был верен» и «текст пришлось переписать» — разная обратная связь, и без неё рутина повторяла бы отвергнутую формулировку слово в слово. Правки владельца, потерявшие своё предложение (граф разошёлся — `stale`), не применяются: применять уже нечего, правленый текст остаётся карточкой в треде.
- **Пачка решений — вопросы и отложенное без остановки прогона** [D42]. Прогон, наткнувшийся на небезопасное, больше не упирается в тупик: одиночное действие уровня `explicit-confirmation` он **откладывает** (§7.10), а вопрос, без ответа на который работа всё-таки продолжается, задаёт нетерминальным `orbis_ask` (§9.2), — и в обоих случаях работает дальше, а не завершается. Открытые единицы прогона — карточки в треде рутины и на экране прогона (02-core-os §3.5) — и есть его **пачка**; флажок `undecided` на аспекте (§3.15) делает её видимой списком «Рутины» (02-core-os §3.3), не заставляя пересчитывать тред. Единица приёмки — **одна карточка**: внутри неё атомарно (тот же batch и тот же откат, что у предложения), между единицами атомарности нет и она не обещается — «Принять все» идёт последовательно и отдаёт сводку по каждой, а одна протухшая не блокирует остальные; зависимые операции кладутся в одну единицу, зависимостей между единицами не бывает по построению. Судьба единицы **единственна**: ответ и гашение борются под одним замком, первая записанная финальна, и ответ важнее гашения — то же правило, что у терминального вопроса. Нерешённое **гасит следующий прогон** — плановый или запущенный кнопкой «Продолжить сейчас», — снимая `undecided`; откат прогона гасит пачку так же, до архивации. Следствие, которое владелец знает заранее: ответив на часть и продолжив, остальное он теряет — актуальное новый прогон переспросит и переотложит заново, по свежему состоянию. Ответы доезжают **историей прогонов**, а не лентой треда: к каждому прогону хвоста едет список его единиц с судьбами («спрашивал: … — ответ: …», «откладывал: … — принято»), усечённый с честным «и ещё N решений»; автозапуска по ответу нет — работу продолжает плановый прогон или кнопка владельца. Потолок единиц на прогон — **10**, и превышение отдаётся модели структурным отказом («пачка полна — заверши прогон»), а не молчаливым усечением: карточки читает человек, и список, не помещающийся на экран, — требование довериться, а не решение.
- **Всё это откатывается тем же Undo — с поправкой на бухгалтерию.** Откат рутинного прогона (кнопка на экране прогона) собирает по `run_id` его **работу** — действия источника `routine`: мутации модели и применённое предложение — и отменяет их существующей механикой в обратном порядке, ища конфликты только по их сущностям; бухгалтерия прогона (создание, шаги, закрытие, пометки) и решения владельца о нём (ответ на вопрос) не инвертируются и конфликтом не считаются, а след отката — **архив прогона** явной операцией (слот при этом остаётся отработанным — ретрая нет; карточка принятого предложения показывает «Принято, затем откачено»). Это отличает его от отката грантового прогона, который инвертирует всё, включая создание. «Отмени последнее» после утреннего прогона снимает правку модели, а после «Принять» — применённый план, а не бухгалтерию прогона (§7.8, расщепление атрибуции). Откат прогона с ещё открытым предложением или вопросом **гасит их** (`stale`: предложение отклонено причиной `stale`, вопрос снят с записью в тред рутины) до архивации — архивный прогон для решения и ответа «не найден», и карточка с живыми кнопками вела бы в ошибку, а обзор рутины считал бы их ожиданием; «ждут ответа» и «есть открытое предложение» обзор считает только по неархивным прогонам (последний прогон и история — по всем). Смерть процесса посреди прогона закрывает его `failed` — при штатной остановке это делает сам раннер по сигналу (и плановый прогон в тике, и **ручной «прогнать сейчас»** — у него свой процессный реестр с рубильником, остановка дожидается закрытия), при `SIGKILL` — подметание по порогу без шагов, тем же механизмом, что у оборванного прогона внешнего агента, — и слот исполняется заново ближайшим ретраем. Цена в одну потраченную попытку на деплой принята осознанно. Внутри процесса «не больше одного идущего прогона на рутину» держит замок рутины вокруг решения о запуске: тик и кнопка в одно окно не заводят два `running` с разными ключами; между процессами один бакет по-прежнему сходится по `batch_id`/PK.

### §9.4 Экспорт данных

JSON-дамп всего графа пользователя — одна ручка (`user`-роутер, §9.1) и кнопка в настройках (02-core-os §1.6). Состав дампа: сущности (`entities`), связи (`relations`), треды и сообщения чатов (`chat_threads`, `chat_messages`), настройки (`user_settings`), кастомные аспекты (`aspect_definitions` с непустым `owner_id`) — встроенные аспекты не экспортируются, это не пользовательские данные. **Закреплённые версии тела (`entity_versions`, §4.15) в дамп не входят** — решение ADE-среза 1, а не пробел: версия есть рабочий инструмент владельца («сохрани, пока отдаю запись агенту»), точка возврата внутри живой работы, а не корпус его жизни; текущее тело каждой записи в дампе есть, и восстановить по нему граф можно без снимков. Пересмотр — Future, вместе с повторным импортом. Формат — единый JSON-файл, пригодный и для чтения человеком, и для будущего повторного импорта. При любом будущем CSV-экспорте (Future) обязателен **formula-injection escaping**: значения, начинающиеся с `=`, `+`, `-`, `@`, экранируются, чтобы открытие файла в Excel/Sheets не выполняло произвольную формулу. Экспорт доступен с первого дня слайса 1 — система, претендующая на роль единственного хранилища жизни владельца, обязана иметь выход без ожидания более зрелых итераций.

## §10. Правила проектирования аспектов и записей реестра

Три правила проектирования аспектов, обязательные для всех — встроенных и будущих; каждое выведено из конкретной ошибки v2.2. С реформой к ним добавились три правила проектирования **записей реестра** — они выведены из ошибок, которые реформа и разбирала.

**Правило 1: ограниченные массивы.** Список внутри значения свойства допустим, только если он ограничен по размеру и пишется в рамках одной сессии (сеты одной тренировки: ~5–30 элементов, write-once). Верхняя граница обязательна формой: у списка скаляров это `maxItems`, у списка объектов — тот же кап в схеме (§4.16). Неограниченно растущие во времени ряды — это child-сущности ребром иерархии, не список.

*Обоснование:* JSONB-аспект пишется атомарно — каждое добавление элемента переписывает весь объект (write-amplification), а LWW на уровне API (§5.2) при конкурентной записи выбирает одну версию целиком: параллельные дописывания в массив с двух вкладок/устройств теряют более раннюю из двух правок. *Нарушение в v2.2:* `check_ins[]` внутри аспекта привычки — годовой ряд чекинов в одном JSONB: каждый чекин переписывал растущий объект, а чекины, поставленные офлайн на втором устройстве, стирались merge'ем.

**Правило 2: детерминированные ID порождаемых сущностей.** Всё, что система порождает от шаблона по расписанию, получает `id = uuidv5(ORBIS_NAMESPACE, "<template_id>:<дата>")` (точная формула — §5.4).

*Обоснование:* материализация вызывается многократно и конкурентно (открытие Agenda и Budget одновременно, повторный запрос диапазона дат) — при случайных UUID конкурентные вызовы создали бы два разных объекта «один и тот же инстанс на одну дату». Детерминированный ID делает вставку идемпотентной — дубль невозможен по построению, без дедупликации и эвристик, независимо от того, сколько раз материализация была запрошена. *Нарушение в v2.2:* recurring-инстансы со случайными UUID, порождаемые на клиенте офлайн, — дубли платежей и событий после офлайн-работы на двух устройствах.

**Правило 3: производные значения — кэш, не истина.** Стрики привычек, прогресс целей, `spent` конвертов вычисляются из графа (транзакции, чекины, query-агрегации). Хранить их в аспекте можно только как кэш, пересчитываемый при записи затрагивающих сущностей.

*Обоснование:* производное значение, хранимое как истина, неизбежно расходится с источником — правка задним числом или Undo (§7.8) меняют исходные данные в обход кода, который когда-то вычислил кэш. Обязательный пересчёт при каждой записи, затрагивающей источник, держит кэш в согласии с графом. *Нарушение в v2.2:* `streak` хранился в аспекте привычки как авторитетное значение — после sync-merge чекинов на двух устройствах стрик молча показывал неверное число. В v3.1 тот же принцип закрывает `spent` конвертов (§3.5): хранили бы — разъезжался бы с транзакциями при каждой правке задним числом. С реформой у правила появился механизм: свойство-кэш несёт флаг `computed` и `model_writable: false`, то есть «истина где-то ещё» стало проверяемым признаком, а не договорённостью (§4.16).

**Правило 4: у факта один дом** [D43]. Один факт — одно свойство с одним id на всю систему. Два имени одного смысла («категория транзакции» и «категория конверта») — не удобство, а расхождение, которое проявится на первом же запросе поперёк доменов. Заводя свойство, проверяют не «нужно ли мне поле здесь», а «есть ли уже свойство про этот факт»; нашлось похожее — его переиспользуют или сливают, а не заводят второе.

*Обоснование:* до реформы `category_ref` жил в двух аспектах, `currency` — в двух, `grant_id` — в двух, и каждый запрос про них требовал уточнения, каким аспектом спрашиваем. Слияние трёх пар в три свойства убрало не строки кода, а класс вопросов «а по какому из двух считать».

**Правило 5: наборы, а не перечни** [D43]. Условие, перечисляющее значения (`status != done && status != cancelled`), обязано жить **одним именованным набором**, на который ссылаются потребители, а не копией в каждом. До реформы «незакрытая работа» была написана семью разными местами в двух зонах кода, и разъехаться им ничто не мешало. Механизм именованных наборов приезжает с контрактами (часть Б); в срезе А правило действует как **дисциплина проектирования**: новое перечисление значений — повод спросить, не набор ли это.

**Правило 6: расширять словарь — только формой, которая понадобилась дважды** [D43]. Новый `kind` типа, новый шаблон, новое поле декларации заводятся, когда форма встретилась **≥ 2 раза** или когда она generic по построению (ограничение роли `target_max_incoming` — про любую роль, а не про конверты). Под один случай новый kind не заводят: он и есть второй язык, который потом придётся понимать всем.

*Обоснование:* словарь типов свойств закрыт (§4.16) не из бедности, а потому что открытый словарь — это генератор частных случаев: у каждого свой рендер, свой валидатор и своя строчка в промпте.

## §11. Приложение: проверка масштабируемости

Три домена прогнаны через модель данных v3.1 — ядро (слои сущности, relations, query-движок, персистентность и конкурентность §5) не потребовало изменений ни в одном случае. Два из трёх (фитнес, привычки) остаются будущими; третий, цели, реализован в слайсе 3 — и §11.3 из проверки на бумаге стал описанием работающего кода.

### §11.1 Фитнес

```
Программа «База 3×/нед»            (entity + orbis/fitness-program)
 ├─ subitem ─→ День A: грудь/трицепс   (orbis/workout-plan:
 │              упражнения — ограниченный массив, правило 1)
 │              └─ instance-of ──→ Тренировка 2026-06-09
 │                                  (orbis/fitness: фактические сеты
 │                                   + orbis/schedule: когда была)
 ├─ subitem ─→ День B: спина/бицепс
 │              └─ instance-of ──→ Тренировка 2026-06-11 ...
 └─ subitem ─→ День C: ноги
```

Сеты тренировки — массив внутри `orbis/fitness`: ограничен (десятки элементов) и пишется в одной сессии — правило 1 соблюдено. Каталог упражнений — клиентский JSON + кастомные упражнения как сущности. Ядру нужны только записи в реестре (`orbis/fitness-program`, `orbis/workout-plan`, `orbis/fitness`) и view.

### §11.2 Привычки

```
Привычка «Зал 3×/нед»   (orbis/habit: тип, frequency,
 │                       streak — КЭШ (правило 3),
 │                       auto_source: {query})
 ├─ subitem ─→ Чекин 2026-06-09   id = uuidv5(NS, habit_id + ":2026-06-09")
 ├─ subitem ─→ Чекин 2026-06-11   id = uuidv5(NS, habit_id + ":2026-06-11")
 └─ subitem ─→ Чекин 2026-06-13   ...
```

Чекины — child-сущности (неограниченный ряд — правило 1), с детерминированными ID (правило 2), стрик — кэш, пересчитываемый из чекинов (правило 3). **Авто-чекин из графа**: `auto_source` — сохранённое дерево запроса (например `aspect=orbis/fitness, orbis/start_at=today` в печатной форме); непустой результат автоматически зачитывает привычку за день — тренировка закрывает «зал 3×/нед» без ручного чекина. Это была бы новая точка вызова компилятора (§6.3) — домен остаётся будущим, и в списке потребителей его нет.

### §11.3 Цели — реализовано в слайсе 3

```
Цель «Накопить 300 000 ₽»   (orbis/progress_source: {
 │                             query: {filter: {and: [
 │                               {aspect: "orbis/financial"},
 │                               {prop: "orbis/direction", op: "eq", value: "income"},
 │                               {tag: "savings"}]}},
 │                             aggregate: "sum",
 │                             field: "orbis/amount"
 │                           },
 │                           orbis/current_value — КЭШ (правило 3),
 │                           orbis/target_value: "300000")
 └─ ребро роли mention ──→ сущности-вехи, заметки
```

Прогресс цели = дерево запроса (§6) + агрегация: `aggregate: "sum" | "count" | "latest"`, агрегируемое свойство — отдельным ключом `field` (для `sum` и `latest`; при `count` ключ `field` **запрещён** — нормативная схема §3.11). «Прочитать 24 книги» — `aggregate: "count"`; «вес 80 кг» — `aggregate: "latest", field: "user/weight"`. `orbis/current_value` — кэш по правилу 3. Честное ограничение: агрегация `max` **внутрь** JSONB-массивов (цель «жим 100 кг» по сетам внутри тренировок) — за скоупом этого механизма (§12); такой цели потребуется либо вынос рекордов на уровень полей аспекта, либо расширение движка.

**Как это работает в слайсе 3** (`apps/server/src/goals/progress.ts`):

- **Считает сервер, на каждом чтении.** `entity.get` сущности с `orbis/goal` дополняет ответ полем `goalProgress` (`current`, `target` — и только они). Числа — decimal-строки от начала до конца, готовой доли в ответе нет: процент выводит клиент, точно, из тех же строк (02-core-os §3.5), потому что `floor(доля × 100)` на числе с плавающей точкой врёт (0.29 × 100 = 28.999… → «28 %»). Кэш `current_value` при этом **не пишется**: `entity.get` остаётся чтением, единственный путь мутаций — исполнитель (§9.2). Правило 3 §10 этим не нарушено — оно разрешает кэш, а не обязывает к нему.
- **Fail-soft, а не исключение.** Беда источника — неразобранный запрос, ненайденное или нечисловое поле, `children_of=this` вне контекста, отказ самого SQL — отдаётся полем `unsupported` с одним из четырёх значений (`array_field`, `invalid_query`, `invalid_field`, `compute_failed`), и сущность остаётся открываемой. Иначе цель со сломанным `progress_source` нельзя было бы починить: чинят её, открыв. Пустая выборка отказом не считается — это честный ноль (§6.4).
- **Без материализации повторяющихся.** Запрос исполняется напрямую, мимо материализации инстансов (§5.4), потому что та ПИШЕТ в граф. Следствие честное: экземпляры повторяющейся задачи или платежа, ещё не материализованные ничем другим (списком, бюджетом, повесткой), в прогресс не попадают.
- **Представление — только detail-экран** (02-core-os §3.5 п. 3): полоса на вкладке «Сущность», над телом записи, — а не карточка аспекта на «Деталях»: у цели прогресс это то, ради чего её открывают. В строках списков прогресса нет — отступление от буквы D22, оформленное отдельным решением **D23** (04-decision-log).

### §11.4 Вывод

**Ядро не меняется: новый домен = записи в реестрах + подписки поверхностей.** Слои сущности, роли рёбер, детерминированные ID (§5.4), канон запросов и контракт тулов покрывают все три домена в текущем виде; правила §10 предотвращают известные по v2.2 ошибки на этапе проектирования. С реформой «записи в реестрах» стало точнее, чем «записи в реестре аспектов»: домен приносит свои **свойства**, свои **аспекты** и, если ему нужны свои связи, свои **роли рёбер**. Вторая половина формулы — **подписки** вместо «+ view»: поверхность узнаёт о новом домене декларацией, а не своим экраном. Это **часть Б**; в срезе А новый домен по-прежнему въезжает записями реестров плюс, при необходимости, кодом поверхности.

Слайс 3 проверил тезис на практике одним из трёх доменов: цели приехали записью в реестре (§3.11) плюс расчётом поверх существующего query-движка — новых таблиц, миграций и узлов грамматики не потребовалось. С поправкой, которую честнее назвать, чем спрятать: **view не понадобился вовсе** (D22), и «+ view» в формуле оказался не обязательной половиной, а опцией.

## §12. Известные ограничения

Фиксируются честно — это осознанные компромиссы, а не упущения.

1. **Тяжёлая аналитика поверх JSONB** — не сильная сторона модели: сложные агрегации по полям аспектов (по месяцам × категориям × годам) упираются в JSONB-извлечение. Клапан: декларация `aggregations` в реестре аспектов (§4.3) как точка будущей материализации, без изменения модели данных.
2. **Офлайн-правки недоступны.** Офлайн покрывает только буферизованный ввод (retry-буфер fast-path-create, §5.3) и кэш чтения (server-state-кэш, §5.1); открытие уже загруженных данных работает, правка существующих сущностей и LLM-путь — нет.
3. **Две вкладки/устройства, правящие один и тот же `body`, — optimistic-check с отказом, не merge** (§5.2): проигравшая правка не теряется молча — она отклоняется структурированной ошибкой и требует перезагрузки и повторного ввода вручную.
4. **Полный offline-first отложен осознанно** (см. `04-decision-log.md`, D1) — сознательный компромисс ради быстрого выхода в продакшен под реальную среду владельца (телефон + ноут, почти всегда онлайн).
5. **Семантический поиск отсутствует** — только full-text (`search=`, GIN по title + body). «Найди заметку, где я думал про смену работы» работает по словам, не по смыслу — до добавления embeddings (Future Directions, 00-product.md).
6. **`max`-агрегации внутрь JSONB-массивов** (личные рекорды из сетов внутри тренировок) — вне механизма целей (§11.3): `progress_source` агрегирует поля сущностей, но не элементы массивов внутри аспектов. Ограничение осталось в силе после реализации слайса 3 и там же названо вслух: цель с полем вида `sets[].weight` отвечает флагом `unsupported: 'array_field'` — отдельным от «поле не найдено», чтобы осознанное ограничение не выглядело опечаткой пользователя.
7. **Снято реформой D43.** Ограничение звучало «поле `orbis/budget.limit` затенено reserved-ключом грамматики `limit`». Namespaced key снял его по построению: `orbis/limit>1000` — свойство, `limit=20` — параметр проекции, и различает их слэш, а не порядок правил резолва (§6.1).
8. **Кавычки не «гасят» относительные date-токены** — литеральное строковое значение `today`/`overdue`/`next_7d`/`after_7d` в поле типа date/timestamp невыразимо. Для встроенных аспектов коллизий нет; для будущих кастомных аспектов — пересмотреть лексику кавычек до их появления.
9. **`relation_delete` последнего ребра роли `instance-of` не ре-валидирует §3.3 target-сущности** — достижима «сирота» с `orbis/recurring=true` без `orbis/recurrence` и без ребра происхождения; симметрично — attach `orbis/financial` к сущности с ранее накопленными привязками к конвертам. Точка enforcement — запись аспекта; следующая правка сущности упрётся в INVARIANT. Снятие — вместе с recurring-материализацией слайса 2.
10. **Снято реформой D43.** Ограничение перечисляло щели реестра, недостижимые в MVP: не валидируется формат id и имён полей, правила коллизии builtin/custom расходятся между резолвом и валидатором, merge-семантика `null` асимметрична. Реформа закрыла их не чек-листом, а устройством: форма `key` проверяется регуляркой при записи, уникальность — четырьмя partial-индексами (§4.9), снятие значения выражено отдельным списком `unset` вместо `null` (§9.2), а правки владельца поверх системных определений живут дельтами, а не переписыванием строки (§4.16).

11. **Границы канона запросов — осознанные** [D43]. Q отвечает на вопрос «какие сущности подходят», и за его границей по построению остались: соединение двух свободных сущностей («задачи, у которых есть транзакция дороже их оценки»), агрегатные предикаты («проекты, где больше пяти незакрытых задач»), обход **сразу по нескольким ролям** одним предикатом, пути и циклы как результат (а не как отказ), сходство и семантическая близость. Это не долг: попытка выразить их в том же языке превратила бы предикат в подзапрос, а разбор при сохранении — в невозможный. Запросы за границей получают **отказ с кодом** (`QUERY_JOIN`, `QUERY_MULTI_ROLE`), а не молчаливую пустоту, и по коду видно, что делать: подняться на уровень выше — вычисляемым свойством, ведомостью подписки или отдельной ручкой движка.

12. **Граница языка выражений — часть Б, и она названа заранее.** Язык, на котором будут писаться правила, условия показа и формулы ведомостей, тотален по построению: в нём нет циклов, пользовательских функций, функций высшего порядка, ввода-вывода, недетерминизма и самоссылки, а разыменование ссылки — ровно на один шаг. Всё, чему нужно «если/пока/подумать», — это рутина (§9.3), а не выражение. **Часть Б; в срезе А не реализовано** — но граница записана здесь, чтобы её не пришлось двигать под первый неудобный случай.

## §13. Приёмочные проверки критических инвариантов

1. **Optimistic-check body:** два клиента читают сущность, оба правят `body`. Поздняя (по прибытии на сервер) правка со stale `updated_at` отклоняется структурированной ошибкой (§5.2); после перезагрузки сущности и повторной правки — правка проходит успешно.
2. **Идемпотентность досылки:** повторная отправка `entity_create` с тем же client-generated UUID (например, из retry-буфера, §5.3, после разрыва соединения на середине ответа) не создаёт дубль и возвращает исходный результат первой успешной попытки.
3. **Один entity-тред:** два клиента одновременно впервые пишут в тред одной и той же сущности (например, владелец с телефона и повторный запрос упавшей вкладки). Существует ровно одна строка `chat_threads` с детерминированным ID (§4.5, §5.4) — оба сообщения оказываются в ней; конфликт гасится уникальным индексом на уровне БД, а не логикой клиента.
4. **Атомарный batch:** в batch из трёх операций вторая не проходит валидацию. Не применяется ни одна операция и не создаётся action. Повтор успешного batch с тем же `batch_id` не меняет данные второй раз и возвращает исходный результат.
5. **RLS чатов и связей:** пользователь B не может прочитать или вставить `chat_messages` в тред пользователя A и не может создать ребро, где хотя бы одна сущность принадлежит A; запросы отклоняются политикой БД, а не только API. Предикат политики связей от перехода на роли не изменился — он и раньше спрашивал про владельцев обеих сущностей, а не про тип связи.
6. **Decimal:** операции `0.10 + 0.20`, carryover `-0.10` и сравнение `orbis/amount=0.30` дают точный результат `0.30` в PostgreSQL; точность проверяется в БД и в persisted JSON — IEEE-754 значения там отсутствуют.
7. **Одна привязка к конверту:** конкурентные попытки привязать финансовую сущность к двум конвертам дают максимум одно живое ребро роли `envelope-binding` — это ограничение `target_max_incoming: 1` в строке реестра ролей (§4.2), а не отдельное правило про budget-parent'ов [D43]; проигравший вызов получает структурированную ошибку или выполняет атомарный перенос, частичного состояния нет.

Новые пункты приехали с реформой (D43). Часть из них — приёмка среза А, часть описывает норму, которую исполняет часть Б; где так — сказано прямо.

8. **Паспорта родов заполнены:** у каждого рода кирпичиков (запрос, вычисляемая величина, ограничение, преобразование, представление, выражение, паттерн) названы граница, «за границей → куда», гарантии, обратимость и способ приёмки. **Норма спеки реформы; кодом не проверяется** — это дисциплина проектирования, а не тест.
9. **Покрытие без пустых клеток:** каждое место системы, которое реформа затрагивает, отнесено к роду и к правилу — пустых клеток в таблице покрытия нет. **Норма спеки; пересчёт числа мест — открытый вопрос владельцу.**
10. **Канонические отказы:** у каждого класса невыразимого — свой код и своя фикстура, красная до валидатора и зелёная после, с мутационной проверкой. **Полный набор — часть Б**; в срезе А заведены и покрыты фикстурами шесть: запись вычисляемого свойства, системная роль из тула, нестатическая область, соединение, обход по нескольким ролям, нерегулярный паттерн.
11. **Граф зависимостей строится и проверяется** на каждой записи в реестр; цикл деклараций — отказ. «Кто на этом свойстве стоит» читается из графа, а не из рукописного списка: именно поэтому вопрос «что сломается, если я это скрою» имеет ответ.
12. **Консервативность:** пользовательская декларация, не трогающая встроенные контракты, не меняет ни одного результата встроенных поверхностей — проверяется снимками четырёх состояний реестра. **Часть Б** (снимки поверхностей приезжают вместе с подписками).
13. **Обратимость по шаблонам:** у каждого преобразования есть golden «применить → отменить → байт-в-байт». В срезе А это исполнено для правки значений и для слияния свойств; остальные шаблоны — вместе с каталогом правил (часть Б).
14. **Один язык:** ноль строковых формул вне канонического JSON-дерева выражений в сидах и реестрах — проверяется греп-гейтом. **Часть Б** (язык выражений); греп-гейт на старые формы запросов работает в срезе А.
15. **Тьюринг-тест наоборот:** попытка выразить цикл, самовызов, рекурсию или ветвление любым кирпичиком отвергается валидатором. **Часть Б.**
16. **Операция реестра атомарна и откатывается одним undo:** слияние свойств — одно действие с одним inverse; частичного слияния не бывает.
17. **Мутация реестра не бывает молчаливой** ни для какого актора — проверяется тестом на каждый путь: чат, рутина, MCP, сид (§7.10).
18. **Версия реестров монотонна и согласована:** любая мутация реестров владельца инкрементирует версию в **той же транзакции**; кеши — реестра, агрегатов, промпта — смену версии не переживают.
